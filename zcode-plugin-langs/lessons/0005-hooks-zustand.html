第 5 课：Hooks + Zustand——一条消息的状态之旅

目标：学完这课，你能说清"输入一句话 → 界面出现流式回复"完整的状态流转， 并理解 useStore.ts 为什么是前端的"协议中枢"。

一、为什么需要全局状态（不用 useState 逐层传）

如果每个组件自己 useState 存消息列表，那么：子组件改完状态，父组件不知道； 兄弟组件要同步得把回调传成"回调地狱"。所以本仓库用 Zustand 建一个 "前端唯一的真相源"：所有状态放 store，任何组件都能读、任何 action 都能改。

二、Zustand 三件套（useStore.ts 开头）

import { create } from 'zustand'

interface StoreState {
  // 连接
  connectionStatus: ConnectionStatus
  lastError: string | null
  // 会话 / 消息 / 流式 / 模型 / 额度 / 用量 ...
  messages: ZCodeMessage[]
  streaming: boolean
  ...
  // actions（改状态的函数也声明在接口里）
  init: () => void
  sendMessage: (text: string) => void
  ...
}

export const useStore = create<StoreState>((set, get) => ({
  connectionStatus: 'connecting',      ← 初始值
  messages: [],
  streaming: false,
  ...
  sendMessage: (text) => { ... set(...) },   ← action 里用 set 改状态
}))

三个 API 背熟：

API作用仓库实例
create<T>((set, get) => ({ ... }))建 store：初始状态 + actions 一把梭useStore.ts L113
set(partial)合并更新状态（类似 setState）sendMessage L201-205
get()读取当前最新状态（action 内部用）sendMessage 第一行 get().currentSessionId

三、组件怎么读：selector 模式

// WaitingIndicator 里：只订阅需要的字段，字段变了才重渲染
const currentModel = useStore((s) => s.currentModel)
const messages = useStore((s) => s.messages)

// App.tsx 里：整个 store 一把梭（简单但每次任何字段变化都重渲染）
const { sessions, messages, streaming, sendMessage } = useStore()

selector（(s) => s.xxx）是 Zustand 的订阅粒度控制：选得越细，重渲染越少。 评审提示：高频更新的字段（如 messages、streaming）尽量用细粒度 selector。

四、一条消息的状态之旅（sendMessage 精读）

sendMessage: (text) => {
  const sid = get().currentSessionId
  if (!sid || !text.trim() || get().streaming) return    ← 防御：无会话/空文本/已在流式

  set({
    streaming: true,                                     ← ① 进入流式状态
    streamingMessageId: null,
    waitingSince: Date.now(),                            ← 计时起点（WaitingIndicator 用）
    lastError: null,
  })

  // 确保已订阅（规格书 §4：先 subscribe 再 send，否则丢事件）
  sendToJava({ op: 'subscribe', sessionId: sid, ... })   ← ② 先订阅（防丢事件）
  sendToJava({ op: 'send', sessionId: sid, text, ... })  ← ③ 再发送（IPC 见第 6 课）

  // 本地把用户消息立即加入列表（不等 reload，体验更快）     ← ④ 乐观更新
  const userMsg: ZCodeMessage = { info: { role: 'user', time: { created: Date.now() }, id: `local_u_${Date.now()}` }, parts: [{ type: 'text', text }] }
  set((s) => ({ messages: [...s.messages, userMsg] }))
},

状态机（文件头注释里写的流式生命周期）：

sendMessage → subscribe（确保不丢事件）→ send → turn.started
→ model.streaming（累加 delta）→ tool.updated（更新状态）
→ turn.completed/failed → 重新拉 messages（确保数据一致）

关键设计：事件来了不直接拼消息，而是等 turn.completed 后重新拉全量 messages—— 因为增量拼装容易漏（部分事件可能丢失），全量拉取保证最终一致。这是流式 UI 的经典取舍。

五、事件入口：handleStreamBatch（批量合并）

第 2 课讲过 Java 端 16ms 节流合并，前端对应（L560 附近）：

// 批量流式事件（Java 端 16ms 节流合并）：一次处理整批，只 set 一次
onStreamBatch((sid: string, events: StreamEvent[]) => handleStreamBatch(sid, events, set, get))

// 单事件兜底（mock 模式 + Java 端关键事件走 streamEvent 单推）
onStreamEvent((sid: string, event: StreamEvent) => handleStreamEvent(sid, event, set, get))

两条订阅通道：批量通道（生产，高频 delta 合并）+ 单事件通道（mock 开发模式与关键事件兜底）。 这是"开发体验"与"生产性能"分离的典型做法——第 7 课跑 mock 时会直接体会到。
