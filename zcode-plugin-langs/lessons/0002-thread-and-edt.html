第 2 课：线程与 EDT——插件并发模型

目标：学完这课，你能解释为什么本仓库 Kotlin 端所有 UI 操作都包着 invokeLater，并在评审代码时一眼看出线程违规。

思考题：你觉得本仓库 Kotlin 端用的并发模型是？

一、先纠正一个直觉：本仓库没有协程

很多 Kotlin 教程上来就讲协程，但本仓库 grep kotlinx.coroutines 零结果。 实际模型是：

  • 协议客户端（ZCodeProtocolClient）：阻塞 IO + 回调（subscribe(sessionId, onEvent = { ... })）
  • UI 面板（ZCodeToolWindowPanel）：收到回调后，用 invokeLater 跳回 UI 线程再操作界面

这个模型足够支撑本插件的并发需求。课程最后会讲"如果未来要引入协程怎么映射"。

二、EDT 铁律（IntelliJ 平台的宪法）

只有 Event Dispatch Thread（EDT）可以读写 UI 组件。 后台线程（协议回调、子进程输出、定时器）想碰 UI，必须把任务"扔"回 EDT 执行。

为什么？Swing/IntelliJ 的 UI 组件不是线程安全的，允许并发操作会带来 不可复现的崩溃和卡死。平台文档称之为 Threading Model——本课主源。

三、回 EDT 的两种写法（本仓库都在用）

写法出处区别
SwingUtilities.invokeLater { ... }ZCodeToolWindowPanel.kt L136/230/978JDK 自带，任意线程可调
com.intellij.openapi.application.invokeLater { ... }ZCodeToolWindowPanel.kt L609/636/658IntelliJ 版：线程安全 + 支持 ModalityState（模态窗口下也排队执行）

两者都是"把任务塞进 EDT 队列，EDT 空闲时执行"。评审提示：调用 invokeLater 时闭包捕获的对象，其字段必须可见性安全（本仓库用 @Volatile 或不变对象）。

四、真实案例精读：协议消息 → 打开编辑器

前端点"在编辑器打开文件"，Java 侧收到协议消息后处理（ZCodeToolWindowPanel.kt handleOpenFile，L609 附近）：

/** op=openFile — 在 IDEA 编辑器打开文件（支持行号定位）*/
private fun handleOpenFile(msg: JsonObject): JsonObject {
    val filePath = msg["filePath"]?.jsonPrimitive?.content
        ?: return errorResponse("缺少 filePath")
    val line = msg["line"]?.jsonPrimitive?.content?.toIntOrNull()
    com.intellij.openapi.application.invokeLater {          ← 回 EDT：下面是 UI 操作
        val vfile = LocalFileSystem.getInstance().findFileByPath(filePath)
        if (vfile != null) {
            val editor = FileEditorManager.getInstance(project).openFile(vfile, true)
            if (line != null && line > 0) {                  ← 行号定位
                val selected = FileEditorManager.getInstance(project).selectedTextEditor
                if (selected != null) {
                    val offset = selected.document.getLineStartOffset(
                        minOf(line - 1, selected.document.lineCount - 1)
                    )
                    selected.caretModel.moveToOffset(offset)
                }
            }
        } else {
            log.warn("打开文件失败：文件不存在 $filePath")
        }
    }
    return buildJsonObject { put("op", "fileOpened") }
}

要点拆解：

  • 这个函数本身运行在协议线程（app-server 消息处理循环），所以打开编辑器这类 UI 操作必须包 invokeLater——不包就会"Wrong thread access"报错或随机崩溃。
  • invokeLater 是异步的：函数先返回 fileOpened 响应给前端，编辑器稍后打开。UI 的最终效果是"尽力而为的延迟"。
  • minOf(line - 1, lineCount - 1) 防越界——底层 API 边界处理是评审时最容易漏的点。

五、流式推送：三层瓶颈与 16ms 节流

这是本仓库踩坑最深的并发场景（L68/L890 附近有专门注释）。流式事件（模型每 token 一个 delta）会导致：

瓶颈现象对策（已实现）
EDT 队列积压每次 delta 都 executeJavaScript 推给前端，高频时 UI 卡死先缓冲，每 16ms（60fps）合并成一批推送
日志风暴每个 delta 打一行日志，日志面板爆炸合并后只打批次日志
React 重渲染风暴前端每个事件 set 一次状态，整棵树重渲染前端 onStreamBatch 一次处理整批、只 set 一次

评审提示："高频小事件"是线程模型的头号敌人——先合并再跨线程，是通用原则。

六、对照：如果未来引入协程

本仓库的"线程 + 回调 + invokeLater"可以无痛升级为协程，映射关系：

现在的写法协程写法
回调 onEvent = { ... }suspend fun + 挂起接收
invokeLater { ui() }withContext(Dispatchers.Main / EDT) { ui() }
阻塞 request(...)withContext(Dispatchers.IO) { request(...) }
缓冲 16ms 合并Channel + consumeEach 或 buffer 算子

需要时再看 官方协程指南，本课不展开。
