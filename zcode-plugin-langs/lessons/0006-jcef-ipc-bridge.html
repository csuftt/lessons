第 6 课：JCEF IPC 桥——React 和 Java 怎么打电话

目标：学完这课，你能画出一条消息从 React 按钮 → Java handler → 流式事件 → 回到 React 的完整路径， 并读懂 bridge.ts 与 ZCodeToolWindowPanel.kt 的对应关系。

一、为什么需要 IPC 桥

React UI 跑在 JCEF（IntelliJ 内置的嵌入式 Chromium）里，和 Kotlin 端不在同一个 进程/上下文。两端通信只有两条官方通道（文件头注释 L40-48）：

方向通道仓库实现
JS → JavaJBCefJSQuery（官方推荐，签名稳定）前端调 window.sendToJava(jsonStr)
Java → JSexecuteJavaScript(...)（直接执行 JS）Java 调 window.zcodeBridge.onMessage(obj)

二、JS → Java：注入的"动态函数名"问题（bridge.ts 精读）

// ============ 全局类型声明 ============
declare global {
  interface Window {
    /** Java 注入：JBCefJSQuery 动态函数（发送消息到 Java） */
    __ZCODE_CEF_QUERY__?: (args: {
      request: string
      persistent?: boolean
      onSuccess?: (r: string) => void
      onFailure?: (e: string) => void
    }) => void
    /** 兼容：旧版直接挂到 window 上的 sendToJava */
    sendToJava?: (msg: unknown) => void
    /** Java → JS 回调入口 */
    zcodeBridge?: { onMessage: (msg: unknown) => void }
    ...
  }
}

关键难点（注释里写得很清楚）：JBCefJSQuery 创建时生成的 JS 函数名是 运行时动态的（如 cefQuery_1015760238_1），不能硬编码。 所以 Java 端注入页面时把它赋给固定全局变量 __ZCODE_CEF_QUERY__。 TS 的 declare global 就是给这些"Java 塞进来的窗口属性"写类型声明—— 类型契约跟着代码走，两端才不会对不上。

三、Java → JS：字符串转义陷阱（ZCodeToolWindowPanel.kt 精读）

Java 往 JS 推消息是"拼一段 JS 代码字符串"：

// L318 附近的注释（原样保留）：关键：executeJavaScript 的 JS 代码里，
// 我们构造一个 JS 字符串字面量
val js = "window.zcodeBridge.onMessage(${jsonText})"

如果 jsonText 里含 "、\、换行，拼出来的 JS 直接语法错误——所以 任何经 executeJavaScript 传的字符串必须做 JSON 转义（这就是为什么注释强调 "构造 JS 字符串字面量"）。这是 JCEF 通信第一坑：不是网络协议，是代码注入。

另外（L229 附近注释）：注入必须在 UI 线程执行——这呼应了第 2 课的 EDT 铁律： executeJavaScript 是 UI 操作。

五、开发模式：没有 JCEF 怎么办（mock）

bridge.ts L13-15 注释：开发模式（localhost:5173）没有 JCEF，走 isInJcef() 检测后改用 mock 响应，方便纯前端调试。两条通道并存：

  • 生产：JCEF 注入 → 真 Java 桥
  • 开发：vite dev server → mock（伪造 Java 响应）

这就是为什么 store 的订阅要分"批量通道 + 单事件兜底通道"（第 5 课）——mock 模式只能走单事件通道。
