大模型的参数与缓存：一次调用的全链路

模型卡上写着 7B，下载下来却是 15GB；标着 4bit 的量化版，显存却没省到四分之一；同一段系统提示词反复发，账单却能差五十倍。这篇把参数怎么来、怎么压、怎么进显存、怎么被一次调用流过去、又怎么靠缓存把账压下来串成一条线——从训练机房一路走到你的 API 账单。

01场景：四个卡住的地方

用大模型的人，几乎都在这四句话上卡过：

一：数字对不上。下载 Qwen2.5-7B，模型卡写 7B 参数，下完占盘约 15GB——差一倍，是不是下多了？

二：不敢说真话。跟 AI 助手聊了一下午工作上的事，突然想到：这些对话会被"学"进模型吗？

三：量化没省到位。换了个标着 4bit 的量化版，指望显存降到四分之一，结果一跑还是显存不足。

四：账单看不懂。同一段系统提示词天天发，有一天换了个写法，费用突然涨了几十倍；而且不管怎么算，输出永远比输入贵。

这四个困惑其实分属一条链路上的四个站点：训练、部署、推理、访问。把它们连起来看，四个问题会一起变得可算。

02全链路：一条请求穿过四个站点

1

训练

数据 → 梯度 → 调参数

参数诞生的地方

2

部署

量化 → 权重进显存

参数变成能服务的形态

3

推理

Prefill → Decode

参数被逐层读取，产生激活值

4

访问

API 计量 → 计费

谁便宜、谁贵，在这里结算

这条线上有两类东西要一直分清：

  • 参数（parameter）：训练学出来的浮点数，训练完就冻结。它决定"模型有多大、显存要多少、下载多大"。
  • 激活值（activation）与缓存（cache）：请求经过时产生的中间结果。它随请求生、随请求灭，决定"这一次跑得多快、花多少钱"。

一句话概括全片：参数是电路，请求是电流——电流流过去，不会留下来；而整条链路上所有省钱的手段，都是在"如何少读一遍参数、少算一遍激活值"上做文章。

03训练：参数是怎么来的，B 又是什么

一个参数就是一个浮点数。训练开始时它们是一堆随机数；训练做的事，是拿海量文本反复走三步：

1

前向

读一遍参数算预测

一个字接一个字往下猜

2

算损失

预测与真实差多少

差得越多，要改的劲越大

3

反向 + 更新

梯度指出该往哪调

这才是"写进参数"的唯一时刻

B 是 billion（十亿）的缩写：7B 就是约 70 亿个这样的数字。训练结束，这批数字冻结、打包成权重文件发布——之后同一个模型服务一万个人，参数永远只有一份，谁调 API 都改不动它。

70 亿个数字并不均匀。以 Qwen2.5-7B 的官方配置实算（隐藏维度 3584、28 层、词表 152064、前馈维度 18944）：

训练那本账大得反直觉。混合精度 Adam 训练时，除了权重本身，还要养梯度和优化器状态：ZeRO 论文（arXiv:1910.02054）的原文分解是 2Ψ+2Ψ+KΨ=16Ψ 字节——每个参数 16 字节，是推理权重的 8 倍。所以 7B 训练要 7.6B × 16 ≈ 122GB，单张 80GB 的 A100 都放不下。

⚠
只有训练会写参数，推理一个数字都不改

"聊天被学进模型"只在训练时发生。你调 API 的那些话，走的是推理路径——参数冻结、只被读取。至于厂商会不会把你的数据收进下一轮训练语料，那是另一个离线过程，看你用的服务条款

顺带记一个数字：训练每一步的计算量约是 6 × 参数量（前向 2N、反向 4N，缩放定律论文的口径），也就是 7B 模型每训练一个 token 约 450 亿次浮点运算——比推理贵三倍。

04部署第一刀：量化，把每个数字压窄

参数量决定"有多少个数字"，量化决定"每个数字占多宽"。模型通常以 bf16（16 位浮点）发布，每参数 2 字节；量化把它压到更窄的格式：

精度每参数字节8B 模型权重7.6B 实算
bf16 / fp16（发布常态）2 字节约 16GB15.2GB
FP8 / INT81 字节约 8GB7.6GB
INT4（GPTQ / AWQ 等）0.5 字节约 4~5GB3.8GB 起

这张表的尺度来自 Hugging Face 官方文档的原话：8B 模型 bf16 约 16GB、8 位约 8GB、4 位约 4~5GB，并明确"位越少，精度损失越大，每种方法在显存、速度、精度之间权衡不同"。主流路线是 weight-only 量化——只压权重，计算时再反量化，所以省的是显存，不是算力。

⚠
标着 4bit，显存不一定省到四分之一

HF 文档明确写了：大多数 GGUF 模型加载时会被反量化回全精度，占的显存和未量化模型一样多。所以看量化版别只看标称位宽，要看你用的运行时是不是真的保住了压缩格式（如 llama.cpp 的 GGUF、vLLM 的 AWQ/GPTQ 内核）

压窄之后，权重能塞进什么卡也变得可算：

  • 7B INT4（3.8GB）+ KV 缓存：一张 8GB 消费级卡就能跑起来，24GB 卡能撑较高并发。
  • 70B INT4（约 35GB）：单张 40GB 卡勉强，通常要两张卡做张量并行（把计算拆到多卡上）。
  • 70B bf16（约 140GB）：单卡装不下，必须多卡切分，或者干脆放弃全精度推理。

注意，量化省的是显存，速度不一定变快。Hugging Face 文档的原话是：weight-only 方法省内存但不一定更快，因为反量化给每次矩阵乘都加了活；它只在显存受限的场景（也就是一次只生成一个词元的解码阶段）才划算——那时读 4 位权重只搬 bf16 四分之一的字节，省下的搬运时间盖过了反量化的开销。

代价：输出质量到底掉多少

量化不是免费的，而且根源是结构性的。Hugging Face 文档举的数字最直观：int8 只能表示 256 个整数，int4 只有 16 个——一个权重要塞进这 16 个格子里，舍入误差不可避免，任何量化方法都只是"怎么让这个误差别伤到输出"。

位宽可表示值实际影响
8 位256 个整数几乎无损，实践中当全精度用
4 位 + 校准 + 分组16 个整数可做到"精度退化可忽略"——GPTQ 论文对 175B 压到 3~4 位的原话
4 位裸压（无校准）16 个整数明显退化；GPTQ 默认按 128 个权重一组，就是为了缩小误差
2 位及以下4 个整数，不够用开始崩；要靠码本向量量化或量化感知训练（QAT）才勉强可用

为什么 4 位还能"几乎无损"？因为权重不是同等重要。AWQ 论文的结论是："not all weights in an LLM are equally important"，而只保护约 1% 的显著权重，就能大幅降低量化误差——这些显著权重由激活值大小识别出来，缩放后再舍入。所以量化方法的核心竞争点，就是"怎么把那 1% 找出来、怎么分组"。

⚠
损伤不均匀，越难的活掉得越多

日常闲聊、摘要、改写这类任务，4 位量化的差别往往感知不到；但长链推理、数学、代码生成这类"错一步就全错"的任务，对舍入误差更敏感。判断标准只能是自己的评测集：同一批题目，全精度和量化版各跑一遍，比跑分差多少，别只看别人的结论

工程上的三条判断规则：

  • 显存够，首选 8 位：几乎无损，最省心。
  • 要压到 4 位，选带校准的方案：GPTQ（每 128 权重一组、逐列补偿误差）、AWQ（按激活值保护 1% 显著权重）；裸压的 4 位是最差选择。
  • 上线前必做对比评测：用你们的真实任务集跑分，而不是看通用榜单——量化对任务类型高度敏感。

05推理的两个阶段：Prefill 与 Decode

这是理解后面所有优化（KV 缓存、前缀命中、批处理、计费差异）的物理基础。一次生成被切成两段：

Prefill（预填充）

处理你发的那整段话

  • 并行：整段 prompt 一次喂进去算
  • 计算密集：矩阵大、算力吃满
  • 决定 TTFT（首字延迟）
  • 长 prompt 越贵，但可以缓存复用

Decode（解码）

一个词一个词往外蹦

  • 串行：每步只算一个新 token
  • 访存密集：每步都要把权重读一遍
  • 决定 TPOT（每词时间）
  • 输出无法缓存，永远按原价

Databricks 的性能工程文章把这层差异讲得最直白："Generating the first token is typically compute-bound, while subsequent decoding is memory-bound operation."（生成第一个 token 通常是计算受限，后续解码是访存受限。）它还给了一个更能解释真相的结论：预测出词速度时，显存带宽比峰值算力更准——因为 decode 每出一个词，都要把全部权重从显存搬到计算单元附近，算力大量闲置。

整体延迟因此可以直接写成公式：

延迟 = 首字 + 每词 × 词数
# Databricks 原文：latency = TTFT + TPOT × 生成 token 数
# 一段 500 词的输出、TPOT 20ms → 光生成就要 10 秒
# 所以"回答长"不只是字数多，是线性叠加的时间

想让多个请求不排队，就得上批处理：把多个请求拼成一批一起算，吞吐能上去，但每个请求的单体延迟会变长——这就是"高峰期慢一点"的根本原因。Databricks 提到连续批处理（continuous batching）比传统动态批处理吞吐高 10~20 倍，这也是 vLLM 这类引擎的立身之本。

06KV 缓存：让 decode 不重算前文

Decode 是逐词的，算到第 1001 个词时，前面 1000 个词的注意力结果本来要全部重算——KV 缓存（键值缓存）把这些算好的 K、V 向量存起来复用，每步只算新词。Hugging Face 文档的对比很干净：不用缓存，每步注意力成本随序列长度二次方增长；用缓存，降到线性。省的是计算，付的是显存。

⚠
KV 缓存是推理专属，训练时必须关

HF 官方原文："Caching should only be used for inference. It may cause unexpected errors if it's enabled during training."（缓存只该用于推理，训练时开启会出错误）——训练每一步梯度都在变，缓存旧值等于用过期数据

显存怎么算也跟着清楚了：Qwen2.5-7B 用分组查询注意力（4 个 KV 头），每 token 每层存 2 × 4 × 128 个数，28 层合计约 56KB/token，随上下文线性涨、还要乘并发数。128k 上下文就是 7GB 出头。

但缓存本身也要管理，不然会浪费。vLLM 的 PagedAttention 借的是操作系统虚拟内存的思路：把 KV 缓存切成固定大小的块（默认 16 个 token 一块），逻辑块按需映射到不连续的物理块，用一张块表记录映射：

论文里的浪费数字很扎眼：旧系统只有 20.4%~38.2% 的 KV 显存真的存着 token 状态，其余是预分配和碎片造成的空转。PagedAttention 通过"逻辑/物理块分离 + 引用计数 + 写时复制"，既消除碎片，又让多个请求共享同一份前缀块——吞吐因此提升 2~4 倍。

这条"共享前缀块"的能力，就是下一个站点的技术底座。

07缓存命中：前缀一样，就别再算一遍

既然 KV 缓存能存下来、还能跨请求共享，那么自然可以更进一步：把这个请求的前缀算好的 KV 块留着，下一个请求前缀一样，直接拿来用。这就是前缀缓存（prefix caching），各家 API 叫法不同——上下文缓存（context caching）、提示词缓存（prompt caching），机制是同一个。

判断"前缀是否一样"靠哈希。vLLM 的设计文档写得很具体：每个块的哈希 = 父块哈希 + 本块 token + 额外信息（如 LoRA 适配器编号），默认 sha256；只有填满的块才会被缓存（"We only cache full blocks."）。命中后跳过的是重复的 prefill 计算——官方把它叫"almost a free lunch"（近乎白吃的午餐）。

服务商那一层，规则更硬。三家的一手原文：

OpenAIAnthropicDeepSeek
命中条件整个渲染后的前缀必须完全一致；GPT-5.6+ 门槛 1024 个可见输入 token前缀 100% 相同（含图片），按 tools → system → messages 顺序叠加完全匹配一个已持久化的缓存前缀单元，识别多请求的公共前缀
读缓存价格0.1 × 未缓存输入价（GPT-5.6+），部分模型 0.05×0.1 × 基础输入价（部分型号低至 0.025×）输入命中价与未命中价差 30~50 倍
写缓存价格1.25×（30 分钟）/ 2.5×（12 小时）1.25×（5 分钟 TTL）/ 2×（1 小时 TTL）文档未单列写入费
最小可缓存量1024 token（GPT-5.6+）512 / 1024 / 2048 / 4096，按模型而定未公布；文档称 best-effort
保留时间30 分钟（默认）或 12 小时5 分钟（默认，每次读免费续期）或 1 小时几小时到几天，不用即清除

怎么才能命中？三家文档给出的规则惊人一致，而且都是可执行的确定性动作：

  • 稳定内容放最前面：系统提示词、工具定义、参考资料、few-shot 示例放开头；用户这次的具体问题放最后。
  • 追加而不是重写历史：多轮对话里只往后加新消息，别回头改前面的措辞——一改，后面全部失效。
  • 工具定义保持稳定：函数签名挪一下顺序、改一句描述，前缀就变了。
  • 越靠前的层级越要稳：Anthropic 的顺序是 tools → system → messages，靠前的变了，后面全都跟着失效。
⚠
缓存不是保证，是尽力而为

DeepSeek 文档明说缓存是 best-effort，不保证命中；Anthropic 的回溯窗口是 20 个块，超出就找不到；OpenAI 按老模型会把命中数向下取整到 128 token 的倍数。所以别把命中当成必然——它是优化项，不是正确性依赖

08访问：为什么输出永远比输入贵

回到最开始第四个困惑。看 DeepSeek 的公开价目（每百万 token，低谷期）：

模型输入·缓存命中输入·未命中输出
deepseek-flash$0.003$0.15$0.60
deepseek-v4-pro$0.022$0.66$1.98

两个倍数值得记住：

输入命中 vs 未命中：约 30~50 倍。同一段系统提示词，命中时几乎白送，未命中按原价——这就是"换了个写法，账单涨几十倍"的全部原因。

输出 vs 输入未命中：约 3~4 倍。这个差距不是厂商随意定的，它精确对应第五节的两个阶段：

输入 token 便宜

  • Prefill 并行处理，算力吃满
  • KV 能缓存、能跨请求共享
  • 所以能打折，甚至打到 0.1×

输出 token 贵

  • Decode 逐个生成，串行
  • 每步都要把权重读一遍，访存受限
  • 无法缓存、无法并行 —— 只能原价

所以那句"输出比输入贵"不是定价策略，是物理定律的价格化。你想省钱，方向就很明确：

  • 把固定内容做成可命中的前缀，让输入 token 走 0.1× 通道。
  • 让输出短：限制 max_tokens、要求简洁回答、用小模型做摘要——输出是唯一不能打折的部分。
  • 别在对话中回头改前面：一改前缀，缓存全废，账单回到原价。
  • 先分场景定指标：交互式砍首字延迟（缩 prompt / 靠命中），批处理提吞吐（上批处理）。

09规则与坑

⚠
B 是个数，不是字节

7B = 70 亿个参数；文件大小 = 参数个数 × 每参数字节数。bf16 约 15GB，INT4 约 4GB——压的从来不是参数个数，是每个数的存储宽度

⚠
量化省显存，不一定省时间

weight-only 量化在计算时要反量化，decode 阶段位宽变窄能搬得更快，但反量化有开销——要看实测的每词时间，别只看标称位宽

⚠
GGUF 的 4bit 可能白压

HF 文档明确：多数 GGUF 加载时会反量化回全精度，显存占用和未量化一样。用 llama.cpp 这类原生支持压缩格式的运行时才真省

⚠
长上下文吃的是 KV 缓存，不是权重

权重是常量，缓存随"上下文 × 并发"线性涨。128k 上下文的 KV 缓存可以和权重一样大——显存不够先砍上下文或并发

⚠
缓存命中不能当正确性依赖

best-effort、有 TTL、有回溯窗口、按组织隔离。缓存是省钱手段，miss 了必须照样得出正确答案——所有逻辑都该在 miss 时正常工作

⚠
不同模型的 B 不能直接横比

口径有差：含不含嵌入、Dense（稠密）还是 MoE（稀疏混合专家）、量化还是全精度。MoE 要读两个数：Mixtral 总计 46.7B、每 token 只激活 12.9B

10今日带走

  • 参数在训练时被写、推理时只读；B 是参数个数，文件大小 = 个数 × 每参数字节。
  • 量化压的是每个数的宽度：bf16 2 字节 → 8 位 1 字节 → 4 位 0.5 字节；8B 模型 16GB → 8GB → 4~5GB。
  • 推理分两段：Prefill 并行、计算密集（决定首字延迟）；Decode 串行、访存密集（决定每词时间，且是带宽瓶颈）。
  • KV 缓存让 decode 不重算前文；PagedAttention 用 16 token 的块 + 块表管理，旧系统只有 20~38% 的 KV 显存是有效的。
  • 前缀缓存命中的本质：块哈希对上 → 复用 KV → 跳过重复 prefill；靠"稳定内容在前、只追加不改写"提高命中率。
  • 输入能打折（命中 0.1×）、输出永远原价——这不是定价策略，是 prefill 可并行可缓存、decode 不可缓存的价格化。
