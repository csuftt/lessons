git worktree：一个仓库，多个工作目录

切分支的两难人人都遇到过：stash 攒着攒着就失忆，clone 一份又双倍臃肿。worktree 给的是中间档——对象库和分支只有一套，工作目录想要几个开几个。这篇从"为什么需要它"讲到"为什么同一个分支天生不能检出两次"，把这个概念一次吃透。

01场景：改到一半，线上着火

周五下午，你正在 feature/new-checkout 分支改一个跨五个文件的改动，工作区里全是没提交的半成品。这时群里弹出一句话：线上下单失败，需要立刻热修复。热修复要在干净的 master 上做，而你手里这摊东西既不能提交（没写完），又不能丢。

传统答案两个，各有各的难受：

答案一：git stash——把半成品塞进抽屉，切走修完再回来。麻烦在于 stash 是栈：紧急情况往往连环来（修着 master 又被叫去看一个配置问题），两三次 stash 之后，git stash list 里攒了一串 WIP on feature/…，哪个是哪摊事全靠猜；pop 时一旦撞上冲突，你的半成品和切回来的分支变更缠在同一片工作区里，解开比写完还费劲。更常见的是忘——三天后才发现 stash 里还压着东西。

答案二：再 clone 一份——git clone ../repo repo-hotfix，彻底隔离，互不干扰。代价是一个仓库变两个世界：对象库全量复制一份（大仓库动辄上 GB），远端与凭证各配各的，两边各自 fetch 各自漂移，你还得记着哪边是"正身"。用一个仓库的纪律去维护两个仓库，图省事的工具反而制造了新的管理成本。

把两难摆开看：stash 是"一个工作目录上串行切换"，clone 是"两个仓库完全隔离"。真正想要的是中间那档——仓库还是同一个，工作目录多开几个，每个目录安安稳稳待在自己的分支上。这就是 git worktree。

02原理：仓库的本体，与"检出"这件事

要理解 worktree，先拆掉一个习惯性误解：Git 仓库的本体不是那个装着代码的目录，而是 .git 里的对象库和引用库。对象库（objects/）存的是不可变的内容寻址块——每个提交、每棵目录树、每个文件版本都在里面；引用库（refs/）存的是可移动的指针——分支和标签只是"指向某个提交的便签"。至于你眼睛看到的工作目录，它只是某个提交按 HEAD 展开出来的检出快照，配套一个暂存区（index）。

普通的 clone 里，.git 目录和主工作目录是绑死的：一个仓库本体，配一个检出。而 git worktree add 做的事，就是在共享同一个本体的前提下，再挂一个独立的检出：

落到磁盘上是这样的：挂接目录（linked worktree）里没有 .git 目录，只有一个 .git 文件，内容一行 gitdir: …/主目录/.git/worktrees/hotfix，指回主仓库为本检出开的私有目录；HEAD、index 这些"每个检出一份"的数据就存在那里。两边看到的是同一个分支列表、同一套对象——在 ../hotfix 里 fetch，主目录立刻可见；在主目录里建的分支，../hotfix 直接能检出。

主干记住一句话就够：HEAD 和暂存区独立，其余共享。这个模型是 Git 2.5（2015 年 7 月）引入的，早已是官方一等公民，不是什么实验性技巧。

深挖：哪些引用是每个检出私有的？▶ 点击展开

绝大多数引用（refs/heads/、refs/tags/……）全局共享，但有三个例外是每个检出各一份：refs/bisect（二分调试的进度状态）、refs/worktree、refs/rewritten（变基时 --autosquash 改写的备份）。这带来一个实用推论：两个工作目录可以各自跑各自的 git bisect，一边二分线上问题、一边继续开发，互不干扰。跨工作目录访问别人的 HEAD 也有专用语法：main-worktree/HEAD、worktrees/<名字>/HEAD（配合 git rev-parse 用）。日常用不到，知道有这回事即可。

03实战：从创建到合并，走完一个来回

1

建 worktree

worktree add ../hotfix

基准决定从哪分叉

2

新目录里干活

commit / push

主目录半成品不动

3

合回 master

merge 或走 PR

普通分支，照旧合并

4

收尾

remove + branch -d

目录和分支分开收

从什么分支创建：基准规则

git worktree add 的新分支从哪分叉，取决于你写不写基准：

基准的两种写法
git worktree add ../hotfix -b hotfix-1025 master
Preparing worktree (new branch 'hotfix-1025')
HEAD is now at 3d8f21a
git worktree add ../hotfix
Preparing worktree (new branch 'hotfix')

上面带 master 的写法，新分支从 master 分叉；下面省略写法自动建同名分支 hotfix，但基准是当前 HEAD——主目录此刻在 feature 上，它就从 feature 分叉，不是"默认从 master"。延续当前思路开平行工作区时这正合适；热修复这种基准必须明确的场景，把 master 老老实实写全，别赌自己此刻在哪个分支。

开发完，怎么合回主分支

答案出奇地简单：worktree 没有改变 Git 的任何分支模型，hotfix-1025 就是一个普通分支，合回 master 和你日常合并完全一样——两条路任选：

合并的常规两条路
# 路一：本地直接合并（在主目录，或任何检出 master 的地方）
git checkout master && git merge hotfix-1025
Updating 3d8f21a..a91c4e2
Fast-forward
git push
# 路二：在 ../hotfix 目录里推远端，走 PR / MR
git push -u origin hotfix-1025
⚠
git worktree remove 只删工作目录，不删分支

remove 之后 hotfix-1025 依然存在，随时可再检出；确认不要了再 git branch -d hotfix-1025

常见节奏就是开篇那条步骤条：热修复目录里提交 → push → 线上合并（或本地 merge）→ worktree remove 收目录 → branch -d 收分支。

管理命令四板斧

日常管理
git worktree list
G:/proj    3d8f21a [feature/new-checkout]
G:/hotfix  a91c4e2 [hotfix-1025]
git worktree remove ../hotfix
git worktree prune
# 手动 rm -rf 过目录才需要 prune 清账；remove 走的不用

两个补充行为：--detach 检出某个提交而不挂分支，适合考古——把旧版本跑起来复现 bug；add 给的分支名如果已存在，就直接检出那个分支（不新建），这也是并行评审的用法：把同事的分支检出成第二个目录，对照着看代码。目录在移动硬盘或网络挂载上时，git worktree lock 锁一下，防止被 prune 当成废弃条目清掉。

你问我答

主目录在 feature 上，执行省略写法的 add ../x，新分支从哪分叉？

从当前 HEAD——也就是 feature 的最新提交分叉。省略写法的基准永远是"你现在站在哪"，不是 master。想从 master 分叉，就把 master 显式写进命令。

在 ../hotfix 里开发完，这些改动怎么进 master？

把 hotfix-1025 当普通分支处理：主目录 checkout master 后 merge hotfix-1025，或者直接 push -u origin hotfix-1025 走 PR。worktree 没有引入任何新的合并机制。

remove 掉工作目录后，那个分支还在吗？

在。remove 只收走目录，分支原样保留——这是刻意设计：目录是一次性的，分支是资产。确认分支也不要了，再 git branch -d 删。

04规则与坑：为什么同一个分支只能检出一次

⛔
同一个分支，最多只能在一个 worktree 里检出——add 会直接拒绝

--force 能强开，但两处检出会互相污染，别

几乎每个人都会撞上这条规则：你在主目录检出着 master，再到别的 worktree git worktree add ../x master，Git 直接拒绝，提示该分支已在哪个目录检出。这不是 Git 嫌麻烦：分支指针是全局共享的，两处同时检出等于两个 HEAD 拴在同一根指针上，任何一边 commit、reset，另一边的工作区立刻"过期"，两边各改各的直接互相污染。Git 是在模型层面保护你。

其余的坑按踩中概率排：

  • 构建产物不共享，成本 ×N：node_modules、target、venv、IDE 索引，每个工作目录各装各的。大仓库开三个 worktree，磁盘和依赖安装时间就是三份——这是一体两面：独立构建也保证了各工作区的产物互不污染。
  • remove 只删干净的工作区：有未提交修改或未跟踪文件时会被拒绝，确认不要了再加 --force。反过来提醒你：真正想留下的东西，别靠"反正还有个 worktree 开着"来记忆。
  • 手动删目录要 prune：直接 rm -rf ../hotfix 的话，worktree list 里会残留一个标着 prunable 的条目，git worktree prune 清账。
  • submodule 用户悠着点：官方手册明确写了"多检出对 submodule 的支持不完整"，含 submodule 的项目不建议开多个检出；这类工作区不能 move，remove 还要 --force。
  • 配置默认只有一份：所有 worktree 共享 .git/config，想让每个工作区有自己的用户名之类的配置，见下面折叠块。
深挖：per-worktree 配置怎么开？prune 的过期策略是什么？▶ 点击展开

独立配置：先 git config extensions.worktreeConfig true 打开开关，之后 git config --worktree user.name "review-bot" 写的配置就只作用于当前工作目录（存在 .git/worktrees/<名字>/config.worktree）。不开开关时 --worktree 参数会报错。

prune 过期：手动删目录后不跑 prune 也没关系——垃圾回收会按 gc.worktreePruneExpire（默认 3 个月）自动清理掉失联条目；等不了就用 git worktree prune --expire <时间> 立刻按阈值清。

05怎么选：stash、clone、worktree 的边界

📦 stash

抽屉——一个目录里串行切换

适合 几分钟的短暂切换；栈攒多了失忆，pop 冲突两摊事缠住

🌍 clone

两个世界——完全独立的两套

适合 长期独立副本、不同凭证；磁盘全量翻倍，两边越用越漂

🗂️ worktree

多开窗口——同仓库多份检出

适合 同一项目并行干活；构建产物各一份，换来互不污染

git stash再 clone 一份git worktree
心智模型抽屉：一个目录里串行切换两个世界：完全独立的两套多开窗口：同仓库多份检出
适合几分钟级别的短暂切换长期独立副本、不同凭证/权限并行任务各自要有活跃工作区
主要成本栈失忆、pop 冲突磁盘全量翻倍、两边漂移构建产物与依赖各一份
切换即时性要收拾现场才能走目录即开即用目录即开即用

一句话记：短暂切换用 stash，陌生环境用 clone，同一项目里并行干活用 worktree。三个工具不是替代关系，是三种颗粒度。

06今日带走

  • worktree = 共享本体 + 独立检出：对象库、分支引用、配置、远端只有一套；HEAD、暂存区、工作区文件每个目录一份。一个仓库，多个工作目录。
  • 挂接目录里 .git 是文件不是目录：一行 gitdir 指回主仓库为本检出开的私有目录——这是识别 linked worktree 的最快办法。
  • 同一分支只能检出一次，是引用模型的必然：分支指针全局共享，两处拴同一根指针必然互相污染，Git 从源头拦下。
  • 基准规则：写不写基准，决定从哪分叉：显式写 master 就从 master 分叉；省略写法基于当前 HEAD——主目录在 feature 上，新分支就从 feature 分叉。基准要明确的场景把基准写全。
  • 分支就是普通分支，合并照旧：合回 master 与日常完全一样（checkout + merge，或推远端走 PR）；remove 只删工作目录不删分支，分支确认不要了再 branch -d。
  • 成本在心里：构建产物不共享，磁盘与依赖安装 ×N；submodule 项目慎用多检出。
