DNS 解析：一次查询到底走了多少步

“改了域名半天不生效”“有的用户好了有的没好”——这些日常怪象都藏在一句“域名变 IP”的背后。这篇把一次 DNS 查询从浏览器一路走到权威，看清递归与迭代是谁替谁跑腿、TTL 到底管着谁、CNAME 为什么有禁令；再把解析装进 HTTPS（DoH）和移动端的 HTTPDNS 讲透——“查域名”这件事本身，也值得加密。

01场景：改了域名配置，为什么半天不生效

发布现场几乎都遇到过这一幕：迁移机房要切流量，改完解析记录，自己本机 dig 一下已经是新 IP，可同事那边还连着旧机器；再等等，有人好了、有人没好。“部分生效”是域名变更的常态，不是谁的机器坏了。另一种更吓人的场景：新域名明明配好了，本地怎么查都是 NXDOMAIN（域名不存在），感觉配置根本没上去。

这两个现象都不是故障，而是 DNS 的“设计行为”：解析结果不会只存在你改的那台权威服务器上——它会沿途被一层层缓存；而替用户去问解析的那个角色，也未必站在用户旁边。所以“改域名”实质上是改一个被多处复制的分布式状态，生效天然是渐进的。你没等它，它就不是“没生效”，是还在生效的路上。

还有一类高频怪象来自移动世界：同一个 App，换个网络解析到的机房就变了，开始跨网、变慢；在个别网络里，域名甚至会被解析到一个陌生的 IP。这也不怪 App——问题出在“替它问路的那个人”身上。这一期先走完整条链路（02 原理），再亲手验证（03 实战），最后一节看今天“查域名”的两种新姿势：加密的 DoH 和应用层的 HTTPDNS。

02原理：一次查询的完整路径

三级接力：只会问的、替你跑的、只答自己那段的

DNS 世界的角色分工从 RFC 1034 起就定得很清楚，一共三个：Stub Resolver（存根解析器）——浏览器和操作系统里的那个 DNS 客户端，只会“问”，不会“查”；递归服务器——运营商 LocalDNS、公司内网 DNS、8.8.8.8 与 223.5.5.5 这类公共 DNS，接受“帮我查完”的委托，负责跑完整趟；权威服务器——域名主人在自己的 DNS 服务商那里配置的那台，只回答自己管辖区内的数据。

把图读一遍：客户端发查询时把 RD（Recursion Desired，期望递归）位置 1，意思是“替我查完”；递归服务器愿意干这活，就在回复里把 RA（Recursion Available，可提供递归）置 1——RFC 1034 §4.3.1 说，客户端靠“回复里 RD 和 RA 都置位”来确认递归真的发生了。递归器先翻自己缓存，没中就拿着问题从根开始：根说“.com 归谁管”，.com 说“example.com 归谁管”，example.com 的权威才给出真正的 A 记录（域名对应的 IP 地址）和 TTL；递归器把答案按 TTL 缓存一份，原路返回。

图里「本地缓存先过一遍」这半句值得展开——缓存不在存根本身上（它只问不存，TTL 计时、负缓存都是递归器那侧的活），而在它上下好几层，各管各的：浏览器自己一份（Chrome 在 chrome://net-internals/#dns 里能看、能清）；操作系统一份——Windows 的 DNS 客户端服务会缓存最近拿到的应答，官方文档说它“在查询配置的 DNS 服务器之前”先用这些记录（ipconfig /displaydns 能列出来、/flushdns 能清，负结果也在其中）；Linux 要看发行版有没有装 systemd-resolved 这类本机解析器，裸的 glibc 默认不缓存；应用运行时还各有一份，比如 JVM 的 InetAddress 对成功解析缓存一段实现相关的时长（HotSpot 默认 30 秒）、失败的默认 10 秒——“发版后还连旧 IP”常撞在这。最特殊的是 hosts 文件：它不是缓存，是本地强制复写——命中的域名根本不会发出 DNS 查询，也永远不受 TTL 管辖；只有你一台机器解析异常、别人都正常时，先看它。

为什么要这么绕？因为要去中心化：没有一台服务器知道全世界的域名，每一层只对下一层授权、只答自己那一段。扩容和治理由此变成分治问题；代价是查询要多走几跳——不过有缓存兜着，绝大多数查询在第一站（递归器）就结束了。

递归与迭代：一个替你把全程跑完，一个只给你下一站

这两个词在任何 DNS 材料里都会出现，一句话区分：递归是“你帮我查完”，迭代是“你去找它”。RFC 1034 §4.3.1 的定义非常干净：非递归（迭代）模式下，服务器返回“一个错误、一个答案，或者一个指向更接近答案的服务器的委派”；递归模式下，服务器“要么给错误，要么给答案，但绝不返回委派”。规范还给了一条分工：迭代是所有服务器都必须支持的，递归是可选的——所以现实里递归被集中放在“递归服务器”这一层，客户端只跟它打一次“递归”交道，后面的路全由它逐跳迭代走完。

记住这个分工，排障直觉就来了：客户端永远只看到“一次问答”。如果问答根本没发生（超时、SERVFAIL），问题在递归器这一跳或它的上游；如果问答发生了但答案是旧的，问题在缓存。

TTL：缓存的契约，也是“生效慢”的根源

TTL 是每条 DNS 记录随身带的一个数字。RFC 1034 §3.6.1 定义为“32 位整数、单位秒”，“描述一条记录在被丢弃之前可以被缓存多久”；由每个区的管理员自己设，短 TTL 减少缓存，TTL 设为 0 表示禁止缓存。

谁在按这个数字倒计时？浏览器、操作系统、递归器（缓存量最大的一层）、公司出口……每一层都按自己看到的 TTL 各自计时。于是“生效时间线”是这样的：你在权威上改掉记录，不等于大家立刻看到——要等所有缓存里的旧记录各自过期。这也是“有人好了有人没好”的原因：不同递归器缓存旧答案的时刻不同，到期时间就不同。

于是教科书做法是一个变更窗口：要改的记录先把 TTL 调小（比如提前一天调到 60 秒），静置一个“旧 TTL”周期等旧缓存自然过期，再动手改，确认全网生效，最后把 TTL 调回来。改完十分钟就指望全网生效的，说明改之前缓存里那条记录的寿命本来就标得很长。

还有一条更隐蔽的期限：负缓存。查一个不存在的域名会得到 NXDOMAIN，而“不存在”这个结论本身也会被缓存。RFC 2308 规定负缓存时长取“SOA——起始授权记录，每个区唯一一条——的 MINIMUM 字段与 SOA 自身 TTL 中的较小者”，并提示 1 到 3 小时的实践效果较好、超过一天“会有问题”。所以“域名明明配好了，为什么还报 NXDOMAIN”——多半是某个递归器在几小时前就把“不存在”存下来了。

03实战：用 dig 把这趟旅程看穿

dig 是随 BIND（那套最经典的 DNS 服务器软件）分发的标准查询工具，三招就能把上一节的图逐段验证。

第一招：默认查询——看一次“递归问答”

递归查询（缺省行为）
dig www.example.com
;; ->>HEADER<<- opcode: QUERY, status: NOERROR, id: 46112
;; flags: qr rd ra; QUERY: 1, ANSWER: 1, AUTHORITY: 0, ADDITIONAL: 0
;; QUESTION SECTION:
;www.example.com.		IN	A
;; ANSWER SECTION:
www.example.com.	300	IN	A	93.184.216.34
;; SERVER: 192.168.1.1#53(192.168.1.1)

三个关键点。flags 里 rd 是你请求了递归，ra 是对方说“我接受递归”——这两个字母就是上一节那张图的开关。dig 的缺省就是发递归查询（BIND 手册原话：RD 位“缺省置位”），不带任何参数时，它做的就是“客户端那一跳”的事。ANSWER 里的 300 是缓存剩余秒数，不是权威上配的原始值——再查一次它会继续变小。而 SERVER 行告诉你是谁在替你跑（Linux 上这个地址来自 /etc/resolv.conf，也就是系统配置的递归器）。

第二招：+trace——把“迭代全程”自己走一遍

从根开始逐跳迭代
dig +trace www.example.com
.			518400	IN	NS	a.root-servers.net.		← 根：. 的 NS 列表
com.			172800	IN	NS	a.gtld-servers.net.		← 委派：去问 .com
example.com.		172800	IN	NS	a.iana-servers.net.		← 委派：去问它的权威
www.example.com.	300	IN	A	93.184.216.34			← 权威给出的答案

+trace 会自动关掉递归（BIND 手册原话：“使用 +trace 时递归被自动禁用”），dig 从根服务器开始跟着委派一路往下走——上面四段输出，正是递归器替你跑的那条路。日常排障里它最大的价值是钉死断在哪一层：根、.com 段都出来了却没有权威答案，问题大概率在权威配置；第一段就断了，多半是本地网络或防火墙把 53 端口封了。

第三招：@server 与 +norecurse——验证缓存与调度

指定递归器对比答案
# @server 越过系统配置，直接指定递归器
dig @223.5.5.5 www.example.com +short
93.184.216.34
# +norecurse：关掉「帮我查完」，只翻对方缓存
dig +norecurse @223.5.5.5 www.example.com

@server 让不同公共 DNS 的答案排排站：结果不同不是谁“错了”，而是两个递归器位置不同，权威给出的是各自的“就近答案”（下一节细说这背后的机制）。+norecurse 则关掉“帮我查完”、只翻对方缓存——它是回答“是缓存问题还是解析问题”的利器：norecurse 也秒回，说明答案一直躺在缓存里；报错或退回委派，说明这台递归器缓存里没有、得靠正常查询现查。

04规则与坑：CNAME 的禁令，与 LocalDNS 的三宗罪

CNAME：别名不是转发，同一条名字上不许再挂别的

CNAME 的含义是“这条名字是另一个名字的别名”。RFC 1034 §3.6.2 的原文很硬：“如果某个节点上存在 CNAME 记录，就不应存在任何其它数据”——理由也写在同段：要让“别名与正名的数据不可能不一致”，这样一来，缓存里的 CNAME 可以被直接拿来把后续查询重定向到正名，不必再回头问权威。如果同一条名字上又 CNAME 又 A，它到底算谁？

RFC 2181 §10.1 把这条规则写成了更干净的“四选一”：任何一个名字，要么只有一条 CNAME（可带 DNSSEC 相关的 SIG、NXT、KEY），要么存在一组非 CNAME 记录，要么“存在但没有记录”，要么“不存在”——没有第五种状态。“根域名不能做 CNAME”也就顺理成章：根上必然有 NS（负责应答的服务器记录）、SOA（区的起始授权记录），和共存禁令直接冲突，所以域名商干脆不让你设。

还有个实操后果：解析器遇到 CNAME 会拿正名“重启”查询（RFC 1034 §4.3.2 的服务端算法就是这么写的）——CNAME 是改名，不是转发，链上每多一层 CNAME 就多一跳查询。能少则少，别拿它当“跳转”使。

LocalDNS 的三宗罪

运营商或公司给你配的那台递归器（俗称 LocalDNS）是绝大多数查询的终点站，但它有三类典型问题，正是另一半“解析怪象”的来源：

  • 劫持：传统 DNS 跑在明文的 UDP 上、没有认证——链路中间任何一环都能把答案改掉。被塞广告页、被解析到钓鱼 IP，都从这里来。
  • 调度不准：权威是按“提问者的位置”给就近答案的，可提问的是递归器，不是用户——它的出口 IP 可能代表几十公里外一个县城的机房。腾讯云官方文档的原话说得直白：LocalDNS 会“按权威 DNS 目标 IP 做 NAT 或转发请求，权威 DNS 无法识别其 IP”，结果是“域名解析错误、流量跨网”。小运营商出口少、位置偏，跨网慢就是这么来的。
  • 缓存不守约：TTL 是给缓存的建议，个别递归器会超期缓存；缓存量最大的一层不守时，全网生效就被它拖长。
⚠
变更纪律：动解析之前，先把 TTL 降到 60 秒并静置一个旧周期

切机房、切 CDN、改负载均衡都同理——让“路上”的旧记录先自然死光，再动源头。这条纪律比任何工具都有效

⛔
CNAME 与其它记录同挂、或给根域名加 CNAME，会让解析半瘫

部分查询类型可达、部分直接报错，排查起来极费时。先把别名和正名的记录配清楚，再谈上线

dig 出来 TTL 只剩 3 秒，是不是我配错了？

不是。你看到的是缓存里的“剩余保质期”，正在倒计时；过几秒再查它会继续变小，刷新后又会回到接近原始值——说明链路是活的、缓存也在正常工作。想确认原始 TTL，去问权威本身（dig @权威服务器）。

同事都好了，就我一个人还是旧解析，按什么顺序查？

由近到远四步。① 先看 hosts 有没有这条域名的强制复写（Linux、macOS 在 /etc/hosts，Windows 在系统盘 drivers\etc\hosts）——命中的话它根本不发查询。② 刷本机三层：浏览器 host cache（chrome://net-internals/#dns 清除）、系统解析器缓存（ipconfig /flushdns；Linux 用 resolvectl flush-caches）、JVM 的名字缓存（重启进程最省事）。③ 用 dig @递归器地址 直接问你们在用的那台递归器，看它缓存是不是还没过期。④ 以上都新，再回头怀疑权威配置。顺序别反——先怀疑远端最费时间。

公司内网、家里宽带、手机 4G 解析结果各不相同，以哪个为准？

以“出问题的那台客户端实际使用的递归器”为准。排障要在故障现场查：在公司机器上 dig，别拿你手机的结果去解释公司内网的故障——两边的递归器、缓存、甚至出口路径都不是同一条。dig +norecurse 可以逐个确认每个递归器缓存里到底存着什么。

05把解析装进 HTTP：DoH 与 HTTPDNS

把前面的问题归成一句话：传统 DNS 是明文的、依赖路程的、没有认证的。改良它的努力分成两条路线：把 DNS 加密（DoT、DoH、DoQ——分别把 DNS 装进 TLS、HTTPS、QUIC 三种传输，IETF 标准），和绕开系统解析路径（HTTPDNS，应用层方案）。两条路线都用上了 HTTP/HTTPS。先看加密三兄弟的对照——注意：换的只是“传输方式”，DNS 报文的语义一律不变。

传统 DNSDoTDoHDoQ
传输UDP 53（明文）TCP 853 + TLS（RFC 7858）HTTPS 443（RFC 8484）QUIC / UDP 853（RFC 9250）
加密无，链路可窥探可篡改有（专用通道）有（与网页流量同管道）有（每条查询一个流）
形态一问一答的裸报文加密长连接，适合复用看不出是 DNS，难被单独针对独立流 + 0-RTT，最激进
谁在用全世界系统级（Android“私密 DNS”）浏览器级（Chrome“安全 DNS”）较新，仍在铺开

两个系统级的印证：“Android 私密 DNS”设置里一开，DNS 的问与答就走加密，官方说明很诚实——“私密 DNS 只保护 DNS 的问与答，保护不了其它流量”；Chrome 的安全 DNS 是同一思路，官方描述是“Chrome 会在解析过程中加密你的信息”，自动模式下缺省开启、失败还会回退到未加密模式。DoQ 则把整套搬到 QUIC 上：RFC 9250 规定 UDP 853 端口、每条查询一个独立双向流——所以 DoQ 里 DNS 报文的 ID 字段直接置 0，流的编号已经天然对齐了问答。

DoH：一次“解析”是怎么装进 HTTP 的

这是最值得慢下来看的拼接——DNS 和 HTTPS 到底怎么合到一起？四步：

1

组包

照 RFC 1035 组装查询报文

和发往 53 端口的那份一模一样

2

装进 HTTP

GET 「?dns=base64url」或 POST 原始报文

Content-Type: application/dns-message

3

响应

HTTP 2xx = 一次合法的 DNS 响应

NXDOMAIN 也装在 2xx 里

4

缓存合账

HTTP 新鲜期 ≤ 答案里最小 TTL

客户端还要扣掉 Age 头

四步各有一段规范原文值得记住。第 2 步：GET 请求把报文做 base64url 编码放进 ?dns= 参数，且“不得包含 padding”；POST 则把原始报文直接当 body（“不做编码”），媒体类型是 application/dns-message，报文上限 65535 字节。第 3 步最容易误解：RFC 8484 §4.2.1 规定，用“2xx 状态码表示任何合法的 DNS 响应，无论 DNS 响应码是什么”——也就是说 NXDOMAIN、SERVFAIL 都是 HTTP 层面的“成功”；反过来，401、415 这类 4xx/5xx 才代表 DoH 通道本身出了问题。第 4 步：服务器给响应的 HTTP 新鲜期“不得大于 Answer 段里最小的 TTL”（§5.1），客户端算 DNS TTL 时要把 Age 头（这条响应在缓存里已躺了多久）扣掉——DNS 的 TTL 和 HTTP 的 Cache-Control 在这里就是同一笔账。

为什么这套有用：DoH 跑在 443 上、和浏览网页走一条加密管道——链路上能看到的只是“你在和一个 DoH 服务说话”，至于你查的是哪个域名，全在加密里。这也是它比 DoT（853 专用端口）更难被单独针对的原因。当然，隐私不是白给的：你的 DoH 服务商能看到你全部的查询——加密只是把“谁能看见”从本地网络换成了服务商，选服务商就是在选托付对象。

注意 DoH 解决的是“可窥探、可篡改”，没解决“调度”——替你去问的依然是那台递归器，权威看到的还是它的位置。要连调度一起解决，就轮到移动端那条路线了。

HTTPDNS：绕开 LocalDNS 的应用层方案

HTTPDNS 不是 IETF 标准，是商业 DNS 服务（阿里云、腾讯云都有）面向 App 的一种“解析直连”方案。它的原点正是上一节 LocalDNS 的第二宗罪。阿里云官方文档写得很直白：“通过集成 HTTPDNS 提供的客户端 SDK 或调用 HTTP API，您的应用可以绕过传统 Local DNS 服务器，直接通过 HTTP(S) 协议向 HTTPDNS 服务发送 DNS 查询请求”；服务端则“能够直接得到客户端的出口公网 IP，从而更准确地判断客户端地区和运营商，得到更精准的解析结果”。一句话：让它替 App 问——而且它能看到 App 的真身位置。

App 内 SDK 发起的解析请求（阿里云 HTTPDNS 接口示意）
GET http://203.107.1.1/100000/d?host=www.example.com
{"host":"www.example.com","ips":["203.0.113.10"],"ttl":57,"origin_ttl":120}
# ips = 候选 IP 列表；ttl = 结果可缓存秒数；origin_ttl = 权威给出的原始 TTL

拿到 IP 之后，App 直接连 IP、不再让系统解析。但“直连 IP”必须自己补一整套身份动作——HTTP 要带上 Host 头，HTTPS 还要处理 SNI 与证书校验。阿里云官方文档的步骤：手动设置“Host: 原始域名”；把“原始域名写入 SNI 扩展”（SNI：TLS 握手里声明“我要连谁”的字段）；证书校验时“在 TLS 校验阶段显式传入原始域名，确保 CN/SAN 比对正确”。否则 IP 连得上、证书却对不上域名（hostname mismatch），或者 SNI 填错被服务端拒绝。

和 DoH 的关系一句话：两条路线都“绕过系统解析路径、走 HTTP(S)”，区别在DoH 是标准协议（无鉴权、不支持业务参数），HTTPDNS 是带鉴权的私有协议（可自定义调度、可批量解析）。阿里云官方对比的原话：“两者都通过 HTTP/HTTPS 通道绕过操作系统 Local DNS 解析路径……HTTPDNS 除私有协议外也支持 DoH，但适用场景不同。”分工也就出来了：浏览器和操作系统层面用 DoH，App 要精细调度、可控选路、失败兜底就用 HTTPDNS——而且很多 App 是两者并存，先 HTTPDNS、兜底 DoH/LocalDNS。

开了加密 DNS，域名就“劫持不了”了吗？

加密保护的是“你到递归器”这一段；递归器往上到权威那一小段是否加密，取决于递归器自己的配置。另外 DoH 自身也依赖“你连的 DoH 服务器地址”没被篡改。安全是链式的，加密 DNS 补上了过去最大的短板，但不是全部。

深挖：权威服务器到底怎么知道“你在哪儿”——以及 ECS 的隐私代价▶ 点击展开

ECS（EDNS Client Subnet）是标准侧的补丁：递归器可以把客户端 IP 截断后附在查询里（RFC 7871，EDNS0 选项代码 8），权威据此返回“就近答案”；规范建议截断到 IPv4 的 24 位、IPv6 的 56 位。但它是可选、可被忽略的，RFC 7871 的作者甚至建议“默认关闭、确有收益再开”——因为它会把缓存切碎（按网段缓存、命中率大降），还向权威暴露了客户端网段。

这正是 HTTPDNS 在移动端大行其道的另一个原因：它不用走 ECS 这套折中，服务端直接看到客户端出口 IP，“精准调度”是天然属性。加密与调度的账，在两条路线上是分开算的。

06今日带走

  • 一次解析是三级接力：stub 只会问、递归器替你跑、权威只答自己那一段；客户端视角永远只有“一次问答”。
  • 递归是“帮我查完”，迭代是“去问它”：唯一一次递归发生在客户端与递归器之间，往里全是一层层委派（RFC 1034 §4.3.1）。
  • TTL 是缓存的契约：改解析 = 改一个多处复制的状态——先降 TTL 再改、等旧缓存过期；负缓存（NXDOMAIN）还有一个 SOA MINIMUM 定的期限（RFC 2308）。
  • CNAME 是别名不是转发：同一条名字上不许再挂别的记录（RFC 2181 §10.1 的“四选一”），根域名因此天然不能设 CNAME。
  • DoH = 把 DNS 报文装进 HTTPS：GET ?dns=base64url 或 POST application/dns-message，NXDOMAIN 也装在 2xx 里；HTTP 缓存与 DNS TTL 在此合账。
  • HTTPDNS 是应用层绕行：App 直接向服务商要 IP + TTL，再 IP 直连——Host、SNI、证书校验都得用回原始域名。
