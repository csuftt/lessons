大模型 API 格式：为什么全世界都在兼容 OpenAI

打开 DeepSeek、vLLM、Ollama 的文档，第一句几乎都是“兼容 OpenAI”——base_url 一改就能跑。可 OpenAI 自己又冒出个 Responses API，Anthropic 坚持另一套 Messages 格式，Gemini 还有自己的方言。这篇把“调大模型的那个 HTTP 请求”解剖开：事实标准是怎么长出来的、三家格式差在哪、换供应商时哪里最容易翻车——顺带澄清一个高频口误：OpenAI 和 OpenAPI，完全是两回事。

01场景：换一家模型，为什么代码几乎不用改

几乎每个自己接过模型的开发者都见过这句话：文档首页写着“OpenAI 兼容（OpenAI-compatible）”。DeepSeek（深度求索的国产模型）写、vLLM 和 Ollama（两个最主流的开源推理引擎）写、通义千问也写。实际体验也确实神奇：用 OpenAI 官方 SDK，把 base_url 从 api.openai.com 换成 api.deepseek.com，同一行 client.chat.completions.create(...) 立刻调通了另一家的模型。“兼容 OpenAI”兼容的到底是什么？是端点路径、请求体结构、响应结构、流式事件这一整套约定——业内叫事实标准（de facto standard）：没有委员会投票，用的人多了，它就是标准。

但往下学很快会撞上三层困惑。第一层：OpenAI 自己又出了个 Responses API，官方说新项目推荐用它——那我刚学会的 Chat Completions 过时了吗？第二层：Anthropic 明明有自己的 Messages API，格式和 OpenAI 不一样（system 放哪、必填参数、工具调用写法都不同），可为什么全世界的兼容层都围着 OpenAI 转？第三层是个高频口误：OpenAI ≠ OpenAPI——OpenAPI 是 Swagger 那套描述 REST 接口的规范（一个 YAML/JSON 文件描述你的接口给机器看），和大模型没有半点关系；OpenAI 是公司名。名字只差一个字母，完全是两个世界的东西。

这篇按四步走：先看事实标准是怎么长出来的（02 原理），再把三家最小请求并排写一遍、缺省行为逐个说破（03 实战），然后趟一趟换供应商时最容易翻车的水区——工具调用（04 规则与坑），最后一张大表收走所有差异，附怎么选（05 对照）。

02原理：事实标准是怎么长出来的

三年时间线：一个引爆，两个应答

1

2023-03-01

ChatGPT API（gpt-3.5-turbo）发布

每千 token 两美分，比 text-davinci-003 便宜 90%，开发者蜂拥而入

2

2024-03-04

Claude 3 家族 + Messages API

Anthropic 换掉旧的补全接口，Claude 3 只走 Messages——另一家门派成型

3

2025-03-11

OpenAI 发布 Responses API

内置工具、服务端状态，定位是 Chat Completions 的演进

4

2026-01

Open Responses 开放规范

OpenAI 把 Responses 格式开源成多供应商互操作规范——格式之争进入下一局

“兼容 OpenAI”为什么成了默认？看第一步的连锁反应：2023 年 3 月 ChatGPT API 发布，价格一步降到原来的十分之一，一年之内教程、LangChain、客户端 SDK、开源项目全围着 /v1/chat/completions 这一个端点建。后来者想让这批开发者零成本切换，最省事的选择不是发明新格式，而是让自己的接口“说同一种方言”——端点路径一样、请求体一样、响应结构一样、流式事件一样，OpenAI SDK 换个 base_url 直接用。DeepSeek 官方文档的原话是：“The DeepSeek API uses an API format compatible with OpenAI/Anthropic”，而且它真的同时开了两个口子：api.deepseek.com（OpenAI 格式）和 api.deepseek.com/anthropic（Anthropic 格式）——连 Anthropic 格式也成了被兼容对象，只是体量远小于 OpenAI 这门“通用语”。

剥开方言：同一副骨架

三家格式看着互不相同，剥开看是同一件事：无状态的 HTTP POST + 角色消息列表 + 采样参数。“无状态”是理解一切的关键——服务端不记得你上一轮说了什么，每一轮请求都要把完整对话历史重发一遍。模型没有记忆，所谓“上下文”，是你每轮亲手拼好发过去的。那个消息列表（messages / input / contents），本质就是逐轮对话的完整重放。

为什么没人统一成一个格式？

因为格式不只是外壳，还是各家模型能力的表达方式。Anthropic 把 thinking（思考过程块）做成消息内容的一种类型，把缓存控制（cache_control，提示缓存的生效范围与时长）做成消息上的标记；OpenAI 的 Responses 把推理摘要、函数调用、内置工具的结果都做成类型化的输出项。这些设计跟着各自模型的特性走，谁也说服不了谁——于是标准化的努力走向了另一个方向：不是让三家改说一种话，而是让“翻译层”便宜。你会在 05 节看到这条路线的最新形态。

03实战：同一句“你好”，发三家

空谈结构不如真发一次。下面是三个最小可运行请求（curl 直发，不用 SDK），问的都是同一句话——注意三段代码里标粗意涵的四处不同：端点、system 的位置、max_tokens 的必填性、从响应里取答案的路径。

第一家：Chat Completions（事实标准的本体）

OpenAI · POST /v1/chat/completions
curl https://api.openai.com/v1/chat/completions -H "Authorization: Bearer $KEY" -H "Content-Type: application/json" -d '{"model":"gpt-5.2","messages":[{"role":"user","content":"你好"}]}'
{"choices":[{"message":{"role":"assistant","content":"你好！有什么可以帮你？"}}],
 "usage":{"prompt_tokens":8,"completion_tokens":9}}
# messages 必填；没写 max_tokens = 不设上限，生成到自然停止
# 取答案：choices[0].message.content

第二家：Responses（OpenAI 的演进版）

OpenAI · POST /v1/responses
curl https://api.openai.com/v1/responses -H "Authorization: Bearer $KEY" -H "Content-Type: application/json" -d '{"model":"gpt-5.2","input":"你好"}'
{"output":[{"type":"message","content":[{"type":"output_text","text":"你好！"}]}],
 "usage":{"input_tokens":8,"output_tokens":9}}
# input 可直接给字符串；系统提示是顶层 instructions，不在消息里
# 取答案：output 数组里 type=message 的那一项（SDK 提供 output_text 捷径）

第三家：Messages（Anthropic 的门派）

Anthropic · POST /v1/messages
curl https://api.anthropic.com/v1/messages -H "x-api-key: $KEY" -H "anthropic-version: 2023-06-01" -H "Content-Type: application/json" -d '{"model":"claude-sonnet-5-5","max_tokens":1024,"messages":[{"role":"user","content":"你好"}]}'
{"content":[{"type":"text","text":"你好！有什么可以帮你？"}],"stop_reason":"end_turn"}
# max_tokens 必填——漏了它，两家都不用比，这一步就直接 400 报错
# 鉴权是 x-api-key + anthropic-version 版本头，不是 Bearer
# 取答案：content 数组里 type=text 的那些块

把缺省行为说破，这组对照才算讲完。max_tokens 不写会怎样？OpenAI 这边它是可选参数——不写就是参数层面不设上限，模型生成到自然停止（注意这个参数已改名 max_completion_tokens，而且推理模型的思考 token 也计入）；Anthropic 这边它必填，官方文档明说这是“生成停止前最大的 token 数”，不写直接被拒。系统提示放哪？Chat Completions 里它是消息列表的一条（新模型推荐用 developer 角色替代 system）；Responses 里是顶层 instructions；Anthropic 里是顶层 system，根本不进消息列表。角色必须严格交替吗？Anthropic 允许连续同角色的消息，服务端会自动合并；把最后一条写成 assistant 还能玩 prefill（让模型接着你的半句话说）——OpenAI 的消息列表没有这两个行为。

04规则与坑：工具调用，换供应商时最容易翻车的段

“让模型调用你的函数”是现代 AI 应用的地基，也是三家用语分歧最大的地方。但先看清那个完全一致的闭环——四步：

1

声明工具

tools 里给函数名 + 参数的 JSON Schema

告诉模型“有哪些能力可以调”

2

模型要调工具

不直接回答，返回带 id 的调用请求

参数由模型生成，含在返回里

3

本地执行

你自己跑这个函数——模型只出嘴不出手

要不要执行、怎么执行，永远是你说了算

4

结果回传

把执行结果拼回消息列表，再发一次

模型看到结果，才给出最终回答

分歧全在第 2 步的返回长相和第 4 步的回传写法上。OpenAI：模型的调用请求放在 assistant 消息的 tool_calls 数组里（id + 函数名 + arguments）；你回传时，用一条独立的 role:"tool" 消息装结果，靠 tool_call_id 对上号。Anthropic：模型的调用请求是 assistant 消息里的一个 tool_use 内容块（同样带 id）；你回传时，把 tool_result 块塞进下一条 user 消息的内容数组里——没有 tool 这个角色。同一次“问天气”，回传体一个长这样：

工具结果回传：同一件事的两种方言
# OpenAI：独立 role:"tool" 消息，靠 tool_call_id 对号
{"role":"tool","tool_call_id":"call_abc123","content":"259.75 USD"}
# Anthropic：tool_result 块装进下一条 user 消息的 content 数组
{"role":"user","content":[{"type":"tool_result","tool_use_id":"toolu_01D7...","content":"259.75 USD"}]}
⚠
OpenAI 的 arguments 是字符串化的 JSON，且官方警告“不总是合法 JSON”

拿到 tool_calls 先解析校验再执行——直接当对象用会撞运行时错误。另外模型只要了工具、没写正文时，content 可以是 null，别对它取长度

⛔
Anthropic 的 max_tokens 必填、system 不进消息列表——这两条是从 OpenAI 平移代码时最常见的报错来源

前者直接 400，后者不报错但系统提示悄悄失效，模型“人设全丢”

流式输出三家都支持吗？写一个通用网关要处理几种？

都支持，而且都用 SSE（Server-Sent Events，服务器单向推流的 HTTP 长连接）——但事件结构是三种方言。Chat Completions 推 chat.completion.chunk，增量文本在 delta 里，结尾是 data: [DONE]；Responses 推类型化事件（response.output_text.delta 一类，事件名即语义）；Anthropic 推 content_block_delta 一类事件、按内容块分段。网关要各写一套解析器，这是“兼容层”真正的成本所在。

多轮对话要自己存历史吗？Responses 的“状态管理”是什么？

Chat Completions 和 Messages 都是无状态的——历史由你自己存、自己拼、每轮全量重发。Responses 多给了一个选项：store: true 时服务端帮你存这轮的输入输出，下一轮只带 previous_response_id 就能接上，不必重发全史；对数据合规敏感（不许服务端留存）的场景，可以用加密的 reasoning 项走无状态模式。它甚至还提供了会话对象——但骨架没变：所谓会话，仍然是历史的一种托管方式。

表的最右一列是这期的题眼：Chat Completions 是唯一被全行业当“通用语”来兼容的格式。而两个最新动向值得知道。其一，OpenAI 官方对 Chat Completions 的态度是“仍支持、未废弃，但新项目一律推荐 Responses”，而且最新模型（GPT-6 系列）的工具调用已经只认 Responses——上一代通用语的原产地，正在推下一代通用语；老的 Assistants API 已于 2026-08-26 正式下线，就是这个方向的注脚。其二，2026 年 1 月 OpenAI 把 Responses 格式开源成 Open Responses 规范，目标是一个规范接多家模型——标准化正在从“大家兼容某一家”走向“共享一个开放规范”。

怎么选：三个场景三个答案

① 直连 OpenAI 的新项目 → Responses。新能力都先落在这里（内置联网搜索、文件检索、远程 MCP 工具），reasoning 模型表现更好，服务端状态省掉自己拼历史的代码。

② 要最大兼容面（开源模型、vLLM/Ollama 自建、随时换供应商） → 守 Chat Completions。全行业的兼容层都说这门方言，一行 base_url 换后端。

③ 主力用 Claude → Messages + Anthropic 官方 SDK。顶层 system、必填 max_tokens、thinking 块这些设计要按它家的规矩来，SDK 已替你包好。

一条不变的底线

无论选哪门方言，底层骨架一样：无状态 POST、角色消息列表全量重发、采样参数。理解了骨架，任何新格式都只是“又一种方言”——看一遍端点和消息结构，就能上手。

真正需要盯紧的不是格式本身，而是它们背后的能力差异：谁的服务端状态、谁的思考块、谁的内置工具——格式是外壳，能力才是选型时真正的筹码。

深挖：Gemini 的 generateContent 长什么样——第四种方言速览▶ 点击展开

Gemini 走的是 Google 自己的 REST 风格：模型名直接放 URL 路径（POST .../v1beta/models/gemini-2.0-flash:generateContent，流式把动词换成 :streamGenerateContent）。消息叫 contents，角色叫 user 和 model——没有 assistant 这个词；每条消息的内容切成 parts 数组，文本、图片（base64 内联或文件引用）、函数调用各是一种 part。系统提示是顶层 systemInstruction；采样参数（temperature、maxOutputTokens、stopSequences…）全部收进 generationConfig 一个对象，而不是像 OpenAI 那样平铺在请求体顶层。字段命名还混着驼峰（generationConfig）和下划线（system_instruction）两个习惯——读它的文档时多留个心眼。

对照前三家你会发现：换的只是词汇表，“无状态 + 角色消息 + 采样参数”的骨架纹丝不动。这也是为什么各家网关（LiteLLM、OpenRouter 这类）能做到一个入口翻译四方——骨架同源，翻译才便宜。

06今日带走

  • “兼容 OpenAI” = 兼容 Chat Completions 那套端点+请求+响应+流式约定：它是无委员会的事实标准，DeepSeek、vLLM、Ollama、千问都说这门方言，base_url 一改就能换后端。
  • 所有大模型 API 共用一副骨架：无状态 HTTP POST + 角色消息列表 + 采样参数；每轮全量重发历史——模型的“记忆”是你每轮亲手拼出来的。
  • max_tokens 一边可选一边必填：OpenAI 不写就是不设上限（参数已改名 max_completion_tokens）；Anthropic 不写直接 400 报错。
  • system 三个位置：OpenAI 放消息里（新模型叫 developer）、Anthropic 放顶层 system、Gemini 放顶层 systemInstruction——平移代码时悄悄失效的就是它。
  • 工具调用闭环四步一致，方言在第 2、4 步：OpenAI 用 role:"tool" 消息回传，Anthropic 把 tool_result 块塞回 user 消息——换供应商最容易翻车的就是这段。
  • 选型三句：直连 OpenAI 新项目用 Responses；要兼容面守 Chat Completions；主力 Claude 用 Messages+官方 SDK。格式是外壳，服务端状态、思考块、内置工具这些能力才是筹码。
