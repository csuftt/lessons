大模型 API 格式：为什么全世界都在兼容 OpenAI

打开 DeepSeek、vLLM、Ollama 的文档，第一句几乎都是“兼容 OpenAI”——base_url 一改就能跑。这篇把“调大模型的那个 HTTP 请求”解剖到实操级：系统提示词放哪、工具（脚本/skill/MCP）怎么声明怎么回传、流式输出怎么配，Chat Completions / Responses / Messages / Gemini 一张表收走差异——顺带澄清一个高频口误：OpenAI 和 OpenAPI，完全是两回事。

01场景：换一家模型，为什么代码几乎不用改

几乎每个自己接过模型的开发者都见过这句话：文档首页写着“OpenAI 兼容（OpenAI-compatible）”。DeepSeek（深度求索的国产模型）写、vLLM 和 Ollama（两个最主流的开源推理引擎）写、通义千问也写。实际体验也确实神奇：用 OpenAI 官方 SDK，把 base_url 从 api.openai.com 换成 api.deepseek.com，同一行 client.chat.completions.create(...) 立刻调通了另一家的模型。“兼容 OpenAI”兼容的到底是什么？是端点路径、请求体结构、响应结构、流式事件这一整套约定——业内叫事实标准（de facto standard）：没有委员会投票，用的人多了，它就是标准。

但真到自己动手，问题就来了：系统提示词到底放哪？本地的工具——一个脚本、一个 skill（给 AI 用的技能包）、一个 MCP 服务（MCP：Model Context Protocol，接外部工具的开放协议）——怎么通过 API 交给模型？模型说要调工具时，返回体里靠什么识别？还有流式输出，人人都在用，配置和协议上到底和一次性响应差在哪？再加一个高频口误要澄清：OpenAI ≠ OpenAPI——OpenAPI 是描述 REST 接口的一套规范文档格式（Swagger 那套），和大模型没有半点关系；OpenAI 是公司名。名字只差一个字母，完全是两个世界的东西。

这篇按这个顺序走：先看事实标准和共同骨架（02 原理），把三个最小请求并排写一遍（03 实战），然后是重头戏——工具调用全链路（04）与流式输出（05），最后一张大表收走所有差异，附怎么选（06 对照）。

02原理：事实标准与同一副骨架

三年时间线：一个引爆，两个应答

每千 token 两美分，开发者生态一年内全围过来

2

2026-01

Responses 格式开源成多供应商互操作规范

“兼容 OpenAI”为什么成了默认？2023 年 ChatGPT API 引爆后，教程、SDK、开源项目全围着 /v1/chat/completions 建；后来者（DeepSeek、vLLM、Ollama）想让这批开发者零成本切换，最省事的就是让自己的接口说同一种方言。DeepSeek 官方文档原话：“The DeepSeek API uses an API format compatible with OpenAI/Anthropic”，而且同时开了两个口子：api.deepseek.com（OpenAI 格式）和 api.deepseek.com/anthropic（Anthropic 格式）——连 Anthropic 格式也成了被兼容对象，只是体量远小于 OpenAI 这门“通用语”。

剥开方言：同一副骨架

三家格式看着互不相同，剥开看是同一件事：无状态的 HTTP POST + 消息 + 参数。“无状态”是理解一切的关键——服务端不记得你上一轮说了什么，每一轮请求都要把完整对话历史重发一遍。模型没有记忆，所谓“上下文”，是你每轮亲手拼好发过去的。参数区除了模型名和采样参数（temperature、max_tokens），还藏着两个现代应用的开关：tools（工具清单）与 stream（流式开关）——这篇 04、05 两节就拆这两个。

03实战：同一句“你好”，发三家

三个最小可运行请求（curl 直发，不用 SDK），问的都是同一句话，三家都带上系统提示词——注意“系统提示词放哪”在三段代码里的三种答案，以及 max_tokens 的必填性差异。

第一家：Chat Completions（事实标准的本体）

OpenAI · POST /v1/chat/completions
curl https://api.openai.com/v1/chat/completions -H "Authorization: Bearer $KEY" -H "Content-Type: application/json" -d '{"model":"gpt-5.2","messages":[{"role":"system","content":"你是一位简洁的技术助手"},{"role":"user","content":"你好"}]}'
{"choices":[{"message":{"role":"assistant","content":"你好！有什么可以帮你？"}}]}
# 系统提示词 = 消息列表第一条（role:system，新模型推荐 developer）
# max_tokens 可选，不写=不设上限；取答案：choices[0].message.content

第二家：Responses（OpenAI 的演进版）

OpenAI · POST /v1/responses
curl https://api.openai.com/v1/responses -H "Authorization: Bearer $KEY" -H "Content-Type: application/json" -d '{"model":"gpt-5.2","instructions":"你是一位简洁的技术助手","input":"你好"}'
{"output":[{"type":"message","content":[{"type":"output_text","text":"你好！"}]}]}
# 系统提示词 = 顶层 instructions 参数（不进消息）；input 可直接给字符串
# 返回是类型化 output 数组：正文/推理/函数调用各带类型标签

第三家：Messages（Anthropic 的门派）

Anthropic · POST /v1/messages
curl https://api.anthropic.com/v1/messages -H "x-api-key: $KEY" -H "anthropic-version: 2023-06-01" -H "Content-Type: application/json" -d '{"model":"claude-sonnet-5-5","max_tokens":1024,"system":"你是一位简洁的技术助手","messages":[{"role":"user","content":"你好"}]}'
{"content":[{"type":"text","text":"你好！有什么可以帮你？"}],"stop_reason":"end_turn"}
# 系统提示词 = 顶层 system 参数；max_tokens 必填——漏了直接 400 报错
# 鉴权是 x-api-key + anthropic-version 版本头，不是 Bearer

把缺省行为说破。先说清 max_tokens 是什么：单次回答最多生成多少个 token——token 是模型切分与计费文本的单位，一个汉字约一到两个；它管“说多少”，不管“读多少”（一次能读进的总长度叫上下文窗口，是模型自带属性，不在请求里设）。不写会怎样？OpenAI 这边可选——不写就是参数层面不设上限，模型生成到自然停止（该参数已改名 max_completion_tokens，推理模型的思考 token 也计入）；Anthropic 这边必填，不写直接被拒——它要你显式给输出设预算。系统提示词放错会怎样？不报错，但人设悄悄失效、模型性情大变——平移代码时最阴的雷。另外 Anthropic 允许连续同角色的消息（服务端自动合并），把最后一条写成 assistant 还能玩 prefill（让模型接着你的半句话说）——OpenAI 的消息列表没有这两个行为。

max_tokens 是上下文长度的上限吗？

不是，两者名字像、职责完全不同。max_tokens 管“说多少”：你给这次输出设的预算，超了回答被截断，结束原因会标 max_tokens（而不是 end_turn）。上下文窗口管“读多少”：模型一次能读入的总长度（历史输入 + 本次输出共享），是模型自带属性——历史太长 API 不会替你截，要么自己裁剪、要么换长窗口模型。一个是输出预算，一个是记忆容量。

04工具调用全链路：声明、识别、回传

“让模型调用你的函数”是现代 AI 应用的地基。你本地的工具——一个脚本、一个 skill、一个 MCP 服务——到 API 这一层，表达全部收敛为请求里的 tools 数组。示例口径：本节 OpenAI 示例均为 Chat Completions 写法（事实标准，各家兼容层认的都是这套）；Responses 的工具定义是扁平结构 {type, name, parameters}、结果回传走 call_id + function_call_output，思路相同不再展开。全链路四步：

1

声明工具

tools 里给名字 + 描述 + 参数的 JSON Schema

描述决定模型什么时候调它

2

模型发起调用

不直接回答，返回带编号的调用请求

参数由模型生成，含在返回体里

3

本地执行

你自己跑这个函数——模型只出嘴不出手

要不要执行、怎么执行，永远你说了算

4

结果回传

结果拼回消息列表，再发一次

模型看到结果，才给出最终回答

第 1 步：tools 数组怎么写

声明工具：OpenAI 与 Anthropic 的写法
# OpenAI（Chat Completions 写法）：type=function + 名字 + 描述 + 参数的 JSON Schema
{"tools":[{"type":"function","function":{
   "name":"get_stock_price","description":"查询股票当前价格",
   "parameters":{"type":"object","properties":{"ticker":{"type":"string"}}}}}],
 "tool_choice":"auto"}
# Anthropic：同款思路，字段叫 input_schema，少一层包装
{"tools":[{"name":"get_stock_price","description":"查询股票当前价格",
   "input_schema":{"type":"object","properties":{"ticker":{"type":"string"}}}}]}
# 内置工具与 MCP 的捷径（OpenAI）：一个 type 就带上整套能力
{"tools":[{"type":"web_search"}]}                        # 平台内置，免定义
{"tools":[{"type":"mcp","server_url":"https://..."}]}   # 工具清单由 MCP 服务器提供

两家的自定义工具结构几乎同款：函数名、一句描述、参数的 JSON Schema（一种描述数据长什么样的通用格式，模型照着它生成参数）。描述别乱写——模型就是靠它决定什么时候调；tool_choice: "auto" 则表示调不调由模型自己决定。两条捷径只此一家（OpenAI Responses）：内置工具一个 type 就带上整套能力（联网搜索、文件检索、代码解释器），定义都不用写；MCP（Model Context Protocol，模型上下文协议）声明一个服务器地址，工具清单由 MCP 服务器自己提供——几十个工具也不用逐个定义。

第 2 步：模型要调工具时，返回体长什么样

识别调用：三个信号 + 参数形态差异
# OpenAI（Chat Completions）：tool_calls 数组，参数 arguments 是 JSON 字符串
{"choices":[{"message":{"role":"assistant","content":null,
   "tool_calls":[{"id":"call_abc","type":"function",
      "function":{"name":"get_stock_price","arguments":"{\"ticker\":\"AAPL\"}"}}]},
 "finish_reason":"tool_calls"}]}
# Anthropic：content 数组里多一个 tool_use 块，参数 input 是现成对象
{"content":[{"type":"tool_use","id":"toolu_01D7","name":"get_stock_price",
   "input":{"ticker":"AAPL"}}],
 "stop_reason":"tool_use"}

识别一次调用，两家都给三个信号：结束原因变了（finish_reason 变 tool_calls / stop_reason 变 tool_use）、多了类型字段（tool_calls 数组 / tool_use 块）、每项带编号 id。参数形态是一家一个坑：OpenAI 的 arguments 是字符串化的 JSON，官方文档白纸黑字警告“不总是合法 JSON”——拿到先解析、校验，再执行；Anthropic 的 input 是现成对象，不用再解析。另外 OpenAI 只要了工具没写正文时 content 是 null，别对它取长度。

⚠
OpenAI 的 arguments 是字符串，且“不总是合法 JSON”——先校验再执行

直接当对象用会撞运行时错误；模型只发起调用的回合 content 可能为 null

第 4 步：结果回传，分歧最大的一步

回传：同一件事的两种方言
# OpenAI（Chat Completions）—— 独立 role:"tool" 消息，靠 tool_call_id 对号
{"role":"tool","tool_call_id":"call_abc","content":"259.75 USD"}
# Anthropic —— tool_result 块，塞进下一条 user 消息的 content 数组
{"role":"user","content":[{"type":"tool_result","tool_use_id":"toolu_01D7","content":"259.75 USD"}]}

语义一模一样，长相完全两样：OpenAI 有独立的 tool 角色；Anthropic 没有——把 tool_result 块塞进下一条 user 消息的 content 数组里。实操提醒：重发时要把模型上一轮那条带编号的调用请求（assistant 的 tool_calls 消息 / tool_use 块）原样拼回消息列表，再接结果消息——只发结果一条，服务端不认，两家同理。这就是换供应商时最容易翻车的一段，也是多模型网关（LiteLLM、OpenRouter 这类）真正的成本所在。

05流式输出：一行配置，协议变 SSE

生产环境调大模型几乎默认流式：一段回答可能要生成几十秒，一次性等完整响应，用户就对着白屏干等；流式让首字几秒内蹦出来、后面逐字吐。配置只要请求体加一行 "stream": true（三家同名参数；Gemini 是 :streamGenerateContent 端点加 ?alt=sse）。一次流式请求的完整过程：① 你照常发 POST，多带一行 stream:true；② 服务端几乎立刻返回 HTTP 200——但这只是响应头先回（Content-Type: text/event-stream），正文一个字还没生成；③ 模型边生成边推，每出一个词推一条 data: 事件；④ 结束标记到达（如 data: [DONE]），连接关闭，你把增量拼成完整回答。最容易误解的是第②步：收到 200 不等于收到答案。事件结构则是三种方言：

SSE 事件流：三家方言（原始报文示意）
# Chat Completions：增量在 delta，结尾 data: [DONE]
data: {"choices":[{"delta":{"content":"你"}}]}
data: {"choices":[{"delta":{"content":"好"}}]}
data: [DONE]
# Responses：类型化事件，事件名即语义
event: response.output_text.delta
data: {"delta":"你"}
# Anthropic：按内容块分段推进（文本块/工具块各自成段）
event: content_block_delta
data: {"delta":{"type":"text_delta","text":"你"}}

写通用网关时这一层要各写一套解析器：第一家的增量挂在 delta 上、以 DONE 标记收尾；第二家按事件名分发；第三家按内容块分段，一次回答可能混着文本块和 tool_use 块各推各的。还有一笔账要知道：流式的用量统计不是都在最后一条事件里——比如 OpenAI Chat Completions 要在请求里显式开启 stream_options.include_usage，结尾才多给一条用量 chunk，计费对账别漏。

多轮对话要自己存历史吗？Responses 的“状态管理”是什么？

Chat Completions 和 Messages 都是无状态的——历史由你自己存、自己拼、每轮全量重发。Responses 多给一个选项：store: true 时服务端帮你存这轮的输入输出，下一轮只带 previous_response_id 就能接上，不必重发全史；数据合规敏感（不许服务端留存）的场景可用加密的 reasoning 项走无状态模式。骨架没变：所谓会话，仍然是历史的一种托管方式。

怎么选：三个场景三个答案

① 直连 OpenAI 的新项目 → Responses。新能力都先落在这里（内置联网搜索、文件检索、远程 MCP 工具），服务端状态省掉自己拼历史的代码。

② 要最大兼容面（开源模型、vLLM/Ollama 自建、随时换供应商） → 守 Chat Completions。全行业的兼容层都说这门方言，一行 base_url 换后端。

③ 主力用 Claude → Messages + Anthropic 官方 SDK。顶层 system、必填 max_tokens、thinking 块这些规矩，SDK 已替你包好。

一条不变的底线

无论选哪门方言，底层骨架一样：无状态 POST、消息列表全量重发、采样参数与两个现代开关（tools/stream）。理解了骨架，任何新格式都只是“又一种方言”。

真正需要盯紧的不是格式本身，而是它们背后的能力差异：谁的服务端状态、谁的思考块、谁的内置工具——格式是外壳，能力才是选型时真正的筹码。

深挖：Gemini 的 generateContent 长什么样——第四种方言速览▶ 点击展开

Gemini 走的是 Google 自己的 REST 风格：模型名直接放 URL 路径（POST .../v1beta/models/gemini-2.0-flash:generateContent，流式把动词换成 :streamGenerateContent 加 ?alt=sse）。消息叫 contents，角色叫 user 和 model——没有 assistant 这个词；每条消息的内容切成 parts 数组，文本、图片（base64 内联或文件引用）、函数调用各是一种 part。系统提示是顶层 systemInstruction；采样参数（temperature、maxOutputTokens、stopSequences…）全部收进 generationConfig 一个对象。字段命名还混着驼峰与下划线两个习惯——读它的文档时多留个心眼。

对照前三家你会发现：换的只是词汇表，“无状态 + 消息 + 参数”的骨架纹丝不动。这也是各家网关能做到一个入口翻译四方的原因——骨架同源，翻译才便宜。

07今日带走

  • “兼容 OpenAI” = 兼容 Chat Completions 那套端点+请求+响应+流式约定：事实标准，DeepSeek、vLLM、Ollama、千问都说这门方言，base_url 一改就能换后端。
  • 系统提示词三个位置：OpenAI 放消息列表第一条（新模型叫 developer）、Responses 放顶层 instructions、Anthropic 放顶层 system——放错不报错，但人设悄悄失效。
  • 工具全链路：tools 数组声明（名字+描述+JSON Schema）→ 返回认 tool_calls / tool_use 块 → 本地执行 → 结果回传（role:"tool" 消息 / tool_result 块塞 user 消息）。
  • 识别一次调用看三处：结束原因（finish_reason/stop_reason）、类型字段、编号 id；OpenAI 的 arguments 是 JSON 字符串，先校验再执行。
  • 流式 = stream:true，响应变 SSE 事件流：三家事件结构不同（delta 增量 / 类型化事件 / 内容块分段），网关要各写一套解析器。
  • 选型三句：直连 OpenAI 新项目用 Responses；要兼容面守 Chat Completions；主力 Claude 用 Messages+官方 SDK。格式是外壳，能力才是筹码。
