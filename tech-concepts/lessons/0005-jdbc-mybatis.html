JDBC 与 MyBatis：mapper 一行代码，到 SQL 之间发生了什么

天天写 mapper.getUserById(id)，一行进去、一个对象出来——中间那条链路你敢说自己讲得清吗？这篇从 JDBC 的"插座标准"讲到 MyBatis 的动态代理与绑定路由，把六步链路逐环拆开；再讲清一个常被含糊带过的问题：SQL 到底是谁写的（手写路由、MyBatis-Plus 启动注入、条件构造器三层光谱）；最后回答"换国产信创数据库要改什么"——Mapper 一行不动，动的是哪两行。

01场景：一行进去，一个对象出来

Java 后端开发者每天都在写这样的代码：User u = userMapper.getUserById(42L);——一行进去，一个填好字段的对象出来。没有 SQL、没有 ResultSet、没有连接管理。但面试官问一句"中间发生了什么"，很多人只能答到"MyBatis 执行了 SQL"。SQL 是你写的还是框架生成的？接口没有实现类，调用怎么成立的？结果集怎么变成对象的？这三个问题答不圆，等于没讲清。

要理解这层"魔法"，得先回到没有框架的年代。原生 JDBC 查一个用户要六步：拿连接（DriverManager.getConnection）→ 预编译语句（prepareStatement）→ 手动设参（ps.setLong(1, id)）→ 执行（executeQuery）→ 遍历结果集手动逐字段 setter（rs.getLong("id")…）→ 关闭三件资源。三样痛点全在这六步里：SQL 与 Java 代码搅在一起、参数一个个手动设、结果一行行手动搬。MyBatis 解决的就是这三痛——但它到底在 JDBC 之上做了什么、没做什么，先从 JDBC 本身说起。

还有一类现实的担心：项目要换国产信创数据库（达梦、人大金仓）了，持久层代码要大改吗？这篇最后会给出精确答案：换库动的是两行配置，Mapper 一行不动——为什么敢这么讲，读完链路你就明白了。

02JDBC：Java 定的"插座标准"

JDBC（Java Database Connectivity）不是某个产品，是 JDK 里的一套接口标准（java.sql 包）。官方定义原话：它提供"用 Java 访问与处理数据源中数据的 API"，且包含"一个可以动态安装不同驱动来访问不同数据源的框架"。最贴切的比喻是墙上的插座标准：插座形状统一（JDBC 接口），各家电厂的插头（数据库驱动）各自生产，但都必须符合这个形状——Java 代码面对的永远是插座，不关心背后是哪家电。

核心接口一张表：| 接口 | 干什么 |——DriverManager：管理一组驱动、建立连接；Connection：一条数据库会话，创建语句、管事务；PreparedStatement：预编译语句，? 占位符 + setLong(1, x) 设参（参数序号从 1 开始）；ResultSet：结果集，rs.next() 逐行游标。两个必讲行为：其一，? 占位符的参数走"值"通道，不参与 SQL 语法解析——这就是预编译防 SQL 注入的根：用户输入永远只是参数值，不可能变成 SQL 结构（拼接 ' or '1'='1 进 ? 也只是一个普通字符串值）。其二，Connection 的 autoCommit 默认是 true（每条语句自动提交一个事务）；要手动事务就 setAutoCommit(false)，最后 commit() 或 rollback()。

03MyBatis 的真实角色：不写 SQL 的替代品，是路由器

先纠正一个常见含糊：MyBatis 不会替你生成 SQL。它的角色是——你把 SQL 写在 XML 或注解里，它把"Java 方法调用"路由到这条 SQL 上，并自动完成参数绑定与结果映射。对准 JDBC 六步的三大痛点，各给一个解法：

JDBC 的三痛 → MyBatis 的三解

SQL 混在 Java 里 → SQL 独立成 XML/注解：语句与方法分离，SQL 归 SQL、代码归代码。

手动设参 → #{id} 自动绑定：占位符写参数名，框架翻译成 ? 并按类型设参。

手动搬结果 → 自动映射成对象：ResultSet 到对象字段的搬运（含驼峰转换）由框架按映射规则完成。

它没做什么

连接的建立与管理仍在 JDBC/连接池（MyBatis 只是包装了 DataSource）；SQL 语法仍是各家数据库的方言——MyBatis 站在 JDBC 之上，不替代 JDBC。理解这个定位，后面的链路和信创迁移就都顺了。

第 2~3 步：没有实现类的接口，凭什么能调

启动时 MyBatis 扫描 Mapper 接口，为每个接口注册一个 JDK 动态代理；你注入使用的 userMapper，实际是 session.getMapper(UserMapper.class) 这条路给出的代理对象。调用 getUserById 时，代理把"哪个接口的哪个方法"翻译成一个查找键——接口全限定名 + 方法名，去查 MyBatis 配置对象里的语句 Map（每条语句一个 namespace.id 一个条目，启动时由 XML 解析而来——后面 Plus 注入的语句也进这同一个 Map）。MyBatis 官方文档对绑定规则的表述：将映射文件的 namespace 设为接口全限定名后，"命名空间就可以直接映射到同名的映射器类，并将已映射的 select 语句匹配到对应名称、参数和返回类型相同的方法"。也就是说绑定不靠任何魔法注解处理，就是一次字符串对齐：

绑定：接口方法 ↔ XML 语句
# 接口：没有实现类，方法名就是查找键的一半
public interface UserMapper {
    User getUserById(Long id);          // ← id 必须与 XML 的 id 一致
}
# XML：namespace = 接口全限定名，这就是另一半
<mapper namespace="com.demo.mapper.UserMapper">
  <select id="getUserById" resultType="User">
    select * from users where id = #{id}
  </select>
</mapper>
# 查找键 = com.demo.mapper.UserMapper.getUserById = namespace + id

第 4 步：动态 SQL——拼的是结构，不是值

if / where / foreach（官方示例改编）
<select id="findActive" resultType="Blog">
  SELECT * FROM Blog
  <where>
    state = 'ACTIVE'
    <if test="title != null">
      AND title like #{title}          <!-- 值仍走 #{} 预编译 -->
    </if>
  </where>
</select>
# <where> 只在子元素产出内容时才插入 WHERE，并去掉开头的 AND/OR
# <foreach> 常用于 IN 列表：separator="," 在各项之间插逗号

执行时 MyBatis 用 OGNL 表达式（test="title != null"）对参数求值，决定拼进哪些片段，拼装发生在 PreparedStatement 创建之前——拼的是 SQL 结构；而值的位置始终是 #{}，仍走 ? 通道。结构动态、值永远安全，这是动态 SQL 的正确理解姿势。

第 5 步：#{} 与 ${}，一条安全一条危险

官方文档写得很直白：#{id} 会"创建 PreparedStatement 占位符，等价于 JDBC 中用 ? 并调用 ps.setInt(1, id)"——参数走预编译通道，安全。${column} 则是"字符串替换，直接插入 SQL"——官方同时警告：把用户输入用作这类参数"会导致潜在的 SQL 注入攻击"。所以规矩是：值一律 #{}；只有动态表名/列名这种"必须成为 SQL 结构一部分"的场合才用 ${}，且值必须来自白名单，绝不来自用户输入。

第 6 步：ResultSet 怎么变成对象

执行查询拿到 ResultSet 后，MyBatis 按映射规则搬运字段：默认按"列名与属性名一致"匹配；开启 mapUnderscoreToCamelCase 后，数据库的 user_name 自动映射到 userName；列名与属性名完全不同的（如 mobile 列进 phone 属性），用 resultMap 显式声明对应关系。搬运靠反射：实例化对象、逐列 set 进属性——这就是你不用写二十行 setter 的原因，代价只是启动时的映射解析，运行时是纯反射赋值。

05SQL 到底是谁写的：三层光谱

"MyBatis 从函数生成 SQL"是常被说混的一句话——按 SQL 的作者分，其实是一个三层光谱：

纯 MyBatisMyBatis-Plus 内置 CRUD条件构造器 Wrapper
SQL 谁写你，手写在 XML/注解框架：启动时自动注入通用 SQL半自动：方法链描述条件，框架翻译成 WHERE
典型用法<select id="getUserById">userMapper.selectById(42L) 零 SQLwrapper.eq(User::getName, "x")
适合复杂查询、多表、调优 SQL单表的增删改查动态条件组合查询

MyBatis-Plus 官方给自己的定位是"MyBatis 最佳搭档，只做增强不做改变"。它没有另起炉灶——核心机制就一条："启动即会自动注入基本 CRUD"（官方原话）。你继承 BaseMapper<User> 后，selectById / insert / updateById / deleteById 这些方法对应的 SQL，是 Plus 在启动阶段拼装好、按同样的 namespace.id 规则注入进前面链路里查的那个语句 Map的——所以它们跑在和你手写 SQL 完全相同的代理、绑定、参数、映射链路上。LambdaQueryWrapper（eq(User::getStatus, 1) 用方法引用写字段名，编译期就能查出写错）把条件描述翻译成 WHERE 片段，本质也是生成一段 SQL 交给同一套链路执行。

内置方法的 SQL 最终放在哪？是在目录下加了个 XML 文件吗？

不落任何文件。MyBatis 里 SQL 的最终载体本来就不是 XML——XML 只是来源，解析后的形态是 Configuration（内存配置对象）里的 MappedStatement（每个 namespace.id 一条）。Plus 注入走的是源码里 AbstractMethod.inject() 那条链：从实体注解（@TableName/@TableId）解析出表元数据 TableInfo → 每个内置方法（SelectById/Insert…）拿代码里的 SQL 模板 + TableInfo 填出这条 SQL → 调 MyBatis 自己的 builderAssistant.addMappedStatement() 注册进 Configuration——和 XML 解析殊途同归，进的是同一个 Map。启动后打断点看 Configuration.mappedStatements，selectById 和你手写的 getUserById 并排存放。两个细节：① 注入前有查重，同 id 已被 XML/注解定义时 Plus 跳过注入（日志 "Has been loaded by XML…ignoring this injection"）——手写优先于内置，这就是"只做增强不做改变"的物理实现；② Wrapper 更晚一步：SelectList 模板里留的是 ${ew.customSqlSegment} 占位，执行时才把条件翻译成 WHERE 片段填进去。

那 JPA/Hibernate 那种"方法名派生查询"呢？

光谱还能往右延伸一层：Spring Data JPA 的 findByNameAndAge(...) 连方法名都是语义——框架解析方法名直接生成 SQL。代价与收益是同一件事：SQL 不归你写，也就不由你精细控制（复杂查询要么学它的语法要么退回原生 SQL）。MyBatis 系把 SQL 留给你，Plus 只收编"不值得手写的那部分"——两层可以共存：单表交给 BaseMapper，复杂查询照旧手写 XML。

06信创迁移：Mapper 一行不动，动的是哪两行

回到开头的问题：MySQL 换达梦（DM8）或人大金仓（KingbaseES），持久层改什么？按第 02 节的分层图答案已经出来了——MyBatis 只产 JDBC 调用，方言差异被 JDBC 的驱动层隔离；换库 = 换驱动 jar + 改 url/driver 配置，Mapper 接口一行不动（XML 里的方言写法是另一回事，后面单独说）：

换库实际改的两行（数据源配置）
# MySQL
driver-class-name: com.mysql.cj.jdbc.Driver
url: jdbc:mysql://host:3306/db?useSSL=false
# 达梦 DM8：驱动换 DmJdbcDriver18（兼容 Oracle 语法系）
driver-class-name: dm.jdbc.driver.DmJdbcDriver
url: jdbc:dm://host:5236/SYSDBA
# 人大金仓 KingbaseES：PG 内核，走兼容模式（支持 MySQL/Oracle 模式）
driver-class-name: com.kingbase8.Driver
url: jdbc:kingbase8://host:54321/db

达梦和金仓的"路数"值得记一句：达梦深度兼容 Oracle 语法系（自增用 SEQUENCE（数据库预建的自增计数器）、大量 Oracle 函数行为），驱动 DmJdbcDriver 对应 JDBC 4.2 标准；金仓基于 PostgreSQL 内核发展，PG 生态工具基本直接可用，另提供 MySQL/Oracle 兼容模式（如 MySQL 模式下适配了 NOW()、IFNULL 这类写法）。

那用着 MyBatis-Plus 的项目呢？——单表 CRUD 全是框架自带方法，复杂 SQL 才手写 XML。适配责任按 SQL 来源分四层，完全不同：

SQL 来源适配动作原因
① BaseMapper 内置 CRUD零改生成的是基础标准 SQL（WHERE id=? / 标准 INSERT），达梦天然认——框架生成的 SQL 反而是最稳的部分
② 分页 selectPage一行配置唯一有真正方言行为的内置功能：分页拦截器按 DbType 生成分页 SQL，官方支持列表含达梦/金仓/OceanBase/GaussDB——DbType.MYSQL 换 DbType.DM（官方建议显式配；3.5.9+ 分页拆到 mybatis-plus-jsqlparser 依赖）
③ 主键策略配置/注解层IdType.AUTO 依赖库自增，达梦 Oracle 模式换 @KeySequence 指向序列；最省心 ASSIGN_ID 雪花——框架侧生成、与库无关（3.3.0 起默认），主键的信创问题直接消失
④ XML + Wrapper 手写片段真工作量在这wrapper.apply("date_format(...)")、last("limit 1") 是手动塞进框架的 SQL 片段——方言风险与手写 XML 完全同级，用同一份方言清单扫描；XML 用 databaseIdProvider 多方言共存

适配实操：分页、主键、多方言共存的配置怎么写

② 分页拦截器 DbType · ③ 主键两写法
// ② 分页：DbType 换成 DM（官方支持列表：达梦/金仓/OceanBase/GaussDB…）
@Bean
public MybatisPlusInterceptor mybatisPlusInterceptor() {
    MybatisPlusInterceptor i = new MybatisPlusInterceptor();
    i.addInnerInterceptor(new PaginationInnerInterceptor(DbType.DM));
    return i;   // 官方提醒：多个插件时，分页最后添加
}
// ③ 主键写法一：ASSIGN_ID 雪花——框架侧生成，与数据库无关（3.3.0 起默认）
@TableId(type = IdType.ASSIGN_ID)
private Long id;
// ③ 主键写法二：沿用数据库序列（达梦 Oracle 模式 / PG）
@TableId(type = IdType.INPUT)
@KeySequence("SEQ_USER_ID")     // insert 前从序列取值回填
private Long id;
④ 多方言共存：databaseIdProvider 双版本语句
# 配置数据库厂商标识：给每家库起个短名
<databaseIdProvider type="DB_VENDOR">
    <property name="MySQL"   value="mysql"/>
    <property name="DM DBMS" value="dm"/>      # 达梦
</databaseIdProvider>
# 同一个方法写两版语句，运行时按当前连接自动选
<select id="findRecent" databaseId="mysql" resultType="Order">
    select * from t_order order by create_time desc limit 10
</select>
<select id="findRecent" databaseId="dm" resultType="Order">
    select * from (select * from t_order order by create_time desc) where rownum <= 10
</select>
# 注意：property 的 name 必须写驱动自报的产品名（达梦上报 DM DBMS）——写错则短名永不生效
# Wrapper 手塞片段同理：date_format 是 MySQL 写法，达梦 Oracle 模式要换 to_char
w.apply("date_format(create_time,'%Y-%m') = {0}", month)
⚠
一句话：Plus 自带的动配置不动代码；手写的两处（XML + Wrapper 片段）才是迁移真工作量

达梦侧开 MySQL 兼容模式能兜住 LIMIT/NOW() 等写法，但"能跑"不代表行为一致——SQL 兼容性扫描与回归测试省不得

如果同一套 Mapper 要在多方言数据库上共存，MyBatis 还有内置方案：databaseIdProvider 配置后，语句可按 databaseId 区分（如同一 id 写 MySQL 版和达梦版两条），运行时按当前连接自动选择——方言差异被收敛在 SQL 文件里，Java 侧依然一行不动。

07今日带走

  • JDBC 是插座标准，驱动是插头：java.sql 只定接口，厂商各发驱动实现——换库换插头，代码面向插座不变（JDBC 4.0 起 SPI 自动注册，无需 Class.forName）。
  • ? 占位符是防注入的根：参数走"值"通道不参与语法解析；Connection 的 autoCommit 默认 true，手动事务要显式关。
  • MyBatis 不生成 SQL，它是路由器：动态代理拦截方法调用 → 按 namespace+方法名查语句 Map（XML 解析与 Plus 注入进同一个 Map）→ 参数绑定 → 结果反射映射。
  • #{} 走预编译，${} 是字符串拼接：值一律 #{}；${} 只给表名/列名且必须白名单。
  • SQL 的作者是三层光谱：纯 MyBatis 手写路由；MyBatis-Plus"启动即自动注入基本 CRUD"（BaseMapper 零 SQL，手写优先于内置）；Wrapper 方法链半自动——底层同一套链路。
  • 信创换库 = 换驱动 jar + 改两行配置，Mapper 一行不动：适配按 SQL 来源分四层——内置 CRUD 零改、分页换 DbType、主键优先雪花、XML 与 Wrapper 手写片段用同一份方言清单扫。
