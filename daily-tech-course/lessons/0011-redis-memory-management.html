Redis 内存管理：淘汰策略、过期删除与碎片治理（系列收官）

📅 2026-08-25（周二） ⚡ Redis 系列 · 第 7 讲 · 收官 ⏱ 预计阅读 10 分钟 🎯 maxmemory-policy / 惰性+定期删除 / 内存碎片 / LFU

一、一场由"内存水位"引发的连环事故

某晚高峰，营销系统的 Redis 集群触发告警：maxmemory 使用率达到 95%。十分钟后，业务侧开始批量报错 OOM command not allowed when used memory > 'maxmemory'——该实例用的是默认策略 noeviction，内存打满后所有写请求（包括 SET/EXPIRE）直接被拒。更糟的是，临时切换到 allkeys-lru 后又出现延迟抖动：Redis 在内存高水位下持续"采样—淘汰"，每秒淘汰数千个 key，主线程压力骤增。

复盘发现三重问题叠加：① 容量规划缺失，没有预留淘汰缓冲；② 大量 key 没设 TTL，导致冷数据永远占着内存；③ 碎片率 1.6，18GB 有效数据实际占了 29GB 物理内存。今天把 Redis 内存管理一次性讲透：内存账本怎么算、过期 key 怎么删、8 种淘汰策略怎么选、碎片怎么治。

二、原理：先看懂 Redis 的"内存账本"

排查内存问题的第一步永远是 INFO memory，但三个核心指标经常被误读：

  • used_memory：Redis 通过分配器（jemalloc）申请的内存总量，包含数据、字典元数据、客户端缓冲区、复制积压缓冲等；
  • used_memory_rss：操作系统视角下进程占用的物理内存（Resident Set Size）；
  • mem_fragmentation_ratio = rss / used_memory，即碎片率。
used_memory（分配器视角）
数据 + 元数据 + 客户端 buffer + repl-backlog
vs
used_memory_rss（OS 视角）
进程实际驻留物理内存（含碎片页）
碎片率 = RSS / used_memory —— 两者差值就是"碎片 + 分配器 overhead + fork COW"
1.0 ~ 1.5
健康区间（jemalloc 正常开销）
> 1.5
碎片严重，或正处 fork COW / 客户端 buffer 暴涨
< 1.0
危险：部分内存被换出到 swap，性能断崖
# 一条命令看全内存画像
redis-cli info memory | egrep \
  "used_memory_human|used_memory_rss_human|mem_fragmentation_ratio|maxmemory_human|maxmemory_policy|mem_not_counted_for_evapor"

# 让 Redis 自己"看诊"（4.0+，会给出碎片/lua/大 client buffer 诊断）
redis-cli memory doctor

# 逐项拆解内存去向：字典元数据 / 各 db key 数 / 客户端 buffer
redis-cli memory stats
⚠️ 常见坑：碎片率 > 1.5 未必是碎片 fork 做 RDB/AOF rewrite 时的 写时复制（COW）会让 RSS 短暂翻倍；某个慢客户端把输出缓冲区撑到几百 MB 也会推高 RSS。看到高碎片率先问：最近有没有 bgsave？client list 里有没有 omem 巨大的连接？

三、过期删除：惰性 + 定期的组合拳

key 设置了 EXPIRE 后，Redis 不会为它启动定时器。到期的 key 依靠两个策略协同清理：

  • 惰性删除：每次访问 key 时先检查时钟，过期就地删除并返回 nil。代价几乎为零，但冷 key 永远不会被清理；
  • 定期删除：由 hz 控制（默认 10，即每 100ms 一轮），每轮从设置了 TTL 的 key 中随机抽 20 个检查，删除已过期的；若过期占比超过 25%，立即再抽一轮继续。这是一个自适应循环——过期 key 越多清理越勤，但单轮有时间上限，避免阻塞主线程。

架构含义：定期删除是概率性的，"设置了 TTL"不等于"到期即删"。如果你有 1000 万个一次性 key 同时到期，它们会分批被清掉，期间内存水位持续偏高——大批量过期应把 TTL 加随机抖动打散，而不是精确同一时刻。

💡 主从架构注意 从库不主动删除过期 key，只等主库同步 DEL 指令（读取时按逻辑过期返回空）。所以过期 key 的内存占用要在主库视角评估，从库 RSS 偏高属正常现象。

四、8 种淘汰策略：怎么选才不踩坑

当 used_memory > maxmemory 时触发淘汰。8 种策略 = 作用域（allkeys / volatile）× 算法（LRU / LFU / random / ttl），外加默认的 noeviction：

策略候选范围算法适用场景
noeviction（默认）不淘汰写命令报错Redis 当存储用（分布式锁、去重表、队列）用作缓存时是事故之源
allkeys-lru全部 key近似 LRU纯缓存首选，key 没设 TTL 也无所谓
allkeys-lfu全部 keyLFU（4.0+）热点分明的缓存，防"偶发批量扫描"污染
volatile-lru / volatile-lfu仅带 TTL 的 key近似 LRU / LFU混合用途：既存永久数据又存缓存，永久 key 永不淘汰
volatile-ttl仅带 TTL 的 key剩余 TTL 最短先走知道"越早过期的越没价值"的业务
allkeys-random / volatile-random全部 / 带 TTL随机访问概率均匀、key 同质化时（少见）
⚠️ volatile 系列的隐藏陷阱 如果实例里没有任何 key 设置 TTL，volatile-* 无 key 可淘汰，行为退化为 noeviction——继续报 OOM 错误。切策略前先 redis-cli --bigkeys 确认 TTL 覆盖情况。

近似 LRU：为什么不用精确 LRU

精确 LRU 需要全局双向链表：每个 key 额外约 24 字节指针，1000 万 key 就要多耗 200MB+，且每次访问都要移动链表节点。Redis 的做法是复用每个对象头里已有的 24bit lru 字段存"最后访问时钟"，淘汰时随机采样 maxmemory-samples（默认 5）个 key，淘汰其中最久未访问的；3.0+ 又加了候选池（eviction pool），多轮采样积累候选，使效果逼近精确 LRU。采样数调到 10 更准，但 CPU 开销随之上升——一般 5 就够。

LFU：按访问频率淘汰（4.0+）

LRU 的软肋是偶发访问：一次离线任务批量扫描 50 万个冷 key，LRU 会误以为它们"最近常用"而把真正的热点挤出去（缓存污染）。LFU 复用同样的 24bit：高 16 位存分钟级衰减时钟，低 8 位存对数计数器（Morris 近似计数，0~255）——不是线性计数，访问次数越多增长越慢，255 就能代表百万级访问。

# LFU 调参（改前先评估访问模式）
CONFIG SET maxmemory-policy allkeys-lfu
CONFIG SET lfu-log-factor 10    # 越大计数增长越慢（10 时约 100w 次访问到 255）
CONFIG SET lfu-decay-time 1     # 每隔 1 分钟未被访问，计数 -1（防"过气网红"占位）

# 观察单个 key 的空闲时间 / 访问计数
OBJECT FREQ hot:key      # LFU 计数
OBJECT IDLETIME hot:key  # LRU 空闲秒数（会刷新时钟，排障专用，别在业务里调）

五、碎片治理：activedefrag 而不是重启

碎片怎么来的？jemalloc 按固定大小类别分配内存，频繁写入长度不一的 value、大量删除后，空闲页散落在各处，分配器无法归还给操作系统——于是 RSS 居高不下。4.0+ 的主动碎片整理可以在不重启的前提下，把数据搬移到连续内存块，把碎片"挤"出去：

# redis.conf（确认编译时使用 jemalloc：INFO server 里的 mem_allocator）
activedefrag yes
active-defrag-ignore-bytes 100mb      # 碎片绝对量低于此值不触发
active-defrag-threshold-lower 10      # 碎片率超过 10% 开始整理
active-defrag-threshold-upper 100     # 碎片率 100% 时整理占 CPU 上限
active-defrag-cycle-min 1             # 整理线程最低 CPU 占比 %
active-defrag-cycle-max 25            # 最高 CPU 占比 %（峰值期调低）

碎片整理本质是用 CPU 换内存，会带来额外延迟（通常 <1ms 量级）。生产建议：碎片率 > 1.5 且持续再开启；开启后观察 latency 与 CPU，逐步调参；同时从业务侧根治——固定 value 尺寸、拆大 key、避免长短混杂写入，比事后整理划算得多。

六、架构师清单：容量规划与监控红线

  • 容量公式：maxmemory ≈ 物理内存 × 50%~70%。余量要覆盖 fork COW、复制积压缓冲、客户端 buffer、碎片（10%~30%）和淘汰缓冲。32GB 机器跑缓存，maxmemory 设 20GB 是稳妥起点；
  • 缓存定位：选 allkeys-lru 或 allkeys-lfu，且 maxmemory 之上留 20% 水位缓冲——高水位下持续淘汰会引发延迟抖动（"淘汰风暴"）；
  • 存储定位：选 noeviction，但必须配容量冗余 + 水位告警（80% 预警 / 90% 严重），淘汰丢数据比报错更可怕；
  • 监控四指标：used_memory 水位、mem_fragmentation_ratio、evicted_keys（每秒淘汰数）、expired_keys。evicted_keys 持续大于 0 = 容量不足或 TTL 缺失；
  • Cluster 注意：maxmemory 与淘汰策略是节点级配置，逐节点设置；hash 倾斜时单节点先触发淘汰，扩容前先看热分片。

📌 今日要点

1
三个内存指标
used_memory（分配器）vs RSS（OS）；碎片率 1.0~1.5 健康，>1.5 先排除 fork COW / 大客户端 buffer，<1.0 说明在用 swap。
2
过期 = 惰性 + 定期
定期删除每 100ms 抽样 20 个、过期超 25% 再来一轮；大批量同时过期要加随机抖动，从库不主动删过期 key。
3
策略选型一句话
纯缓存 allkeys-lru/lfu；混合用途 volatile-*（确认 TTL 覆盖）；存储定位 noeviction + 水位告警 + 容量冗余。
4
LFU 防缓存污染
对数计数器 + 分钟衰减，天然抵御偶发批量扫描；调 lfu-log-factor 控制敏感度、lfu-decay-time 控制"过气"速度。
5
碎片用整理不用重启
activedefrag 用 CPU 换内存，治本是固定 value 尺寸、拆大 key；重启前必须做主从切换 + 缓存预热方案。

🧠 架构师思考题

Q1你们系统有个后台任务每晚批量"预热"50 万个商品 key（只访问一次），次日发现真正的热点 key 被大量挤出缓存。为什么 LRU 会这样？换 LFU 就万事大吉了吗？还要调哪些参数？▶

解题方向

本题考察 LRU/LFU 的失效场景与 LFU 参数的架构权衡，分三层回答：

① 为什么 LRU 会误伤

LRU 的唯一依据是"最后访问时间"。预热任务把 50 万个冷 key 挨个访问一遍，每个 key 的 lru 时钟都被刷新成"刚刚"，而真正的热点如果恰好有几分钟没被访问（比如凌晨低峰期），在采样淘汰时反而比刚扫过的冷 key"更旧"，于是被挤出去。这是典型的缓存污染：LRU 区分不了"访问一次"和"访问一万次"。

② 为什么 LFU 能缓解

LFU 的 8bit 对数计数器按频率计数：新 key 初始计数为 5，预热扫一次最多涨到 6~7；而历史热点计数早已到几十上百。淘汰采样时冷 key 几乎总是最小分被逐出，热点得以保全。

③ 换 LFU 不是万事大吉——参数与代价

  • lfu-log-factor 过大 → 计数涨不动，所有 key 都挤在低位，退化成近似随机淘汰；过小 → 一访问就到高位，又变成"一次性热点占死内存"，需要按业务 QPS 做压测标定；
  • lfu-decay-time 决定衰减速度：商品热点有周期性（大促前后切换），衰减太慢会导致"上周的热点"赖着不走，衰减太快热点身份保不住；
  • 另一个工程解法是不换策略，改用法：预热任务绕开主缓存（预热到本地/独立实例），或对预热 key 打短 TTL——架构上"隔离污染源"往往比调算法参数更稳。

参考结论：换 allkeys-lfu + 标定 log-factor/decay-time 是正解之一，但先评估能否把批量扫描隔离出缓存路径——能隔离就不动全局策略，改动面最小。

Q2线上单实例 used_memory 18GB、RSS 27GB、碎片率 1.5 持续两周，业务量没增长。你会怎么排查和治理？如果最终决定"重启回收"，直接 shutdown 有什么风险，怎么安全地做？（进阶）▶

解题方向

这是一道完整的内存排障 + 变更管控题，考察"先定位、再治理、变更要有回退路径"的架构素养。

第一步：确认碎片是真碎片

  • 对照 bgsave/aof-rewrite 时间线，排除 fork COW 的瞬时 RSS 膨胀（COW 是脉冲，碎片是持续）；
  • client list 查 omem 异常的慢消费客户端（Pub/Sub 或从库全量同步未完成都会撑大输出缓冲）；
  • MEMORY DOCTOR / MEMORY STATS 让 Redis 给出官方诊断；INFO memory 里的 mem_not_counted_for_evict 是否巨大。

第二步：治理优先级

① 业务侧先治大 key 与长短混杂写入（用 --memkeys 找出元凶）；② 确认 mem_allocator 是 jemalloc 后，低峰开启 activedefrag，从 cycle-min=1 小步试跑，观察延迟和 CPU；③ 只有整理无效（如碎片源于历史超大 value 已删）才考虑重启回收。

第三步：直接 shutdown 的三重风险

  • 冷启动雪崩：18GB 缓存清空后，数百万请求同时 miss 打到 DB，可能直接压垮数据库——这是最大的风险；
  • 可用性窗口：单实例重启 = 服务中断；若有 AOF，18GB 数据重放可能要几分钟；
  • Cluster 连锁反应：分片集群中主节点下线触发主从切换，期间该分片写入受影响，若其他从库数据陈旧还可能丢最近写入。

安全重启的标准动作

① 确认有可用的从库且主从同步完成（master_repl_offset 追平）；② 低峰期执行故障转移（sentinel failover 或 cluster failover），让从库转主，业务无感；③ 旧主空实例重启，内存干净归还；④ 预热后再做一次 failover 切回（或保持新拓扑不动）；⑤ 全程盯着 miss 率、DB QPS、分片延迟，随时可中止。没有预热方案的重启 = 定时炸弹。
