TDENGINE · TDengine 系列第 3 讲（数据分发篇 · 数据订阅）

数据订阅：让下游按需拉增量，不再轮询数据库

上一讲在 Pulsar 聊了契约治理，Pulsar 主线告一段落，今天回到 TDengine——把"数据怎么流到下游"讲完。时序平台的经典困局：告警、大屏、同步 ES、规则引擎……每个下游都想知道"有没有新数据"，最直觉的答案是每 5 秒查一次库。今天这期聊 TDengine 内置的数据订阅（TMQ）：它把 WAL 改造成一个保留事件到达顺序的存储引擎，让下游像消费 Kafka 一样按需拉增量——很多场景里，外挂消息队列这一层可以直接省掉。

01五个下游，五把"每 5 秒扫一次"的耙子

某能源平台 4 万块智能电表，写入 第 22 期那套 TDengine 集群。下游有五个消费方：实时告警、设备大屏、数据同步 ES、规则引擎、计费预处理。最初的实现最直觉——每个下游各自轮询：每 5~15 秒执行一次 SELECT * FROM meters WHERE ts > now - 15s。上线三个月，两笔账摆到桌上：

数据库的账：五个下游错峰轮询，白天平均每秒 2~3 次"找最新数据"的查询。每次查询即使没新数据，也要走一遍"定位块—比较时间戳"的路径，叠加起来 DB 全天约 40% 的算力花在回答"没有新数据"上——查询资源被空转轮询吃掉，月度报表一跑，轮询查询的排队延迟先涨，告警反而更慢了。下游的账：平均感知延迟 ≈ 轮询间隔的一半，5 秒轮询平均慢 2.5 秒、最坏 5 秒；想快一倍，查询频率就得翻倍，数据库的账先爆。

真正的爆点是深夜补报：采集端 10:05 断网、10:40 恢复，补报数据的时间戳还是 10:05——而轮询的 WHERE 条件是"最近 15 秒"，35 分钟前的数据永远匹配不上，一路漏到 T+1 对账才发现。三个根因叠在一起：轮询按"墙上时钟"找增量而不是按"写入顺序"；轮询间隔是延迟和负载的双重约束；每个下游独立扫一遍，同一个数据被"发现"了五次。解法只有两条路：外挂一套消息队列把数据再搬一份（架构多一跳、多一份数据、多一套运维），或者用数据库自己把增量吐出来——TDengine 3.0 起内置的数据订阅，就是后一条路。

02原理：WAL 被改造成了一个"消息队列"

三个关键机制

① WAL 的第二职业。TDengine 为 WAL 自动建立索引以支持快速随机访问，并提供可配置的文件滚动与保留策略（时间、大小双维度）——官方的说法是"把 WAL 改造成一个保留事件到达顺序的、可持久化的存储引擎"。消费时按当前 offset 从 WAL 直接读数据，再用与普通查询同一套查询引擎做过滤和变换：这就是查询 topic 能在服务端完成 WHERE voltage > 240 过滤的机理——下游只收到需要的数据，而不是全量搬运后再各自筛。② at-least-once 投递。消费组带 ACK 机制：处理完提交位点，崩溃重启后从上次位点继续——语义与 第 21 期聊的消息队列一致，代价也一样：可能重复投递，消费端必须幂等。③ 消费组的 Kafka 式模型。同组消费者分摊 vgroup（一个 vgroup 同一时刻只归一个消费者），不同组进度独立；消费者异常退出约 12 秒触发 rebalance，状态转 LOST 后约 1 天自动清理，新增消费者约 2 秒完成加入——API 设计贴近 Kafka 习惯，bootstrap.servers、group.id、auto.offset.reset 这些参数名原样照搬，Kafka 团队几乎零学习成本。

三种 topic：粒度从细到粗

类型语法要点结构行为典型用途
查询 topicCREATE TOPIC t AS SELECT ... WHERE ...（支持标量函数，不支持聚合与窗口）结构在建 topic 时定死；被订阅的列不能删改，表结构变了新列不出现（3.3.9 起可 RELOAD TOPIC 重载）告警、大屏——服务端过滤，只推需要的数据
超级表 topicCREATE TOPIC t AS STABLE stb [WHERE 标签条件]（WHERE 只能用 tag/tbname）返回非结构化数据，结构随超级表演进；不锁表结构变更；返回数据不含标签按超级表全量增量分发；WITH META 供迁移工具用
数据库 topicCREATE TOPIC t AS DATABASE db整库全部表数据（WITH META 时含建表/删表/改表语句）数据同步、跨系统迁移——官方也提醒属高级模式，易错

选型直觉

粒度越细（查询 topic）越省下游的过滤成本，但结构锁得越死；粒度越粗（库 topic）越灵活，但下游要自己应对结构变化和全量数据。默认答案：业务分发用查询 topic，迁移同步用 WITH META 的超级表/库 topic。另注意集群默认 topic 上限 tmqMaxTopicNum = 20——topic 是有代价的对象，别把订阅当视图滥用。

03架构设计：保留窗口是一块要花钱的地皮

WAL 保留的三笔账

数据订阅所有架构权衡都压在一个事实上：WAL 的压缩率远低于 TSDB 的列式存储（官方建议保留时长一般不超过几天），而消费位点不受 WAL 清理机制保护——清理只看时间与大小，不看谁还没消费。三笔账：地皮账：保留窗 = 写入吞吐 × 窗口时长。日写 300GB 的库，留 4 小时就是 50GB 量级的额外 WAL 空间，留 3 天就是 TB 级——保留窗按"最慢消费者允许落后多久"倒推，再放一倍余量。落后账：消费者故障 8 小时，保留窗 4 小时——重启后位点指向的数据已被回收，只能按 auto.offset.reset 重置（跳过丢失段或从头再来），丢增量在订阅模型里是设计内行为，不是故障。堆积账：一个慢消费组不影响别人（各写各的位点），但它决定你必须把保留窗开多大——最慢的那个消费者，替全集群决定了 WAL 预算。

两种消费拓扑：触发与搬运

触发模式（替轮询）：告警/规则引擎直接消费查询 topic，数据到达即触发计算——延迟从"轮询间隔的一半"降到亚秒级，且补报数据按写入顺序到达，10:05 的迟到数据不会再被 now-15s 的窗口漏掉。搬运模式（替双写）：一个消费组把增量搬去 ES/缓存/异地，写侧不再多写一份——原来"写 TDengine + 写 ES"的双写一致性难题（两套事务域），退化成"消费 + 幂等重试"的单向链路。更进一步，搬运途中还能顺手做轻聚合（1 分钟均值再写回 TDengine 降采样表），把 第 22 期的流计算降采样换成显式可控的消费管线。

维度TDengine 数据订阅轮询查询外挂消息队列
数据份数一份（WAL 复用）一份两份（库 + 队列）
延迟亚秒（写入即推）≈ 轮询间隔/2亚秒
库负载按需拉取，无空转持续空转扫描零（不碰库）
迟到/补报数据按写入顺序到达 ✅按墙上时钟漏掉 ❌取决于生产端逻辑

回溯窗口WAL 保留窗内有限全历史保留期内
削峰/复杂路由弱—强（队列本色）

边界判断

数据订阅不是消息队列的替代品——官方定位是"以数据分发为中心的场景可以省掉外部队列"。判断式很简单：需求是"新写入的时序数据分发给若干下游"，用 TMQ；需要削峰填谷、延迟队列、复杂路由、事务消息，上 Pulsar/Kafka。两者也能叠着用：TMQ 消费 → 规则加工 → 写 Pulsar 供多方消费，库只被消费一次。

版本坐标（2026-10）

3.0 重写了数据订阅（当前 TMQ 形态的起点）；3.2 起支持 vnode 迁移与分裂场景下的订阅（红线：订阅依赖 WAL，而迁移不同步 WAL——动 vgroup 前必须先把 WAL 消费完），同年 auto.offset.reset 默认值变更；3.3.6.0 起 DROP TOPIC/CONSUMER GROUP 支持 FORCE；3.3.7.0 起 MQTT 客户端可直接订阅；3.3.9 起 RELOAD TOPIC 让表结构变更无需重建订阅；当前 3.4.x（2026-02 发布 3.4.0.0，流计算与虚拟表性能大幅优化），升级注意 3.4 客户端必须先行升级。

04实战：三段落地

片段一：建库开保留窗，建 topic 定粒度

-- 开订阅的库，先给 WAL 留地皮：按最慢消费者倒推
CREATE DATABASE power WAL_RETENTION_PERIOD 14400   -- 4h
    WAL_RETENTION_SIZE 1073741824                    -- 1TB KB 兜底
    WAL_ROLL_PERIOD 3600  WAL_SEGMENT_SIZE 262144;   -- 1h / 256MB 滚动

-- 告警用查询 topic：过滤下推，只推过压数据，带表名定位设备
CREATE TOPIC topic_overvoltage AS
    SELECT ts, current, voltage, tbname, groupid
    FROM power.meters WHERE voltage > 240;

-- 全量分发用超级表 topic：结构随表演进，不锁 DDL
CREATE TOPIC topic_meters_all AS STABLE power.meters;

片段二：Java 消费者（手动提交 + 幂等键）

Properties props = new Properties();
props.setProperty("bootstrap.servers", "td1:6030");
props.setProperty("group.id", "alert-group");          // 组内分摊 vgroup
props.setProperty("auto.offset.reset", "latest");      // 无位点时只追新数据
props.setProperty("enable.auto.commit", "false");      // 处理完再提交
props.setProperty("msg.with.table.name", "true");      // 默认 false！没表名拿不到设备
props.setProperty("value.deserializer", "...MetersDeserializer");

try (TaosConsumer<MetersRow> consumer = new TaosConsumer<>(props)) {
    consumer.subscribe(List.of("topic_overvoltage"));
    while (running) {
        for (ConsumerRecord<MetersRow> r : consumer.poll(Duration.ofMillis(500))) {
            alertEngine.fire(r.value().getTbname(), r.value().getVoltage(),
                             idempotentKey(r));        // 幂等键防重复投递
        }
        consumer.commitSync();                          // 处理完成才推位点
    }
}

片段三：订阅可观测性三板斧

SHOW TOPICS;            -- topic 台账：类型、SQL、库
SHOW CONSUMERS;         -- 消费者：组、订阅状态（READY/LOST）
SHOW SUBSCRIPTIONS;     -- 消费组 × vgroup 分配与位点推进
-- 巡检口径：位点长时间不动 + 消费组仍在 = 堆积告警
--          保留窗口口 = NOW - WAL_RETENTION_PERIOD，位点不得早于它

五个必踩的坑：① msg.with.table.name 默认 false——消息里不带子表名，设备维度直接丢失，查半天才发现"数据都有但不知道是谁的"；用超级表 topic 时标签也不随数据走，设备维度要靠表名自己带。② WAL 保留参数没配就上生产——单副本默认落盘即删，消费组重启一次就从 latest 重来，增量丢了都不知道。③ 把订阅当视图无限建——topic 上限默认 20，且每个查询 topic 都占 WAL 读取路径，多了互相拖累。④ 消费端不幂等——at-least-once 必然重复投递（重启、rebalance 都会），告警去重键、ES 写入用 (tbname, ts) 做 upsert。⑤ 消费者数超过 vgroup 数——多出来的消费者纯空转还占连接；先 SHOW SUBSCRIPTIONS 看 vgroup 数再加人。

✅ 数据订阅体检清单

☐ 开订阅的库显式配置 WAL_RETENTION_PERIOD/SIZE（按最慢消费者倒推 ×2 余量）　☐ auto.offset.reset 显式声明（新组上线语义明确）　☐ msg.with.table.name=true 且消费端确认设备维度可用　☐ 消费端幂等（幂等键/upsert）已落地并演练过重启重放　☐ 位点推进进监控（不动即告警），位点落后保留窗的差值做容量预警　☐ 消费者数 ≤ vgroup 数（SHOW SUBSCRIPTIONS 核对）　☐ 消费者优雅退出（unsubscribe/close，别等 12 秒 rebalance）　☐ vgroup 迁移/分裂前先排空 WAL 消费　☐ topic 台账季度评审（tmqMaxTopicNum 不是免费额度）　☐ 迟到数据链路演练：补报一条 35 分钟前的数据，验证端到端到达

05今日要点

  • 轮询的三宗罪：空转吃掉数据库算力（40% 花在回答"没有新数据"）、延迟与负载互相锁死、按墙上时钟找增量会漏掉补报数据——数据订阅按写入顺序推增量，三个问题一起解。
  • 机制内核：WAL 的第二职业——索引化的 WAL + 统一查询引擎 = 保留事件到达顺序的消费源；数据只有一份，写入即发布，查询 topic 的过滤在服务端完成。
  • 保留窗口是要花钱的地皮：WAL 压缩率远低于 TSDB，清理只看时间/大小不看消费进度——最慢的消费者替全集群决定 WAL 预算；落后超窗丢增量是设计内行为。
  • Kafka 式消费组，at-least-once 投递：组内分摊 vgroup、组间进度独立、异常退出 12 秒 rebalance——投递语义与外挂队列一致，消费端幂等一个都不能少。
  • 边界判断：需求是"时序增量分发"用 TMQ 省掉外挂队列；要削峰、延迟队列、复杂路由、事务消息，老老实实上消息队列——两者还能叠着用。

06架构师思考题

题目一：你要把实时告警链路从"5 秒轮询"迁到数据订阅。当前配置：日写入 300GB，告警服务双实例部署，历史上最长的下游故障是 8 小时（那次 ES 同步链路挂了）。① WAL 保留窗怎么定？给出推导过程和参数。② 告警服务双实例消费同一个 topic，部署上要注意什么？消费端代码要补什么？③ 迁移后第二周，值班同学反馈"告警偶尔重复触发"，这是缺陷吗？怎么治？▶ 点击展开解析

🔍 逐问拆解

① 保留窗由"允许落后多久"倒推，不是拍脑袋给个大数。约束链：最坏故障恢复时间 8 小时 → 保留窗必须 ≥ 8 小时才敢说"故障期间的数据不丢"；再放一倍余量应对"恢复后发现还要回放重算"的场景 → 16 小时起步，配 24 小时（一天）便于运维记忆。空间核算：日写 300GB → 24 小时保留 ≈ 300GB 量级的额外 WAL 空间（WAL 压缩率低，不能按 TSDB 的 1/10 压缩比估算），确认 vgroup 所在节点磁盘余量 ≥ 2 倍；再配 WAL_RETENTION_SIZE 做大小兜底，防止吞吐突增（比如批量补报）把盘撑爆。反过来验证：如果磁盘只够留 4 小时，就要把"告警链路允许丢 4 小时以上故障窗的增量"写进架构决策记录，并给告警链路加"恢复后从 TSDB 补扫"的兜底——保留窗不足时，订阅只管实时、TSDB 查询管补偿，两条腿走路。

② 双实例 = 一个消费组两个消费者，注意三点。其一，分摊单位是 vgroup：先 SHOW SUBSCRIPTIONS 看目标 topic 覆盖多少个 vgroup，消费者数 ≤ vgroup 数才有意义（超出的空转）；其二，两个实例用同一个 group.id 才是"分摊"，配错了组名就变成两份全量、告警双发；其三，优雅退出：发版停机走 unsubscribe/close，不要 kill -9——异常退出要等约 12 秒才触发 rebalance，这 12 秒里分到的 vgroup 无人消费，高频告警链路能感知到停顿。消费端代码要补的是幂等：at-least-once 语义下，rebalance 和重启都会造成消息重复投递，告警去重键用 (tbname, ts, 告警规则 ID) 在 Redis 里做短窗口去重，或者让告警面板天然支持"同键覆盖显示"。

③ 不是缺陷，是 at-least-once 的固有行为，治法在消费端不在传输端。重复的来源：enable.auto.commit 或手动 commit 之前的崩溃（处理了但没来得及提交位点，重启后重投）、rebalance 期间的边界消息。想从传输端消灭重复只能退回"先提交再处理"，那会把语义换成 at-most-once——丢告警比重复告警贵得多，方向反了。正确姿势就是幂等消费：去重键的 TTL 覆盖"最大重投延迟"（rebalance 周期 + 重启窗口，给几分钟够了）；更彻底的是把告警动作做成状态化（"设备 X 已在告警中"是状态，重复触发只是状态机的重复输入，天然收敛）。这和 第 21 期的结论同构：投递语义选完之后，幂等永远是消费端的功课。

题目二：同步 ES 的链路用超级表 topic 搬了一年，某天 ES 同学反馈"最近三天的数据少了一块"，排查发现：三天前凌晨该库做过一次 vgroup 迁移，同步服务当晚正好在重启窗口。① 数据丢失的机理是什么？为什么"重启 + 迁移"两个各自无害的操作叠在一起就出事？② 立即止损怎么做？长期补强做哪三件事？③ 如果这条链路的消费端换成"先提交位点、再异步批量写 ES"（为了吞吐），风险面怎么变化？▶ 点击展开解析

🔍 逐问拆解

① 机理：订阅绑定的 WAL 在 vgroup 迁移时不随迁。官方文档明确：订阅依赖 WAL 文件，而 WAL 不在 vnode 迁移/分裂时同步——迁移前没消费完的 WAL 数据，迁移后无法继续消费。当天的时间线是：同步服务重启（位点停在迁移前的某个 offset）→ 迁移执行（旧 vgroup 的 WAL 剩余段作废）→ 服务恢复，从位点继续拉，但那段数据已经"不在了"——于是位点跳过了丢失段继续推进，监控上一切正常，静默丢失比崩溃丢失危险一个量级。单独看每个操作都没错：重启窗口丢了的消息本来会在重启后补上（位点还在）；迁移本来也要求"先消费完 WAL 再动"（运维手册写了，但没人把"有个慢消费组"和"能迁移"关联起来）。叠在一起出事，是因为两条纪律分别属于两个团队的知识域——这是订阅这类"跨库中间件特性"特有的组织风险。

② 止损：从 TSDB 补数，不是从订阅补。丢失段的数据在 TSDB 里完好（WAL 回收不影响已落盘数据），按丢失时间窗 + 库表范围直接 SELECT 拉出来重写 ES，幂等键 (tbname, ts) 保证重写安全。长期补强三件事：其一，迁移前置检查——vgroup 迁移/分裂的 runbook 第一条改为"SHOW SUBSCRIPTIONS 确认所有消费组位点已推到最新，否则先等或先停"；其二，对账巡检——订阅链路必须有独立对账（TSDB 按小时 count vs ES 按小时 count，差值告警），本次事故拖了三天才发现，就是缺这条；其三，位点监控——消费组位点与写入水位（endOffsets）的差值进大盘，位点长时间不动、位点倒退、位点与保留窗边界距离过近，三个都要告警。

③ 风险面从"丢"挪向"更隐蔽的丢"，且窗口扩大。先提交再处理 = 处理失败（写 ES 失败、进程崩溃在提交后）的那批消息永久跳过——语义从 at-least-once 动等价于 at-most-once，而且失败是无声的：位点已推进，重启后从新位点继续，连"重投"都不会发生。吞吐焦虑的正确解法不是先提交，而是：批量攒批 + 写完再提交（poll 500ms 攒一批，ES bulk 成功后一次 commitSync——批量化本身就能把吞吐拉起来）；真要异步，就必须给"已提交未写入"的段加本地缓冲 + 失败回补，复杂度立刻超过收益。这个取舍和 第 21 期消费端"先处理后 ack"是同一条纪律：位点是承诺，提交之前先兑现。
