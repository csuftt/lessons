Spring Cloud Gateway 流量入口治理：把"转发"做成"防线"

上一讲聊了东西向的 OpenFeign 调用治理，今天把视线拉回南北向——全公司流量都要经过的那道门：Spring Cloud Gateway。很多团队的网关是"路由配好、能转发"就上线了，而它的默认值哲学是"演示友好"：连接超时 45 秒、响应超时不设限、连接池弹性无上限还不回收空闲连接。这一讲从一次"单下游 GC，全站网关雪崩"的复盘讲起：一次请求穿过网关的三段旅程、三个默认值陷阱、响应式网关独有的"阻塞 event loop"大坑，最后落到一套可以抄走的生产配置——超时、连接池、限流、金丝雀一次配齐。

01一次"单下游 GC，网关全站雪崩"的复盘

某电商中台 40 个服务用 Spring Cloud Gateway 做统一入口，路由表配了几十条，"能转发"阶段一切安好。大促预热第一晚，营销服务一台实例 Full GC 停顿十秒——按剧本这本该是一次"营销接口抖十秒、熔断兜底"的局部事件，实际剧本却是：网关到营销的请求全部挂死等待。原因在三个默认值：Gateway 的 response-timeout 默认不设限（下游不回，网关就永远等）；连接池默认 ELASTIC 弹性模式无连接数上限，挂死的连接占着，新请求就继续新建 TCP；而 max-idle-time 默认为空，空闲连接永不回收。

于是连接数像吹气球一样涨：入口 QPS 持续涌入 → 网关→营销的连接一条条堆积 → 节点的内存、文件描述符、TCP 表全线飙升。最要命的是故障外溢：event loop 与连接资源被慢路由大量占用，不经过营销服务的订单、库存路由也开始排队变慢——网关是全公司流量的咽喉，它的问题没有"局部故障"这个选项。营销服务 GC 早就结束了，网关的连接数却半小时下不来（空闲连接不回收，华为云那个著名的 TCP 连接暴涨 case 就是同一机制）。复盘还有第二个发现：有团队在全局过滤器里写了同步 JDBC 查日志——网关的 worker 线程就是 CPU 核数个 event loop，一个阻塞调用占住一个 loop，几百并发就把整个网关拖进泥潭。结论：网关的默认值必须上线第一天就显式重写，而且要按"防线"而不是"转发器"来设计它。

02原理：一次请求穿过网关的三段旅程

三段旅程看清了，三个"默认值陷阱"就一目了然。第一，connect-timeout 默认 45 秒：这是源码里 HttpClientProperties 的默认值（毫秒计的 45000），对内网毫秒级握手来说宽到离谱——下游实例死亡时，网关要傻等 45 秒才放弃。第二，response-timeout 默认不设限：01 节挂死等待的直接来源，网关是全链路超时预算的天花板，天花板"不存在"等于把 0031 期讲的"逐层递减漏斗"整个掀翻。第三，连接池默认 ELASTIC 且 max-idle-time 为空：弹性池无上限意味着下游变慢时连接无限扩张，空闲连接不回收意味着故障恢复后资源也不回来——生产要切 fixed 池 + 显式 max-connections + max-idle-time。第四个坑是响应式独有的：worker 线程默认就是 CPU 核数个 event loop，任何阻塞调用（JDBC、同步 HTTP、大 body 读进内存）都会占住 loop 拖垮全部路由——需要阻塞就 boundedElastic 调度器隔离，需要读 body 就想清楚内存账。

版本现状与命名空间迁移（2026-09 口径）

当前主版本线为 5.0.x（5.0.0 于 2025-11 GA，随 Spring Cloud 2025.1 / Spring Boot 4，最新 5.0.3）；存量最多的 4.3.x 维护线（4.3.5，2026-06，修复 CVE-2026-47825）。升级 5.0 最大的坑是配置前缀迁移：WebFlux 网关的属性从 spring.cloud.gateway.* 迁到 spring.cloud.gateway.server.webflux.*，旧前缀在 5.0 静默不绑定（启动不报错、路由就是加载不到，4.x 时代的老配置搬过来必踩）；建议升级前挂 spring-boot-properties-migrator 过渡。另一个行为变化：X-Forwarded-For/Forwarded 头默认不再信任（CVE-2026-47825 修复后），要拿真实客户端 IP 必须配 trusted-proxies 正则白名单。本文 YAML 以 5.0 新前缀为准并注明 4.x 对照。

03架构设计：网关的四层治理职责与容量账

四层职责：网关不是"转发器"，是"防线"

路由治理（路由表即资产：稳定 route id、动态路由走 Nacos 配置中心推送，别把几十条路由写死在包里的 YAML）、流量治理（超时/重试/限流/熔断，本期主角）、安全治理（边缘鉴权与身份头改写、CORS 全局收口一处配、可信代理与真实 IP）、可观测（route id 维度的指标与访问日志——网关日志是全链路排障的第一现场）。每层只做"横切"的事，业务编排永远不进过滤器：网关里每多一行业务代码，全公司流量就多一分被它拖累的风险。

超时与重试：预算漏斗的顶层在网关

0031 期讲过"上游预算 = 下下游预算 + 余量、从网关到 DB 逐层递减"；漏斗的第一层就在网关本身。典型分配：网关 response-timeout 3s（全站天花板）→ 服务间 Feign read 1.5s → DB 800ms。慢接口（报表、导出、登录短信）用路由级 metadata 覆盖单独放宽，绝不动全局天花板——这与 0031 期"局部覆盖不动全局"是同一条纪律。重试守则也同构：Retry 过滤器只配在 GET 幂等路由上（statuses 限定 5xx、methods 限定 GET、指数退避），写操作绝不在网关重试——网关看不到业务语义，幂等键只能在业务层闭环，这与 0031 期"传输层重试的前置条件"完全一致，只是位置从 Feign 换到了入口。

参数默认值生产建议理由
connect-timeout45s1~2s内网握手毫秒级；连接超时=实例大概率已死，快弃快换
response-timeout不设限全站天花板（如 3s）+ 慢路由覆盖无上限=01 节挂死雪崩；它是链路预算漏斗第一层
pool.typeelastic（无上限）fixed + max-connections弹性池在下游变慢时无限扩张；fixed 才有背压
pool.max-idle-timenull（不回收）30~60s空闲连接不回收=故障恢复后连接数下不来
Retry 过滤器默认无仅 GET + 5xx + 退避网关看不到业务幂等语义，写操作重试=重复下单
限流无route 维度 RequestRateLimiter / Sentinel按路由不按全局，防止一个吵闹客户端吃光全站配额

容量三笔账（入口 8000 QPS、下游 40 服务、P99=300ms 场景）

连接账：并发驻留 = 8000 × 0.3s ≈ 2400；fixed 池 max-connections 建议 3000~4000（留 30% 余量），acquire-timeout 配 2~5 秒——池满时排队快速失败，好过无限等。注意连接数按下游分片：Reactor Netty 按远程地址分池，单慢下游只会占满自己那片。线程账：event loop = CPU 核数（8 核节点就是 8 个 loop），理论吞吐 = loop 数 × 每秒可处理事件数，够撑几万 QPS 转发——前提是零阻塞：一个同步 JDBC 查询占住 1/8 的全网关算力，这就是 01 节二次发现的数学本质。内存账：流式转发下网关堆小而稳（几百 MB 量级正常）；堆飙涨的第一个嫌疑永远是"某个过滤器把 body 读进内存"——读 10MB 的请求体 × 200 并发 = 2GB 瞬时分配，网关层能不碰 body 就不碰。

04实战：一套可以抄走的生产配置

路由三件套：Path 断言 + StripPrefix + lb://

# application.yml（5.0 前缀；4.x 去掉 server.webflux 两层）
spring:
  cloud:
    gateway:
      server:
        webflux:
          routes:
            - id: order-api                    # 稳定 route id：指标/日志/限流都以它为键
              uri: lb://order-service           # reactive LoadBalancer + Nacos
              predicates:
                - Path=/api/order/**
              filters:
                - StripPrefix=2                # /api/order/items → /items
            - id: search-api                    # 查询类路由：可以配重试
              uri: lb://search-service
              predicates:
                - Path=/api/search/**,Method=GET
              filters:
                - name: Retry
                  args:
                    retries: 2
                    statuses: BAD_GATEWAY,SERVICE_UNAVAILABLE
                    methods: GET                # 只重试 GET；写操作绝不进这条
                    backoff: { firstBackoff: 100ms, maxBackoff: 1s, factor: 2 }

HttpClient：三超时一池，雷区一次排完

          httpclient:
            connect-timeout: 2000              # 默认 45s，显式重写
            response-timeout: 3s               # 全站天花板；慢路由用 metadata 覆盖
            pool:
              type: fixed                      # 默认 elastic 无上限
              max-connections: 4000
              acquire-timeout: 3000            # 池满排队 3s 快速失败
              max-idle-time: 60s               # 默认 null 不回收，必配
              metrics: true                    # 连接池指标进 Micrometer

限流与金丝雀：KeyResolver + Weight

// 按登录用户限流（未登录回落 IP）；网关层 Key 要"贵"——按用户/租户，别按全局
@Bean
KeyResolver userKeyResolver() {
    return exchange -> {
        var uid = exchange.getRequest().getHeaders().getFirst("X-User-Id");
        var ip  = exchange.getRequest().getRemoteAddress();
        return Mono.just(uid != null ? uid : String.valueOf(ip));
    };
}
# 金丝雀：同组按权重分流，search-v2 先接 10% 观察再逐步放大
# - id: search-v2  uri: lb://search-service-v2  predicates: Weight=grp,10
# - id: search-v1  uri: lb://search-service-v1  predicates: Weight=grp,90

限流定量方法（ replenishRate/burstCapacity 怎么取压测值）回看第 1 期 Sentinel——SCA 体系里也可以直接用 Sentinel 的网关流控（GatewayFlowRule 按 route id 维度），集群精确配额走它的 Token Server。金丝雀配合 CircuitBreaker 过滤器（fallbackUri 指向网关内的降级端点）可以让 v2 出错自动跌回 v1；灰度期间盯三个信号：route id 维度的错误率、P99、v2 的业务指标对齐度。

四个必踩的坑：① 5.0 旧前缀静默失效——4.x 的 spring.cloud.gateway.routes 搬到 5.0 不报错但路由全丢，新前缀是 spring.cloud.gateway.server.webflux.*；② CORS 双写——网关配了 globalcors、下游服务又各自配 CORS，响应头出现两个 Access-Control-Allow-Origin，浏览器直接拒绝，全局收口在网关一处；③ 拿不到真实 IP——5.0.2+/4.3.5+ 后 X-Forwarded-For 默认不信任，必须配 trusted-proxies 白名单 LB 网段，否则限流键、审计日志全是大厅 IP；④ 过滤器里写阻塞代码——同步 RestTemplate/JDBC/Thread.sleep 占住 event loop，正确姿势是 subscribeOn(Schedulers.boundedElastic())，或者干脆把这件事挪出网关。

✅ 上线体检清单

☐ connect/response 超时显式配置，response-timeout 是全站链路预算天花板且与 Feign/DB 递减不倒挂　☐ pool.type=fixed + max-connections 按并发驻留×余量 + max-idle-time 必配　☐ Retry 只存在于 GET 幂等路由，statuses/methods/backoff 三项显式　☐ 全部过滤器审查过"零阻塞、不读 body"，必须阻塞的隔离到 boundedElastic　☐ route id 稳定且有含义，指标/日志/限流都以 route id 为键　☐ CORS 只在网关一处配置，下游已清理　☐ trusted-proxies 已配 LB 网段，真实 IP 可用　☐ 连接池指标与 route 维度请求指标进了大盘（联动第 28 期 Prometheus）　☐ 金丝雀路由有成对的 CircuitBreaker 兜底与回退预案　☐ 动态路由（Nacos 推送）有变更审计与回滚路径

05今日要点

  • 网关的默认值是"演示友好"不是"生产友好"：connect 45s / response 不设限 / elastic 池无上限且空闲不回收——三个默认值组合起来就是"单下游变慢、全站连接吹气球"的雪崩剧本，上线第一天显式重写。
  • 网关是超时预算漏斗的顶层：response-timeout 即全站天花板（如 3s），慢接口路由级覆盖、绝不动全局；网关→Feign→DB 逐层递减的纪律与上一讲 OpenFeign 一脉相承。
  • 响应式网关的死穴是阻塞：worker 就是 CPU 核数个 event loop，一个同步 JDBC 调用占住 1/N 的全网关算力；零阻塞、不碰 body 是过滤器代码的两条军规。
  • 重试与限流的守则不变：Retry 只配 GET+5xx+退避（网关看不到业务幂等语义）；限流按 route/用户维度配，不按全局——一个吵闹客户端不该吃光全站配额。
  • 版本升级先想命名空间：5.0 的属性前缀迁到 spring.cloud.gateway.server.webflux.*，旧前缀静默失效；X-Forwarded-For 默认不信任，trusted-proxies 必配——升级前把这两条写进 checklist。

06架构师思考题

题目一：网关未配 response-timeout，下游支付服务某天因数据库磁盘 IO 饱和从 200ms 劣化到 30s 且不报错。① 描述网关侧随后 10 分钟内连接数、event loop、全站其他路由的演化过程；② 给出"三段防线"的完整配置思路；③ 为什么说 max-idle-time 不配，故障恢复后问题还没结束？▶ 点击展开解析

🔍 逐问拆解

① 演化推演（四步）：第一步，请求发出后网关在"等响应"状态无限挂起——response-timeout 不设限意味着这个等待没有终点；第二步，入口流量持续涌入，已有连接全被占住，elastic 池开始新建 TCP 连接，支付路由的连接数按"入口 QPS × 30s"线性堆积（QPS 100 就是每 10 秒涨 3 万个连接需求，受限于 FD 和端口很快触顶）；第三步，新建连接的 connect-timeout 又是 45s，坏实例上的连接尝试也在长时间占资源；第四步，event loop 要维护的 channel 数暴涨、内存与 FD 逼近上限，不经过支付的路由开始排队变慢——咽喉被堵，全身缺氧，这就是 01 节剧本的完整微观机制。注意支付服务"不报错"这个细节：它还在正常处理，只是慢，所以没有任何 5xx 能触发熔断——慢故障比错故障更考验超时治理。

② 三段防线：第一段，网关层 response-timeout 3s（全站天花板）+ 支付慢流程路由级覆盖（如 8s，且推动异步化改造把慢从同步链路赶出去）；第二段，服务间调用层（Feign read-timeout 按 0031 期漏斗递减，支付客户端单独评估）；第三段，资源层连接池 fixed + max-connections + acquire-timeout 3s——即使前两段失守，池满后排队 3 秒快速失败，把"无限挂起"变成"有界失败"，网关自身永远有退路。三段防线的共同哲学：每一层都要有"放弃"的机制，且越靠外越保守。

③ max-idle-time 的账在故障恢复之后才开算：磁盘修复、支付恢复 200ms 后，雪崩期间建立的几万个连接里大量已空闲，但 max-idle-time=null 意味着空闲连接永不回收——它们继续占着 FD、内存和连接表，网关带着故障期的"虚胖"继续跑（华为云 case 里连接数下不来只能靠重启解决）。配上 max-idle-time 60s，空闲连接一分钟内被逐出，连接数自动回落到稳态。这也是"故障恢复 ≠ 恢复健康"的经典例子：没有回收机制的系统，每次故障都会留下资源疤痕。

题目二：搜索服务要发 v2 新版本（换了召回算法），你决定用网关金丝雀：Weight=90/10 起步。① 设计完整方案（路由、兜底、观察指标、放量节奏）；② 灰度中发现 v2 的 P99 是 v1 的 3 倍但错误率相同，继续放还是回退？决策依据是什么？③ 有同学建议"不配 Weight，直接把 v2 实例加进 search-service 的 Nacos 服务列表让 LoadBalancer 自然分流"，两个方案的本质区别是什么？▶ 点击展开解析

🔍 逐问拆解

① 方案四件套：路由上，两条路由同 Weight 组（search-v1 weight 90 / search-v2 weight 10），route id 不同所以指标天然分开——这正是稳定 route id 的价值；兜底上，v2 路由挂 CircuitBreaker 过滤器（fallbackUri 可以转发到 v1 的降级端点，或直接返回降级 JSON），保证 v2 崩了最多 10% 流量受影响且自动回落；指标上，盯三组：两 route 的错误率/P99（网关层）、两版本的召回质量业务指标（业务层，算法换了光看技术指标不够）、v2 的资源水位（新算法可能更吃 CPU/内存）；节奏上，90/10 → 30 分钟无异常 → 50/50 → 30 分钟 → 90/10（反向）→ 100，每步之间留足观察窗，任何一步指标越界就停在当前比例或回退。

② P99 变 3 倍但错误率相同：先定性再决策。错误率相同说明功能正确，P99 变长说明长尾请求显著变慢——网关 response-timeout 3s 是天花板，v2 P99 若逼近天花板就会开始出现超时（表现为网关层 504 而不是下游错误率上涨，这是最容易误判的地方：错误出现在网关指标里，不在服务指标里）。决策依据三问：v2 的 P99 绝对值离网关超时还有多少余量？慢的那部分请求是否就是新算法的目标场景（比如长尾 query 本来就该多算）？业务上 3 倍长尾是否可接受？余量充足且长尾可解释 → 停在 10% 深入排查再决定；余量不足或无法解释 → 立即回退 100/0。灰度的意义就是把"要不要回退"这个决策的成本降到最低——10% 流量下你永远有得选。

③ 本质区别是"控制面粒度"：Weight 路由是路由级控制——两条路由是两个独立对象，各有 route id、过滤器链、熔断器、指标序列，可以精确到"这条路由 10%"且 v2 出问题摘除是一条配置的事；LoadBalancer 自然分流是实例级控制——v2 实例混进同一个服务的实例列表，流量按负载均衡策略近似均分（默认轮询约等于 50/50，想 10% 得精确控制实例数比例），且两者共用同一个 route id：指标混在一起看不出 v2 的错误率，熔断器也一起兜底——v2 慢会把整个服务的熔断统计拉高，误伤 v1。一句话：混实例是"同一服务的新成员"，Weight 是"独立的新路由"；前者适合无风险的扩容/小版本，后者适合算法更换这种需要独立观测面和独立兜底的变更。需要 10% 精度、独立指标、秒级回退的场景，选 Weight。
