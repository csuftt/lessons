Seata 分布式事务：下单链路的终极自救

订单成功了、库存扣了、积分没加 —— 当一个业务动作横跨三个数据库，谁来保证"要么全成、要么全不发生"？聊聊 Seata 的四种模式与架构师最该警惕的事务边界。

🍃 Spring Cloud Alibaba 📅 2026-09-04 · 第 18 期 ⏱ 预计阅读 10 分钟

01一次没有回滚的下单事故

电商下单链路，三个服务三个库：订单服务创建订单（MySQL-A）→ 库存服务扣减库存（MySQL-B）→ 积分服务增加积分（MySQL-C）。某天促销大促，积分服务所在节点 GC 抖动，调用超时。结果：

  • 订单库：订单已创建，状态"待支付"；
  • 库存库：库存已扣减（本地事务早就提交了）；
  • 积分库：积分没加（调用根本没到达）。

用户没看到积分，投诉进来；运营对账，发现"扣了库存、没加积分"的脏数据上千条。更糟的是这批订单已经流转到下游仓储，人工修复要横跨三个系统，改哪个库都心惊胆战。

问题的本质：每个服务用自己的本地事务（ACID），保证了单库一致性；但跨库的业务原子性——一个业务动作里的 N 个本地事务要么全提交、要么全回滚——没有任何机制保证。这就是分布式事务问题。解决它的思路历史上只有两个方向：

1

刚性事务（强一致）：XA / 二阶段提交（2PC）。所有参与者锁定资源直到全局提交，一致性强但性能差、可用性差；

2

柔性事务（最终一致）：TCC、Saga、本地消息表等。放弃隔离性、用补偿换性能，让数据"短暂不一致、最终对齐"。

Seata 的价值在于：把这两类方案的公共部分（全局事务管理、分支注册、锁管理、网络通信）做成了中间件，业务方按场景挑模式、少写基础设施代码。今天把四种模式一次讲清，重点是 AT 模式的"零侵入"到底是怎么做到的。

02原理：全局事务是怎么跑起来的

三个角色一张图

三角色分工：TC（Transaction Coordinator）独立部署，是全局事务的"大脑"，维护状态机；TM（Transaction Manager）是发起全局事务的那个服务（通常是入口服务），只负责 begin/commit/rollback 三个动作；RM（Resource Manager）管分支事务，每个操作数据库的服务都是 RM。XID（全局事务 ID）由 TC 生成，随 RPC 调用链透传（HTTP header / Dubbo attachment），每个 RM 用 XID 向 TC 注册分支。这就是"一阶段提交 + TC 驱动二阶段"的骨架。

AT 模式：一行注解背后发生了什么

AT（Automatic Transaction）是 Seata 的招牌：业务 SQL 不用改，加个 @GlobalTransactional 注解就拥有回滚能力。魔法在代理数据源——它解析业务 SQL，在本地事务提交前后各做一件事：

1

解析 SQL，查"前镜像"：按 WHERE 条件把将被修改的行修改前的值查出来存进 undo_log；

2

执行业务 SQL，查"后镜像"：同一批行修改后的值也存进 undo_log，与业务数据在同一个本地事务里提交；

3

一阶段直接提交本地事务，并向 TC 上报分支状态；连接立刻释放，不长期锁资源；

4

二阶段：全局提交 → 异步删 undo_log（极快）；全局回滚 → 用前镜像生成反向 SQL 补偿（update 回旧值），提交前会校验后镜像与当前数据一致，防止"脏写"。

所以 AT 的本质是自动补偿：一阶段就提交、不持锁等待（只记录行级锁供 TC 全局仲裁），回滚靠 undo_log 反向 SQL。对比 XA：XA 二阶段前资源一直被锁，AT 一阶段即提交，吞吐高一个量级；代价是隔离性弱化——回滚期间若被别的全局事务改了同一行，后镜像校验会失败，需要人工介入。

四种模式一张表

模式侵入性一致性/性能适用场景
AT 零侵入（注解+代理数据源） 最终一致 · 一阶段提交，性能最好 大多数内部微服务；不愿写补偿逻辑的团队首选
TCC 高（手写 Try/Confirm/Cancel 三方法） 最终一致 · 不依赖 undo_log，资源预留制 资金类核心链路；需要对"冻结"语义精细控制
Saga 中（写正向服务+补偿服务，状态机编排） 最终一致 · 长事务友好，无全局锁 跨企业调用、流程长（分钟/天级）、参与者非本地库
XA 低（依赖数据库 XA 协议） 强一致 · 二阶段锁资源，性能最差 传统多库同构、强一致刚需、并发量不大
TCC 三方法语义Try：预留资源（如冻结库存 100 中的 10）；Confirm：确认扣减（冻结转真实扣，必须幂等）；Cancel：释放预留（解冻，必须幂等）。空回滚（Try 没到、Cancel 先到）、悬挂（Cancel 之后 Try 才到）、幂等是 TCC 三大坑，Seata 通过事务日志表帮忙兜了一部分，但业务语义只有你自己清楚。

03架构设计：选型、部署与容量

选型决策树

?

第一步，先问"要不要分布式事务"：能靠规避就不引入——把强关联的数据收敛到一个库/一个服务（拆分时的边界设计）；非核心链路用本地消息表/事务消息（Pulsar）最终一致。分布式事务是最后手段，不是默认选项；

?

第二步，确定刚性还是柔性：强一致刚需且并发低 → XA；其余绝大多数 → 柔性；

?

第三步，柔性里挑：内部服务、能改表结构、想要省事 → AT；资金核心、要资源预留语义 → TCC；链路长、参与者异构（含第三方接口）→ Saga。

TC 的部署形态

TC 是全局事务的大脑，本身必须按高可用部署（呼应上一期的 L2 中间件层）：

  • 存储三选一：file 模式（单机，只适合开发）→ db 模式（MySQL，多数生产选择，全局事务状态、分支状态、全局锁三张表）→ redis/raft 模式（新版，性能与可用性更优）；
  • 多实例 + 注册中心：TC 多实例注册到 Nacos，客户端按集群名连接，一个挂了自动切；
  • 网络与超时：TC 与 RM 之间是高频心跳 + 状态上报，跨机房部署时 RTT 会直接放大全局事务时延，TC 尽量与应用同机房。
AT 模式容量规划要点

① undo_log 表与业务同库同事务写入，写放大约 2~3 倍（前镜像+后镜像+业务 SQL），扣减类热点表的 QPS 容量要按此打折；② 全局锁在 TC 侧串行化同行竞争，热点行冲突高时全局事务的提交会被拉长，热点账户/爆款 SKU 这类场景 AT 并发上限明显，考虑 TCC 或队列串行化；③ 全局事务超时（默认 60s）务必按链路 P99 调整，超时会被 TC 主动回滚。

04实战：把下单链路接进 Seata

① TC Server（db 模式）+ Nacos 注册

# file.conf —— TC 存储改 db，事务状态落 MySQL，支持多实例高可用
store {
  mode = "db"
  db {
    datasource = "hikari"
    url = "jdbc:mysql://10.0.0.21:3306/seata?useSSL=false"
    user = "seata"
    password = "***"
  }
}
# registry.conf —— TC 注册到 Nacos，客户端按集群名寻址
registry {
  type = "nacos"
  nacos {
    serverAddr = "10.0.0.11:8848,10.0.0.12:8848,10.0.0.13:8848"
    cluster = "default"
  }
}

每个业务库执行 undo_log.sql 建表；TC 库执行 global_table / branch_table / lock_table 三张表脚本（发行包 script 目录自带）。

② 应用侧接入（订单服务 = TM）

<!-- Spring Cloud 应用只需两个依赖：seata-spring-boot-starter + nacos 注册发现 -->
<dependency>
  <groupId>io.seata</groupId>
  <artifactId>seata-spring-boot-starter</artifactId>
</dependency>

# application.yml —— 数据源代理自动开启，XID 经 Feign 拦截器透传
seata:
  enabled: true
  application-id: ${spring.application.name}
  tx-service-group: order_tx_group          # 逻辑事务组 → 映射 TC 集群
  service:
    vgroup-mapping:
      order_tx_group: default                    # default = registry.conf 里的 cluster
  config:
    type: nacos
    registry:
      type: nacos

// 发起全局事务：一个注解，XID 自动透传到库存/积分服务
@GlobalTransactional(timeoutMills = 30000, name = "create-order")
public OrderDO createOrder(OrderRequest req) {
    orderMapper.insert(buildOrder(req));      // 分支①：MySQL-A
    stockClient.deduct(req.getSkuId(), req.getQty());   // 分支②：MySQL-B（Feign 透传 XID）
    pointClient.add(req.getUserId(), req.getPoints());  // 分支③：MySQL-C
    return order;
}

③ 出问题时的排查路径

1

查全局事务：TC 控制台/全局表里拿 XID，看状态（Begin/Commit/Rollback/RollbackRetrying），RollbackRetrying 说明反向 SQL 执行失败，重点查 undo_log；

2

查分支与镜像：branch_table 定位分支，业务库 undo_log 看前后镜像是否完整；hasUndoImage 缺失多为代理数据源没生效（检查 seata.enabled 与数据源是否被代理）；

3

脏写告警：回滚时后镜像校验失败（数据已被别的全局事务改动），Seata 会重试并告警——这是 AT 隔离性弱化的典型现场，需要人工对账修正。

✅ Seata 接入检查清单

☐ 每个业务库已建 undo_log　☐ tx-service-group 与 TC 端 vgroup-mapping 一致　☐ XID 透传链路完整（Feign/Dubbo 拦截器）　☐ 全局事务超时 > 链路 P99×2　☐ 热点表评估过 undo_log 写放大　☐ TC 多实例 + db/raft 存储　☐ 回滚失败告警有人接手

05今日要点

  • 分布式事务是设计问题，不是框架问题：先靠服务边界收敛与事务消息规避，最后才引入 Seata——框架解决的是"不得不用"的那部分。
  • AT = 自动补偿：一阶段直接提交本地事务（前/后镜像进 undo_log），二阶段提交只删日志、回滚用反向 SQL；性能好，但隔离性弱化，脏写需人工兜底。
  • TCC 是资金类唯一正解：Try 预留 / Confirm 确认 / Cancel 释放，绕开 undo_log 依赖；三大坑——空回滚、悬挂、幂等——必须逐个处理。
  • Saga 留给长事务：跨企业、分钟级以上流程、参与者异构（含第三方 HTTP 接口），用状态机编排正向与补偿服务。
  • TC 按中间件标准部署：db/raft 存储 + 多实例 + Nacos 注册 + 与应用同机房；它是新的单点候选，别让它裸奔。

06架构师思考题

题目一：账户余额扣减（A 转 B 100 元，两账户在两个库），团队想直接用 AT 模式。你会批准吗？给出分析与替代方案。▶ 点击展开解析

🔍 为什么不批

资金场景的硬约束：任何时刻都不能出现"凭空多钱/少钱"，且热点账户并发极高。AT 的两个特性正好撞枪口上：① AT 没有 XA 那样的隔离性——一阶段就提交，回滚前中间态对外可见（B 已到账、A 的回滚还在路上），对账系统与用户都可能读到"转账成功又失败"的中间态；② 回滚依赖 undo_log 反向 SQL，若出现脏写（另一个全局事务改了同一行），后镜像校验失败后钱就停在中间态等人救——资金系统里这是事故级事件。另外大 V 账户是热点行，TC 侧全局锁的串行化会让冲突事务排队，吞吐塌方。

✅ 替代方案（TCC 为骨架）

  • TCC 资源预留：Try 冻结 A 账户 100 元（available_balance -100，frozen +100），Confirm 把冻结额真正划走，Cancel 解冻。中间态语义显式（"冻结中"），不依赖 undo_log，回滚确定性高；
  • 幂等/空回滚/悬挂三件套：事务控制表记录 xid+分支状态，Cancel 先查 Try 是否到达（空回滚直接成功），Try 后到发现已有 Cancel 记录则拒绝执行（防悬挂），Confirm/Cancel 用状态机保证幂等；
  • 热点账户再叠加两招：账户影子表拆分（一个账户拆 N 个子账户分片削峰）或异步入账（转账拆"扣款事务 + 入账消息"，B 侧消费消息加钱，秒级到账变最终一致——需要业务接受）；
  • 底线对账：无论哪种方案，资金链路必须有每日对账 + 差错处理流程，补偿机制永远要假设"会有补偿失败的那一天"。
题目二：全局事务回滚时，订单服务（分支①）自己收到异常走了本地 try-catch 把异常吞了，Seata 还能回滚它的分支吗？由此谈谈 @GlobalTransactional 的正确用法与 XID 透传失效的排查思路。▶ 点击展开解析

🔍 机制拆解

能回滚，但路径不同。分支①是在同一个 JVM 里：方法抛异常 → TM 侧拦截器感知 → 向 TC 发起全局回滚 → TC 通知所有分支回滚 → 分支①用 undo_log 反向补偿。即使你在订单服务内部 catch 了远程调用（分支②③）的异常，只要异常最终冲出 @GlobalTransactional 方法，全局回滚照样触发——真正危险的是把异常吞到方法内部不重新抛出：TM 认为一切正常发起全局提交，分支②③（若它们自身也没报错）全部提交，数据不一致。所以铁律是：@GlobalTransactional 方法内 catch 了异常必须 rethrow（或手动调 GlobalTransactionContext.rollback()）。

✅ 正确用法与排查清单

  • 注解加在入口方法（TM 所在服务），下游服务不需要重复标注——它们是 RM，靠 XID 注册分支；给内部服务也加注解等于嵌套全局事务，多数场景是误解；
  • 异常类型要匹配：默认只回滚 RuntimeException 与 Error，受检异常（如自定义 BusinessException extends Exception）不会触发回滚，需配置 rollbackFor = Exception.class——这是最常见的"为什么不回滚"事故源；
  • XID 透传失效排查：现象是下游分支没注册（branch_table 里查不到）。按链路查：Feign 拦截器是否被排除（seata-http 依赖缺失）、网关/新建线程池是否断了上下文（异步场景要手动传 XID）、下游数据源是否被代理（没代理 = 不注册分支、不写 undo_log，等于游离在全局事务之外）；
  • 超时与重试：全局超时默认 60s，链路里混了个慢接口就会被 TC 强制回滚；回滚本身有重试上限，配合告警把 RollbackRetrying 状态的事务捞出来人工处理。
