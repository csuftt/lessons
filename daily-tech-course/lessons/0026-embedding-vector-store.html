替语义建一座图书馆：Embedding 与向量库选型（Milvus vs PGVector）

上一讲把 RAG 的翻书链路拆完了，这一讲往下挖一层：书页上的"语义坐标"是怎么来的，又该存进哪座图书馆。Embedding 模型负责给每块文本一个坐标系里的位置，语义越近、向量夹角越小；向量库负责在这个坐标系里毫秒级找到最近的一批邻居。今天讲透三件事：HNSW 为什么快但吃内存、PGVector 与 Milvus 背后是两种形态哲学（数据库里的一个扩展 vs 为向量而生的独立基础设施）、以及"百万向量分水岭"这道选型题怎么算——最后给出不停机迁移的蓝绿方案。

01一次"POC 很香、推广被否"的向量库选型复盘

智能客服项目 POC 阶段，知识库 10 万块向量跑在 PGVector 上，检索又快又省事——向量就住在业务库的 PostgreSQL 里，一个扩展、几行 SQL，连新服务都不用部署。业务看到效果后全面推广：知识库扩到 300 万块、检索峰值数百 QPS、三条业务线都要接入。扩容评审会上，三张否决票接连拍下：

  • DBA 的容量票：300 万块 × 1024 维 × 4 字节 ≈ 12GB 原始向量，HNSW 索引开销 2~3 倍就是 25~35GB 内存——和业务表、连接池、共享缓冲挤同一台 PG 实例，扩容等于整套数据库升配，又贵又影响业务；
  • 压测组的性能票：高并发下检索 P99 延迟抖动明显——向量索引的内存访问和业务查询在缓冲池里互相踩踏，大促期间业务库 CPU 本就报警，再叠一层检索流量是火上浇油；
  • SRE 的运维票：向量检索成了核心链路后，需要独立扩缩容、独立监控、按业务线做租户隔离——混在业务库里，这些一样都做不到。

复盘结论：不是 PGVector 不好，而是它被用在了超出舒适区的阶段——POC 阶段它就是最优解：零新增运维、SQL 一把梭、事务与 JOIN 白拿。向量库选型的本质是一道时机题：什么时候该把向量检索从数据库里拆出来，升级成独立基础设施。要答对这道题，得先看清 Embedding 和向量索引到底在做什么、各自的账怎么算。

02原理：语义坐标系与它的图书馆

Embedding 模型做的事：把文本映射成语义坐标系里的一个点。语义相近的文本（"退货运费谁承担"与"退货的运费规则"）会被映射到相近的位置，无关文本则相隔很远——模型在训练时见过海量"哪些句子在回答同一件事"的语料，把这种共现关系压缩进了几何结构。检索于是变成纯几何问题：拿查询向量在库里找夹角最小（cosine 距离）的 K 个邻居。精确逐个比对是 KNN，百万级向量、毫秒级延迟下算不动，生产用 ANN（近似最近邻）——HNSW 就是主流答案：多层图结构，顶层稀疏长边负责跨簇快速定位、底层稠密短边负责邻域精找，查询只拜访一小部分节点就逼近精确解。它的代价写在图里：图索引必须整体常驻内存，实际内存约为原始向量的 2~3 倍——向量库选型的一切纠结，都源于这面"内存墙"。

三个必须算在选型前的工程参数

参数它决定什么工程要点
维度单个向量的成本基数容量 = 数量 × 维度 × 4 字节（float32），再乘索引系数 2~3；维度跟着 Embedding 模型走，选模型即选维度
精度/量化同样的向量占多少内存float32 → halfvec 半精度省约一半 → int8 省四分之三 → binary 省 32 倍；压缩越狠召回掉得越多，需评测集验证
模型版本向量空间是否同一套坐标系不同模型的向量不在同一空间，绝对不能混存混检——换模型 = 全量重嵌入 + 重建索引 + 蓝绿切换（见上一讲）

维度与精度是"账"，模型版本是"红线"。团队里最容易踩的坑就是半路换了个评测分更高的 Embedding 模型，新向量直接插进旧索引——新旧两套坐标系混在一起，检索质量无声劣化，还不报错。把 embedding_model 与版本写进每条向量的元数据，检索默认带版本过滤，是和上一讲"块带 version 元数据"同一条纪律。

03架构设计：两种形态哲学与分水岭决策

两个产品背后是两种形态哲学。PGVector 是"数据库里的一个扩展"：向量列与业务表同居一库，SQL/事务/权限/JOIN/备份全部白拿，是零新增运维的最短路径——代价是垂直扩展的单机内存墙，向量索引与业务查询共享同一台实例的资源池。Milvus 是"为向量而生的独立基础设施"：存算分离架构（计算节点无状态、数据沉到对象存储、消息队列串起写入链路），检索与写入按分片水平扩展，2.5 版起还内置了 Sparse-BM25 全文检索，混检不用再外挂一个搜索引擎——代价是运维面骤增：etcd、消息队列、对象存储、多角色节点，这是一整套分布式系统的账单。

选型对比表

维度PGVectorMilvus
舒适区规模百万级以内（量化后可再撑一档）千万~亿级，分片线性扩展

决策口诀：百万向量是分水岭，运维意愿是第二票。向量总量百万以内、检索并发中小、结果要与业务数据强 JOIN——PGVector 是性价比之王；向量奔千万、QPS 上百、多业务线共用——Milvus 集群；卡在中间的，先做量化与只读副本再决策，别急着上分布式。回到第 01 节的复盘：300 万块、数百 QPS、三业务线——三个条件全部踩在 Milvus 一侧，但迁移不是拍脑袋，还有最后一道容量账要算清楚：

容量三笔账（以 300 万块 × 1024 维为例）

原始账：300 万 × 1024 × 4B ≈ 12GB；索引账：HNSW 系数 2~3 → 内存 25~35GB（PGVector 单实例很挤，Milvus 可分片摊到多节点）；量化账：halfvec 内存减半 ≈ 13~18GB、int8 减至四分之一 ≈ 6~9GB（召回损失 1~3 个点，必须用评测集验证业务可接受）。先算这三笔，再决定"撑一撑"还是"迁"。

04实战：两边各搭一条最小链路

PGVector：半精度索引 + 迭代扫描（0.8+）

CREATE EXTENSION vector;
CREATE TABLE chunks (
  id        bigserial PRIMARY KEY,
  doc_id    text NOT NULL,
  content   text,
  embedding vector(1024),          -- 维度跟 Embedding 模型走
  emodel    text DEFAULT 'bge-m3@v1'  -- 模型版本红线：随行落库
);
-- 半精度 HNSW：索引内存省约一半，召回损失小
CREATE INDEX ON chunks USING hnsw
  (embedding::halfvec(1024) halfvec_cosine_ops);
SET hnsw.iterative_scan = relaxed;   -- 0.8+：过滤后不足额就继续扫，治"过度过滤"

SELECT id, content FROM chunks
 WHERE emodel = 'bge-m3@v1'          -- 版本过滤：单一向量空间
 ORDER BY embedding::halfvec <=> :query_vec::halfvec
 LIMIT 10;

Milvus：建 Collection + 过滤检索

from pymilvus import MilvusClient, DataType

client = MilvusClient("http://milvus-lb:19530")       # 接入 LB，多副本
schema = client.create_schema()
schema.add_field("id", DataType.INT64, is_primary=True)
schema.add_field("vec", DataType.FLOAT_VECTOR, dim=1024)
schema.add_field("doc_id", DataType.VARCHAR, max_length=64)  # 过滤字段

idx = client.prepare_index_params()
idx.add_index("vec", index_type="HNSW", metric_type="COSINE",
              params={"M": 16, "efConstruction": 200})
client.create_collection("kb_chunks", schema=schema, index_params=idx)

res = client.search("kb_chunks", data=[query_vec], limit=10,
                    # 标量过滤先裁剪，再在分片内做向量近邻——过滤字段同样要建索引
                    filter='doc_id like "hr-2026q3%"',
                    output_fields=["doc_id"], search_params={"params": {"ef": 64}})

☐ 选型前量化过三笔账（原始/索引/量化）与 QPS 峰值　☐ 每条向量带 embedding_model 版本元数据且检索默认过滤　☐ 量化前后用评测集验证召回损失（1~3 个点内）　☐ 过滤字段建标量索引（PG：btree；Milvus：标量索引/Clustering Compaction）　☐ ef/M/nprobe 等索引参数按召回-延迟曲线压测调定，不抄默认值　☐ 迁移走双写+影子读+蓝绿切流，留回滚窗口　☐ 向量库故障有降级路径（仅 BM25 或缓存热点答案）　☐ 监控盯两个指标：检索 P99 延迟与召回抽检得分

05今日要点

  • Embedding = 语义坐标系：模型把文本映射成向量，语义越近夹角越小；检索就是找最近邻。模型决定坐标系，不同模型的向量绝不能混存混检——版本红线写进元数据。
  • HNSW 快在多层图、贵在内存墙：顶层长边定位、底层短边精找，查询只拜访小部分节点；代价是索引整体常驻内存（原始向量 × 2~3 倍），这面墙决定了选型的物理边界。
  • 两种形态哲学：PGVector 是"数据库里的扩展"——SQL/事务/JOIN 白拿、零新增运维，垂直扩展有顶；Milvus 是"为向量而生的基础设施"——存算分离水平扩展、原生混检，代价是一套分布式系统的运维面。
  • 百万向量是分水岭，先算账再投票：百万以内 PGVector 是性价比之王；千万级高 QPS 多租户上 Milvus；中间地带先量化（halfvec/int8）、读副本、分区撑一撑，别急着上分布式。
  • 迁移走蓝绿不停机：双写 → 影子读比对 → 评测集验收 → 原子切流 → 保留旧索引观察期；容量按"原始账 × 索引系数 × 量化档位"三笔算清再动手。

06架构师思考题

题目一：你们用 PGVector 上线的知识库运行半年：500 万块向量、白天峰值 200 QPS，且大促期间业务库 CPU 常年报警。CTO 建议迁 Milvus。① 迁移前哪些数字必须先量化？② 有哪些"不迁移"的替代方案？③ 如果最终决定迁，怎么做到不停机？▶ 点击展开解析

🔍 逐问拆解

① 先量化四组数：真实向量总量与半年增长曲线（判断是"已经越界"还是"恐慌性提前"）；检索 QPS 与 P99 延迟分布（峰值持续时间——短尖峰可用缓存削）；PG 实例内存水位与缓冲池命中率（向量索引与业务查询的踩踏程度）；量化空间（halfvec 减半、int8 减至四分之一后，500 万块 ≈ 20GB 原始 → 量化后 5~10GB，可能直接从"很挤"变"宽松"）。没有这些数就上 Milvus，是用一个分布式系统的运维成本去换一个可能不存在的问题。

② 替代方案按侵入性排序：把向量检索切到专用只读副本（写走主库、读隔离，业务库 CPU 立刻解耦）；halfvec/int8 量化把内存砍到 1/2~1/4（评测集验证召回损失）；按业务线分区拆表（大库变小库）；热点查询结果缓存（问答场景长尾明显，命中率高）。多数"半越界"场景，这四招组合能再撑一年以上。

③ 不停机迁移 = 蓝绿 + 双写 + 影子读：新 Milvus 集群建好 collection；入库链路改造为双写（PG 与 Milvus 同步写，Milvus 失败不阻塞主链路、记补偿日志）；存量数据批量搬迁+校验（数量对账+抽样向量比对）；影子读阶段线上查询同时打到两边但只返回 PG 结果，比对召回差异跑一到两周；评测集验收通过后按流量比例切流（5% → 50% → 100%）；旧 PGVector 索引保留一个月作回滚兜底。切流原子性靠"版本号+配置中心开关"，与上一讲的蓝绿索引切换是同一套纪律。

题目二：现网用 768 维的旧 Embedding 模型，新模型 1024 维、语义评测榜明显更高，团队想升级。① 为什么不能把新模型的向量直接插进现有索引？② 换模型要动架构里的哪些东西？③ 给出平滑切换方案，并说明如何验证"新模型真的更好"。▶ 点击展开解析

🔍 逐问拆解

① 不同模型 = 不同坐标系：768 维旧模型和 1024 维新模型各自有一套独立的向量空间，连维度都不同；即便维度凑巧相同，同一句文本在两个空间里的坐标也没有可比性——新旧块的相似度分数不可比，混存混检的结果是排序整体失真，而且不报错、只变差，是最难排查的一类静默故障。这就是"模型版本红线"。

② 连锁改动清单：存储层——Milvus 要建新 collection（维度是 schema 一部分，建定不可改）或 PG 加新列/新表，旧索引保留；嵌入层——全量文档重嵌入（500 万块的 GPU/时间/费用预算，通常按天级排期）；检索层——查询侧 Embedding 调用同步换模型（查询与文档必须同模型）；元数据——emodel 字段值更新，检索过滤条件跟着切；容量——1024 维比 768 维贵 33%（12GB → 16GB 原始账，索引账、量化账同比例放大）；上游——切块策略最好与新模型的训练分布匹配，顺带复核。

③ 平滑切换 = 蓝绿索引 + 评测验收：新向量写入新 collection（蓝绿中的"绿"）；离线批量重嵌入存量；先评测后切流——用固定的评测问题集（问题+标准答案+相关块）分别在新旧索引上跑召回率、nDCG、端到端答案质量（RAGAS 类框架），新模型必须在自己的业务语料上赢，榜单分数只是入场券；验收通过后配置中心原子切读；旧索引保留观察期（既是回滚兜底，也能对比线上真实查询分布下的表现）。切完盯一周"检索 P99 + 抽检召回 + 用户负反馈"三件套，稳了再下线旧索引。
