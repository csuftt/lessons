索引建了却不走：执行计划判读与索引失效实战

明明加了索引，EXPLAIN 一跑还是全表扫描——问题多半不在"索引不够"，而在"索引不生效"。今天把 EXPLAIN 的判读方法、优化器的成本抉择、八大失效场景和一套线上排查 SOP 一次讲透。

🐬 MySQL 📅 2026-09-07 · 第 19 期 ⏱ 预计阅读 10 分钟

01一次"索引无效"的线上事故

工单系统列表页突然超时。表 t_workorder 560 万行，按手机号查工单，执行 8 秒。开发很委屈：mobile 列上明明建了索引，怎么还会慢？DBA 拉出执行计划：

mysql> EXPLAIN SELECT * FROM t_workorder WHERE mobile = 13800138000;
+----+-------------+--------------+------------+------+---------------+------+---------+------+---------+----------+-------------+
| id | select_type | table        | partitions | type | possible_keys | key  | key_len | ref  | rows    | filtered | Extra       |
+----+-------------+--------------+------------+------+---------------+------+---------+------+---------+----------+-------------+
|  1 | SIMPLE      | t_workorder  |   NULL     | ALL  | idx_mobile    | NULL | NULL    | NULL | 5563821 |    10.00 | Using where |
+----+-------------+--------------+------------+------+---------------+------+---------+------+---------+----------+-------------+

possible_keys 里有 idx_mobile（优化器知道这个索引），但 key=NULL, type=ALL——它放弃了，选择全表扫描 556 万行。根因是那句 SQL 里的手机号没加引号：mobile 是 varchar，传入的是数字，发生了隐式类型转换，索引直接失效。一行代码的事故，暴露的是团队缺两样东西：读得懂执行计划的眼睛，和知道索引什么时候会失效的直觉。这正是本期的主线。

02原理：EXPLAIN 怎么读，优化器怎么想

五列定生死

EXPLAIN 输出十几列，日常判读盯五列就够：

  • type：访问方式的"健康等级"，好坏一眼可辨（见下图）；
  • key / possible_keys：实际用的索引 vs 候选索引。possible_keys 有而 key 为 NULL，就是"索引被放弃"的信号；
  • rows：预估扫描行数。几百万行的表扫出百万级 rows，无论 type 显示什么都等于全扫；
  • Extra：附加动作。Using index（覆盖索引，好）、Using index condition（索引下推 ICP，好）、Using filesort（额外排序）、Using temporary（临时表）——后两个出现就要警惕；
  • key_len：索引实际用了几列。联合索引 idx(a,b,c) 的 key_len 只覆盖 a，说明 b/c 没用上（常见于中间列用了范围）。

优化器为什么"不听话"

优化器的决策是成本计算：预估每种走法的 IO 成本 + CPU 成本，挑最便宜的。两个关键输入经常坑人：

1

统计信息（基数 cardinality）不准：预估基于采样，大量写入后基数漂移，优化器可能算出"走索引更贵"的错误结论——索引明明存在却不选。批量导入后跑一次 ANALYZE TABLE 是廉价保险；

2

回表成本真实存在：二级索引只存主键值，命中后还要回主键索引取整行。当预估命中行数很大（比如百分之几十的表），逐行回表还不如顺序全表扫——此时优化器放弃索引是理性选择，问题出在你的 SQL 选择性太差，不在索引本身。

03索引失效八大场景：一张速查表

以下场景在 MySQL 8.0 InnoDB 下逐一验证过，覆盖线上九成的"索引不生效"工单。反例 → 正解的对照直接可用：

#失效场景反例（不走索引）正解
1 索引列被函数/运算包裹 WHERE DATE(create_time)='2026-09-07' WHERE create_time >= '2026-09-07' AND create_time < '2026-09-08'
2 隐式类型转换（varchar 列传数字） WHERE mobile = 13800138000（mobile 是 varchar） WHERE mobile = '13800138000'——本期开头的事故
3 左模糊 / 全模糊 WHERE name LIKE '%三' 右模糊 LIKE '张%' 可走 range；模糊搜索需求 → ES / ngram 全文索引
4 OR 混入无索引列 WHERE user_id=1 OR age=30（age 无索引） 拆 UNION ALL，或补索引；index merge 有时能救但不可依赖
5 违反最左前缀 idx(a,b,c) 下 WHERE b=1 AND c=2 条件必须从 a 开始连续命中；b/c 单独查需另建索引
6 范围查询截断后列 idx(a,b) 下 WHERE a>100 AND b=5（b 用不上） 联合索引等值列在前、范围列在后：idx(b,a)
7 NOT IN / != / NOT LIKE WHERE status NOT IN (0,1) 视选择性而定：结果集占比小仍可能走索引；更稳妥用 NOT EXISTS 或正向枚举
8 JOIN 列字符集/排序规则不一致 utf8mb4 表 join utf8 表的同名列 统一 utf8mb4_0900_ai_ci；否则索引失效且驱动表选择错乱
怎么快速定位是哪种？EXPLAIN 里 possible_keys 有值但 key=NULL → 先查 1/2/3/5/6/8（索引被写法干掉）；key 有值但 rows 巨大 → 多半是选择性差或统计信息漂移（02 节两个根因）。再配合 SHOW WARNINGS 能看到优化器改写后的真实 SQL。

04架构视角 + 线上排查 SOP

索引是写读权衡，不是越多越好

每个二级索引都是一棵独立的 B+ 树：写入时全部维护（写放大）、占空间、还会让优化器选择变难。架构上的几条纪律：

  • 一表 5~6 个索引封顶；idx(a) 能被 idx(a,b) 覆盖的就是冗余索引，删；
  • 覆盖索引优先：把高频查询的 select 列收进联合索引，消灭回表，Extra 出现 Using index 就是理想态；
  • 前缀索引（如 mobile(11) 之外的长文本列）省空间，但会失去覆盖与排序能力——空间换功能的权衡要显式做；
  • 统计信息治理常态化：大表批量导入/归档后 ANALYZE TABLE；非索引列的分布统计用 8.0 直方图补齐，帮优化器做对决策。

慢查询排查 SOP（五步）

1

找 Top SQL：慢日志 long_query_time=0.5s + pt-query-digest 聚合，按总耗时排序锁定头号目标，别凭感觉；

2

EXPLAIN 三问：type 是否 ≥ range？key 是不是预期索引？Extra 有无 filesort / temporary？三问定性质；

3

对照八场景表定位失效原因；再用 SHOW INDEX FROM t 看基数是否漂移；

4

真实验证：8.0.18+ 用 EXPLAIN ANALYZE 拿实际执行耗时与行数（预估值 vs 真实值差距大 = 统计信息问题）；统计漂移则 ANALYZE TABLE t;

5

闭环：改写 SQL / 调整索引后回归验证，并把该 SQL 的 EXPLAIN 截图归档——发布评审时新 SQL 必须附执行计划。

✅ 索引健康检查清单

☐ varchar 列查询值都带引号　☐ 无函数/运算包裹索引列　☐ 联合索引等值在前、范围在后　☐ 高频查询有覆盖索引　☐ 冗余/未使用索引定期清理（sys.schema_unused_indexes）　☐ 批量写入后 ANALYZE TABLE　☐ 新 SQL 上线前 EXPLAIN 过审　☐ 慢日志周报有人看

05今日要点

  • EXPLAIN 判读盯五列：type（≥ range 是红线）、key vs possible_keys（索引是否被弃用）、rows（预估扫描量）、Extra（filesort/temporary 是危险信号）、key_len（联合索引用了几列）。
  • 索引存在但不被用，两类根因：写法干掉了索引（八大场景），或成本计算放弃了索引（统计漂移 / 回表代价高 / 选择性差）——先分清是哪类，再动手。
  • 隐式类型转换是头号惯犯：varchar 列传数字等价于对索引列套 CAST 函数，直接失效；JOIN 列字符集不一致同理且更隐蔽。
  • 索引是写读权衡：覆盖索引消回表是首选手段，冗余索引是负资产，一表 5~6 个封顶。
  • 治理靠流程不靠灵感：慢日志 + pt-query-digest 找 Top SQL，EXPLAIN 纳入发布评审，ANALYZE TABLE 纳入批量写入 SOP。

06架构师思考题

题目一：运营后台导出"第 45 万页"数据，SQL 是 SELECT * FROM t_order ORDER BY id LIMIT 9000000, 20，跑了 30 秒。id 是主键，为什么还慢？给出至少两种优化方案与各自的适用前提。▶ 点击展开解析

🔍 为什么主键索引也救不了它

LIMIT 9000000, 20 的执行方式不是"跳过 900 万行"，而是按顺序取满 9000020 行再丢掉前 900 万行。虽然走主键索引免了排序，但每取一行都要回表（SELECT * 要整行数据），900 万次回表就是 30 秒的主要开销——慢在"取了再扔"的无效回表，不在有没有索引。这是典型的深分页问题，索引只解决了排序，解决不了偏移量。

✅ 方案对比

  • 方案一：延迟关联（服务端分页导出的主流解法）。先用覆盖索引把目标页的主键找出来，再回表取整行：SELECT t.* FROM t_order t JOIN (SELECT id FROM t_order ORDER BY id LIMIT 9000000, 20) tmp ON t.id = tmp.id;——子查询只扫二级索引（索引里就有 id，不回表），回表从 900 万次降到 20 次，通常能从 30s 降到 1s 以内。适用前提：排序列上有索引且排序方向一致；
  • 方案二：游标 / 键集分页（互动界面的更优解）。记上一页末尾 id：WHERE id > :last_id ORDER BY id LIMIT 20——每次定位直接走索引 range，复杂度与页深无关，永远 O(20)。适用前提：排序键唯一且连续推进，只支持"下一页"，跳页需要额外设计；
  • 方案三：产品侧约束（架构师该主动提的）。限制最大跳页深度（如前 1 万条内）、导出走异步任务 + 流式写出（游标遍历），总数展示用估算。深分页本质是产品需求问题，能谈掉比技术优化更便宜。

选型结论：后台导出用延迟关联 + 异步流式，用户端列表用游标分页，跳页需求靠产品约束——三个手段通常组合使用。

题目二：第 01 节的事故里，mobile 是 varchar，传数字 13800138000 索引失效；但反过来，id 是 bigint，传字符串 '123' 却不会失效。为什么？再延伸：两张表 JOIN 列字符集不一致时会发生什么？▶ 点击展开解析

🔍 转换方向的 asymmetry（不对称性）

MySQL 的比较规则是"数字与字符串比较时，把字符串转成数字"。所以：① varchar 列与数字比，等价于 CAST(mobile AS DOUBLE) = 13800138000——转换函数套在索引列上，整棵索引失效，全表逐行转换；② bigint 列与字符串 '123' 比，转换发生在常量一侧（'123' → 123），索引列完好无损，照常走索引。记忆口诀：转换套在谁的身上，谁的索引就失效。同理：日期列 DATE(create_time) 失效、create_time >= '2026-09-07' 不失效，都是这个规律。另外这个转换还有一个隐藏坑：'138abc' 转数字是 138，mobile=13800138000 还可能"误命中"一堆前缀相同的号——不仅是性能问题，还是正确性问题。

✅ 字符集不一致的 JOIN：双重打击

  • 索引直接失效：utf8mb4 列与 utf8 列比较时需要字符集转换（utf8mb4 → utf8 收窄），转换施加在列上，两边的索引都用不了，大表 JOIN 秒变笛卡尔积级别的灾难；
  • 驱动表选择错乱：优化器基于错误成本估算选驱动表，常常选反，被驱动表每行都全扫；
  • 排查与治理：EXPLAIN 特征是 JOIN 两表的 type 全是 ALL 且 filtered 异常；用 SELECT table_name, column_name, character_set_name, collation_name FROM information_schema.columns WHERE table_schema=...() 巡检同名列；治理 = 建表规范统一 utf8mb4 / utf8mb4_0900_ai_ci，存量表用 ALTER TABLE ... CONVERT TO CHARACTER SET utf8mb4 低峰期分批迁移；
  • 架构启示：把"隐式转换零容忍"写进 SQL 规范与代码评审清单（ORM 参数类型校验 + 静态扫描），比事后救火便宜两个数量级。
