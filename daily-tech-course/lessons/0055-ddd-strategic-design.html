DDD 战略设计：康威定律、限界上下文与团队拓扑

新的技术栈轮换线开启：上一讲聊完湖仓一体，数据架构线告一段落，今天开启架构方法论与工程效能线。公司按渠道拆了七个订单团队，一年后订单服务长出了七套"几乎一样"的接口；十几个团队共用一张 200 万行的订单大表，加个字段要发十几封邮件——这两类"接口爆炸"和"共享数据库"的病，代码评审拦不住，因为病根不在代码里，在边界里。DDD 战略设计不讲类图，讲的是系统怎么切、边界谁守、模型放哪。这一讲用一条被忽视的实证铁律（组织结构决定架构）做骨架，把限界上下文、子域划分、上下文映射和团队拓扑串成一套可落地的切系统方法。

01场景：接口爆炸与共享大表，两种"边界病"

事故复盘：一个订单域的两种畸形生长

某电商公司订单域的真实演化史（合并自多家公司的公共剧本）：

  • 病一：接口爆炸。公司按渠道设了七个订单团队（App、小程序、主站、开放平台、线下门店、直播、海外），每个团队都在订单服务里有"自己人"：加个字段要拉七个群对齐，发版要排七条流水线的空档；七年下来订单服务对外暴露了 200+ 个接口，其中 30% 是"同一业务语义的七个变体"——按团队复制，不按业务抽象。新人入职三周不敢碰。
  • 病二：共享大表。十几个团队共用一张 200 万行的订单主表（100+ 字段）：加字段要通知所有下游评估影响，一次变更窗口排两周；不同渠道团队给同一列写不同语义的值（status 字段六套枚举），"订单"这个词在每次需求评审会上都要重新吵一遍定义。DBA 夜里被叫醒的原因，一半是某个团队一条慢查询拖垮了所有人。
  • 两次失败的治理：第一次按"渠道垂直拆微服务"——七套订单服务各自演化，三个月后公共逻辑抄了七份，改一个促销规则要发七次版；第二次把公共逻辑抽成"订单中心统一服务"——所有团队排队改一个服务，发布排队比原来更长。垂直抄一遍、水平抄一遍，怎么切都切不对。
复盘的真正结论

两次治理都在"怎么切代码"上打转，没人问过"业务边界本来在哪、组织边界把它拧成了什么样"。七个团队对应七个接口变体——这不是巧合，这是康威定律在收组织结构欠下的税；一张共享大表——这是缺少限界上下文边界，让所有人在同一个模型上互相踩脚。DDD 战略设计提供的正是这套"先找业务边界、再用边界改组织、最后才动代码"的操作顺序。

02原理：组织结构决定架构——一条被忽视的实证铁律

康威定律不是段子，是被量化验证过的工程事实

1968 年 Melvin Conway 在《How Do Committees Invent?》里写下："任何设计系统的组织，都将产生一种设计与该组织内沟通结构同构的设计。"这句话长期被当作"管理学段子"，直到 2008 年被微软研究院和马里兰大学量化验证：Nagappan、Murphy、Basili 对 Windows Vista 的全部二进制组件建模——不看一行代码，只用八个"组织指标"（改过该组件的工程师数量、已离职工程师数量、组织架构中参与编辑的层级深度、参与编辑的组织占比、跨组织交叉因子等），去预测哪些组件上线后会出故障。

结果：组织结构模型预测精度 86.2%、召回率 84.0%，优于全部五组代码级指标（代码变动 78.6%/79.9%、复杂度 79.3%/66.0%、依赖 74.4%/69.9%、覆盖率 83.8%/54.4%、历史缺陷 73.8%/62.9%）。结论只有一句话："谁写的、几个人写的、跨了几个部门"，比"代码写得多复杂"更能预测哪里会坏。对架构师的直接含义：组织架构图是工程输入，不是软性话题——想改缺陷分布，最强杠杆是改组织，而不是改代码规范。

DDD 战略设计的三层武器：子域 → 限界上下文 → 上下文映射

子域划分（按业务价值）：支撑域、通用域、核心域。核心域是公司赚钱的差异竞争力——投放系统之于广告平台、履约调度之于即时零售，值得最好的人和自主的模型；支撑域是必需但不产生差异化价值的（如商家管理后台）；通用域是行业里大家都一样、直接买或用开源的（认证、消息、支付网关对接）。投入策略的核心纪律：好的架构师把兵力花在核心域，通用域的正义是"别自研"。

限界上下文（模型生效的显式边界）：同一个"订单"，交易上下文里关心价格与履约状态，物流上下文里关心包裹与运单，结算上下文里关心金额与账期——它们不该是同一个类，甚至不该是同一张表。限界上下文的判别式不是"名词有几个"，而是"同一名词的模型在何处不再一致"：当两个团队对'订单已取消'的定义打架时，边界就在打架的地方。一个限界上下文 = 一个自治的模型 + 一份它独占的数据 = 一支能端到端负责它的团队。

上下文映射（边界之间的集成关系）：识别出"下游团队"与"上游团队"的九种关系模式中，工程上最常落地的三种：防腐层（下游在自己的边界内翻译上游模型，上游烂不至于传染——0040 期在 RPC 治理里用过同一思想）、开放主机服务（上游发布标准协议，如消息事件契约——与 0038 期 Schema Registry 同构）、共享内核（两上下文共享一小块模型——最危险的选项，共享面积就是耦合面积）。

团队拓扑：给每个上下文配一支"认知负载合身"的团队

Skelton 与 Paise 的《Team Topologies》给康威定律装上了操作系统，四种团队类型 + 三种交互模式：

团队类型职责订单域例子
流团队 stream-aligned端到端拥有一个限界上下文，面向业务流交付交易团队拥有"交易上下文"（模型+库+服务+值班）
平台团队 platform提供自助式内部平台，降低流团队认知负载订单中台暴露自助 API，不帮业务写代码
赋能团队 enabling临时辅导流团队掌握新能力，教完就走DDD 教练团带三个团队画上下文图后撤离
复杂子系统团队独占高复杂度子系统，对内屏蔽复杂运费引擎/风控规则引擎团队

三种交互模式：X-as-a-Service（平台把能力做成自助服务，交互最轻）、协作 collaboration（两团队共创，交互最重，要限时）、促进 facilitating（赋能团队辅导流团队）。团队拓扑的落地要诀：先让组织结构对齐期望的架构（逆康威机动），再动代码——顺序反了，组织引力会把架构拉回原形。

03架构设计：先把模型钉在图上，再切组织与代码

事件风暴：两个下午挖出真实边界

事件风暴（Event Storming）是战略设计阶段性价比最高的工作坊：业务与工程同室，按"领域事件 → 命令 → 聚合 → 限界上下文"的顺序贴墙。时间线阶段贴领域事件（订单已创建/已支付/已取消…），热点阶段贴业务痛点（橙色便签），热点聚类处就是上下文候选边界——吵架吵得最凶的地方，就是模型不一致的地方，就是边界该划的地方。两个下午、一面墙、比三个月的文档评审挖出的边界更真。七渠道订单的案例里，事件风暴会很快暴露：七个渠道团队贴出的"订单已取消"事件定义有四种（用户取消/超时取消/风控取消/客服仲裁取消）——这四个语义本来就属于不同的限界上下文。

目标架构：一张上下文映射图

容量与选型的三笔账

  • 人力账：限界上下文的数量级 = 能端到端负责的团队数量级。7 渠道 × 全功能 = 7 支昂贵团队重复造轮子；按上下文切 = 交易/履约/结算各 1 支流团队 + 7 支轻渠道适配团队，适配团队 2~3 人即可（模型翻译是薄层），总人力显著低于 7 支全功能团队。
  • 发布账：边界即发布单元。事件契约下的消费端自治让"加字段"从"十几封邮件 + 两周变更窗口"降为"上游发事件新版本、下游按需订阅"——协调成本从组织流程转嫁为契约版本管理（这正是 0038 期 Schema Registry 治理的用武之地）。
  • 演化账：Amazon Prime Video 监控工具从 Step Functions + Lambda 回流单体进程省 90% 成本、Segment 从 140+ 微服务合并回 3 个服务——边界不是越细越好，没有独立伸缩/独立团队/合规隔离诉求的"细"，是给自己发分布式税。先模块化、有真实信号再拆分。

04实战：用 Spring Modulith 把边界钉进 CI

战略设计的落地痛点是"图上画的边界，代码里慢慢糊掉"。Spring Modulith（当前 2.0.x，配 Spring Boot 4；Boot 3 用 1.x 线）把限界上下文映射为包级模块，边界验证进 CI，糊掉就挂构建：

第一段：包结构即边界

com.example.shop
├─ Application.java
├─ order/                        // 模块根 = 公开 API
│  ├─ OrderService.java          //   对外只能用这些
│  ├─ OrderCompleted.java        //   公开领域事件
│  ├─ package-info.java          //   声明允许的依赖
│  └─ internal/                  // 内部实现 = 对外不可见
│     ├─ OrderRepository.java
│     └─ OrderEntity.java
└─ inventory/
   ├─ InventoryService.java
   └─ internal/

第二段：模块依赖白名单 + 边界验证测试

// order/package-info.java —— 依赖白名单，越界即构建失败
@ApplicationModule(allowedDependencies = { "inventory" })
package com.example.shop.order;

// 验证测试 —— 一行挂进 CI
class ModularityTests {
  ApplicationModules modules =
      ApplicationModules.of(Application.class);

  @Test void verifiesModularStructure() {
    modules.verify();  // 越界访问 internal → 精确报出文件与行号
  }
}

第三段：模块间用事件解耦（注册表保证可靠投递）

// order 模块：事务内发事件
@Transactional
public void complete(Order order) {
  repository.save(order.complete());
  events.publishEvent(
      new OrderCompleted(order.getId()));
}

// inventory 模块：独立事务异步消费
@ApplicationModuleListener
void on(OrderCompleted event) {
  // 独立事务 + 主事务提交后才执行
  stock.decrement(event.orderId());
}
// Event Publication Registry 把事件落库，
// 崩溃重启后重发 —— 应用内 Outbox，无需外挂消息中间件
这是模块化单体的姿势：一个进程内先把边界立起来（验证、事件、按模块出文档），哪天某个上下文需要独立伸缩或独立团队，沿事件缝拆出去就是微服务——Fowler 的判断至今成立："几乎所有成功的微服务故事，都从拆掉一个太大的单体开始；几乎全部从零直接上微服务的系统，最后都陷入严重麻烦。"先立边界、后拆进程，顺序别反。

05今日要点

  • 组织结构是工程输入，不是软性话题：Vista 实证——组织指标预测缺陷（精度 86.2%/召回 84.0%）优于全部代码指标；接口爆炸与共享大表的病根都在边界，不在代码。
  • 限界上下文的判别式是"模型何处不再一致"：两个团队对"订单已取消"定义打架的地方就是边界；同一名词在不同上下文就该有不同模型、不同表。
  • 投入跟着子域走：核心域配最好的团队与自主模型，通用域的正义是"别自研"，支撑域够用就好——兵力错配是最大的架构浪费。
  • 先改组织再迁代码（逆康威机动）：团队拓扑四类型三交互给边界配团队；顺序反了，组织引力会把架构拉回原形。
  • 边界要进 CI 才不会糊：Spring Modulith 把限界上下文变成包级模块 + 构建期验证 + 事件解耦；模块化单体是微服务的前置形态，不是妥协。

06架构师思考题

题目：某公司 800 人技术部门，订单域：30 人共用一个订单服务与一张共享订单大表，发布需全员协调；业务侧有 5 个渠道团队排队提需求，每次跨团队变更要"提单 → 排期 → 会审"三步，平均等待两周。公司决定"全面微服务化"，拟将订单服务按渠道拆成 5 个微服务、每个渠道团队一个。作为架构师：① 用 DDD 战略设计给出你的边界方案（子域/限界上下文/团队拓扑），并说明为什么"按渠道拆 5 个"大概率重蹈覆辙；② 给出 12 个月分阶段迁移路线（团队与代码如何动、存量共享大表如何拆、怎么验证每阶段边界没糊）；③ 若迁移进行到一半，两个渠道团队被合并成一个事业部，你的架构会遭遇什么反噬，怎么应对？▶ 点击展开解析

🔍 三问拆解

① 边界方案："按渠道拆 5 个微服务"重复了场景篇病一的错误——渠道是组织的销售触点，不是业务的模型差异；按渠道切，公共交易逻辑会抄五份（或者抽一个"公共订单中心"让五队排队，回到第二次失败治理）。正确切法：先用事件风暴挖模型差异——交易（价格/取消语义）、履约（包裹/运单）、结算（金额/账期）是三个真上下文，渠道只是交易上下文的适配器。目标：交易/履约/结算各 1 支流团队（核心域，配最强的人），5 渠道各留 2~3 人的薄适配层（支撑域），认证消息等用现成组件（通用域）。这样服务数是 3+薄层，不是 5 个全功能副本；渠道间的"复用"由事件与契约承担，不再由代码拷贝承担。团队拓扑上再配一个平台团队把"事件契约、CI 边界验证、云底座"做成 X-as-a-Service，流团队自助消费。

② 12 个月路线：第一阶段（1~2 月）冻结+画像：新需求一律按目标上下文实现（哪怕暂住旧库），存量冻结不再加深耦合；用 Modulith 对现有代码做"实际依赖画像"（ArchUnit/Modulith 文档器出图），让"边界糊成什么样"第一次可见。第二阶段（3~5 月）先组织后代码：按目标边界重组团队（逆康威机动）——交易/履约/结算三支流团队到位、渠道并入适配层；代码上先把单体内部按 Modulith 模块立边界、verify() 进 CI。第三阶段（6~9 月）数据搬家：共享大表按上下文拆——先"读分离"（各上下文建自己的投影表，从事件流回填），再"写收口"（写入路径逐上下文切换，双写对账），最后下线共享表；事件契约上 Schema Registry 管版本兼容（0038 期纪律直接复用）。第四阶段（10~12 月）进程拆分按需执行：只有出现"独立伸缩/独立发布节奏/合规隔离"真实信号才把模块拆成独立服务，否则保持模块化单体——Prime Video/Segment 的回流案例是清醒剂。每阶段验证：verify() 零违例 + 事件契约兼容检查 + 跨团队变更等待时长（应从两周降到天级）三个指标入月度架构评审。

③ 组织合并的反噬：两渠道团队并成一个事业部 = 康威定律反向发力：他们的两个适配层会自然"融合"——共用代码、共用排期、最后互相 import 内部包，若这个事业部再被赋予交易域的诉求，边界会被重新拉歪。应对三招：边界自适应机制——限界上下文图不是一次性交付物，架构评审每季度对照组织变化重画一次（团队拓扑本身就要求"组织动、拓扑动"）；技术边界顶住组织引力——CI 里的 verify() 与事件契约让"融合"有摩擦成本，糊边界会挂构建，给管理者一个"要不要改边界"的显式决策点而不是无声漂移；顺势收编——若合并是长期事实，承认它是信号：把两渠道适配层合并为一个多渠道适配上下文（减少一支团队），但交易上下文的独立性不让步——渠道怎么合并是支撑域的事，核心域边界不动。康威定律不可违抗，但可以被管理：你要做的不是阻止组织变化，而是让每次变化都显式地过一遍边界重审。
