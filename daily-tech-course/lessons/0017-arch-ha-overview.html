高可用架构设计：别把 99.9% 挂在嘴边

一次机房网络抖动引发的全线雪崩复盘 —— 可用性的数学、故障域与四层冗余模型，以及一套能落地的高可用基线清单。

🏗 架构运维通用 📅 2026-09-03 · 第 17 期 ⏱ 预计阅读 10 分钟

01一次 200ms 网络抖动，放倒了 12 个服务

某业务团队的复盘记录：凌晨 2 点，机房一台汇聚交换机固件缺陷引发间歇性 200ms 网络抖动。就这点抖动，15 分钟内 12 个微服务连环雪崩：MySQL 主从复制延迟飙升 → 应用线程池被慢查询占满 → 上游调用无超时兜底全数阻塞 → 网关线程池打满 → 全站 502。交换机 3 分钟后自动恢复，服务却持续故障了 15 分钟——因为线程池和连接池没有从"半死"状态里恢复过来。

复盘最扎心的结论是：每个服务单独看都"设计合理"，链路整体却极度脆弱。根因不在某一处配置，而在架构层面从来没有回答过三个问题：

1

系统的可用性目标是多少？没有数字，就没有设计——"高可用"三个字不构成任何约束；

2

故障会从哪里来、炸多大？故障域从未被识别，冗余自然无从谈起；

3

挂掉之后靠什么恢复？没有预设的故障转移路径，恢复全靠人肉。

今天这期把这三个问题一次讲透。这是"架构与中间件运维"系列的第一讲，也是后面所有中间件课程（注册中心、缓存、消息、时序库、对象存储、K8s）共用的总纲。

02原理：可用性的数学与故障域

可用性是乘法，而微服务在疯狂做乘法

可用性等级的通用换算：

等级年不可用时间大致对应
99%（2 个 9）3.65 天传统单机应用
99.9%（3 个 9）8.76 小时多数内部系统的现实水平
99.99%（4 个 9）52.6 分钟需要全链路冗余 + 自动故障转移
99.999%（5 个 9）5.26 分钟电信级，改一次配置的窗口都快不够了

关键在下一行公式。串联链路的可用性是各环节相乘：

# 一条请求链路：网关 → 订单 → 库存 → MySQL 主库，各 99.9%
0.999 × 0.999 × 0.999 × 0.999 ≈ 99.6%  # 年不可用 ≈ 35 小时

# 微服务拆到 10 个环节串联，仍各 99.9%
0.999^10 ≈ 99.0%  # 每个服务都"三个9"，整体只剩"两个9"

这是微服务架构的第一性矛盾：拆分越多，串联环节越多，整体可用性越差。高可用架构的全部工作，本质上就是在对抗这个乘法——用冗余提升单环节可用性，用并行依赖与降级把乘法变回加法。

错误预算：把"不可用"变成资源

SLO 定为 99.9%，意味着每年有 8.76 小时允许故障。这笔"错误预算"可以花在发版、重启、混沌演练上。预算有结余 → 放心迭代；预算烧光 → 冻结变更、优先稳定性。这样"稳定性 vs 迭代速度"的扯皮就变成了查账。SLO / SLI / 错误预算是 Google SRE 方法论的基石，也是后续监控告警一讲的主角。

故障域：先知道会炸多大，再谈冗余

故障域 = 一次故障能波及的最大范围（爆炸半径）。识别方法很朴素：把共享的底层资源画出来——同一个 Pod、同一台宿主机、同一个机架/交换机、同一个机房、同一个云区域，每一层都是一个故障域。冗余设计只有一条铁律：

冗余设计铁律

多副本必须落在不同的故障域里。两个 Redis 主从放在同一台宿主机、同一个机房，可用性等于没有冗余——故障域没隔开，副本数只是心理安慰。

03架构设计：四层冗余模型与权衡

按故障域从小到大，冗余投资分四层，成本递增、收益递减，绝大多数系统止步于第三层：

四个必须当面对冲的权衡

  • 可用性 vs 一致性：多机房双活必然引入复制延迟，追 RPO=0 就要半同步/强一致，写延迟上升；追低延迟就接受 RPO>0。这两个 9 不能都要满，按业务定（交易可对账补偿，浏览可容忍旧数据）；
  • 冗余 vs 成本：L3 直接翻倍。正确姿势是分层设 SLO——交易核心链路 99.99%，内部管理后台 99.5%，把钱花在刀刃上；
  • 自动切换 vs 误切：自动故障转移是双刃剑，脑裂比单点故障更难排查。MySQL MHA、Redis 哨兵都要配法定多数（quorum）与 fencing；
  • 容量规划：N+1 原则——任意一个实例/节点挂掉，剩余容量仍能以 ≤70% 水位扛住峰值。即集群容量 ≥ 峰值 ÷ 70% × (N+1)/N，留出故障时的降级余量。
调用侧韧性是另一半冗余解决"有备份"，还要解决"快速切过去"：超时（比下游 P99 略宽）→ 熔断（连续失败快速失败）→ 重试（仅幂等操作、有限次数、带退避和抖动）→ 降级（读走缓存、写进队列）。开篇事故里，这四件事一件都没做，200ms 抖动才演变成 15 分钟雪崩。具体熔断限流实现见 第 1 期 Sentinel。

04实战：一套 Spring Cloud 微服务的高可用基线

以下配置可直接作为评审清单用——每一项都对应上面某个故障域。

① 注册中心：Nacos 至少 3 节点，客户端带容灾

# application.yml —— 关键是 server-addr 列出全部节点 + 本地容灾开关
spring:
  cloud:
    nacos:
      server-addr: "10.0.0.11:8848,10.0.0.12:8848,10.0.0.13:8848"  # 3 节点跨机部署
      discovery:
        namespace: prod
      config:
        file-extension: yaml
# Nacos 客户端默认会把服务列表快照落盘（JM.SNAPSHOT），
# 集群整体不可用时仍可用本地快照启动 —— 不要关闭该机制

② 调用链：超时 + 有界重试，一个都不能少

# OpenFeign 超时与重试（必须配合服务端幂等）
spring:
  cloud:
    openfeign:
      client:
        config:
          default:
            connect-timeout: 1000   # 连接 1s：快速发现"实例不可达"
            read-timeout: 3000      # 读 3s：按下游 P99=800ms 放宽到 3 倍多
            retryer: com.xxx.config.FeignRetryConfig  # Retryer.NEVER(1, 1s, 3)
# 原则：只有幂等接口才重试；次数 ≤3；退避加随机抖动，
# 否则重试风暴会把下游剩余健康实例也压垮（雪崩放大器）

③ 部署层：K8s 反亲和 + 预算保护

# 把副本打散到不同节点（故障域隔离） + 滚动更新时保住容量下限
spec:
  topologySpreadConstraints:
    - maxSkew: 1
      topologyKey: kubernetes.io/hostname   # 同一服务的副本不挤在同一宿主机
      whenUnsatisfiable: DoNotSchedule
---
apiVersion: policy/v1
kind: PodDisruptionBudget
spec:
  minAvailable: 2          # 驱逐/更新期间至少保 2 副本在岗

④ 验证：可用性是演练出来的，不是画出来的

1

故障注入常态化：在预发环境定期"拔插头"——kubectl delete pod、kill -9 MySQL 主库、断开机房间链路，观测 RTO 是否达标；

2

告警盯"剩余健康度"：监控不报"挂了 1 个节点"（这是设计内的正常故障），报"剩余容量水位 > 70%"——前者制造疲劳，后者才需要人介入；

3

每季度跑一次全链路故障演练，把"切换是否自动、业务是否无感、数据是否对账一致"三个问题重新回答一遍。

✅ 高可用基线清单（拿去对表）

☐ 无状态服务 ≥2 副本且跨节点 　☐ 无任何单点（连 Nacos/Redis/MySQL/MQ/定时任务都算）　☐ 所有外部调用有超时 　☐ 幂等 + 有界重试 　☐ 核心链路有降级预案 　☐ 中间件集群跨故障域部署 　☐ PDB/反亲和就位 　☐ 故障演练本季度跑过

05今日要点

  • 串联可用性相乘：10 个 99.9% 的服务串联只剩 99.0%。微服务拆得越细，越要用冗余、并行依赖和降级对冲乘法。
  • 先定 SLO 再做设计：99.9% 做到实例级+中间件级冗余即可，99.99% 才值得上同城双活。错误预算用来平衡稳定性与迭代速度。
  • 冗余的唯一铁律是隔开故障域：副本数不等于可用性，同宿主机/同机房的多副本只是心理安慰。
  • 容量规划用 N+1：挂任何一个节点，剩余容量仍 ≤70% 水位扛住峰值，才是合格的冗余。
  • 可用性是演练出来的：RPO/RTO 不进监控、不做混沌验证的方案，都只是 PPT 高可用。

06架构师思考题

题目一：你们计划把一个单体应用拆成 8 个微服务，各服务可用性 99.95%。CTO 问："拆完之后系统是不是更稳了？"请给出定量分析与架构建议。▶ 点击展开解析

🔍 定量分析：乘法先算账

最坏情况是 8 个服务全串联：0.9995^8 ≈ 99.60%，年不可用 ≈ 35 小时。而拆分前的单体是 99.95%，年不可用 ≈ 4.4 小时。若链路形态不变，拆分让整体可用性下降了约 8 倍——这是微服务架构反直觉但必须直面的事实。但拆分同时带来两个补偿性收益：故障隔离（一个服务的故障不再全站瘫痪，可按调用方分级熔断）与独立冗余/部署（每个服务可单独多副本、灰度、回滚）。所以答案不是"更稳"或"更不稳"，而是取决于拆分后是否补齐了韧性配套。

✅ 架构建议

  • 减少串联深度：能并行的并行（如订单确认时库存/优惠券/风控三调用并行化）；强串联依赖考虑本地缓存 + 失败降级，把"必须可用"的环节从 8 个降到 3~4 个；
  • 逐环节提升单点可用性：每个服务 2+ 副本跨节点 + 无单点中间件，单服务从 99.95% 提到 99.99% 后，0.9999^8 ≈ 99.92%，加上降级兜底，整体可以反超单体；
  • 非核心链路异步化：积分、通知、日志类依赖改走消息队列（Pulsar），链路从同步串联中摘除——同步链路只留"交易成败必需"的环节；
  • 给 CTO 的正确表述：拆分买来的是隔离性和演进速度，代价是链路复杂度；配套（超时/熔断/降级/冗余）没做完之前，可用性不升反降。拆分计划应与韧性建设同批交付。
题目二：业务 SLO 定为 99.99%（年不可用 52.6 分钟），你主导设计同城双活方案。数据库用 MySQL，缓存 Redis，消息 Pulsar。请给出整体架构与关键取舍，并说明为什么不用异地多活。▶ 点击展开解析

🔍 目标拆解

99.99% 意味着单次机房级故障的 RTO 必须 ≤ 5 分钟且全年只允许发生数次——人工决策切换不可能达标，切换必须自动化。方案核心：两个同机房域对等部署，正常按单元化路由分流，故障时一键（自动）切流。

✅ 参考架构

  • 接入层：智能 DNS/GSLB + 网关双活，两机房各承担 50% 流量，健康检查失败自动摘除；
  • 应用层：两机房对等部署全量服务（K8s 集群各一套，副本数按 60%~70% 峰值容量配，单机房要能临时扛 100%）；
  • MySQL：机房 A 主 + 机房 B 半同步从（after_sync，RPO=0），配合 MHA/Orchestrator 自动切换；半同步退化超时要设保护（rpl_semi_sync_master_timeout），避免从库抖动拖垮主库写入——这是 RPO=0 与写延迟之间的核心取舍点；
  • Redis：两机房各自集群，不跨机房主从（复制延迟 + 脑裂风险）；缓存以"可重建"为原则，切流后直接回源预热，用短暂穿透换架构简单；
  • Pulsar：Bookie 与 Broker 双机房混布，机架感知 placement（bookkeeper ensemble 覆盖两机房），消息天然多副本，无需双写；
  • 单元化路由：按用户 ID 哈希分单元，写操作落在数据归属机房，避免双写冲突；跨单元调用只允许读。

⚖️ 为什么止步于同城双活

同城（<10ms 延迟）可以用半同步保 RPO=0；异地延迟 30ms+，强同步写入不可接受，只能异步复制（RPO=分钟级）——99.99% 的 SLO 允许的年故障预算是 52 分钟，数据丢失对交易类业务是不可接受的第二种故障，而异地多活的单元化改造 + 流量调度 + 数据对账成本要再翻一倍以上。正确路径：同城双活保 SLO，异地做"备份级"容灾（异步复制 + 定期演练切换），业务量级到了再演进多活。
