Apache Pulsar 系列开篇：存算分离架构，凭什么让扩容不搬数据（与 Kafka 对比）

📅 2026-08-27（周四） 🛰 Apache Pulsar 系列 · 第 1 讲 · 开篇 ⏱ 预计阅读 10 分钟 🎯 Broker/BookKeeper 分层 / Ledger 条带 / E-Qw-Qa / 订阅模型

一、一次"扩容引发的线上事故"

某电商中台 Kafka 集群（36 台 broker）磁盘水位升至 82%，决定扩容 12 台新节点。运维执行 partition reassignment 后，副本数据开始跨机架搬迁：网卡打满、磁盘 IO 争抢，消费 P99 延迟从 20ms 飙到 800ms，持续 6 小时，最后被迫凌晨降级重做。更早之前还踩过一个坑：单台 broker 宕机重启，因为挂了 4TB 分区副本，日志索引恢复耗时 40 分钟，期间相关分区全部不可写。

复盘结论：事故根因不是 Kafka"不行"，而是它的架构使然——计算（服务）与存储（日志副本）耦合在同一个 broker 进程和磁盘上。扩存储必然牵动数据搬迁；broker 故障必然带着几百 GB 副本一起"遭殃"。Pulsar 的存算分离（Compute-Storage Separation）正是冲着这两个痛点设计的。今天作为 Pulsar 系列开篇，把这套分层架构、Ledger 模型、与 Kafka 的核心差异一次讲清。

二、原理：两层架构 + Ledger 条带化

Pulsar 把"服务请求"与"持久化数据"拆成两个独立集群：

  • 计算层 Broker（无状态）：不存任何消息数据。负责接收 Producer 写入、推送给 Consumer、维护 topic 的 ownership（一个 partition 同一时刻只由一个 broker 服务）与订阅游标（cursor）。因为无状态，ownership 可以秒级切换——broker 宕机，其他 broker 立即接管，数据毫发无损。
  • 存储层 BookKeeper（bookie 集群）：真正落盘。每个 partition 的消息流被切成一个个 ledger（segment），每个 ledger 以条带化方式分布到一组 bookie 上；写满（按时间/大小阈值）就 roll 出新 ledger，落到（可能不同的）一组 bookie。

关键机制一：Ledger roll（切分滚动）

一个 partition 的数据 = 无限追加的 ledger 序列。扩容 bookie 后，新 ledger 自然写到新 bookie，老 ledger 一字不动——这就是"扩容不搬数据"的原理。用下面这张条带图理解（新增 Bookie-4 后，只有 L3 之后的 ledger 用到它）：

● = 该 ledger 的一个副本在此 bookie 上；E=3 时每个 ledger 恰好落在 3 台 bookie（不同组合）

关键机制二：Quorum 写法定义

BookKeeper 写入由三个参数决定：E（Ensemble，ledger 分布的 bookie 数）、Qw（Write Quorum，每条消息写几副本）、Qa（Ack Quorum，几副本落盘即应答）。生产典型配置 E3-Qw3-Qa2：3 副本、写成功 2 个即向客户端应答——任一 bookie 慢盘不拖累写入延迟，同时保证宕机一台不丢已确认消息（还剩 2 副本）。要求更高持久性用 E4-Qw3-Qa2（滚动冗余）。

关键机制三：Auto-recovery

bookie 宕机后，BookKeeper 的 rereplication 机制后台把缺失副本从其余 bookie 补到健康节点，broker 与业务全程无感。对比 Kafka：ISR 收缩 + leader 切换发生在服务路径上，数据量大时恢复窗口长。

三、架构视角：这套设计值钱在哪，代价是什么

  • 扩容解耦：连接数/吞吐涨 → 加 broker；存储涨 → 加 bookie。两条曲线独立扩展，容量规划不再"一锅粥"。
  • 故障域更小：broker 故障只迁移 ownership（秒级）；bookie 故障走后台补副本。存储节点重启不用重放日志索引，恢复时间与数据量基本无关。
  • 百万级 topic：数据与游标分离，单 broker 服务的 topic 数不再受本地磁盘与启动恢复约束，适合 IoT、多租户 SaaS 场景。
  • 多租户原生：tenant → namespace → topic 三级模型，配额（rate limit）、ACL、retention/backlog 策略全部挂在 namespace 上，开箱即用。
⚠️ 架构师要清醒：代价同样真实 组件从 1 个变 3 个（broker + bookie + ZK 元数据），链路更长，排障面更宽（写入要同时看 broker 日志和 bookie journal）；小规模（日增 GB 级、几十个 topic）下收益不明显，反而吃掉运维预算。没有银弹，只有权衡——规模与多租户压力越大，分层的红利越明显。

顺带立个框架：四种订阅模式

  • Exclusive：排他订阅，单 consumer；
  • Failover：主备，同一时刻只有主 consumer 消费（≈ Kafka consumer group 的分区独占）；
  • Shared：轮询分发到多个 consumer，牺牲分区内顺序换水平扩展吞吐；
  • Key_Shared：按消息 key 哈希"黏"到固定 consumer，同 key 保序 + 水平扩展——这是 Kafka 模型做不到的差异化能力（后续课程专门讲）。

四、实战：3 分钟起环境，验证"存算分离"不是口号

1. 本地 standalone（学习/联调）

# 开发联调用 standalone（内嵌 broker + bookie + ZK）
docker run -it --rm \
  -p 6650:6650 -p 8080:8080 \
  apachepulsar/pulsar:3.3.2 bin/pulsar standalone

2. 查看 topic 的 ledger 结构（验证分层）

# 造 1000 条消息
bin/pulsar-client produce -m "hello-" -n 1000 persistent://public/default/orders

# 看 topic 内部：每个 ledger 的 id/条数/大小/所在 bookie
bin/pulsar-admin topics stats-internal \
  persistent://public/default/orders

# 输出片段 —— 消息确实存在 bookie 上，不在 broker 上：
"ledgers": [
  { "ledgerId": 17, "entries": 1000, "size": 48213,
    "bookieAddressSet": ["bk1:3181", "bk2:3181", "bk3:3181"] }
]

3. 生产端 Java 代码（吞吐关键参数）

PulsarClient client = PulsarClient.builder()
    .serviceUrl("pulsar://broker1:6650,broker2:6650")  // 多地址自动容灾
    .connectionsPerBroker(1)                        // 连接复用，别多开
    .build();

Producer<byte[]> producer = client.newProducer()
    .topic("persistent://trade/orders/topic")
    .enableBatching(true)                    // 吞吐核心开关
    .batchingMaxMessages(1000)
    .batchingMaxPublishDelay(1, TimeUnit.MILLISECONDS)
    .blockIfQueueFull(true)                // 生产端背压，防 OOM
    .sendTimeout(30, TimeUnit.SECONDS)
    .create();

4. namespace 策略（运维重点，坑点高发区）

# 消费 ack 后保留 7 天 / 100G（默认 retention=0：消费即删，与 Kafka 语义相反！）
bin/pulsar-admin namespaces set-retention public/default \
  --retentionTimeInMinutes 10080 --retentionSizeInMB 102400

# backlog（未 ack 积压）上限，超限丢弃最老消息，防止慢消费者撑爆 bookie
bin/pulsar-admin namespaces set-backlog-quota public/default \
  --limit production-limit --limitSize 53687091200 --policy producer_exception
⚠️ 生产坑点清单 ① bookie 的 journal 与 entry log 必须分盘（journal 用 NVMe，顺序写延迟决定写入 TPS）；② 客户端连接是复用的，严禁每条消息 new 一个 producer；③ 默认 retention=0 表示"消费 ack 后即删"，想重放历史必须显式设置 retention 或用 持久订阅；④ 存量 Kafka 生态可用 KoP（Kafka-on-Pulsar）协议层平滑接入，客户端零改造。

五、Kafka vs Pulsar：选型对照与容量速算

维度KafkaPulsar
存储模型分区副本存 broker 本地磁盘Broker 无状态 + BookKeeper ledger 条带
扩容partition reassignment 搬数据新 ledger 落新 bookie，老数据不动
故障恢复leader 选举 + 日志恢复，数据量大时慢ownership 秒级切换，数据不动
消费模型consumer group（分区独占），生态极成熟4 种订阅模式（Shared / Key_Shared 差异化）
多租户弱，靠 topic 命名约定原生 tenant/namespace + 配额/ACL
Schema / 函数外部组件（Schema Registry / Streams）内置 Schema Registry、Functions
运维复杂度单组件，心智负担低broker + bookie + ZK 三组件，链路更长

容量规划速算（以 10 万 QPS × 1KB 为例）

  • 入口流量 ≈ 100 MB/s；按 E3-Qw3-Qa2 写 3 副本 → bookie 侧实际写入 300 MB/s，journal 盘必须 NVMe；单 bookie journal 写能力按 150~200MB/s 估，6 台 bookie 起步（留 1 台故障冗余）。
  • broker 无状态，主要消耗连接与 batching，4C8G 单台可扛数万 QPS，3 台起步按吞吐线性加。
  • 保留 7 天：100MB/s × 86400 × 7 ≈ 57TB × 3 副本 ≈ 170TB 原始存储（entry log 压缩后再打折），bookie 水位控制在 70% 以内 → 规划 240TB+。

六、今日要点

1
存算分离是根基
Broker 无状态只管服务，BookKeeper bookie 只管落盘；topic = 无限滚动的 ledger 序列，条带化多副本。
2
扩容不搬数据
扩 bookie 只影响新 ledger 的落点，老 ledger 不动；对比 Kafka reassignment，扩容窗口从小时级降到秒级。
3
故障域更小
broker 挂 → ownership 秒切；bookie 挂 → auto-recovery 后台补副本，恢复时间与数据量基本无关。
4
E / Qw / Qa 定权衡
典型 E3-Qw3-Qa2：3 副本、2 应答。持久性、延迟、成本三者的旋钮全在这三个参数里。
5
选型不跟风
海量 topic / 多租户 / 存储独立扩容 / 秒级恢复 SLA → Pulsar；生态成熟度优先、规模适中 → Kafka 依然是好答案。

七、架构师思考题

Q1"Pulsar 扩容不搬数据"真的没有代价吗？请分析老数据分布不均的问题与缓解手段。▶

解题方向：从 ledger 生命周期切入，代价藏在"分布均匀性"里

代价一：老 ledger 永远不迁移，数据倾斜是必然的。新扩的 bookie 只承接新写入的 ledger，如果 topic 写入速率低（ledger roll 周期长），新 bookie 可能数天都分不到数据；反之老 bookie 上堆积着大量热数据与冷数据，磁盘水位不均，监控上会看到"同规格 bookie 水位差 30%+"的告警噪音。

代价二：ledger 粒度决定均衡的"最小单元"。BookKeeper 的均衡以 ledger 为单位搬运，ledger 设得太大（比如按 2GB 切），均衡一次搬的块就太大、太重；设得太小，元数据（ZK 里的 ledger 清单）膨胀，roll 频繁也会抖动。这是一个典型的"块大小权衡"，类似文件系统的 block size 或 LSM 的 SSTable 大小。

缓解手段（按优先级）：

  • Placement 策略：启用 rack-awareness / region-awareness ensemble placement，让 broker 写新 ledger 时优先选水位低、负载轻的 bookie（BookKeeper 自带 WeightedRandomPlacement，基于 bookie 上报的磁盘利用率与写入速率做加权随机）；
  • 调小 ledger roll 阈值：高写入 topic 用时间阈值（如 10 分钟）而非大空间阈值，让"新数据流向新节点"的收敛更快；
  • auto-recovery 顺势均衡：对水位过高的 bookie 做计划内下线-补副本，借 rereplication 把数据"顺路"搬到低水位节点——这是有损窗口的主动均衡，要避开高峰；
  • 接受不完美：架构师要向业务方讲清楚"秒级扩容"与"立即均衡"不可兼得，水位倾斜是可接受的稳态，只在超过阈值（如 15%）时干预。

结论：Pulsar 把 Kafka"扩容时的数据搬迁"转化为"扩容后的渐进均衡"，把 O(全量数据) 的搬迁成本摊薄到后台与时间维度——这不是消灭了代价，而是把代价从关键路径挪到了非关键路径。这个"代价转移"的思维方式值得在所有架构决策里复用。

Q2你负责的消息平台基于 Kafka，什么信号出现时值得评估迁移 Pulsar？迁移路径如何设计才能把风险压到最低？▶

解题方向：先建立"值得迁移"的量化信号，再设计可回滚的灰度路径

第一步：触发信号清单（满足 2 条以上才立项评估，避免为迁移而迁移）：

  • 存储年增速：数据保留周期不断拉长、存储年增 50%+，Kafka 每次扩容的 reassignment 已造成过线上抖动事故；
  • 恢复 SLA：业务要求 broker 故障恢复分钟级甚至秒级，但 Kafka 大数据量分区恢复动辄半小时；
  • topic 规模：topic/partition 数逼近十万级（IoT、多租户 SaaS），Kafka broker 启动加载元数据与副本恢复成为瓶颈；
  • 多租户刚需：需要按团队/客户做配额、隔离、独立 retention 策略，在 Kafka 上只能靠命名约定 + 人肉纪律；
  • 消费模式需求：出现"同 key 保序 + 水平扩展"（Key_Shared）或同一份数据多组独立游标回放的需求，Kafka 模型实现别扭。

反信号（出现即暂缓）：团队没有专职中间件运维；重度依赖 Kafka Connect/Streams/KSQL 生态；当前规模用 Kafka 半年都没出过扩容/恢复事故——此时迁移纯属引入新风险。

第二步：低风险迁移路径（KoP 双轨灰度）：

  • 阶段 1 · 兼容试点：在 Pulsar broker 上启用 KoP（Kafka-on-Pulsar）协议处理器，选 1~2 个非核心 topic，用原有 Kafka 客户端直连读写，验证语义（ack、offset 对应 cursor）与性能基线，业务零改造；
  • 阶段 2 · 双写切读：新增消息走"双写"（生产端旁路镜像或 MirrorMaker2 反向同步 Kafka→Pulsar），消费端按团队灰度切到 Pulsar 订阅；出问题秒级切回 Kafka——因为双轨都在，回滚成本≈改一个开关；
  • 阶段 3 · 收编存量：老 topic 按保留周期自然过期或用迁移工具搬迁，Kafka 集群缩容下线；此阶段才逐步把客户端从 Kafka 协议换成原生 Pulsar 协议（享受 batching、Schema Registry 等全部红利）；
  • 全程护栏：两侧对账（消息条数/位点延迟监控）+ 书面化回滚预案 + 每阶段观察至少一个完整业务周期（含大促/月末峰值）。

结论：迁移决策的本质是"现有架构的痛点成本"与"新架构的学习/运维成本"之间的对赌。架构师的价值不在于选最新最潮的技术，而在于把两边的成本都量化清楚，并且始终给自己留一条"便宜的退路"。
