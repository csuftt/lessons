AI · AI 大模型应用系列第 1 讲（RAG 架构篇）

给大模型外挂一个可随时更换的教科书：RAG 检索增强架构

大模型的知识固化在训练参数里——像是闭卷考试，教不了它你公司上周才改的退货政策。RAG（检索增强生成）的思路很朴素：考试时允许翻书。今天把这条"翻书"链路拆成离线索引与在线检索两条管线讲清楚：切块为什么决定上限、向量与关键词为什么要混检、重排器在堵什么洞、四把质量标尺怎么用，以及 RAG 与微调的选型账。这是 AI 大模型应用系列的第一讲。

01一个"演示惊艳、上线翻车"的企业知识库复盘

某集团要上线"制度问答助手"，覆盖 5 万份制度文档、产品手册与运维手册。Demo 当天效果惊艳，全员鼓掌；两周试运行，工单系统里堆了三类投诉：

  • 答非所问型：用户问"XR-7500 的额定功率是多少"，助手把 XR-7000、XR-7500S 的参数各抄了一段混在一起——型号差一个字符，语义向量看来几乎一样；
  • 知识过期型：用户问"现在的差旅报销标准"，助手引用的是三年前就废止的旧制度——源文档早就更新了，向量索引里躺的还是旧版本切片；
  • 东拉西扯型：概念类问题（"预算管理的总体原则是什么"）检索回来 10 段毫不相关的碎片，上下文被污染，模型开始一本正经地胡说。

复盘结论扎心：大模型本身没有变差，坏的是"翻书"的每一环。型号匹配失败是精确匹配缺位（该配关键词检索）；旧制度复活是索引更新链路缺失；上下文污染是排序与过滤粗糙。三类故障分别对应检索质量的三把标尺——召回率、精确率、排序质量。这一讲就沿着"书怎么切、怎么查、怎么摆到模型面前"把整条链路讲透。

02原理：离线生产"书页"，在线完成"翻书"

离线管线生产"书页"，在线管线完成"翻书"——这是 RAG 的总纲。离线侧：文档解析清洗后切块（Chunking），每个块经 Embedding 模型编码成向量写入向量索引，同时建关键词倒排索引（BM25）；在线侧：用户问题先做查询改写（补主语、扩同义词），然后双路并发检索，RRF 倒数排名融合成候选集，再用 Cross-Encoder 重排出最相关的少数几块，拼进提示词交给 LLM 生成带引用的答案。

切块：决定检索上限的第一道工序

为什么不把整篇文档直接丢给模型？三个原因：Embedding 模型有输入长度上限（几百到几千 token）；整篇文档的向量是"全文平均语义"，查询词的信号被稀释——块越大语义越糊，块越小上下文越碎；上下文窗口是按 token 计费的稀缺资源。经验起点：按文档结构递归切分，目标块 300~800 token、相邻块重叠 10%~20%（防止关键句正好被切断）。表格、代码这类结构化内容尽量不切断，并把章节标题、文档元数据（版本、生效日期）附在每个块上——第 01 节"旧制度复活"的毛病，一半要靠元数据过滤来治。

混合检索与重排：宽召回、严排序

向量检索（稠密）懂语义但认不了"XR-7500"这种精确符号；BM25（稀疏）擅长精确匹配但不懂"预算管理"约等于"费用管控"。两路各取 Top 20~50，用 RRF 融合——公式很朴素：每路按排名贡献 1/(k+名次) 的分数（k 取 60），两路都靠前的块胜出，且不需要调融合权重。候选集出来后，Cross-Encoder 重排器把"问题+块"拼在一起过一遍精算，管住最后几名的精确率——代价是每块 10~50 毫秒，所以只对 Top 50 精排，不做全库。生产经验：混检+重排对纯向量方案的提升普遍在 15%~25%，这已经是 2025 年后生产级 RAG 的默认形态，不再是加分项。

四把质量标尺

指标量什么坏了的典型症状先动哪里
召回率 Recall该查到的块查到没有答不出库里明明有的问题块大小/查询改写/Top-K
精确率 Precision查回来的块有多少相关东拉西扯、上下文污染重排/降 Top-K
nDCG相关的块排没排前面答案引用了次相关的段落重排模型/融合策略
忠实度 Faithfulness答案是否只依据上下文检索对了仍一本正经胡说提示词约束/换模型

排查必须先量指标再动手：答案不好时，先判断是检索坏（前三把尺子）还是生成坏（第四把）——这是 RAG 排障的第一岔路口，评测框架（RAGAS 等）就是把这四把尺子自动化，留到本系列评测专题展开。

03架构设计：选型、容量与高可用

切块策略选型

策略原理适用代价
递归分块按标题/段落/句子层级优先切通用默认起点几乎为零
语义分块相邻句向量相似度骤降处切开主题跳变多的长文入库成本×3~5
父子分块子块（小）做检索，父块（大）做上下文制度/合同等结构化文档双索引+指针，存储约翻倍

RAG 还是微调？

维度RAG微调
知识更新换文档重索引，分钟级生效重新训练，天级起步
可溯源答案带引用出处知识熔进权重，无法引用
擅长事实型问答、多文档汇总风格/格式/领域语感
单位成本检索+推理按次计费训练一次性投入大

决策口诀：知识用 RAG，行为用微调，两者可叠加。让模型"知道新退货政策"是知识问题，走 RAG；让模型"用客服口吻按固定 JSON 模板回复"是行为问题，走微调。分不清时先上 RAG——成本曲线平缓得多，而且 RAG 的检索质量数据（哪些问题没召回）反过来是微调数据集的最佳来源。

容量与高可用要点

  • 向量容量账：5 万文档 × 平均 10 块 × 768 维 × float32 ≈ 50 万向量、原始向量约 1.4GB——再乘 HNSW 索引开销 2~3 倍估内存；可用标量量化（int8）再省 3/4，精度损失通常可接受。百万级以内 PGVector 够用，亿级或高 QPS 再上 Milvus 集群（选型细节留到向量库专题）；
  • 延迟预算：端到端 P99 预算 3~5 秒的话——检索 50ms、重排 100~300ms、LLM 生成 1~3s，大头永远在生成；先卡 LLM 的流式首 token，再优化检索；
  • 索引生命周期：知识库版本化（蓝绿索引），重建走新索引、原子切别名，回滚 = 切回旧索引；文档变更走增量同步（源系统事件驱动），别攒全量；
  • 降级路径：向量库故障时降级为"仅 BM25 + 免责声明"，检索整体故障时直接 LLM 作答但明确提示"未查阅知识库"——检索链路也是依赖，要有兜底，别让问答机器人整体宕机。

04实战：Spring AI 搭一条最小可用链路

离线入库（Ingestion）

var doc = new TikaDocumentReader(resource).read().get(0);   // 解析 PDF/Word
var chunks = new TokenTextSplitter(          // 递归切块
        new TokenTextSplitterConfig()          // 默认约 800 token
            .withKeepFormulas(true), 20, 200, 10).apply(doc);
chunks.forEach(c -> c.getMetadata().put("version", "2026-09")); // 块级元数据：版本/生效期
vectorStore.add(chunks);                                   // Embedding + 写入向量库

在线问答（混合检索 + RAG 顾问）

// 1. 混合检索：向量 Top20 ∪ 全文检索 Top20，RRF 融合
var req = SearchRequest.query(question)
        .withTopK(20).withSimilarityThreshold(0.5)
        .withFilterExpression("version == '2026-09'");      // 元数据过滤挡旧版本
var docs = vectorStore.similaritySearch(req);               // 与 BM25 结果做 RRF 合并

// 2. RAG 顾问：拼提示词（"仅依据以下资料回答，未命中就明说"）→ LLM
ChatClient.create(chatModel).prompt()
        .advisors(new QuestionAnswerAdvisor(vectorStore, req))
        .user(question).call().content();

05今日要点

  • RAG = 开卷考试：离线管线切块建索引生产"书页"，在线管线混合检索+重排完成"翻书"；可换书（分钟级更新）、可溯源（带引用），是企业知识场景的默认架构。
  • 切块决定上限：递归分块 300~800 token、重叠 10%~20% 是起点；结构化文档上父子分块（小块检索、大块供上下文）解决"块大小两难"；元数据随块入库是版本治理的前提。
  • 混检+重排是生产标配：向量懂语义、BM25 认精确符号，RRF 免调权融合，Cross-Encoder 只精排 Top50——对纯向量方案普遍提升 15%~25%。
  • 四把尺子分开量：召回/精确/nDCG 量检索，忠实度量生成；答案不好先判断坏在哪一段，评测集是 RAG 的"单元测试"。
  • 选型口诀：知识用 RAG、行为用微调、可叠加；容量先算向量账（数量×维度×字节×索引系数），高可用靠索引版本化与检索降级路径。

06架构师思考题

题目一：你们的知识库问答上线后收到两类投诉：A 类"问 XR-7500 的参数，答案混进了 7500S"；B 类"问总体原则这类概念题，答案东拉西扯"。① 两类故障分别对应哪把质量标尺坏了？② 各自怎么修？③ 为什么"统一调大 Top-K"对两类都是反作用？▶ 点击展开解析

🔍 逐问拆解

① A 类是精确率问题，B 类表象是"答案质量差"，根子常在召回+排序两处。A 类：相关块（XR-7500 专属页）其实检索到了，但不相关的相似型号块也混进上下文，模型无法区分——精确率坏了。B 类：概念题的查询向量本身模糊，召回的块良莠不齐且最相关的没排到前面——召回质量与 nDCG 都可疑。判断手段：抽查问答日志里"实际检索回的块"，人工标注相关性，分别统计两类问题的召回率/精确率——没有这个日志，一切优化都是盲调。

② A 类修法（治精确）：补 BM25 路（型号是精确符号，倒排索引天生治这个）；块元数据加"型号"字段做检索前过滤（filter product == "XR-7500"）；重排器管最后一公里。B 类修法（治召回与排序）：查询改写环节把口语问题扩写成带同义词的规范查询；概念题改走"父子分块"（子块命中、父块给完整论述）；确认 Top-K 与相似度阈值没有把次相关块放进来。

③ 调大 Top-K 是"喂更多上下文碰运气"：对 A 类，更多相似型号块涌进来，精确率进一步恶化，模型更分不清；对 B 类，噪声块稀释注意力，东拉西扯更严重。Top-K 调大只在"召回不足且排序足够好"时有效——这正说明先量指标定位环节，再动参数：指标不清时动任何旋钮都可能在对症的反方向用力。

题目二：知识库要扩到 20 万份文档（约 200 万块、768 维向量），且制度文档每季度集中修订一次。① 估算向量存储与内存量级，PGVector 还扛得住吗？② 季度修订 5 万份文档，全量重建还是增量更新？给出你的索引更新方案。③ 重建期间线上问答怎么不受影响？▶ 点击展开解析

🔍 逐问拆解

① 算账：200 万向量 × 768 维 × 4 字节（float32）≈ 5.5GB 原始向量；HNSW 索引开销按 2~3 倍估 → 内存 11~17GB；若用 int8 标量量化可压到 1/4（精度损失一般在 1~3 个点，需评测验证）。PGVector 用 HNSW 时索引必须放内存，200 万向量单实例已接近舒适区上限（还要给 PG 的共享缓冲、连接池留量），可以扛但很挤：低 QPS 内部场景可继续（分区+量化+读副本），高并发或持续增长就该迁 Milvus 集群——迁移别急着做，先量化 QPS 与增长曲线再决策。

② 增量为主，全量为兜：修订是文档级的，5 万份修订 ≠ 200 万块重算——按"文档 ID 删旧块、插新块"增量更新，重索引量直接降一个数量级。前提是入库时块带文档 ID 与内容哈希：内容没变的块哈希相同，直接跳过。每半年或索引碎片化明显时做一次全量重建（顺带切换 Embedding 模型版本——模型不能混用，新旧向量不在同一空间）。

③ 蓝绿索引 + 原子切别名：新版本写进 index_v3，构建完成后把服务查询的别名从 v2 原子切换到 v3——切换是一瞬间，问答请求无感知；出问题切回 v2 即回滚。增量更新期间新旧块共存于同一索引（靠版本元数据过滤），只要检索默认带 version 过滤，就不会出现"新旧制度混答"。另有脏数据兜底：修订期间给"生效日期"打标，答案引用时展示"依据 2026-Q3 版制度"，让用户看得见知识版本。
