SPRING CLOUD ALIBABA · SCA 系列第 5 讲（RPC 治理篇 · Dubbo）

Dubbo RPC 治理：从线程池防线到 Triple 协议现代化

上一讲在 TDengine 把数据分发讲完，今天按排程开启 Spring Cloud Alibaba 的 Dubbo RPC 治理。第 31 期聊过调用方怎么"调得稳"，这期换到桌子另一边——Provider（服务提供方）怎么"扛得住"：一个默认 200 线程的线程池，怎么成了整个服务的可用性天花板；Dubbo 3 的应用级服务发现和 Triple 协议，又把这套老底子中间件现代化到了什么程度。

01一次 Thread pool EXHAUSTED：慢接口吃光公共线程池

某会员服务（Dubbo Provider，3 实例）挂了 6 个下游消费方。大促前压测第 4 天，营销侧新上线一个"批量查会员"接口：一次请求带 2000 个会员号，单次要 800 毫秒。上线 10 分钟后监控报警，日志刷屏 Thread pool is EXHAUSTED——连一直健康的单笔查询接口也全线报错，故障 45 分钟。

复盘算三笔账。第一笔，线程池的天花板：Dubbo Provider 默认 fixed 线程池 200 个线程、queues=0（SynchronousQueue，不排队）——池满后新请求立即拒绝。批量接口单次 800ms，意味着每线程每秒只能处理 1.25 个请求，200 个线程的理论上限就是 250 QPS；而单笔查询只要 10ms，同样 200 线程理论上能扛 2 万 QPS。两类流量混在同一个池里，整体吞吐被最慢的那类拖到 250——一个慢接口，把快接口的地盘也占了。第二笔，queue=0 是设计者的选择：快速失败优于排队雪崩（对比 第 31 期Tomcat 线程池挂满的墨汁晕染），这次 JVM 没死、恢复很快，但"拒绝"本身就是给客户端的可用性事故。第三笔，监控缺位：线程池 activeCount 长期 190+ 无人看，慢接口是压死骆驼的最后一根草，不是第一根。

根因从来不是"线程池太小"，而是没有隔离、没有限流、没有按容量规划线程预算。这期把 Provider 侧的防线一次讲完，再往深看一层：Dubbo 3 的两个架构级现代化——应用级服务发现与 Triple 协议——值不值得你启动存量升级。

02原理：一次调用在 Provider 身上走过的四道门

线程池：三道可调的闸

① 池本身：dubbo.protocol.threads（默认 200）、queues（默认 0）、threadpool（fixed/cached/eager/bounded）。经验：CPU 密集型 200 够用，IO 密集型按容量账推导（见 03 节），不建议用无界队列换吞吐——排队只是把拒绝变成延迟，代价更隐蔽。② 服务级限流：@DubboService(executes = N) 限制单个方法在 Provider 侧的最大并发，超了直接拒绝——这是 01 节事故的正解：批量接口 executes=50，就算它慢出天际也只占 50 个线程。③ 消费端背压：@DubboReference(actives = N) 限制调用方每个方法的并发上限——调用方自己先限流，比 Provider 被迫拒绝优雅得多。线程耗尽时 AbortPolicyWithReport 会拒绝并打印完整池状态，还自动 dump jstack（默认开启、10 分钟节流）——拿到 dump 文件第一件事看 200 个线程都卡在哪，答案通常不是"线程不够"。

应用级服务发现：为什么它值得你升级

Dubbo 2.x 接口级注册：一个应用 50 个接口 × 100 实例 = 注册中心 5000 条 URL，每个消费者还要按接口全量订阅、常驻内存随接口数线性膨胀。工商银行的规模（接口级地址数亿条）直接把注册中心存储与推送效率推到极限，消费端 Dubbo 框架常驻内存占比超 40%。Dubbo 3 应用级发现把粒度收敛到应用：注册中心只存"应用 → 实例列表"一份，接口到应用的映射放元数据。官方与工行联合压测：节点间数据传输量降 90%，消费端常驻内存——仅升 3.0 就降近 40%，切到应用级后降到原来的 30%，地址推送期 GC 几乎归零。迁移设计也很克制：升级即自动双注册/双订阅（默认 APPLICATION_FIRST，应用级订阅不到自动回落接口级），存量升级不用停机，全部消费方迁完再把开关切到 FORCE_APPLICATION 收掉接口级订阅的内存。

Triple 是什么

一句话：Dubbo 的 RPC 协议从私有 TCP 换到了 HTTP/2 标准轨道。收益三条——与 gRPC 协议互通（Protobuf IDL 定义服务，跨语言直接调）；Nginx/Envoy/APISIX 等标准网关可直接代理（老 dubbo 协议需要专门的协议转换插件）；原生支持流式调用。3.3 的 Triple X 进一步兼容 HTTP/1、HTTP/3，REST 风格访问无需网关转协议。存量 POJO 服务可以用 Wrapper 模式先切协议不动代码（序列化仍走 hessian2/fastjson2），新服务直接上 IDL 模式拿满跨语言与安全红利。

03架构设计：线程预算、协议选型与序列化红线

容量三笔账

线程账：需求并发 = 峰值 QPS × P99（秒）。6000 QPS × 50ms = 300 并发，单实例 200 线程 × 3 实例 = 600，余量 2 倍，健康；但混入 10% 的 800ms 批量请求后加权并发需求暴涨，慢接口永远应该单独隔离而不是共享大池。放大账：默认 retries=2（failover 集群容错，失败重试 2 次共 3 连发）——下游过载时重试是兴奋剂（第 31 期同款教训），非幂等写操作必须显式 retries=0。序列化账：大报文（批量接口的 2000 个会员号）序列化开销与网络放大都吃 IO 线程，报文预算要进接口契约评审。

序列化即攻击面

Dubbo 的反序列化是历史漏洞重灾区（CVE-2023-23638 等 RCE 都打在这里）。官方在 3.x 做了三次收口：3.2 默认序列化从 hessian2 切到 fastjson2（性能更好、原生支持 JDK17+），同时 serialize-check-status 默认升到 STRICT 白名单强校验（不在信任清单的类直接拒绝反序列化）；3.3 把默认支持的序列化收窄到 Hessian2 / Fastjson2 / Protobuf（移除了 JDK 序列化等高风险项）；而 Triple + Protobuf IDL 模式因为报文结构完全由 IDL 约束，天然免疫任意类反序列化——官方安全文档的原话是"该协议默认安全"。存量升级 3.2+ 的推荐姿势：先 -Ddubbo.application.serialize-check-status=WARN 观察日志无告警，再收紧 STRICT——直接强切可能把泛化调用的合法类拦在外面。

版本坐标（2026-10）

Java 线最新特性版 3.3.6（2025-11 发布，含 JDK 21/Loom 支持、Affinity 路由、HTTP/2 连接预取强化），3.2.19 为稳定维护线；JDK 8~21 全覆盖（3.2 线到 17）。2.7.x 已 EOL 多年——还在 2.7 的存量，升级不是选择题。SCA 集成注意版本配平：Spring Boot 3.x + SCA 2023.0.1.0+ + Dubbo 3.3.x 是新一代组合，JDK 8 存量用 Boot 2.7 + Dubbo 3.2.x 线先升级后换代。

04实战：三段落地

片段一：慢接口隔离——独立线程池 + executes 限流

# application.yml：全局池按容量账调大，同时给批量接口独立预算
dubbo:
  protocol:
    name: tri                      # Triple 协议，新服务默认
    port: 50052
    threads: 300                   # 容量账：6000QPS×50ms÷3实例≈100，×3 冗余
    queues: 0                      # 保持快速失败，不排队

@DubboService(executes = 50, timeout = 3000)   # 方法级并发上限 50
public class MemberBatchServiceImpl implements MemberBatchService {
    // 2000 个会员号的批量查询，慢且量小——隔离在这个预算里
    // ...
}

片段二：Triple + IDL 最小落地（跨语言与 curl 直调）

syntax = "proto3";
service MemberService {
  rpc getMember(GetMemberReq) returns (MemberResp);
}
// 生成代码后，Provider 侧与普通 Dubbo 服务无异
@DubboService
public class MemberServiceImpl implements MemberService { /* ... */ }

# 消费端不写 Java 客户端也能直调——HTTP/2 标准轨道：
curl --http2-prior-knowledge -d '{"memberId":"M1001"}' \
     -H "Content-Type: application/json" \
     http://member-svc:50052/org.demo.MemberService/getMember

片段三：序列化加固与线程池观测

# ① 序列化协商：优先 fastjson2，旧版本消费方回落 hessian2
dubbo.provider.prefer-serialization: fastjson2,hessian2
# ② 升级观察期：先 WARN 看日志，确认无告警再收紧 STRICT
# -Ddubbo.application.serialize-check-status=WARN
# ③ 线程池观测：QoS 端口看池状态（或接 Micrometer 进 Grafana）
telnet 127.0.0.1 22222   # ls / status 命令；EXHAUSTED 时自动 dump 的
                          # jstack 文件在 user.home，直接看 200 线程卡在哪

五个必踩的坑：① queue 改大换取"不拒绝"——排队把故障从客户端可见的报错变成更隐蔽的延迟雪崩，拒绝是减压阀不是故障本身。② retries 用默认值跑写操作——默认 failover 重试 2 次，超时后同一笔扣减最多打 3 次，与 31 期传输层重试是同一条纪律。③ 3.2 升级直接开 STRICT——泛化调用、跨团队 POJO 可能被白名单拦截，官方升级指南明确建议先 WARN 观察。④ 双注册跑一年不切 FORCE_APPLICATION——接口级订阅的内存一分没省，迁移只做了一半。⑤ 线程池只看 reject 报警——等 EXHAUSTED 再看就晚了，activeCount 长期 >85% 就该启动容量评审。

✅ Dubbo Provider 体检清单

☐ 线程池容量按"峰值 QPS × P99"推导过并留 2 倍余量　☐ 慢接口（P99 > 200ms）已用 executes/独立 executor 隔离　☐ 高风险调用方配了 actives 背压　☐ 所有写操作显式 retries=0　☐ timeout 按下游 P99~P99.9 分层配置（全局 1s 只是兜底）　☐ activeCount/池拒绝数进监控（>85% 告警）　☐ EXHAUSTED 自动 dump 的 jstack 有归档与复盘机制　☐ 序列化：prefer-serialization 显式声明 + STRICT 白名单落地　☐ 跨网络边界/对外暴露的接口走 Triple IDL 或网关层鉴权　☐ 存量 3.x 双注册迁移有截止日期，迁完切 FORCE_APPLICATION

05今日要点

  • queue=0 是刻意设计：fixed 200 线程 + 不排队 = 快速失败优于排队雪崩；但快速失败只是保住 JVM，可用性要靠隔离（executes）与背压（actives）挣回来。
  • 线程池是被慢接口打爆的，不是被流量打爆的：800ms 批量接口把 200 线程的理论吞吐钉在 250 QPS——隔离永远优先于扩池。
  • 应用级服务发现是 Dubbo 3 最大的架构红利：注册中心传输量 -90%、消费端内存 -50%+（工行实测）；升级即双注册，迁完切 FORCE_APPLICATION 才算收割完成。
  • Triple 把 RPC 搬上标准轨道：HTTP/2 + gRPC 互通 + 标准网关可代理；新服务默认 Triple，存量 Wrapper 模式免 IDL 平滑过渡。
  • 序列化即攻击面：3.2 默认 fastjson2 + STRICT 白名单、3.3 收窄默认序列化集；Triple IDL 模式天然免疫反序列化 RCE——高安全场景的不二选。

06架构师思考题

题目一：会员服务 3 实例（threads=300/实例），大促目标 6000 QPS，单笔查询 P99=50ms；营销批量接口 P99=800ms，占比 10%（600 QPS）。① 算一算：现状线程预算扛得住吗？瓶颈先出现在哪里？② 设计隔离方案：executes、actives、独立线程池怎么组合？③ 有人提议把 queues 改成 10000"先不报错"，给出你的裁决。▶ 点击展开解析

🔍 逐问拆解

① 两笔账分开算。单笔查询：6000×90%=5400 QPS × 0.05s = 270 并发需求；批量：600 QPS × 0.8s = 480 并发需求——合计 750，而供给是 3×300=900，理论上"总账"够（余量仅 1.2 倍，已经不健康）。真正的雷在分布：如果两类流量共享线程池，抢占是随机的——批量请求到达得早一点，480 个线程位置被占满，单笔查询的 270 并发需求里有相当部分落在"池满拒绝"上，可用性事故不是发生在总需求超供给时，而是发生在共享池被慢流量稀释时。大促一旦超预期 20%，直接击穿。

② 三层组合拳，各管一段。Provider 侧 executes：批量接口按"目标延迟内能处理的量"给预算——600 QPS×0.8s=480 并发是它的"应得"，但业务上批量是低优先级，压到 executes=300（每实例 100）足够；单笔查询可给独立线程池（@DubboService(executor=...) 指向专属 Executor）或至少不设限。消费端 actives：营销应用对批量接口的并发上限压到 300，把背压前移到调用方——调用方限流失败可以本地降级（返回缓存、异步补齐），比 Provider 拒绝后干等好。容量余量恢复到 2 倍以上。这套与 第 1 期Sentinel 的 Warm Up + 隔离是互补关系：Sentinel 管入口总量，Dubbo 原生参数管方法级预算，别用两套工具做同一件事。

③ 否决，理由三段。其一，排队不消灭故障只改造故障：600 QPS 的批量需求不会因为排队变成 300，延迟从"立即报错"变成"排队 3 秒后超时报错"，错误率统计还更好看了——监控反而被污染。其二，内存账：10000 深度队列 × 每任务附带请求上下文，瞬时内存膨胀可达 GB 级，把"拒绝问题"升级成"OOM 问题"。其三，正确方向是把预算花在隔离与背压上（第②问），而不是给共享池加缓冲。唯一例外场景：短时毛刺（秒级突发）可用 eager 线程池（先扩线程再入队）平滑，但那是"扩"不是"排"。

题目二：你在治理一套 2.7 存量（40 个应用、注册中心 ZooKeeper、消费端框架内存占比 35%），立项升级 Dubbo 3.3。① 给出升级路径的关键四步与每步的验收标准。② dubbo 协议要不要同步切 Triple？给出灰度策略。③ 切完序列化 STRICT 第一天，三个跨团队泛化调用接口报 ClassNotFound 类校验异常，怎么处置？▶ 点击展开解析

🔍 逐问拆解

① 四步走，每步带验收。第一步，依赖升级 2.7→3.3（com.alibaba 坐标换 org.apache.dubbo，注解 @Service→@DubboService）：验收是单应用回归通过——3.x 对 2.x 协议层完全兼容，可灰度任意数量应用。第二步，双注册双订阅（升级后默认 register-mode=all / APPLICATION_FIRST）：验收在注册中心与元数据中心看到应用级数据完整、消费端调用零异常，同时用 链路追踪抽样核对流量正常。第三步，逐应用切 FORCE_APPLICATION：验收是消费端框架常驻内存显著回落（工行数据是从 40% 级降到 15% 级量变），ZooKeeper 上接口级地址条目开始减少。第四步，收口 register-mode=instance（只注册应用级）：验收是注册中心存储与推送量下降 90% 量级，2.7 存量全部清零后下线接口级兼容逻辑。全程不停机——双注册双订阅的迁移模型就是为这个设计的。

② 协议切换单独立项，与版本升级解耦。版本升级是刚需（2.7 EOL），协议切换是优化项，混在一起出问题无法定位。灰度策略：Provider 双协议发布（dubbo.protocol.protocols 配 tri + dubbo 两个协议，同服务双端口暴露），消费端逐应用配 dubbo.consumer.protocol=tri 切换；存量 POJO 用 Triple Wrapper 模式（序列化走 hessian2/fastjson2，不写 IDL、不改代码），验证稳定后再对高价值接口引入 IDL 模式（跨语言需求、对外暴露的接口优先）。网关侧同步验证：Triple 走标准 HTTP/2 代理后，可以顺势把 第 32 期的入口治理策略延伸到 RPC 层。切换验收：两侧协议的 P99 对比、序列化兼容性回归、gRPC 跨语言冒烟。

③ 这是 STRICT 白名单的预期行为，不是升级事故。根因：泛化调用不经过字节码扫描，类信任清单（AutoTrustSerializeClass 递归信任服务接口相关的包）对跨团队 POJO 覆盖不全，STRICT 把"清单外"全部拒绝。处置三步：临时降级 -Ddubbo.application.serialize-check-status=WARN 恢复业务（WARN 只黑名单拦截、清单外记日志）；按日志提示把三个接口的 POJO 包补进信任清单（dubbo.application.trust-serialize-package 或调 TrustSerializeClassLevel 放宽到公共包层级）；观察一周无新增告警再收回 STRICT。要避免的两个极端：一是被报警吓住把全局永久停在 WARN（等于放弃 RCE 防线，等于白升级）；二是为了"彻底"给全包 * 白名单（等于没有白名单）。长期正解是推动跨团队接口走 IDL 模式——结构由契约约束，跳出"用类清单防类攻击"的猫鼠游戏，这也是官方安全文档的推荐方向。
