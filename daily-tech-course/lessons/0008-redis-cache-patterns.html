Redis 缓存设计模式：穿透 / 击穿 / 雪崩的系统化治理

📅 2026-08-20（周四） ⚡ Redis 系列 · 第 4 讲 ⏱ 预计阅读 10 分钟 🎯 布隆过滤器 / 互斥重建 / 逻辑过期 / 多级缓存

一、一次凌晨两点的事故复盘

某电商平台的商品详情页缓存采用"Cache-Aside"模式：读缓存 → miss 则查 DB → 回写缓存，TTL 统一 30 分钟。凌晨两点运营批量导入 10 万个新商品，同时爬虫用不存在的商品 ID 高频探测接口。三分钟后 MySQL CPU 100%，整站商品接口超时。复盘发现三个问题叠加爆发：

  1. 穿透：爬虫查询不存在的 ID，缓存永远 miss，请求全部砸向 DB；
  2. 击穿：10 万商品同时导入，TTL 起点相同，30 分钟后集中过期，热点 key 过期瞬间并发重建把 DB 打挂；
  3. 雪崩效应：DB 慢 → 请求线程堆积 → 应用线程池耗尽 → 故障从商品服务扩散到订单、支付。

这三个问题形态相似、根因不同、解法各异，混为一谈会导致治理无效。今天从架构师视角系统化拆解。

二、三兄弟的本质区别：先诊断，再开药

维度穿透（Penetration）击穿（Breakdown）雪崩（Avalanche）
触发条件查询不存在的数据热点 key 过期瞬间大量 key 同时过期 / Redis 宕机

核心解法布隆过滤器 + 空值缓存互斥重建 / 逻辑过期随机 TTL + 多级缓存 + 熔断降级

击穿

▲ 记忆口诀：穿透查"无"、击穿点"热"、雪崩塌"片"

穿透治理：把"不存在的请求"挡在缓存之外

  • 布隆过滤器：启动时将全量合法 ID 灌入（约 1GB / 1亿 key，误判率 1%）。请求先过过滤器：说"不存在"就一定不存在，直接拒绝；说"存在"才继续查缓存。代价是新增数据需异步补录，删除有滞后；
  • 空值缓存：查 DB 确认不存在后，写入 key → null 并设短 TTL（30s~5min），兜住过滤器误判与漏录窗口；
  • 入口校验：ID 格式、范围、权限在网关层拦截，能挡掉 80% 的恶意探测。

击穿治理：热点 key 重建只放一个请求进去

  • 互斥锁重建：缓存 miss 时先抢分布式锁，抢到的线程查 DB 回写，其余线程短暂自旋重读缓存（不是直接打 DB）。吞吐略降，但 DB 压力恒定；
  • 逻辑过期：物理 TTL 永不失效，value 内嵌过期时间字段。读到"逻辑过期"数据时返回旧值 + 异步线程抢锁重建——绝不阻塞读请求，适合秒杀类热点，代价是短暂的数据陈旧窗口。

雪崩治理：把失效时间与故障域打散

  • TTL 加随机抖动：TTL = base + random(0, 600s)，从根上消灭"同时过期"；
  • 多级缓存：本地 Caffeine（秒级）→ Redis（分钟级）→ DB，Redis 整体不可用时本地缓存兜住核心读；
  • 熔断降级：缓存层故障时对 DB 回源限流（如 Sentinel 按 DB 水位的 60% 限流），返回默认页/兜底数据，保住 DB 就是保住全局。

三、实战代码：三套可落地的治理方案

方案一：布隆过滤器防穿透（Redisson）

// 启动时初始化：预计 1 亿商品，误判率 1%
RBloomFilter<Long> filter = redisson.getBloomFilter("product:bloom");
filter.tryInit(100_000_000L, 0.01);  // 约 120MB 内存

public Product getProduct(Long id) {
    if (!filter.contains(id)) {
        return null;                    // 一定不存在，直接拒绝
    }
    // ... 正常 Cache-Aside 流程，miss 时回写缓存
}

方案二：互斥锁重建防击穿

public Product getWithMutex(Long id) throws Exception {
    String key = "product:" + id;
    String val = redis.get(key);
    if (val == null) {
        String lockKey = "lock:rebuild:" + key;
        RLock lock = redisson.getLock(lockKey);
        // 等 3s 获取锁；持有 30s 自动释放，防死锁
        if (lock.tryLock(3, 30, TimeUnit.SECONDS)) {
            try {
                val = redis.get(key);          // ★ 双重检查：可能已被重建
                if (val == null) {
                    val = loadFromDb(id);
                    redis.setex(key, 1800 + randomTtl(), val);
                }
            } finally { lock.unlock(); }
        } else {
            Thread.sleep(50);              // 未抢到锁：自旋重读，而非打 DB
            return getWithMutex(id);
        }
    }
    return parse(val);
}

方案三：逻辑过期防击穿（不阻塞读）

// value 结构：{"data":{...},"expire":1755648000000}，物理 TTL 不设置
public Product getWithLogicalExpire(Long id) {
    CacheWrapper w = parse(redis.get("product:" + id));
    if (w != null && !w.isExpired()) return w.data;   // 新鲜：直接返回

    // 已逻辑过期：抢到锁才异步重建，抢不到/已有人重建 → 返回旧值
    if (redisson.getLock("lock:rebuild:" + id).tryLock()) {
        executor.submit(() -> {
            try { rebuildFromDb(id); }
            finally { unlock(); }
        });
    }
    return w == null ? null : w.data;   // 旧值兜底，读永不阻塞
}
⚠️ 生产坑点清单
  • 双重检查不能省：拿到锁后必须再查一次缓存，否则锁排队线程会重复重建，锁形同虚设；
  • tryLock 必须带 waitTime 上限：自旋递归要有最大次数（如 20 次），否则 Redis 抖动时线程栈打爆；
  • 布隆过滤器不能删元素：商品下架后过滤器仍放行 → 必须与空值缓存配合使用；
  • 逻辑过期有陈旧窗口：库存、价格类强一致数据禁用此方案，只用于展示型热点数据。

四、整体防御架构：四层漏斗模型

单一方案都有失效场景，生产环境应按"逐层过滤、越往后流量越小"的漏斗思路组合部署：

L1 入口校验
网关层 ID 格式/频控/签名 → 挡恶意流量
L2 布隆过滤器
不存在的 key 直接拒绝（穿透）
▼
L3 本地缓存
Caffeine 秒级 TTL，兜住热点与 Redis 抖动（击穿/雪崩）
L4 Redis + 随机 TTL
互斥重建 + 逻辑过期（击穿）+ 多级兜底（雪崩）
▼
L5 DB 回源（限流）
Sentinel 按 DB 水位 60% 限流，超限走降级页 —— 最后的底线
▲ 每层只放行"下一层能承受"的流量，DB 永远不是第一承受者
💡 容量规划参考 估算回源峰值 QPS = 热点 key 数 ÷ 重建周期 × 并发系数。例：1 万热点商品、TTL 30min（含抖动均值）→ 稳态回源 ≈ 1万/1800s ≈ 6 QPS，但冷启动或缓存整体失效时瞬时可达数千 QPS——按瞬时值规划 DB 水位与限流阈值，而不是稳态均值，这是雪崩预案最常犯的估算错误。

五、今日要点

1
先诊断再开药
穿透查"无"、击穿点"热"、雪崩塌"片"——三者也常叠加爆发，治理方案要组合部署而非单选。
2
穿透三板斧
入口校验 + 布隆过滤器（说无则无）+ 空值缓存（兜误判）。布隆不能删元素，必须与空值缓存配合。
3
击穿双方案
互斥锁重建（一致性好、读有阻塞）vs 逻辑过期（读不阻塞、有陈旧窗口），按数据一致性要求选型。
4
雪崩靠打散+兜底
TTL 随机抖动消灭集中过期；多级缓存与回源限流保住 DB——保住 DB 就保住全局。
5
按瞬时值规划
回源容量按冷启动/整体失效的瞬时峰值规划限流阈值，稳态均值会严重低估风险。

六、架构师思考题

Q1你的系统用布隆过滤器防穿透，运行三个月后突然出现 DB 回源激增。排查发现过滤器误判率从 1% 涨到了 8%。可能是什么原因？作为架构师，如何在设计阶段就规避这个问题？▶

解题方向

考察对布隆过滤器"只能增、不能删"特性的工程化理解。误判率不是静态的，它会随着数据规模和过滤器状态的演变而恶化。

参考思路

  • 原因一：预估容量远小于实际数据量。布隆过滤器的误判率公式约为 (1 - e^(-kn/m))^k（k 哈希次数、n 实际元素数、m 位数组大小）。当初按 1 亿 key、1% 误判率分配的位数组，若实际灌入 1.5 亿 key，位数组置位比例（load factor）超出设计值，误判率会指数级上升——这是最常见的根因，业务增长超预期。
  • 原因二：没有考虑"删除"需求。大量商品下架后，过滤器仍认为 key 存在，为了"纠错"有人会重建过滤器，若重建期间并发写入使用不同实例或错过的增量未补录，状态错乱后误判与漏判同时出现（漏判更危险：存在的 key 被拒，业务直接报错）。
  • 设计阶段规避：① 容量预估打 2~3 倍冗余，把"三年后的数据量"作为 n 代入公式；② 选用 Counting Bloom Filter 或 Redisson 的 RCountingBloomFilter 思路（代价是 4~8 倍内存），支持删除操作；③ 有条件时升级为 Cuckoo Filter，天然支持删除且空间效率更高；④ 监控过滤器置位率，超过 70% 告警并触发"滚动重建"：新过滤器建好后原子切换（双 buffer），期间双写保证增量不丢。
  • 兜底防线：永远保留空值缓存作为第二道防线——即使过滤器误判率恶化到 8%，穿透到 DB 的请求仍会被空值缓存挡住大部分。这体现了核心架构思想：任何单点方案都会退化，纵深防御才可靠。
Q2秒杀场景下，爆款商品详情是典型热点 key，业务要求"读延迟 P99 < 50ms、数据可容忍 5 秒陈旧、DB 绝不能被打挂"。你会如何组合今天的三套方案设计缓存架构？说明每一层的取舍理由。▶

解题方向

没有标准答案，考察的是把"一致性要求、延迟要求、可用性要求"翻译成技术选型的能力。关键洞察：5 秒陈旧容忍度非常高，这直接指向逻辑过期方案。

参考思路

  • 第一层：本地缓存 Caffeine，TTL 3~5 秒。秒杀读 QPS 可达数十万，即使 Redis 集群也会因单分片热点产生尾延迟。本地缓存把 95% 以上的读挡在应用进程内，P99 天然达标。3~5 秒 TTL 与业务容忍度对齐，且秒杀商品数极少（<100 个），内存占用可忽略。
  • 第二层：Redis + 逻辑过期，重建周期 5 秒。不用互斥锁重建——秒杀场景读阻塞 3 秒等于事故，而 5 秒陈旧窗口恰好覆盖逻辑过期的代价。value 内嵌过期时间，过期后返回旧值 + 异步重建，读路径上没有任何同步等待。爆款 key 物理永不过期，从根上消灭击穿。
  • 第三层：重建任务用"合并回源"（singleflight 思想）。同一商品 5 秒窗口内只允许一个重建任务打到 DB（Redisson 锁或 JVM 内 CompletableFuture 去重），DB 对每个热点商品的回源频率被锁定为 ≤1 次/5 秒，无论线上 QPS 多高——这就是"按瞬时值规划"的极致形式：回源 QPS 有数学上界。
  • 第四层：Sentinel 回源限流兜底。若出现未预料的新热点（突然爆红的商品）没有本地缓存和逻辑过期保护，回源限流按 DB 容量的 60% 设阈值，超限返回静态降级页（"商品信息加载中"），保 DB 不挂。宁可少数用户看到降级页，不能全站雪崩。
  • 加分项：① 指出秒杀热点 key 在 Cluster 下的倾斜问题——爆款商品 hash tag 会集中到单分片，可配合本地缓存消化（这正是第一层存在的另一个理由）；② 提到"预热"：秒杀开始前 10 分钟主动加载热点数据到本地缓存与 Redis，避免开场冷启动回源风暴。
