TDENGINE · TDengine 系列第 2 讲（性能篇）

写得进、查得快：时序数据写入与查询性能优化

时序库的快是"追加写 + 列式压缩"给的，慢多半是姿势不对：单条 insert、NOW() 互相覆盖、CACHEMODEL 用默认值、报表现场扫明细。今天把写入路径与读路径两头讲透——批量与相邻性、乱序的代价、标签过滤下推、SMA 与流计算降采样，最后给一套能直接抄的建库参数与改造清单。

01一个"资源不缺、姿势不对"的性能复盘

智能电表平台 8 万块表上线半年，两件事同时爆出来：写入侧，晚间批量上报时段写入 TPS 只有 3000（目标是 5 万），vnode 写队列堆积，写延迟 p99 飙到秒级；查询侧，运营大屏翻一页"每块表最新读数"要 3~5 秒，月度报表直接超时。DBA 看监控更困惑：CPU 30%、磁盘 IO 40%——资源明明不缺。

复盘出的三个根因，每一个都和 TDengine 的设计假设背道而驰：

  • 写入端：开发图省事，逐条 insert + 自动建表 + 用 NOW() 取时间戳——单条往返把网络 RTT 打成了主成本；更糟的是同一条 SQL 里多个 NOW() 会被解析成同一个时间戳，批量数据自己覆盖自己，成功条数永远小于发送条数；
  • 查询端：CACHEMODEL 用默认值 none，大屏每个"最新值"都在打磁盘随机读；月报表对 3 个月原始数据现场聚合，亿级行参与运算；
  • 架构侧：没有降采样层——大屏、报表、告警三类负载全压在明细数据上。

结论一句话：时序数据库为"批量、有序、追加"的写入模式和"最近值 + 预聚合"的查询模式而生，偏离这个假设，它的性能优势就兑现不了。建模基础（超级表/子表/标签）见0015 期，今天专讲性能。

02原理：写入路径与读路径各发生了什么

重复时间戳：不是报错，是覆盖

TDengine 3.0 彻底移除了 2.0 的 update 参数：子表内时间戳是主键，写入相同时间戳的数据不会报错，而是按版本号处理——后写入的胜出（NORMAL/NULL 取高版本，未赋值列取低版本，天然实现部分列更新）。这带来了两个高频坑：一是同一条 INSERT 里多个 NOW() 解析为同一时间戳，批量互相覆盖；二是采集端用"服务器当前时间"而非"设备采样时间"做时间戳，重传/补发时旧数据被新到达时间"顶掉"。正确姿势：时间戳永远用设备侧时间，批量内保证升序。

读路径：查询慢在哪

标签过滤下推是超级表查询的第一道闸门：带标签条件的查询会先在元数据层筛出目标子表集合，再只碰这些子表的数据块；没有标签条件就是全子表广播。所以"查询慢先看 WHERE 有没有标签条件"应该写进团队的 SQL 规范。CACHEMODEL 决定"最新值"查不查磁盘；SMA（建表时对聚合列声明）把 min/max/sum 等块级统计预计算好；流计算则把降采样表在写入侧持续物化——这是 3.0 对 2.x 连续查询的重写，乱序数据也能触发结果修正。

03架构设计：容量规划与选型

写入方式相对效率慢在哪适用
参数绑定（stmt） 最快 —— 高吞吐采集通道
SQL + 预建表 快 SQL 解析开销 绝大多数业务写入
SQL + 自动建表 较慢 每批检查表是否存在 原型验证
无模式（schemaless） 慢 自动建表 + 动态改 schema 协议直通（InfluxDB 行协议迁移）
CACHEMODEL缓存内容加速场景
none（默认）不缓存—几乎不该用于生产
last_row每子表最近一行LAST_ROW设备当前状态大屏
last_value每列最近非 NULL 值无过滤/分组的 LAST仪表盘"最近有效值"
both两者都缓存LAST + LAST_ROW内存富余时的稳妥选择
容量规划三笔账（建库前必算） ① vgroups：官方建议 CPU 核数 × 2 起步——注意 vgroups 建库时定死、事后不可修改，只能新建库迁移，宁可在容量评估时一次定准；② 内存：≈ vgroups × (BUFFER 256MB + 元数据缓存 + CACHEMODEL 缓存)，16 核 32 vgroups 约 8~9GB；③ 磁盘：行宽 × 日增行数 ÷ 压缩比（典型 10:1），再留 30% 水位。副本默认 1，核心库 replica 3（写放大 3 倍），且 2 副本仅企业版支持。

两级查询架构是时序平台的标准形态：原始层（秒级明细，KEEP 90~180 天，服务排障与明细下钻）+ 降采样层（流计算写小时/天表，KEEP 长期，服务大屏、报表、告警）。这样三类读负载互不干扰，原始层还能激进地限寿清理。Schema 层面记得：超级表加列会级联到全部子表，亿级子表场景的 schema 变更要走低峰窗口，并在发布流程里显式审批。

04实战：建库参数、攒批写入与查询改造

建库：一次定准（vgroups 不可改）

CREATE DATABASE iot_power
  PRECISION 'ms'        -- ms 足够；us/ns 空间翻倍，别无脑上
  VGROUPS  32            -- 16 核 → 32；建库定死，事后不可改！
  BUFFER   256           -- 每 vnode 写内存池（默认 256MB）
  WAL_LEVEL 1           -- 1=写 WAL 不强制 fsync（默认）；计费级用 2
  KEEP     90            -- 原始明细留 90 天，过期自动清理
  CACHEMODEL 'both'    -- 大屏高频取最新值必开（默认 none 是坑）
  CACHESIZE 16;          -- 每 vnode 缓存上限（默认仅 1MB，通常要调大）

-- 预建子表：写入免存在性检查，也不必每批带 TAGS
CREATE TABLE d2140a01 USING meters TAGS('厂区A', 214);

SQL 批量：一条语句写多表多行

-- 单条 SQL 上限 1MB：攒到数百~上千行再发，通常差一个数量级的吞吐
INSERT INTO
  d2140a01 VALUES ('2026-09-10 09:00:00.000', 220.3, 1.10)
                   ('2026-09-10 09:00:10.000', 220.4, 1.08)
  d2140a02 VALUES ('2026-09-10 09:00:00.000', 219.8, 0.96)
                   ('2026-09-10 09:00:10.000', 219.9, 0.99);

采集端：按子表哈希分线程 + 攒批 flush

// 核心：同子表的数据永远进同一个写入线程 → 天然按时间升序，乱序为零
int idx = Math.floorMod(tableName.hashCode(), WRITER_THREADS);
queues[idx].offer(point);                       // 无锁入队，攒批交给写入线程

class Writer implements Runnable {        // 每线程独立连接，避免连接竞争
    void drain() throws SQLException {
        List<Point> buf = queue.pollBatch(1000, Duration.ofMillis(200));
        if (buf.isEmpty()) return;
        buf.stream().collect(groupingBy(Point::table)).forEach((tbl, pts) -> {
            stmt.execute(buildInsert(tbl, pts)); // 同子表拼一条多值 INSERT
        });
    }
}
// 时间戳一律用设备采样时间（升序），绝不用 NOW()——同语句同值会自覆盖
// 更高吞吐可换参数绑定（stmt 绑定），免 SQL 解析；采集源多而碎时，用队列先汇聚再攒批

降采样：流计算 + SMA

-- 流计算：秒级原始 → 小时表，窗口关闭自动触发，写入侧持续物化
CREATE STREAM s_hourly INTO meters_hourly_st AS
  SELECT _wstart, AVG(voltage) v_avg, MAX(current) i_max, COUNT(*) n
  FROM meters PARTITION BY tbname INTERVAL(1h);

-- SMA：建表时对聚合列声明，块级统计预计算，AVG/SUM 类查询跳过读原始块
CREATE STABLE meters (ts TIMESTAMP, current FLOAT, voltage FLOAT, ...)
  TAGS (location BINARY(32), gid INT) SMA(current, voltage);

查询改造：前后对比

-- 慢：无标签条件 → 8 万子表全参与；CACHEMODEL none → 打磁盘
SELECT LAST_ROW(*) FROM meters;

-- 快：标签过滤下推裁剪子表 + last_row 命中缓存
SELECT LAST_ROW(ts, current, voltage) FROM meters
 WHERE location = '厂区A' AND gid = 214;

-- 快：报表查降采样表（90 天明细 → 每子表 2160 行/小时表），再按天聚合
SELECT _wstart, AVG(v_avg) FROM meters_hourly_st
 WHERE ts >= NOW - 90d AND location = '厂区A'
 INTERVAL(1d);

✅ 性能体检清单

☐ 单条 SQL 攒批（多行多表），不逐条 insert　☐ 时间戳用设备采样时间，禁 NOW() 批量　☐ 同子表同线程，天然升序　☐ 预建子表，不用自动建表　☐ vgroups 按 CPU×2 建库前定准（不可改）　☐ CACHEMODEL 匹配"最新值"查询，CACHESIZE 别留默认 1MB　☐ 大表聚合走 SMA/降采样表　☐ 原始数据 KEEP 限寿　☐ 监控 STT 文件数、vnode 写队列水位、WAL 落盘延迟

05今日要点

  • 批量是写入的第一杠杆：时序库的快来自"追加写 + 顺序 IO + 列式压缩"，单条 insert 把优势全丢掉。单条 SQL 攒多行（上限 1MB）、同批同子表、预建表、参数绑定——四招通常拿回一个数量级。
  • 乱序不是错，但贵：乱序/补报数据落 STT 小文件、读时按"时间戳 ASC + 版本号 DESC"多路归并。按子表哈希到固定写入线程，让数据天生有序，是零成本的优化。
  • 同时间戳 = 版本覆盖：3.0 没有 update 参数，后写胜出；同一条 SQL 里多个 NOW() 解析为同一时间戳，批量写入用它等于自己覆盖自己。时间戳永远用设备侧时间。
  • 读侧三板斧：标签过滤下推裁剪子表、CACHEMODEL 缓存最新值（默认 none 是生产坑）、SMA/流计算预聚合。口诀：大屏查缓存、报表查降采样表、明细才扫原始表。
  • vgroups 建库定死：官方建议 CPU 核数 × 2 起步，内存按 vgroups × (BUFFER + 缓存) 预算，磁盘按行宽×行数÷10 压缩比估算——三笔账都在建库前算清，事后改不了。

06架构师思考题

题目一：8 万块电表中 2000 块因基站故障断线 3 小时，网关缓存了这批数据，恢复后要补进去。网关开发说"数据都在，按到达顺序原样写入就行"。这个方案会发生什么？请给出你的补报通道设计。▶ 点击展开解析

🔍 "原样写入"的三层后果

正确性层面反而没事——这是很多同学的意外点：补报数据时间戳落在 3 小时前，属于乱序写入，TDengine 3.0 不会拒绝，落 STT 文件、查询时按时间戳+版本号多路归并，时间戳是设备侧时间的话数据一条不丢、不错（这正是版本号机制的设计意图）。

性能层面有事：3 小时 × 2000 子表的乱序数据集中涌入，STT 小文件瞬间堆积，读放大上升，期间所有查询变慢——乱序的代价全在读侧兑现，而且由全部查询共同买单。

边界与下游：① 若库的 KEEP=90 而缓存数据更久远（超过 now − KEEP），会被直接拒写——补报窗口必须小于 KEEP；② 依赖窗口关闭触发的流计算，晚到的数据可能错过触发时机，小时表"少算"，需要补算；③ 若时间戳误用了"到达时间"而非采样时间，历史数据被顶掉——这才是真正的丢数据。

✅ 补报通道设计

  • 双通道隔离：补报数据走独立队列/独立写入线程组（或独立 topic），与实时流互不挤占；网关侧先按"设备 + 时间"排序再发，把乱序压到单文件内；
  • 低峰回放 + 限速：补报速率限流，避开上报高峰；回放期间监控 STT 文件数与合并进度，堆积告警；
  • 下游补偿：回放完成后，对受影响时间区间显式补算降采样表（重跑区间聚合或临时触发流计算），再刷新报表缓存；
  • 对账兜底：按"设备 × 小时"比对源端计数与落库行数，缺数重放——补报通道没有对账，等于没闭环。
题目二：新项目：1 万台设备、10 秒一条、每条 8 个 float 列；查询需求 = 大屏 1 秒刷新最新值 + 月度报表；单机 8 核 32G。请给出 vgroups/BUFFER/CACHEMODEL 的取值与月报表的查询路径，并算出依据。▶ 点击展开解析

🔍 三笔账

容量：日增 = 1 万设备 × 8640 条/天 = 8640 万行；行宽 ≈ 8×4B + 8B(ts) ≈ 40B → 原始约 3.2GB/天，列压缩 ~1/10 → 落盘约 350MB/天、月增 ~10GB——单机完全装得下，瓶颈根本不在容量，别为"存不下"过度设计。

写入：稳态 1000 行/s，峰值按 ×3~5 也只有 5k 行/s，对 8 核是小意思。vgroups = 8 × 2 = 16（官方建议；注意不是越多越好——vnode 过多反而制造资源竞争），BUFFER 默认 256MB 不动。内存预算：16 × 256MB = 4GB 写池 + 元数据 + 读缓存，约 5GB，32G 机器宽裕，甚至可以反问"为什么不拆双节点做 replica 2/3"。

读取：大屏 1s 刷最新值 → CACHEMODEL 至少 last_row，稳妥选 both；CACHESIZE 从默认 1MB/vnode 提到 16MB（16 vnode 也只多占 256MB，便宜得很）。

✅ 月报表路径

  • 绝不现场扫明细：90 天 × 8640 万行/天 ≈ 78 亿行参与运算，必然超时；
  • 建 1 小时降采样流：小时表每月 = 1 万子表 × 720 行 ≈ 720 万行，月报在小时表上再按天聚合，毫秒~秒级返回；聚合列同时声明 SMA，明细层的偶发查询也受益；
  • 原始层 KEEP 90~180 天限寿，服务排障下钻；降采样表 KEEP 长期——两级生命周期，冷热天然分层。

一句话：先把"写路径有序批量、读路径预聚合"设计进去，这套需求在单机上只是热身——容量规划的意义不是买大机器，而是证明不需要买。
