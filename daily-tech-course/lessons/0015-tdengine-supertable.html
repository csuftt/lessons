TDengine 超级表与子表数据建模
—— 一设备一表，是玄学还是科学？

时序数据库建模的第一道分水岭：建错表，写入翻车、查询爆炸；建对表，千万设备稳如老狗。
🗄 TDengine 📅 2026-09-01 ⏱ 预计阅读 10 分钟

01从一个真实事故说起

某能源平台接入 12 万台智能电表，每台 5 秒上报一次电流、电压、相位。团队最初用 MySQL，三个月后单表 40 亿行，写入延迟飙升到秒级，磁盘告警。迁移 TDengine 后，架构师拍脑袋做了两个决定：

  • ❌ 所有设备塞进一张超级表，device_id 做普通列而非标签 —— 查单设备曲线要全表扫描标签列；
  • ❌ 标签里放了「当日累计电量」这种高频变化字段 —— 每次上报都在更新标签，标签索引疯狂重建。

结果：TDengine 撑住了写入，但查询比 MySQL 还慢。问题不在数据库，在建模。时序库的建模哲学与传统 OLTP 完全不同——今天我们把这层窗户纸捅破。

02核心原理：超级表 = 模板 + 标签

TDengine 的「一个数据采集点一张表」不是营销口号，而是存储引擎的根基：

  • 超级表（STable）：定义数据列（时序采集量，随时间变化）和标签列（静态属性，如设备位置、厂商）。它只是模板，本身不存数据。
  • 子表：每个设备一张，继承超级表 schema，各自持有不同的标签值。子表内数据按时间严格有序、列式压缩（时间戳用 delta-of-delta 编码，压比极高）。
  • 二维剪裁：查询时先按标签过滤定位子表（标签有内存索引），再按时间范围裁剪数据块——两层过滤让 IO 只发生在极小的数据切片上。

💡 架构师视角的关键洞察
子表数量本身不是负担（百万级子表完全 OK），负担来自错误的聚合方式。把「设备维度」下沉为子表边界后，单设备查询天然变成主键点查；跨设备聚合则利用标签索引先收敛集合，再并行扫描。

03建模决策：四条架构权衡

① 一张超级表还是多张？

维度合入一张超级表拆分多张超级表
采集 schema字段基本一致字段差异大、大量空列
采集频率相近（同数量级）秒级 vs 小时级混存浪费严重
查询模式常做跨类型联合聚合各查各的、互不关联
保留策略KEEP 是库级参数，一致即可需不同保留期 → 必须拆（甚至拆库）

② 标签设计三原则

  • 只放静态属性：位置、厂商、型号、所属线路。任何会随上报变化的值放数据列。
  • 面向查询过滤：业务高频过滤条件 = 标签候选。没人查的字段别做标签，白占内存索引。
  • 控制基数语义：标签值的组合数决定子表定位效率，「设备 ID」这类唯一标识放标签即可，不需要额外冗余。

③ 库与 vgroups 规划

database 是资源隔离与保留策略的边界：按业务线/地域分库；VGROUPS 决定写入并行度（每个 vgroup 是一组多副本的存储分片）。经验起点：每 50~100 万 TPS 量级对应 8~16 个 vgroup，后续可结合副本数与磁盘 IO 压测微调。

④ 容量粗算

磁盘 ≈ 设备数 × 每日报文数 × 列数 × 单值压缩后字节 × 副本数。时序压缩收益极高（电压这类缓变列可压到 1 字节以内/值），但务必按真实数据压测——别拿 OLTP 的容量直觉套时序库。

04实战：从建库到降采样查询

power-modeling.sql
-- 1. 建库：保留 365 天，每个文件覆盖 10 天数据，4 个 vgroups
CREATE DATABASE power KEEP 365 DURATION 10 VGROUPS 4;

-- 2. 超级表：数据列 + 标签列
CREATE STABLE power.meters (
  ts        TIMESTAMP,
  current   FLOAT,
  voltage   INT,
  phase     FLOAT
) TAGS (
  location  NCHAR(64),   -- 静态：安装位置
  factory   NCHAR(32),   -- 静态：厂商
  line_id   INT           -- 静态：所属线路
);

-- 3. 自动建子表写入（首次出现 d001 时自动建表并打标签）
INSERT INTO power.d001 USING power.meters
  TAGS('广州-1号变电站', '厂商A', 7)
  VALUES(NOW, 10.3, 220, 0.31);

-- 4. 单设备曲线：点查子表，毫秒级
SELECT * FROM power.d001
WHERE ts > NOW - 10m;

-- 5. 跨设备聚合：先标签剪裁，再并行扫描
SELECT location, AVG(voltage), MAX(current)
FROM power.meters
WHERE factory = '厂商A' AND ts > NOW - 1h
PARTITION BY location;

-- 6. 降采样：5 分钟窗口均值，喂给监控大盘
SELECT _wstart, AVG(current), MAX(phase)
FROM power.meters
WHERE ts > NOW - 1d
INTERVAL(5m);
⚠️ 生产环境三大坑
  1. 标签批量更新代价：几十万子表集体改标签会触发元数据重写，安排在低峰期，分批 ALTER TABLE ... SET TAG。
  2. 乱序写入：时间戳大幅回跳（如设备对时钟漂移）会让压缩失效、写入放大。网关侧先做时间戳校准。
  3. 时区陷阱：写入统一用 UTC 毫秒，展示层转换时区；混用本地时间会导致窗口聚合错位 8 小时。

📌 今日要点

  1. 一个设备一张子表是 TDengine 的存储根基：时间有序 + 列式压缩 + 二维剪裁（标签定子表、时间定数据块），建模必须顺着这个哲学走。
  2. 标签只放静态属性，且必须是高频过滤条件；高频变化字段进标签等于自废武功。
  3. 拆不拆超级表看四件事：schema 差异、采集频率、查询模式、保留策略（KEEP 是库级，不同保留期必须拆）。
  4. 容量与并行度靠公式 + 压测：vgroups 决定写入并行度，磁盘按「设备 × 频率 × 列 × 压缩字节 × 副本」估算后用真实数据验证。
  5. 生产三大坑：标签批量更新、乱序写入、时区错位——都在网关/写入侧提前治理，别指望数据库兜底。

05架构师思考题

思考题一：12 万电表（5 秒/次）+ 2 万充电桩（1 秒/次），schema 有 60% 重合，该建一张超级表还是两张？
建模权衡

结论先行：建议拆成两张超级表，甚至两个 database。逐层拆解理由：

1. 采集频率差一个数量级

1 秒 vs 5 秒意味着单位时间写入量差 5 倍。混存时，充电桩子表的数据块密度远高于电表，文件合并（compaction）策略、内存占用曲线都被高频端主导，低频端的存储碎片率上升。分开建表后可对充电桩库单独加大 BUFFER 与 vgroups 配额。

2. schema 重合 60% ≠ 应该合表

剩下 40% 的差异字段（充电桩特有的 SOC、功率模块温度等）会造成电表子表大量空列。虽然 TDengine 空列存储开销极低，但查询侧 SELECT * 的反序列化成本与语义混乱是真实代价。「加 type 标签区分」的方案会让每次电表查询都要带上 WHERE type='meter' 过滤，一旦漏写就污染聚合结果——这是典型的正确性风险换表数量的负收益交换。

3. 业务查询模式天然隔离

电表侧关心线损与负载曲线，充电桩侧关心充电会话与功率峰值，几乎不存在跨两类设备的联合聚合。若确有「全站点总功率」这类需求，在应用层分别查询后求和，或用流计算预聚合，都比物理合表更干净。

4. 保留策略大概率不同

电网侧合规要求曲线数据留 1~3 年，充电桩运营数据可能只需 3~6 个月。KEEP 是 database 级参数，保留期不同基本锁死了「拆库」的答案。

决策口诀：频率差数量级、schema 差四成、查询不交叉、保留期不一致——四条中了两条就该拆。

思考题二：新项目预计 50 万设备、每设备 10 列、10 秒上报一次，3 副本、保留 180 天，如何预估磁盘容量与 vgroups？
容量规划

第一步：算原始写入速率（定 vgroups）

每日报文数 = 86,400 秒 ÷ 10 秒 = 8,640 条/设备/天；全局 TPS = 500,000 × 0.1 = 5 万行/秒（每行 10 列 ≈ 50 万列值/秒）。按「8~16 vgroups 支撑百万级 TPS」的经验斜率，5 万 TPS 属轻负载，初始 4~6 个 vgroups 足够；若读写混合且有重查询，取上限 6~8 并压测确认。vgroups 后期可扩但涉及数据重平衡，宁可一次到位也别缩手缩脚。

第二步：算压缩后磁盘（定存储）

单行原始约 10 列 × 4~8 字节 ≈ 50~80 字节；时序压缩后（delta-of-delta + 列级字典），缓变列可到 1 字节/值以下，激进估计单行 5~15 字节。取中位 10 字节：

  • 每日原始数据：500,000 × 8,640 × 10 B ≈ 43 GB/天（压缩后）；
  • 180 天保留：43 × 180 ≈ 7.7 TB；
  • × 3 副本 ≈ 23 TB，另留 30% 余量应对 compaction 峰值与标签/索引元数据 → 规划 30 TB。

第三步：压测校准（拒绝纸面架构）

公式给的是数量级，真实压缩率取决于数据形态（电压 220 缓变 vs 电流剧烈波动，压比差 5~10 倍）。拿真实设备采样 1 周，用 SHOW DATABASES 观察磁盘增长率反推压缩率，再回到第二步修正。同时监控 vgroup 写入延迟 P99，超过 100ms 持续出现即触发扩容预案。

架构口诀：TPS 定 vgroups，保留期 × 压缩率定磁盘，压测定真相。
