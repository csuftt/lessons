eBPF 与 Cilium 网络：把数据面装进内核

上一讲聊完 Istio ambient 的"节点共享"路线，这一期继续云原生前沿线，进入它的对门——内核路线。eBPF 让数据面逻辑不经用户态代理、直接在 Linux 内核里跑：策略执行、负载均衡、加密、可观测性一次到位。从一次 iptables 规则风暴引发的全厂 API 超时事故讲起，拆开 eBPF 的安全模型（验证器 + JIT）、内核版本硬账，再落到 Cilium 的架构、kube-proxy 替换、基于身份的网络策略与灰度上生产剧本。

01一起"规则风暴"事故：iptables 的税，藏在规模里

事故复盘：5000 个 Service 拖垮的不只是网络

某电商团队的大促压测夜，凌晨 1 点起全站 RPC 调用超时告警爆发。排查方向从应用、注册中心一路拐到网络，最后在节点上 top 看到 CPU sys 占比飙到 35%+，火焰图里全是 iptables 规则匹配的内核函数。账目是这样的：

  • 集群已长到 约 5000 个 Service、3 万个 Pod，kube-proxy 的 iptables 规则链随 Service×Endpoint 数量近似线性膨胀——社区通行的估算是 每条 Service 规则链约占 2KB 内存、Service 数过千后新建连接延迟开始肉眼可见（0024 期讲过它的 O(n) 线性匹配机制，本期不重讲）；
  • 压测中大促预发的几百个新 Service 集中下发，kube-proxy 全量刷新规则（iptables 无增量 API），iptables-restore 单次卡秒级——期间新建连接排队，上游超时重试叠加（0049 讲过的重试放大），延迟雪崩成形；
  • 最疼的是恢复动作：切 IPVS 模式要滚动重启全部节点的 kube-proxy，而值班同学当时根本不敢在生产夜里动它——排障知识缺位让故障时长从 20 分钟拖到 2 小时。
复盘的真正结论

iptables 不是"错"了——它设计给主机防火墙，没人打算让它扛每秒百万次的服务发现转发。错的是把 O(n) 的用户态规则引擎放在了 O(1) 问题的数据路径上。这一年多数团队的动作是：新集群直接上 eBPF 数据面（Cilium），老集群把"iptables 模式退化"纳入监控。Cilium 官方自己也曾披露：大规模 Service 场景下 iptables 模式的 CPU 与延迟曲线崩溃式上扬，正是 eBPF 替换项目的最初动机。

02原理：eBPF 的安全模型与内核版本账

先回答"凭什么敢把代码塞进内核"

eBPF（extended Berkeley Packet Filter）的本质：把一小段经过安全验证的字节码动态加载进运行中的 Linux 内核，挂在事件钩子上执行——网卡收包、系统调用、Socket 操作都可以是钩子。它敢这么干而不崩内核，靠的是加载前的三道关：

  1. 验证器（Verifier）：加载时静态分析所有执行路径——证明程序必然终止（内核 5.3 起才允许可证明边界的循环，之前一律禁循环）、所有内存访问在界内、指令数不超限（内核 5.2 起上限 100 万条验证指令）。证明不了安全的程序直接拒绝加载——这是"内核不崩"的数学保证；
  2. JIT 编译：通过验证的字节码编译成本机指令执行，接近原生速度——这是"快"的来源，不是靠解释执行硬扛；
  3. 能力管控：加载 eBPF 程序需要特权（5.8 起拆出独立的 CAP_BPF 能力位），普通容器进程塞不进去。

内核与用户态之间用 maps（键值表）交换数据：策略表、连接表、统计计数都住在 maps 里，用户态控制面写表、内核态程序查表执行——控制逻辑与数据逻辑分离，这正是 Cilium 架构的底座。

版本账：4.x 到 6.x，一张决定生产形态的表

内核版本关键能力对生产的意义
4.x（≤4.19）基础 XDP/tc 钩子、无有界循环、验证器较弱CentOS 7 时代内核——能跑但处于 eBPF"西部时代"，多程序共存隔离差，生产慎用

03架构：Cilium 数据面与三本账

Cilium 是什么：eBPF 之上的网络、安全、可观测三合一

Cilium 是 CNCF 毕业项目（2023 年 10 月，首个以 eBPF 为核心毕业的项目），在 Kubernetes 里同时扮演三个角色：CNI 网络 插件、网络策略引擎、可观测性平台（Hubble）。它的核心抽象只有一个：基于身份的安全模型——每个 Pod/节点获得集群级身份（安全标识），策略与加密绑定身份而非 IP 地址，Pod 重建 IP 变了身份不变，策略不用跟着改。

账一：kube-proxy 替换——O(n) 到 O(1) 的量级变化

Cilium 可以整体替换 kube-proxy（kubeProxyReplacement 模式）：Service 转发从"iptables 规则链线性匹配"变成"eBPF 哈希表查找"，复杂度从 O(n) 降为 O(1)。东西向流量在 Socket 层（connect() 系统调用时）直接改写目标后端，不经 NAT、不建 conntrack，每包开销大幅下降；南北向在 XDP 层做负载均衡——Cilium 1.8 时代的经典实测：单节点外部压测同一 Service，kube-proxy 每秒约转发 210 万请求即开始丢包，XDP 加速后打满数据源每秒 1000 万请求。社区复现的建连延迟对比：Service 数从 1000 涨到 5 万，eBPF 路线 P99 从 0.38ms 到 0.48ms 几乎平的；iptables 模式从 1.8ms 恶化到 85ms（IPVS 居中，1.2ms）。

账二：基于身份的网络策略——IP 治理换身份治理

传统 NetworkPolicy 依赖 IP（Pod 重建即失效，先要 IP 归属推断）。Cilium 给每个工作负载分配集群身份，策略写"允许 frontend 标签的身份访问 backend 的 8080 端口"，身份随 Pod 调度实时生效，且能覆盖东西向 + 南北向 + FQDN（域名级出站控制）+ L7 HTTP/Kafka 规则。对安全团队的意义：出站不再只能按 IP 段粗粒度封禁——"允许访问 api.weixin.qq.com、拒绝其他外网"这类策略第一次成为一等公民。

账三：Hubble 可观测性——免费的全链路流日志

Hubble 复用 eBPF 数据面天然看到的全部流量，输出服务依赖图、流日志（谁在何时被谁因哪条策略拒绝）、黄金指标——零应用侵入、零 sidecar。"被 NetworkPolicy 拒绝的连接到底是谁"这个排障高频问题，Hubble 一条命令出答案。0046 期讲的长连接网关排障里，"这连接到底建立没有"的确认成本，在 Hubble 集群近乎为零。

账外账：透明加密与边界

节点间流量可开 WireGuard/IPsec 透明加密（1.20 起同节点 Pod 间流量也纳入加密，补齐多租户同宿主机窥探缺口）。而 eBPF 路线的边界也要写清楚：① L7 深度流量治理仍需 Envoy（每节点一个，不是每 Pod），复杂金丝雀/镜像等能力成熟度不如 Istio 体系——0051 讲过的分界在这里兑现：L4 进内核、L7 按节点；② 内核版本是硬依赖（见 02 节）；③ eBPF 程序排障要求内核技能，火焰图/验证器日志不是普通运维的日常工具。Cilium（内核路线）与 Istio ambient（节点共享路线）并非互斥——大量团队用 Cilium 做 CNI 承载 Istio 网格，两层各干各的活。

版本坐标（2026-10）

当前维护线 1.20.2 / 1.19.8 / 1.18.14（2026-09-15 同批补丁；1.20 于 2026-09-14 发布）。1.20 要点：CNI 二进制从 76MB 瘦到 16MB（500 节点集群 CNI 存储从约 38GB 降到 8GB，节点启动更快）；同节点 Pod WireGuard 加密；Kubernetes ClusterNetworkPolicy（Admin/Baseline 分层，平台团队终于有了集群级策略权威）；netkit datapathMode: auto 自动探测内核（6.8+ 用 netkit、否则回退 veth）；数据面插件机制 beta（Google 主导，第三方 eBPF 程序不再需要 fork Cilium）。1.19 的 Multi-Pool IPAM 转稳定。生产采用面：Trip.com "五年生产零重大数据面事故"、DigitalOcean、Form3（跨数据中心切换）、Adobe、Bell Canada 等；GKE/Datadog 深度参与上游。

04实战：内核预检、kube-proxy 替换与灰度上生产

实战一：内核与前置条件预检（决定性的一步）

# 1. 内核版本与 BTF（CO-RE 依赖 /sys/kernel/btf/vmlinux）
uname -r                              # 期望 ≥ 5.10（生产基线）
ls /sys/kernel/btf/vmlinux            # 无此文件的节点，eBPF 程序加载即失败

# 2. cilium-cli 预检：内核能力逐项核对（每类集群都要跑）
cilium sysdump --output-filename pre-check   # 采集现场
kubectl -n kube-system logs ds/cilium | grep -i "require\|probe"
# 常见红灯：KernelVersion 低 / BPF Map 大小受限 / 缺 BTF

# 3. eBPF 程序共存盘点——多工具冲突的第一道防线
bpftool prog show | wc -l             # 已加载的 eBPF 程序数
bpftool map show | head -5            # maps 占用（探针类工具常驻大表）

预检的三个红灯各有含义：内核过低——能力缺失或行为退化，先升内核再说；缺 BTF——换带 CONFIG_DEBUG_INFO_BTF=y 的节点镜像；已有大量 eBPF 程序——排障"看不见的共存者"（安全探针/观测探针由不同团队部署），混部前先对齐归属与资源占用，老内核上多程序共存隔离性差是真实事故来源（某 4.18 内核环境两个探针共存直接 kernel panic 连环重启 24 台）。

实战二：kube-proxy-free 集群（新集群推荐姿势）

# Helm 安装：eBPF 直接接管 Service 转发（不再部署 kube-proxy）
helm install cilium cilium/cilium -n kube-system \
  --set kubeProxyReplacement=true \
  --set k8sServiceHost=API_SERVER_IP --set k8sServicePort=6443 \
  --set bandwidthManager.enabled=true \    # 需内核 ≥5.10（替代 iptables 限速）
  --set hubble.enabled=true --set hubble.relay.enabled=true

# 验证三件套
cilium status --wait                     # agent/operator 全 Ready
cilium connectivity test                 # 内置连通性套件（含策略用例）
kubectl get ds -n kube-system            # 确认 kube-proxy 已不在列表

两个注意点：① kubeProxyReplacement 要求把 API Server 地址显式传给 Cilium（原来这个活是 kube-proxy 干的）；② 从 1.14 起 replacement 默认就是"能开尽开"的探测逻辑，但混合云/特殊 CNI 环境（如自带路由的 Terway）要单独核对探测报告，不要默认全绿。另外本页验证三件套里 cilium connectivity test 会真实发起跨节点/跨策略用例，压测窗口别跑，选业务低峰执行。

实战三：存量集群灰度迁移剧本（iptables → Cilium）

1

预检与容量：按实战一跑全套预检；盘点现有 NetworkPolicy 语义（iptables 系策略迁移到身份策略要重写语义，不是翻译 YAML）；选定首灰度节点池（无状态业务 + 可随时摘除）。

2

双 CNI 并存期（如环境不支持原地换）：新节点池跑 Cilium、旧节点池维持原状，跨池流量走标准 Pod 网络；此阶段验证的东西向连通性、DNS、出站策略三件套，每项都要有用例。

3

节点池轮换：业务逐池迁移（Pod 漂移即完成数据面切换——eBPF 的优势：换的是节点不是应用）；每池迁移后跑 cilium connectivity test + 业务冒烟，P99 延迟基线对比（预期不变或略降）。

4

收尾：全网切换后退役旧 CNI 与 kube-proxy；把"内核版本纳入节点池镜像管理 + eBPF 程序清单纳入变更管理"写进平台规范（内核小版本升级 = eBPF 兼容性回归测试，这是长期纪律）。

✅ eBPF / Cilium 上生产体检清单（10 条）

☐ 内核版本统一在 5.10+（最好 5.15+），节点池镜像带 BTF　☐ 每类节点镜像在 CI 里跑 eBPF 兼容性测试　☐ eBPF 程序清单有台账（bpftool 定期导出，探针类工具部署走变更流程）　☐ cilium-agent 的 CPU/内存有独立容量规划（它不等于数据面开销，别混着看）　☐ kubeProxyReplacement 探测报告全绿或有明确豁免记录　☐ NetworkPolicy 已从 IP 语义迁移到身份语义并经安全评审　☐ Hubble Relay/UI 已部署、流日志接了告警（策略拒绝突增要有声音）　☐ 跨节点加密（WireGuard/IPsec）按合规要求评估开启　☐ 内核小版本升级 SOP 包含 P99 延迟回归基线　☐ 有"摘除 Cilium 节点池回退旧数据面"的演练记录

05今日要点

  • eBPF 的安全模型三件套：验证器（加载时证明安全，内核不崩的数学保证）+ JIT（近原生速度）+ 特权管控（CAP_BPF）——"敢把代码装进内核"的完整答案，maps 是内核态与用户态的分界线。
  • 内核版本是硬账不是软建议：5.3 有界循环、5.8 能力位拆分、5.10/5.15 生产基线、6.8 netkit；版本过关 ≠ 跑得稳——每个内核小版本都要有兼容性与延迟回归。
  • Cilium 三本账：kube-proxy 替换（O(n)→O(1)，Service 5 万时 P99 0.48ms vs iptables 85ms）；身份网络策略（IP 治理换身份治理，FQDN 出站控制）；Hubble 可观测（零侵入全链路流日志）。
  • L4 进内核、L7 按节点：eBPF 路线不是万能替代——深度 L7 治理仍需 Envoy（每节点一个）；与 Istio ambient 是两条互补路线，Cilium CNI + Istio 网格的组合大量存在。
  • 上生产的顺序是预检先于一切：内核/BTF/eBPF 共存盘点三红灯一个都不能漏；eBPF 程序"对用户态完全透明"，没有台账就等于没有排障入口。

06架构师思考题

题目：你们有一个 800 节点、1.2 万 Pod 的存量集群（内核 5.4 混 5.10，iptables 模式，Service 约 6000 个），频繁出现"滚动发布窗口 API 建连超时"，已确认与 iptables-restore 全量刷新相关。领导拍板"半年内迁移到 eBPF 数据面"。① 给出你的迁移方案骨架与阶段验收标准；② 迁移中某夜值班收到"Cilium 节点池上跨节点 Pod 互访批量失败、同节点正常"，网络抓包显示包到了目标节点但没人处理——给出至少三个假设与定位路径；③ 两个月后安全团队要求在全部节点部署基于 eBPF 的运行时安全探针，你如何评估与落地？▶ 点击展开解析

🔍 三问拆解

① 方案骨架与验收：第一阶段内核统一到 5.10+（或 5.15+）——800 节点按节点池滚动重刷镜像，验收=全节点 ls /sys/kernel/btf/vmlinux 存在 + CI 里 eBPF 兼容性测试通过（5.4 内核是硬短板：无有界循环等能力不说，大量 Cilium 特性降级运行，先升内核再迁数据面，变量解耦）；第二阶段试点节点池——无状态业务池先迁（双 CNI 并存或节点池轮换），验收=cilium connectivity test 全绿 + 建连延迟基线对比（重点盯"发布窗口建连超时"指标是否消失——这是本次迁移的业务级 OKR）+ Service 转发路径核验（bpftool prog show 有 lb 程序、iptables 里 Service 链不再增长）；第三阶段全网轮换 + kube-proxy 退役，验收=iptables 规则总量归零、发布窗口指标连续两周无尖刺。节奏建议：月一~二内核、月三试点、月四~五逐池、月六收尾。

② 跨节点失败、同节点正常的定位：三个假设按概率排序——

  • 假设一：MTU/封装不匹配（跨节点流量走 VXLAN/Geneve 封装加头，若底层网络 MTU 未预留或应用发了大包，表现为"包到了目标节点但 veth 丢弃"，kubectl logs ds/cilium 查 drop 原因字段、cilium metrics 里 cilium_drop_count_total 按 reason 分桶——这是 Cilium 排障第一入口）；
    • 假设二：身份策略误伤（迁移期新身份未同步或策略语义从 IP 改写为身份后，跨节点对端身份解析失败导致默认拒绝——同节点走 Socket 层快路径可能不触发同一条策略路径，特征=Hubble 流日志里 FORGotten/Policy Verdict DENY，hubble observe --verdict DROPPED 一查便知）；假设三：eBPF 程序加载不完整（目标节点 agent 异常或内核差异导致 tc 程序没挂上，"包到了没人处理"的字面原因——bpftool prog show 对比正常/异常节点的程序清单、cilium-agent 日志 grep attach 失败）。定位次序：先 cilium metrics drop reason（量级最大方向）→ Hubble DENY 流（策略方向）→ 节点程序清单对比（加载方向）。

    ③ eBPF 安全探针评估落地：先算三笔账——共存账（bpftool 盘点现有程序与 maps 占用，Cilium 与探针的钩子/资源冲突在老内核上是真实事故源，本集群已统一 5.10+ 风险可控但要留资源余量）；性能账（探针类工具在高频系统调用路径上的 CPU 开销按节点压测，按公开复盘口径预留 5~10% 内核态余量，灰度节点池先跑两周看 P99）；治理账（探针的 TracingPolicy 策略变更走与网络策略同级的评审流程——eBPF 探针能 kill 进程，策略写错的爆炸半径不亚于网络策略）。落地姿势：独立 DaemonSet 分批灰度（不与 Cilium 升级同窗口）、事件出口接独立管道（安全事件与网络流日志分流，防互相打饱和）、并约定"探针类工具部署必须登记台账"的平台规范——把这次评估沉淀成 eBPF 治理制度，而不只是又一次安装。
