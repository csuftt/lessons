MySQL 索引优化与执行计划深度分析

🗄️ MySQL 📐 索引优化 · 执行计划 · InnoDB ⏱️ 约 10 分钟 🎯 架构师 / 高级工程师
📅 2026-08-14 周四

1从一个线上告警说起

某电商大促前夕，订单中心数据库 CPU 飙到 95%，慢查询日志暴增。开发同学反馈："明明查询字段都加了索引，为什么还这么慢？"

这是一道典型的"伪索引"陷阱。DBA 排查后发现：SELECT * FROM t_order WHERE user_id = ? AND create_time > '2026-08-01' ORDER BY status 这条语句走了 idx_user_id 索引，但因为返回行数过多，触发了大量回表，最终执行时间 800ms。

问题的根源不在于"有没有索引"，而在于索引是否被正确使用。这正是架构师必须掌握的核心能力——读懂执行计划，理解索引工作原理，才能在数据库设计阶段就规避性能风险。

💡 架构师视角

索引优化不是 DBA 一个人的事。表结构设计、查询写法、业务模型都决定了索引能否生效。性能问题 80% 可在设计阶段消除，而不是等上线后再救火。

2InnoDB 索引底层：B+ 树原理

要理解为什么某些索引"失效"，必须先搞清楚 InnoDB 的索引结构。InnoDB 的所有索引都是 B+ 树（B+ Tree），它有三个关键特性：

  • 非叶子节点只存键值 + 指针，不存数据，一个节点可以放更多键 → 树更矮 → 磁盘 IO 更少
  • 数据全部存在叶子节点，且叶子节点之间用双向链表连接 → 范围查询极快
  • 聚簇索引 vs 二级索引：聚簇索引的叶子节点存整行数据；二级索引的叶子节点只存主键值，需要回表才能拿到完整行
图 1：InnoDB B+ 树索引结构示意图
⚠️ 关键认知

一棵 3 层 B+ 树可以索引约 2000 万行数据（假设每页 16KB、每个非叶子节点能存 1000+ 个键）。所以"千万级表索引慢"几乎都是使用姿势问题，不是 B+ 树本身的瓶颈。

3EXPLAIN：架构师的"X 光片"

拿到一条慢 SQL，第一步永远是 EXPLAIN。它会告诉你 MySQL 实际如何执行这条语句。我们先看最关键的几个字段：

字段含义架构师关注点
type访问类型从好到差：system > const > eq_ref > ref > range > index > ALL。生产至少 range
key实际使用的索引NULL 表示没用索引！
rows预估扫描行数越小越好，超过 1 万需警惕
Extra额外信息Using filesort / Using temporary 是危险信号
key_len索引使用长度判断联合索引用到了几个字段

实战：诊断一条慢查询

SQLMySQL 8.0
-- 业务场景：查询某用户近 30 天的订单，按状态排序
EXPLAIN SELECT order_id, user_id, amount, status, create_time
FROM t_order
WHERE user_id = 10086
  AND create_time > '2026-07-14'
ORDER BY status;

现有索引：idx_user_id (user_id)。执行计划输出：

typekeyrowsExtra
refidx_user_id12800Using filesort
🚨 三个红色信号
  • rows=12800：预估回表 1.28 万次，IO 压力大
  • Using filesort：索引无法完成排序，需要额外排序步骤（可能内存或临时文件）
  • 只用了 idx_user_id 的 user_id 一个字段，create_time 和 status 都没走索引

优化方案：建立联合索引

根据最左前缀原则，设计一个覆盖查询条件和排序字段的联合索引：

SQLDDL
-- 联合索引：等值在前，范围在中，排序在后
ALTER TABLE t_order
  ADD INDEX idx_uid_time_status (user_id, create_time, status);

-- 删除冗余的单列索引（已被联合索引覆盖）
ALTER TABLE t_order DROP INDEX idx_user_id;

再次 EXPLAIN：

typekeykey_lenrowsExtra
range idx_uid_time_status 12 320 Using index condition

效果立竿见影：扫描行数从 12800 降到 320（40 倍提升），filesort 消失，执行时间从 800ms 降到 8ms。

4六大常见索引失效场景

① 对索引列使用函数或运算

反面 vs 正面SQL
-- ❌ 失效：函数包裹索引列
WHERE YEAR(create_time) = 2026
WHERE DATE(create_time) = '2026-08-14'

-- ✅ 正确：改写为范围查询
WHERE create_time >= '2026-01-01' AND create_time < '2027-01-01'
WHERE create_time >= '2026-08-14 00:00:00'
  AND create_time <  '2026-08-15 00:00:00'

② 隐式类型转换

字符串列的陷阱SQL
-- phone 是 VARCHAR，传入整型 → MySQL 给列加 CAST → 索引失效
WHERE phone = 13800138000     -- ❌ 全表扫描

-- 加引号，类型一致，索引生效
WHERE phone = '13800138000'  -- ✅ 走索引

③ 最左前缀原则被破坏

对于联合索引 (a, b, c)：

查询条件能否用索引用了哪些字段
WHERE a=?✅a
WHERE a=? AND b=?✅a, b
WHERE a=? AND b=? AND c=?✅a, b, c
WHERE b=? AND c=?❌无（缺最左 a）
WHERE a=? AND c=?⚠️只用 a（中间断开）

④ LIKE 以通配符开头

WHERE name LIKE '%张'     -- ❌ 索引失效
WHERE name LIKE '%张%'    -- ❌ 索引失效
WHERE name LIKE '张%'     -- ✅ 走索引（前缀匹配）

解法：全文检索（FULLTEXT）、ES、或冗余一个反向字符串列。

⑤ OR 条件中存在非索引列

-- 假设 id 有索引，remark 无索引
WHERE id = 1 OR remark = 'xxx'  -- ❌ 整条 SQL 全表扫描

-- 改为 UNION ALL，两部分各自走索引
SELECT ... WHERE id = 1
UNION ALL
SELECT ... WHERE remark = 'xxx' AND id <> 1

⑥ 数据分布严重倾斜

当优化器判断某个值会命中超过约 30% 的行时，会主动放弃索引改走全表扫描（因为全表扫描是顺序 IO，比随机回表更快）。这是优化器的聪明之处，但也常让开发者困惑。可以通过 FORCE INDEX 强制，但通常应相信优化器。

💡 排障速查口诀

函数包列、类型隐转、最左缺失、左模糊、OR 含非索引、分布倾斜——遇到慢查询，按这六条逐一排查，命中率 90%+。

5架构师视角：索引设计的权衡

选型决策框架

🎯 建索引前问自己三个问题
  1. 基数（Cardinality）：该列有多少不同值？性别只有 2 个值，建索引意义不大；订单号唯一，必须建。
  2. 查询频率：每天被查 10 万次的字段 vs 每月查一次的字段，优先级天差地别。
  3. 写读比：索引加速读但拖慢写。高写入表（如日志）要克制建索引；高读低写表可多建。

容量与成本估算

每增加一个二级索引，会带来：

  • 存储成本：索引大小约为表数据的 20%-80%（取决于列宽）
  • 写入开销：每次 INSERT/UPDATE/DELETE 都要同步维护所有索引
  • 内存占用：Buffer Pool 需要缓存索引页，过多索引会挤占数据页缓存

经验值：单表索引数量建议 ≤ 5 个，联合索引字段数 ≤ 5 个。超过这个量级，应该考虑分表或引入搜索引擎。

覆盖索引：避免回表的终极武器

覆盖索引示例SQL
-- 索引 idx_uid_status (user_id, status)
-- 查询只需要的列都在索引里 → 直接从索引树返回，无需回表
SELECT user_id, status FROM t_order WHERE user_id = 10086;
-- Extra 会显示 "Using index" → 完美

-- 反例：SELECT * 必然回表
SELECT * FROM t_order WHERE user_id = 10086;
⚠️ 生产铁律

线上严禁 SELECT *！这是索引优化中最简单也最容易被忽视的一条。只查需要的列，能走覆盖索引就走覆盖索引，性能差距可能达到 10 倍以上。

6生产实战检查清单

检查项命令 / 做法
开启慢查询日志SET GLOBAL slow_query_log = ON; long_query_time = 1;
定期分析慢日志pt-query-digest slow.log（Percona Toolkit）
查看索引使用情况SELECT * FROM sys.schema_unused_indexes;
查找冗余索引SELECT * FROM sys.schema_redundant_indexes;
实时查看正在执行的 SQLSHOW PROCESSLIST; 或 information_schema.processlist
强制使用特定索引（慎用）SELECT ... FROM t FORCE INDEX(idx_xxx) WHERE ...
大表加索引使用 ALGORITHM=INPLACE, LOCK=NONE（Online DDL），或 gh-ost / pt-osc
🚫 大表加索引的坑

千万级表上直接 ALTER TABLE ADD INDEX 在 MySQL 5.6 之前会全程锁表。即使是 MySQL 8.0 的 Online DDL，超大表（亿级）仍建议使用 gh-ost（GitHub 开源）或 pt-online-schema-change，它们通过 binlog 复制 + 影子表实现零停机变更。

📌 今日要点小结

  1. 索引本质是 B+ 树：3 层可索引 2000 万行，"千万级慢"通常是使用问题，不是结构问题。
  2. EXPLAIN 是第一诊断工具：盯紧 type、key、rows、Extra，Using filesort 和 Using temporary 是红色警报。
  3. 六大失效场景：函数包列、隐式类型转换、破坏最左前缀、左模糊、OR 含非索引列、数据分布倾斜。
  4. 联合索引设计三原则：等值在前、范围在中、排序在后；遵循最左前缀；尽量覆盖查询。
  5. 架构师权衡：单表索引 ≤ 5 个，禁止 SELECT *，高写入表克制建索引，亿级表用 gh-ost 做变更。

7🧠 架构师思考题

选一两道深入思考，把今天的知识内化为架构判断力。

思考题 1：联合索引 (a, b, c) 下，这些查询分别用了索引的哪些字段？为什么？

给出 5 个查询，逐一分析 key_len 和索引利用情况：

查询 A：WHERE a = 1 AND b = 2 AND c = 3

完整使用 a, b, c。三个字段都是等值匹配，且顺序与索引一致。如果 SELECT 的列也在索引内，会触发覆盖索引，Extra 显示 Using index。

查询 B：WHERE a = 1 AND c = 3

只使用 a（中间断了 b）。这是索引截断现象。MySQL 8.0.13 之后引入了 Index Skip Scan（跳跃扫描优化），当 a 的不同值很少时（如枚举字段），可能仍能利用 b/c，但这属于优化器的特殊处理，不是通用情况。生产中应避免这种写法，必要时重建索引为 (a, c)。

查询 C：WHERE a = 1 AND b > 10 AND c = 3

使用 a 和 b，c 失效。因为 b 是范围查询，范围查询之后的字段无法走索引（B+ 树无法继续精确定位）。这是"范围之后失效"规则，也是为什么联合索引要把范围字段放最后。

查询 D：WHERE b = 2 AND c = 3

索引完全失效（除非 Index Skip Scan）。因为缺少最左列 a，B+ 树无法从根节点定位入口。可改为 UNION 拆分，或为 (b, c) 单独建索引。

查询 E：WHERE a = 1 ORDER BY b, c

使用 a 做过滤，b/c 用于排序，Extra 不会出现 Using filesort。这是联合索引最优雅的用法——把 ORDER BY 字段纳入索引，让 B+ 树天然有序，省去排序步骤。

架构师总结

联合索引的设计本质是为最频繁的查询模式"量身定制"。拿到一组 SQL 后，先列出所有 WHERE、ORDER BY、GROUP BY 字段，统计出现频率，再用"等值在前、范围在中、排序在后"的原则组合。一个设计良好的联合索引，往往能覆盖 70%+ 的业务查询。

思考题 2：一个 5 亿行订单表，按 user_id 查询近一年订单很慢，加索引还是慢，怎么办？

这是典型的单表数据量瓶颈场景，单纯加索引已无法解决，需要从架构层面思考。

第一步：确认瓶颈根因

先 EXPLAIN 看 rows 字段。如果即使走了 idx_user_id_create_time，rows 仍然显示几十万，说明单个用户的订单量本身就很大（比如大客户一年几十万单），这时索引筛选后仍需大量回表和排序。

第二步：分层解决方案（按成本递增）

方案 A · 冷热分离（推荐首选，成本低）

  • 按 create_time 分表：t_order_2024、t_order_2025、t_order_2026
  • 查询时根据时间范围路由到对应表，近一年数据量直接减少 70%+
  • 历史冷数据可迁移到 TiDB / ClickHouse，只保留热数据在 MySQL

方案 B · ShardingSphere 分库分表

  • 分片键选 user_id，按 hash 或 range 分到 N 个库 M 个表
  • 注意：分片键一旦确定不可更改，跨片查询（如按 merchant_id 查）会退化为广播查询
  • 需要在应用层引入 ShardingSphere-JDBC（无侵入）或 ShardingSphere-Proxy（数据库代理）

方案 C · 引入搜索引擎（复杂查询场景）

  • 用 Canal 订阅 binlog，把订单数据同步到 Elasticsearch
  • 多维度查询（用户、商户、时间、金额范围）交给 ES，MySQL 只做事务写入
  • 代价：数据延迟（秒级）、一致性维护成本、运维复杂度上升

方案 D · TiDB 直接替换（终极方案）

  • TiDB 兼容 MySQL 协议，分布式架构天然支持水平扩展
  • 适合数据量持续爆炸增长（10 亿+）、且不想改业务代码的场景
  • 代价：硬件成本高、需要适应分布式事务延迟、运维团队需要学习

架构师决策树

不要盲目选最先进的方案，按问题严重程度 → 成本 → 团队能力排序：

  1. 单表 < 2000 万、慢 SQL 偶发 → 先优化索引和 SQL（今天的主题）
  2. 单表 2000 万-1 亿、查询模式固定 → 冷热分离 + 分表
  3. 单表 > 1 亿、查询维度多变 → ShardingSphere + ES 双写
  4. 数据量持续爆炸、团队有 DBA → 迁移 TiDB
