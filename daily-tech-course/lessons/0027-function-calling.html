AI · AI 大模型应用系列第 3 讲（工具调用篇）

教会大模型动手：Function Calling 与工具调用

前两讲解决了大模型"知道得更多"（RAG 外挂知识、向量库管检索），这一讲解决"做得到"——用户说"帮我把预发环境的订单服务扩到 4 副本"，助手不该甩回一篇扩容文档，而是真的去调接口把事办了。Function Calling 的心智模型一句话就能说清：模型永远不执行任何东西，它只输出结构化的调用意图，执行永远发生在你的代码里。今天讲透这个协议循环、工具的接口设计、执行编排层的安全闸门，以及"编参数、幻觉工具、死循环"三类经典事故的根治办法。

01一个"会说不会做"与"会做就出事"的连环复盘

集团 IT 的智能运维助手第一版上线：接了知识库（就是前两讲那套 RAG），问什么都能答一段，工单却一张没少——用户问"帮我把 2033 预发环境的订单服务扩到 4 副本"，它礼貌地回了扩容操作手册的链接。会说，不会做，转人工率纹丝不动。

第二版接上工具，三天出了三起事故：

  • 编参数：用户说的是"预发环境"，模型调用扩容工具时 environment 参数填了 prod；副本数给的是字符串 "4.0"，工具侧类型校验直接炸——幸好炸了；
  • 幻觉工具：提示词的背景资料里提到过"重启服务"这个能力，但工具从没注册，模型一本正经地调用了 restart_service，应用层收到一个不存在的函数名；
  • 死循环：某个查询工具超时返回错误，模型把同一个调用原样重发了 11 次，token 烧穿预算，页面转圈 90 秒才报错。

复盘结论：三起事故没有一起是"模型不行"，全是工程层没接住。参数编造是 schema 约束缺位，幻觉工具是"给模型看的能力"与"实际注册的工具"两本账没对齐，死循环是编排层没有轮次与重试预算。工具调用这件事，模型的职责边界其实非常窄——理解今天这套协议循环，你就知道该把可靠性建设押在哪几层。

02原理：模型只表态，你的代码才动手

Function Calling 的本质是一次职责分离：模型是决策者，负责"该不该调、调哪个、参数填什么"；你的应用是执行者，负责校验、鉴权、真正执行与结果回传。协议是一个循环：用户请求连同一批工具定义（JSON Schema）发给模型；模型若决定用工具，返回的不是自然语言而是一条 tool_call（函数名 + 参数 JSON）；你的代码执行后把结果以 tool 角色消息追加进对话再发给模型；模型据此生成回答——或继续发起下一个调用，直到它认为任务完成。这个"继续"就是 Agent 的种子，本期先把单循环讲扎实。

为什么必须结构化，而不是让模型自己"说清楚"

早期做法是提示词里写"请按 JSON 格式输出调用意图"再自己解析——模型偶尔会好心加上一句"好的，以下是您要的 JSON"，解析就崩了。现在的 Function Calling 把这层契约交给了协议本身：工具定义用 JSON Schema 描述，模型的输出受 schema 约束。OpenAI 的 strict: true（Structured Outputs）进一步保证参数严格贴合 schema——代价是 schema 要按规矩写：所有对象 additionalProperties: false、全部字段列入 required、可选字段写成 type: ["string", "null"]。把 schema 当 API 合同来设计，是工具调用可靠性的第一来源：枚举用 enum 约束（环境只有 staging/prod，模型就没机会编出 uat）、类型定死（replicas 是 integer 就不会出现 "4.0"）。

控制参数作用工程时机
tool_choice: auto模型自行决定调不调、调几个（默认）通用助手的默认档
tool_choice: required本回合必须至少调一个工具强制走结构化抽取的管线
tool_choice: 指定函数锁定只调这一个确定性路由，不给模型选择权
parallel_tool_calls允许一回合并行发多个调用读操作可开（查三台机器水位）；写操作务必关

并行调用是双刃剑：三个独立的只读查询并行发，延迟从串行的 3×300ms 压到约 300ms；但两个写操作并行执行，谁先谁后不可控，还可能重复下单——读并行、写串行是底线。

03架构设计：编排层是可靠性的一半

工具的接口设计：像设计公共 API 一样设计工具

  • 小而专，动词命名：一个工具一件事（get_deployment_status、scale_deployment），别做万能的 k8s_operator——描述写不清"什么时候该用它"，模型选择准确率直线下降；
  • description 写"何时用"而非"是什么"："用户询问副本数、资源水位、部署状态时使用"远好于"获取部署信息"——模型靠描述做路由，这是它唯一的菜单；
  • 参数尽机器可判：枚举用 enum、格式用 format、边界用 minimum/maximum，把"预发"到 staging 的翻译收进 schema 或工具内部，别指望模型自由发挥；
  • 幂等与结构化错误：可重试的工具必须幂等（幂等键），失败返回结构化错误对象（错误码 + 人可读原因），让模型能读懂并决定纠正参数还是放弃——抛异常给编排层，模型就失去了自愈机会。

安全三道闸：不信模型的自觉，信架构的约束

第一道，鉴权在工具内部做：以"当前用户"的身份执行（工具拿到的是用户凭证或按用户映射的服务账号），模型永远碰不到凭证——第 01 节"越权创建别人工单"那种事故，根因就是把鉴权寄托给了模型的判断。第二道，写操作过确认：扩容、下单、删除这类有后果的动作，执行前把"将对 X 做 Y"回显给用户确认（human-in-the-loop），高危操作再加审批流。第三道，最小权限：每个工具只授它需要的权限，查询工具就不该持有写凭证——权限面越小，模型被提示词注入攻击后的爆炸半径越小。工具一旦接上，模型就成了新的攻击入口，注入防御与权限收敛必须同步做。

工具生态：MCP 把工具从"方法"升级成"服务"

工具写到十几个，重复造轮子就开始亏：每个应用各自包一遍数据库、仓库、云厂商的接口。MCP（Model Context Protocol）把工具的发现、描述与调用标准化成协议——工具提供方实现一次 MCP server，任何支持 MCP 的客户端（IDE、Agent 框架、Spring AI 应用）都能挂载使用。对架构师的意义：企业内部把高频能力沉淀成 MCP 工具服务统一治理（注册、鉴权、审计一处收口），应用侧只做编排——Spring AI 1.0 已内置 MCP client/server 支持，这与微服务时代"能力平台化"是同一个演进逻辑。

两笔账：token 与延迟

token 账：每个工具的 schema 都随每轮请求计入输入 token（一个工具约 100~300 token），20 个工具全挂 = 每轮多付数千 token，还稀释模型的选择准确率——工具按场景分组装载，别一股脑全上。延迟账：每轮循环 = 一次模型往返（1~3 秒）+ 工具执行时间，3 轮任务轻松 10 秒——把"模型能不能少跑几轮"当成设计目标：能一次给足的上下文别让模型查三轮，确定性的前置步骤（如先查权限）在代码里做掉，不交给模型。

04实战：Spring AI 的工具调用三件套

Spring AI 1.0 GA 的工具模型非常薄：一个 @Tool 注解把普通方法变成模型可调用的工具，@ToolParam 描述参数，注册进 ChatClient 即可——schema 生成、协议解析、方法反射调用全部由框架完成，你只写业务方法。

定义工具（description 写"何时用"，参数用枚举收敛）

@Component
public class DeployTools {

  @Tool(description = "查询指定环境的部署状态：副本数、就绪数、CPU与内存水位。"
      + "用户询问服务运行状态、是否扩容前评估时使用")
  public DeployStatus getStatus(
      @ToolParam(description = "目标环境：预发=staging，生产=prod") Environment env) {
    return deployClient.query(env);          // 以当前用户身份执行（鉴权在内部）
  }

  @Tool(description = "扩容指定环境的Deployment副本数。写操作：调用前必须已获得用户确认")
  public ScaleResult scale(
      @ToolParam(description = "目标环境", required = true) Environment env,
      @ToolParam(description = "目标副本数，1~20", required = true) int replicas) {
    return deployClient.scale(env, replicas); // 服务端幂等键=env+服务+发起者
  }
  public enum Environment { staging, prod }  // 枚举即 enum 约束，编不出第三个值
}

注册并对话

ChatClient ai = ChatClient.builder(chatModel)
    .defaultSystem("你是运维助手。只使用提供的工具操作环境，"
        + "执行写操作前先复述动作并等用户确认")
    .defaultTools(deployTools)              // 注册：schema 自动生成
    .build();

String answer = ai.prompt().user("把预发订单服务扩到4副本")
    .call().content();
// 框架自动完成：模型返回tool_call → 反射调用scale(staging,4) → 结果回传 → 模型总结

✅ 上线体检清单

☐ 工具 schema 按合同设计：枚举/类型/边界全上，strict 模式可用则开　☐ 提示词里提到的能力与注册表严格对齐，删掉一切"幽灵能力"描述　☐ 编排层有最大轮数、同参重试上限与总超时　☐ 鉴权在工具内部以用户身份执行，模型不碰凭证　☐ 写操作回显确认 + 幂等键　☐ 工具返回结构化错误而非抛异常　☐ 全链路审计：谁、调了什么工具、什么参数、结果如何　☐ 工具按场景分组装载，控制每轮 schema 的 token 开销　☐ 并行只开读操作，写操作强制串行

05今日要点

  • 模型只表态，你的代码动手：Function Calling 输出的是结构化调用意图（JSON），校验、鉴权、执行、回传全在你的编排层——可靠性建设的主战场在工程侧，不在提示词里。
  • schema 就是 API 合同：enum 约束取值、类型定死、边界显式；strict 模式把"编参数"的空间压到最小。工具描述写"什么时候用"，模型靠它做路由。
  • 编排层四道闸 + 循环预算：schema 校验拦编参数、权限配额拦越权、沙箱超时拦事故、审计留痕可追责；最大轮数与同参重试上限治死循环。
  • 安全不信模型自觉：鉴权在工具内部以用户身份执行、写操作回显确认、最小权限收敛爆炸半径——接上工具的模型就是新的攻击入口。
  • 两笔账别忘算：工具 schema 每轮都付 token，按场景分组装载；每轮循环都是一次模型往返，确定性的步骤在代码里做掉，别让模型多跑。

06架构师思考题

题目一：运维平台沉淀了 40 个工具（查询、扩缩容、发布、日志、数据库操作……），产品要求"全都给助手挂上"。① 全量挂载会带来哪些具体问题？② 给出你的治理方案。③ 如果工具数量未来涨到 200 个，架构要怎么演进？▶ 点击展开解析

🔍 逐问拆解

① 三重代价：token 账——40 个工具 schema 每轮约 4000~12000 token，全部请求都在为"模型看得见的菜单"付费，成本随轮次×并发线性放大；准确率账——选项越多模型选错率越高，相近工具（查日志 vs 搜日志）的描述差异会被稀释，误路由概率上升；安全账——每次对话的可操作面都等于全量工具，一次提示词注入能摸到的攻击面也是全量的。

② 治理三板斧：按场景分组装载——对话开始时由意图分类（或入口场景）决定挂哪一组工具，运维巡检对话只挂查询组，发布窗口只挂发布组；工具合并与分层——高频复合操作沉淀成粗粒度工具（"重启并验证"一个工具内部做两步，比让模型编排两个工具少一轮往返、少一分出错面）；注册表治理——命名规范、描述评审、schema 模板统一，把工具当公共 API 管理，有 owner、有版本、有废弃流程。

③ 200 个量级走"工具检索"：把工具的名称+描述+参数摘要做成向量索引，每轮按用户意图先检索 Top-K 个工具再动态注入请求——本质是拿上一讲的 RAG 思路治理工具菜单（"RAG over tools"），模型每轮只见 10~20 个相关工具，token 与准确率同时受控；再往上是工具网关/MCP 目录服务：统一注册发现、按调用方权限动态裁剪可见工具、审计全收口——工具规模化后的形态，就是当年 API 网关治理服务的那条老路。

题目二：审计日志显示，模型用完全合法的参数调用了 create_ticket 工具，但创建出的工单归属人不是发起对话的用户——参数没编、工具也没抛错。① 这起事故的问题出在哪一层？② 鉴权应该放在哪里、以谁的身份执行？③ 写操作类工具还需要哪些防误伤设计？▶ 点击展开解析

🔍 逐问拆解

① 出在信任边界划错：参数合法只说明 schema 合同履行了，不代表授权成立。根因是编排层把"模型说调谁"当成了"用户授权做什——assignee 参数是模型从上下文里填的（可能是对话里出现过的第三个人名），而工具侧无主见地信了它。模型填的每一个参数都属于"不可信输入"，与用户表单提交的字段同级，必须过同样的授权校验。

② 鉴权收进工具内部，身份跟着用户走：工具以"当前登录用户"的身份调用下游（凭证由编排层从会话注入，模型全程碰不到），create_ticket 的 assignee 即使允许指定他人，也要校验"当前用户是否有替他人建单的权限"；需要跨用户操作的高权限场景，用按用户映射的服务账号 + 显式授权记录，而不是给工具一把万能钥匙。原则一句话：模型的判断决定"做什么"，用户的身份决定"能做什么"，两者在工具入口合流。

③ 写操作四件套：回显确认——执行前把完整动作（工具、关键参数、影响范围）复述给用户，确认后才放行（高危再加审批流）；幂等键——客户端生成、服务端去重，网络重试不会变成重复创建；影响面预检——能 dry-run 的操作先跑 dry-run（扩容前先校验配额与水位）；审计留痕——谁、经确认与否、以何身份、调了什么、参数与结果全记录，事后可追责可回放。四件套合起来，才配得上"让模型动手"这四个字。
