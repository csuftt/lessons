价格改了，页面就是不变：缓存与数据库一致性架构

缓存和数据库是两个独立存储，任何"两步写"都逃不开并发窗口。今天把 Cache-Aside 的标准姿势、延迟双删的补救逻辑、binlog 订阅的终态方案一次讲清，并给出不一致窗口的时序分析与兜底设计。

01一次"改价不生效"的资损事故

运营把爆款商品价格从 199 改到 99，改价服务日志显示 DB 已提交、缓存也删了，但商品详情页在之后近一小时里仍显示 199，用户按旧价下单，产生资损。代码是这样写的——"直觉上先删缓存更安全"：

// 改价服务（事故版本）
redis.delete(key);          // ① 先删缓存
productMapper.update(p);    // ② 再更新 DB

问题出在 ①② 之间的并发读：详情页高并发下，一个读请求恰好在"已删缓存、DB 还没提交"的瞬间未命中缓存，回源 MySQL 读到旧值 199；写请求随后提交了 DB 并以为自己"已经删过缓存"；读请求再把这个旧值 SET 回缓存，TTL 一小时——旧价格就此"锁"了近一个小时。删除动作发生在了旧值回填之前，等于白删。这不是代码 bug，而是架构问题：两个独立存储之间不存在原子操作，一致性设计的本质不是"消灭窗口"，而是"把窗口压到多小 + 靠什么兜底"。

02原理：三种写顺序，谁踩坑谁安全

缓存一致性方案的所有争论，几乎都浓缩在"写请求到底按什么顺序动这两个存储"。三种朴素策略的结局：

  • 先删缓存，后更新 DB：01 节的事故。删完到 DB 提交之间的任何一次并发读，都会把旧值捞回来。单用必错；
  • 先更新 DB，后删缓存（Cache-Aside 标准姿势）：窗口最小、工程默认选择。但仍有一个极端时序会让旧值活下来——见下图；
  • 更新 DB 的同时"更新"缓存：看似一步到位，实则两宗罪：并发双写时网络乱序会让缓存停在先写的旧值上（永久不一致），且写多读少场景全是无效写（写放大）。结论：删除优于更新——删除幂等、天然 lazy loading，用到时再算。

延迟双删：低成本补救

针对旧值回填，最便宜的补刀是延迟双删：写完 DB 后，延迟一段时间再删第二次，把窗口内被回填的旧值清掉：

1

第一删：更新 DB 前先删一次（或直接走标准姿势省略这步），拦截马上要发生的旧值回填；

2

更新 DB：事务提交，真实状态落库；

3

第二删（延迟）：延迟取值 = 业务读链路 p99 耗时 + 主从延迟（读走从库时必须算上，否则删了个寂寞）+ 缓冲，典型 500ms~1s。第二删必须可重试、可观测——它失败的那一刻，兜底就只剩 TTL 了。

03架构选型：五种方案一张表

方案没有最好，只有与业务容忍度、写入口数量、团队能力匹配。先看全景再下结论：

方案不一致窗口业务侵入运维成本适用场景
Cache-Aside + 短 TTL ≤ TTL（分钟级） 极低 极低 默认选择；所有方案的必叠底层
+ 延迟双删 ≈ 延迟值（秒级） 低（写路径改造） 低 写入口收敛在应用内、可接受秒级窗口
binlog 订阅删除（canal / Flink CDC） 消费延迟（百 ms~秒级） 零侵入 中（多一条链路要维护） 中大型系统终态；写入口多（含 DBA/批处理）
删除 + 异步重建 小（重建期间） 中（需消息队列） 中 缓存值计算昂贵的聚合数据
强一致（分布式锁 / 版本号 CAS） ≈ 0 高 高 金融余额、库存扣减等不可出错的少量关键数据
选型三问（架构评审必答）① 业务能容忍多久不一致？——答案就是 TTL 与方案档位的分界线；② 写入口有几个？只有应用写 → 双删够用；DBA 改数、定时任务、多系统共写库 → 只有 binlog 订阅能全覆盖；③ 读走不走从库？走从库时，双删的延迟、binlog 消费都要把主从延迟算进窗口，否则一切兜底都会被从库旧快照击穿。

04实战：双删代码与 binlog 链路

延迟双删（Spring 写法，含重试）

@Service
public class ProductCacheService {
    private final RedisTemplate<String, Product> redis;
    private final ProductMapper productMapper;

    public void updateProduct(Product p) {
        String key = "product:" + p.getId();
        redis.delete(key);                            // ① 第一删
        productMapper.update(p);                      // ② 更新 DB（事务提交）
        // ③ 第二删：读 p99 500ms + 主从延迟 300ms + 缓冲 200ms
        CompletableFuture.delayedExecutor(1000, TimeUnit.MILLISECONDS)
            .execute(() -> retryableDelete(key, 3));
    }

    void retryableDelete(String key, int retries) {
        try { redis.delete(key); }
        catch (Exception e) {
            if (retries > 0) retryableDelete(key, retries - 1);
            else deadLetterQueue.offer(key);       // 死信队列 + 告警，别静默吞掉
        }
    }
}
⚠️ 两个常踩的坑延迟双删的"延迟"不是拍脑袋常数：读走从库而延迟小于主从延迟时，第二删删完，从库还没同步，读请求照样回填旧值。另外第二删别用固定线程池 Thread.sleep 阻塞实现——高写入下线程池会被拖垮，用调度线程池或 MQ 延迟消息。

binlog 订阅：终态架构

删除逻辑从所有业务写路径中剥离，统一由 binlog 消费者执行。要点：canal 挂在从库上拉 binlog（别给主库添乱）；Kafka 分区键用 表名+主键，同一行的变更保序消费；消费者幂等（重复 DEL 无害）；上线前做全量预热，避免缓存冷启动打穿 DB。监控三件套：binlog 消费延迟、删除失败率、低峰期抽样比对（随机抽 key 比对缓存值与 DB 值，不一致率超阈值告警）——这是唯一能证明"一致性真的成立"的手段。

✅ 一致性设计检查清单

☐ 写顺序 = 先更新 DB 再删缓存（绝不用"更新缓存"）　☐ 所有缓存必设 TTL（最终兜底）　☐ 延迟双删的延迟 ≥ 读 p99 + 主从延迟　☐ 第二删有重试 + 死信告警　☐ 写入口 > 1 个就上 binlog 订阅　☐ 消费延迟与删除失败率有监控　☐ 有抽样比对巡检　☐ 金融级数据不走缓存或加版本号校验

05今日要点

  • 一致性问题的本质：两个独立存储无原子操作，任何"两步写"都有并发窗口。目标是把窗口压到业务可容忍的范围，而不是消灭它——先问业务"能忍多久"，再选方案。
  • 标准姿势 = 先更新 DB 再删缓存，删除优于更新：删除幂等、天然 lazy loading；"更新缓存"有并发写乱序（永久不一致）和写放大两宗罪，默认不用。
  • 延迟双删是低成本补救：延迟取值 = 读链路 p99 + 主从延迟 + 缓冲（典型 500ms~1s）；第二删必须可重试、可观测，失败进死信队列。
  • binlog 订阅是终态方案：业务零侵入、覆盖应用/DBA/批处理所有写入口、以 DB 真实状态为准；代价是一条要维护和监控的链路（消费延迟、删除失败率）。
  • TTL 永远是最后防线：所有方案都要叠加 TTL 兜底，再配抽样比对巡检证明一致性成立；金融余额类数据要么不进缓存，要么加版本号 CAS。

06架构师思考题

题目一：团队里有人说"我们用了先更新 DB 再删缓存的标准姿势，所以不需要 TTL 了，缓存可以永久有效"。这个论断哪里站不住？如果要彻底堵死旧值回填，你会怎么设计？▶ 点击展开解析

🔍 为什么标准姿势也离不开 TTL

02 节的时序图已经给出反例：读请求 ② 在写事务 ③ 之前读了旧值，而它的回填 ⑤ 发生在删除 ④ 之后——这次 DEL 删的是"回填前"的缓存，旧值是在删除之后才落地的。这个时序要求一次读操作同时"起跑早于整个写事务、回填晚于删除"，概率很低，但在高 QPS 长期运行下必然发生（概率 × 时间 = 必然）。一旦发生且无 TTL，旧值将永久存活——不是"晚到的一致"，是"永不到的一致"。所以 TTL 不是可选项，它是把不一致窗口从"无限"压到"有上界"的唯一保证；标准姿势只是让"TTL 到期前"的窗口尽量小。

✅ 彻底堵死的三层设计

  • 第一层（缩短窗口）：延迟双删。第二删把绝大多数窗口内回填的旧值清掉，延迟按"读 p99 + 主从延迟"取值，覆盖常规时序；
  • 第二层（兜底极端时序）：binlog 订阅。DB 的 binlog 是最终真实状态：即便旧值回填成功，它对应的 UPDATE 事件也会再触发一次 DEL——除非 binlog 消费挂了，否则旧值活不过消费延迟。这一层与业务代码时序完全解耦，所以能覆盖应用侧无法预知的并发交错；
  • 第三层（保险丝）：TTL + 抽样比对巡检。TTL 保证前两层全失效时窗口仍有上界；低峰期随机抽 key 比对 DB 与缓存值，不一致率异常说明前两层出了问题——它是整个体系的"体检"手段，没有它你永远不知道一致性是否真的成立。

结论："标准姿势"解决的是概率，TTL 解决的是上界，binlog 解决的是确定性，巡检解决的是可证性——四者是互补关系，不是替代关系。

🔍 并发双写的乱序事故

设商品价格初始为 100，两个运营几乎同时改价：A 改成 150，B 改成 120。DB 层面两个 UPDATE 都加行锁，最终落库顺序是 A 先 B 后，DB 终值 = 120（后写覆盖，正确）。但缓存走的是各自应用进程的网络请求，DB 提交顺序 ≠ 缓存写入到达 Redis 的顺序：完全可能出现"B 的 SET 120 先到、A 的 SET 150 后到"——缓存终值 = 150，DB 终值 = 120，永久不一致，且没有任何报错。更糟的是：回填读请求也可能参与竞争（读到 120 回填，覆盖 A 刚写的 150），三方乱序后你甚至无法推断缓存里现在是什么。

✅ 删除为什么免疫

  • 幂等性：DEL 执行一次和执行三次结果相同。A 删、B 删、A 再删——缓存始终是"没有值"，下一个读请求回源 DB 拿到的一定是行锁串行化后的已提交终值。删除操作没有"值"这个竞争资源，乱序无意义；
  • lazy loading：删除意味着"用到时再算"，写多读少场景下大量被更新的缓存根本没人读——更新缓存是纯浪费的写放大，删除则什么都不做；
  • 复杂度：缓存值常是多表聚合计算的结果（商品页 = 商品 + 库存 + 价格 + 活动），"更新缓存"要把这套计算逻辑搬到写路径里，链路越长越容易和 DB 计算漂移；删除让读路径独占这套逻辑，单一事实来源。

唯一例外：写后立刻要读的热点 key（比如首页榜单），删除会带来一次回源毛刺，此时用"删除 + 延迟异步重建"或 binlog 驱动的"订阅更新"（由单一消费者串行执行，天然保序）来兼顾——但这是对删除语义的工程增强，不是回到"业务代码各自更新缓存"。
