Redis 持久化机制：RDB vs AOF 的架构权衡

📅 2026-08-17（周一） ⚡ Redis 系列 · 第 2 讲 ⏱ 预计阅读 10 分钟 🎯 持久化 / RDB / AOF / 混合持久化

一、从一个真实的故障场景说起

凌晨 2 点，某电商平台的缓存集群主节点因宿主机内存故障宕机。哨兵 30 秒内完成了主从切换，业务看似无感。但 5 分钟后，运营侧反馈：商品详情页的库存计数全部归零。排查后发现，该集群只开了 RDB 快照，最后一次成功快照是 29 分钟前，切换后从库基于旧快照提供服务，近 30 分钟的库存变更全部丢失。

这个案例引出今天要回答的核心问题：

  • RDB 和 AOF 各自的原理与代价是什么？
  • 什么业务场景必须用 AOF，什么场景 RDB 就够？
  • Redis 7 的混合持久化解决了什么问题？
  • 作为架构师，如何做容量规划和参数权衡？
⚠️ 架构师的第一性原理 Redis 的持久化不是为了替代 MySQL，而是为了缩短故障后的恢复窗口。先明确"你能容忍丢多少数据"（RPO），再谈选型——这是所有权衡的出发点。

二、RDB 快照：某一时刻的全量内存镜像

核心机制：fork + 写时复制（COW）

RDB 通过 BGSAVE 生成紧凑的二进制快照文件。主进程 fork() 出子进程，子进程遍历内存生成 RDB；期间主进程继续服务写请求，依赖操作系统的写时复制（Copy-On-Write）保证父子进程内存隔离。

Redis 主进程
持续处理读写命令
响应客户端请求
→ fork() →
子进程 bgsave
遍历全量数据
生成紧凑二进制 RDB
→ 写入 →
dump.rdb
全量快照文件
恢复快 · 文件小
写时复制（COW）：主进程修改某页数据时，OS 才复制该内存页 → 子进程看到的是 fork 瞬间的数据视图

触发方式与关键配置

# redis.conf — 自动触发条件（任一满足即 BGSAVE）
save 3600 1      # 1 小时内至少 1 次修改
save 300 100    # 5 分钟内至少 100 次修改
save 60  10000  # 1 分钟内至少 10000 次修改

stop-writes-on-bgsave-error yes  # 快照失败时拒绝写入（保护数据一致性的兜底）
rdbcompression yes            # LZF 压缩，CPU 换磁盘空间

# 手动触发
redis-cli BGSAVE   # 异步，生产环境用这个
redis-cli SAVE     # ⚠️ 同步阻塞主线程，生产禁用
⚠️ 生产坑点：fork 的隐形成本

1. fork 瞬间阻塞：实例越大，页表复制越慢。16GB 实例 fork 耗时约 100~200ms，期间所有请求排队——大实例抖动的常见元凶。

2. COW 内存放大：bgsave 期间若写入量大，被复制的内存页会额外占内存。极端情况下（全量热数据被改写）内存占用翻倍，触发 OOM 或 maxmemory 驱逐。经验值：bgsave 期间预留 20%~30% 内存余量。

3. 云上机器关 THP 需谨慎：透明大页（THP）会让 fork 延迟放大 2~5 倍，但关闭后常规内存操作开销略增，需压测评估。

三、AOF 日志：先执行后记录的命令流

核心机制：写前执行 + 三种 fsync 策略

AOF 以 RESP 协议格式追加每一条写命令。与传统 WAL（先写日志后执行）相反，Redis 是先执行命令、成功后才写 AOF——日志里天然没有语法错误，恢复时逐条重放即可，无需回滚机制。

① 客户端写命令
SET k v / INCR ctr
→
② 主进程执行
修改内存数据
→
③ 追加 aof_buf
协议格式化后进入缓冲区
→
④ fsync 策略
always / everysec / no
everysec 策略下：后台线程每秒 fsync 一次 → 最多丢 1 秒数据（主线程阻塞时后台线程会主动上报并放弃本次 fsync）
# redis.conf — AOF 核心配置（Redis 7+ 多文件结构）
appendonly yes
appendfilename "appendonly.aof"
appenddirname "appendonlydir"   # Redis 7: manifest + 增量 + 基础文件分目录管理

appendfsync everysec   # 生产默认；always 最多丢 0 秒但吞吐降 ~60%

# AOF 重写（BGREWRITEAOF）触发阈值
auto-aof-rewrite-percentage 100  # 当前大小比上次重写后大一倍
auto-aof-rewrite-min-size     64mb # 且至少 64MB，避免小文件频繁重写

# Redis 7 混合持久化（强烈推荐开启）
aof-use-rdb-preamble yes  # 重写时基础文件 = RDB 格式，增量 = AOF 命令流

AOF 重写：解决文件无限膨胀

命令追加意味着 AOF 会记录 INCR ctr 十万次——但当前值只是一个数字。BGREWRITEAOF 同样 fork 子进程，根据当前内存数据生成最小命令集，把十万条 INCR 压缩成一条 SET ctr 100000。重写期间的新写入存入 aof_rewrite_buf，重写完成后再追加到新文件，保证不丢数据。

💡 Redis 7 的多文件 AOF 结构 Redis 6.x 及之前，重写期间要同时维护"aof_buf + 重写缓冲区"双缓冲，高写入场景下重写结束后的追加残留命令可能阻塞主线程数百毫秒。Redis 7 改为manifest 清单 + base 基础文件 + incr 增量文件：重写期间新命令直接写新的 incr 文件，不再需要"追写"旧数据，彻底消除了这一阻塞点。升级 Redis 7 是解决 AOF 重写抖动的根本手段。

四、架构师视角：对比、选型与容量规划

维度 RDB AOF
数据安全（RPO） 丢失最后一次快照后的全部数据（分钟级） everysec 最多丢 1 秒；always 丢 0 秒
恢复速度 直接加载二进制镜像，快（10GB 约 1~2 分钟） 逐条重放命令，慢（同量级可能 5~10 倍时长）
文件大小 紧凑压缩，约为内存的 50%~80% 命令流格式，重写前可达数倍
性能影响 fork 瞬间阻塞 + COW 内存放大 everysec 几乎无感；always 吞吐下降明显
可读性 / 可修复性 二进制不可读 文本可读，redis-check-aof --fix 可截断修复
典型场景 纯缓存、冷备份、跨机房种子数据 计数器、去重、限流、分布式锁等有状态业务

选型决策树

问题：数据丢了能从哪找回来？
先问 RPO，再问恢复时间 RTO
可全量重建（DB 兜底）

甚至关持久化 + 主从高可用
可容忍丢 1 秒

架构判断：如果业务要求 RPO = 0，说明数据不该只放在 Redis —— Redis 是缓存/内存数据库，不是系统的唯一事实源

生产推荐组合（Redis 7+）

# 有状态业务的标准生产配置
appendonly yes
appendfsync everysec
aof-use-rdb-preamble yes        # 混合持久化
save 3600 1                     # 保留 RDB 用于快速拉起 + 备份
auto-aof-rewrite-percentage 100
auto-aof-rewrite-min-size 4gb     # 大实例调大，降低重写频率

# 关闭主从复制期间的 AOF 重写互斥（避免复制积压与重写叠加）
no-appendfsync-on-rewrite no    # 保持 no：宁可写延迟抖动也不丢 fsync
⚠️ 容量规划红线

磁盘空间：AOF 目录预留 当前内存大小的 1.5~2 倍（重写期间新旧文件并存）；RDB 预留 1 倍。

内存余量：maxmemory 建议设为物理内存的 60%~70%，为 fork COW、重写、复制缓冲留余量。

监控指标（Prometheus + redis_exporter 重点告警项）：

  • latest_fork_usec 持续 > 50ms → 实例过大，考虑拆分
  • aof_delayed_fsync 增长 → 磁盘 IO 瓶颈
  • rdb_last_bgsave_status / aof_last_bgrewrite_status 非 OK → 立即告警
  • current_cow_size → COW 放大实时监控（Redis 6.0+）

五、排障实战：三个真实案例的定位路径

案例 1：每隔几小时业务延迟毛刺 200ms

# 1. 查 fork 耗时趋势
redis-cli INFO persistence | grep latest_fork_usec
# latest_fork_usec:185000   → 185ms！fork 是元凶

# 2. 确认是否 COW 放大（Redis 6.0+）
redis-cli INFO stats | grep current_cow_size

# 3. 处置：实例拆分（大Key治理 + 按业务域拆 4 个 4GB 实例）
#    fork 从 185ms 降至 ~40ms，毛刺消失

案例 2：重启后 AOF 加载数小时未完成

# 加载期间 tail 日志：
# * Reading RDB base file on AOF loading... (fast)
# * Reading incremental AOF... 持续 3 小时未完成

# 根因：incr 文件 28GB（长期未重写，命令流膨胀）
# 处置（换从库加载验证）：
redis-check-aof appendonly.aof.1.incr.aof          # 校验完整性
redis-check-aof --fix <file>                # 截断损坏尾部
# 之后：开启混合持久化 + 调低 rewrite-min-size，重写后 base=RDB，加载恢复到分钟级

案例 3：主从切换后从库数据比主库"新"

主库 maxmemory 触发驱逐 → 部分热 Key 被淘汰 → 从库异步复制 DEL 命令晚于本地读取。这是复制与持久化无关的另一层一致性陷阱：持久化保住"磁盘上的数据"，但保不住"内存里被策略驱逐的数据"。若 Key 不可丢，用 noeviction + 容量规划，而不是全keys-lru。

六、今日要点

1
RDB = 全量镜像，AOF = 命令流
RDB 靠 fork+COW 生成紧凑快照，恢复快但丢数据多；AOF 追加写命令，丢得少但恢复慢。两者不是二选一。
2
RPO 决定选型
先问"能容忍丢多少数据"：纯缓存用 RDB（甚至关闭），有状态业务用混合持久化 + everysec，RPO=0 的数据不该只放 Redis。
3
fork 是隐形成本
实例越大 fork 越慢、COW 放大越猛。大实例（>10GB）建议拆分，监控 latest_fork_usec 与 current_cow_size。
4
混合持久化是生产标配
Redis 7 的 aof-use-rdb-preamble：base=RDB（快速加载）+ incr=AOF（秒级丢失窗口），兼得两者优点。
5
磁盘与内存双预留
AOF 目录预留 1.5~2 倍内存空间，maxmemory 设物理内存 60%~70%，为重写和 COW 留余量。

七、架构师思考题

Q1你的 Redis 集群使用 everysec + 混合持久化，但磁盘 IO 出现周期性打满，导致 aof_delayed_fsync 持续增长。请分析可能的原因，并给出短期止血与长期治理方案。 ▶

定位：为什么 aof_delayed_fsync 会增长

everysec 的后台线程每秒执行 fsync；若上一次 fsync 超过 2 秒仍未完成（磁盘忙），主线程会感知到并记一次 aof_delayed_fsysnc，同时放弃本次写盘（数据仍缓存在 aof_buf，最多丢 2 秒）。所以该指标增长 = 磁盘跟不上写入速率。

可能原因（按概率排序）

  • AOF 重写窗口叠加：重写期间子进程写新 AOF 与后台线程 fsync 旧 AOF 并发，IO 翻倍，这正是周期性打满的典型模式——周期 ≈ 重写触发间隔。
  • 磁盘带宽不足或混部：Redis 数据目录与 MySQL/日志采集等 IO 大户共盘，或使用低 IOPS 的云盘（如吞吐型而非高 IOPS 型）。
  • 写入放大：大量小命令（INCR/HSET 单字段）使 fsync 的有效数据密度低，元数据开销占比高。
  • 操作系统页缓存争用：dirty page 回写策略（vm.dirty_ratio）过于激进，内核批量刷盘挤占 Redis 的 fsync。

短期止血

  • 临时关闭自动重写（auto-aof-rewrite-percentage 设 0），改为业务低峰期手动 BGREWRITEAOF；
  • 调小 vm.dirty_bytes（如 64MB）平滑内核刷盘，避免瞬时 IO 风暴；
  • 若混部，立即迁移 Redis 到独立云盘（优先 SSD/ESSD PL1 及以上）。

长期治理

  • 升 Redis 7+：多文件 AOF 消除重写期间的双缓冲追写；混合持久化让 base 为 RDB，重写产物更小；
  • 重写错峰调度：多个实例的重写窗口用脚本/平台错开，避免同时 fork + 重写叠加；
  • 写入侧优化：客户端 pipeline/批量命令提升单次 fsync 的数据密度；评估部分业务改写 RDB-only；
  • 容量与告警：对 aof_current_size 增长速率建模，提前扩容 IO；aof_delayed_fsync 增速 > 1 次/分钟即告警。
Q2团队争论：缓存场景下"开 AOF 增加成本，不如纯 RDB + 主从 + 快速预热"。你作为架构师如何裁决？什么信号出现时必须补开 AOF？ ▶

裁决框架：先分类数据，再谈统一配置

"缓存场景"往往不是纯缓存——同一个实例里通常混着三类数据：可重建的缓存数据（商品信息，DB 有源）、半状态数据（计数器、布隆过滤器、去重集合，重建代价高但可近似）、真状态数据（分布式锁、令牌、幂等表，丢失即故障）。争论的错误在于用一把尺子量所有数据。

支持"纯 RBD + 主从"的合理性

  • 若实例内 95% 以上是可从 DB 重建的缓存，AOF 的 everysec fsync 是纯粹的额外成本（IO、重写抖动、运维复杂度）；
  • 主从 + 哨兵/Cluster 已覆盖单点故障，RDB 足以支撑冷备与快速拉起；
  • 缓存雪崩防护（预热脚本 + 多级缓存）比持久化更对症。

必须补开 AOF 的信号

  • 出现无源数据：任何 Key 的"事实源"只存在于 Redis（如限流窗口、分布式锁的 owner 标记、幂等去重集）——RDB 的分钟级丢失窗口会直接造成超卖/重复请求；
  • 重建成本不可接受：预热需要小时级全表扫描（DB 已是高压），丢 30 分钟数据意味着 DB 要扛住重建风暴；
  • 审计/合规要求：需要证明恢复点精确到秒；
  • 出现过切换丢数据事故：复盘结论指向快照间隔内的丢失。

推荐落地方案

  • 物理分离：纯缓存实例（RDB-only 甚至关闭持久化）与状态数据实例（混合持久化 + everysec）分开部署，互不影响、成本清晰；
  • 状态数据下沉：能搬到 DB/磁盘 KV 的强一致数据不要留在 Redis，Redis 只做加速层——这是比 AOF always 更根本的答案；
  • 治理动作：给"状态 Key"建立命名规范与登记机制（如 state:* 前缀），让数据分类可审计，避免下次再靠争论裁决。
