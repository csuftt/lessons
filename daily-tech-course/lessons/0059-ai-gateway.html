AI 网关：LLM 流量的入口、账房与保险丝

公司三十个团队各自接模型 API，密钥散落代码仓库、账单月底才见真章、供应商一限流全站陪葬——这是多数公司 AI 落地的现状：Kong 平台口径的企业 AI 流量九个月涨了七倍，而其中只有不到 1% 的组织部署了任何 AI 专项治理。这一讲从 2026 年 3 月 24 日那次真实的 AI 网关供应链投毒事件讲起（40 分钟毒包窗口、官方镜像因锁版本幸免、披露 36 小时后 SQL 注入就被在野利用），把 AI 网关的三顶帽子讲透：入口（统一端点与协议适配）、账房（token 计费、预算与缓存）、保险丝（fallback、限流与内容治理）——以及它自己成为高价值靶子之后，你的部署姿势为什么决定你是幸存者还是受害者。

01场景：40 分钟毒包，36 小时打表

事故一：AI 网关被供应链投毒，谁中招了？

2026 年 3 月 24 日 10:39（UTC），开源 AI 网关 LiteLLM 的 v1.82.7 被推上 PyPI，v1.82.8 随后跟上——这两个包不是官方发布流程的产物：攻击者污染了 CI 流水线里的安全扫描器依赖（Trivy），偷走静态存放的发布凭据，绕过官方 CI 直接向 PyPI 投毒。毒包里带了一个凭据窃取器：扫描环境变量、SSH 私钥、云厂商凭据、K8s ServiceAccount 令牌、数据库密码，加密后回传到一个仿冒域名。两个包在 PyPI 上存活了约 40 分钟后被隔离，当天 16:00 被彻底删除。

谁中了招？官方给出的判定清单像一份部署姿势考试：用 pip install litellm 不锁版本、恰好在那个窗口升级的——中招；让依赖把它间接拉进来的（AI 编排框架、MCP server 常这么干）——中招；而跑官方 Docker 镜像的团队全部幸免，因为镜像在 requirements.txt 里锁死了依赖版本，根本不碰 PyPI 上的毒包。三天后官方请来 Mandiant 与白帽团队做代码审计，砍掉约 6000 个开放分支、发布凭据全部改临时凭据、镜像全部 cosign 签名——这是这个项目一生中最贵的一次安全补课。

事故二：披露 36 小时后，攻击者开始精确打表

同年 4 月，同一产品的代理鉴权路径被报出 SQL 注入（CVE-2026-42208，CVSS 9.3）：未认证攻击者构造一个 Authorization 头，就能经由错误处理路径触达数据库查询。Sysdig 威胁研究团队观测到公告发布 36 小时 07 分钟后出现首次利用尝试——且不是无差别的扫描器 spraying，而是对生产库表的定向枚举，直奔三张高价值表：虚拟密钥表、供应商凭据表、环境变量配置表。为什么打得这么准？因为 AI 网关的数据库里躺着全公司所有模型供应商的真实密钥。

两起事故的公共结论

AI 网关把"每个团队各自保管一把模型密钥"收敛成"一个集中保管箱"——这正是它的价值，也精确地重铸了它的风险：网关一旦被攻破，全公司的模型账户、全部经过网关的 prompt（常含客户数据与内部代码）、全部调用配额一次性暴露。它的安全等级必须对标密钥管理系统，而不是"一个内部转发工具"。

02原理：LLM 流量不是普通 HTTP

五点不同，决定了 API 网关不能直接复用

传统 API 网关的四层防线（路由、认证限流、熔断降级、观测——0026 期之前的 Spring Cloud Gateway 一讲已展开，此处不重讲）解决的是"请求进、响应出"的同步语义。LLM 流量在这个模型上有五处对不上：

  • 响应是流：SSE 逐 token 吐出，一次回答几十秒、连接全程挂着——网关不能缓冲完整个响应再转发，超时、重试、日志的语义全部要按"流"重写；
  • 计费按 token：成本藏在响应体的 usage 字段里，同一个请求贵模型与便宜模型差一到两个数量级——"记条访问日志"升级成"逐请求计费记账"；
  • 路由键是模型名：同一个端点，model 字段决定去哪家供应商——路由决策从"路径"变成"模型目录 + 策略"；
  • 上游是外部依赖：模型供应商会宕机、会限流、会涨价、会下线旧版本——fallback 与多供应商冗余不是高可用选项，是日常操作；
  • 载荷是敏感数据：prompt 里混着客户信息、源码、内部工单——脱敏、审计留存、合规边界都长在载荷上。

由此收敛出 AI 网关的五件事

把五点不同翻成能力清单：应用与 Agent 只对接一个统一端点（事实标准是 OpenAI 兼容协议），网关在中间做认证与虚拟密钥、模型路由与 fallback、token 计费与预算、语义缓存、内容治理（guardrails 与审计），北向是各家公有模型与自建推理集群。落到组织里，它同时是三顶帽子：入口（协议适配与模型目录）、账房（每一分模型钱记到团队头上）、保险丝（上游出事时业务不断电）。

关键不变式：供应商真实密钥只在网关侧存在，业务与 Agent 拿到的是可撤销、带预算、带模型白名单的虚拟密钥——这是"入口"这顶帽子的安全内核，也是事故二里攻击者直奔密钥表的原因：那里是全公司的钥匙串。

03架构设计：选型、密钥与三笔账

形态选型：三条路线

维度独立 AI 网关（以 LiteLLM 为例）API 网关 + AI 插件（以 Kong 为例）云托管入口
定位LLM 优先：路由/预算/缓存开箱即用API 体系优先：AI 是插件之一跟云账号走，零运维
优势模型目录更新快（新模型 day-one 支持）、虚拟密钥与预算体系完整复用既有网关的认证限流观测体系；治理面统一几分钟上线
代价多养一个组件，安全责任自负（本期两起事故就是它）AI 深能力（语义缓存、预算台账）弱于专业网关锁定供应商；策略与审计受平台边界限制
适合模型团队主导、多供应商混用已有成熟 API 网关团队验证期、单云架构

两条路线正在互相靠近：Kong 自 3.14 起补齐 A2A 流量治理与 token 交换，LiteLLM 也在加 MCP 网关能力——但选型的第一判据仍是你团队原本的治理资产在哪一侧，而不是功能清单谁长一行。

密钥与预算：账房的核心账本

虚拟密钥体系三件事：主密钥只做发钥匙一件事（不进应用、不进 CI、进密钥管理系统）；业务密钥=身份+预算+模型白名单（"客服团队、月预算 2 万、只许调中小档模型"是一条密钥的全部定义）；预算三级记账（key / team / 月度总额），超预算在网关侧熔断而不是等月底账单。配套纪律：供应商真实密钥季度轮换——它在网关侧集中存放，轮换成本是"一处换、全网关生效"，这是集中保管箱相对"密钥散落 11 个仓库"的唯一正收益，不用白不用。

容量与高可用：保险丝的物理实现

  • 网关自身不能是新的单点：多副本 + 无状态化（配置与台账进数据库/Redis），前置负载均衡照旧——网关挂了等于全公司 AI 断电，它的可用性目标要高于任何一个单一业务。
  • 流式响应的重试是语义雷区：SSE 已经吐了一半的请求挂了，盲目重试等于把同一段生成再买一遍单（重复计费 + 用户看到重复内容）。正确姿势：重试只发生在首 token 之前；流中断的处理交给客户端续跑（Agent 编排层的检查点机制，0047 期已讲）。
  • fallback 按模型对配置：主路由打满或供应商 5xx，降级链是"同档备用供应商 → 低一档模型 → 排队或拒绝"；降级触发的告警要单独分级——它意味着用户正在悄悄拿到质量更差的回答。

省钱三板斧：精确缓存、语义缓存、模型分层

精确缓存（请求逐字节相同直接返回）便宜但命中率低，作 L1。语义缓存作 L2：把请求向量化，相似度过阈值直接返回旧答案，整次模型调用被跳过——公开口径的收益区间为 40%~86%（AWS ElastiCache 评估：阈值 0.75 时命中率 90.3%、成本降 86%；GPT Semantic Cache 论文：命中率 61.6%~68.8%、正向命中准确率超 97%）。但"相似"不等于"相同"：有团队上线后用户问"北京明天天气"，命中了"北京今天晴"的缓存——时间敏感、个性化、带随机上下文的问题一律是语义缓存的禁区，阈值也要分查询类调（技术问答 0.92 起步，代码/法律/医疗 0.95 以上）。模型分层路由是第三板斧：难任务走贵模型、简单任务走便宜模型，路由策略下沉淀在网关，业务无感知。三者叠加，才配得上"账房"这个名字——只记账不省钱的账房只是日志系统。

04实战：三段可落地的骨架

第一段：网关配置——虚拟密钥、预算与 fallback

# config.yaml(LiteLLM 骨架,策略同样适用于其他网关)
model_list:
  - model_name: chat-main            # 业务侧看到的模型名(路由键)
    litellm_params:
      model: openai/gpt-5.5-mini
      api_key: os.environ/OPENAI_KEY # 真实密钥只从环境/密钥管理系统注入
  - model_name: chat-main
    litellm_params:
      model: anthropic/claude-sonnet-5.5   # 同名双部署 => 天然 fallback
      api_key: os.environ/ANTHROPIC_KEY

router_settings:
  num_retries: 2
  allowed_fails: 3            # 连续失败后摘除该部署,冷却再回
  fallbacks: [{"chat-main": ["chat-cheap"]}]

general_settings:
  master_key: os.environ/MASTER_KEY   # 主密钥只管发钥匙,不进任何应用

业务侧申请虚拟密钥：/key/generate 带 max_budget（月预算）、models（白名单）、team_id（记账归属）——一条密钥即一份权限与预算契约，撤销即失效，不用去供应商控制台删 key。

第二段：语义缓存的启用边界（先圈禁区，再谈收益）

litellm_settings:
  cache: true
  cache_params:
    type: redis                 # L1 精确缓存(Redis)
    ttl: 86400
# 语义缓存按命名空间启用,只给"意图聚类明显"的流量开:
#   客服 FAQ / 文档问答        -> 开,历史口径命中率 60%+
#   代码助手 / 长文摘要        -> 关,个性化上下文为主,误命中代价高
# 禁区清单(写进评审 checklist):
#   时间敏感(行情/天气) 个性化(用户上下文) 强随机性(创意生成)

上线顺序建议：先只开精确缓存观察一周（命中率数据决定语义层值不值得养），语义层再按命名空间灰度。每一路缓存都要能回答：误命中一次的业务代价，省下的 token 钱扛不扛得住——这是缓存策略里唯一的判断式。

第三段：部署加固——让"下一个 3·24"发生在别人身上

# 1. 锁版本 + 官方镜像基线(毒包事件的幸存者姿势)
#    Dockerfile: FROM ghcr.io/berriai/litellm:v1.105.0   # 不用 latest
# 2. 验签:官方镜像自 1.83 起全部 cosign 签名
cosign verify --key <官方仓库>/cosign.pub ghcr.io/berriai/litellm:v1.105.0
# 3. 出口白名单:容器只许访问配置过的模型供应商端点
#    (窃取器的回传域名连不上,泄密链路从物理上断)
# 4. 升级通道:安全公告进值班群,高危 CVE 48 小时内评估
#    每月演练一次:拔掉一个供应商密钥,看 fallback 是否真的接得住

四条加固各自对应一个真实攻击面：锁版本防投毒、验签防调包、出口白名单防外传、升级通道防"披露 36 小时后"的那种精确打击。AI 网关的运维手册第一页应该写着：你是全公司模型资产的保管箱，攻击者的工时是按你的密钥价值定价的。

05今日要点

  • AI 网关=入口+账房+保险丝：统一端点与协议适配、虚拟密钥与 token 计费预算、fallback 与内容治理——LLM 流量的五点特殊（流式、按 token 计费、模型名路由、外部上游、敏感载荷）决定了传统 API 网关不能直接复用。
  • 集中保管密钥是价值也是靶心：3·24 供应链事件里官方 Docker 镜像因锁依赖幸免、pip 不锁版本中招；SQL 注入披露 36 小时就被定向打表——部署姿势（锁版本/验签/出口白名单）决定你是幸存者还是受害者。
  • 账房要会省钱：精确缓存 L1 + 语义缓存 L2（公开收益 40%~86%，但时间敏感/个性化/强随机是禁区，阈值按查询类分层）+ 模型分层路由，三板斧叠加才是账房，只记账那是日志系统。
  • 流式重试是语义雷区：重试只许发生在首 token 之前；流中断的恢复交给 Agent 编排层的检查点，网关别越位替业务做"重新生成"的决定。
  • 选型看治理资产在哪侧：独立 AI 网关（模型团队主导）vs API 网关+AI 插件（已有网关团队）vs 云托管（验证期）——Kong 口径企业 AI 流量九个月涨七倍、不到 1% 组织有 AI 专项治理，先收口，再谈优化。

06架构师思考题

题目：三十个团队、两百把散落密钥、三家供应商——你的 AI 网关收编方案怎么设计？

背景：公司三十个团队各自接了模型 API，安全扫描发现两百把真实密钥散落在代码仓库、配置中心和本地环境文件里；月底账单总额没人说得清归属；上周供应商 A 大范围限流，三个核心业务陪葬。你主导 AI 网关收编，请回答：

① 两百把存量密钥的收编迁移怎么做？设计四步与每步的验收标准。
② 供应商 A 再限流的那天，网关该自动做什么、绝不做什么？
③ 复盘 3·24 式供应链事故：怎么保证毒包事件发生在你的网关身上时，你是幸存者？

🔍 深度解析

① 收编四步=盘点→镜像→切换→作废：（a）盘点——扫代码仓库与配置中心建立密钥清单（谁、哪个供应商、调哪些模型、大概什么量级），验收=清单覆盖度与扫描工具误报率；（b）镜像——在网关侧按清单建虚拟密钥（预算先设成该团队历史月均的 1.2 倍，模型白名单按实际调用记录生成，别拍脑袋），真实供应商密钥收进网关的密钥管理系统，验收=每把虚拟密钥都有 owner 与预算归属；（c）切换——按团队灰度切端点，双跑期旧密钥保留只读监控（对比网关侧计量与供应商账单的偏差），验收=计量偏差 <5%、无业务报障；（d）作废——去供应商控制台吊销全部旧密钥，这一步不可逆所以放最后，验收=控制台零遗留密钥、仓库扫描器连续两周零告警。关键节奏：先易后难，从内部工具类团队切起，核心交易链路最后动。

② 自动做的三件事与绝不做的两件事：自动——按 fallback 链切到供应商 B 与自建推理集群（响应头里带降级标记，让业务可感知）；对供应商 A 的调用预算自动收紧（故障期重试风暴是账单杀手，allowed_fails 摘除部署）；把限流事件按 P2 告警出去（降级=用户正在拿到质量更差的回答，不能静默）。绝不——绝不在流式响应中途自动重试（首 token 后中断交给业务层检查点续跑，网关重试=重复计费+重复内容）；绝不静默把请求无限排队（排队的延迟会吃掉业务的超时预算，宁可快速失败带明确错误码，让业务的降级逻辑有机会接手——0049 期重试预算的纪律在这里同样适用）。

③ 幸存者清单四条，每条对应一个攻击面：（a）锁版本+官方镜像——3·24 里幸存者的唯一共性是"部署路径不碰 PyPI 浮动版本"，私有镜像仓库同步固定 tag，验收=生产无 latest；（b）签名验证——cosign 验签进部署流水线，防"下一个仿冒域名"式的调包，验收=未验签镜像无法进集群（准入策略）；（c）出口白名单——网关容器只许访问配置过的供应商端点，凭据窃取器即使跑起来也传不出数据，验收=随机注入测试域名被拒；（d）升级演练——安全公告接值班流程，高危 CVE 48 小时内评估、每月一次"拔密钥看 fallback"演练，验收=演练记录与 fallback 实际生效时间。一句话总结：收编方案的安全下限不是网关产品的 CVE 记录，是你自己的部署姿势——集中保管箱的价值，一半在收口那天，另一半在每天的运维纪律里。
