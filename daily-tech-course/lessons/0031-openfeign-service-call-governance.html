SPRING CLOUD ALIBABA · Spring Cloud Alibaba 系列第 3 讲（微服务通信篇 · 服务间调用）

OpenFeign 服务间调用治理：把"能调通"变成"调得稳"

可观测性三件套（指标·追踪·日志）讲完，视线拉回服务之间：微服务架构里最频繁的跨进程动作就是服务间调用，而多数团队对它的全部治理是——"@FeignClient 注解一加，能调通就行"。这一讲从一次"下游虚机 GC 十秒、上游线程池被拖干"的雪崩复盘讲起：声明式调用只是入口，超时的三层结构、重试与幂等的攻守盟约、连接池的容量账，才是调用治理的主战场。你会看到一次加配置就能让吞吐翻倍、一次乱配重试就能让删库跑两次的微观机制，最后落到一套可以抄走的生产参数表。

01一次"下游 GC 十秒，上游全线雪崩"的复盘

某电商中台 40 个服务上线第一年，服务间调用用 OpenFeign 声明式接口，"能调通"阶段皆大欢喜。大促压测第一天，订单依赖的库存服务一台实例发生 Full GC，STW 十秒。预期剧本是：库存服务抖一下，调用方超时快速失败，熔断兜底；实际剧本是——订单服务的 Tomcat 工作线程被一条条挂在这台坏实例上，整整 60 秒。OpenFeign 的默认读超时就是 60 秒（feign.Request.Options 默认 connectTimeout=10s、readTimeout=60s，Spring Cloud OpenFeign 不改配置时原样继承）。线程池 200 个线程，QPS 800 的入口流量几分钟内把线程全部按在超时等待上，订单服务自身先雪崩，连不调用库存的接口也一起 503——故障像墨汁一样从一台虚机的 GC 日志晕染到半个中台。

复盘还有第二个发现：有团队"怕超时"，把一个 FeignClient 的重试打开了（Retryer.Default，最大 3 次）；压测时读超时一触发，慢查询下游收到的请求量直接 ×3，把快要恢复的服务再次压趴——重试是给瞬时故障的止痛药，对过载是兴奋剂。第三个发现更隐蔽：默认 HTTP 客户端是 JDK 的 HttpURLConnection，没有连接池，每次调用新建 TCP 连接，压测时 TIME_WAIT 堆了六万多个端口，吞吐被握手开销吃掉三分之一。

复盘结论：OpenFeign 的"零配置可用"恰恰是它最大的生产陷阱。声明式只是把 HTTP 调用写得像本地方法，而调用治理——超时、重试、连接池、隔离、可观测——一样都不能少。这一讲把这些默认值一个一个翻出来，讲清楚每层怎么改、改成多少、以及为什么。

02原理：一次 Feign 调用的分层结构与治理点

分层看清了，三个"默认值陷阱"就一目了然。第一，超时默认值对生产偏长：connect 10s/read 60s 是"互联网不可达也别摔程序"的宽容值，微服务内网调用里它意味着下游故障时线程要挂满 60 秒——线程是上游最稀缺的资源，超时的本质是用快速失败保护调用方自己的线程池。第二，默认不重试，且原版 Retryer.Default 不分 GET/POST：Feign 的重试发生在 ErrorDecoder 判定 retryable 之后、逐字节重发请求体——对非幂等接口（下单、扣款）开启它，等于给"超时但可能已成功"的调用再执行一次。第三，默认传输层是 JDK HttpURLConnection：每次调用新建 TCP 连接（内网还要完整三次握手），高并发下端口耗尽 + 握手开销；生产必须换 Apache HttpClient 5 或 OkHttp 走连接池。另外注意 Ribbon 已退役，实例选择在 Spring Cloud LoadBalancer 里——它默认不做重试，重试语义由 Feign Retryer 与 LB retry 配置共同决定，两处都配会叠加，这是新版本最经典的坑。

Spring Cloud OpenFeign 版本现状（2026-09 口径）

当前主版本线为 5.0.x（5.0.0 于 2025-11 GA，随 Spring Cloud 2025.1.x / Spring Boot 3.4+ 走，最新 5.0.3）；存量最多的 4.x 线仍在维护（4.3.3，2026-06）。命名空间统一在 spring.cloud.openfeign.*（3.x 时代的 feign.* 与 Ribbon 已成历史）。本期参数口径以 4.x/5.x 文档为准，两者在这些默认值上一致。Sentinel 适配器（SentinelFeignClient）在 SCA 新版本也已回归可用，熔断注解可直接盖在 FeignClient 上。

03架构设计：超时、重试与幂等的攻守盟约

超时：三层漏斗与预算分配

一次跨服务请求的完整耗时 = 连接建立 + 服务端处理 + 网络往返（± 重试放大）。治理铁律：上游超时预算 = 下下游预算 + 本级余量，从入口到最底层逐层递减，任何一层"抄默认"都可能把上层预算击穿。典型三层漏斗：网关（如 3s）→ 服务 A 的 Feign 调用（如 1.5s）→ 服务 A 里的数据库查询（如 800ms）。超时没有银弹数值，但它有两个属性是结构性的：连接超时要短（内网握手正常在毫秒级，超过 1~2 秒基本说明实例已不可用，快速放弃才能让 LoadBalancer 换实例）；读超时要参考下游 P99（压测拿到下游接口 P99，readTimeout 设在 P99~P99.9 之间，宁短勿长——超时是保护自己的，不是容忍别人的）。

重试的攻守盟约：重试只配在幂等接口上，非幂等接口的重试必须带幂等键走兜底对账。理由在于"超时 ≠ 失败"——读超时只说明调用方没等到响应，下游可能已提交成功；此时盲目重发就是重复执行。攻（什么时候重试）：GET 查询类接口、瞬时抖动（连接被拒、连接超时这类"请求大概率没到达"的错误）最适合重试，指数退避 + 少量次数（如 1~2 次）可以吃掉大部分秒级抖动。守（什么时候绝不重试）：写操作、读超时（请求已到达、结果未知）、下游已在过载熔断中（重试 = 补刀）。写操作的可靠性不靠传输层重试，靠业务幂等键 + 状态机 + 对账：请求携带唯一键，下游按键去重，超时后调用方查询结果决定重发还是放行——这与第 21 期 Pulsar 的 at-least-once + 幂等消费是同一个思想：分布式系统里"恰好一次"从来都是"至少一次 + 幂等"拼出来的。

参数默认值生产建议理由

容量三笔账（调用方 QPS 800、下游 3 实例、P99=500ms 场景）

线程账：入口 QPS 800 × 下游 P99 0.5s ≈ 并发驻留 400；若读超时放到 60s，一次下游挂起最多可驻留 800×60=48000 线程需求——200 线程的 Tomcat 池撑不过第二轮。超时收紧到 2s，最坏驻留需求 1600，线程池 + 快速失败就能扛住抖动。连接账：QPS 800、keep-alive 复用 + HC5 池 max-per-route 200 足够；若用默认 HttpURLConnection，每次调用一个新连接，800 QPS 就是每秒 800 次 TCP 握手 + 对应 TIME_WAIT，高峰端口表轻松破表。重试放大账：开 Retryer.Default(100ms,1s,3) 且全局生效，下游过载时收到的请求量 ×3，恢复窗口被拖长 2~3 倍——重试预算要算进下游容量（下游要按"峰值 × 重试系数"留余量），或者干脆把重试留给异步消息与对账。

04实战：一套可以抄走的生产配置

声明式接口：契约即文档

// 库存服务客户端：contextId 区分同服务多客户端；path 收拢公共前缀
@FeignClient(name = "stock-service", contextId = "stockQueryClient",
             path = "/api/stock", fallbackFactory = StockFallbackFactory.class)
public interface StockQueryClient {

    @GetMapping("/items/{skuId}")          // GET 查询：可重试
    StockVO getStock(@PathVariable("skuId") Long skuId);

    @PostMapping("/deduct")                // POST 扣减：绝不走传输层重试
    DeductResult deduct(@RequestBody DeductCmd cmd);  // cmd 携带幂等键 idempotentKey
}

全局 + 单服务超时：YAML 一段配齐

# application.yml —— default 全局兜底，服务名单独覆盖（优先级：服务名 > default > 代码 Bean）
spring:
  cloud:
    openfeign:
      client:
        config:
          default:
            connect-timeout: 2000        # 内网 2 秒连不上 = 实例大概率没了
            read-timeout: 3000           # 全局读超时，按最慢下游 P99 定
          stock-service:                  # 慢服务单独放宽（报表/导出类）
            read-timeout: 8000
      httpclient:
        hc5:
          enabled: true                   # 换掉 HttpURLConnection，走连接池
      # okhttp: { enabled: true }        # 二选一，OkHttp 同样池化
      compression:
        request: { enabled: true, min-request-size: 2048 }
        response: { enabled: true }

重试：只给幂等客户端开，且要认得出"值得重试"的错

// 只挂在查询类客户端的 configuration 上，绝不进全局组件扫描包！
public class StockQueryRetryConfig {
    @Bean
    Retryer queryRetryer() {
        // 首次重试等 200ms，指数退避封顶 1s，总共最多调 3 次（1 次 + 重试 2 次）
        return new Retryer.Default(200, TimeUnit.SECONDS.toMillis(1), 3);
    }
    // 配套 ErrorDecoder：只对"请求大概率未到达"的错标记 retryable
    // 连接被拒/连接超时 → retry；读超时/4xx/5xx → 不 retry（交给熔断与降级）
}

三个纪律：① 配置类不要放在 @SpringBootApplication 扫描包内，否则局部配置会泄漏成全局（文档原话：会被所有 client 共享）；② 开了 Feign Retryer 就不要再开 LoadBalancer 的 retry（spring.cloud.loadbalancer.retry.enabled），两处重试相乘，次数会平方级放大；③ 重试次数记进监控——重试率上升是下游恶化的前兆指标，比错误率更早报警。

fallback 与熔断：降级要"有内容"，不是"返回 null"

@Component
public class StockFallbackFactory implements FallbackFactory<StockQueryClient> {
    @Override
    public StockQueryClient create(Throwable cause) {
        return new StockQueryClient() {
            @Override public StockVO getStock(Long skuId) {
                // 降级读本地缓存/默认值，并埋点计数——降级是可用性换正确性的交易，要记账
                return stockCache.getOrDefault(skuId, StockVO.UNKNOWN);
            }
            @Override public DeductResult deduct(DeductCmd cmd) {
                // 写操作不降级：抛业务异常，交上游决策（挂起/稍后重试/转人工）
                throw new StockServiceUnavailableException(cmd.getIdempotentKey(), cause);
            }
        };
    }
}

用 FallbackFactory 而不是裸 fallback 的原因：能拿到触发降级的异常——它是排障的第一现场。写操作降级的正确姿势是"转异步 + 对账"：把扣减请求落本地消息表或发事务消息（联动第 21 期 Pulsar 延迟重试 + 死信），而不是编造一个"成功"。熔断层在 SCA 体系里用 Sentinel 盖在 Feign 资源上（@SentinelResource 或开启 feign.sentinel.enabled 自动适配），熔断参数怎么定量见第 1 期——本期的边界是"调用方怎么把超时、重试、降级摆成互相咬合的一套。

四个必踩的坑：① 同名 FeignClient 启动报错——两个客户端指向同一服务必须用 contextId 区分（子上下文名冲突）；② 局部 Retryer 配置类被组件扫描——本想给查询客户端开重试，结果全服务的写接口都开始重试，压测时下游请求量 ×3；③ Feign Retryer 与 LoadBalancer retry 叠加——3×3=9 次请求，下游还没恢复就被补刀打死；④ 超时改了代码 Bean 没改 YAML（或反之）——属性优先级是"YAML 服务名 > YAML default > @Configuration Bean"（default-to-properties 默认 true），两处都配时改了一处以为生效，实际被另一处覆盖。

✅ 上线体检清单

☐ 全局 connect/read 超时已显式配置（不裸奔默认 10s/60s），慢服务单独覆盖　☐ read-timeout 有下游 P99 依据，超时预算从网关到 DB 逐层递减不倒挂　☐ HTTP 客户端已换 HC5/OkHttp，连接池 max-per-route ≥ 调用方峰值并发　☐ Retryer 只存在于幂等客户端的局部配置，配置类在扫描包外　☐ Feign 重试与 LoadBalancer retry 只开一处　☐ 写操作接口有幂等键 + 超时后查结果再重发的对账路径　☐ fallbackFactory 有异常入参且降级动作有埋点　☐ 同服务多客户端已用 contextId 区分　☐ Micrometer 指标已接（feign.Client 调用时长/异常），重试率与超时率进了大盘　☐ 与 Sentinel 熔断的分工已明确：超时管单次、熔断管趋势、降级管兜底

05今日要点

  • 默认值是陷阱清单：connect 10s / read 60s 偏长、默认不重试、默认 HttpURLConnection 无连接池——"能调通"的三件默认配置在生产里各藏一颗雷，上线第一天就该显式重写。
  • 超时是保护自己的：本质是保护调用方线程池不被下游故障拖干；read-timeout 按下游 P99~P99.9 定、宁短勿长，超时预算从网关到 DB 逐层递减，任何一层抄默认都可能击穿上层。
  • 重试与幂等是攻守盟约：只在幂等接口 + "请求未到达"类错误上重试（1~2 次 + 指数退避）；读超时 = 结果未知，写操作靠幂等键 + 对账兜住——与消息队列"至少一次 + 幂等"同构。
  • 连接池是白捡的吞吐：换 HC5/OkHttp 开池化 + keep-alive，消掉每调一次握一次手的开销与 TIME_WAIT；池上限按调用方峰值并发配，过小会排队超时误判下游慢。
  • 超时/熔断/降级各管一段：超时管单次调用的止损，熔断（Sentinel，见第 1 期）管故障趋势的熔闸，降级管熔断后的兜底内容——三层咬合，缺一层雪崩剧本就会重演。

06架构师思考题

题目一：网关超时 3 秒，订单服务的下单链路是"订单 →（Feign）→ 库存 →（Feign）→ 营销"，库存 P99=300ms、营销 P99=450ms，DB 层 P99=150ms。① 给出这条链路的超时预算分配；② 大促前营销要做一次 8 秒的新人弹窗活动，怎么不改全局配置让它上线？③ 若把订单→库存的 read-timeout 设成 8 秒，会发生什么？▶ 点击展开解析

🔍 逐问拆解

① 自底向上分配预算：DB 150ms 是地基；库存服务自身逻辑（除 DB 外）留 ~100ms，则库存接口整体 P99 ≈ 400ms，营销同理 ≈ 550ms。订单聚合两者 + 自身逻辑 ≈ 1.1s。给预算时每层留 50~100% 余量防长尾：营销 Feign read-timeout ≈ 1s，库存 ≈ 800ms（注意营销预算不能超过库存的——链路上两者是并行的，取大者约束订单层）；订单自身处理 + 下游取大值 ≈ 1.5s；网关 3s，剩余 ~1.2s 就是整条链路的"抖动缓冲"。核心校验：任何一层的超时都不能大于网关剩余预算，否则上层已对用户超时、下层还在空转烧线程——这正是 01 节雪崩的微观机制。

② 局部覆盖，不动全局：在 YAML 里给 spring.cloud.openfeign.client.config.marketing-service.read-timeout: 9000 单独放宽（服务名配置优先于 default），或者更干净的做法——为营销的慢接口单独建一个 FeignClient（contextId 区分，如 marketingActivityClient），只对这个客户端放宽。为什么不建议全局放宽：全局 read-timeout 从 1s 放到 9s，等于把所有下游故障时线程挂起时长 ×9，一次营销抖动可以拖干订单线程池。若慢调用是常态，还应推动营销侧把弹窗接口改成异步领取 + 轮询/推送，把"8 秒同步等待"从调用链里赶出去——超时治理的尽头是接口治理。

③ 三个后果连锁：第一，网关 3 秒已对用户返回失败，但订单线程会继续挂满 8 秒——上游资源消耗（线程、连接池驻留）放大约 2.7 倍，同样抖动下雪崩阈值显著降低；第二，用户看到失败会重试/刷新，下游收到叠加流量，而旧请求还在跑，形成"僵尸请求 + 新请求"双倍打下游；第三，Sentinel 熔断的 RT 统计被拉长（默认 RT 阈值口径下的慢调用比例上升），熔断频繁开启又恢复，来回震荡。结论一句话：这个配置能让熔断器和线程池同时失灵——超时永远要和网关预算、熔断统计一起看，不能孤立地"给慢下游多点耐心"。

题目二：库存服务的扣减接口（POST /deduct）偶发读超时。团队 A 的方案：给扣减接口的 Feign 客户端开 Retryer.Default（3 次，指数退避）；团队 B 反对，说会重复扣库存。① 精确描述"重复扣减"在什么条件下发生、什么条件下不发生；② 如果坚持要传输层自动重试，前置条件是什么？③ 设计一个不靠传输层重试的兜底方案，说明超时后调用方第一步做什么。▶ 点击展开解析

🔍 逐问拆解

① 重复的充要条件是"第一次请求已到达且已提交"：读超时只意味着调用方在 read-timeout 内没等到响应——三种可能：(a) 请求根本没到达（连接建立后被重置、服务端队列丢弃）——重发安全，不会重复；(b) 请求到达但服务端还没处理完（GC、排队）——超时触发时处理仍在进行，重发的第二笔在第一笔提交前后落地，若服务端无幂等去重，两笔都生效——重复发生；(c) 服务端已提交成功、响应在回程丢失——重发必然重复。Retryer.Default 不区分这三种情况（它对 RetryableException 一律重发），所以只要 (b)(c) 的概率非零，重复扣减就是统计意义上必然事件，压测量足够大时一定出现。

② 传输层自动重试的前置条件是幂等性在服务端闭环：扣减请求必须携带全局唯一幂等键（如 orderId+skuId 派生的 idempotentKey），库存服务落"幂等键 → 处理结果"表（或 Redis SETNX + 最终落库），重发命中已处理键直接返回上次结果。同时 ErrorDecoder 要把重试范围收窄到"请求大概率未到达"的错误：连接被拒、连接超时可重试；读超时不可重试（结果未知，交给上层）；4xx 不可重试（请求有问题，重发一样错）。二者缺一——没有幂等键，重试就是赌博；ErrorDecoder 不收窄，读超时也会被 Retryer 重发。做到这两条，传输层重试才是安全的。

③ 兜底方案：幂等键 + 结果查询 + 状态机，超时后第一步是"查"不是"重发"：调用方超时后，拿着幂等键调库存服务的查询接口（GET /deduct/{idempotentKey}）：查到"已成功"→ 本地订单推进；查到"明确失败"→ 走重试或失败流程；查不到（处理中）→ 进延迟重查队列（本地消息表或 Pulsar 延迟消息，联动第 21 期的重试队列 + 死信设计），按退避节奏重查 N 次仍无结果才转人工对账。库存服务侧用幂等键做并发控制（同一键的处理串行化/互斥），保证"查询接口看不到半成品"。这套方案的本质是把"至少一次投递 + 幂等消费"从消息队列搬到同步调用：超时是分布式系统的常态而不是异常，可靠性设计的目标从来不是消灭超时，而是让超时之后的世界是确定的——传输层重试只是这条原则在"确定没发生"分支上的优化，不能越权处理"不确定"的分支。
