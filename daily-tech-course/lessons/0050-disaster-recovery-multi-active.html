架构运维 · 架构与中间件运维系列第 6 讲（容灾篇）

容灾架构与多活：RPO 与 RTO 不是口号，是换算表

上一讲把散装的分布式设计模式拼成了地图，这一期继续架构运维线，往上走一层——当故障不是"某个实例挂了"，而是整个机房、整个区域、甚至云厂商的控制面一起出事时，架构拿什么应对。两场真实大故障开局，然后讲透容灾的度量衡（RPO/RTO）、从容备到异地多活的五档阶梯、同城双活的落地细节（半同步的静默退化是最深的一口坑），最后给一套能直接拿去评审的演练与盘点清单。

01两场大故障：一个炸了 3.5 小时，一个只挂 18 分钟

第一场：2023 年 11 月 12 日，阿里云。17:44 起，云产品控制台访问与管控 API 调用出现异常，故障波及全球所有地域——淘宝、钉钉、闲鱼、阿里云盘相继登上热搜，大量客户的业务跟着受影响，21:11 才全部恢复，全程约 3.5 小时。官方确认根因是"某个底层服务组件"（业内普遍指向鉴权类公共服务）。最值得架构师回味的是故障的形状：数据面大体正常—— ECS、RDS 上跑着的虚机和数据库大多还在工作；炸掉的是控制面——控制台登不进、API 调不动、想扩容想切流的人都只能干瞪眼。

第二场：2016 年 4 月 11 日，Google Cloud。Compute Engine 全球多个区域同时失去网络连通性，18 分钟完全中断。事后 Google 给受影响客户赔偿了最高 25% 的月度账单，并公开了完整事故报告。18 分钟 vs 3.5 小时，差距不在运气，在于：Google 那次坏的是网络设备（数据面，自动恢复路径清晰）；阿里云这次坏的是全局共享的控制服务——它是所有客户共用的一个隐形单点。

这两场故障共同逼出的一个问题

你的系统挂在"单个云厂商、单个地域、两个可用区"上，自称双活。请问：机房没了怎么办？区域没了怎么办？云厂商的控制面没了怎么办？第三个问题在 2023 年 11 月 12 日之前，绝大多数容灾方案里连一行字都没有。

回答这三个问题，靠的不是"我们有多活架构"这句话，而是两张换算表：RPO（Recovery Point Objective，恢复点目标——能容忍丢多少数据）和 RTO（Recovery Time Objective，恢复时间目标——多久能恢复服务）。0017 期讲高可用时给过这两把尺子的定义，这一期把它们变成容灾选型的设计输入。

02原理：度量衡、分级，和"容灾 ≠ 高可用"

先分清：高可用对付组件，容灾对付站点

0017 期的高可用四层冗余模型，对付的是实例、节点、机架级的组件故障：频率高、爆炸半径小、秒级自动切换。容灾对付的是机房级、区域级、厂商级的灾难：频率低、爆炸半径大、恢复动作里往往有人工决策。两者不是替代关系，是上下层关系——没有 L1/L2 的高可用垫底，双活机房的日常抖动就能把你拖死；只有 L1/L2 而没有容灾，一场机房级事件就能让 0017 里算过的可用性数学全部作废。

RPO 由复制模式决定，RTO 由预案成熟度决定

复制/备份模式RPO 理论值典型 RTO代价
同步/半同步复制（同城）0（提交即已传输）分钟级写延迟增加，跨机房链路成为写路径
异步复制（跨区域）秒级 ~ 分钟级分钟 ~ 小时级灾难时可能丢数据，需对账补偿
定时备份（每日全量+binlog）小时级（受备份频率限制）小时 ~ 天级最便宜，只能兜底不能扛在线业务
多数派共识跨城（如三地五中心）0<30 秒每笔写都要跨城同步，写延迟高、成本高

这张表是选型的起点：业务说"一条都不能丢"，RPO 就必须是 0，异步复制直接出局；业务说"最多丢 5 分钟"，那花三倍价钱追 RPO=0 就是在烧钱。反过来，RTO 的敌人从来不是技术，是流程——2019 年某云厂商一地域故障时，不少"有灾备"的客户恢复花了半天，因为切流预案只存在于架构图上，谁也没演练过，DNS 的 TTL 设置、数据库账号权限、备端配置的时效性全是现场踩的坑。

冷备备端只有数据备份，无系统小时级天级存储费

阶梯上每一格都有官方参照系：OceanBase 的容灾部署文档给出了从"同机房三副本"到"三地五中心"的完整对照——同城三机房（每机房一个 Zone）机房级故障 RPO=0、RTO<30 秒；两地两中心主备库架构地域级故障 RPO>0、RTO 分钟级；要到三地五中心五副本（前两城各两副本、第三城一副本，每笔事务至少同步到两个城市）才实现地域级故障 RPO=0。这张官方表把一个关键事实摆得很清楚：想跨城市不丢数据，必须让多数派跨城，写延迟的账单躲不掉——这就是绝大多数公司止步同城双活、异地只做灾备的根本原因。

03架构设计：同城双活参考形状与三个必须面对的坑

坑一：半同步会"静默退化"，而且专挑坏天气退

同城双活数据层的标配是 MySQL 半同步复制。它的手册语义很美好：主库提交时等待至少一个从库确认收到 binlog 才返回客户端。但有个参数的默认值决定了现实：rpl_semi_sync_source_timeout（MySQL 8.4 命名，8.0.26 前叫 rpl_semi_sync_master_timeout）默认 10000 毫秒——从库 10 秒内没应答，主库不会报错，而是悄悄降级回异步复制继续提交。这意味着你的 RPO 从 0 变成了"取决于复制延迟"，而且降级恰好发生在从库不健康或机房链路抖动的时候——正是你最需要它的时刻。生产纪律：超时改 2000~3000ms（快速感知+留抖动余量），并且对降级本身做高级别告警（监控 Rpl_semi_sync_source_status 从 ON 变 OFF、Rpl_semi_sync_source_no_tx 计数增长），把"半同步实际在不在岗"变成一块每天有人看的仪表盘，而不是配置文件里的一行自我安慰。

坑二：缓存和消息不能照抄数据库的双活姿势

Redis 不要做跨机房主从——复制延迟叠加脑裂风险，切流时两边各说各话；正确姿势是两机房各自独立集群，以"缓存可重建"为原则，切流后接受短暂穿透回源（0017 思考题已推演过这条结论）。消息队列则相反，天然适合跨机房：以 Pulsar 的 BookKeeper 为例，多副本加机架感知 placement，让写集合覆盖两机房，消息层无需任何双写（Kafka 的机架感知副本分配同理）。对象存储（MinIO）用双站点纠删码异步复制。每种数据资产的容灾姿势由它的可重建性决定，这是比"全都双活"省钱也稳得多的思路。

坑三：控制面单点——2023 年那场故障的核心教训

盘点你的全局共享服务：注册/配置中心、网关管控面、K8s API Server、监控告警、堡垒机、以及云厂商的控制面本身。这些组件挂掉时数据面也许还在跑，但你失去的是"改变系统的能力"——扩不了容、切不了流、改不了配置，甚至看不了监控。对策三层：① 切流入口与云控制面解耦（GSLB/DNS 服务别和业务同厂商同账号体系，至少留一条手工切换通道）；② 手工作业预案（机房型故障时的电话树、本地留存的账号与配置台账、不依赖云 API 的操作路径）；③ 数据面尽量自治（应用本地兜底的注册快照、配置快照——0002 期讲过的客户端容灾机制在这里第二次救你）。

04实战：半同步配置、切流演练、单点盘点

① MySQL 8.4 同城半同步（机房 A 主、机房 B 从）

# 机房 A（主库）——8.4 新命名：rpl_semi_sync_source_*
INSTALL PLUGIN rpl_semi_sync_source SONAME 'semisync_source.so';
SET GLOBAL rpl_semi_sync_source_enabled = 1;
SET GLOBAL rpl_semi_sync_source_timeout = 3000;      # 默认 10s 太钝，3s 快速感知
SET GLOBAL rpl_semi_sync_source_wait_point = AFTER_SYNC;  # 无损模式：先收 ACK 再提交
# 机房 B（从库）
INSTALL PLUGIN rpl_semi_sync_replica SONAME 'semisync_replica.so';
SET GLOBAL rpl_semi_sync_replica_enabled = 1;
# 退化监控（放进 Prometheus 采集，任何一条触发都说明 RPO=0 已失守）：
# SHOW GLOBAL STATUS LIKE 'Rpl_semi_sync_source_status';   -- ON 才是半同步在岗
# SHOW GLOBAL STATUS LIKE 'Rpl_semi_sync_source_no_tx';    -- 降级后提交的事务计数
# SHOW GLOBAL STATUS LIKE 'Rpl_semi_sync_source_yes_tx';   -- 半同步成功提交计数

两个细节别省：wait_point=AFTER_SYNC（默认值）保证所有客户端看到同一提交视图，主库故障切换不丢已确认事务；配置务必写进 my.cnf——半同步参数是动态的，重启丢配置后你的"双活"会静默变单机房加异步从库，监控却一切绿色。

② 切流演练剧本（每季度至少一次真刀真枪）

1

预检：两机房容量水位（B 机房能否扛 100% 峰值）、半同步状态 ON、复制延迟 <1s、GSLB 健康检查配置正确、DNS TTL 已提前压到 60s 以下；

2

切流：低峰期 GSLB 将机房 A 权重逐步降为 0（先 50%→25%→0，观察 5 分钟再下一步）；确认 A 无流量后，B 机房从库执行 STOP REPLICA; RESET REPLICA ALL; 升级为可写主库，应用连接串通过配置中心切指新主；

3

验证：核心链路下单/支付冒烟、缓存命中率回稳曲线、消息积压消费进度、对账任务数据齐平——四项全绿才算切流成功；

4

回切与复盘：原主库修复后以新从库身份重建半同步，流量按预案切回（或保持新主，双写窗口内对账）；把演练中每一步的实际耗时记进 RTO 台账——声明的 RTO 与实测 RTO 的差距，就是下一次故障的 surprise 大小。

05今日要点

  • RPO/RTO 是换算表不是口号：RPO 由复制模式决定（同步=0、异步=秒~分钟、备份=小时），RTO 由预案成熟度决定。业务先给数字，架构才有选型。
  • 想跨城不丢数据，必须让多数派跨城：OceanBase 三地五中心官方口径（地域级 RPO=0、RTO<30s）的代价是每笔写跨城同步——这是多数公司止步同城双活的根本原因，不是技术不会，是账不划算。
  • 半同步的最大风险是静默退化：默认 10 秒超时后悄悄变异步，RPO=0 名存实亡，且专挑链路抖动时发生。改 3 秒 + 对降级状态做高级别告警，是双活数据层的生死线。
  • 每种数据资产按可重建性选容灾姿势：数据库半同步、Redis 机房独立可重建、消息跨机房多副本、对象存储双站点——别一把梭"全都双活"。
  • 控制面是 2023 年后必须盘点的故障域：机房双活防不住云控制面故障。切流入口解耦、手工作业预案、数据面自治三层对策，把"改变系统的能力"也纳入容灾范围。

06架构师思考题

题目一：你们的核心交易系统部署在单一云厂商的单地域（两个可用区），MySQL 主从 + 应用双 AZ。业务方给出新要求："机房级故障 RTO ≤ 15 分钟、RPO = 0"，但预算明确不支持异地多活。①给出你的目标架构；②列出三个最容易翻车的点及对策；③解释为什么在这个预算下 RPO=0 与异地容灾不可兼得。▶ 点击展开解析

🔍 目标架构：同城双活（不是"双 AZ 高可用"）

业务要求的是机房级故障恢复，双 AZ 只防可用区级故障（同机房的电力/网络域），机房级事件（光纤挖断、机房级火灾、制冷失效——2022 年某云香港机房制冷故障宕机超 10 小时就是前车之鉴）会把两个 AZ 一起带走。目标形态：同城两机房对等部署（GSLB 分流）、MySQL 半同步（AFTER_SYNC）跨机房、Redis 机房独立、消息副本跨机房、单机房容量可扛 100% 峰值。异地只做备份级容灾（异步复制 + 每日备份异地存放），明确声明异地 RPO>0——这是预算约束下的诚实设计，比"伪多活"安全得多。

✅ 三个最容易翻车的点

  • 半同步静默退化：默认 10s 超时降级异步，故障切换那一刻才发现 RPO 早就不是 0。对策：timeout 收紧到 3s、降级状态高级别告警、每日巡检 no_tx 计数归零；
  • 切流决策的自动化程度：RTO 15 分钟容不下"打电话找领导拍板"。但全自动切换有误切风险（机房间歇抖动时来回切比故障本身更伤）。对策：分级的自动化——数据层故障切换（主库心跳超时+从库数据完整校验）自动化，机房级整体切流保留"一键人工触发"（预案脚本化到只剩一个按钮），决策 2 分钟内可执行；
  • 备端时效性漂移：B 机房的配置、账号、证书、DNS 记录长期不用会悄悄腐化，真切换时连不上库、证书过期、配置不一致。对策：把 B 机房常态承载 50% 流量（真双活），让时效性由日常使用天然保鲜；演练剧本每季度真跑。

⚖️ 为什么 RPO=0 与异地不可兼得

RPO=0 要求事务提交前数据已到达异地——即同步或多数派跨城。跨城 RTT 通常 30ms 起，每笔写至少翻倍延迟，交易 TPS 与用户体验的直接代价之外，还要多城多机房 ×2~3 的资源成本。OceanBase 三地五中心做到地域级 RPO=0，靠的是"每笔事务至少同步到两个城市"的多数派设计，这是金融级预算和写延迟容忍度换来的。预算不支持时的正确姿势：同城保 RPO=0，异地保"活着"（分钟~小时级 RPO 的灾备 + 对账补偿能力），并把两地三中心写进演进路线图，业务量级和预算到位后再升级。
