湖仓一体：Iceberg、Paimon 与 Fluss 的分层和解

上一讲聊完 Flink 流批一体，这期继续数据架构线。凌晨两点，DWD 层一张核心表被误清空，新来的分析师用旧 SQL 全表重跑覆盖了分区，恢复靠 DBA 从昨天的全量备份里人肉捞——"湖上建仓"两年了，为什么数据安全感还不如当年那个 Hive 集群？这一讲拆开湖仓一体的三层结构：开放表格式（Iceberg/Paimon）解决"湖上的表怎么像表"，流式存储（Fluss）解决"湖怎么变得实时"，再把"三个开源项目怎么选、怎么组合"落成一张决策表。

01场景：凌晨两点的"表没了"事故

事故复盘：一次 INSERT OVERWRITE 引发的三个系统都要修

某电商团队的湖仓建在对象存储上，凌晨两点值班群炸了：DWD 层订单明细表（T+1 分区、下游 40+ 张 ADS 表、3 条报表链路）查询全挂。时间线还原：

  • 02:03 新入职分析师跑历史回补，脚本里 INSERT OVERWRITE 的分区条件少写一个月份过滤——全表被当成了一个分区覆盖。Hive 时代这种事故靠"误删分区还能从回收站捞目录"，但对象存储没有回收站，目录被覆盖就是物理覆盖；
  • 02:03 注意时间戳——覆盖动作秒级完成，没有任何提交冲突、没有任何告警。对象存储的 PUT 是原子的，但"覆盖两千个文件"这个业务语义没有任何校验；
  • 02:15 团队想回滚，发现这套链路是"Flink 直接写 Parquet 文件到对象存储"的裸奔方案：没有快照、没有版本、没有时间旅行。最终恢复 = 从前一天的全量备份 + 当天 Kafka 重放（ODS 队列 retention 只剩 3 天，险象环生），恢复耗时 6 小时，错过早间报表。
复盘的真正结论

直接写文件到对象存储，用的是存储的语义（PUT 成功 = 写成功），丢的是表的语义（原子提交、版本、回滚、schema 演进）。湖仓一体的核心命题不是"把数据搬到对象存储上省存储费"，而是在廉价存储之上重建一张"像数据库的表"该有的一切事务语义——这正是开放表格式（Iceberg/Paimon）存在的意义。而这个事故里的"从 Kafka 重放恢复"，则引出本期第二个主角：如果 Kafka retention 不止 3 天、如果队列和湖是同一份数据的不同温度层——恢复根本不用 6 小时。

02原理：一张湖表的"表语义"从哪来

开放表格式：把"表"做成一组元数据文件

Iceberg 的回答是把表状态做成元数据树：数据文件（Parquet/ORC）不可变，其上是清单文件 manifest（每个清单记录一批数据文件的路径、分区统计、列级 min/max），最顶上是快照 snapshot（指向一组清单，代表表的某个一致版本）。每次写入 = 新数据文件 + 新清单 + 新快照，通过 Catalog 的原子指针切换提交（旧快照不动，新快照生效）。这套结构一次性带来：ACID（提交原子、读快照隔离）、时间旅行（旧快照还在，SELECT ... AS OF 直接查历史版本）、schema 演进（加列不重写文件）、分区演进（改分区策略不动存量数据）。凌晨事故里那类"误覆盖"，在 Iceberg 表上是一次新快照——回滚 = 把指针切回上一个快照，秒级完成。

Paimon 的出发点不同：它要在湖上接住流式更新。主键表底层是 LSM-Tree（与 HBase/RocksDB 同族的结构）：写入先落小文件（L0），后台 compaction 逐层合并去重，读取时多路归并按主键取最新值。这个结构让 Paimon 能以分钟级延迟接住 CDC 流的持续 upsert，还带出了三个流式特性：merge engine（去重/部分更新/预聚合/首行，按业务语义选）、changelog-producer（产出完整正确的变更流，下游流算子不用另做去重）、CDC 整库同步。代价是 LSM 永动：compaction 是常态运行成本，小文件与读放大是它一生的敌人。

一张图看懂分层：格式层与热层各管什么

分层的要害在边界：Fluss 是流式存储（一个独立的集群系统，不是文件格式），它管"数据最热的那几天"，Arrow 列式流 + 服务端下推让流读也省带宽；Iceberg/Paimon 是文件格式 + 元数据约定（不是集群，没有常驻进程），管"全量历史与事务语义"。Fluss 1.0 起支持湖一体：日志表数据自动沉降为湖上的 Parquet（当前对接 Paimon/Iceberg），主键表可通过 Union Read 把 Fluss 热段与湖上冷段合并成一个视图。换句话说：Fluss 不与湖竞争，它是湖的"实时前置层"。

03架构：选型决策表与组合参考架构

Iceberg vs Paimon：不是二选一，是分工

维度IcebergPaimonFluss
本质开放表格式（元数据树）湖格式（主键表 LSM）流式存储系统（集群）
强项大规模批分析、多引擎生态最广、快照回滚流式 upsert 分钟级入湖、CDC 整库同步、changelog秒级流读、KV 点查、与湖自动冷热分层
更新姿势MERGE INTO（COW/MOR，v3 引入删除向量 DV）主键表原生 upsert + merge engine主键表实时 upsert + Delta Join

典型角色DWD/DWS 批层、ADS 湖上集市DWD 实时层、CDC 入湖落地表Kafka 替代/共存 + 实时点查层
版本坐标（2026-10）1.12.0（2026-09-30）2.0.0（2026-08-07）1.0（2026-09-21）·8 月毕业 TLP

决策口径：纯批分析为主、生态广度优先 → Iceberg；Flink 实时数仓主力、CDC 持续 upsert → Paimon；秒级流读 + 点查 + 想把 Kafka 热数据也纳入统一元数据 → Fluss（可替代或共存于 Kafka）。三者不互斥：常见的生产组合是 Fluss（热）+ Paimon（实时湖层）+ Iceberg（批层/集市层），靠 Catalog 语义打通。另注意 Paimon 1.2+ 提供"Iceberg 兼容元数据"（Paimon 表可同时暴露为 Iceberg 表供 Trino/StarRocks 读）——两个格式间的墙正在被拆掉。

组合参考架构：三条入湖链路

以典型电商实时数仓为例（承接 0053 的分层话语）：

  • 实时链路（秒~分钟）：业务库 binlog → Flink CDC → Fluss 日志表（ODS 实时层，替代 Kafka，队列即表）→ Flink 流作业聚合 → Paimon 主键表（DWD/DWS 实时层，upsert 持续更新）→ StarRocks/Trino 直读供报表与 OLAP；
  • 沉降链路（自动）：Fluss 日志表按 TTL 沉降为 Paimon/Iceberg 分区（湖上 ODS 全量历史），热段过期即只剩湖——同一份数据不需要在队列和湖各存一份；
  • 批链路（小时~天）：湖上 ODS → Spark/Flink 批模式 → Iceberg DWD/DWS/ADS（大表批加工、快照对账、报表集市）→ 各引擎按 Catalog 直读。

容量三笔账：①存储账——对象存储单价约为自建 HDFS 三分之一以下，但小文件是头号成本刺客：每 GB 对象存储每日上千次 LIST/GET 请求费可能反超存储费本身，Iceberg 的 manifest 合并、Paimon 的 compaction、Fluss 的沉降都直接压请求费；②新鲜度账——Fluss 热段秒级、Paimon 分钟级、Iceberg 批小时级，链路每降一层温度，延迟和成本各降一档，按业务 SLA 分层放置而不是全量追求秒级；③恢复账——有了快照与可回放 ODS，"凌晨事故"类恢复从 6 小时人肉恢复降为分钟级快照回滚 + Fluss/Kafka 重放——湖仓的事务语义本质上是买了一份"数据可恢复性"保险。

04实战：三段最小可用配置

① Flink SQL 一条链路写 Paimon 主键表（CDC 入湖）

-- Flink SQL：MySQL binlog 整库入 Paimon 主键表
CREATE CATALOG paimon WITH (
  'type'='paimon',
  'warehouse'='s3://lake/warehouse'              -- 对象存储路径
);
CREATE TABLE dwd_orders (
  order_id BIGINT,
  user_id BIGINT,
  status STRING,
  op_time TIMESTAMP(3),
  dt AS DATE_FORMAT(op_time, 'yyyy-MM-dd'),      -- 0053 讲过：事件时间派生分区
  PRIMARY KEY (order_id) NOT ENFORCED
) PARTITIONED BY (dt) WITH (
  'changelog-producer'='input',                  -- 源是 CDC 流，变更语义完整
  'bucket'='4',                                  -- 分桶数=写入并行度上限
  'snapshot.time-retained'='2 h'                 -- 快照保留窗口
);
-- 同步作业：Source 为 CDC 连接器，upsert 持续合入
INSERT INTO dwd_orders SELECT ... FROM orders_cdc;

② Iceberg：快照回滚与表维护（凌晨事故的解药）

-- Spark SQL：误覆盖后秒级回滚
SELECT * FROM dws_gmv /* OPTIONS('snapshot-id'='4113') */;  -- 先查旧快照确认
CALL iceberg.system.rollback_to_snapshot(
  table => 'lake.dws_gmv',
  snapshot_id => 4113                            -- 指针切回，旧数据文件从未被删
);
-- 表维护：过期快照清理 + 小文件合并（控对象存储请求费）
CALL iceberg.system.expire_snapshots('lake.dws_gmv',
  'older_than'=>'2026-10-01 00:00:00');
CALL iceberg.system.rewrite_data_files(
  table => 'lake.dws_gmv',
  strategy => 'sort', sort_order => 'dt DESC'   -- 顺便做聚类，查询裁剪受益
);

③ Fluss：建一张自动沉降的日志表

-- Flink SQL（Fluss Catalog）：日志表 + 湖一体沉降
CREATE TABLE ods_events (
  event_id STRING,
  payload STRING,
  event_time TIMESTAMP(3)
) WITH (
  'table.type'='log',                            -- 日志表（流读语义）
  'bucket'='8',
  'log.ttl'='3 d',                               -- 热层只留 3 天
  'table.lake-enable'='true',                    -- 开启湖一体
  'table.lake-format'='paimon',                  -- 沉降为 Paimon 分区
  'datalake.ttl'='365 d'                         -- 湖上留一年
);
-- 消费端视角：FlussConnector 自动做 union read，
-- 3 天内走 Fluss 热段，更早的走湖上 Parquet，一条 SQL 两种温度。

05今日要点

  • 湖仓一体 ≠ 数据上对象存储：对象存储只给"廉价 + 持久"，表语义（ACID、快照、回滚、演进）由开放表格式的元数据层重建——凌晨误覆盖事故的根因是用存储语义冒充了表语义。
  • Iceberg 与 Paimon 是两种出身：Iceberg 是元数据树，为大规模批分析而生、生态最广；Paimon 是湖上 LSM，为流式 upsert 而生、分钟级 CDC 入湖——不是竞品二选一，是"批层与实时层"的分工。
  • Fluss 补上"实时湖"缺口：流式存储集群，日志表秒级流读可替代 Kafka 热段，主键表支持点查；数据按温度自动沉降入湖（Paimon/Iceberg），队列与湖从"两份数据两套系统"变为"一份数据两个温度"。
  • 小文件是湖仓头号成本刺客：对象存储的请求费可能反超存储费——compaction/manifest 合并/沉降策略不是性能优化，是成本工程。
  • 快照 + 可回放 ODS = 数据可恢复性保险：误覆盖恢复从 6 小时人肉捞备份降为秒级快照回滚；ODS 队列/湖表保留窗口要按"最坏重放需求"倒推。

06架构师思考题

题目：你们公司实时数仓现状：Kafka（ODS 队列，retention 3 天）+ Flink 流作业 + StarRocks 供数；离线数仓：Hive on HDFS（T+1 调度）。老板要求"一年内湖仓一体"，并明确三个目标：① 实时与离线的 ODS 不再各存一份（存储费砍半）；② 核心链路具备"误操作可分钟级恢复"能力；③ 大促期间实时报表能扛住（当前 StarRocks 在大促时因高频 upsert 出现查询抖动）。给出你的目标架构（画分层、选组件、定边界），并回答：④ Kafka 是否退役、Fluss 是否引入的决策依据；⑤ 迁移的分阶段路线（不允许全量重写、业务无感）。▶ 点击展开解析

🔍 五问拆解

①②③ 目标架构：分层画法——ODS 层：binlog → Flink CDC → Fluss 日志表（table.lake-enable=true，沉降 Paimon 分区；Kafka 不再承担全量 ODS，仅保留跨团队外部订阅场景或直接退役）。热段 3 天覆盖 StarRocks 拉取窗口与重放需求。DWD/DWS 层：Flink 流作业读 Fluss → 写 Paimon 主键表（分钟级 upsert）；同一份数据由 compaction 作业维护。批层/ADS：Spark/Flink 批模式读 Paimon ODS → 写 Iceberg DWD/ADS（大表批加工、集市）；StarRocks/Trino 通过 Catalog 直读湖。这样：ODS 一份数据两个温度（存储费目标①达成）；全链路快照化（目标②：误覆盖 = 快照回滚，Paimon snapshot + Iceberg rollback 都是秒级指针操作）；大促查询抖动（目标③）的根因是"高频 upsert 直打 OLAP 引擎"，解法是 OLAP 引擎改为读湖上批层（读多写少的 ADS），实时侧仅小表直读——读写分离到温度层，而不是给 StarRocks 加机器。

④ Kafka 退役与 Fluss 引入的决策依据：退役的收益 = ODS 双份存储消除 + 队列/湖两套元数据合一；不退役的理由 = Kafka 生态成熟度（connector、运维团队技能、跨语言客户端）与 Fluss 1.0 的生产验证周期。决策判据三条：一看消费模式——消费方是否需要"秒级流读 + 点查 + 湖上全量"三合一？只有流读 → Kafka 够；要三合一 → Fluss。二看组织能力——Fluss 是新集群系统，要评估运维画像（类似 Kafka 但有 TabletServer/协调器，大促容量规划另一套）；三看迁移窗口——外部订阅方多（数据团队之外的消费者）时 Kafka 退役牵连面大，可先"Fluss 承接 Flink 内部链路、Kafka 保留对外分发"的双轨，后续再收敛。技术上还要核对 Fluss 1.0 的能力边界（如消费组管理、Kafka 协议兼容在 1.1 roadmap）——别让目标架构跑在 roadmap 前面。

⑤ 分阶段路线（业务无感）：第一阶段（1~2 月）打底：建 Catalog 与对象存储规范（路径/权限/生命周期）、Iceberg ADS 层先行（纯增量，不动存量 Hive——新报表走湖，老的按周迁移）；第二阶段（2~3 月）双轨实时层：Fluss 集群灰度上线，一条新业务链路 CDC → Fluss → Paimon 全链试点，与 Kafka 链路双跑对账（口径、延迟、成本三张表）；第三阶段（2~3 月）ODS 收敛：存量 Kafka ODS 逐 topic 迁 Fluss（消费组批量切，保留回切预案），Paimon 沉降分区替代离线 Hive ODS 的每日同步任务，Hive T+1 任务改为读湖（Spark 直读 Paimon/Iceberg，SQL 兼容层验证）；第四阶段（收尾）Hive 退役评估：存量 HDFS 数据迁移（Iceberg migrate 或保留只读）、Hive 集群下线成本复盘。全程两条纪律：每个阶段有"可停点"（双轨任一侧能独立承担全量业务）；对账先行——口径对上了再切流量，0053 讲的三笔制度性差额教训在湖仓迁移里同样成立。
