磁盘坏 4 块也不怕：分布式部署与纠删码

对象存储的可靠性不是靠"多复制几份"堆出来的。今天讲透 MinIO 的看家本领——纠删码：N=K+M 的分片数学、读仲裁与写仲裁、M=N/2 时的 K+1 防脑裂设计、坏几块盘会发生什么的降级梯子，以及拓扑为什么"初始化后定死"。最后补一课 2025 年 10 月起的社区版分发变局——这次事件本身就是给所有架构师上的供应链风险管理课。

01一个"三份方案都过不了评审"的选型复盘

影像审计平台扩容评审会，需求很朴素：每天新增 800GB 影像与日志，保留 3 年，全量约 900TB，要求任意单点故障不影响业务、坏盘换盘不丢数据。三个方案全被拍回来：

  • 方案一 NFS + RAID6：16 块 8TB 盘的 RAID6 只容忍 2 块盘故障，而大容量盘重建要 1~2 天——重建窗口里再坏一块盘就整卷丢失。评审意见：容错窗口太脆弱；
  • 方案二 双副本存储：900TB 数据存两份，裸容量直接 1800TB 起。评审意见：存储预算翻倍，pass；
  • 方案三 云对象存储：审计数据出域有合规问题。pass。

最终落地 MinIO 分布式集群：纠删码 EC:4——900TB 数据按 12/16 的存储效率落盘，裸容量约 1200TB 拿下；任意坏 4 块盘业务无感，换盘后自动修复；连"盘静默坏字节"都有每分片的校验和兜底。比双副本省 1/3 容量，比 RAID6 容错能力翻倍且重建以对象为单位、粒度细得多。

这期就把这套方案的底层机制讲清楚：纠删码到底怎么切数据、坏几块盘会怎样、拓扑怎么规划、2025 年之后社区版怎么部署。

02原理：一次 PUT 在 16 块盘上发生了什么

MinIO 把每个服务器池（Server Pool）里的盘分成若干大小相同的纠删集（Erasure Set），每个纠删集 2~16 块盘。4 节点 × 4 盘 = 16 块盘，正好组成一个纠删集——这是官方最经典的最小生产拓扑。写入时，对象被切成数据分片（K）+ 校验分片（M），满足公式：

核心公式

N（纠删集盘数）= K（数据分片）+ M（校验分片），M 可取 0 ~ N/2。16 盘纠删集配 EC:4，即切成 12 个数据分片 + 4 个校验分片（Reed-Solomon 编码），存储效率 12/16 = 75%。校验分片是对象的数学变换——任意凑齐 K 个分片（不区分数据还是校验）就能完整还原对象。

还有一个容易忽略的细节：对象写入时用的 EC 配置会记进对象元数据，之后修改纠删集校验配置只影响新写入的对象，老对象不回溯迁移。所以 storage class 要在放量之前一次定准。另外，每个分片落盘时都附带 HighwayHash 校验和（bitrot 防护）——读取时先验哈希再使用，静默坏字节（磁盘电容故障、线缆干扰的常见产物）会被拦截并用好分片重建，这是 RAID6 给不了的保障。

03架构设计：拓扑、档位与 2025 年的分发变局

拓扑三原则

  • 节点数 ≥ 4，每节点盘数一致：纠删集跨节点混布分片，单节点离线最多吃掉纠删集里"每节点盘数"个分片。4 节点×4 盘时单节点离线 = 纠删集丢 4 个分片，恰好被 EC:4 兜住；如果 2 节点×8 盘，单节点离线就丢 8 个分片，EC:4 直接击穿；
  • 盘独立直挂（JBOD），不做 RAID，MinIO 独占：冗余由 EC 负责，盘只提供裸容量；混用 RAID 等于双层冗余浪费一倍空间，共享盘还会破坏"独占盘"的修复模型；
  • 拓扑初始化后不可改：纠删集的数量与大小在服务器池初始化时定死。扩容的正确姿势是加新的服务器池（新数据优先落新池），而不是往老纠删集里塞盘——这是和"加盘扩容"直觉相反、必须提前规划的一点。

容量规划一笔账 可用容量 = 裸容量 × K/N。裸容量按"计划采购的盘数 × 单盘容量"算，别忘预留水位（建议 ≤80%）与元数据、版本化对象的开销。反过来：需求容量 ÷ (K/N) ÷ 0.8 = 要买的裸容量。注意对比"同效率下的容错"：EC:4/16 盘与三副本（效率 33%）相比，用一半的容量换来了"坏 4 块盘"的容错；与 RAID6（效率 87.5% 但只容 2 块、整盘重建）相比，多花 12.5% 容量买到双倍容错与对象级修复。
⚠ 2025-10 起的社区版分发变局（选型必读） MinIO 社区版自 2025 年 10 月起转为仅源码分发：不再发布预编译二进制与官方 Docker 镜像（历史版本仍可下载但不再维护更新）；Web 控制台的管理功能被大幅精简（最后的功能完整版本为 RELEASE.2025-04-22），管理操作回归 mc 命令行；社区文档并入商业版文档站。许可证方面 AGPLv3 的"网络服务即分发"条款需要法务评估（仅内部使用一般风险可控，二次封装对外提供 S3 服务则有开源义务）。架构师应对：① 锁定版本 + 自建镜像流水线（Dockerfile 源码构建），把 CVE 跟踪纳入自己的流程；② 运维体系一律以 mc / API / Prometheus 为准，不依赖 Web 控制台；③ 每年重评估一次替代项（Ceph RGW、Garage、SeaweedFS 等兼容 S3 的开源方案，或商业版），把退出成本控制在"数据是标准 S3 语义、可整体迁移"的边界内。

高可用再往上走一层是站点复制（Site Replication）：两个机房各一套集群互为副本，适合容灾要求高于 EC 本地容错的场景——注意它是整站复制，容量开销回到"双份"量级，一般只给核心 bucket 开。监控侧，MinIO 原生暴露 Prometheus 指标（磁盘离线数、heal 队列深度、节点在线数），把"离线盘数 ≥ M-1"设为高危告警——离写仲裁只差一步的时刻，必须有人知道。

04实战：从源码构建到拔盘演练

安装（2025-10 后的正确姿势）

# 方式一：源码直装（官方推荐，需要 Go 工具链）
go install github.com/minio/minio@RELEASE.2026-XX-XX   # 锁定版本，别用 latest

# 方式二：Dockerfile 自建镜像（纳入自己的 CI 与 CVE 扫描流水线）
# 官方仓库提供 Dockerfile，构建后推到内部镜像仓库，禁止再拉公网 lastest

4 节点 × 4 盘集群（systemd 托管）

# /etc/default/minio —— 四个节点同一份配置
MINIO_VOLUMES="http://node{1...4}/data{1...4}"   # 拓扑在此声明，初始化后不可改
MINIO_OPTS="--console-address :9001"
MINIO_ROOT_USER=minioadmin
MINIO_ROOT_SECRET_KEY=********            # 新版已从 PASSWORD 更名为 SECRET_KEY
MINIO_SERVER_URL="https://minio.internal:9000"  # 对外统一入口（LB 后面四节点）

# 每节点启动（盘为裸 XFS 直挂，无 RAID 无 LVM）
minio server $MINIO_VOLUMES $MINIO_OPTS

# mc 初始化：设置纠删档位（只影响新写入对象！）
mc alias set cluster https://minio.internal:9000
mc admin config set cluster storage_class standard=EC:4   # 写前定准，避免新老对象档位混杂
mc admin service restart cluster

验收：三件事 + 一次拔盘演练

mc admin info cluster          # ① 4 节点 16 盘全在线，显示纠删集拓扑
mc mb cluster/audit-img       # ② 建桶 + 试写试读一个对象
mc admin prometheus generate cluster  # ③ 接入监控：盘离线 / heal 队列 / 节点数

# 拔盘演练（上线前必做，测试环境）：
#   拔 1 块盘 → 读写正常，heal 队列开始工作
#   插回新盘 → mc admin heal 触发，受影响对象逐个重建
mc admin heal -r cluster/audit-img   # 手动兜底，日常后台 heal 会自动做

05今日要点

  • 纠删码的本质是用数学换容量：N=K+M，任意 K 个分片可还原对象；EC:4/16 盘 = 75% 存储效率 + 容忍任意 4 块盘故障，比双副本省一半容量、比 RAID6 容错翻倍且按对象修复。
  • 两条仲裁规则决定一切降级行为：读仲裁 = K，写仲裁 = K（M 恰为 N/2 时 = K+1 防脑裂）。16 盘 EC:4 坏 0~3 块全功能、4 块压线、5 块对象不可读写；换盘窗口必须当紧急事件处理。
  • 拓扑是"一次性决定"：纠删集数量与大小初始化后定死，扩容 = 加服务器池（新数据落新池）；节点数 ≥ 4、每节点盘数一致、盘独立直挂是三条铁律。
  • EC 配置跟着对象走：改 storage_class 只影响新写入，老对象不迁移——放量之前定准档位，别让集群里两代 EC 混居。
  • 2025-10 分发变局是供应链风险课：社区版 source-only、控制台精简、AGPL 边界——锁版本自建镜像、运维去控制台化、保留 S3 语义的可迁移性，是三条底线动作。

06架构师思考题

题目一：测试环境为省机器，用 2 节点 × 4 盘部署了 MinIO（单纠删集 8 盘，EC:4）。某天两节点之间的网络中断（进程都活着，各自还能服务各自的客户端）。这个集群此时能读吗？能写吗？会不会出现"两边各自写入、数据分叉"的脑裂？为什么官方坚持最小生产拓扑用 4 节点？▶ 点击展开解析

🔍 推演过程

先算参数：8 盘纠删集，EC:4 → K = 8 − 4 = 4，M = 4 恰好等于 N/2。网络中断后两侧各剩 4 块盘：

  • 读：读仲裁 = K = 4，两侧各有 4 个分片，恰好满足——两侧都能读（注意能读到的是"中断前"的一致视图）；
  • 写：因为 M = N/2，写仲裁升级为 K+1 = 5，两侧都只有 4 块盘 → 两侧都拒绝写。集群整体退化为"只读"，不会分叉。

这正是 K+1 规则的设计意图：把纠删集对半劈开时，数学上保证任何一半都无法独立满足写条件。若没有 K+1，两侧各 4 盘 = 各自满足 K=4 的写仲裁，同一个对象就能在两半各写出一个版本，网络恢复后谁覆盖谁？——脑裂了。K+1 用"多要一票"掐灭了这种可能。

✅ 为什么最小生产拓扑是 4 节点

  • 2 节点部署把"单节点故障"放大为"纠删集丢一半分片"：4 盘×EC:4 压线、EC:3 直接失能；而 4 节点×4 盘时单节点离线只丢 4/16 个分片，EC:4 下集群读写 heal 全不受影响——节点数决定了"单故障域吃掉纠删集的比例"；
  • 同理，每节点盘数也要克制：16 盘纠删集配 8 节点×2 盘（单节点离线丢 2 分片）比 2 节点×8 盘（丢 8 分片）健康得多。省机器的正确位置在"盘的容量"，不在"节点数量"；
  • 运维推论：测试环境 2 节点可以，但要写进架构决策记录——该拓扑读可用但写脆弱，且任何对半分区都是全只读，别把测试环境的省机器方案带进生产。
题目二：影像平台 3 年全量 900TB（净数据）。你提的方案是 8 节点 × 8 盘 × 16TB。请算出：纠删集数量、EC:4 下的可用容量、这个配置能不能撑住 3 年；如果能再加 4 节点扩容，容量和数据分布会发生什么，老数据要不要迁？▶ 点击展开解析

🔍 第一笔账：初始方案根本不够

8×8 = 64 块盘，纠删集大小 16 → 64 / 16 = 4 个纠删集。裸容量 64 × 16TB = 1024TB；EC:4 可用 = 1024 × 12/16 = 768TB；再按 80% 水位算安全可用到 ~614TB < 900TB——不够。若退到 EC:2 换 87.5% 效率（896TB × 0.8 ≈ 717TB）仍不够，且 EC:2 低于生产线，直接排除。纠删码的容量账必须写进采购评审，下单前算，不是上线后算。

✅ 正确姿势：按需求反推盘数

900TB ÷ 0.8 水位 ÷ (12/16) = 1500TB 裸容量 → 96 块 16TB 盘（12 节点 × 8 盘，6 个纠删集）或等价拓扑；可用 1152TB，水位 78%，达标。另一个方向是压单盘容量需求：冷数据走 ILM 分层到更廉价的纠删集/池——但那是优化项，不是达标项。

🔍 第二笔账：扩容加 4 节点之后

假设初始就上了 8 节点（768TB 可用），一年后加 4 节点 × 8 盘 = 新服务器池（512TB 裸，同样 4 个纠删集）：

  • 容量：集群总可用 = 768 + 512 × 12/16 = 1152TB，按池加权，立即可用；
  • 数据分布：老对象不会自动迁移——扩容不改老池的纠删集（拓扑定死），新写入优先落新池，老数据原地不动直到生命周期策略处理；想要均衡需要主动迁移：测试侧用双写灰度切换，存量用 mc mirror 搬到新池 bucket，校验对象数与 etag 后切换别名——本质是一次数据搬迁项目，要有窗口与回滚预案；
  • 别忘元数据一致性：迁移期间写放大的对象要处理版本（开启 versioning 的桶 mirror 要带 --versions），断点续传与校验是迁移工具链的必备能力。

一句话：纠删码集群的扩容语义是"加池不加盘"——容量立即并网、数据不自动重排；把"什么时候必须整体搬迁"想清楚再动手，是这类系统容量治理的核心。
