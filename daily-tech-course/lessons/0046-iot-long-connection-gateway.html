千万级设备长连接网关架构：从 LB 到内核的接入层工程

01一次接入层连环事故：平台还有容量，就是"进不来、留不住"

某车联网平台扩容到 500 万台车，架构是上一讲的"标准答案"：两台 Nginx stream 做 TLS 卸载 + 四层代理，后面挂 8 节点 EMQX（全 Core）。按容量评审，EMQX 集群还有一倍余量。大促前 30 万台新车集中激活，事故分两段爆出来：

第一段：新设备注册不了。激活高峰集中在凌晨，大量车辆 TCP 连上后被直接 reset。排查发现第一台 Nginx 的内存爆了——不是业务进程，是 Nginx 每条连接一个 worker 侧开销 + TLS 会话缓存把 32GB 吃穿；再看监控，单台 Nginx 的 established 连接已经爬到 40 万，而它上面跑的还有安全组件，conntrack 表（连接跟踪表，内核给防火墙/NAT 记录每条连接的四元组）默认 65535 条目已经打满，内核日志里全是 nf_conntrack: table full, dropping packet——新包被丢，应用层还有余量，包在内核就被扔了。

第二段：在线的设备也在掉。扩了两台 Nginx 缓过第一波，三天后轮巡发现凌晨总有批量掉线。抓包看到：部分车辆的运营商 NAT 比较激进，空闲连接约 5 分钟就被回收，而车机心跳是 10 分钟——连接实际已被运营商中间设备断掉，服务端要等 1.5 × keepalive（15 分钟）才判死，下发指令全部超时。同时单台 Nginx 的 CPU 在凌晨两点规律性打满——正是另一批设备集中重连的时刻，每条重连都要重跑一次完整 TLS 握手，ECDHE 非对称运算把CPU烧掉，TLS 新建连接是 CPU 密集操作，一台 16 核机器每秒也就消化几百条。

复盘的结论很扎心：EMQX 集群本身还有一倍余量，卡死的是它前面那层"顺手用 Nginx 搭的"接入层。长连接接入层从来不是"加个 LB"这么简单——它是容量、内核、TLS、网络四本账叠加的独立工程域。

02原理：四层 LB 在百万长连接面前的四个先天上限

上限一：每条连接都是有成本的，代理与不代理差一个量级

先立一把尺子——C10K 是编程问题，C1000K 是系统工程问题。1999 年 Dan Kegel 的 C10K 论文推动了 epoll/IO 多路复用的普及，今天单机 epoll 写法扛十万连接是基本功；但从十万到一百万，瓶颈从"程序怎么写"变成"内核参数、文件句柄、内存、conntrack、中断分布"的叠加。WhatsApp 2012 年在 FreeBSD + Erlang 上把单机做到 200 万+ 连接，靠的就是把这整串系统参数逐个调透。代理模式的致命处在于：连接成本要付两遍。客户端→LB、LB→后端各是一条完整连接，各占句柄、各占内存、各进一张连接表；更贵的是 NAT 模式下响应流量也要过 LB，每包都要查表改写。LVS NAT 模式在千兆环境下单机 CPU 70% 时大约 5~8 万并发就开始恶化——这与长连接接入需要的百万级差一个量级还多。

上限二：单 IP 只有 65535 个端口，NAT 模式的数学天花板

这是最像"脑筋急转弯"却最硬的一条：LVS NAT / Nginx stream 这类代理或 NAT 模式，LB 要用"本地IP:随机端口"去连后端。一条 TCP 连接由四元组（源IP、源端口、目的IP、目的端口）唯一标识——LB 对同一台后端的同一端口，源侧只有 ip_local_port_range（默认 32768~60999，约 2.8 万个端口）可用。单（VIP×后端IP×后端端口）组合就是 6 万端口硬顶，连 10 万设备都撑不住，更别提百万。解法有三条路：多 VIP 或多后端端口做乘法、开大 ip_local_port_range 到 1024~65535（治标，翻一倍也就 6.4 万）、或者干脆不走 NAT——这就是 DR 模式存在的意义。

上限三：conntrack——最隐蔽的一刀，丢包发生在你看见之前

Linux 上只要加载了 iptables/nftables（云主机几乎必然），每条连接都会在内核 conntrack 表里占一条。默认 nf_conntrack_max 常见值 65535，表满后内核直接丢新包——应用层一切健康，监控毫无异常，就是有设备连不上，这是 01 节第一段事故的元凶。调整公式：CONNTRACK_MAX = 内存字节数 / 16384 / 2（64GB 机器约 209 万），且要同步扩哈希桶（建议 buckets = max/4），只扩 max 不扩桶会把链表拖长、查询变慢。每条 conntrack 约 300 字节，200 万条约 600MB，是真实内存支出。更彻底的方案：接入链路上的 LB 和网关机器，如果不需要状态防火墙，直接 NOTRACK 卸掉 conntrack——每包省一次表查找。

上限四：TLS 在谁手上终结，谁就要付非对称加密的账

长连接接入绕不开 TLS。社区实测的两组数：EMQX 老版本 8C32G 机器，20 万 TCP 连接 CPU 10%、内存 2GB；同样机器 20 万 TLS 双向认证连接，CPU 70%、内存 31GB——内存翻了 15 倍，CPU 翻了 7 倍（SSL 会话状态驻留内存）。另一组公开压测：TCP 1GB 内存可维持约 5 万连接，TLS 只能维持约 1.5 万。EMQX 官方 FAQ 的建议就是：前面加一层 LB 做 TLS 卸载，LB 到 EMQX 走纯 TCP。TLS 的成本集中在握手的非对称运算（ECDHE/RSA），重连风暴时每条重连都全额支付一次；会话复用（Session Ticket / TLS 1.3 PSK）用对称运算替代非对称握手，能把重连的握手成本降一个量级——这是后面架构层的重点武器。

成本项量级与成因第一解法
连接内存（无 TLS）约几十 KB/连接（内核 socket 缓冲 + 进程结构），百万连接几十 GB压测定参，读写缓冲按业务报文调小
连接内存（含 TLS）翻 3~15 倍，TLS 会话状态驻留TLS 终结从 broker 剥离到接入层
conntrack 条目约 300B/条，默认表 65535 条就满，满了丢新包扩 max+buckets 或 NOTRACK
TLS 新建握手CPU 密集，单机每秒数百次量级，重连风暴全额支付会话复用 + 硬件加速 + 摊薄重连
NAT 端口单 VIP×单后端端口 6 万硬顶DR/FNAT+SES，或多 VIP×多端口乘法

03架构视角：两条主线与四本账

主线一：转发路径做减法——LVS 三模式与 DPVS

四层 LB 的本质差异在"包怎么走"。LVS 三模式：NAT 改 IP 转发，来回都过 LB，有端口天花板与双倍带宽；DR（直接路由）只改 MAC 头，响应从后端直发客户端、根本不过 LB，LB 只在建连那一个包出场，所以它对百万长连接几乎"免费"——代价是 LB 与后端必须同二层、后端要在 lo 上配 VIP 并抑制 ARP；TUN 用 IP 隧道封装，换来跨机房能力。教科书建议很直接：百万级长连接接入，DR 是标配。再往下是用户态方案 DPVS（爱奇艺开源的 DPDK 版 LVS）：内核旁路 + 独享网卡 + 无锁 per-CPU，官方口径转发性能数倍于内核 LVS、与 Google Maglev 相当；它的 SES（Session Reuse）特性专门解 NAT 模式端口耗尽——回收已结束连接的四元组复用，让 NAT 模式也能扛海量并发；还带 NAT64（IPv6 客户端进、IPv4 后端出，不改后端吃进 IPv6 流量）。云上则优先看 SLB/NLB 的规格与连接数上限。Nginx stream 这类用户态代理不是不能用，而是它的定位是"少量入口、需要七层灵活性"，让它扛百万长连接是岗位错配——01 节事故的一半根源就在这。

主线二：终结点前移——接入层独立成军

这套分层的灵魂是把"连接"从 broker 身上剥离：网关层持有连接、终结 TLS、做设备认证（认证结果本地缓存，别每条连接都打认证后端——重连风暴时那就是每秒几十万次查询）；网关到 EMQX 走内网纯 TCP，broker 只做消息路由与会话（上一讲的内容）。EMQX 官方架构建议本质就是这个形状。它的直接收益：broker 从此可以随意升级发布——设备无感知，网关自动重连后端；网关自身升级则靠"可牺牲性"：摘 LB、主动断连、设备按退避重连到其他节点。微信的后台演进公开资料里，接入层（ACCESS）与逻辑层分离、接入层无状态化随扩随加，走的是同一条路——长连接平台的接入层最后都会长成这个形状。

四本账：容量、内核、TLS、网络

账本怎么算关键参数/事实
容量账节点数 = 峰值连接 ÷ (单机压测上限 × 0.7)，再 × N+1 冗余内存主控：无 TLS 几十 KB/连接起步压；重连风暴时新建速率单机每秒千级封顶要排进模型
内核账句柄、端口、conntrack、backlog、内存逐项过file-max/nofile 百万级、somaxconn/tcp_max_syn_backlog 拉大、nf_conntrack_max 按内存公式扩或 NOTRACK
TLS 账握手 CPU 峰值 = 重连风暴速率 × 每握手成本会话复用降一个量级；ECDSA 证书 + X25519 + AES-GCM 组合最省；规模化后看 QAT 硬件卸载
网络账心跳带宽 = 连接数 × 包大小 × 频率 ÷ 压缩比百万连接 30s 心跳 ≈ 每秒 3.3 万小包（TCP+TLS 头约 100B）；中断靠 RSS/RPS 分散到多核

容量账里最容易被漏掉的是重连风暴的"速率维度"：稳态 500 万连接毫无压力的集群，在 30 万设备同秒重连时照样被打穿——上一讲算过"补发峰值 = 设备数 × 断线时长 × 频率"的消息账，这一讲补上连接账：建连速率峰值 = 设备数 ÷ 退避摊开后的时间窗。jitter 把 30 万设备从"同一秒"摊成 60 秒长尾，每秒建连就从 30 万降到 5 千——这就是"客户端参数决定服务端架构命运"的又一次应验。

04实战：百万连接节点的五道内核坎 + 一套敢上生产的配置

片段一：sysctl 五道坎（每台网关/broker 节点）

# /etc/sysctl.d/99-million-conn.conf —— 百万长连接节点
fs.file-max = 2000000                    # 坎1:系统级句柄
fs.nr_open = 2000000                     #   (nofile 上限受它约束)
net.core.somaxconn = 65535               # 坎2:accept 队列
net.ipv4.tcp_max_syn_backlog = 65535     #   半连接队列同步拉大
net.netfilter.nf_conntrack_max = 1048576 # 坎3:连接跟踪表(或 NOTRACK)
net.netfilter.nf_conntrack_buckets = 262144  #   桶=max/4，只扩 max 会拖慢
net.ipv4.ip_local_port_range = 1024 65535# 坎4:NAT/代理类组件的本地端口
net.core.rmem_max = 33554432             # 坎5:socket 缓冲按内存预算定
net.core.wmem_max = 33554432
# systemd 服务再叠一层: LimitNOFILE=2000000 (nofile 不能只改 limits.conf)
# 验收: sysctl -p && ulimit -n && cat /proc/sys/net/netfilter/nf_conntrack_count

五道坎的验收标准是压测时逐项核对余量：nf_conntrack_count 距离 max 要有 30% 以上空间；ss 统计的 established 数逼近 nofile 前就要告警；内存要给"连接数 × 每连接开销"留足预算。别忘了容器化部署时宿主机内核参数同样要调——pod 里的进程共享宿主的 conntrack 表和句柄池，这是 K8s 跑长连接网关最常见的隐形坑（0024 期讲过的 conntrack 预留是同一件事的入口侧）。

片段二：DPVS/TLS 接入层关键配置（示意）

# DPVS: FNAT 模式 + SES 端口复用（NAT 也能扛海量长连接）
./ipvsadm -A -t 10.0.0.100:8883 -s wlc
./ipvsadm -a -t 10.0.0.100:8883 -r 10.0.1.11:8883 -b
./ipvsadm -a -t 10.0.0.100:8883 -r 10.0.1.12:8883 -b
#   -b = FNAT；配套 conf: conn_reuse = 1  # SES: 回收四元组，绕开 6 万端口
#   ECMP+Keepalived 多活：router bgp 宣告同一 VIP，交换机哈希分流

# 网关 TLS（NGINX stream / Envoy 通用要点）:
ssl_protocols TLSv1.2 TLSv1.3;
ssl_session_cache shared:SSL:512m;       # 会话复用缓存(约200万会话)
ssl_session_tickets on;                  # Ticket 无状态，多网关共享密钥
ssl_ecdh_curve X25519;                   # 握手最快的曲线
ssl_certificate /etc/ssl/ecdsa-gw.crt;   # ECDSA 证书验签更快
# 到后端: proxy_pass 10.0.1.x:1883 (内网纯 TCP, TLS 成本不进 broker)

片段三：网关升级的"摘除-排空-重连"剧本

# 1) DNS/LB 摘除：新 VIP 列表不再含本节点(存量连接不受影响)
# 2) 通知设备"礼貌告别": 网关广播 disconnect 通知(带重连提示+新接入点)
#    —— 把"被断"变"主动告别", 客户端退避更平稳
# 3) 分批断存量: 每批 5% 间隔 30s, 100 万连接约 10 分钟排空
# 4) 每批重连落到其他节点, 观察集群建连速率 < 单机上限×70%
# 5) 确认本节点连接归零后升级/下线; 上线后重新加回 VIP 列表
# 逆命题也成立: 任何时刻主动 kill 一台网关 = 一次计划内演练

这套剧本的本质是承认一个物理现实：TCP 连接状态在节点内存里，进程死了连接就没了，"迁移"是不存在的。业界把 QUIC 的连接迁移（connection ID 与四元组解耦，换网不断连）当作下一代答案，但设备端协议栈支持普及之前，工程正解就是"可牺牲节点 + 快速重连"——把重连成本从"事故"降级为"例行公事"。

五个必踩的坑：① 顺手拿 Nginx/HAProxy 扛百万长连接——用户态代理的连接双倍成本 + NAT 端口天花板是岗位错配，四层海量接入的正解是 DR/DPVS/云 NLB。② conntrack 表满当网络故障查——"部分新连接超时、老的正常、dmesg 才有真相"，接入层机器扩表或 NOTRACK 要进基线。③ 只算稳态不算风暴——容量模型必须含"建连速率峰值 = 设备数 ÷ 退避窗口"，jitter 不做，多好的架构都会被同秒重连打穿。④ TLS 让 broker 自己扛——内存翻数倍 CPU 翻七倍，TLS 终结前移到网关/LB 层，broker 走内网纯 TCP，这是 EMQX 官方 FAQ 的明文建议。⑤ 升级网关想"不断连接"——连接迁移在 TCP 上做不到，别在伪需求上堆复杂度；把功夫花在"礼貌告别 + 分批断连 + 客户端退避"的剧本上。

✅ 长连接接入层体检清单

☐ 四层 LB 模式明确登记（DR/FNAT/NAT/代理），NAT 与代理类组件的 6 万端口天花板算过账　☐ LB 自身：ECMP/Keepalived 多活，响应路径不过 LB（DR）或已用 SES（DPVS FNAT）　☐ 接入链路机器 conntrack 容量核对或 NOTRACK，压测时 count/max 余量 >30%　☐ TLS 终结点在网关/LB 层，broker 到网关纯 TCP；会话复用已开且密钥多节点共享　☐ 单机内核五坎（句柄/backlog/conntrack/端口/缓冲）全部按目标连接数压测验收　☐ 容量模型含建连速率峰值维度，重连风暴演练过（主动 kill 一台网关 = 一次演练）　☐ 客户端：接入点 IP 列表缓存 + 指数退避 + jitter + 会话复用，固件预埋（事后无法补救）　☐ 网关升级走"摘除→告别→分批断→重连"剧本，断连批次与观察指标固化为脚本　☐ 运营商 NAT 超时已建模：心跳间隔 < 中间设备最短空闲回收时间的 1/2　☐ 设备路由关系在注册中心/Redis，不在网关进程内存里单点

05今日要点

  • 接入层是独立工程域：C10K 是编程问题，C1000K 是系统工程问题——句柄、端口、conntrack、TLS、中断五本账叠加，"加个 LB"不是答案。
  • NAT/代理模式的天花板是数学：单 VIP×单后端端口 65535 条四元组硬顶，响应流量还过 LB；百万长连接的正解是 DR（响应不过 LB）或 DPVS FNAT+SES（端口复用）。
  • conntrack 是最隐蔽的刀：表满丢新包，应用层一切正常；接入层机器要么按内存公式扩表，要么 NOTRACK 卸掉。
  • TLS 终结前移 + 会话复用：TLS 让连接内存翻 3~15 倍、握手 CPU 密集；终结点放网关层、broker 走内网纯 TCP、重连靠 Ticket/PSK 降一个量级。
  • 连接无状态化 + 可牺牲节点：路由关系外置注册中心，任何网关节点可被随时牺牲；升级=礼貌告别+分批断连+退避重连——TCP 上没有连接迁移，别为伪需求堆复杂度。

06架构师思考题

题目一：共享充电宝平台，200 万台设备，现架构"2 台 Nginx stream（TLS 卸载+四层代理）→ 4 节点 EMQX"。设备通过域名 + 单 VIP 接入，心跳 60 秒，TLS 单向认证，无会话复用。凌晨一次机房网络抖动 30 秒，恢复后 40 分钟不可用。① 估算抖动恢复瞬间的建连压力，指出链条上最先饱和的三个资源。② 有人说"加 Nginx 就行"——用数字说明为什么加不动。③ 给出分阶段的改造路线（先救命、再治病、后进化），每阶段各解决哪一刀？▶ 点击展开解析

🔍 逐问拆解

① 建连压力三笔账：抖动 30 秒内全部 200 万设备检测掉线、按无 jitter 的固定 1~2 秒间隔重连，假设摊在 30~60 秒窗口，每秒新建 3~7 万条连接。最先饱和的资源：第一刀 TLS 握手 CPU——每条完整 TLS1.2 握手按单核每秒几十次、整机每秒几百到一两千次的消化能力算，每秒几万条握手需要几十核专门烧在非对称运算上，2 台 Nginx 的 CPU 秒级打满，后面排队超时；第二刀 Nginx 单机连接内存——重连成功的一半连接要重建 TLS 会话状态，单机几十万连接 × 会话内存直接顶穿 32GB（01 节事故重演）；第三刀 conntrack——旧连接条目还在表里没过期（established 超时默认 5 天），新连接四元组又要加条目，表满丢包，恢复被进一步拖慢。三者互相放大：握手慢→设备更焦虑→更密集重连→更满。② 加不动的原因是乘法不成立：Nginx stream 是代理模式，单 VIP 对单个后端端口只有约 2.8~6.4 万本地端口可用，200 万连接 ÷ 6 万 ≈ 需要 30+ 个（VIP×后端端口）组合——要么 30 个 VIP（域名解析管理复杂度爆炸）、要么后端开 30 个端口（EMQX listener 配置灾难）；同时每台 Nginx 的响应流量也要过自身网卡，带宽与 CPU 随连接数线性涨。加机器能摊 CPU，但摊不掉端口数学和每台机器各自的 conntrack/内存上限——这个架构的天花板是模式给的，不是数量给的。③ 改造三阶段：救命（一周内）——固件/客户端开指数退避+jitter（把每秒 7 万建连摊成每秒几千）+ 开 TLS 会话复用（重连握手成本降一个量级）+ 两台 Nginx 的 conntrack 扩容与 NOTRACK——不改架构，先把风暴峰值压掉一个量级；治病（一个季度）——接入层换型：LVS DR 或 DPVS（FNAT+SES）+ 网关集群独立（TLS 终结+认证前移，节点数 = 200万÷(压测上限×0.7)），EMQX 退到纯 TCP 后端只做消息域；域名解析多 VIP，设备端缓存 IP 列表绕开 DNS 抖动；进化（规划）——ECMP+Keepalived 把 LB 层做成多活无单点、建连速率纳入容量模型与常态化演练（主动 kill 网关节点）、评估 QUIC/连接迁移与 IPv6 多 VIP 空间。检验标准就一条：下次同规模抖动，恢复时间由客户端退避窗口决定，而不是由服务端饱和决定。

题目二：公司长连接网关要按"每个网关节点 100 万连接"设计。给的机器是 32 核 128GB，万兆网卡，容器化部署在 K8s 宿主机上。① 逐项给出内核/系统层要过的坎与参数量级，指出哪一项最容易被漏掉。② TLS 放在哪一层终结？给出你的推理与两种方案的资源对比。③ 上线前你会设计哪三个"自残式"演练？各自验证什么？▶ 点击展开解析

🔍 逐问拆解

① 内核坎逐项过：句柄——fs.file-max 与 fs.nr_open 提到 200 万级（留余量），systemd LimitNOFILE 同步，容器内 ulimit 跟宿主 ConfigMap/启动参数对齐；端口——网关作为 DR 后端直连设备不需要本地端口池，但若走 FNAT/NAT 上游则要 ip_local_port_range 1024~65535 且评估 6 万×组合数；conntrack——按公式 128GB≈419 万条目，但宿主机上跑的不止它一个，建议 200~400 万 + buckets 四分之一同步，最容易被漏掉的就是它：pod 里一切正常，宿主 conntrack 满了丢的是所有 pod 的包，K8s 的 kube-proxy iptables/ipvs 模式本身就吃 conntrack（0024 期入口侧），两层叠加更要有宿主级监控；backlog——somaxconn 与 tcp_max_syn_backlog 65535，配合 accept 循环效率；缓冲——rmem/wmem 按业务报文（几十字节心跳）调小省内存，max 值给足峰值；中断与多核——RSS/RPS 把网卡中断摊到多核，否则单核 softirq 在每秒几万小包心跳时就成瓶颈。内存总账：100 万无 TLS 连接按 20~50KB/条 = 20~50GB，128GB 机器可行但过半，开 TLS 后要重算（可能直接翻爆）。② TLS 终结位置推理：判据是"谁付握手 CPU、谁驻留会话内存、证书轮换在哪运维"。方案 A 网关进程内终结：简单、少一跳，但 100 万 TLS 会话内存（实测口径 3~15 倍）可能把 128GB 顶穿，且重连风暴的握手 CPU 与业务转发抢同一批核；方案 B 前置专用 TLS 层（DPVS/网关分两层或 LB 卸载）：会话内存与握手 CPU 独立扩容、证书集中管理、后端纯 TCP——100 万/节点的目标下选 B，代价是多一跳延迟（内网微秒级可忽略）与多一层运维；若选 A，必须开会话复用 + 限制单节点目标连接数（比如 50 万）并单独压握手峰值。资源对比一句话：A 省一跳但内存弹性差，B 多一跳但两张账分开算、各自水平扩——规模越大，B 的解耦价值越高。③ 三个自残式演练：演练一"kill -9 一个网关节点"——验证可牺牲性：LB 摘除速度、设备重连摊开程度（退避+jitter 是否真实生效）、其余节点建连速率峰值与内存爬坡是否在预算内、业务侧消息补投是否幂等；演练二" conntrack 打满注入"——在预发用 iptables 统计注入或压满 conntrack 表，验证：监控告警是否在表满前触发（count/max 比率）、现象识别（新连超时 vs 存量正常）是否写进 runbook、扩容/NOTRACK 预案是否可一键执行；演练三"TLS 证书轮换 + 会话复用失效"双打——轮换证书导致旧会话票据全部失效，重连高峰全部走完整握手，验证握手 CPU 余量、Ticket 密钥多节点共享机制、证书热加载是否断存量连接。三个演练共同验证的是同一个命题：所有"峰值时刻"的行为，平时就要花钱演练，不能等事故替你演。
