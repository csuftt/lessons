KUBERNETES · Kubernetes 系列第 2 讲（流量链路篇）

流量进集群的三道门：Service、Ingress 与 Gateway API

一个请求从公网到 Pod，要过四层负载均衡、七层入口网关、Service 集群内转发三道门。今天把整条链路拆开讲：EndpointSlice 如何维护"就绪名单"、iptables 为什么会在 Service 上千后拖慢发布、滚动发布 502 的真正根因，以及 2026 年 3 月起 ingress-nginx 正式退役后，入口选型该怎么重做。

01一次"发布就 502、扩容更卡、审计还红了"的复盘

小程序商城平台大促演练夜，三个报警先后爆出来：

  • 发布侧：每次滚动发布，网关 5xx 错误率都会尖刺 20~30 秒——明明是"无损"的滚动策略，监控里却像掉了一波机器；
  • 集群侧：平台上线一年，Service 数量涨到 3000+，每次发布后流量规则要好几秒才收敛，发布高峰节点 CPU 系统态（sys）飙到 40%；
  • 审计侧：安全扫描直接亮红灯——集群入口用的社区版 ingress-nginx 控制器已于 2026 年 3 月正式退役（仓库归档只读、不再有安全补丁），它还是整个集群唯一直接暴露在公网的组件。

这三个问题分别落在流量链路的三层：入口层（Ingress/Gateway 的选型与治理）、转发层（Service 与 kube-proxy 的规则机制）、发布协同层（EndpointSlice 与网关的信息同步）。今天自上而下把这条链路讲透。容量弹性（Pod 怎么扩缩）见0016 期 HPA，本期专注"流量怎么进来、怎么找到 Pod"。

02原理：南北向流量的五跳链路

Service 提供稳定地址，EndpointSlice 提供真实名单——这是理解链路的钥匙。Pod IP 随调度漂移、随发布更替，Service 用一个不变的 ClusterIP 把"找谁"的问题接走；而"此刻有哪些 Pod 已就绪"由 EndpointSlice 对象维护：端点控制器 watch 每个 Pod 的就绪条件，就绪则加地址，失联/退出则摘除。网关和 kube-proxy 都是这份名单的订阅者。注意最后半句：订阅是异步的——这正是滚动发布 502 的伏笔。

kube-proxy 三种模式：iptables 为什么会"越用越慢"

模式转发机制复杂度适用
userspace用户态进程中转—历史产物，已淘汰
iptables（默认）内核规则链，顺序匹配 + DNAT线性 O(规则数)中小规模集群
ipvs内核哈希表 + 调度算法查找 O(1)Service 上千 / 高频发布

iptables 模式的规则量 ≈ Service 数 × 每个 Service 的后端数 × 2~3 条规则，且每次端点变更都要全量重建规则链。3000 个 Service、平均 3 个后端就是两三万条规则——发布高峰端点频繁增删，规则同步排队、CPU sys 飙高就是这么来的。ipvs 模式把后端表放进内核哈希结构，查找常数时间、更新增量进行，还自带轮询/最少连接/源地址哈希等调度算法。经验阈值：Service 超过 ~1000 个或发布频繁的大集群，切 ipvs（注意先确认内网 CNI 与 conntrack 配置兼容，留好回滚预案）。

滚动发布 502：一个 1~2 秒的窗口

另一个 502 变种正好相反：新 Pod 还没就绪就接流量——应用进程起来了但依赖没连上（数据库、注册中心），请求进来照样 5xx。这就是 readinessProbe 没配或配得过松的代价。两道保险一个管"退出侧"、一个管"进入侧"，缺一不可。

03架构设计：2026 年的入口选型

⚠ 必须面对的事实：ingress-nginx 已于 2026-03 退役 Kubernetes SIG Network 与安全响应委员会于 2025-11 公告：社区维护的 kubernetes/ingress-nginx 进入 best-effort 维护，2026 年 3 月起停止一切发布、修复与安全补丁，仓库转为只读。根因是长期维护者枯竭（仅一两名志愿者），叠加 snippets 类注解允许注入任意 NGINX 配置、成为安全负债（IngressNightmare CVE-2025-1974 直接暴露了这个问题）；原定接棒的 InGate 项目也未成熟、一并退役。注意三个"不是"：Ingress API 本身没有被移除（仍可用但功能冻结）；NGINX 软件本身不受影响；F5 维护的 nginxinc/kubernetes-ingress 是另一个项目、仍在维护。已有部署不会立刻故障，但"无补丁的公网暴露面"每天都在积累风险。
路线做法优点代价
A. Gateway API（推荐） GatewayClass / Gateway / HTTPRoute 三层资源 + 一个实现（Envoy Gateway、Istio、Cilium、NGINX Gateway Fabric 等） 社区主推方向；角色分离适合多团队；流量切分/重写/跨命名空间授权是标准字段；CRD 已 GA（L4 Route 亦转正） 清单需重写（ingress2gateway 可自动转换 30+ 常用注解）；少量长尾注解要人工设计
B. 换维护中的 Ingress 控制器 Traefik / HAProxy / F5 nginxinc 等，继续用 Ingress API 改动最小，Ingress 清单基本不动 nginx 系注解要手工翻译；Ingress API 功能冻结，将来大概率二次迁移
C. 云上七层入口 ALB / Application Gateway 等托管 L7 免运维、有 SLA 绑定云厂商；自建机房不可用

决策建议：新集群直接 Gateway API 起步；存量集群把网关并行双跑（两套入口共存，按 Host/路径逐业务灰度切流），用 ingress2gateway print 生成初版清单再人工核对长尾注解；集群只剩一年寿命且路由极简，可以选 B 过渡——但要写进架构决策记录，明确"这是还债不是终点"。

入口层的高可用与容量要点：

  • 网关多副本 + 反亲和：入口控制器至少 2 副本打散在故障域（节点/可用区）；DaemonSet + hostNetwork 是自建机房的经典形态，四层 LB 对节点 80/443 做健康检查，节点挂了流量自动摘——入口自身不成为单点；
  • 证书与域名解耦：cert-manager 管 TLS 生命周期，external-dns 管解析，网关只声明"我要什么"；
  • 连接容量：网关节点的 conntrack 表与文件句柄要按"长连接数 × 每连接开销"预留（WebSocket 密集场景尤其），单节点十万级长连接前先压测内核参数；
  • 边界提示：Gateway API 也能建模东西向（服务间）流量（GAMMA initiative），但那是 Service Mesh 的领地——Istio 流量治理留给"云原生前沿"系列展开，本期只管南北向。

04实战：从 Ingress 注解到 HTTPRoute

老写法：Ingress + 私有注解（ingress-nginx 风格）

apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: mall-api
  annotations:
    nginx.ingress.kubernetes.io/rewrite-target: /$2   # ← 控制器私有注解，换实现就失效
spec:
  ingressClassName: nginx
  rules:
  - host: api.mall.example.com
    http:
      paths:
      - path: /v1(/|$)(.* )
        pathType: ImplementationSpecific
        backend: { service: { name: mall-api, port: { number: 80 } } }

新写法：Gateway + HTTPRoute（标准字段，金丝雀切分原生支持）

# 运维侧：网关实例（一个 Gateway = 一个负载均衡实体）
apiVersion: gateway.networking.k8s.io/v1
kind: Gateway
metadata: { name: public-gw, namespace: gateway-infra }
spec:
  gatewayClassName: envoy
  listeners:
  - name: https
    port: 443
    protocol: HTTPS
    tls: { mode: Terminate, certificateRefs: [{ name: mall-tls }] }
    allowedRoutes:                       # 哪些命名空间的路由能挂上来
      namespaces: { from: Selector, selector: { matchLabels: { gw-access: "true" } } }
---
# 业务侧：路由规则写在业务自己的命名空间
apiVersion: gateway.networking.k8s.io/v1
kind: HTTPRoute
metadata: { name: mall-api, namespace: mall }
spec:
  parentRefs: [{ name: public-gw, namespace: gateway-infra }]
  hostnames: ["api.mall.example.com"]
  rules:
  - matches: [{ path: { type: PathPrefix, value: /v1 } }]
    filters:
    - type: URLRewrite                        # 路径重写是标准字段，不再靠注解
      urlRewrite: { path: { type: ReplacePrefixMatch, replacePrefix: / } }
    backendRefs:
    - { name: mall-api,        port: 80, weight: 90 }   # 金丝雀：90% 稳定版
    - { name: mall-api-canary, port: 80, weight: 10 }   # 10% 灰度版

无损发布三板斧（Deployment 侧）

readinessProbe:                    # 进入侧：没就绪不进名单
  httpGet: { path: /actuator/health/readiness, port: 8080 }
  periodSeconds: 5
lifecycle:
  preStop:                          # 退出侧：等名单摘干净再死
    exec: { command: ["sleep", "15"] }
terminationGracePeriodSeconds: 30

kube-proxy 切 ipvs + 排障命令

# 切换（kubeadm 集群）：
kubectl -n kube-system edit cm kube-proxy     # mode: "ipvs"
kubectl -n kube-system rollout restart ds kube-proxy
ipvsadm -Ln | head                            # 验证：能看到 Service 的虚拟服务表

# 排障三件套：
kubectl get svc mall-api -o wide              # ① ClusterIP 是否在
kubectl get endpointslices -l kubernetes.io/service-name=mall-api
                                              # ② 就绪地址数对不对（0 = 全部未就绪）
kubectl -n mall exec deploy/mall-api -- curl -s localhost:8080/actuator/health
                                              # ③ 应用自己健康吗

✅ 入口链路体检清单

☐ 网关 ≥2 副本且反亲和 / LB 健康检查指向节点端口　☐ ingress-nginx 退役风险已有迁移决策（目标与时间表落纸）　☐ readinessProbe + preStop sleep + 连接排空三件齐　☐ Service 上千的集群评估过 ipvs 模式　☐ EndpointSlice 就绪数接入监控与告警　☐ cert-manager/external-dns 接管证书与解析　☐ 网关节点 conntrack / fd 容量按长连接压测过　☐ 演练过"摘一个网关节点""杀一个 Pod"两类故障

05今日要点

  • 链路的钥匙是"两个对象"：Service 提供稳定 ClusterIP，EndpointSlice 维护"此刻哪些 Pod 就绪"的真实名单；网关与 kube-proxy 都是名单的异步订阅者——异步，就是 502 的窗口。
  • iptables 随规模线性恶化：规则量 ≈ Service × 后端 × 2~3 且端点变更全量重建；Service 上千或高频发布的集群切 ipvs（内核哈希 + 调度算法），留回滚预案。
  • 无损发布三板斧缺一不可：readinessProbe 管进入侧、preStop sleep 弥合名单传播窗口、网关连接排空保长连接——只配一个都不叫无损。
  • ingress-nginx 已于 2026-03 退役：仓库只读、无安全补丁，而它是公网暴露面。新集群直接 Gateway API；存量双跑灰度迁移（ingress2gateway 自动转换 + 长尾注解人工设计）。
  • Gateway API 的本质是角色分离：GatewayClass 归平台、Gateway 归运维、HTTPRoute 归业务团队，跨命名空间用引用授权——多团队协作的边界从"约定"变成"API 权限"。

06架构师思考题

题目一：你们的入口网关是 DaemonSet + hostNetwork 部署，四层 LB 后面挂着全部 6 个节点。某天凌晨一个网关节点内核崩溃。① 此时正在 established 状态的长连接（WebSocket）会怎样？② 流量多久能恢复？③ 如果老板问"能不能做到用户完全无感"，你的改造方案是什么？▶ 点击展开解析

🔍 逐问拆解

① 存量长连接全部断开。四层 LB 的健康检查摘除只影响"新连接"的分配；已经建立在崩溃节点上的 TCP 连接随内核一起消失，客户端会收到 RST 或直接超时——WebSocket 客户端的自动重连逻辑此时是唯一救命的稻草，所以它必须是客户端标配而不是可选项；

② 新流量恢复时间 = 健康检查检测周期。LB 摘节点要等"连续 N 次探测失败"（典型配置 3 次 × 5 秒间隔 ≈ 15 秒内）。要压缩这个窗口：探测间隔与阈值调紧、探测目标从节点端口改为网关健康端点（区分"节点活着"和"网关能服务"）；

③ "单节点完全无感"在四层摘除模型下做不到，但可以把影响压到"重连一次"：

  • 客户端：指数退避自动重连 + 会话恢复（令牌重附着），把"断"变成毫秒级的抖动；
  • 接入层：LB 摘除提速之外，给网关加一层 DNS 级多入口（双 LB VIP + 健康解析），抗"整套 LB 故障"这一层；
  • 更彻底的是连接层不落在单点：长连接密集业务把接入下沉到有连接迁移能力的方案（如云厂商的接入层、或客户端多路复用/自动选路），那已经是接入架构的重新设计，不是配置调优；
  • 架构师要诚实：高可用是"故障影响的有界化"，不是"故障不存在"。把 RTO（上面 ~15 秒）、长连接断开范围（单节点上的那部分）写进 SLO，比承诺"无感"更专业。
题目二：集群里 5000 个 Service、平均每 Service 3 个后端，iptables 模式。发布高峰 kube-proxy 规则同步出现秒级排队、节点 CPU sys 飙高。① 估算规则量级并解释为什么"每次发布"都全量重建；② 切 ipvs 为什么能解决？③ 切换本身有什么风险，你的实施步骤是什么？▶ 点击展开解析

🔍 第一问：规则量的账

每个"Service-后端"对大约产生 2~3 条规则（DNAT + 概率匹配/统计链），5000 × 3 × 2~3 ≈ 3~4.5 万条，叠加 Service 自己的链与跳转规则。iptables 的匹配是逐条线性的，更要命的是 kube-proxy 的更新模型：任何端点变化 = 整张表加锁重写（iptables 无增量 API）。发布高峰每个 Deployment 的 Pod 更替都触发重建，多次重建排队叠加，就表现为规则同步延迟与 CPU sys 飙高——规则的"全量重建"是设计使然，不是配置失误。

✅ 第二问：ipvs 为什么快

ipvs 是内核里的虚拟服务表：查找走哈希（常数时间，与表大小无关），更新走增量修改（只动变化的虚拟服务/后端项，不用重写整表），并且原生提供轮询、加权轮询、最少连接等调度算法（iptables 模式的"随机式均衡"靠概率规则模拟，代价就是上面的规则量）。两个痛点——查找慢、更新贵——同时解掉。

⚠ 第三问：切换的风险与步骤

  • 风险点：① nodeLocalDNS/某些 CNI 的流量拦截方式与 ipvs 的兼容性要确认；② 会话保持语义变化（ipvs 的会话保持与 conntrack 的行为有差异，依赖"同一客户端永远同一后端"的业务要验证）；③ 切换瞬间存量连接的处理（建议逐节点滚动，不要一次全切）；④ 少数依赖 iptables 规则做网络策略的旧组件需要回归测试；
  • 实施步骤：测试集群全量验证 → 生产挑一个低峰、先切一小批节点（kube-proxy 是 DaemonSet，可以按节点分批）→ 观察规则同步耗时、CPU sys、连接错误率三个指标 → 全量切换 → 保留"改回 iptables + 滚动重启 kube-proxy"的回滚剧本；
  • 顺带的架构提醒：ipvs 解决的是"转发规则"的规模问题；如果真实瓶颈是 Service 数量本身的膨胀（微服务拆分过细、每个都建 Service），先做一次 Service 治理（合并、ExternalName、去掉无谓的抽象）可能比换模式更治本——先量化，再动手，是容量治理的通用姿势。
