Redis 数据结构与选型
同样的数据，选对结构 = 省一半内存、快一个数量级

🟥 Redis 系列 · 数据结构与选型 📅 2026-08-16 ⏱️ 预计阅读 10 分钟
SCENARIO · 从实际问题出发

🚨 全部用 String 存 JSON，一台 64G 的 Redis 被塞满了

某电商 App 需要五类缓存能力：购物车、商品销量计数、大促排行榜、每日签到、活动页 UV 统计。初期团队图省事，所有数据都用 String 存 JSON 字符串。三个月后问题集中爆发：

  • 内存爆炸：3000 万购物车 key，每个 value 是完整 JSON，序列化体积 400B+，实际有效数据只有 60B；
  • 更新低效：购物车改一个商品数量，也要 GET 整个 JSON → 反序列化 → 修改 → 再 SET，网络来回放大 7 倍；
  • 排行榜没法做：用 ZRANGE 之外的方式排序，只能拉全量数据到应用层内存排序，一次 8 秒；
  • UV 统计把内存打穿：每个访客一个 key，一天 2 亿 key，直接触发 maxmemory 驱逐，缓存雪崩。

这不是容量问题，是建模问题。Redis 是"数据结构服务器"而不是大号 HashMap——每类业务语义都对应一个最优结构。本讲从底层编码讲起，给出架构师视角的选型方法论。

PRINCIPLE · 原理讲解

📦 双层结构：命令层的"类型"与存储层的"编码"

Redis 对外暴露 9 种类型，但对内每个 key 的存储会根据数据规模与内容自动选择紧凑编码或标准结构——小数据用省内存的紧凑结构，长大了自动"升级"，过程对业务完全透明，但升级的代价必须被架构师知晓。

bashredis-cli · 用 OBJECT ENCODING 看穿存储真相
SET stock:1001 500
OBJECT ENCODING stock:1001      # → int
SET user:name "arch"
OBJECT ENCODING user:name     # → embstr（≤44B）
HSET cart:1001 skuA 2 skuB 1
OBJECT ENCODING cart:1001     # → listpack
# 往这个 Hash 塞 129 个 field 之后：
# OBJECT ENCODING cart:1001 → hashtable（再删回 128 个也不会降级！）
升级不可逆。listpack → hashtable 是单向门。线上排查"内存突然涨了一截"时，先想想是不是某批数据把一批 key 推过了阈值。同样地，渐进式 rehash 期间 dict 同时持有两张哈希表，大 key 改造期内存峰值接近 2 倍，扩容评估要留余量。

PRACTICE · 生产实战

🛠️ 重构：三个典型场景的代码级改法

① 购物车：String+JSON → Hash

redis-cli / Java (Lettuce)字段级原子更新，网络流量缩 85%
# 加购 1 件，一条命令搞定，无需读-改-写整个 JSON
HINCRBY cart:1001 sku:8848 1
# 结算时才取全量
HGETALL cart:1001
// Java 侧：RHash 结构直映射，替代 RBucket<CartJson>
RMap<String, Integer> cart = redisson.getMap("cart:1001");
cart.addAndGet("sku:8848", 1);

② 大促排行榜：ZSet 一把梭

redis-cliTop100 实时榜 + 我的排名
# 下单后原子加分（score = 销量）
ZINCRBY rank:activity:2026 1 "sku:8848"
# 实时 Top 100（带分数），O(logN + M)
ZREVRANGE rank:activity:2026 0 99 WITHSCORES
# 查某商品排名（返回 0-based），无需全量排序
ZREVRANK rank:activity:2026 "sku:8848"
# 榜单瘦身：只留前 1 万名，防止亿级 member 撑爆 skiplist
ZREMRANGEBYRANK rank:activity:2026 10000 -1

③ 签到：一亿用户一天一个 Bitmap

redis-cli内存从 9GB+ 降到 12MB
# uid=10086 在 8 月 16 日签到（offset = uid）
SETBIT sign:20260816 10086 1
# 当日签到总人数
BITCOUNT sign:20260816
# 连续 7 天都签到的用户：AND 聚合到新 key
BITOP AND sign:7d sign:20260816 sign:20260815 sign:20260814 …
# 用户维度查 31 天签到日历：按天分桶 + BITFIELD 取位段
GETBIT sign:20260816 10086

④ 坑点排查：bigkey 与编码突变

bash线上巡检三板斧
# 采样找出大 key（低峰期执行，-i 0.1 限速防打爆 CPU）
redis-cli --bigkeys -i 0.1
# 精确测量单个 key 内存（O(1) 元素数 + 采样字节数）
MEMORY USAGE cart:1001 SAMPLES 0
# 异步删除大 key：UNLINK 代替 DEL，不阻塞主线程
UNLINK huge:key
# 渐进清空大 Hash：SCAN 游标遍历 + 分批 HDEL
真实事故模式：大促前运营批量导入 50 万 SKU 到一个 ZSet，skiplist 内存是 listpack 的 5～8 倍，且该 key 热点写集中——主线程 CPU 单核打满，所有命令 P99 从 1ms 涨到 80ms。解法：按类目分片成 100 个 ZSet（rank:{cate}:act），查询侧先合并 TopN。
SUMMARY · 今日要点

✅ 带走这 5 条

  1. Redis 是数据结构服务器：选型先看读写模式（局部更新→Hash、排序→ZSet、去重→Set/HLL、位标记→Bitmap），不要全用 String 存 JSON。
  2. 双层结构 + 阈值升级：listpack/intset 紧凑省内存但写是 O(N)；超阈值（默认 128 entries / 64B value）自动升级为 hashtable / skiplist，不可逆。
  3. 容量规划看编码：同样的数据，编码不同内存差 5～8 倍；Bitmap 让"亿级用户签到"从 9GB 变 12MB，HyperLogLog 让 UV 统计恒定 12KB。
  4. bigkey 是万恶之源：单 key 元素数控制 1 万以内，删除用 UNLINK，遍历用 SCAN，巡检用 --bigkeys + MEMORY USAGE。
  5. 热点写 key 考虑分片：排行榜按类目/分片拆 ZSet，读写压力与内存双降——这是用架构手段化解单 key 天花板。
THINK · 架构师思考题

🧠 点击展开，检验你的架构判断力

思考题 1：为什么 Redis 小数据用 listpack 而不是 hashtable？把 hash-max-listpack-entries 调大到 10000 是好主意吗？

解题方向：从两种结构的内存模型与操作复杂度入手

hashtable 每个条目需要独立的 dictEntry（约 24B：三个指针）+ 两个指针的桶数组开销 + 内存碎片，还有指针跳转破坏 CPU 缓存局部性；listpack 是一块连续内存，元素紧凑排列，只有"entry 头 + 内容 + 长度"的边际开销，且顺序遍历对 CPU L1 缓存极其友好。对于几十个 field 的小对象，listpack 通常省 4～6 倍内存。

为什么不能无脑调大阈值

listpack 的写操作（插入/修改/删除）需要原地移动后续所有字节，复杂度 O(N)；N=10000 时每次 HSET 都要 memmove 数十 KB。而 hashtable 写是均摊 O(1)。阈值本质是"内存收益 vs CPU 代价"的平衡点：默认 128/64 是官方压测的经验拐点。合理区间是 128～512，且 value 长度阈值别超过几百字节。

参考结论

小对象（如购物车、商品属性）适度调大 entries 阈值（如 256）通常划算；但要看监控指标：latency 与 instantaneous_ops，如果 HSET P99 抬升就回退。更本质的优化是控制业务建模粒度——让单个 Hash 天然只装一个领域对象的字段，而不是靠阈值兜底。

思考题 2：亿级用户的活动榜单，只奖励 Top 100，但要支持"我离上榜还差多少"。只用一个 ZSet 存全量用户可行吗？如何设计？

先算容量账（架构师第一反应）

1 亿 member 全塞一个 ZSet：skiplist 每节点 forward 指针（多层）+ backward 指针 + span/level 元数据 ≈ 90～130B/member（member 本身另算），加上伴生 dict，总量在 15GB 量级。单 key 这么大带来三个问题：主线程操作该 key 的耗时被放大（ZINCRBY O(logN)，N=1 亿 ≈ 27 层比较）、迁移/同步以 key 为单位无法并行、删除/过期会长时间阻塞。结论：单 ZSet 存全量不可行。

推荐架构：全量分片 + 冠军榜两层结构

  • 全量层：按 uid 哈希分 128 片，score:{0..127} 每片约 78 万 member（≈120MB），写入压力与内存均摊，ZINCRBY 单片 O(log 78万)；
  • 冠军层：异步任务（每 2s）对 128 片各取 ZREVRANGE 0 99，归并出全局 Top 100 写入 champion 小 ZSet，前端只读它，QPS 再高也无压力；
  • "差多少上榜"：用户读自己分数走所在分片 ZSCORE；与第 100 名分数（从 champion 取）相减即可——不需要全局排名，避开了 ZREVRANK 全量 O(logN) 且单 key 的坑。

权衡说明

两层结构引入最多 2s 的榜尾延迟——对运营型榜单完全可接受；若要求强实时，可改为写时双写（加分后判断是否 > 第 100 名分数，是则同步更新 champion），用少量写放大换实时性。这正体现了用一致性换分区容忍的分布式设计思维。
