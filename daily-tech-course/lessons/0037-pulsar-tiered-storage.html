APACHE PULSAR · Pulsar 系列第 5 讲（存储成本篇 · 分层存储）

分层存储与冷数据下沉：让消息队列的保留期不再是磁盘预算

上一讲聊了 Redis 分布式锁的服役工程，Redis 主线告一段落，今天回到十三类循环的下一站——Apache Pulsar。之前的 Pulsar 期（架构对比、订阅模型、吞吐调优、消息可靠性）都在聊"跑得快、跑得对"，这一期聊"存得起"：消息越攒越多、审计要留三年、磁盘一年买三批——分层存储（Tiered Storage）就是把"保留多久"从磁盘预算问题变成策略问题。Pulsar 是市场上第一个原生支持分层存储的消息系统（2018 年，建立在 BookKeeper 存算分离的地基上），这也是很多团队从 Kafka 迁过来的头号理由。

01一场"存储翻倍"的成本复盘

某平台的风控事件主题，为了满足审计追溯要求把保留期从 7 天改成 180 天。当时的算术很简单：日增 300GB，180 天 ≈ 54TB，把 BookKeeper 集群的 NVMe 盘从 12 块加到 60 块，"一次到位"。三个月后复盘，三个扎心的事实：① 99% 的读取发生在最近 48 小时（消费积压、故障回放、近线分析），三个月前的数据整个季度被读了 4 次，全部来自审计抽查；② SSD 的钱花在了 SATA 都嫌贵的负载上——BookKeeper 的热数据价值来自低延迟读写，冷数据躺在那里只消费"容量"这一项；③ 半年后保留期要改 365 天，再翻一倍盘，采购流程走了六周，期间只能降副本硬扛，可靠性预算被容量问题透支。

这不是 BookKeeper 的问题，是"单一存储介质扛全生命周期"的架构问题。消息的价值密度随时间衰减：写后几分钟内被消费，是最热的数据；几天内可能被回放，是温数据；几个月只等一次审计，是纯冷数据。让三种温度的数据挤同一种 SSD，等于让冷链车拉三年前的档案。分层存储的思路：热数据留在 BookKeeper，冷数据下沉到对象存储，消费端无感——这才是存算分离架构的完整兑现。

02原理：Ledger 关闭，是下沉的天然时机

能下沉，是因为 Pulsar 的存储生来就是分段的

分层存储能做且好做，根子在 Pulsar 的存储模型：Topic 的数据由 Managed Ledger（托管账本）管理，逻辑上切成一段段不可变的 Ledger（账本），分段分布式地存在 BookKeeper 上。Ledger 一旦关闭（写满滚动或超时滚动）就不可变——"不可变"是下沉工程里最值钱的性质：拷贝一个不再变化的文件，不需要锁、不需要暂停写入、不需要压缩合并（对比 LSM 存储引擎的 compaction，那是把"可变"历史的代价分期偿还）。Broker 内置的 Offloader 组件盯着已关闭的 ledger，达到阈值就把整段数据读出来、按 ledger 结构写成不可变对象传到对象存储，成功后在元数据里登记"这段在远端"，再等删除延迟到期，才把 BookKeeper 上的本地副本删掉。读取方向由 Broker 透明路由：消费者完全不知道某段数据来自 S3 还是来自 Bookie——这就是"下沉对业务无感"的全部机制。

三个时间参数，决定数据怎么走过生命周期

整个下沉流程里有三个"时间窗口"，理解它们就理解了全部参数语义：① 触发时机——offload 只在 ledger 关闭后才有得搬（自动触发加在 segment 滚动这个动作上，所以低流量 topic 的最后一次滚动要等写满，别把"配了阈值没下沉"当故障）；② 读取优先级——消息同时存在于 BookKeeper 和对象存储的窗口内，默认 tiered-storage-first 从远端读，介意冷读走网络的可以把读取优先级改成 bookkeeper-first，让本地副本优先服务；③ 删除延迟——上传成功后不立刻删本地副本，默认 4 小时（managedLedgerOffloadDeletionLagMs=14400000），给正在读这段数据的消费者留缓冲。第四个版本演进值得知道：4.0 起 PIP-350 支持禁用删除延迟（只卸载不删本地，供"远端留档 + 本地照常服务"的用法），PIP-348 让 topic 加载阶段就能触发 offload。

版本坐标（2026-09）

当前稳定版 4.2.4（2026-08-03，4.2 线）；4.0 仍是 LTS（4.0.13，安全支持到 2027-10）；5.0.0-M2 里程碑已出（生产勿用）。4.0 的分层存储脉络：Managed Ledger 大重构为可插拔实现铺路（消息 ID 不再绑定 ledger ID/entry ID）；Docker 主镜像与 pulsar-all 的合并让 offloader NAR 进了标准镜像（"装分层存储"从部署清单里消失了）。另注意 4.2.0 起 etcd 元数据后端被移除（4.0~4.1 的实验窗口结束，用过的集群要迁回 ZooKeeper 或 Oxia）——升级存量集群前先核对元数据后端。

03架构设计：把"冷热界线"画在数据上

三级规划法：界线画在哪，钱就省在哪

第一步，画冷热界线。拿最近一个季度的消费数据回答两个问题：读取发生在多新的数据上（P99 读到几小时前的数据）？跳转回放/审计抽查的频率和跨度多大？界线原则：宁可略保守——界线画在"最近 3 天"而读取 P99 落在 48 小时内，多存的成本有限；画太紧（比如 1 天）而积压高峰要回放 3 天，冷读穿透对象的延迟就进了消费链路。第二步，容量规划。BookKeeper 集群按"界线内的热数据 + 写入速率 × 恢复窗口"定容量，而不是按保留期定容量——这是分层存储带来的规划范式转变：磁盘容量与保留期解耦，保留期变成 set-retention 一行策略。第三步，成本核算。对象存储的单价通常只有高性能 SSD 的 1/5~1/10（还能再叠生命周期规则沉降到低频/归档档位），冷数据占比越高省得越多；但要把冷读延迟与出口流量费算进去——回放大跨度冷数据的场景，出口流量可能比存储费先出圈。

触发与删除参数表

参数默认值架构含义

规划完成后给自己留一个验收口径：让"热层占用"成为常驻监控指标——如果开了 offload 之后 BookKeeper 磁盘占用还在跟着保留期线性涨，说明触发配置没有生效或阈值配得太高，省钱的架构没有省到钱。

可靠性：下沉不删数据，只搬数据

安全链条是"先上传成功 → 元数据登记 → 删除延迟到期 → 才删本地副本"——任何一步失败，本地副本都在。唯一的物理真相是下沉后的数据可靠性 = 对象存储的可靠性：BookKeeper 的三副本不再覆盖已删除本地副本的冷段。所以桶策略要按生产标准配：版本控制/防误删（桶策略禁止 hard delete 也能防住管理事故）、跨区复制或异地备份按 RPO 要求选配。冷读延迟要有预期：对象存储的首字节延迟在几十毫秒量级，回放到冷段的第一条消息延迟会高，之后的顺序读会进入节奏——把"回放冷数据 P99"单独纳入压测，别让它第一次出现在审计现场。

04实战：MinIO 后端的三段落地

片段一：broker.conf 配 offloader（S3 兼容端点指向 MinIO）

# broker.conf —— 内网 MinIO 做 S3 兼容后端
managedLedgerOffloadDriver=aws-s3
s3ManagedLedgerOffloadBucket=pulsar-cold-archive
s3ManagedLedgerOffloadServiceEndpoint=http://minio.internal:9000
# 凭证走环境变量或 Vault 注入，不落配置文件
# 4.x 主镜像已内置 offloader NAR，无需再拷 offloaders 目录

片段二：namespace 级策略 + 手动触发

# 冷热界线：热层最多留 100GB，下沉后本地副本保留 1 小时再删
bin/pulsar-admin namespaces set-offload-threshold \
    --size 100G risk/events
bin/pulsar-admin namespaces set-offload-deletion-lag --lag 1h risk/events
# 审计要读三年前？保留期与 offload 是两件事，分开配
bin/pulsar-admin namespaces set-retention --size -1 --time 1095d risk/events
# 低流量 topic 等不及滚动，手动推一把
bin/pulsar-admin topics offload -s 0 persistent://risk/events/audit-track

片段三：回放三个月前的数据（消费者代码零改动）

// 重置订阅到最早位置——哪怕那段数据已在对象存储
Consumer<byte[]> c = pulsarClient.newConsumer()
    .topic("persistent://risk/events/audit-track")
    .subscriptionName("audit-replay-0929")
    .resetIncludeHead(true)   // 从头消费
    .subscribe();
// Broker 自动路由：冷段从 MinIO 拉取，热段走 BookKeeper
// 业务代码对"数据在哪一层"完全无感

四个必踩的坑：① 混淆保留策略与 offload 策略——retention 决定数据活多久（到期真删，对象存储里也删），offload 决定数据住哪里；两个维度四象限，先想清楚每个 topic 落在哪一格再动手。② 删除延迟配成 0——上传成功立刻删本地副本，正在消费这段的 reader 下一秒就变冷读，消费延迟毛刺自己造的；默认 4 小时是缓冲，压缩它要有明确理由。③ 对象存储当冷备份用却没配防删策略——桶能被任何有凭证的人清空；生产桶必须版本控制 + 删除保护，凭证按最小权限发。④ 只算存储单价不算出口流量——频繁回放大跨度冷数据时，对象存储的出口流量费可能反超存储费；高频回放需求认真评估读取优先级与回放任务的调度（错峰、限并发）。

✅ 分层存储上线体检清单

☐ 冷热界线用消费数据定过（读取 P99 落点 + 回放跨度），不是拍的　☐ BookKeeper 容量按"热窗口 + 恢复带宽"重算，不再按保留期　☐ 触发阈值（字节或时间）与删除延迟成对配置并记录理由　☐ 热层磁盘占用有常驻大盘与告警（offload 生效性的一线证据）　☐ 对象存储桶：版本控制/防误删策略开启，凭证最小权限　☐ 冷读延迟（回放首条 + 顺序读）进过压测　☐ 保留策略与 offload 策略分列台账，topic 归属象限清晰　☐ 回放任务有调度约束（错峰/限并发），出口流量费进成本报表　☐ 升级路径核对过版本坐标（4.2.x / 4.0 LTS；etcd 元数据用户先迁移）　☐ 灾难演练含"对象存储不可用"场景：热层不受影响、冷读降级路径明确

05今日要点

  • 分层存储把保留期从磁盘预算变成策略问题：热数据留 BookKeeper 保延迟，冷数据沉对象存储保成本；保留期改一年是改一行策略，不是一批采购单——这是存算分离架构的完整兑现。
  • 能无感下沉，靠的是 Ledger 不可变：offloader 只搬已关闭的 ledger，不需要锁、暂停、压缩合并；Broker 透明路由读取，生产者消费者对数据在哪一层完全无感。
  • 三个时间参数定生死：触发时机挂在 ledger 滚动上（低流量 topic 要等写满或手动推）；双副本窗口内有读取优先级可调；删除延迟（默认 4h）是消费缓冲，别轻易压成 0。
  • 下沉后的可靠性等于对象存储的可靠性：本地副本删除后，三副本不再覆盖冷段——桶的版本控制、防误删、跨区复制按生产标准配，冷读延迟与出口流量费进压测与成本报表。
  • retention 与 offload 是两个正交维度：一个管活多久（到期真删），一个管住哪里；先画好每个 topic 的四象限归属，再动配置。

06架构师思考题

题目一：你们 Pulsar 集群要新增两类 topic：A 类是设备遥测流，日增 500GB，消费延迟秒级，保留期要求 365 天供算法团队随时回放训练；B 类是交易对账流，日增 20GB，保留 7 天但每天凌晨有批处理把整个 topic 从头读一遍。① 两类 topic 的冷热界线与 offload 策略应该怎么差异化设计？② B 类"每天全量重读一遍"的模式对分层存储意味着什么——冷热界线还成立吗？③ 如果对象存储的出口流量单价折算是 SSD 存储单价的 3 倍（按 B 类的读放大折算），你的成本结论会怎么变？▶ 点击展开解析

🔍 逐问拆解

① A 类是分层存储的教科书场景。消费延迟秒级说明读取几乎全部落在最近几分钟到几小时的写入段；365 天保留、低频回放——冷热界线可以画得很激进：热层留 1~2 天（比如阈值 1TB），其余全部下沉。策略组合：字节阈值触发（set-offload-threshold --size 1T）+ 删除延迟默认或略放（回放训练是批量的、可容忍首条慢，不需要长双副本窗口）；保留期 365 天用 retention 配，与 offload 解耦。算容量账：热层稳定在 ~1TB 出头，其余 ~180TB 进对象存储，按 SSD 与对象存储 5~10 倍价差，存储成本降到原来的 5% 量级——这就是"保留期与磁盘解耦"的直接收益。B 类恰恰相反，是个反例题眼。

② B 类每天从头读一遍 = 它根本没有"冷"数据。按读取频率定义温度，7 天前的数据每天都被读一次——它是"整条 topic 全温"。若给它配 offload，每天凌晨的批处理会从对象存储全量拉一遍，出口流量费按时计费地烧；若读取优先级设 bookkeeper-first，本地副本又不能删，offload 变成纯冗余拷贝。结论：冷热界线不是按"数据年龄"画，是按"读取温度"画——B 类的正确方案是：不 offload（或仅做远端容灾副本、本地不删，对应 PIP-350 的"只卸载不删除"用法），把批处理改造为增量读取（cursor 记位点，只读新增），或者让"每天全量重读"这个需求本身退场。这道题的考点就是防止把"分层存储"当无脑默认项——它优化的是"写后少读"的访问模式，对"周期性全量重读"的模式是负优化。

③ 出口流量费会翻转整个决策。给 B 类做个粗算：日增 20GB、保留 7 天 ≈ 140GB 常驻；每天全量重读 = 每天出口 140GB。若出口单价比 SSD 存储单价贵 3 倍（题设折算），一天的读流量费 ≈ 420GB 的 SSD 存储费，而 140GB 数据在 SSD 上放一天只要 140GB 的存储费——读 3 天就比纯 SSD 放着更贵。推广成判断式：当"日读取量 × 出口流量单价"超过"常驻数据量 × 存储单价"时，下沉是亏的。这个不等式应该进分层存储的评审清单：先量化读放大（日读取量 / 常驻数据量），再套当地价目表算账。架构师的价值不在会开功能，在于能算出这个功能在自家负载画像下是赚是赔。

题目二：故障演练中发现：对象存储（MinIO 集群）整体不可用 30 分钟。① 这 30 分钟内，正在实时消费的业务受影响吗？分"消费位点在热层"与"正好回放到冷段"两种情况讨论。② 演练还暴露了一个隐患：运维平台用同一个 AK/SK 管所有桶，一次误操作可以清空冷数据桶。设计这个桶的防误删纵深（至少三层）。③ 如果审计要求"冷数据删除必须留痕、且保留期内不可被任何单点角色删除"，你的治理方案要加什么？▶ 点击展开解析

🔍 逐问拆解

① 位点在热层：完全不受影响。写入路径不经过 offloader，实时消费读的是 BookKeeper 热层——对象存储挂掉那一刻，生产与消费照常，这正是分层架构"热路径与冷层解耦"的分红。唯一受影响的旁路是：这 30 分钟内到达触发阈值的 ledger 无法完成上传，offload 任务排队重试（4.x 的 offloader 会退避重试），热层磁盘占用短暂高于稳态——只要热层容量按"冷层故障窗口 + 写入速率"留过余量，就是无感事件，这也是 03 节容量规划里"恢复窗口"参数的用武之地。正好回放在冷段：冷读失败/阻塞。那段数据本地副本已删，唯一副本在对象存储——回放任务的读取会报错或重试。设计要点是让回放客户端有退避重试与断点续读（位点已 ack 的不重来），把"冷层故障"的影响圈定在那几个回放任务，而不是横向扩散。极端情况：若这批冷数据同时被实时业务依赖（比如新消费者 reset 到冷段追历史），那说明冷热界线画错了或业务不该这么用——回到规划层修。

② 防误删纵深三层：第一层，IAM 最小权限拆分——offloader 用独立凭证，只授目标桶的 PutObject/GetObject/ListBucket，不给 DeleteBucket、不给批量 DeleteObjects；运维平台的凭证与 offloader 凭证物理隔离，绝不用同一个 AK/SK。第二层，对象锁/版本控制 + MFA 删除——桶开启版本控制后，"删除"只是加删除标记，数据还在版本里；再叠加对象锁的合规模式（retention 期内任何人包括 root 都删不掉版本）或至少 governance 模式 + 特权角色审批。MinIO 上对应的是对象锁（Object Lock）与桶配额/桶策略的组合。第三层，元数据与物理隔离的备份副本——冷数据再往低频桶或异地做一份数据目录级备份（冷数据不可变、天然适合异步复制，增量就是新 ledger 对象），恢复演练纳入季度routine。三层合起来：误操作删不掉（一层）、删了能恢复（二层）、极端场景还有底（三层）。

③ 补两块治理：删除留痕与双人控制。删除留痕：开启桶的审计日志（MinIO 的 audit webhook / 云厂商的 CloudTrail 类），DELETE 类操作记录操作者、时间、对象清单，日志落到独立账户/独立集群，防"删证据"；配合版本控制的删除标记，天然形成"谁在何时删了什么"的账本。不可被单点删除：在对象锁合规模式之下（按 retention 策略锁到保留期满），叠加流程层双人机制——真正需要提前删数据的场景（GDPR 类删除请求）走审批流：两人复核 + 专用降权凭证执行 + 审计留痕，任何一个单点角色（包括管理员）都无法独自完成冷数据删除。架构上的最后一道闸：把"删除冷数据"这件事的触发权从运维平台手里拿走——冷数据删除只应来自 Pulsar 的 retention 策略到期（由 broker 用自己的凭证执行、有 ledger 级日志），而不是任何人工通道直接碰桶。人的操作止步于策略层，物理删除只属于系统策略——这句原则值得抄进存储治理规范。
