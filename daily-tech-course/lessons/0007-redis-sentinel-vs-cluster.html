Redis 集群方案：哨兵 vs Cluster 的选型与架构权衡

📅 2026-08-18（周二） ⚡ Redis 系列 · 第 3 讲 ⏱ 预计阅读 10 分钟 🎯 高可用 / 哨兵 / Cluster / 容量规划

一、从一个真实的容量危机说起

某社交电商的 Redis 主从架构（1 主 2 从 + 3 哨兵）平稳运行了一年，直到大促前压测暴露三个问题：

  1. 内存触顶：单实例内存 24GB，逼近 maxmemory，删除策略一旦触发，热 key 淘汰引发缓存穿透；
  2. 写瓶颈：写 QPS 峰值 9 万，单节点（64C 机器）CPU 已到 75%，无法水平扩展；
  3. 故障恢复慢：主从切换后，新从库全量同步生成 RDB + 传输 + 加载耗时 8 分钟，期间只读降级。

团队面临一个经典架构决策：继续主从+哨兵做读写分离缓解？还是引入 Redis Cluster 分片？这正是今天要拆解的问题。

二、两种方案的本质区别：HA 与扩展性

先厘清一个常被混淆的概念：哨兵解决的是"高可用"，Cluster 同时解决"高可用 + 水平扩展"。但两者的实现机制完全不同。

哨兵：旁路仲裁 + 故障转移

哨兵本身是一组独立进程（建议 ≥3 个、奇数部署），不处理数据，只做三件事：监控、仲裁、故障转移。核心流程：

  • 主观下线（sdown）：单个哨兵 ping 主节点超过 down-after-milliseconds 未响应；
  • 客观下线（odown）：达到 quorum 个哨兵都认为下线，才判定真故障；
  • 选举 leader：哨兵之间用 Raft 思想选 leader 执行转移，需 majority（n/2+1） 授权；
  • 挑选新主：按 replica-priority → 复制偏移量越大越优先 → runid 字典序，三层排序。

Cluster：数据分片 + 去中心化自治

Cluster 把数据切成 16384 个哈希槽，每个节点负责一部分槽：slot = CRC16(key) mod 16384。它没有旁路仲裁者，节点间通过 gossip 协议互相交换状态，自己完成下线判定与主从提升。客户端可连任意节点，路由不匹配时返回重定向：

  • MOVED：槽已归属他节点（迁移完成），客户端应更新本地槽位表；
  • ASK：槽正在迁移中，仅本次请求转向目标节点，不动槽位表。

三、架构选型对比：一张表定胜负

维度主从 + 哨兵Redis Cluster
数据容量受限于单机内存（建议 ≤25GB）线性扩展，数百 GB～TB 级
写吞吐单主写入，无法水平扩展按分片数线性提升
多 key 操作MGET/事务/Lua 全兼容要求 key 同 slot（hash tag）
客户端任意客户端 + 哨兵地址即可需支持集群协议与拓扑刷新
运维复杂度低，语义简单高：扩缩容需迁移槽位
适用场景缓存、容量可控、语义依赖强大规模存储、高写入、可预见的增长
💡 架构师经验法则 纯缓存场景优先哨兵：数据可从 DB 重建，容量可通过拆业务命名空间缓解，简单可靠胜过一切；当满足任一条件时上 Cluster——单实例内存预计超过 25GB、写 QPS 单点打满、或 Redis 承担了存储职责（丢失不可接受）。

四、实战配置：两套方案的关键参数

哨兵方案：必须改的三个默认值

# sentinel.conf —— 生产基线
port 26379
sentinel monitor mymaster 10.0.1.10 6379 2          # quorum=2
sentinel down-after-milliseconds mymaster 5000   # 默认30s太慢
sentinel failover-timeout mymaster 30000
sentinel parallel-syncs mymaster 1              # 逐个复制，避免带宽打爆

# ---- 被监控节点侧（防脑裂的关键）----
min-replicas-to-write 1     # 至少1个从库心跳正常才接受写
min-replicas-max-lag 5     # 从库延迟超5秒视为失联

Spring Boot 接入只需给哨兵地址，客户端自动发现真实主节点：

spring:
  data:
    redis:
      sentinel:
        master: mymaster
        nodes: 10.0.1.20:26379,10.0.1.21:26379,10.0.1.22:26379
      password: ******

Cluster 方案：从建集群到多 key 支持

# 每个节点 redis.conf
cluster-enabled yes
cluster-config-file nodes-6379.conf
cluster-node-timeout 15000   # 节点失联判定窗口

# 一条命令创建 3 主 3 从
redis-cli --cluster create 10.0.2.11:6379 10.0.2.12:6379 10.0.2.13:6379 \
  10.0.2.14:6379 10.0.2.15:6379 10.0.2.16:6379 \
  --cluster-replicas 1

# hash tag：让相关 key 落入同一分片，解锁 MGET/Lua
# user:1001:profile 与 user:1001:orders → {user:1001}:profile
SET {user:1001}:profile "..."
SET {user:1001}:orders "..."
MGET {user:1001}:profile {user:1001}:orders   # 同slot，OK
⚠️ 生产坑点清单
  • hash tag 是双刃剑：大热点用户的 key 全挤一个分片，等于人为制造热 key，热点账号要单独治理；
  • 扩容要提前规划：槽迁移期间性能下降 10%–30%，务必在低峰执行并开启客户端 ASK 重定向支持；
  • cluster-require-full-coverage 默认 yes：任一分片全挂则整个集群拒绝写——缓存场景可设为 no，牺牲一致性保可用；
  • 客户端拓扑刷新：Lettuce 需开启 enableClusterTopologyRefresh，否则故障切换后持续打到已下线节点。

五、容量规划与高可用设计要点

以开篇案例做一次规划演算：目标数据量 60GB，读 30 万 QPS / 写 9 万 QPS，单节点安全水位定为内存 70%、CPU 60%：

  • 分片数：60GB ÷ (25GB × 70%) ≈ 4 分片（向上取整，预留 40% 增长）；
  • 读写校验：写 9万 ÷ 4 = 2.25 万/分片（安全），读 30万 ÷ 4 主 + 4 从，均摊 3.75 万/节点（安全）；
  • 部署反亲和：同一分片的主从必须跨机架/可用区，避免宿主机故障导致分片整体消失；
  • 多副本跨 AZ：3 分片 × 2 副本 = 6 节点，主从分置两个 AZ，容忍单 AZ 故障；
  • 大 key 预防：单 key 超过 10KB 或集合超 5000 元素即告警，分片再大也扛不住大 key 迁移风暴。

六、今日要点

1
定位不同
哨兵只解决高可用；Cluster 同时解决高可用与水平扩展，代价是客户端和运维复杂度。
2
选型法则
纯缓存、单实例 ≤25GB 用哨兵；数据量大、写瓶颈、Redis 承担存储职责时上 Cluster。
3
哨兵防脑裂
quorum 与 majority 是两回事；节点侧配 min-replicas-to-write，失联旧主自动拒绝写入。
4
Cluster 多 key
MGET/事务/Lua 要求同 slot，用 hash tag 解决，但需警惕热点倾斜。
5
容量规划
按内存 70%、CPU 60% 水位反推分片数，主从跨 AZ 反亲和，规划期预留 40% 增长。

七、架构师思考题

Q1你们的核心缓存目前是"哨兵主从"架构，业务方希望把用户关系（关注/粉丝，约 80GB，丢失需全量重建）也放进 Redis。作为架构师，你会迁移到 Cluster 吗？迁移过程中如何保证业务无感？▶

解题方向

不要直接回答"迁"或"不迁"，先做职责切分——这是架构师与工程师的分水岭。缓存和存储的可信度要求完全不同，混布一套集群会让容量规划和故障域互相污染。

参考思路

  • 第一步：数据分层。核心缓存（可重建、延迟敏感）保留哨兵架构不动；用户关系这类"丢失不可接受"的数据，本质是存储，应迁移到 Cluster（或评估是否更适合用文档数据库承载）。80GB 已远超单机安全水位，Cluster 是合理选择。
  • 第二步：迁移方案——双写 + 灰度读。典型四阶段：① 新集群建好后开双写（以旧集群为准，新集群写失败仅告警）；② 存量数据用 SCAN 分批搬运（禁止 KEYS，每批 100–500 个 key，控制迁移 QPS）；③ 对账：抽样比对两边数据一致率，达 99.99%+ 后按流量比例灰度切读（1% → 10% → 50% → 100%）；④ 观察一周无对账差异后停旧写、下线旧集群。
  • 关键保障：双写阶段必须可回退——读流量切到新集群的开关要能在 1 分钟内拨回；迁移批任务要限速，避免打满旧集群带宽影响线上；给用户关系 key 设计 hash tag（如 {user:1001}:follows）时先采样验证 key 分布，防止倾斜。
  • 加分项：提出"迁移期间一致性窗口"问题——双写中间态下新旧集群短暂不一致，读旧集群可能读到新值、读新集群读到旧值，需要业务侧容忍最终一致或按 key 版本号对齐。
Q2Cluster 集群某分片的主从节点同时宕机（宿主机故障），此时集群整体是什么状态？默认配置下业务会受到什么影响？你如何设计配置和部署来把这个故障域控制到最小？▶

解题方向

考察对 cluster-require-full-coverage 的理解深度，以及"配置决策必须回归数据职责"的思维。同一故障在缓存场景和存储场景下，正确答案截然相反。

参考思路

  • 状态分析：该分片的 16384/N 个槽无节点服务，其余分片健康。默认 cluster-require-full-coverage yes 时，整个集群对所有槽不完整的写请求返回 CLUSTERDOWN 错误——不是只挂 1/N 流量，而是全部写不可用，这是很多人踩过的最惨烈的坑。
  • 配置决策：① 纯缓存场景 → 设为 no，牺牲该分片数据的可用性换取其余 1-1/N 流量正常，配合缓存 miss 回源 DB 兜底，代价是 DB 短时压力升高（要预估回源放大倍数）；② 存储场景 → 保持 yes，宁可整体拒写也不能让部分 key 悄悄消失——可用性故障可修，静默丢数据是事故升级。
  • 部署层控制故障域：① 主从强制反亲和（跨机架/跨 AZ），用 K8s podAntiAffinity 或云厂商置放组硬性保证，从根上消除"主从同宿主机"的可能；② 增加副本数：核心数据 3 副本（1 主 2 从），容忍双节点故障；③ 监控前置：对 cluster_state、cluster_slots_ok、复制延迟 master_repl_offset差值 配置告警，故障切换发生时 30 秒内触达值班人。
  • 恢复预案：节点拉起后若数据目录完好，会自动重新加入并追增量；若数据丢失，从备份（RDB+备份中心）恢复后以新节点身份空槽加入，等待槽位重分配——预案里要写清楚两种路径的操作步骤与预计耗时。
