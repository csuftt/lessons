KUBERNETES · Kubernetes 系列第 5 讲（第二轮循环 · 存储篇）

Kubernetes 存储卷：PV、PVC 与 CSI 的引力场

有状态负载上 K8s 的第一课往往不是怎么写 YAML，而是被"磁盘"教育：PVC 卡在 Pending、节点挂了数据库 Pod 半小时起不来、删了 StatefulSet 云盘还在悄悄扣费。这一讲把存储这条链拆开看——PV、PVC 与 StorageClass 是"谁要盘、谁给盘、按什么规格给"的三张契约，CSI 是把存储厂商挡在 K8s 发布周期之外的隔离层。存储最容易被忽视的属性是它的"引力"：盘在哪个可用区，Pod 就被钉在哪个可用区，调度器不是不想搬，是物理上搬不动。从一起节点宕机引发的跨 AZ 漂移失败讲起，讲清绑定、拓扑、挂载三道关卡与回收策略的生死簿，最后给出"数据库到底该不该上 K8s"的四问决策法。

01场景：一次节点宕机，数据库"失联"35 分钟

时间线还原

某平台把 MySQL 主从跑在 K8s 上（StatefulSet 3 副本，云盘走 CSI 动态制备），一个周二下午，一台承载 mysql-0 的节点硬件故障宕机。接下来的 35 分钟里值班同学经历了三连问：

  • 为什么 mysql-0 不在新节点上重建？Pod 一直 Terminating/Unknown。原因：StatefulSet 有"at-most-one"语义——同一序号的 Pod 在任何时刻至多一个，旧 mysql-0 的卡死状态没解除前，控制器不会创建新的 mysql-0，否则两个实例共写一块盘就是数据损坏。节点 NotReady 后控制面默认要等约 5 分钟（pod-eviction-timeout 相关机制随版本演进为按 taint 驱逐）才把 Pod 标记为可强制处理，而谁也不敢随手 --force --grace-period=0——万一节点只是网络抖动又回来了，两个 mysql-0 同时挂一块盘。
  • 强制删除后为什么还起不来？新 Pod 卡在 ContainerCreating，事件里报 Multi-Attach error：云盘仍挂在死节点上。块存储默认 ReadWriteOnce，一块盘同时只能挂一台机器，attach/detach 是云控制面侧的操作，死节点来不及执行 detach，新节点要等云厂商超时（典型 6~10 分钟）接管卷。这 6~10 分钟里数据库主节点没有磁盘，谁也救不了。
  • 为什么最后还差一点？强制删除后新 Pod 调度到了另一个可用区的节点，事件报 volume node affinity conflict——盘在 AZ-a，Pod 被安排在 AZ-b，卷的拓扑约束直接拒绝调度。存储有引力：卷在哪个区创建，使用它的 Pod 就被钉死在哪个区。

复盘：三个问题其实是同一件事

把三条时间线叠起来看：约 5 分钟等控制面确认节点死亡 + 6~10 分钟等云盘强制脱离死节点 + 拓扑约束下等 AZ-a 有可调度节点。三段等待没有一段是"K8s 不行"，全是存储的物理属性在起作用——磁盘不可网络化移动、块设备不能多机共享、数据有地理位置。这正是 0043 讲控制循环时埋下的伏笔：无状态负载的恢复是"找一个健康节点重拉容器"，有状态负载的恢复是"等存储的世界恢复可挂载状态"。前者秒级分钟级收敛，后者每一步都在跟物理和云厂商的超时打交道。

一句话病灶

无状态世界里"节点挂了就漂移"是肌肉记忆；有状态世界里数据的引力大于调度的自由。存储架构设计的本质不是选哪个盘快，而是设计好"盘与节点与可用区"的绑定关系，并诚实计算故障时的恢复时间预算。

02原理：三张契约与一个隔离层

PVC → StorageClass → PV：一次动态制备的完整链路

用户不直接要盘，而是提交一张"申请单"PVC（要多大、什么访问模式、哪个类）；StorageClass 是"供货目录"（谁供货、什么参数、怎么绑定）；PV 是"到货的实物"（后端真实卷的映射）。动态制备的完整链路：

链路上有三道关卡，卡住的位置不同，症状不同：绑定关（PVC Pending：没有匹配的 PV 或制备失败）、拓扑关（Pod Pending：卷的区与节点的区对不上）、挂载关（ContainerCreating：attach/mount 超时或 Multi-Attach 冲突）。排障先定位卡在哪一关，再看对应组件的事件与日志。

WaitForFirstConsumer：先定 Pod 再定盘

StorageClass 的 volumeBindingMode 决定"什么时候创建盘"。Immediate 是 PVC 一提交就建——但如果 Pod 因为亲和性只能跑在 AZ-b，而盘已经建在了 AZ-a，就是一场必输的调度。生产默认应该用 WaitForFirstConsumer（WFFC）：推迟到第一个使用它的 Pod 完成调度后，再按 Pod 所在的拓扑创建卷——先定人再定房，卷与计算天然同区。这条配置是防"Day 1 分区碎片"的第一道保险，也是公开故障复盘里被反复点名的清单项。

CSI：把存储厂商挡在发布周期之外

2018 年以前存储插件长在 K8s 主仓库里（in-tree），存储厂商改一个 bug 要跟 K8s 发版节奏。CSI（Container Storage Interface，容器存储接口）是一份独立演进的 gRPC 规范（2019 年随 K8s 1.13 GA 对接，规范自身已迭代到 v1.13.0），三个服务各管一段：Identity 报身份能力、Controller 管"建盘/删盘/快照/扩容"这类集群级操作、Node 管"格式化/挂载"这类节点级操作。K8s 侧由一组 sidecar（external-provisioner/attacher/resizer/snapshotter）监听 API 对象并翻译成对驱动的 gRPC 调用。对架构师的价值：存储能力矩阵（能不能扩容、能不能快照、支不支持 RWX）由驱动实现决定，选存储先查驱力的能力表，而不是假设 K8s "天然支持"。近年的演进方向是把"卷"变成更接近云原生的消费体验：1.31 起 volumeAttributesClassName 支持 PVC 建后换挡（1.34 GA）——先建银牌卷再在线升金牌 IOPS，不用重建卷；快照与扩容均已标准化为 CRD + 控制器。

回收策略：删除的语义是"策略"不是"按钮"

PV 的 persistentVolumeReclaimPolicy 决定 PVC 删除后盘的命运：Delete（默认，动态制备）连后端卷一起删；Retain 保住数据等人工处理；Recycle 已废弃。两个高频踩坑：删 StatefulSet 不删 PVC——volumeClaimTemplates 生成的 PVC 是独立对象，删控制器后 PVC 与云盘原地不动，这在保护数据的同时也意味着"删库跑路"不会真正释放云账单（孤儿盘持续计费是云成本审计常客）；反过来，测试环境用默认 Delete 策略随手删 namespace，快照没做就是数据当场蒸发。回收策略是数据生命周期治理的入口，不是运维细节。

03架构设计：拓扑、冗余与四问决策

存储的引力模型：AZ 是最小的"可漂移单元"

把 01 节的三段等待抽象成一个引力模型：

  • 盘钉住 Pod：RWO 卷的拓扑约束使 Pod 只能调度到卷所在的 AZ/节点域——这是引力的向内分量；
  • AZ 决定恢复上限：节点故障时，同 AZ 有余量则分钟级重调度；同 AZ 无余量则等扩容或人工介入——故障恢复的最小保障单元是"每个 AZ 至少 2 台可调度的有状态节点"（公开复盘清单的标准条目）；
  • 多 AZ 反而更危险（若不理解引力）：节点池跨 3 个 AZ 但 3 副本因调度随机散开成"每 AZ 一个"，任一 AZ 故障时该副本的恢复依赖该 AZ 内新增节点——单 AZ 节点数≥2 才是安全线。

容量与恢复的三笔账

账目怎么算经验红线
挂载放大账块存储 attach/detach 走云 API + 存储后端，大规模扩容时按队列排队ContainerCreating 超 5 分钟必须告警
故障恢复账RWO 盘恢复 = 控制面确认超时 + 云侧强制 detach 超时 + 同 AZ 调度预算按 5+10 分钟起算，数据库切换走副本而不是等漂移
孤儿卷成本账删 StatefulSet/namespace 后 PVC 残留，云盘按小时持续计费按月对账 kubectl get pvc -A vs 云控制台盘数

「数据库该不该上 K8s」四问

这是存储决策的终极形态。按顺序问自己：

  1. 能不能不改代码直接搬？数据库pod 化的第一站是"编排有状态进程"——StatefulSet 给稳定身份（pod-0/1/2）+ 每副本独立 PVC + headless Service 直连，进程内的主从复制逻辑不用改。
  2. 要不要 Operator？裸 StatefulSet 不会做故障转移、不会提升从库、不会做 PITR 点恢复——这些是领域知识，要么买 Operator（CloudNativePG、各类厂商发行版），要么自己写控制器。"StatefulSet + 裸 MySQL" 只是半成品。
  3. 故障时等不等得起漂移？01 节的账告诉我们 RWO 漂移以十分钟计。可用性靠"副本切换"而不是"卷漂移"——主从复制或共识协议把恢复时间从分钟级压到秒级，这与在不在 K8s 上无关。
  4. 团队能不能养？存储运维（扩容/快照/升级 CSI 驱动）+ 数据库运维 + K8s 运维三份技能叠加，是这条路上真实的组织成本。

四问都过，数据库上 K8s 是能力；有一问含糊，托管数据库 + K8s 只跑无状态部分是更诚实的架构。

通用语境不绑品牌名

存储选型按"块存储（数据库/消息队列单写）/ 共享文件（多读多写日志与素材）/ 对象存储（归档与数据湖）"三分类对号入座——具体产品名只在实战配置段与互链锚文本出现（遵循 2026-10-12 定稿纪律）。

04实战：三段可落地的配置

第一段：StorageClass——WFFC + 扩容 + 拓扑，三条生产默认

apiVersion: storage.k8s.io/v1
kind: StorageClass
metadata:
  name: fast-ssd
provisioner: ebs.csi.aws.com          # 以云厂商 CSI 驱动为例
parameters:
  type: gp3
volumeBindingMode: WaitForFirstConsumer   # 先定 Pod 再定盘:随 Pod 落区
allowVolumeExpansion: true            # 在线扩容的开关,建类时就要想好
reclaimPolicy: Delete                  # 数据库类建议改 Retain
mountOptions:
- noatime                              # 数据库卷减少元数据写放大

WFFC 防分区错配、扩容开关要在建类时打开（后补要改类）、回收策略按数据等级分——这三条是"建类一时的事，没做全是事后的坑"。

第二段：PVC 在线扩容——从 100Gi 到 200Gi 不停机

# 前提: StorageClass allowVolumeExpansion: true + 驱动支持
# (CSI 1.1 起规范含 EXPAND_VOLUME,主流云盘驱动均已实现)
kubectl patch pvc mysql-data-mysql-0 \
  -p '{"spec":{"resources":{"requests":{"storage":"200Gi"}}}}'

# 扩容是两段式: PVC FileSystemResizePending 前为后端盘扩容,
# Pod 重启后由 kubelet 完成 文件系统 扩展(在线文件系统扩展依驱动)
kubectl get pvc -w    # 盯 CAPACITY 从 100Gi 变 200Gi
# 注意: 只能扩大不能缩小;扩容期间可能短暂进入 resizing 状态

规划期把容量斜率算清楚：在线扩容只能救急不能当容量规划用——每次扩容是一次"盘级变更"，与快照、监控告警（容量水位 70% 告警）配套做。

第三段：快照与恢复——VolumeSnapshot 的标准姿势

# 前提: 集群已装 VolumeSnapshot CRD + external-snapshotter
apiVersion: snapshot.storage.k8s.io/v1
kind: VolumeSnapshot
metadata:
  name: mysql-0-pre-upgrade
spec:
  volumeSnapshotClassName: csi-snapclass
  source:
    persistentVolumeClaimName: mysql-data-mysql-0
---
# 恢复 = 从快照建新 PVC(数据卷克隆),不是"塞回去"
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: mysql-data-mysql-0-restore
spec:
  storageClassName: fast-ssd
  dataSource:
    name: mysql-0-pre-upgrade
    kind: VolumeSnapshot
    apiGroup: snapshot.storage.k8s.io
  accessModes: [ReadWriteOnce]
  resources: { requests: { storage: 200Gi } }

快照的定位是"变更前保险"（升级/大迁移前打一张），不是备份体系——跨区域/异地容灾仍然要独立的备份管道（如对象存储 + 生命周期策略），快照与 AZ 同生共死。

05今日要点

  • 存储有引力：盘在哪个可用区，Pod 就被钉在哪个可用区——RWO 卷的拓扑约束是物理约束不是配置项；故障恢复的最小保障单元是"每个 AZ 至少 2 台可调度的有状态节点"。
  • 有状态故障恢复 = 三段等待：控制面确认节点死亡（约 5 分钟）+ 云侧强制 detach（6~10 分钟）+ 同 AZ 重调度——数据库的可用性靠副本切换兜底，永远不要把宝押在卷漂移上。
  • 三道关卡定位法：PVC Pending 卡绑定关（describe pvc 看 ProvisioningFailed）、Pod Pending 卡拓扑关（volume node affinity conflict）、ContainerCreating 卡挂载关（Multi-Attach）——先定关卡再进对应组件的日志。
  • WFFC + 扩容开关 + 回收策略是建类三问：WaitForFirstConsumer 先定 Pod 再定盘；allowVolumeExpansion 建类时打开；回收策略按数据等级分——孤儿卷计费与误删数据都从这条门进。
  • 数据库上 K8s 四问：能不能不改代码搬（StatefulSet 身份+PVC）、要不要 Operator（故障转移/PITR 是领域知识）、等不等得起漂移（可用性靠副本不是卷）、养不养得起（三份运维技能叠加）——四问都过再上。

06架构师思考题

题目：三可用区生产集群，消息队列要上 K8s——存储与拓扑方案怎么设计、怎么验证？

背景：公司核心消息集群（类 Kafka 架构，3 broker，每 broker 一块 2TB 云盘）计划从虚拟机迁到 K8s 生产集群。集群节点池跨 3 个可用区（每 AZ 4 台），存储走 CSI 动态制备的块存储。老板的要求："任何一个 AZ 整体故障，消息服务 5 分钟内恢复写入，数据零丢失。"请回答：

① 拓扑与调度方案怎么设计？
② AZ 故障时的恢复剧本是什么？哪些时间预算要提前实测？
③ "数据零丢失 + 5 分钟恢复"两个承诺分别靠什么机制兑现？哪个更贵？

🔍 深度解析

① 拓扑三件套：WFFC + 分区反亲和 + 单 AZ 节点冗余。StorageClass 必须 WaitForFirstConsumer——broker Pod 先调度、盘随后按 Pod 所在 AZ 创建，从 Day 1 保证" broker 与它的盘同区"。调度用 podAntiAffinity（topologyKey 用 topology.kubernetes.io/zone）把 3 个 broker 强制打散到 3 个 AZ，避免两个 broker 共享同一故障域；同时用节点级 preferred 反亲和防同节点堆叠。节点侧验证"每个 AZ 至少 2 台可调度有状态节点"——这是 AZ 故障时新副本能在同区重建的前提。另注意 StatefulSet 的 at-most-one 语义与OrderedReady 扩缩容顺序，broker 编号即身份，PVC 随身份绑定。

② 恢复剧本分"副本切换"与"卷重建"两条线，时间预算各不同。AZ-a 故障：①broker-0 所在 AZ 失联，控制器/集群自身的副本机制先接管分区 Leader（消息队列的分区多副本设计，秒级到十秒级）；②挂掉 broker 的 Pod 处于 Unknown，StatefulSet 不会自动在别的 AZ 重建它——盘还在 AZ-a，引力还在；恢复写入靠的是剩余 2 个 broker 承载全部分区，这要求容量规划按"N-1 承载全量"预留（2/3 水位线）。要提前实测的预算：Leader 切换时长（决定 5 分钟承诺的大头）、AZ 恢复后 broker-0 回归的 rejoin 时长（盘还在、节点回来即挂回）、以及"AZ 永久报废"场景下跨 AZ 重建盘 + 重放数据的时长（这就是 5 分钟承诺覆盖不了的场景，要提前跟老板对齐）。诚实结论：AZ 故障 5 分钟恢复写入=副本切换兑现；AZ 永久故障=数据重放/备份恢复，以小时计，承诺要分开写。

③ 零丢失靠"副本同步复制 + 生产者确认"，5 分钟恢复靠"多副本热备"，两者的账单不同。零丢失：消息队列的多副本机制配 acks=all 级别的同步复制（所有 ISR 副本确认才算写入成功）+ 生产者重试幂等——代价是写入延迟翻倍量级（同步等 3 个 AZ 落盘 vs 单副本本地落盘），吞吐相应打折。5 分钟恢复：3 副本跨 AZ 打散 + N-1 容量预留——代价是 3 倍存储成本 + 1.5 倍计算冗余。哪个更贵取决于业务：延迟敏感型业务买"零丢失"（同步复制）更痛，成本敏感型业务买"5 分钟恢复"（冗余）更痛；但两者都远比"AZ 故障后从备份重放"便宜——备份恢复是最后兜底，永远不该出现在 5 分钟承诺里。另补一条工程护栏：监控里必须有"ISR 收缩告警"与"同步副本延迟水位"，零丢失承诺的失效往往不是 AZ 故障，而是某副本静默掉队、同步复制悄悄退化为单副本。
