Sentinel 熔断限流实战：从"雪崩"到"稳如磐石"

站在架构师视角，理解限流、熔断、降级的本质权衡与生产级配置
📅 2026-08-12 👤 面向：架构师 / 高级工程师 📦 技术栈：Spring Cloud Alibaba · Sentinel 1.8.x

一、从一个真实的线上事故说起

某电商大促日，订单服务依赖的 库存服务因 DB 慢查询导致响应时间从 50ms 飙升到 3s。订单服务的 Tomcat 线程池在 30 秒内被全部占满，进而导致网关线程也耗尽，整个用户中心、支付服务全部不可用——这就是典型的"雪崩"（Cascading Failure）。

事故根因：下游一个慢调用，因为没有任何保护机制，像多米诺骨牌一样把整条调用链拖垮。缺少的正是"熔断 + 限流"。

架构师的核心职责之一，就是在每个服务调用边界上设置"保险丝"，让故障被隔离、被消化，而不是被放大。Sentinel 正是阿里巴巴开源的、为这件事而生的组件。

二、Sentinel 的核心模型：资源 + 规则

Sentinel 的设计哲学极其简洁，只有两个核心概念：

  • 资源（Resource）：你想要保护的东西——一个接口、一个方法、一段代码、甚至一个 SQL。
  • 规则（Rule）：怎么保护——限流（Flow）、熔断降级（Degrade）、系统保护（System）、热点参数（Param）、授权（Authority）。

运行时，所有对资源的访问都会经过一个 责任链式的 Slot Chain，依次完成：统计 → 限流判断 → 熔断判断 → 授权判断 → 实际放行。

三种"保护手段"的边界要分清

手段解决什么问题触发条件架构语义
限流 Flow流量超过承载能力QPS / 线程数超阈值"我忙不过来了，请等等"
熔断 Degrade下游异常或变慢慢调用比例 / 异常比例 / 异常数"下游在抽风，我先不调它"
降级熔断后的兜底熔断触发后执行 fallback"返回默认值/缓存，保住核心链路"
架构师洞察：很多人把"熔断"和"降级"混用。准确说，熔断是"决策"，降级是熔断后采取的"动作"。没有降级的熔断，对用户来说就是直接报错——这是半成品。

三、生产级 Sentinel 架构：四个组件各司其职

这是最容易绕晕的地方。Sentinel 不是"一个东西"，而是四个独立组件——理解它们的边界，是后续所有配置和排障的基础。先把这张组件归属图刻在脑子里：

不知道 Token Server 的存在。 · Token Server 是「可选数据面」——只为「集群限流」这一个功能服务，跟 Dashboard 互不感知、互不依赖。 · 不用集群限流 → 直接忽略下半部分；单机限流/熔断完全够用，SDK 自己就跑起来了。

Detailed：Dashboard 是怎么"看到"所有服务的？

关键在于反向连接——不是 Dashboard 主动连服务，而是每个 SDK 在本地开一个端口（默认 8719）等 Dashboard 连过来。服务进程启动时拿着 spring.application.name 去 Dashboard 注册，之后保持长连接。Dashboard 左侧栏的"应用列表"就是这么来的：

  • 上行（服务 → Dashboard）：每秒上报 metrics（QPS、RT、异常数）
  • 下行（Dashboard → 服务）：推送规则修改、拉取某资源的 clusterNode 明细

这么设计是因为 K8s 里 Pod IP 经常变，让 Dashboard 追不现实——所以让服务主动"挂"到 Dashboard 上。

最关键的一个坑：Sentinel Dashboard 默认规则存内存，重启即丢。生产环境必须接 Nacos 做持久化——Dashboard 退化成"可视化编辑器 + 实时监控屏"，真正权威的规则源是 Nacos，由应用端通过 datasource 监听拉取。

Detailed：Token Server 两种部署模式

模式适用场景HA 方案自己要写的代码
独立部署

嵌入式部署

四、实战：三步搞定一个生产级熔断

① 引入依赖（Spring Boot 3.x）

<!-- Sentinel 核心 + Spring Cloud Alibaba 起步依赖 -->
<dependency>
    <groupId>com.alibaba.cloud</groupId>
    <artifactId>spring-cloud-starter-alibaba-sentinel</artifactId>
</dependency>
<!-- 将规则持久化到 Nacos -->
<dependency>
    <groupId>com.alibaba.csp</groupId>
    <artifactId>sentinel-datasource-nacos</artifactId>
</dependency>

② 配置 Nacos 数据源（application.yml）

spring:
  cloud:
    sentinel:
      transport:
        dashboard: sentinel.internal:8080
        port: 8719            # 客户端与控制台通信端口
      eager: true           # 应用启动立即上报，不等首次请求
      datasource:
        ds1:                  # 拉取「限流规则」
          nacos:
            server-addr: ${NACOS_ADDR}
            dataId: ${spring.application.name}-flow-rules.json
            groupId: SENTINEL_GROUP
            rule-type: flow
        ds2:                  # 拉取「熔断规则」
          nacos:
            server-addr: ${NACOS_ADDR}
            dataId: ${spring.application.name}-degrade-rules.json
            rule-type: degrade

③ 在 Nacos 中配置一条熔断规则（JSON）

场景：库存服务 GET /inventory/{sku} 一旦慢调用比例过高，自动熔断 10 秒。

[
  {
    "resource": "GET:/inventory/{sku}",
    "grade": 0,                 // 0=慢调用比例, 1=异常比例, 2=异常数
    "count": 500,               // 慢调用阈值：RT > 500ms 视为慢
    "slowRatioThreshold": 0.6,  // 慢调用比例 > 60% 即触发
    "timeWindow": 10,          // 熔断持续时间 10s
    "minRequestAmount": 20,    // 至少 20 个请求才统计，避免误判
    "statIntervalMs": 1000     // 1 秒统计窗口
  }
]

④ 配置降级兜底（fallback）

@Service
public class InventoryService {

    @SentinelResource(value = "GET:/inventory/{sku}",
                     blockHandler = "blockHandler",   // 限流/熔断时走这里
                     fallback    = "fallback")       // 业务异常时走这里
    public Inventory getInventory(String sku) {
        return inventoryMapper.selectBySku(sku);
    }

    // 方法签名必须与原方法一致，且最后追加 BlockException 参数
    public Inventory blockHandler(String sku, BlockException ex) {
        log.warn("inventory 被熔断/限流，返回本地缓存 sku={}", sku);
        return localCache.get(sku);   // 本地缓存兜底
    }

    public Inventory fallback(String sku, Throwable t) {
        log.error("inventory 业务异常 sku={}", sku, t);
        return Inventory.unknown(sku);
    }
}
必知坑点：blockHandler 处理的是 Sentinel 抛出的 BlockException（限流/熔断），而 fallback 处理的是业务方法本身的异常。两者各司其职，混用会导致熔断后用户仍然看到 500。

五、架构师的选型权衡

Sentinel vs Hystrix vs Resilience4j

维度SentinelHystrix（停更）Resilience4j
熔断策略慢调用比例 / 异常比例 / 异常数异常比例异常比例（参考Hystrix）
限流原生支持（QPS/线程/热点）不支持RateLimiter 模块
实时监控自带 Dashboard需对接 Turbine需自建
规则动态推送Nacos/ZK/Apollo弱弱
语言生态Java 为主，多语言 SDK 较新JavaJava 8+ 函数式
选型结论：公司技术栈是 Spring Cloud Alibaba，自然首选 Sentinel——它的限流能力是 Hystrix/Resilience4j 不具备的，且与 Nacos/Dubbo 无缝集成，运维成本低。如果团队全面函数式且追求轻量，再考虑 Resilience4j。

容量规划：阈值怎么定？

  • 压测先行：用 wrk/JMeter 压出服务的 QPS 上限和 P99 RT。
  • 限流阈值：取压测峰值的 70%-80% 留 buffer，例如峰值 1000 QPS，限流设 800。
  • 慢调用阈值：取正常 P99 RT 的 2-3 倍，例如 P99=200ms，慢调用阈值设 500ms。
  • 熔断窗口：10-30s 为佳。太短抖动大，太长恢复慢。
  • minRequestAmount：必须 ≥ 一定量（如 20），否则低流量下偶发慢调用会误熔断。

六、生产排障实战：五个高频坑

  1. 规则丢失：应用重启后规则不见了 → 没接 Nacos 持久化，必须配 datasource。
  2. 资源未生效：接口加了 @SentinelResource 但限流不触发 → 多半是资源名拼错，或方法被 AOP 内部调用绕过（同类 this.xxx() 不走代理）。
  3. Dashboard 看不到节点：检查客户端 spring.cloud.sentinel.transport.dashboard 是否可达，以及 eager:true。
  4. 熔断后一直不开：检查 statIntervalMs 与 minRequestAmount，低 QPS 服务要调小阈值。
  5. 集群限流不准：Token Server 单点要 HA，否则一旦宕机限流退化为单机模式，容量翻倍。

七、今日要点小结

  • 限流防"超载"，熔断防"雪崩"，降级保"体验"——三者各司其职，缺一不可。
  • Sentinel 核心模型：资源 + 规则，Slot Chain 责任链式处理。
  • 生产环境规则必须持久化到 Nacos，控制台只做展示与编辑，不做存储。
  • blockHandler 管 Sentinel 异常，fallback 管业务异常——不要混用。
  • 阈值来自压测数据：限流取峰值 70-80%，慢调用取 P99 的 2-3 倍，留足 buffer。

八、架构师思考题

思考题 1：某核心接口 P99 RT 突然从 50ms 升到 800ms，但服务本身 CPU、内存都正常。你会如何用 Sentinel 与排障思路定位并止血？

解题方向（止血优先，根因其次）：

① 快速止血：先确认是下游变慢还是自身 GC/锁竞争。

  • 查看 Sentinel Dashboard 该资源的 RT 曲线、慢调用比例。
  • 检查 JVM GC 日志（-Xlog:gc*）——Full GC 会引起整体 STW。
  • 用 arthas trace <class> <method> 看每一步耗时，定位到 DB / Redis / RPC。

② 临时兜底：在 Sentinel 上临时加一条慢调用熔断规则（RT=300ms，慢比例 50%，熔断 15s，fallback 走本地缓存或默认值），先把用户感受稳住，避免线程池被打满引发雪崩。

③ 根因定位：

  • 若 DB：检查慢查询日志、连接池是否耗尽、是否走了索引（EXPLAIN）。
  • 若下游 RPC：链路追踪（SkyWalking/Sleuth）找到具体 span，联系下游 owner。
  • 若自身：锁竞争用 jstack 抓线程栈，定位 BLOCKED 线程。

④ 复盘加固：把临时规则固化为长期熔断规则，补充 HPA + 告警，并增加该接口的常态化压测。

思考题 2：集群限流（Cluster Flow Control）和单机限流该如何选？什么时候必须上集群限流？它的代价是什么？

核心权衡：精度 vs 复杂度。

单机限流：每个 Pod 独立计数。假设阈值 100 QPS/实例，部署 N 个实例，总上限 = 100×N。优点：零依赖、无单点、延迟低。缺点：实例数变化时总容量被动变化；对"全局配额"类限制（如 API 每秒 1 万次）无法精确控制。

集群限流：所有实例向 Token Server 申请令牌，Server 全局统算。优点：精确的全局配额控制。缺点：

  • 引入单点：Token Server 宕机会退化为单机限流（容量翻倍），所以 Server 必须 HA（至少 2 节点 + LB）。
  • 额外一跳网络延迟：每次取令牌多 1-2ms，对极低延迟场景敏感。
  • Server 容量瓶颈：单 Server 处理能力有限（万级 QPS），超大规模需分片或 Token Server 集群。

何时必须用集群限流？

  • 开放平台 API 售卖固定 QPS 配额（如"客户 A 全局 500 QPS"）——必须精确全局控制。
  • 保护下游不可水平扩展的资源（如单实例的老旧系统、第三方付费 API）。
  • HPA 自动伸缩频繁的场景——单机限流会因实例数波动导致总容量不稳。

结论：常规内部服务用单机限流足够；涉及"全局配额"或"保护下游稀缺资源"才上集群限流，并配套 Token Server 的 HA 与监控。
