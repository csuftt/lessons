REDIS · Redis 系列第 5 讲（数据治理篇 · 畸形 Key）

Redis 大 Key 与热 Key 治理：两种"畸形"，一套生命周期

上一讲聊了 MySQL 的行锁与 MVCC，把"热点行吞吐 = 1/持锁时长"这条物理定律拆开看完了。这一讲开启 Redis 主线，聊一个同构但反方向的问题：数据库怕"行太热"，Redis 怕"Key 太大、太热"——大 Key 是单次操作代价畸形（一条命令几十毫秒，卡住单线程里所有请求），热 Key 是聚合流量畸形（一个 Key 吃掉整个分片的 CPU 与带宽，加分片也救不了）。两者一个是"空间病"一个是"流量病"，但治理是同一套方法论：发现要有雷达，拆解要有方案，删除要有姿势，架构要有防线。这一讲从一次大促凌晨的连环事故讲起，把四个环节一次讲透。

01一次大促凌晨的连环事故

某电商平台的 Redis Cluster（12 分片）撑日常交易。大促当天凌晨两点，连环出了三件事：第一件，商品详情接口 P99 从 3 毫秒飙到 120 毫秒——排查发现运营提前把 800 个商品的详情预热进了缓存，其中 30 个"爆品"的详情 JSON 被整包塞进了单个 String，每个 2MB；一次 GET 就要在网络上传 2MB，千兆网卡被打到 90%，同分片所有 Key 陪跑。第二件，主库周期性"卡死"几十毫秒——一个大 Hash（120 万 field 的粉丝列表）恰好在整点过期，同步删除 120 万个 field 的内存，主线程直接停顿，慢日志里出现 DEL 开头的"慢命令"。第三件，秒杀开始的 10 秒内某分片 CPU 100%——秒杀库存 Key 只有 1 个，十万 QPS 的 DECR 全砸在一个分片上，其余 11 个分片围观。

复盘的结论让人清醒：三件事分别是大 Key 的两张面孔和热 Key 的一张面孔。2MB 的详情 Key 是"读放大"——单次操作传输量畸形；120 万 field 的粉丝 Hash 是"删放大"——回收代价畸形；秒杀库存是热 Key——流量聚合畸形。共同根源是：Redis 的单线程命令执行模型（命令执行单线程，持久化与异步删除等才走后台线程）把"任何一个 Key 的操作代价"变成了"整个实例所有请求的代价"。这个模型换来了极致的简单与低延迟，代价就是——Key 的形态纪律，就是 Redis 的生命线。

02原理：单线程模型下的两种代价畸形

大 Key：一次操作，三方买单

多大算大？行业通行的参考线：String 类型 value 超过 10KB、集合类型元素超过 5000 个（阿里云口径 1 万）即预警，超过 1MB / 10 万元素进入治理红线。但比数字更重要的是机理——大 Key 的一次操作，有三方买单：主线程买单（遍历、序列化、内存回收都是 CPU 时间，O(N) 命令的 N 就是停顿时长的分子）；网络买单（2MB 的 GET 占用的带宽，挤占同实例所有 Key 的传输）；复制与持久化买单（主从全量同步时 RDB 快照变大、AOF 重写时fork 子进程页表膨胀，大 Key 越多 COW 压力越大——回看第 6 期持久化的 fork 停顿）。同理，危险命令不止 DEL：HGETALL、SMEMBERS、LRANGE 0 -1、KEYS 都是大 Key 的"雷管"——Key 本身大不可怕，可怕的是一条命令把"大"整体引爆。

热 Key：流量聚合，分片无效

热 Key 的定义是相对的：单个 Key 的流量在实例总流量中占比畸高（参考线：单 Key QPS 超过 5000，或单分片流量是均值的 5 倍以上）。机理上它是 Cluster 架构的宿命：一个 Key 通过 CRC16 哈希只落在一个 slot、一个分片上，加分片加的是"并行度"，不是"单 Key 容量"——十万 QPS 打一个 Key，12 分片与 120 分片没有区别。Redis Software 8.0.20-44 的发行说明里专门有一句：为修复"海量流量打向单个热 Key 导致高延迟与 OOM"的问题，默认启用了 client_eviction（按客户端缓冲内存驱逐）——热 Key 打爆输出缓冲区把实例拖进 OOM，是官方都认账的坑。此外还有一层隐秘的连带：大 Key 往往同时是热 Key（爆品详情既大又高频读），两种畸形叠加，是最危险的组合。

为什么"单线程"反而是理解一切的那把钥匙

Redis 用一个线程串行执行所有客户端命令（持久化 fork、UNLINK 后台回收、AOF 刷盘走别的线程）。这个设计换来的是无锁、无上下文切换、缓存友好的极致低延迟——代价是任何一个命令慢，所有命令排队。所以大 Key 治理的本质是"控制单次操作的代价上限"，热 Key 治理的本质是"控制单 Key 的流量占比上限"。两条纪律，同一个出发点。理解了这一点，后面所有方案（拆分、异步删除、本地缓存、副本打散）都不再是零散技巧，而是同一条原理的推论。

03架构设计：发现 → 拆解 → 删除 → 防线

发现：三代雷达

大 Key 拆解：按结构下药

大 String：先压缩（JSON 开启 GZIP/Snappy，长文本常省 60~80%），压完还大就说明它不该住在 Redis——转存对象存储（关联第 23 期 MinIO），Redis 只留元数据与小指纹。大 Hash：按 field 哈希拆成 N 个子 Key（user:1001:0 ~ N-1，field 上带路由位）；Redis 7.4+ 的 field 级 TTL（HEXPIRE）让"粉丝列表里失效的关注"能自动过期，从源头防堆积。大 ZSet/List：按时间窗或分值区间分片；List 型 feed 用 LPUSH + LTRIM 截断成有界队列，或直接换 Stream 的 MAXLEN ~ 近似裁剪。所有拆分的公共心法：读路径改成"先算路由再定向读"（HMGET 指定 field、ZRange 限定区间），全量读命令从代码里清出去。

删除的姿势：UNLINK 与 lazyfree 四开关

大 Key 的删除是事故高发位：同步 DEL 一个百万 field 的 Hash，主线程停顿以百毫秒计。正确姿势是4.0+ 一律用 UNLINK——逻辑删除在主线程原子完成，内存回收交给 bio 后台线程，返回即完成。更隐蔽的是"被动删除"：过期清理与内存淘汰默认也是同步路径，lazyfree-lazy-expire / lazyfree-lazy-eviction 两个开关把它们也改成后台异步；再配 lazyfree-lazy-server-del（RENAME 等服务端隐式删除）与 replica-lazy-flush（从库全量同步前清库）。四个开关全开是现代部署的基线（7.0 起还可用 lazyfree-lazy-user-del 让代码里的 DEL 也自动走异步路径）。超大的存量 Key（千万 field 级）连 UNLINK 都嫌重时，用 HSCAN + HDEL 分批啃，最后 UNLINK 收尾。lazyfree_pending_objects 指标进监控——后台回收队列堆积说明"删得比生得快"，那是另一级警报。

热 Key 防线：四层递进

层级手段量级效果代价 / 边界
L1本地缓存（Caffeine + 毫秒~秒级 TTL）热读 QPS 的 90%+ 消化在 JVM 内极短 TTL 换弱一致，业务要能接受；与第 20 期一致性同源权衡
L2读写分离：读 replica / 只读节点读吞吐随副本数水平扩展复制延迟的一致性窗口；写仍集中在主
L3Key 复制打散：写 N 份副本随机读单 Key 流量 ÷ N更新要广播全部副本；一致窗口 = 副本 TTL，适合读极多写少的配置类
L4重新路由：按业务维度拆 Key / 上本地全量快照根治：热源消失改数据模型，成本最高；秒杀级热点才动用

选型顺序永远是 L1 → L4 能低不高：本地缓存的性价比断档领先，只有当热点本身是设计错误（全局配置 Key 人为造热、爆品打榜未预热）时才直奔 L4。还有一个容易忽略的组合拳：热 Key + 淘汰策略——热点被打到 maxmemory 水位触发淘汰时，LRU 系策略可能把真热点逐出去（回看第 11 期的缓存污染），LFU 系靠频次计数天然免疫，这也是缓存实例推荐 allkeys-lfu 的又一重理由。

容量三笔账（畸形 Key 视角）

大 Key 网络账：2MB value × 每秒 50 次读 = 100MB/s 出网流量，千兆网卡（125MB/s）到 80%——一个 Key 决定整个实例的网卡水位。热 Key CPU 账：十万 QPS × 单命令 2μs 朴素估算 = 20% CPU 听起来不高，但叠加输出缓冲排队、TLS、大 value 序列化后轻松翻几倍；官方用 client_eviction 兜 OOM 说明真实曲线远比朴素估算陡。淘汰连带账：大 Key 被淘汰或过期瞬间释放的内存，会触发分配器归还（可能伴随 madvice 系统调用），在低碎片阈值下引发延迟毛刺——删除姿势不只是"删得掉"，还要"删得安静"。

04实战：巡检、异步删除、热 Key 打散

大 Key 巡检与精确复核

# 日常巡检：SCAN 采样（-i 0.1 每次扫描间隔 0.1s 限速，低峰执行）
redis-cli --bigkeys -i 0.1          # 按元素数口径找最大 Key（每种结构输出 Top1）
redis-cli --memkeys -i 0.1          # 按内存口径（两者结论可能不同，都要跑）

# 嫌疑 Key 精确复核：内存估值 + 元素计数
redis-cli MEMORY USAGE detail:1001 SAMPLES 8
redis-cli HLEN fans:1001            # Hash：field 数；LLEN/SCARD/ZCARD 同理

# 8.6+ 热 Key 归因：按 CPU 与网络字节采样 30 秒（老版本用 --hotkeys，需 LFU 策略）
redis-cli HOTKEYS START METRICS 2 CPU NET COUNT 10 DURATION 30000
redis-cli HOTKEYS GET               # 输出 top-k：CPU 毫秒归因 + 网络字节归因
redis-cli HOTKEYS RESET             # 用完释放采样状态

删除姿势：四开关 + 分批啃

# redis.conf / CONFIG SET —— lazyfree 四开关全开（现代部署基线）
lazyfree-lazy-eviction yes      # 内存淘汰走后台线程
lazyfree-lazy-expire yes        # 过期清理走后台线程（治"整点过期卡死"）
lazyfree-lazy-server-del yes    # RENAME 等隐式删除走后台
replica-lazy-flush yes          # 从库全量同步前清库走后台
lazyfree-lazy-user-del yes      # 7.0+：代码里的 DEL 也自动转 UNLINK（兜底）

# 应用代码：删除一律 UNLINK；千万 field 级超大 Key 分批啃
redis-cli UNLINK fans:1001
# 超大 Hash 渐进删除：每批 1000 个 field，批次间 sleep，最后 UNLINK 收尾
# for: cursor, fields = HSCAN fans:big $cursor COUNT 1000 → HDEL fans:big $fields

# 监控后台回收队列是否堆积（持续 > 0 说明删不过来）
redis-cli INFO stats | grep -E "lazyfree_pending|lazyfreed"

热 Key 打散：副本随机读（Java）

// L3：热点配置 Key 复制 N 份，读随机打散、写广播 + 短随机 TTL（1~5s 内随机）
public String hotGet(JedisPool pool, String key, int n) {
    int i = ThreadLocalRandom.current().nextInt(n);
    String v = pool.getResource().get(key + ":" + i);   // 读随机副本
    if (v != null) return v;
    v = db.load(key);                                    // 回源数据库
    String ttl = 1 + ThreadLocalRandom.current().nextInt(4) + "s";  // 短随机 TTL
    for (int k = 0; k < n; k++) pool.getResource().setex(key + ":" + k, ttl, v); // 写广播
    return v;
}
// L1（更优先）：Caffeine 本地缓存挡在 Redis 前面，TTL 100ms~5s 按 staleness 预算配

五个必踩的坑：① DEL 上生产——4.0+ 仍写 DEL 的代码，遇到大 Key 就是"整点卡死"的定时炸弹，UNLINK + lazyfree-lazy-user-del 双保险；② 大批量 Key 同一时刻过期——同一秒几万个 Key 到期，过期清理本身成为 CPU 尖峰，TTL 一律加随机抖动（±20%）；③ 把 --bigkeys 当精确工具——它是 SCAN 采样，采样就会漏，重大治理前用 MEMORY USAGE 逐个复核；④ 热 Key 只靠加从库——写热点（DECR、INCR）在从库上根本不存在分担，读写分离只治读热；⑤ 拆完大 Key 不改读代码——数据拆成 8 片了，HGETALL 循环 8 片再合并，网络往返 ×8，"治大治出个治热"，拆分方案必须与读路径改造同批上线。

05今日要点

  • 两种畸形一个根源：大 Key 是单次操作代价畸形（主线程/网络/复制三方买单），热 Key 是聚合流量畸形（哈希单 slot 落位，加分片无效）——都踩在"单线程命令执行"这条生命线上，Key 的形态纪律就是 Redis 的稳定性预算。
  • 发现要靠雷达不要靠运气：大 Key 双口径巡检（bigkeys 元素数 + memkeys 内存），热 Key 从 LFU 频次排名（--hotkeys）进化到 8.6 的 CPU/字节归因（HOTKEYS 命令）——从"猜谁热"到"证明谁吃了资源"。
  • 删除的姿势比删除本身重要：UNLINK 替代 DEL 只是起点，lazyfree 四开关把过期/淘汰/隐式删除全改异步，大批量过期 TTL 加随机抖动，超大 Key 用 SCAN 系分批啃——"删得安静"是稳定性工程。
  • 拆解必须读写同改：String 压缩/转存、Hash 分片 + field 级 TTL（7.4+）、List 截断有界——数据拆碎的同时读路径改成定向读（HMGET/区间查询），只拆不改读等于把"大"病治成"热"病。
  • 热 Key 防线能低不高：本地缓存（毫秒级 TTL）性价比断档领先，读写分离治读不治写，副本打散适合读极多写少，重新设计是最后手段——热点账进容量规划，不靠事后救火。

06架构师思考题

题目一：直播间 500 万人同时在线，礼物打赏接口每次都要读"直播间配置 Key"（String，约 50KB），实测该 Key 峰值 30 万 QPS，单分片 CPU 95%、P99 80ms。① 该 Key 同时是大 Key 还是热 Key？两种畸形在这里各自贡献了什么问题？② 团队提案三个方案：A 直接扩 Cluster 分片数 12→24；B 配置 Key 拆成 N 份副本随机读；C 应用侧本地缓存 500ms TTL。逐个评估能否解决、代价是什么。③ 如果产品再加需求"主播端改配置要 1 秒内生效"，C 方案的 TTL 还能设 500ms 吗？给出一致性预算的推理。▶ 点击展开解析

🔍 逐问拆解

① 双重畸形叠加，且互相放大。50KB 超过 String 10KB 预警线，是大 Key——贡献网络账：30 万 QPS × 50KB = 15GB/s 的理论出网流量（实际有连接复用与压缩缓解，但网卡水位必然爆表），还贡献序列化 CPU；单 Key 30 万 QPS 远超 5000 参考线，是热 Key——贡献CPU 账：CRC16 把它钉死在一个分片，12 分片里 1 个 95%、11 个围观。最关键的乘法效应：大 Key 让每次热访问更贵，热 Key 让贵的访问更高频——50KB × 30 万 QPS 才是真实压力，两个病必须一起治。

② A 无效，B 有效但不优，C 最优。A 扩分片加的是并行度不是单 Key 容量——这个 Key 还落在一个 slot 上，24 分片里照样 1 个被打满（还多花了 12 个分片的成本），这是热 Key 的"分片免疫"铁律。B 副本打散：把流量 ÷ N，比如 8 副本单 Key 流量降到 3.75 万 QPS——但注意它是大 Key，每个副本都 50KB，读流量没有变小的只是摊开了，网卡总出水反而因副本广播写入略增；且写路径要广播 8 份，配置更新的一致窗口 = 副本 TTL。C 本地缓存：500ms TTL 下，500 万观众（假设 5000 个应用实例）每实例每 500ms 回源一次 = 回源 QPS 仅 1 万，挡掉 96%+ 的流量，且顺带把"大"的问题也治了——50KB 在 JVM 内命中，网络传输消失。C 的代价是 500ms 的 staleness 窗口与 JVM 内存占用（50KB × 热点 Key 数，可忽略）。结论：C 是正解，B 可作为 C 之前的紧急止血（不动应用代码，运维侧先加副本）。

③ 一致性预算推演：TTL 必须 ≤ 1s 生效要求，但也不能贴着 1s 设。"1 秒内生效"的含义是最坏情况下观众在配置变更后 1 秒内看到新值——本地缓存的 staleness 上界就是 TTL（不含变更通知路径），所以 TTL 500ms 依然满足：最坏 500ms 后回源拿到新值。真正的风险在变更链路的额外延迟：主播端改配置 → 写数据库 → 失效广播到全部实例（或等 TTL 自然过期）——如果走"写后主动失效"（配置中心推送 / Redis Pub-Sub 通知），链路本身要预留几百毫秒，TTL 就要压到 200~300ms 或改推送模式；如果纯靠 TTL 自然过期，500ms 刚好在预算内但没有任何余量，建议 200~300ms + 变更主动失效的组合：平时靠 TTL 兜底，变更时推送加速收敛。这个推理过程就是"一致性预算"：把业务能接受的 staleness 拆成分配给缓存 TTL、变更传播、时钟误差三段，加起来不超过业务红线——与第 20 期"延迟双删取值 = 读 P99 + 主从延迟 + 缓冲"是同一个框架。

题目二：你们的社交 App 有个"好友列表"Hash，单用户最大 120 万 field（field=好友 ID，value=备注），运营抱怨"某些大 V 的好友列表加载超时"。团队决定拆分。① 给出拆分方案：路由怎么定、子 Key 怎么命名、field 级 TTL（7.4+）能帮上什么忙？② 拆分迁移怎么做才能不影响线上读？给出双写与切流顺序。③ 迁移完成后第二天，实例周期性出现 30ms 毛刺，lazyfree_pending_objects 偶发 5 万+——最可能的根因是什么？怎么治理？▶ 点击展开解析

🔍 逐问拆解

① 拆分方案三要素。路由：对 field（好友 ID）做一致性哈希或简单 hash(friendId) % 8——注意好友列表天然按用户隔离，用好友 ID 做路由位而不是用户 ID，这样同一用户的好友摊到 8 个子 Key；命名：friends:{userId}:0 ~ friends:{userId}:7（拆 8 片是元素数与路由复杂度的平衡点：120 万 ÷ 8 = 15 万/片仍偏大，大 V 可以按需 16 片——分片数进元数据（如 friends:{userId}:meta 存 {"shards":8}），未来扩片不用改代码约定）；field 级 TTL 的用武之地：好友关系的"失效"场景（拉黑、注销）——7.4 前只能 HDEL 主动删或整 Key 过期，现在给单个 field 设 HEXPIRE friends:{userId}:0 2592000 FIELDS 1 friend123（30 天无互动自动清理），把"清理逻辑"从应用层定时任务下沉到数据结构自带语义，从源头防 field 无限堆积——这是大 Hash 治理里最值得用的新武器。

② 迁移四步：双写 → 影子读 → 切读 → 停写旧。第一步双写：新数据同时写老 Key 和新子 Key（写路径加开关，灰度放量）；第二步存量搬迁：低峰用 HSCAN 分批读老 Key、按路由规则写进子 Key（每批 1000 field，批间 sleep，--memkeys 确认老 Key 不再增长）；第三步影子读对账：切流前随机抽样 1% 请求"读新+读老"比对（新读生效但丢弃结果，记不一致率，趋零才切）；第四步切读：按百分比放量 1% → 10% → 50% → 100%（观察错误率与延迟），稳定一周后停写老 Key、UNLINK 回收——回收动作放在最后且用 UNLINK，120 万 field 的老 Key 用 DEL 收尾等于把迁移全程的谨慎一次性赌掉。读路径同步改造：列表页只取第一页（HRANDFIELD 或按时间排序的辅助 ZSet），详情按需单 field 读——迁移是读路径升级的最佳窗口，别拆完还按 HGETALL 全量读。

③ 根因：删除速率超过了后台回收能力，"迁移后遗症 + TTL 集中到期"。线索链：迁移完成 → 老版本过期清理逻辑下线/调整 → 但 8 个子 Key 上的 field 级 TTL 大多在同一批迁移时写入、TTL 相同（迁移脚本忘了加抖动）→ 每天固定时刻集中到期 → lazyfree-lazy-expire 虽然把回收扔给了后台线程，百万级 field 的到期仍会在后台队列堆积（lazyfree_pending_objects 5 万+），bio 线程 CPU 冲高连带主线程调度毛刺；30ms 周期性毛刺与到期时刻对齐即可实锤。治理三板斧：先止血——把存量 field 的 TTL 用 HSCAN 批量重设为"原值 ± 20% 随机抖动"，打散到期时刻；再治本——迁移与批量写入脚本规范里固化"TTL 必带随机抖动"（与第 04 节坑 ② 同一条纪律的迁移版）；后观测——lazyfree_pending_objects 设阈值告警（如持续 > 1 万），配合 expired_keys 速率曲线，到期尖峰与队列堆积提前可见。深层教训：lazyfree 是把同步停顿换成了异步背压，不是把代价变没了——后台队列的堆积水位，就是删除代价的"分期账单"，监控它才算真正管住了删除。
