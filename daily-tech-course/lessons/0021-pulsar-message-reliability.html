消息到底丢在哪：消息可靠性全链路

"消息丢了"很少是集群的锅——中间件只对已经到达它的消息负责。今天把生产端送达确认、BookKeeper 落盘副本（E/Qw/Qa）、消费端 ack 时机与重试/死信机制串成一条链，讲清"丢"与"重"各自的堵法。

🧰 Apache Pulsar 📅 2026-09-09 · 第 21 期 ⏱ 预计阅读 10 分钟

01一次"一边丢、一边重"的压测复盘

大促压测第二天，两个工单同时进来：库存组说有三万条"订单取消"消息没消费到，库存一直被占着，从超卖变成了少卖；营销组说同一场压测里，一批用户的优惠券发了两次。一边丢、一边重，两组都怀疑 Pulsar 集群出了问题，但 broker 指标一切正常。排查结论：

  • 丢失侧：生产者用了 sendAsync() 但回调里什么都不做（fire-and-forget），压测高峰待发队列打满，一批发送异常被静默吞掉——消息根本没到 broker；
  • 重复侧：消费者处理完业务、发 ack 前进程被重启，消息按规则重投，而消费逻辑没有幂等——第二次投递又发了一遍券。

这两件事共同指向一个认知：消息系统的可靠性是三段链路共同决定的——生产端（把消息安全送达）、存储端（确认过的消息不丢）、消费端（处理成功才确认、失败能重投）。中间件只承诺中间那段，前后两段都是你的代码说了算。

02原理：三段链路，五个风险点

投递语义：先选边，再谈实现

语义典型做法丢失重复适用
at-most-once 发送即忘 / 处理前先 ack 可能丢 不会重 日志、指标采样，丢一条无所谓
at-least-once 发送等确认 + 处理成功后 ack 链路配齐则不丢 可能重 绝大多数业务消息
effectively-once at-least-once + 消费幂等 不丢 重复被幂等吸收 订单、库存、资金类

为什么没有"裸的 exactly-once"？发送超时的二义性决定了：超时那一刻你无法探知消息到底写没写进去，重试则可能重、放弃则可能丢——端到端必须选边。工程上的答案是 at-least-once + 幂等 = 有效一次。

存储端：BookKeeper 的 E / Qw / Qa

Broker 收到消息后写入 BookKeeper ledger（存算分离架构详见0012 期）。三个参数决定一条消息怎么落盘：ensembleSize(E) ledger 分布在几台 bookie 上；writeQuorum(Qw) 每条消息写几个副本；ackQuorum(Qa) 几个副本落盘后才向生产者确认。约束 Qa ≤ Qw ≤ E，默认 3/3/2。bookie 的 journal 就像 MySQL 的 redo log——默认先 fsync 再回 ack，保证"确认过的消息重启不丢"（这个开关别乱关）。

03架构选型：副本组合与语义档位

组合（E/Qw/Qa）确认条件丢消息条件写延迟适用
3 / 3 / 2（默认） 3 副本写，2 台落盘即确认 确认后第三台未写完期间，两台已确认 bookie 同时永久损毁 由第 2 快的决定 在线业务通用
3 / 3 / 3 3 台全部落盘才确认 需三台同时损毁才丢 由最慢一台决定 金融、计费、审计
6 / 3 / 2（E>Qw） 条带化摊到 6 台，单条仍 3 副本 同 3/3/2 低（负载更均衡） 大吞吐流量的 bookie 横向扩容
可靠性选型三问（评审必答）① 丢一条代价多大？——决定副本档位与生产端兜底投入；② 重复一次后果多严重？——决定幂等档次：去重表、状态机还是加锁串行；③ 谁来消费 DLT？——没有 DLT 消费者和告警，等于把"丢失"改名叫"死信"，问题没消失，只是换了仓库。

容量规划要点：Qw 决定 bookie 端写放大——磁盘写入量 ≈ 消息量 × Qw。3/3/2 就是 3 倍写放大，盘容量按 3 倍数据量规划，再留 20%~30% 水位缓冲；bookie 尽量机架/机房感知放置，把"两台同时损毁"的概率从同机架拉到跨机房级别。

04实战：把三段链路逐段堵死

生产端：确认送达 + 兜底落库

Producer<OrderEvent> producer = client.newProducer(JSONSchema.of(OrderEventSchema.class))
    .topic("persistent://oms/core/order-event")
    .producerName("oms-cancel-1")          // 配合 broker 端去重
    .sendTimeout(3, TimeUnit.SECONDS)
    .enableBatching(true)
    .blockIfQueueFull(true)              // 队满阻塞而非直接报错（默认 false）
    .create();

producer.newMessage()
    .key(event.getOrderId())                     // 同订单路由到同分区，保序交给订阅模式
    .value(event)
    .sendAsync()
    .whenComplete((id, ex) -> {
        if (ex != null) {
            // 客户端内部重试耗尽仍失败：落本地事件表（Outbox），对账任务补偿重发
            outbox.saveForRetry(event, ex);      // 千万别只打一行日志了事
        }
    });
⚠️ 两个高频坑① sendAsync() 不处理回调 = fire-and-forget，任何失败都静默蒸发，这是生产端丢消息的第一大成因；② sendTimeout 触发存在二义性——超时 ≠ 失败，消息可能已写入，所以兜底重发必须配 broker 端去重或业务幂等，否则把"可能丢"修成"可能重"。

消费端：处理成功才 ack + 重试队列 + 死信

DeadLetterPolicy dlp = DeadLetterPolicy.builder()
    .maxRedeliverCount(16)
    .retryLetterTopic("persistent://oms/core/order-event-retry")
    .deadLetterTopic("persistent://oms/core/order-event-dlt")
    .build();

Consumer<OrderEvent> consumer = client.newConsumer(JSONSchema.of(OrderEventSchema.class))
    .topic("persistent://oms/core/order-event")
    .subscriptionName("stock-service")
    .subscriptionType(SubscriptionType.Shared)   // 注意：Shared 只能逐条 ack，累计确认仅限 Exclusive/Failover
    .ackTimeout(30, TimeUnit.SECONDS)          // 防"静默卡死"：默认 0 = 未 ack 永不重投
    .enableRetry(true)                     // 启用重试队列
    .deadLetterPolicy(dlp)
    .subscribe();

while (true) {
    Message<OrderEvent> msg = consumer.receive(5, TimeUnit.SECONDS);
    if (msg == null) continue;
    try {
        if (!dedup.tryFirst(msg.getValue())) {     // ① 幂等检查：重复消息直接放行确认
            consumer.acknowledge(msg);
            continue;
        }
        stockService.releaseStock(msg.getValue()); // ② 业务处理
        consumer.acknowledge(msg);                // ③ 成功后才 ack —— 顺序不能反
    } catch (Exception e) {
        consumer.reconsumeLater(msg, backoff(msg)); // 带退避进重试队列，超限自动进 DLT 并在原 topic ack
    }
}

幂等：用业务键，不是 messageId

// 幂等键 = 业务唯一键（订单号 + 事件类型），绝不是 messageId
// —— 生产端超时重发会产生新 entry、新 messageId，messageId 防不住这种重复
Boolean first = redis.opsForValue().setIfAbsent(
    "dedup:stock:" + event.getOrderId() + ":" + event.getType(),
    "1", Duration.ofHours(24));
return Boolean.TRUE.equals(first);

Namespace 级副本与去重策略

# namespace 级持久化策略（金融核心域用 3/3/3）
pulsar-admin namespaces set-persistence oms/core -e 3 -wq 3 -qa 2

# 开启 broker 端生产去重：按 producerName + sequenceId 丢弃重复写入
pulsar-admin namespaces set-deduplication oms/core --enable

DLT 治理三件套：DLT 消费 lag 告警（它是业务异常的影子库）、死信处理台（人工修数后重放）、DLT 消息按 subscription 隔离（同名订阅才能消费对应死信）。订阅模型与游标细节见0013 期，吞吐与延迟调优见0014 期。

✅ 可靠性体检清单

☐ 异步发送都处理了回调失败　☐ blockIfQueueFull=true 且 sendTimeout 已设　☐ 兜底 = Outbox 落库 + 对账重发　☐ Qa 档位与业务价值匹配（金融 3/3/3）　☐ bookie 机架感知部署、journal 刷盘未关　☐ ack 在业务成功之后　☐ ackTimeout 非零 + 重试队列 + DLT　☐ DLT 有 lag 告警与处理流程　☐ 消费幂等用业务键　☐ 有"消息不丢"的端到端对账

05今日要点

  • 可靠性是三段链路的合取：生产端送达确认、存储端副本落盘、消费端"处理成功才 ack"，任何一段掉链子，整体就是不可靠的——先分段归因，再谈方案。
  • 丢与重是同一枚硬币：所有"确认"机制（发送重试、ack 失败重投、消费者崩溃重投）在堵住丢失的同时都制造重复。目标不是消灭重复，而是用幂等把它吸收掉。
  • E/Qw/Qa 决定存储端档位：默认 3/3/2 覆盖绝大多数场景；金融级 3/3/3 把"确认后双 bookie 同灭"的窗口堵死，代价是确认延迟由最慢副本决定、写放大 3 倍。
  • 消费端三大铁律：ack 永远在业务成功之后；ackTimeout 必须显式设置（默认 0 = 未 ack 消息静默卡死）；重试队列 + DLT 必须配监控和处理流程，否则死信就是改了名的丢失。
  • effectively-once = at-least-once + 业务键幂等：幂等键用订单号等业务唯一键，不用 messageId——生产端重发会产生新的 messageId，防不住。

06架构师思考题

题目一：评审会上有同学说："我们要求一条都不能丢也不能重，直接上 Pulsar 事务 API 就实现了 exactly-once。"这个论断哪里站不住？你会给出怎样的落地组合拳？▶ 点击展开解析

🔍 裸 exactly-once 为什么不存在

根子在ACK 超时的二义性：生产者发出消息后超时，这一刻它无法区分"broker 没收到"和"broker 收到了、确认报文丢了"。重试 → 可能重复写入；放弃 → 可能丢失。这不是 Pulsar 的缺陷，而是不可靠网络上分布式确认的原罪（两将军问题的变体）。所以任何消息系统的端到端投递语义只能选边：at-most-once 或 at-least-once。

🔍 Pulsar 事务真正覆盖的范围

事务 API 解决的是consume-transform-produce 的原子提交：一个事务里消费的消息 ack 与产出的消息写入同生共死，还提供读偏序隔离。但它管不到外部副作用——你在处理逻辑里写了 MySQL、调了第三方接口、发了短信，这些都不在事务边界内，失败了事务照提交不了也回滚不了外部世界。而真实业务的消息消费恰恰几乎都带外部副作用。所以"上了事务 = 不丢不重"是把工具的适用范围想大了。

✅ 落地组合拳

  • 底座：全链路 at-least-once。生产端发送确认 + Outbox 兜底，存储端 3/3/2 或 3/3/3，消费端成功后 ack + ackTimeout + DLT；
  • 去重层一：broker 端生产去重。producerName + sequenceId，把"同生产者超时重发"这类重复在入口就挡掉；
  • 去重层二：消费幂等（关键）。幂等键必须用业务唯一键（订单号+事件类型），因为生产端重发会产生新 entry、新 messageId，messageId 防不住；实现上 Redis SETNX 或唯一索引去重表 + 24h 窗口，严格场景再加状态机校验（"已取消"的订单再收到取消事件直接忽略）；
  • 事务按需使用：只有"消费 A 主题 → 处理 → 生产 B 主题"这种纯消息链路的原子性需求才值得上事务，且要评估吞吐代价；涉及数据库的，用"本地消息表 + 事务"自己保证原子。

一句话：exactly-once 是营销话术，effectively-once（at-least-once + 幂等）才是工程真相。

题目二：3/3/2 被称为"安全默认值"，请构造一个它仍然丢消息的完整时序；journal fsync 在其中扮演什么角色？金融级为什么改 3/3/3，代价是什么，什么时候 3/3/2 就够？▶ 点击展开解析

🔍 丢消息时序（t1～t4）

t1：Broker 把 entry E 并行写给 Bookie A/B/C，A 的 journal fsync 完成、回 ack；t2：B 也 fsync 完成并回 ack —— Qa=2 满足，Broker 向生产者确认"E 已持久化"，但C 此刻还没写入；t3：A、B 所在的两台机器同时永久损毁（掉盘、主板烧毁，不是重启）；t4：E 在世界上只剩"C 上未完成的那份"，实际丢失——而生产者手里握着一条"已确认"。窗口就是 t2～t3：确认达成于第三副本落盘之前。

🔍 journal fsync 的角色

它保证的是"已经回过 ack 的 bookie 不因为宕机重启而丢数据"——先 fsync 到 journal 再回 ack，重启后从 journal 恢复。注意它挡住的是"确认后单机故障"，挡不住"确认后两台同时永久性损毁"——那个窗口属于 Qa 的选择问题。所以 fsync 是必要条件，不是充分条件；反过来说，任何人提议关闭 journal 刷盘换吞吐，等于把"确认"两个字变成谎言，直接否决。

✅ 档位决策

  • 3/3/3：三台全部落盘才确认，任意两台同时损毁也不丢（除非三台全灭）。代价：确认延迟从"第 2 快的 bookie"变成"最慢的那台"决定，长尾延迟上抬；bookie 写入吞吐压力增加（每条都要等最慢者）。金融、计费、审计域值得；
  • 3/3/2 + 部署纪律：机架/机房感知放置让"两台同时损毁"需要跨机架/跨机房级别的灾难，概率被压到与业务风险匹配的水平——在线业务够用，这是吞吐、延迟与可靠性的甜点；
  • 再往上：真正的金融核心再加"跨机房副本 + 定期快照备份 + 演练"，把 3/3/3 的单集群可靠性升级为架构级容灾——副本参数只是容灾的一层，不是全部。

一句话：Qa 决定"确认时敢信几台"，部署分布决定"几台同时坏要多大的灾"，两者合起来才是存储端的真实丢损概率。
