日志体系选型：ELK 与 Loki 的取舍

可观测性走到第三类信号：日志。上一讲（第 29 期）链路追踪已经把 TraceId 织进了每条日志，但这些日志散落在几百个 Pod 的 stdout 里——你要的是一套"存得起、查得到、查得快"的日志平台。这一讲从一次 ELK 存储账单膨胀复盘讲起，拆开 Elasticsearch 倒排索引与 Loki"只索引标签"两种哲学的成本分叉点，讲透 Loki 最容易翻车的流爆炸（标签基数是它的"高基数爆炸"），给出统一语义约定（TraceID/SeverityText）的结构化改造实战与 ELK 迁移 Loki 的五步方案，最后回答"能不能两个都要"。

🛠 架构运维 📅 2026-09-22 · 第 30 期 ⏱ 预计阅读 10 分钟

01一次"存储账单膨胀 8 倍"的 ELK 复盘

某平台 60 个微服务上 K8s 后，日志统一进 ELK（Filebeat → Logstash → Elasticsearch → Kibana），头一年风平浪静：日增 200GB 原始日志，保留 30 天，ES 集群 6 数据节点跑得稳稳的。第二年开春两件事撞在一起——业务量翻倍、顺带把 K8s 元数据字段全量带进了每个文档。存储从 12TB 悄悄涨到 90TB+：原始日志多了 1 倍，索引膨胀贡献了剩下 3 倍多（每行日志的所有分词进倒排索引、_source 存原始 JSON、doc values 存列值、副本再 ×2）。集群开始频繁投毒：热点分片把磁盘 IO 打满，查询 P99 十几秒，大促压测期间 ES 先于业务挂掉——这是 ELK 用户的经典剧本。

复盘时发现更扎心的账：过去 90 天的查询里，95% 是"某服务某时间窗的 ERROR 日志"这类带上下文的定向查询，真正用到"全库任意词搜索"的不到 5%——但所有日志都在为 100% 的全文索引能力付钱。安全团队一次"在 90 天日志里大海捞针找某个支付单号"确实救过急，可那是三个月里唯一一次。

复盘结论：日志平台的选型分歧，本质是"为哪种查询模式付钱"。ELK 为全文检索付索引钱，Loki 为"标签圈定 + 内容扫描"付查询时间钱。这不是哪个更好的问题，是访问模式占比的问题——这一讲把这笔账算清楚。

02原理：两种索引哲学与查询代价模型

ELK 的本质是搜索引擎。Elasticsearch 继承 Lucene 血统：每行日志写入时被分词、展开成倒排索引（词 → 文档列表）、_source（原始 JSON）、doc values（列式排序聚合），再加副本容灾——同一个字段值落在多个结构里。代价换来的是"任意词毫秒级命中"，且词汇表里有模糊匹配、相关性评分、任意字段聚合。值得一提的是 ES 自己也在治这个账：9.0 起 logsdb 索引模式成为 logs 数据流默认（主机优先排序 + 合成 _source + ZSTD 压缩，官方口径最高省 65%+ 存储）——但"写入时全量索引"的哲学没变，只是把同样的哲学压缩得更便宜。

Loki 的本质是"分组 + grep"。设计宣言是"像给 Prometheus 打标签一样给日志打标签"：索引里只存标签组合 → 压缩块位置的映射，日志内容本身以 gzip/snappy 压缩块躺在对象存储（S3/OSS/MinIO）里。查询分两步：先用标签选择器（{app="payment", level="error"}）从索引圈出少量流（stream）的时间段，再把对应压缩块拉下来解压、按行过滤。写入路径几乎只剩"压缩 + 追加"，所以摄入吞吐高、存储便宜（社区参考值：原始量 5~10 倍压缩后进对象存储，约 $0.02/GB 量级；对比 ES 本地 SSD $0.10/GB + 索引膨胀）。同样的便宜也意味着查询侧的边界必须诚实：没有标签圈定的"全库搜某个词"、跨几十个小时的宽窗扫描，就是大量拉块解压——几秒到几十秒能回来，但它永远赢不了倒排索引的主场。

Loki 3.x 的两个现代能力，选型时要摆进天平

① 原生 OTLP 摄取端点：Loki 3.0 起可直接接收 OpenTelemetry 的 OTLP 日志（http://loki:3100/otlp），不再需要 Collector 里那个已废弃的 Loki exporter 做格式转换；资源属性自动映射为标签（service.name → service_name 等，点号规范化为下划线），其余属性进结构化元数据（Structured Metadata）——可不建索引、查询时无需 json 管道就能直接过滤（如 | severity_text="ERROR"）,"高维上下文不付索引钱"就是这个机制。标签策略收敛成服务端一处配置（limits_config.otlp_config 可对每个属性指定 index_label / structured_metadata / drop），平台团队改策略不用重发应用。② 模式识别与 pattern 过滤：自动聚类相似日志行、变量位置挖洞，配合 pattern 过滤运算符做"日志模板分析"，治的是"打印了一大篇但其实是同 20 个模板"的观测噪声。注意：原生 OTLP 的默认标签白名单里有 k8s.pod.name、service.instance.id 这类高基数项（官方文档已提示审计），落地时要主动降级处理。

03架构设计：选型决策、流爆炸防线与容量账

选型对比：八维一张表

维度ELK（Elasticsearch）Loki（+ Grafana）
索引哲学全文倒排，任意词毫秒级只索引标签，内容查询时扫
存储与成本本地/网络 SSD，含索引为原始量 3~6 倍对象存储，压缩 5~10 倍，约为 ELK 的 1/5~1/10
典型查询体验全文/模糊/聚合全能标签圈定快；宽窗全库扫描慢数秒到数十秒
高基数爆炸点mapping 字段数失控（mapping explosion）标签组合失控 → 流爆炸（ingester 内存+索引）
运维形态有状态 JVM 集群：分片/ILM/堆内存，专职运维存算可分离：读/写路径独立扩缩，状态外置对象存储
多租户索引级隔离，较重内置租户头（X-Scope-OrgID），轻
生态契合检索/安全审计/SIEM 场景深Grafana 面板里与 Prometheus 指标、Tempo 链路同屏联动
许可证SSPL/Elastic 许可（OpenSearch 为 Apache 2.0 分支）AGPL v3

选型口诀：按查询画像投票。95% 定向排障（知道服务、知道时间窗）+ 成本敏感 + 已在 Grafana 体系 → Loki；全文检索/安全审计/复杂聚合是日常主业、或合规要求任意词可查 → ELK/OpenSearch；两者都重 → 分层混合（Loki 存全量长保留，ELK 只收错误/安全/关键链路子集）。别忘了第三票是团队：ES 集群要有人会养（分片、ILM、堆调优），Loki 的运维面小但出了流爆炸也得有人会查——没有对应技能的团队，选型优势兑现不了。

流爆炸：Loki 版的"高基数爆炸"

与第 28 期 Prometheus 的序列爆炸同构：每一种唯一的标签组合 = 一条独立的流（stream），每条流有独立的块、独立的索引项、独立的刷盘行为。把 user_id、request_id、trace_id 塞进标签，百万用户就是百万条流——索引膨胀、ingester 内存告警、小碎块刷爆对象存储，集群直接趴下。防线三道：① 标签白名单制度：只有"描述日志来自哪"的静态低基数键可进标签（app/env/namespace/container/level），"描述日志说了什么"的一切高基数值进日志行或结构化元数据；② 服务端闸门：max_streams_per_user、max_global_streams_per_tenant、每流速率限制 per_stream_rate_limit（超限拒绝并计数，可观测到而不是默默炸）；③ 审计常态化：用 Loki 自身的指标与 topk 查询找出最大的流生产者，纳入平台巡检。这是从 ELK 迁过来的团队最容易撞的墙——在 ES 里"多索引一个字段"是习惯，在 Loki 里是事故。

容量三笔账（日增 200GB 原始日志、保留 30 天、95% 定向查询画像）

存储账：Loki 侧 200GB/天 ÷ 8（压缩比 5~10 取中）≈ 25GB/天 × 30 天 ≈ 750GB 对象存储，按 $0.02/GB/月 ≈ $15/月，加索引零头；同样数据 ES 侧 200GB × 30 天 × 4（索引膨胀+副本）≈ 24TB SSD ≈ $2400/月——一个数量级的存储差（ES 9 logsdb 能压回不少，但量级差在"对象存储 vs SSD"这条底层轴上）。查询账：定向查询（标签圈定 ≤ 几十条流、15 分钟窗）秒级返回；宽窗全库扫描要评估查询并发与读路径扩容（读副本水平扩展），把"全库捞针"路由给 ELK 子集或事前采样。保留账：Loki 便宜到"热日志 7 天 + 对象存储归档 180 天"都做得起；ELK 的保留期每个档位都是真金白银，通常只保热 7~14 天。两条总开关仍然是：保留期 × 采样/分级策略——与第 28/29 期同一句结论，三类信号的成本治理是一个思想。

04实战：结构化改造、LogQL 与迁移五步

第一步永远是语义统一（无论选哪个平台）

先按 OpenTelemetry 语义约定改造日志格式——这是比"选 ELK 还是 Loki"更根本的工程：TraceID/SpanID 进资源属性（接第 29 期的 %tid），级别用语义键 SeverityText，服务名统一 service.name。格式统一成 JSON 后，ELK 的字段解析和 Loki 的 | json 管道都直接可用，也把未来接入 OTel Collector 的路铺平了。

# logback 输出 OTLP 语义的 JSON 日志（MDC 里已有 trace_id/span_id，见第 29 期）
{
  "timestamp": "2026-09-22T10:15:32.412Z",
  "severity_text": "ERROR",
  "service_name": "payment",
  "trace_id": "a4f7c2e9b1d3...",     # 与链路追踪互通的钥匙
  "span_id": "6b2e9f1c8a4d...",
  "order_no": "PO2026092215",         # 高基数业务键：留在行内，绝不进标签
  "body": "支付回调处理失败: 下游超时"
}

Loki 侧：Alloy 采集 + LogQL 三板斧

# Alloy（OTel Collector 发行版）日志管线：K8s 发现 → 只放行低基数标签 → OTLP 直推 Loki
# promtail 同理：kubernetes_sd_configs + relabel_configs 白名单
loki.source.kubernetes "pods" { targets = discovery.kubernetes.pods.targets }
loki.process "drop_hi_card" {
  forward_to = [loki.write.default.receiver]
  stage.labels { values = { app = "", namespace = "", level = "" } }   # 白名单：只放静态键
}
loki.write "default" { endpoint { url = "http://loki-gateway:3100/loki/api/v1/push" } }
# LogQL 三板斧 —— ① 定向排障：标签圈定 + 行过滤 + 取上下文
{app="payment", level="error"} |= "回调处理失败" | json | order_no="PO2026092215"
# ② 指标化：把日志变成告警序列（日志版 rate）
sum by (app) (count_over_time({level="error"}[5m])) > 50
# ③ 大盘：各服务错误日志量排行
topk(10, sum by (app) (bytes_rate({namespace="prod"}[1h])))

三板斧的用法边界要清楚：| json 管道发生在查询时、扫多少行就解多少行——白名单标签 + 15 分钟窗内它很快，宽窗全量解析它就慢；这正是 02 节代价模型的日常体现。若走了 OTLP 原生摄取，severity_text、trace_id 等已是结构化元数据，可跳过 json 管道直接过滤。

ELK 迁移 Loki：五步走

  1. 查询画像审计：拉 90 天 Kibana 查询日志，统计"带服务/时间窗的定向查询"占比；全文检索占比高且刚性的部分（安全审计）标记保留在 ES。
  2. 结构化与标签白名单落地：日志改 JSON + 语义键，采集层白名单定型——这一步做扎实，后面全是顺水推舟。
  3. 双写并行（影子期）：采集层同时推 ES 与 Loki（Alloy/Promtail 多出口），只验证不切流；重点观察流数量、ingester 内存、查询体验对照。
  4. 看板与告警搬迁：Kibana 仪表盘 → Grafana（LogQL 重写）、Watcher → Loki Ruler/Grafana Alerting；常用查询沉淀成 variables 模板，别让每个人重学一遍。
  5. 灰度切流 + ES 降级：团队逐个切查询入口，观察一个完整故障周期；ES 数据按保留期自然滚动清空，硬件分批回收——不做 reindex 搬家（历史日志让它按保留期自然过期，比搬运便宜得多）。

三个必踩的坑：① 把 ELK 习惯带进 Loki——什么字段都想要索引，半年后流爆炸；记住"标签描述日志来自哪，行内容描述它说了什么"。② 裸容器化部署 Loki 单体——量小没事，量上来读写互相拖累；Simple Scalable 模式（读/写分组独立扩缩）是自建的标准姿势，状态全部外置对象存储。③ 忽视采集层的解析职责——Loki 不替你解析日志，多行堆栈（异常 stack trace）必须在采集层配多行合并（multiline），否则一行堆栈碎成 N 条流记录，ERROR 日志根本看不全。

✅ 上线体检清单

☐ 标签白名单已评审（只含 app/env/namespace/container/level 级别静态键），高基数键全部留在行内或结构化元数据　☐ 90 天查询画像已审计，选型结论有数据背书　☐ max_streams_per_user 等服务端闸门已配并接了告警　☐ 多行堆栈合并（multiline）已在采集层配置并抽查验证　☐ 保留策略已定（热 + 归档两档），compactor 清理任务已启用　☐ TraceID 语义键已进日志结构，Grafana 里日志 ↔ 链路可互跳　☐ 日志量指标看板已建（bytes_rate / topk 流量异常发现）　☐ 告警规则用 LogQL 指标化语法重写并验证触发　☐ 双写影子期结论已归档（流数/内存/查询耗时对照）　☐ 安全审计等全文检索刚需已安排归属（ELK 子集或保留 ES）

05今日要点

  • 索引哲学决定账单结构：ELK 写入时付钱（全文索引换任意查询毫秒级），Loki 查询时付钱（标签圈定 + 压缩扫描换对象存储级便宜）——选型是查询画像问题，不是优劣问题。
  • 流爆炸是 Loki 的第一杀手：唯一标签组合 = 独立流；高基数值（user_id/trace_id/order_no）永远不进标签。标签描述"来自哪"，行内容描述"说了什么"——与 Prometheus 高基数治理同一个思想。
  • 语义统一比平台选型更根本：OTLP 语义键（service.name/severity_text/trace_id）+ JSON 结构化，让日志与指标、链路三信号互通；Loki 3.x 原生 OTLP 端点让这条路零转换成本。
  • 容量两条总开关不变：保留期 × 采样分级；对象存储便宜到值得"热 7 天 + 归档 180 天"，ES 的保留期每个档位都是真金白银。
  • 混合架构是体面答案：Loki 存全量长保留 + ELK 只收错误/安全/关键链路子集，两个平台各干各的主场，别让任何一个干全部。

06架构师思考题

题目一：你们 ES 集群日增原始日志 500GB、保留 15 天，存储已经压不起，CTO 要求"日志成本砍到 1/5，查询体验不能明显变差"。① 先给三个"不动平台也能省钱"的动作；② 如果决定迁 Loki，给出容量估算与切流步骤；③ "查询体验不能变差"你怎么验收？▶ 点击展开解析

🔍 逐问拆解

① 先摘低垂的果实，再谈换平台：第一，调级降采样——DEBUG/INFO 按服务分级降保留（比如 DEBUG 只保 24 小时甚至不落平台），ERROR/WARN 全保留；多数系统里 DEBUG 体量占 60~80%，一刀下去存储账单先掉一半。第二，字段瘦身——审计采集层带进来的 K8s 元数据字段，砍掉查询里从未用过的（labels/annotations 整个 JSON 常常是白拖的）；ES 侧再确认 logsdb 索引模式与合成 _source（9.0 已默认）生效，老集群升级能省一大截。第三，ILM 分层——热数据 SSD 3 天、温节点便宜盘、冻结层可搜索快照，把"全量都热"改成按访问频率分层。这三步做完通常已省 40~60%，而且给"是否真要迁移"赢得了冷静评估的时间——没做过这三步就上马迁移，多半会把坏习惯一起带进新平台。

② 容量估算：假设降级采样后日增 300GB（DEBUG 只保 1 天折算）。Loki 侧：300GB ÷ 8（压缩 5~10 取中）≈ 38GB/天；ERROR/WARN 全量 + 其他降保留，平均按"7 天热 + 90 天归档"算：38GB × 7 ≈ 266GB 热 + 38GB × 90 ≈ 3.4TB 归档，对象存储总账不到 4TB，月成本几十美元量级；读写路径：Simple Scalable 模式起步 2 写 + 2 读副本（ ingest 300GB/天 ≈ 峰值 10~20MB/s，对 Loki 是小菜），memcached 结果缓存一块。切流五步照第 04 节：查询画像审计 → 结构化+标签白名单 → 双写影子期（重点盯流数与 ingester 内存）→ 看板告警搬迁 → 灰度切流、ES 按保留期自然滚动清空。不搬历史数据——ES 留着只读跑完保留期，比 reindex 便宜且风险低。

③ 验收要量化、不能凭感觉：影子期把 90 天真实查询日志里的 Top 50 高频查询在两边各跑一遍，统计 P50/P95 耗时与结果一致性（抽样比对行数与内容）；定义体验红线——定向查询 P95 < 3 秒、告警规则评估周期内无超时；把"全库任意词搜索"这类长尾查询单独归类，明确它们走保留的 ES 子集（或接受降级为采样检索），在验收单上写清楚每个查询类的归属和耗时承诺。最后留一个月并行期，让"查询体验不能变差"由值班工程师的实际使用投票，而不是架构评审会上拍胸脯。

题目二：Loki 上线三个月后的凌晨，Grafana 突然报 ingester 内存 92%、写入 429 限流，业务日志出现缺口。排查发现某团队把 user_id（千万级）放进了日志标签，还有团队采集器把整个 K8s labels JSON 塞进了标签。① 现场怎么止血？② 流爆炸的根因链条完整讲一遍；③ 治理机制怎么设计，让这类事故不再靠事后发现？▶ 点击展开解析

🔍 逐问拆解

① 止血三步，顺序很重要：第一步，定位最大流生产者——用 Loki 自身指标（per-tenant streams、topk 按标签组合的 chunk 数）或 /loki/api/v1/label 系列接口，找出谁在制造海量流；第二步，掐源头而不是扩容——通知两个团队改采集配置（去掉 user_id 与 K8s labels 标签）滚动重启采集器；配置改不动时用服务端手段：把对应标签在 limits_config 里降级或用 max_label_names_per_series/max_streams_per_user 强制拒收（429 已在拒，确认拒绝计数归属到租户，让对方"疼得知道找谁"）；第三步，ingester 侧缓解——必要时临时调低 flush 阈值让块尽快落盘、水平加 ingester 副本分摊（注意这是争取时间不是治病）。顺序错了会白花钱：先扩容，等于给泄漏的管道换更大的泵。

② 根因链条：高基数标签 → 每个唯一组合注册一条流 → 每条流在 ingester 里独立的 chunk + 索引条目 + 刷盘单元 → 流数从千级暴涨到百万级：索引膨胀（查询定位变慢）、ingester 内存被小碎块吃满（每个未刷盘的 chunk 都占内存）、对象存储出现海量小对象（请求放大）、写入触发 429 限流 → 日志缺口。要害在于它和第 28 期 Prometheus 序列爆炸、第 26 期向量库内存墙是同一个数学结构：基数 × 每单位成本——唯一的标签组合数乘上每条流的固定开销，超过了系统设计水位。user_id 千万级基数一进标签，这场爆炸在数学上就已经发生了，只差几小时发酵时间。

③ 治理三道防线：第一道，采集模板集中管理——标签白名单固化在平台统一分发的 Alloy/Promtail 配置里，业务侧只能选白名单内的标签，"想加标签"走平台评审（评审清单就一条：基数上限是多少）；第二道，服务端硬闸门 + 提前告警——max_streams_per_user/max_global_streams_per_tenant 按容量模型设定并留 50% 余量，stream 数、429 计数、ingester 内存三条告警在"爬坡期"就该响（阈值设在 60~70% 而不是 90%），把事故从事后发现变成事前拦住；第三道，租户维度可观测——每个团队的日志按租户（X-Scope-OrgID）或至少按 label 源头隔离计量，流量/流数排行周报自动化，谁引入高基数标签当周就能看到。配套一条组织规则：采集配置变更与代码变更同级走评审——流爆炸从来不是 Loki 的 Bug，是治理缺位的必然结果。
