MySQL 主从复制与读写分离架构
从"一台扛不住"到"横向扩展"的架构演进之路

🗄️ MySQL 系列 · 主从复制 📅 2026-08-15 ⏱️ 预计阅读 10 分钟
SCENARIO · 从实际问题出发

🚨 业务量翻了 10 倍，单库先倒下了

某电商系统大促期间，订单库 QPS 从平时的 800 暴涨到 12000。DBA 观察到三个典型症状：

  • CPU 飙到 95%+，其中 80% 以上消耗在SELECT查询上（商品浏览、订单列表、报表统计）；
  • 写操作被拖慢：下单事务等待行锁的时间从 2ms 涨到 300ms；
  • 可用性风险：单点故障即全站不可用，没有灾备能力。

此时垂直拆库、索引优化都已做过，下一步的自然选择是主从复制 + 读写分离：写走主库，读走从库，把 80% 的读流量剥离出去，同时获得一份实时热备数据。这是架构师必须掌握的第一级横向扩展手段——比分库分表轻量得多，且对业务代码侵入小。

PRINCIPLE · 原理讲解

📦 主从复制的本质：Binlog 的搬运与重放

三线程协作机制

  1. 主库事务提交时写 Binlog（逻辑日志，记录行变更事件）；
  2. 从库 IO Thread 连接主库，主库 Binlog Dump 线程 推送 binlog 事件；
  3. 从库把收到的事件写入本地 Relay Log（中继日志）；
  4. 从库 SQL Thread（或多线程复制 Worker）重放 Relay Log，数据达成一致。

三种复制模式——架构师的关键选型

模式数据安全延迟适用场景
异步复制（默认）主库不等从库，宕机可能丢数据最低日志、非核心读扩展
半同步复制≥1 个从库 ACK 后才提交成功中（增加 RTT）金融/订单等核心链路推荐
组复制 MGR基于 Paxos 变种，强一致多数派较高金融高可用集群
Binlog 格式选型：生产环境统一使用 ROW 格式——基于行镜像复制，主从数据一致性最强，且是 MGR/ Canal 等数据订阅生态的前提。STATEMENT 格式在 NOW()、UUID()、自增等场景下会导致主从不一致。

并行复制：解决"重放慢"的关键参数

MySQL 5.7+ 引入基于组提交的并行复制（LOGICAL_CLOCK），8.0 进一步支持 WRITESET 无冲突判定，让从库 SQL Thread 多线程重放成为可能：

从库 my.cnf — 并行复制提速ini
slave_parallel_type   = LOGICAL_CLOCK      # 按事务组并行（而非库级）
slave_parallel_workers = 16                  # SQL 重放线程数，一般 8~16
binlog_transaction_dependency_tracking = WRITESET  # 8.0: 行级冲突判定，并行度更高
relay_log_recovery     = ON                  # 从库崩溃后自动恢复 relay log
ARCHITECTURE · 架构设计思路

🏗️ 读写分离架构：不只是"读走从库"这么简单

容量规划（先算账，再扩容）

  • 按读 QPS ÷ 单库读上限（约按 70% 水位） 确定从库数量：如总读 12000，单库水位上限 5000，则需 12000/5000 ≈ 3 个读实例（含 1 个冗余）；
  • 从库与主库同规格起步（重放也消耗资源），纯报表类从库可单独降配 + 限定查询；
  • 延迟预算：核心链路要求复制延迟 < 200ms，超过即触发告警。

路由层的三种实现

方案代表优点坑点
客户端驱动ShardingSphere-JDBC无中间件、性能好多语言需各自维护
代理层ShardingSphere-Proxy / MyCat / ProxySQL对业务透明、异构语言友好多一跳延迟、代理自身高可用
代码注解 dynamic-datasource + @DS灵活、可方法级控制侵入业务代码

最强坑点：读己之写（Read Your Writes）

用户下单后立即查订单列表——写走主库、读走从库，如果复制延迟 500ms，用户会看到"订单消失了"。三种解法按代价排序：

  1. 关键字段强制读主（推荐）：下单后的 N 秒内、或携带 orderId 的查询路由主库，用注解标记；
  2. 会话粘性：写后短时间窗口内该用户请求固定走主库（注意主库压力）；
  3. 等待 GTID：记录写事务的 GTID，读前在从库执行 SELECT WAIT_FOR_EXECUTED_GTID_SET()——最严谨但实现最重。
PRACTICE · 实战示例

🔧 从零搭建一主一从 + 半同步 + 注解路由

Step 1：主库配置

主库 my.cnf [mysqld] 段ini
server-id         = 1
log_bin           = mysql-bin
binlog_format     = ROW          # 生产强制 ROW
binlog_row_image  = FULL         # 保留完整前后镜像，便于数据闪回
gtid_mode         = ON
enforce_gtid_consistency = ON
sync_binlog       = 1            # 每事务刷盘，双一之一
innodb_flush_log_at_trx_commit = 1
# 半同步插件（8.0.26+ 改名 rpl_semi_sync）
rpl_semi_sync_master_enabled  = ON
rpl_semi_sync_master_timeout  = 3000  # 3s 超时降级为异步，防雪崩

Step 2：建立复制账号并授权

主库执行sql
CREATE USER 'repl'@'192.168.10.%' IDENTIFIED WITH caching_sha2_password BY 'Strong#Pass123';
GRANT REPLICATION SLAVE ON *.* TO 'repl'@'192.168.10.%';
SHOW MASTER STATUS\G   # 记下 binlog 文件名与位点（GTID 模式可跳过）

Step 3：从库指向主库（GTID 自动定位）

从库执行sql
CHANGE MASTER TO
  MASTER_HOST     = '192.168.10.11',
  MASTER_USER     = 'repl',
  MASTER_PASSWORD = 'Strong#Pass123',
  MASTER_AUTO_POSITION = 1;        # GTID 自动找位点，免手工对 binlog 位点
START SLAVE;                            # 8.0.22+ 推荐 START REPLICA
SHOW SLAVE STATUS\G  # 确认两列均为 Yes：
#   Slave_IO_Running: Yes / Slave_SQL_Running: Yes
#   Seconds_Behind_Master: 0  ← 核心监控指标

Step 4：应用层读写分离（dynamic-datasource）

pom.xml 依赖xml
<dependency>
  <groupId>com.baomidou</groupId>
  <artifactId>dynamic-datasource-spring-boot3-starter</artifactId>
  <version>4.3.0</version>
</dependency>
application.yml — 一主两从 + 读己之写yaml
spring:
  datasource:
    dynamic:
      primary: master
      strict: false
      datasource:
        master:
          url: jdbc:mysql://10.0.0.1:3306/Orders?useSSL=true
          username: app_wr
        slave_1:
          url: jdbc:mysql://10.0.0.2:3306/Orders
        slave_2:
          url: jdbc:mysql://10.0.0.3:3306/Orders
      seata: false
# Service 层：@DS("slave_1") 走从库；下单后查询加 @DS("master") 保证读己之写
OrderService.java — 读己之写落地java
// 写：默认主库
@Transactional
public Order createOrder(OrderDTO dto) {
    Order order = orderMapper.insert(buildOrder(dto));
    // 下单后 5 秒内的列表查询走主库（读己之写窗口）
    redisTemplate.opsForValue().set("readmaster:" + dto.getUserId(),
                          "1", Duration.ofSeconds(5));
    return order;
}

// 读：默认从库，命中读主标记则切主库
@DS("#session.readMaster ? 'master' : 'slave_1'")
public List<Order> listMyOrders(Long userId) { ... }

Step 5：排障三连（生产必备）

复制延迟排查命令bash
# 1. 看延迟有多大（持续观察优于一次性）
$ mysql -e "SHOW SLAVE STATUS\G" | grep -E "Seconds_Behind|Slave_.*_Running"

# 2. 定位是 IO 慢还是 SQL 重放慢
$ mysql -e "SELECT * FROM performance_schema.replication_applier_status_by_worker\G"

# 3. 大事务是延迟头号元凶——找出单事务超大 binlog
$ mysqlbinlog --base64-output=decode-rows -vv mysql-bin.000123 \
    | grep -c "^###"   # 事件行数异常多即大事务，须拆批（单事务建议 < 1000 行）
经典翻车现场：① 从库上直接写数据 → 主键冲突导致 SQL Thread 卡死，复制中断（修复：set global read_only=ON; super_read_only=ON，并给从库连接串加只读账号）；② 半同步超时未设 → 从库抖动时主库写入全面阻塞（务必设置 rpl_semi_sync_master_timeout 自动降级）；③ 只监控进程不监控延迟 → IO/SQL 都 Yes 但延迟 30 分钟，报表读到的全是旧数据。
TAKEAWAYS · 今日要点

✅ 今日要点

  1. 复制本质是 Binlog 的异步搬运与重放（Dump → IO Thread → Relay Log → SQL Thread），性能瓶颈通常出现在 SQL 重放端，用 LOGICAL_CLOCK + WRITESET 并行复制破解。
  2. 核心链路用半同步（设置超时自动降级防雪崩），非核心用异步；金融级强一致直接上 MGR 组复制。
  3. 容量规划按读 QPS ÷ 单库水位上限 计算从库数，从库与主库同规格起步，延迟预算纳入 SLO。
  4. 读写分离最大的坑是"读己之写"：写后短窗口强制读主是最实用的工程解。
  5. 监控盯三样：Seconds_Behind_Master、两个 Running 状态、大事务 binlog 行数；从库必须 read_only + super_read_only。
THINK · 架构师思考题

🧠 架构师思考题

思考题一：主库宕机，半同步从库提升为新主库后，如何处理已提交但未复制到新主库的"丢失事务"？如何在架构上把这种丢失概率降到最低？

① 先理解丢失是怎么发生的

半同步在超时（如 3s）后会自动降级为异步。若恰好在"降级窗口"内主库宕机，部分已向客户端返回成功的事务只存在于旧主库的 binlog 中——新主库提升后，这些事务对用户来说"凭空消失"。更隐蔽的是，如果老主库恢复后被直接加回集群，它比新主库多出来的事务会造成主键冲突或数据分叉。

② 故障恢复时的标准动作

  • 旧主库先别急着拉回集群：用 mysqlbinlog 或 gtid_executed 对比新旧主的 GTID 集合，找出差集（旧主多出的事务）；
  • 差集事务若为合法业务数据：导出后在新主上人工重放（幂等设计此时是救命稻草）；若是脏数据：跳过并记录审计；
  • 旧主库以新数据快照重建（从备份 + binlog PITR，或直接从新主克隆），再以从库身份加回。

③ 架构上降低丢失概率的手段（按层次）

  • 半同步 + AFTER_SYNC（lossless semi-sync，8.0 默认）：ACK 发生在引擎提交前，保证不丢已 ACK 事务，优于旧版 AFTER_COMMIT；
  • 双一配置 sync_binlog=1 + innodb_flush_log_at_trx_commit=1：即使宕机也不丢本地 binlog，为恢复提供完整依据；
  • MGR 多数派： Paxos 保证多数节点确认才提交，单节点故障天然不丢；代价是写性能与网络要求；
  • 业务侧兜底：关键操作幂等 + 本地消息表/事件溯源，即使底层丢事务也能对账补偿。

④ 一句话结论

半同步降级窗口的丢失风险无法绝对消除，架构师要做的是：缩短窗口（AFTER_SYNC）+ 保证可恢复（双一 + GTID 对账）+ 业务可补偿（幂等），三者叠加把 RPO 逼近于零。

思考题二：从库延迟从 0.1s 持续恶化到 60s，你的系统性排查路径是什么？哪些架构层面的"治本"手段？

① 先分诊：延迟在 IO 端还是 SQL 端？

看 SHOW SLAVE STATUS 三个信号：Seconds_Behind_Master 波动、Master_Log_File 与 Relay_Master_Log_File 的差距、performance_schema.replication_applier_status_by_worker 中各 worker 的 LAST_APPLIED_TRANSACTION。若 IO 端延迟（relay log 追不上 master binlog）→ 网络或主库 Dump 线程问题；若 SQL 端积压（relay log 堆积）→ 重放能力不足，90% 的案例在这一端。

② SQL 端五大元凶逐项排查

  1. 大事务：单事务百万行 DELETE/UPDATE，SQL Thread 重放数小时 → 拆成 1000 行一批的循环；
  2. 从库上的慢查询/锁等待：报表 SQL 打满从库资源，重放线程拿不到 CPU 或被行锁阻塞 → 查 performance_schema 的锁等待，报表隔离到专用从库；
  3. 并行度不足：主库高并发小事务，从库单线程重放天然跟不上 → WRITESET + slave_parallel_workers=16；
  4. 从库硬件降配：机械盘 vs 主库 NVMe，重放 IO 跟不上 → 从库至少与主库同档 IO 能力；
  5. 长事务导致锁级联：主库 10 分钟的大事务持有行锁，从库重放同样持锁阻塞后续可并行事务。

③ 架构层"治本"手段

  • 读写分组隔离：核心读从库（强同步要求）与报表/统计从库物理隔离，互不拖累；
  • 应用层延迟感知路由：中间件检查 Seconds_Behind_Master 超阈值（如 1s）自动把读切回主库，牺牲主库压力换一致性；
  • 写入端治理：事务大小纳入开发规范（单事务 ≤1000 行 / ≤10MB binlog），大任务改用 pt-archiver 分批；
  • 终极形态：读压力继续增长时，引入二级架构——分库分表（ShardingSphere）或把纯查询下沉到 ES/ClickHouse，让 MySQL 专注事务本身。

④ 一句话结论

排查遵循"先定位端（IO/SQL）→ 再找元凶（大事务/锁/并行度/硬件）→ 后治架构（隔离/路由/写入治理）"；延迟不是 DBA 一个人的战斗，而是写入规范 + 资源规划 + 路由策略的系统性工程。
