Redis 分布式锁：从 SET NX 到 Redisson 看门狗与 RedLock 争议

📅 2026-08-21（周五） ⚡ Redis 系列 · 第 5 讲 ⏱ 预计阅读 10 分钟 🎯 SET NX PX / Lua 原子释放 / 看门狗 / RedLock

一、一场"库存变负数"的经典事故

某秒杀系统库存只剩 1 件，两个应用实例同时收到下单请求，各自执行"查库存 → 扣减"。单机时代 synchronized 能锁住进程内并发，但服务是多实例部署的——两个 JVM 各自加锁互不可见，双双读到"库存=1"，双双扣减成功，库存变成 -1。这就是 check-then-act 竞态：读和写不是原子操作，锁的粒度只覆盖了单个进程。

解法是把锁从"进程内"升级到"所有实例可见的共享介质"。Redis 单线程执行命令、延迟低、几乎不额外部署，成了分布式锁最常用的载体。但一行 SETNX 背后藏着四个致命陷阱，今天逐个拆解。

⚠️ 分布式锁的正确性边界 Redis 锁是效率优先（efficiency）的锁：目标是减少重复计算、防止偶发并发，偶尔失效可接受。若业务要求正确性优先（correctness）——错一次就资损（扣款、扣库存），必须叠加数据库层兜底（乐观锁 / 唯一约束），不能把 Redis 锁当唯一防线。

二、四个陷阱与对应解法

陷阱 1：加锁不是原子操作

先 SETNX 再 EXPIRE 两条命令之间进程崩溃，锁成为永不过期的死锁。正解是一条原子命令：

# SET key value NX PX 过期毫秒数 —— NX=不存在才设置，PX=毫秒过期
SET lock:order:1001 "uuid-a1b2" NX PX 30000

陷阱 2：误删别人的锁

客户端 A 业务执行超时，锁自动过期；客户端 B 获得锁后，A 缓过来执行 DEL，把 B 的锁删了——C 又能加锁，B、C 并发。所以 value 必须是每个客户端唯一的标识（UUID+线程 ID），且"判断 + 删除"必须用 Lua 脚本保证原子：

-- release.lua：是我的锁才删
if redis.call("GET", KEYS[1]) == ARGV[1] then
    return redis.call("DEL", KEYS[1])
else
    return 0
end

陷阱 3：过期时间定多少？—— 看门狗机制

设短了业务没执行完锁先过期；设长了持有者崩溃后其他人干等。Redisson 的看门狗（Watchdog）解法：不指定 leaseTime 时，锁默认 30s，后台任务每 30/3=10s 检查一次，业务没执行完就自动续期；进程崩溃则无人续期，锁最多 30s 后自动释放——两难自解。

陷阱 4：主从切换导致锁丢失 —— 最隐蔽的一个

Redis 主从复制是异步的。下面这个时序是 RedLock 方案诞生的直接原因：

① T1客户端 A 在 master 上加锁成功 SET lock NX PX ✅
② T2master 还没来得及把锁 key 异步复制给 slave，master 宕机 💥
③ T3slave 晋升为新 master，但它没有这把锁的数据
④ T4客户端 B 在新 master 上加锁也成功 → A、B 同时持锁，互斥性被打破 ❌
主从切换窗口内锁丢失：异步复制的固有缺陷，单个 Redis 主从架构无解

三、RedLock 与业界著名争论

antirez（Redis 作者）提出 RedLock：部署 2N+1 个互相独立的 Redis 单实例，客户端依次向所有实例加锁（带超时），多数派（N+1）成功且总耗时小于锁有效期才算持锁。任何一台宕机、主从切换丢锁，都只影响少数派，互斥性得以维持。代价是：5 套独立实例的运维成本，且丧失了 Redis Cluster 的弹性伸缩能力。

分布式系统学者 Martin Kleppmann（《DDIA》作者）公开质疑：若客户端在加锁成功后发生长 GC 停顿 / 时钟跳变，暂停恢复时锁已过期，客户端却仍以为自己持锁，继续写共享资源——RedLock 这种依赖时间做判断的锁无法防御。他主张用 fencing token：锁服务发放单调递增的令牌，存储层拒绝携带旧令牌的写入。antirez 反驳称时钟跳变可控、场景极端。工程界的务实结论：

方案一致性性能适用场景
单 Redis + RedissonAP，可能丢锁极高（单跳）绝大多数效率型场景 + DB 兜底
RedLock（多独立实例）较强但有时钟依赖中（需多数派 RTT）无 DB 兜底层、跨系统互斥
ZooKeeper / etcd 临时节点CP，会话断自动释放较低（Raft/ZAB 写放大）正确性敏感：主备选举、任务分配
数据库乐观锁/唯一约束强（最终防线）低资损类操作的最后一道闸
💡 架构师选型建议 默认组合是"Redisson 看门狗锁 + 数据库层兜底"：锁负责挡住 99.9% 的并发重复请求（效率），DB 乐观锁 UPDATE stock SET num=num-1 WHERE id=? AND num>0 兜住极端并发（正确性）。RedLock 和 ZK 只在锁失效不可容忍且无法兜底时考虑。

四、Redisson 生产级代码

// 1. 配置（生产建议连接哨兵或 Cluster，锁 key 会被 hash 到某槽）
Config config = new Config();
config.useSentinelServers()
      .addSentinelAddress("redis://s1:26379", "redis://s2:26379")
      .setMasterName("mymaster")
      .setRetryAttempts(3).setRetryInterval(1500);  // 加锁失败重试
RedissonClient client = Redisson.create(config);
RLock lock = client.getLock("lock:stock:1001");  // 锁粒度=单个SKU，不是整张表

// 2. 推荐姿势：只传 waitTime，不传 leaseTime → 激活看门狗自动续期
boolean ok = lock.tryLock(3, TimeUnit.SECONDS);  // 最多等 3s
if (!ok) {
    throw new BizException("操作太频繁，请稍后再试");  // 快速失败优于无限自旋
}
try {
    deductStockWithDBGuard(skuId);   // 3. 核心业务 + DB 乐观锁兜底
} finally {
    if (lock.isHeldByCurrentThread()) {
        lock.unlock();               // 可重入：内层嵌套只计数不减锁
    }
}
-- 4. 数据库兜底：真正的互斥防线，锁失效也不超卖
UPDATE stock SET num = num - 1
WHERE sku_id = 1001 AND num > 0;   -- 影响行数=0 即扣减失败
⚠️ 高频踩坑清单
  • waitTime 设 30s+ 无限等：高峰期线程全部阻塞在加锁上，把服务拖死。等待应短，失败走降级或 MQ 异步化；
  • 锁粒度过粗：锁"整表"使秒杀退化成串行；应锁到业务实体 ID（如单个 SKU）；
  • unlock 前不判断 isHeldByCurrentThread：锁过期后被他人持有，unlock 抛 IllegalMonitorStateException；
  • 忘了 finally：异常路径锁不释放，只能等看门狗停止后续期、30s 超时——期间所有请求被挡；
  • 执行 RLock 方法时传了 leaseTime：看门狗立即失效，退化成固定过期时间，长任务照样裸奔。

五、今日要点

1
原子加锁 + Lua 原子释放
SET key uuid NX PX 一条命令加锁；释放必须 Lua 判断 value 是自己才 DEL，杜绝误删他人锁。
2
看门狗解决过期时间两难
不传 leaseTime 即激活：默认 30s、每 10s 自动续期，进程崩溃无人续期自动过期。注意传了 leaseTime 看门狗就失效。
3
主从异步复制会丢锁
加锁成功但未复制到 slave 时 master 宕机，切换后新 master 无锁数据，两个客户端同时持锁——主从架构的固有缺陷。
4
RedLock 不是银弹
多数派加锁抗单点丢锁，但依赖时钟稳定，防不住 GC 暂停类失效；正确性敏感场景优先 ZK/etcd 或 fencing token。
5
Redis 锁管效率，DB 兜底管正确性
生产标配双保险：Redisson 挡并发 + 数据库乐观锁/唯一约束兜资损，锁失效也不出事故。

六、架构师思考题

Q1看门狗模式下，持有锁的客户端发生 30 秒 Full GC，锁和业务会发生什么？给出防御方案。 ▶

事故推演（时间线）

T0 客户端 A 获得锁（30s TTL），看门狗每 10s 续期；T+2s A 发生 30s Full GC，业务执行和看门狗续期线程全部冻结；T+12s、T+22s 两次续期窗口错过，锁在 T+32s 过期；T+13s 客户端 B 拿到锁并扣减库存成功；T+32s A 从 GC 恢复，它对锁已过期毫不知情（JVM 时间感知不到暂停），继续执行扣减——超卖发生。随后 A 执行 unlock，Lua 校验 value 不匹配（此时是 B 的锁），返回 0 不误删，这是唯一守住的底线。

防御方案（分三层）

  • 存储层兜底（必选）：扣减用 UPDATE ... WHERE num>0 或版本号乐观锁，B 已扣减后 A 的 UPDATE 影响行数为 0，操作失败回滚——无论锁如何失效，数据正确性不破；
  • 恢复后自检：写共享资源前重新 GET lock 校验 value 是否仍是自己（或比对 fencing token），不是则放弃本次操作；
  • 治理层：选低停顿 GC（G1/ZGC）、禁止在持锁临界区内做重 IO/大对象分配、JVM 参数 -XX:+UseZGC 压缩 STW 到毫秒级，从源头缩小风险窗口。

结论：看门狗只保证"活着就续期、死了就过期"，管不了"活着但暂停"——后者只能靠业务侧幂等与 DB 兜底。

Q2为什么 RedLock 必须要求"多数派加锁成功才视为持锁"？它在时钟跳变场景下如何被攻破？ ▶

为什么需要多数派（N+1 / 2N+1）

RedLock 的本质是用多数派一致性对冲单点故障：任何时刻两个客户端不可能各自在超过半数实例上加锁成功——交集至少有一个实例会被先后访问，后者必然 NX 失败。所以单台实例宕机丢锁、异步复制未完成，都只影响少数派，多数派里至少有一个实例"记得"锁已被谁持有，互斥性得以维持。若只要求"全部实例成功"，任意一台网络抖动就加锁失败，可用性崩塌；若只要少数派成功，两个客户端可各占一半实例，锁形同虚设。5 实例容忍 2 台故障，正是 2N+1 的工程平衡点。

时钟跳变攻破路径

客户端 A 在 5 实例中 3 个加锁成功（TTL=10s）。其中实例 R1 的NTP 同步发生向后跳变（或运维手动改时间），R1 本地时钟回退 15s，A 的锁在 R1 上按本地时钟提前判定过期并删除；客户端 B 随后加锁，恰好拿到 R1 + 另外 2 个实例共 3 票——A、B 各自认为持锁。antirez 的回应是 Redis 用单调时钟、NTP 渐进同步可避免大跳变，但这把正确性寄托在运维纪律上，正是 Kleppmann 批判的核心：以时间判断有效性的锁，无法在时钟异常下自证正确。

改进方向

  • fencing token：锁服务每次发放单调递增令牌（如锁 key 的自增版本），存储层（DB/对象存储）拒绝旧令牌写入——即便客户端持旧锁裸奔，写入也会被拒，防御与锁的时间语义解耦；
  • 对时钟强敏感且无兜底层时，直接放弃 RedLock 换 ZooKeeper/etcd（临时节点 + 分布式一致性协议，会话断开自动释放，不依赖客户端时钟）；
  • 多数派运维纪律：独立部署、禁用大步长 NTP 跳变、各实例时钟监控告警纳入 SLA。
