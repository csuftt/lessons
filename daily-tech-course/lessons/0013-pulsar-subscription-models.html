Pulsar 订阅模型深入：四种订阅、游标机制与 Key_Shared 保序

📅 2026-08-28（周五） 🛰 Apache Pulsar 系列 · 第 2 讲 ⏱ 预计阅读 10 分钟 🎯 Subscription / Cursor / Key_Shared / Backlog

一、一次"扩容后状态错乱"的线上事故

某订单履约中心用 Pulsar 消费订单状态流，初期单 consumer 用 Shared 订阅跑得好好的。大促前扩到 6 个 consumer，第二天客服工单爆炸：大量订单出现"已发货 → 待支付"的状态回跳。排查发现：同一订单的两条状态变更被不同 consumer 并发拉取，处理耗时不同导致写入乱序——Shared 订阅根本没有顺序保证。而另一团队更冤：他们把消费组改名上线，结果整个订阅被当成新订阅，10 万条 backlog 里的消息被重新消费了一遍，下游幂等没做全，产生了重复扣款。

两个事故指向同一个知识点：Pulsar 的消费模型里，"订阅（Subscription）"才是身份，游标（Cursor）挂在订阅上，而不是像 Kafka 那样挂在 consumer group 上由客户端提交 offset。理解订阅与游标，是用对 Pulsar 的第一步，也是本讲主题。

二、原理：订阅即游标，一份消息、多份进度

Pulsar 的三层消费结构：Topic → Subscription → Consumer。一个 topic 可以挂多个不同名字的订阅，消息会向每个订阅都投递一份（天然广播）；每个订阅内部又可以多 consumer 负载均衡（天然单播）。广播与单播不用建两个 topic，全靠订阅组合——这与 Kafka 用 group 实现单播、无原生广播（须 Mirror/回放）是本质差异。

游标（cursor）持久化在 broker 侧的元数据存储中，记录该订阅已确认（ack）的消息位点。consumer 断线、换机器、重启进程，游标原地不动；谁连上来就从游标处继续推。三个直接推论：

  • 订阅名 = 消费身份：改名等于新建订阅，按 initialPosition（默认 Latest，即只消费新消息）从头或从尾开始；
  • 持久订阅（persistent topic）：没有 consumer 在线时消息也不丢，全部堆在 backlog 等待，这与 Kafka "没有 group 就没人消费"的模型不同；
  • ack 两种语义：individual（逐条）与 cumulative（累积确认到某条，此前的全部确认）——注意 Shared / Key_Shared 模式只支持 individual，因为消息散落在不同 consumer 手里，没有全局连续位点。

四种订阅模式一张图记牢

  • Exclusive：单 consumer 独占，最简单，顺序保证最强；
  • Failover：主备，partition 粒度主从，顺序 + 高可用，吞吐上限 = 分区数；
  • Shared：轮询分发到任意 consumer，吞吐水平扩展但不保序；
  • Key_Shared：消息按 key 哈希固定路由到某个 consumer，同 key 保序 + 水平扩展——Pulsar 的差异化能力，Kafka 模型做不到。

三、Key_Shared 保序原理与架构权衡

Key_Shared 的实现：broker 把 2^16 个哈希区间（hash range）动态分配给各 consumer。生产端带 key 的消息哈希后落入某个区间 → 落在谁的区间谁消费。consumer 扩缩容时区间再均衡（AUTO_SPLIT 模式），broker 保证切换期间同一 key 的消息不被两个 consumer 同时持有——手段是阻塞其他区间、等慢 consumer 排空。

2^16 hash range 动态分配（3 个 consumer）：
0 – 21,845 → c1
21,846 – 43,690 → c2
43,691 – 65,535 → c3
key="order-9527" hash→38,201 落在 c2 区间 ⇒ 永远由 c2 处理 ⇒ 同 key 严格有序
⚠️ Key_Shared 的经典坑：慢 consumer 拖垮全局 默认 allowOutOfOrderDelivery=false：区间再均衡时 broker 会暂停其他 consumer，等慢 consumer 确认完旧区间才放行——保序严格但吞吐骤降；设为 true 则切换瞬间可能出现短窗口乱序。另有两种权衡：① hash 热点（某 key 写入量独大时该 consumer 独扛）；② consumer 处理能力差异导致区间频繁迁移。吞吐敏感、且业务能用版本号兜底乱序时，开 true 是更稳的选择。

订阅模式选型决策（架构师视角）

  • 全局有序/单分区低吞吐（配置下发、审计）→ Exclusive 或 Failover；
  • 实体级保序 + 高吞吐（订单、账户、设备状态）→ Key_Shared，key 选业务实体 ID（非事件 ID），热点 key 单独拆 topic；
  • 无序可容忍、追求最大吞吐（日志、埋点、通知）→ Shared + 足够 consumer；
  • 容量规划：Failover 的并行度 ≤ partition 数；Key_Shared/Shared 的并行度 ≤ consumer 数，但单 topic 分区数仍决定写入端并行度，两者别混淆。

四、实战：代码与 backlog 治理命令

1. Java 客户端：Key_Shared 消费 + 重试/死信

Consumer<byte[]> consumer = client.newConsumer()
    .topic("persistent://trade/orders/state")
    .subscriptionName("fulfillment-sub")          // 身份！严禁随手改名
    .subscriptionType(SubscriptionType.Key_Shared)
    .subscriptionInitialPosition(SubscriptionInitialPosition.Earliest) // 新订阅从头消费
    .ackTimeout(30, TimeUnit.SECONDS)             // 处理超时未 ack 自动重投
    .negativeAckRedeliveryDelay(1, TimeUnit.SECONDS)
    .deadLetterPolicy(DeadLetterPolicy.builder()
        .maxRedeliverCount(3)                     // 3 次仍失败 → 进死信
        .deadLetterTopic(".../state-dlq")
        .retryLetterTopic(".../state-retry")      // 定时重试队列，延迟重放)
        .build())
    .receiverQueueSize(1000)                     // Shared/Key_Shared 预取窗口
    .subscribe();
// 乱序兜底：写入前用 version/lastUpdated 乐观锁拒绝旧状态，双保险

2. 运维命令：订阅与 backlog 体检

# 查看订阅列表与积压（msgBacklog=未 ack 条数，backlogSize=占用字节）
bin/pulsar-admin topics stats persistent://trade/orders/state
bin/pulsar-admin topics subscriptions persistent://trade/orders/state

# 不动游标窥探积压消息（排查"卡住"问题第一招）
bin/pulsar-admin topics peek-messages --subscription fulfillment-sub \
  --count 5 persistent://trade/orders/state

# 毒消息处置：跳过 N 条（先 peek 确认，再 skip）
bin/pulsar-admin topics skip --count 100 --subscription fulfillment-sub ...

# 故障回放/灾备演练：把游标回拨到指定时间（幂等前提！）
bin/pulsar-admin topics reset-cursor --subscription fulfillment-sub \
  --time 2h persistent://trade/orders/state
✅ backlog 与 retention 是两笔账 backlog = 未 ack 的堆积（受 backlog quota 策略管控，防慢消费撑爆 bookie）；retention = 已 ack 之后的保留（供重放，默认 0 即删）。容量公式：峰值入速 × 目标消费延迟 SLA ≈ backlog 规模，再叠加 retention 估算总存储。给每个订阅设积压告警（如 > 10 分钟未追平），比看磁盘水位更早发现问题。

六、今日要点

1
订阅即身份
游标持久化在 broker，挂在订阅名上。改订阅名 = 新消费身份，会按 initialPosition 重新消费——上线前把订阅名写进变更单。
2
广播与单播同源
一个 topic 多个订阅各自独立游标，天然广播；订阅内多 consumer 负载均衡，天然单播。不必为多消费方复制数据。
3
Key_Shared 保序原理
hash range 动态分配给 consumer，同 key 永远同 consumer；代价是慢 consumer 可能阻塞全局（默认保序优先）。
4
ack 语义有边界
cumulative 只适用于 Exclusive/Failover；Shared/Key_Shared 只能 individual。毒消息用重试/死信 + skip 治理。
5
backlog 与 retention 分账
backlog 管未 ack 堆积（配 quota 与积压告警），retention 管 ack 后保留（供回放）。容量规划两笔分开算。

七、架构师思考题

Q1你的 Key_Shared 消费组出现"一个 consumer 假死，全组吞吐掉 80%"。请分析根因链条，并设计一套不牺牲业务正确性的完整解法。▶

解题方向：根因是"保序优先"的阻塞机制，解法要分层：客户端、broker、业务三管齐下

根因链条：consumer 假死（GC 停顿/下游 RPC 超时但未断连接）→ 它持有的 hash range 上消息无法 ack → broker 触发区间再均衡需要"排空"旧区间 → 默认 allowOutOfOrderDelivery=false 下 broker 暂停其他区间的投递以保证同 key 顺序 → 全组吞吐坍塌。本质是用全局吞吐换单 key 顺序的设计选择被一个慢节点放大。

分层解法：

  • 客户端层：缩短 ackTimeout（如 30s）让假死 consumer 尽快被判定失联、触发重投；调小 receiverQueueSize 避免"取走太多排不掉"；处理逻辑里所有外部调用设硬超时，绝不无限等待；
  • broker 层：吞吐优先的场景开 allowOutOfOrderDelivery=true，接受再均衡瞬间的短窗口乱序；同时监控 CONSUMERS_CONNECTED、各 consumer 的 unackedMessages 分布，发现倾斜立即告警；
  • 业务层（关键兜底）：状态机写入带版本号或时间戳，下游对旧版本消息直接丢弃（乐观锁式幂等）。只要这层做实，broker 层的乱序窗口就不构成正确性风险——"传输层尽量有序 + 应用层容忍乱序"才是生产可用的组合拳；
  • key 治理：复盘是否热点 key 导致某 consumer 独扛大流量（hash 倾斜），必要时对超大 key 单独拆 topic 或在 key 上加盐分片。

结论：Key_Shared 给的是"尽力而为的传输层有序"，架构师必须把它当作性能优化而非正确性边界——正确性永远由业务幂等与版本控制兜底。这个分层思维适用于一切"有序性"诉求。

Q2同一份订单事件流要供 5 个团队消费：风控要秒级、数仓每天批量回放近 7 天、客服只要近 24h、结算 T+1、搜索近实时。如何设计 topic/订阅/保留策略拓扑，并控制存储成本？▶

解题方向：单 topic + 多订阅为骨架，按消费语义选模式，按保留需求分层，而不是复制五份数据

错误方案先排除：给每个团队建一个 topic 再互相转发——五份存储、五条链路、五个故障点，且新增消费方要改管道。Pulsar 的多订阅模型正是为此而生：一份 ledger 存储，N 份独立游标，存储成本只算一份（加副本系数），新增订阅零数据复制。

推荐拓扑：

  • topic 设计：分区数按写入端吞吐定（如 32，2 倍余量）；所有订阅共用 orders-events 一个 topic；
  • 风控/搜索（近实时）：Key_Shared 或 Shared，consumer 常驻，订阅游标贴近尾部，几乎不产生 backlog；
  • 数仓（回放 7 天）：两种选择——持久订阅 dw-sub 常驻但每天只跑到"今天 0 点"然后等次日（游标滞后最多 24h，backlog 常态化存在，需计入容量）；或不开订阅，用 Reader 接口按时间戳直接读 topic（要求 retention ≥ 7 天），游标不占状态、更干净。回放型需求优先 Reader，这是两者边界；
  • 客服（近 24h）：持久订阅 + backlog quota 设 24h 等效上限，超出即告警；若长期不回看，可配 consumer_backlog_eviction 自动丢弃最老堆积，防止慢消费拖垮存储；
  • 结算（T+1）：持久订阅每日全量跑批，跑完 ack 到尾；游标滞后约 24h，与数仓同理计容量。

保留策略与成本账：retention 取所有消费方上限（本例 ≥ 7 天，由数仓决定）；存储 ≈ 日写入量 × 7 × 副本数 + Σ各订阅 backlog 均值。两个省钱开关：数仓回放完的数据在下游落地后，可把 retention 降到"最大故障重放窗口"（如 3 天）；客服订阅开 eviction 后其 backlog 不再计入。监控上给每个订阅定义独立 SLO（风控 lag < 5s、数仓 < 25h），告警按订阅而非按 topic 下发，责任边界才清晰。

结论：这套设计的本质是"存储一份、消费多元、策略下沉到订阅"。架构师评审此类需求时，先问"每个消费方的保留窗口与滞后容忍"，这两个数字直接决定 retention、backlog quota 和容量，比讨论 topic 数量重要得多。
