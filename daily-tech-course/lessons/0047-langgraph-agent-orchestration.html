AI · AI 大模型应用系列第 4 讲（Agent 编排篇）

Agent 编排：把大模型应用从 if-else 泥潭捞出来

物联网主线的两讲告一段落，今天回到 AI 线，聊一个工程味最重的题目：Agent 编排。0027 期我们把单个工具调用循环讲透了——模型表态、代码动手；但业务的真实流程从来不是一个循环：要分支、要循环重试、要等人审批、半夜发版还不能把跑到一半的会话打死。编排层的本质，是把"流程控制权"从提示词里拿回代码。这一讲从一次"半夜发版打死长任务"的连环事故讲起：图执行模型（状态、节点、条件边）怎么替代 if-else 嵌套，检查点（checkpoint）怎么让 Agent 像工作流引擎一样"断点续跑"，以及最贵的那条铁律——恢复即重放，副作用节点必须幂等。

01一次"半夜发版打死长任务"的连环事故

团队做一个供应商对账 Agent：读邮件里的对账单 → OCR 抽取 → 与 ERP 台账比对 → 差异超过阈值走人工复核 → 通过后自动生成凭证写入财务系统。初版用最顺手的写法：一个 Python 主循环，按步骤调模型、调工具，会话历史塞 Redis，流程控制全靠提示词里那句"请判断下一步做什么"。

上线一个月，三件事连环爆：

第一件：半夜发版，长任务团灭。对账任务一跑就是 20~40 分钟（大量 OCR 与台账查询）。发版重启进程，跑到第 7 步的任务全部蒸发——会话历史在 Redis 里，但"流程走到哪一步、下一步该进哪个分支"这个执行位置没人存。只能整单重跑：OCR 重付费、模型重推理，一晚上白烧的 token 账单肉眼可见。

第二件：提示词流程控制漂移。十个步骤的顺序写在提示词里，模型大多数时候照办，但每月总有几十单"创造性走位"：跳过台账比对直接生成凭证、人工复核没等结果就往下跑。每修一次提示词，回归测试全靠人肉点一遍——流程逻辑活在自然语言里，就永远没有确定性。

第三件：重复写入财务系统。一次任务在"生成凭证"节点超时重试，外部接口实际已受理，重试又提交了一笔——同一个供应商同一张对账单，两张凭证。财务的月结对出来的那一刻，这个问题才被发现。

复盘结论：三件事都不是模型问题，是编排层缺位。你需要的其实是工作流引擎的老能力——确定性的流转、持久化的执行位置、失败后的断点恢复——只不过这个工作流里的某些"步骤"由大模型来决策。这就是 Agent 编排框架要解的问题，也是 LangGraph 这类图运行时的定位。

02原理：图、超步与检查点

心智模型：节点是代码，边是确定性，只有少数节点里坐着模型

LangGraph 的执行模型三件套：状态（State）是一个共享数据结构（TypedDict 或 Pydantic 模型），带着 reducer 规则定义"多个节点写同一个键时怎么合并"；节点（Node）是普通函数，读状态、返回状态更新——可以是 LLM 调用、工具执行，也可以是纯确定性代码（校验、路由、落库）；边（Edge）是流转规则，条件边（conditional edge）就是一个普通函数，读状态返回下一跳——分支逻辑是代码函数，不是提示词。图允许循环（重试、反思、重规划都天然表达），执行采用 Pregel 风格的超步（super-step）模型：每个超步内所有可运行节点并行执行，跑完统一合并状态、写一次检查点，再进下一个超步。这与 0043 期讲的 Kubernetes 控制循环"观测-对比-调谐"是同一种工程审美：期望与实际都在一个可检查的数据结构里，每轮推进可观测、可重放。

检查点：把"执行位置"变成持久化数据

编译图时挂一个 checkpointer，每个超步边界自动把完整状态快照写进存储，按 thread_id 组织成链（同一个 thread 的历史快照像 git log，可以回看、可以 fork）。持久化三档可调：sync（下一步开始前落盘，最安全）、async（默认，边跑下一步边落盘）、exit（只在结束/中断时落一次，最快但中间进度不保）。生产已知的一笔账：一张 40KB 的文档上下文被每个超步全量序列化，2000 次运行后 checkpoints 两张表涨过 1.2GB，且没有内建 TTL/保留策略——上线前就要把清理任务（按 thread 年龄 DELETE + VACUUM）排进计划。大对象别进 State，放对象存储、快照里存引用。

能力机制没有它会怎样（01 节事故对照）
断点续跑同 thread_id 恢复，从最后成功超步继续；同超步内已成功节点的写入以 pending writes 保存，恢复时不重跑发版重启 = 任务团灭，整单重跑重付费（第一件事故）
确定性流转条件边是代码函数；流程结构显式写在图里流程活在提示词里，模型"创造性走位"，改提示词靠人肉回归（第二件事故）
人机协同节点内 interrupt() 暂停 → 状态已持久化 → 进程可退出；审批后同 thread 恢复继续人审结果与流程状态两张皮，等待期间占着进程
时间旅行get_state_history 拉任意历史快照，可改状态 fork 重推"第 6 步为什么走错分支"只能靠翻日志脑补
循环预算recursion_limit 封顶超步数（默认很高，务必显式设小）两个节点互相踢皮球，token 烧到天亮

最重要的那条语义，值得单独一行：LangGraph 的检查点落在超步边界，不在节点内部的任意一行代码上。恢复 = 从节点开头整段重放——包括节点里的 LLM 调用、API 请求、interrupt 本身。有团队在生产中实锤过：进程在扣款工具调用完成后、检查点写入前被杀，恢复后节点从头重放，同一笔扣款打了两次（外部账单里两行 created_at 相差 89 秒的同 ID 扣款记录）。这就是 01 节第三件事故的机制版，解法见下一节。

03架构视角：选型、副作用治理与容量

选型判断：什么时候根本不该上编排框架

先说反例：一次提示词 + 一两次工具调用的线性链，二十行循环代码比任何框架都好读——为了"显得 Agentic"给线性流程套图，是白白交复杂度税。上图运行时的信号有三个：要循环/反思/重规划（图天然表达环）、要长时间挂起等人或等事件（interrupt + 持久化状态让"暂停"零成本）、要崩溃后从断点恢复（for 循环进程一死全丢）。三个信号一个都没有，就别上。Java 团队还有一层考虑：LangGraph 主体是 Python 生态，JVM 上的对应物是 Spring AI Alibaba Graph / LangChain4j（后者无原生 checkpointer，有状态编排能力弱一档）——编排层选型本质上是给团队选运行时，语言边界、运维栈、可观测体系都要一起算，别只比功能表。

副作用治理：幂等是恢复的入场费

把"恢复即重放"当公理，节点分两类治理：纯函数节点（读状态、算结果、无外部副作用）随便重放，零成本；副作用节点（写库、扣款、发邮件、生成凭证）必须幂等。工程上三选一或组合：

  • 确定性幂等键：从稳定状态派生键（如 thread_id + 节点名 + 超步号，或业务键如"对账单 ID + 凭证类型"），调用外部 API 时随请求携带——支付网关类接口原生支持幂等键，重复提交返回首次结果；
  • 意图记录 + 对账：调用前先在事务库里写"意图记录"，调用后回写结果；恢复时先查意图表，已完成的直接跳过——适合不支持幂等键的老旧内部接口；
  • 结构隔离：把副作用挪到 interrupt 之后的独立节点——先中断展示"我将执行 X"，人确认后恢复，副作用节点执行前状态已落检查点，这一跳不会因恢复重放。

另有两条配套纪律：副作用节点别读墙钟做分支（重放时世界已变，now() 会走出不同路径——要判断"睡了七天世界变了没"，用醒来后先查外部事实再决定）；同 thread 并发要自己串行化（webhook 重试和用户点击同时恢复同一个 thread，框架不替你加锁，出双写别怪引擎）。

版本与容量账

版本坐标（2026-10）：LangGraph 与 LangChain 于 2025-10-22 同步发 1.0（LangChain 1.0 的 create_agent 就构建在 LangGraph 上，老的 AgentExecutor 已弃用、维护到 2026 年 12 月）；当前线 langgraph 1.2.12（2026-09-21）。生态数据：与 LangChain 合计月下载约 9000 万，Uber、摩根大通、BlackRock、思科在生产使用。容量与成本账别漏四笔：① 检查点存储账——每超步全量序列化 State，长对话 × 大上下文 = 表膨胀主力，规划清理任务与大对象外置；② 延迟账——大 State 的检查点写延迟在本地 Postgres 16 上慢尾（P95+）能到 110~180ms/步，扇出并行分支的图这笔开销是乘法；③ token 账——恢复不重跑成功节点省的是大头，但重放失败节点照样重付该节点的模型调用费；④ 人审挂起账——interrupt 挂起的 thread 不占进程但占存储，要配超时降级（超时自动 resume 一个"默认驳回"值，别无限期挂着）。

04实战：一个敢上生产的对账 Agent 骨架

片段一：图定义 + 检查点 + 幂等键（Python，节选）

from langgraph.graph import StateGraph, START, END
from langgraph.checkpoint.postgres import PostgresSaver
from typing_extensions import TypedDict, Annotated
import operator

class ReconState(TypedDict):
    statement_id: str
    ocr_text: str
    diff: float
    voucher_id: str | None      # 幂等锚点：已写入则跳过

def ocr_extract(s: ReconState):            # 纯副作用，可重放
    return {"ocr_text": call_ocr(s["statement_id"])}

def llm_compare(s: ReconState):            # 模型节点：差异归因
    return {"diff": model_classify(s["ocr_text"])}

def route(s: ReconState):                  # 条件边：代码管流转
    return "human_review" if s["diff"] > 500 else "post_voucher"

def post_voucher(s: ReconState):           # 副作用节点：幂等键护体
    if s["voucher_id"]:                    # 重放保护
        return {}
    vid = create_voucher(s["statement_id"],
        idem_key=f"{s['statement_id']}:voucher")
    return {"voucher_id": vid}

g = StateGraph(ReconState)
g.add_node("ocr_extract", ocr_extract)
g.add_node("llm_compare", llm_compare, retry=retry_policy())
g.add_node("human_review", human_review)   # 内部 interrupt()
g.add_node("post_voucher", post_voucher)
g.add_edge(START, "ocr_extract")
g.add_edge("ocr_extract", "llm_compare")
g.add_conditional_edges("llm_compare", route)
g.add_edge("human_review", "post_voucher")
g.add_edge("post_voucher", END)

with PostgresSaver.from_conn_string(DB_URI) as cp:
    cp.setup()                              # 首次建表
    app = g.compile(checkpointer=cp)

三个细节值回票价：voucher_id 进 State 本身就是幂等锚点（重放时先查再写）；retry=retry_policy() 只管瞬态失败（超时/限流），业务错误走条件边进异常分支，别混；条件边 route 是纯代码——阈值 500 这个业务规则写在代码里、进 git、有 code review，而不是写在提示词里靠模型自觉。

五个必踩的坑：① 拿 InMemorySaver 上生产——重启全丢，"为什么发版后对话全没了"十有八九是它；② 副作用节点不设幂等——恢复即重放是语义不是 bug，重复扣款/重复凭证早晚对上你；③ recursion_limit 用默认值——两个节点互相路由成环，一夜 token 烧穿，显式设个几十；④ interrupt() 包进 try/except——它靠抛特殊异常实现暂停，裸 except 会把"暂停"吞掉；⑤ 检查点表不管不顾——没有内建 TTL，大 State 全量序列化，不清理就是慢性存储事故。

05今日要点

  • 编排层把流程控制权拿回代码：状态+节点+条件边三件套，分支是函数不是提示词；图允许循环，超步边界统一合并状态、落检查点。
  • 检查点 = 可持久化的执行位置：同 thread_id 恢复断点续跑，成功节点不重付 token；挂起等人、时间旅行审计都是它的副产品。
  • 恢复即重放，幂等是入场费：检查点落在超步边界，节点内副作用整段重放——幂等键/意图记录/结构隔离三选一，别赌运气。
  • 三个信号再上框架：要循环、要挂起、要恢复，一个都没有就写二十行循环；Java 主栈评估 Spring AI Alibaba Graph，选型选的是运行时不是功能表。
  • 两笔隐形账：检查点存储无内建 TTL（上线前配清理）；thread_id 是安全边界也是并发边界——服务端派生 + 同 thread 串行化。

06架构师思考题

题目一：你们的退款 Agent 用 LangGraph 构建，节点结构是"校验 → interrupt 人审 → 执行退款 → 通知"。上线后财务投诉：某笔退款执行了两次。给出完整的机制解释与三层修复方案，并说明为什么"把退款挪进人审节点之后"只能算部分修复。▶ 点击展开解析

🔍 逐层拆解

机制解释：检查点落在超步边界。人审通过后恢复执行，退款节点开始运行——外部支付接口受理了请求，但进程恰好在"接口返回成功"与"节点返回状态更新、检查点落盘"之间被杀（发布重启/OOM/节点驱逐）。恢复时运行时从最后检查点重放，退款节点从函数第一行整段重跑，接口再次被调用——两次真实扣款。这不是框架 bug，是"检查点粒度在超步、不在代码行"的既定语义：节点内部的执行进度对运行时不可见。三层修复：① 接口层幂等键——退款请求携带确定性幂等键（退款单号，或 thread_id+节点+超步号派生），支付网关识别重复请求返回首次结果，这是根治层，前提是外部接口支持；② 意图记录层——节点执行前先在事务库写"退款意图"（含幂等键，与业务库同事务），执行后回写结果；重放时先查意图表，已完成的把结果直接填回状态跳过调用——接口不支持幂等键时的等价物，代价是多一次库写与对账逻辑；③ 状态锚点层——把"退款单号"作为字段写进 State，节点开头检查该字段非空即返回（本文片段一的 voucher_id 模式）——最轻量，但保护窗口比②小：进程死在"接口已受理、状态未回写"之间时锚点还没写入，依然会重放，需要②的意图记录把窗口堵死。为什么"挪到人审之后"只是部分修复：interrupt 之后、副作用之前确实有一个已落盘的检查点，它消除的是"人审等待期间进程重启导致副作用提前/重复触发"这一类问题；但副作用节点自身执行中途被杀的窗口依然存在（上面的机制解释原样成立）。它改善的是概率与场景，不是语义。真正的顺序纪律应该是：副作用独占一个节点、幂等三件套护体、节点内先查锚点再动手——顺序隔离 + 幂等双保险，缺一不可。

🔍 选型推理与架构

选型：图编排留在 JVM——Spring AI Alibaba Graph（OverAllState/条件边/持久化编排与 LangGraph 概念一一对应，复用 Spring 生态的事务、安全、注册配置中心与现成可观测体系）；算法侧快速迭代的新能力（新模型适配、复杂抽取）由两位 Python 工程师做成独立微服务，被图当作工具节点通过 OpenFeign 调用——语言边界即团队边界，别让 Java 团队维护 Python 编排运行时，也别逼算法工程师用 Java 写图。部署架构：编排服务作为普通 Spring Boot 应用进 K8s（副本 ×2+，走公司标准发布流程）；持久化状态用现有 MySQL 加表（工单 thread 表 + 检查点表，DBA 体系内备份审计）——Postgres 若公司没有运维体系就别为一项功能引入新数据库；发版流程按 0043 期发布纪律：preStop 等在途超步跑完（一个超步秒级），副本逐个滚动，在途工单靠持久化检查点在新副本上恢复——"发版不打断"由"检查点在数据库、进程可随意牺牲"保证，与 0046 期"连接无状态化"同构：状态外置，节点可牺牲。三类复盘数据来源：① 路由正确性——条件边的分支决策在节点日志里结构化落库（工单号、走哪条边、状态快照哈希），月度抽样比对人工判断；② 模型节点质量——每个模型节点的输入输出对（脱敏后）进对象存储，接评测集跑准确率/幻觉率趋势（为将来 AI 线的 RAGAS/评测期铺数据地基）；③ 工程健康度——检查点表大小、重放次数（幂等键命中数 = 重放发生次数，这是"恢复即重放"语义的直接观测指标）、人审挂起时长分布、超时降级触发数——全部从现有 Prometheus/Grafana 加埋点出面板。复盘会的产出应该是：哪些分支阈值要调（改代码走发布）、哪些模型节点提示词要升级（进评测回归，不直接上生产）——把"提示词变更"也纳入变更管理，是 01 节第二件事故的终极答案。
