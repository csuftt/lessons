KUBERNETES · Kubernetes 系列第 4 讲（配置管理篇）

Kubernetes 配置管理：ConfigMap 与 Secret 的分发与生效

上一讲把 Pod、Deployment 与 Service 背后的控制循环拆开看了，这期继续 Kubernetes 主线，讲镜像之外容器跑起来的另一半输入：配置。镜像管"程序是什么"，配置管"它在哪个环境、连哪个库、开哪些开关"——配置的交付链路断了或错了，控制平面一脸健康，业务早已悄悄变形。这一讲从一次"中午改开关、半夜才生效一半"的复盘讲起：ConfigMap 与 Secret 根本不是"配置文件"，而是挂在 API Server 上的两份资源对象，它们怎么进 Pod（env / 卷挂载 / subPath 三条通道，收敛语义完全不同）、改了之后怎么生效（滚动重建 vs 约一分钟自动同步 vs 永不更新）、Secret 的"保密"边界到底在哪（base64 不是加密，etcd 静态加密 + 外部密钥库才是正解），最后给一套"配置变更 = 版本化发布"的治理答案。

01一次"改开关"事故：改了 5 分钟，"生效"用了 6 小时

某电商做大促压测，中午 12 点 SRE 在群里喊了一声"降级开关已打开"，把 feature-flags ConfigMap 里的 order.export.enabled 从 true 改成 false。下午压测数据"看起来正常"，晚上复盘时对日志才发现三个事实：

第一，约 40% 的 Pod 当场就没读到新值。这个开关是用 envFrom 注入的环境变量——环境变量在容器启动时写进进程内存，之后 ConfigMap 改一百次，运行中的容器都无感。"中午已生效"只是改对象的人的一厢情愿。

第二，挂载文件方式的那部分 Pod，"生效"分了两批。降级开关的另一部分服务用卷挂载读 /etc/config/flags.properties，kubelet 的同步周期让文件在 1 分钟左右更新了，但这些 Java 服务只在启动时读一次配置文件——K8s 只负责把文件换新，不负责通知应用重读。到晚上自然滚动发布时才真正用上新值，前后差了 6 个小时。

第三，有一个 Pod 永远不会更新。排查发现它用了 subPath 挂单个文件——subPath 挂载是 ConfigMap 更新的盲区，文件在 Pod 生命周期内冻结，没有任何告警。三种引用方式、三种收敛语义，同一行"开关已打开"的群里消息，在集群里兑现成了三种现实。这还不算最贵的：真正贵的教训是配置变更没有走变更管理——kubectl 直接改生产对象，改了什么、谁批准的、哪些工作负载受影响，全都没有记录。

02原理：配置是资源对象，进 Pod 有三条通道

ConfigMap / Secret 是什么：API 对象，不是配置文件

ConfigMap 与 Secret 都是 API Server 管理的资源对象：data 是键值对（ConfigMap 值必须是字符串，数字布尔都要加引号），存在 etcd 里、走 RBAC 鉴权、能被 watch。两者身份差异在语义不在机制：ConfigMap 明文、Secret 的值 base64 编码——base64 是编码不是加密，`kubectl get secret -o jsonpath` 加一行管道就能解出明文，它的价值在于"身份隔离"：Secret 有独立的 RBAC 动词空间（可以把 get/list secret 单独收紧）、审计里能单独追踪、不会被 describe 时顺手打印进工单。两者共同一条硬约束：单个对象不超过 1MiB（etcd 请求大小上限，含元数据与 base64 膨胀后的内容，Secret 实际明文容量约 770KB）。拿 ConfigMap 塞证书链、词库文件，先是 apply 被拒，硬拆成十份对象则是下一场治理灾难。

三条通道与三种收敛语义

为什么改了 ConfigMap 不会自动滚动更新

0043 讲过：Deployment 控制器比对的是 pod 模板，模板里引用 ConfigMap 写的是名字不是内容——对象内容变了，模板一个字节没变，控制循环自然无动于衷。这不是缺陷，是把"内容更新策略"交给使用者的设计：重启型应用该滚动重建，watch 型应用该热加载，K8s 不替你猜。于是收敛通道有三条官方姿势：kubectl rollout restart（上一讲实战三演示过：给模板打 restartedAt 时间戳注解，复用滚动更新机制，遵守 maxSurge/maxUnavailable 全程无损）；CI 流水线里重新 apply Deployment（对 GitOps 天然友好）；或者用 Stakater Reloader 这类控制器自动做这件事——它 watch ConfigMap/Secret，内容 hash 变了就给带注解的 Deployment 更新一个专用注解触发滚动，GitOps 场景建议用它的 annotations 策略而不是默认 env-vars 策略，避免 ArgoCD 把"多出来的环境变量"当成漂移又同步回去。

Secret 的保密边界：base64 之下的三层防线

Secret 的默认形态近乎裸奔：API Server 默认把 Secret 明文写进 etcd，etcd 备份文件流出一个，全集群凭证泄一个。第一层防线是静态加密（EncryptionConfiguration）：在 API Server 配置里给 secrets 挂加密 provider，生产正解是 KMS v2 provider（1.29 GA）——信封加密，数据密钥 DEK 在本地加解密、主密钥 KEK 托管在外部 KMS/HSM，KEK 建议至少 90 天轮换，密钥轮换不用重启 API Server；aescbc 这类静态密钥 provider 只适合过渡，密钥文件躺在控制面节点磁盘上，安全性等于那台机器的文件系统。开启加密后存量 Secret 不会被自动重写，要跑一遍 kubectl get secrets -A -o json | kubectl replace -f - 强制全部过一遍新 provider。第二层是 RBAC：namespace 级别收紧 get/list secret，把"能读 Secret"视为"等于知道凭证本身"来设计权限。第三层是轮换与来源治理：密钥的真源头不放集群里，用 External Secrets Operator 从 Vault/云密钥库同步成 K8s Secret（Git 里只有指针没有凭证，轮换在密钥库侧完成自动同步进来）；GitOps 必须把密钥进仓库的，用 Sealed Secrets——集群侧控制器持私钥，仓库里只有公钥加密的密文。

03架构视角：配置分层、不可变与版本化发布

配置分层：按"变不变"与"敏不敏感"拆通道

配置类型例子通道选择生效语义
启动参数型（基本不变）JVM 参数、监听端口、日志级别底座环境变量 envFrom改了必须滚动重建，行为最确定
运行可调型（偶尔变）降级开关、限流阈值、功能开关卷挂载 + 应用 watch/信号重载约 1 分钟到容器，重载语义看应用
高频动态型（分钟级变）价格策略、灰度白名单、推荐权重不进 ConfigMap：配置中心（Nacos/Apollo）或 KV推送秒级，治理靠配置中心
敏感凭证DB 密码、API Key、TLS 私钥Secret + ESO/Sealed Secrets + 静态加密轮换即发布，见 04 实战

分层的判断标准是变更频率与生效要求：变更频率高于"分钟级滚动重建"能承受的（高频开关、白名单），ConfigMap 本身就不是正确工具——它是"随工作负载版本走的低频配置"，把它当高频开关仓库用，等于每天给控制平面加几百次无审计的对象写。高频动态配置回配置中心，这在 第 2 期 Nacos 讲过，两条路线互补不互斥。

immutable：一个字段买两样东西

immutable: true（ConfigMap/Secret 均支持，v1.21 GA）声明对象创建后不可修改，更新只能"建新删旧"。它同时买到两样东西：安全——kubectl edit 手滑改生产配置这条路被物理封死，配置变更被迫走"新建版本对象 + 改 Deployment 引用"，天然携带版本名（app-config-v2）与回滚路径；性能——kubelet 对 immutable 对象关闭 watch，大集群（数万 ConfigMap 挂载）能显著降 API Server 负载。配套姿势是内容寻址命名：Helm 的 checksum/config 注解、Kustomize 的 configMapGenerator hash 后缀，都是"内容一变名字就变、名字一变模板就变、模板一变滚动更新自动触发"——把"改配置"升格成"发版本"，这正是 01 节事故缺的那块治理。

安全分层：密钥的三条路线怎么选

路线形态适合代价
原生 Secret + KMS v2 静态加密Secret 对象 + etcd 密文多数团队的基线要管 EncryptionConfiguration 与密钥轮换
External Secrets OperatorGit 存 ExternalSecret 指针，ESO 同步成 Secret有 Vault/云密钥库的组织，轮换自动化多一个 Operator 与 Store 配置
Sealed Secrets / Secrets Store CSI公钥密文进 Git / 卷直挂不落地 Secret 对象纯 GitOps 仓库 / 高敏场景密文与集群绑定；CSI 绕开 K8s Secret 生态

选型的主轴是密钥真源头在哪：源头在云密钥库/Vault 就上 ESO（Git 里永远没有明文，轮换不碰集群）；源头必须在 Git 的纯 GitOps 团队用 Sealed Secrets（密文只能在目标集群解密，仓库泄露不直接泄密钥）；安全等级再高一档、连 Secret 对象都不想让它存在于集群的，CSI 直挂卷。三条路线不互斥，按数据分级混用是常态。

04实战：一套"敢上生产"的配置交付

片段一：ConfigMap + Deployment（不可变版本化 + 双通道注入）

apiVersion: v1
kind: ConfigMap
metadata:
  name: order-api-config-v7          # 版本号进名字：更新=新建 v8
immutable: true
data:
  LOG_LEVEL: "INFO"                  # 值永远是字符串，YAML 裸写 true/3 会被隐式转换坑
  feature-flags.properties: |
    order.export.enabled=false
    order.recommend.level=2

---
apiVersion: apps/v1
kind: Deployment
metadata:
  name: order-api
  annotations:
    reloader.stakater.com/auto: "true"   # Reloader 自动兜底：对象变了滚动重建
spec:
  replicas: 4
  selector:
    matchLabels: { app: order-api }
  template:
    metadata:
      labels: { app: order-api }
    spec:
      containers:
      - name: app
        image: registry.example.com/order-api:v1.4.2
        envFrom:
        - configMapRef:
            name: order-api-config-v7   # 环境变量通道：启动参数型
        volumeMounts:
        - name: flags
          mountPath: /etc/config         # 卷挂载通道：运行可调型（应用 watch 重载）
      volumes:
      - name: flags
        configMap:
          name: order-api-config-v7

这套清单的语义边界很清楚：LOG_LEVEL 这类启动参数走环境变量，改了就要滚动重建（Reloader 或 CI 重新 apply 都会触发，行为确定）；feature-flags.properties 走卷挂载，应用 watch 这个文件做热重载，1 分钟内拿到新开关。**同一个对象、两条通道、两种生效语义，按配置项的性质各走各的门**——这是 01 节事故的正解形态。

片段二：Secret 的最小安全姿势

# 1) 建议用 stringData 明文写、API Server 自动编码（避免手工 base64 出错）：
apiVersion: v1
kind: Secret
metadata:
  name: order-db-cred
type: Opaque
stringData:
  username: order_app
  password: "S3cure!2026"

# 2) 静态加密（控制面配置，KMS v2 provider）：
# apiVersion: apiserver.config.k8s.io/v1
# kind: EncryptionConfiguration
# resources:
# - resources: [secrets]
#   providers:
#   - kms:
#       apiVersion: v2
#       name: corp-kms
#       endpoint: unix:///var/run/kms-plugin/socket.sock
#   - identity: {}          # 兜底读旧明文数据，迁移完成后移除
# 开启后强制重写存量：
kubectl get secrets -A -o json | kubectl replace -f -
kubectl get secrets -A -o jsonpath='{range .items[*]}{.metadata.name}{"\n"}{end}' | wc -l
# 验证：etcdctl get /registry/secrets/default/order-db-cred --print-value-only | head -c 100
# 输出 k8s:enc:kms:v2: 前缀即已加密（裸 base64 = 还在明文）

片段三：ESO 从密钥库同步（Git 里只有指针）

apiVersion: external-secrets.io/v1
kind: ExternalSecret
metadata:
  name: order-db-cred-sync
spec:
  refreshInterval: 1h              # 密钥库侧轮换后 1h 内自动同步
  secretStoreRef:
    name: corp-vault               # SecretStore 指向 Vault/云密钥库
    kind: SecretStore
  target:
    name: order-db-cred            # 在集群里物化成这个 Secret
  data:
  - secretKey: password            # K8s Secret 里的键
    remoteRef:
      key: prod/order/db           # 密钥库里的路径
      property: password

Git 仓库里提交的只有上面这段指针，凭证本体在密钥库；轮换在密钥库完成，refreshInterval 到点自动同步，集群侧不用碰。密钥审计、审批、吊销全部收敛到密钥库一套流程——把"配置分发"和"密钥治理"拆成两个域，各用各的专业工具。

五个必踩的坑：① envFrom 改完就以为生效了——环境变量通道改对象永远不影响运行中容器，生效动作（rollout restart / 重新 apply / Reloader）必须成为变更流程的一部分。② subPath 挂载等热更新——subPath 是更新盲区，要么整目录挂载 + 应用只读自己的文件，要么接受"必须重建"并写进发布手册。③ 把高频开关塞进 ConfigMap——ConfigMap 是低频版本化配置的分发通道，分钟级变更的开关/白名单去配置中心，别把 etcd 当配置推送总线。④ Secret 当 ConfigMap 用——"不敏感"的凭证也走 Secret：RBAC 收紧、审计独立、describe 不泄值，三样都是 ConfigMap 给不了的。⑤ 大文件硬塞 1MiB——超限被拒后拆成十份对象是治理灾难；证书链、词库、大 JSON 走对象存储 + initContainer 拉取，ConfigMap 只放"改了要跟着发布走"的那点配置。

✅ 配置管理体检清单

☐ 生产 ConfigMap/Secret 是否 immutable + 版本化命名（更新 = 新建版本 + 改引用）　☐ 每个工作负载的配置通道（env / 卷 / subPath）有登记，生效语义团队人人知道　☐ 卷挂载热更新路径的应用侧重载（watch / 信号）真的实现并演练过　☐ Secret 全集群开启静态加密（KMS v2），etcd 抽查密文前缀验证过　☐ 密钥源头在 Vault/云密钥库，Git 仓库扫描不到明文凭证　☐ get/list secret 的 RBAC 按 namespace 收紧，能读 = 能知道，按此设计　☐ 配置变更走 GitOps PR：谁改的、改了什么、影响哪些工作负载可追溯　☐ Reloader/CI 重新 apply 的自动生效通道与 GitOps 同步策略兼容（annotations 策略）　☐ 大于 1MiB 的"配置"有单独交付方案（对象存储 + initContainer），不在 ConfigMap 硬拆　☐ 密钥轮换演练做过一次：轮换 → 同步 → 应用拿到新值 → 旧值失效

05今日要点

  • 配置是资源对象，不是文件：ConfigMap/Secret 存 etcd、走 RBAC、1MiB 上限；Secret 的 base64 是编码不是加密，它的价值是身份隔离，保密要靠静态加密与外部密钥库。
  • 三条通道三种收敛语义：环境变量启动即冻结（改了必须滚动重建）；整目录卷挂载约 1 分钟同步但应用要自己重读；subPath 是更新盲区。选通道前先回答"这个配置项变了，我希望它怎么生效"。
  • 改对象不触发滚动更新是设计不是缺陷：Deployment 模板只记名字不记内容，内容更新策略交给你——rollout restart、重新 apply、Reloader、checksum/hash 版本化命名，把"改配置"升格成"发版本"。
  • immutable 一字段两收益：物理封死手滑改生产，kubelet 关 watch 降 API Server 负载；配套版本化命名（v7→v8）让每次配置变更自带回滚路径。
  • 密钥治理分两域：分发归 K8s（Secret + 静态加密 KMS v2），真源头与轮换归密钥库（ESO 同步 / Sealed Secrets 进 Git）；高频动态配置回配置中心，ConfigMap 只做"随版本走的低频配置"。

06架构师思考题

题目一：支付服务 6 副本，DB 密码轮换演练：运维在 Vault 改了密码，ESO 一小时内同步出新 Secret，但应用连的还是旧密码——数据库侧旧密码 30 分钟后失效。① 画出新密码从 Vault 到 Pod 内生效的完整链路，指出链路上的所有延迟源。② 为什么 ESO 同步完成 ≠ 应用生效？这中间缺了哪一环？③ 设计一套"轮换无感"的方案，让 6 个副本在不中断的情况下全部换到新密码。▶ 点击展开解析

🔍 逐问拆解

① 链路与延迟源：Vault 改密码（T0）→ ESO 的 refreshInterval 到期才会去拉（最长 1h，可调小到 1m，这是第一个延迟源）→ ESO 更新 K8s Secret 对象（秒级）→ 到这里为止只是"对象新了"。往下还有：环境变量通道的 Pod 要等滚动重建才注入新值（Reloader 检测到变化 → 更新注解 → 滚动更新，maxSurge/maxUnavailable 控制节奏，6 副本分钟级）；卷挂载通道要等 kubelet 同步（约 1 分钟）+ 应用重读或重建。② ESO 同步完成只是把"新值放进了分发通道"，消费端拿到新值还需要触发动作——这正是本讲的核心：对象更新与工作负载生效之间隔着"通道收敛语义"这一环。缺的这一环有三个补法：Reloader 自动滚动（重启型）、应用 watch 文件热重载（连接池型）、CI/GitOps 重新 apply。③ 轮换无感方案的关键是新旧密码重叠窗口：第一步数据库侧先"加"新用户/新密码而不是"改"旧密码（双账号或双密码并存，重叠窗口 = 滚动完成的实际时长 + 缓冲）；第二步 ESO 同步 + Reloader 触发滚动，逐副本用新密码重启连接池，旧密码在重叠窗口内始终可用，任何时刻都有足量副本在服务；第三步全部副本确认使用新连接（连接池建立时间戳/认证日志核对）后再废除旧密码。如果应用支持不重启换连接池（配置热更新 + 重建数据源），可以把滚动重建换成轻量的热重载，窗口更短。这个模式叫 credential rotation with overlap，凡是有"凭证 + 多副本"的地方（TLS 证书、API Key、签名密钥）全部适用——反过来，没有重叠窗口的单点切换，任何一次抖动都会变成认证失败事故。

题目二：团队 40 个微服务共用一个 900KB 的 shared-config ConfigMap（大 JSON 配置），任何团队改自己的字段都 kubectl edit 这个对象。① 这套做法里数一数有多少个架构问题。② 迁移方案怎么设计：对象怎么拆、900KB 的 JSON 怎么处理、40 个团队的变更流程怎么改？③ 有人提议"干脆全搬到 Nacos"——什么该搬，什么不该搬？▶ 点击展开解析

🔍 逐问拆解

① 至少六个问题：其一，爆炸半径——900KB 逼近 1MiB 上限，任何一个团队塞大值都可能 apply 被拒、全员变更中断；其二，变更耦合——kubectl edit 是全量替换，两个团队同时编辑后者覆盖前者（last-write-wins），没有任何冲突检测；其三，无审计无审批——绕过 GitOps 直接改生产对象，改了什么、影响谁全靠猜；其四，消费端混乱——40 个服务全量挂载，任何一次变更的"生效语义"取决于每个服务用哪条通道（env 冻结/卷同步/subPath 盲区），等于 40 种可能的收敛结果；其五，性能税——每个节点的 kubelet 都要 watch 这个大对象，每次变更全集群重新分发 900KB；其六，职责不清——共享对象没有 owner，谁也不敢删、谁都能改。② 迁移方案：第一步按服务边界拆对象（每服务一个 ConfigMap，只放自己的键，共享的少数真公共配置单独一个只读小对象 + 明确 owner）；第二步 900KB 的大 JSON 拆两层——真正"随发布走"的小配置进各自 ConfigMap（通常拆完每份几 KB），确实大的结构化数据（词库、规则库）挪对象存储 + initContainer 拉取或应用直读，ConfigMap 只留一个引用地址；第三步变更流程全部改走 Git PR——immutable + 版本化命名，CI 校验"改了哪个对象、哪些 Deployment 引用它"，合并即发布、发布可回滚。迁移本身用双读过渡：新旧对象并存，服务逐个切换引用，旧 shared-config 只读冻结一个月后下线。③ 搬不搬的判断轴还是本讲的分层表：启动参数型、随发布走的低频配置——留在 ConfigMap + GitOps，它们和镜像版本天然绑定，进 Nacos 反而丢了"配置变更 = 版本发布"的审计链；高频动态型（分钟级开关、白名单、参数调整）——这些本来就不该在 ConfigMap 里，搬 Nacos 是归位；敏感凭证——不进 Nacos 也不进 ConfigMap，走 ESO/密钥库。一句话：Nacos 解决"变得快"，ConfigMap+GitOps 解决"变得可审计"，密钥库解决"变得安全"，三个域各管各的，不是互相替代关系。
