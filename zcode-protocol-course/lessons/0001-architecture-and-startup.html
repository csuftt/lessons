第 1 课：整体架构与进程启动

目标：学完这课，你能画出插件与 zcode.cjs 的整体架构图，并自己用 20 行 Python 把 app-server 拉起来、发对第一帧。这一课是后面 7 课的地基——帧格式错了，后面全白搭。

一、zcode.cjs 是什么，app-server 是什么

zcode.cjs 是 ZCode CLI 的单文件打包产物（Node.js，约 12MB）。 它本身是个多面手命令行：终端里敲 zcode 进交互模式，而带上 app-server 子命令启动时， 它就变成一个stdio 上的 JSON-RPC 服务——不读键盘，stdin 收一帧、stdout 回一帧，专门给 GUI 宿主当后端用。

ZC-GUI 插件的思路就是：不重新实现 AI 逻辑，而是把 CLI 当"引擎"子进程养起来。 会话管理、模型调用、工具执行、MCP、技能……全在 CLI 侧；插件只做两件事：把 UI 翻译成 JSON-RPC 请求，把事件流翻译回 UI。

↑↓ JCEF 桥：sendToJava / executeJavaScript

反向请求（审批、提问、浏览器命令）也从 app-server 发往插件，方向与请求相反，见第 6 课
为什么选 stdio 而不是 HTTP/WebSocket？ 无需端口分配与防火墙顾虑，进程退出即连接断开，生命周期天然跟随 IDE；Line-delimited JSON 也最容易抓包调试（重定向 stdin/stdout 就能录帧）。

二、启动进程：三个环境变量是生命线

用 ProcessBuilder（或任何语言的 spawn）把 node 拉起来即可。但裸启动必失败—— app-server 启动时要从环境变量拿到模型与凭证，否则建会话直接报 -32603 "Model config is missing"：

# 必须注入的三件套（凭证注入后无法取消，属协议硬约束）
ZCODE_MODEL=glm-4.7            # 默认模型
ZCODE_BASE_URL=https://api.z.ai/api/anthropic  # 网关地址
ANTHROPIC_API_KEY=xxxxxxxx     # API Key

# 可选但推荐：让 CLI 的请求头带上宿主身份
ZCODE_APP_VERSION=0.16.5       # 拼进 user-agent / x-title
# 可选：代理
ZCODE_HTTP_PROXY=http://127.0.0.1:7890

20 行 Python 跑通的最小宿主（scripts/diag-stream.py 的骨架，本课程大量复用）：

import subprocess, json, os, threading

env = {**os.environ,
       "ZCODE_MODEL": "glm-4.7",
       "ZCODE_BASE_URL": "https://api.z.ai/api/anthropic",
       "ANTHROPIC_API_KEY": os.environ["MY_KEY"]}
p = subprocess.Popen(["node", "zcode.cjs", "app-server"],
                     stdin=subprocess.PIPE, stdout=subprocess.PIPE,
                     stderr=subprocess.PIPE, env=env, text=True)

def drain_stderr():            # 见本课第四节，绝不省略
    for line in p.stderr: print("[stderr]", line, end="")
threading.Thread(target=drain_stderr, daemon=True).start()

def rpc(id, method, params):   # 注意：帧里没有 "jsonrpc" 字段！
    p.stdin.write(json.dumps({"id": id, "method": method, "params": params}) + "\n")
    p.stdin.flush()

def read_loop():               # 读循环：按 id 路由 + 反向请求应答
    for line in p.stdout:
        msg = json.loads(line)
        if msg.get("id", "").startswith("server"):   # 反向请求，必须应答
            reply(msg)
        else:
            print("←", json.dumps(msg, ensure_ascii=False)[:200])
threading.Thread(target=read_loop, daemon=True).start()
stderr 必须持续排空 stderr 不读的话，管道缓冲区（Windows 上约 4KB）写满后 CLI 会整体卡死，表现为"所有请求超时但进程还在"。 这是全站超时类故障的头号根因。同理，读循环里单帧解析失败绝不能让异常外溢——一个形状古怪的遥测帧把 reader 线程炸掉，全线请求跟着超时（实踩缺陷：数组帧杀 reader）。

三、帧格式：四种帧，没有 "jsonrpc" 字段

这是本课最重要的一行字：信封不带 jsonrpc 字段。 带上了服务端直接回 -32600。它长得像 JSON-RPC 2.0，但实际是个方言。

帧类型方向形状
请求宿主 → CLI{"id": 42, "method": "session/list", "params": {...}}（id 为数字）
响应CLI → 宿主{"id": 42, "result": {...}} 或 {"id": 42, "error": {"code": -32602, "message": "..."}}
通知CLI → 宿主{"method": "session/event", "params": {...}}（无 id）
反向请求CLI → 宿主{"id": "server-1", "method": "interaction/requestPermission", "params": {...}}（id 为 字符串，"server" 前缀）

宿主的读循环按 id 类型做三路分发：数字 id 查 pending 表唤醒等响应的协程； "server*" 字符串 id 交给反向请求 handler（异步执行，见第 6 课）； 无 id 的按通知分发到事件监听器。反向请求的应答帧把原样 id 带回去：

{"id": "server-1", "result": {"decision": "allow"}}
{"id": "server-2", "error": {"code": -32601, "message": "no handler"}}

四、就绪探测：用最轻的请求当心跳

进程拉起 ≠ 服务就绪（Node 还要初始化配置、加载插件）。插件的做法：循环发 session/list 的最小请求 {"limit": 1}，等到第一个响应即视为就绪（默认等 30s）。 选它是因为最轻、幂等、无副作用——别用建会话当探测，失败会留垃圾会话。

rpc(1, "session/list", {"limit": 1})   # 循环发，收到 {"id":1,"result":...} 即就绪

五、协议代际：同一方法，两代参数形状不同

CLI 版本号不可靠（--version 曾长期停在 0.16.5）。真实可用的判别法是读 zcode.cjs 文件内容找标记串：

OLD（v1 代）NEW（v2 代）
判别标记不含 ZCODE_PERSONAL_PROVIDER_CONFIG_FILE文件含该标记串（兜底：看配置文件键形态）
渠道配置~/.zcode/cli/config.json~/.zcode/v2/provider_config.json（watch 热加载）
参数风格宽松，带 runtimeModel 大对象strict schema：多余字段直接 -32602 Unrecognized key
模型参数runtimeModel / modelRefmodelSelection / selection + options.reasoningLevel

插件启动时判一次代，之后所有模型相关调用按代分支。strict 校验是新版最大行为差异， 详细对照与自适应降级策略见第 5 课、第 8 课。

重试纪律 只有幂等读（session/list、session/read 等）允许超时重试；session/create、session/send 这类写操作禁重试——超时≠失败，请求可能已在服务端生效，盲目重发会出两条一样的消息。
