第 2 课：会话生命周期——list / create / resume / close

目标：掌握会话四件套 + session/read 万能读取。学完你能解释： 为什么恢复历史会话前必须 resume、-32004 的两种成因、以及 Windows 路径为什么要查两遍。

一、会话的两种存在形态

app-server 里的会话有两层状态，很多坑都出在混淆这两层：

  • 持久层：落盘在 CLI 的 sqlite 里，重启都在，session/list 看到的是它；
  • 运行时层：进程内存里的"激活槽位"，只有 resume / subscribe / create 过的会话才占槽。 绝大多数操作（read、setModel、send…）要求会话在运行时层是 active 的，否则报 -32004。
-32004 的两种成因，处理方式完全不同 ① 冷会话：历史会话还没激活——session/resume 一次即愈，这是绝大多数情况； ② 真槽位满：运行时槽位约 16 个（LRU），此时 resume 最旧的腾位置。 先试 resume，无效才考虑挤槽。

二、session/list：列出 + 两个 Windows 特有坑

{"id": 2, "method": "session/list",
 "params": {"workspace": {"workspacePath": "G:\\demo", "workspaceKey": "G:\\demo"},
            "includeArchived": false, "limit": 50}}
// → {"id": 2, "result": {"sessions": [{"sessionId": "sess_xxx", "title": "...",
//      "updatedAt": 1758000000000, "status": "...", ...}]}}

三个要点：

  • 路径双形态：历史数据里 G:\demo 和 G:/demo（正反斜杠）可能并存。 权威做法是两种形态各查一次取并集，只查一种会漏会话；
  • 过滤子代理：结果里混着 sess_subagent_* 前缀的子代理会话，展示时要过滤掉（它们不是用户会话）；
  • 按 updatedAt 重排：并集拼接会破坏倒序，客户端拿到后自己按 updatedAt 排。

三、session/create：四个模式值

{"id": 3, "method": "session/create",
 "params": {"workspace": {"workspacePath": "G:\\demo", "workspaceKey": "G:\\demo"},
            "mode": "build"}}
// → {"id": 3, "result": {"session": {"sessionId": "sess_abc", "protocol": {"name": "...", "version": 1}}}}

mode 取 build / edit / plan / yolo（yolo = 全自动不放权限审批）。 创建成功后服务端会立刻反向发来 session/requestRuntimePreferences（第 6 课）—— 不答它会一直等，所以读循环要先于 create 启动。

四、session/resume：激活历史会话的必经之路

// 完整形态：激活 + 绑定工作区（恢复现场时用）
{"id": 4, "method": "session/resume",
 "params": {"sessionId": "sess_abc",
            "workspace": {"workspacePath": "G:\\demo", "workspaceKey": "G:\\demo"}}}

// 轻量形态：只激活（槽位管理、删除前处理时用）
{"id": 5, "method": "session/resume", "params": {"sessionId": "sess_abc"}}

两条铁律：

  • subscribe 前必 resume：订阅一个冷会话，先 resume 再 subscribe，否则事件流接不上；
  • resume 要去重：并发两次 resume 同一会话会互相踩，插件侧维护"已 resume 集合"；
  • resume 中断回合的会话后有约 1.5~2 分钟"忙窗口"（服务端对中断的模型请求做指数退避重试）， 期间该会话的请求会超时，其他会话不受影响——对策是延迟 15s/30s 自动重试，别急着判死。

五、session/close 与删除

{"id": 6, "method": "session/close", "params": {"sessionId": "sess_abc"}}

close 只做两件事：结束运行时、清内存索引，不删持久数据。对未激活（inactive）的会话 close 会报 -32004。 所以完整的删除流程是三段式：resume → close → 直删 sqlite 记录（客户端删除语义是软删 deleted=1）。

六、session/read：万能状态读取器

一个方法顶四个用，插件的上下文圆环、设置面板、目标模式面板全靠它：

{"id": 7, "method": "session/read", "params": {"sessionId": "sess_abc"}}
// → result 里按需取：
//   runtime.contextUsage        上下文占用（圆环数据源）
//   settings.mode               当前权限模式（build/plan/...）
//   settings.thoughtLevel       {current, available:[{label,value}]} 思考级别
//   settings.model              当前模型
//   session.target              目标模式状态（objective/tokenBudget/timeUsed…）
//   goalStats                   目标统计

注意 settings.thoughtLevel.available 是思考级别的唯一权威来源—— 级别集因模型而异（GLM 是 off/high/max，qwen 系是 enabled/disabled），禁止前端硬编码候选值，每次打开面板现场 read。

七、session/setMode：运行中切换权限模式

{"id": 8, "method": "session/setMode", "params": {"sessionId": "sess_abc", "mode": "plan"}}

改完不要自己脑补状态——模式变更的权威回执走 state.updated 通知（patch 里有 mode 字段，见第 3 课）， 本地乐观更新 + 服务端回执对账才是稳的做法。
