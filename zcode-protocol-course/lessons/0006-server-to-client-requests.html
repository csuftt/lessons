第 6 课：反向请求——服务端也会"打电话"过来

目标：掌握 "server-N" 反向请求的处理纪律。协议是双向的： AI 执行中需要权限审批、要问用户问题、要操作浏览器时，会主动向宿主发请求——不接电话，回合就永远挂起。

一、处理纪律（三条铁律）

  • 必须应答：收到 {"id":"server-1","method":...} 后要把同 id 的 result（或 error）写回 stdin。 没接住的未知方法回 -32601，绝不能沉默——服务端在等回执，沉默=空等；
  • handler 必须异步：反向请求在独立线程池处理，禁止在 reader 线程里同步弹窗等待—— reader 一堵，所有请求全部超时；
  • 请求级去重：服务端可能换 id 重发同一请求，按业务键（如 toolCallId）去重，回执缓存复用。

二、反向请求全家福

method何时来应答 result
session/requestRuntimePreferencescreate/resume 会话后立刻{"nativeSearchEnhancementsEnabled": bool, "memoryEnabled": bool, "askUserQuestionAutoResolutionEnabled": bool} 三个键都必须给
interaction/requestPermission工具要执行敏感操作{"decision": "allow"|"deny"|"escalate"|"modify", "reason"?, "modifiedInput"?, "permissionUpdates"?}
interaction/requestUserInputAI 调 AskUserQuestion 工具{"action": "answer", "content": {"answer": "..."}} 或 decline
interaction/requestProviderRuntimeHeaders套餐网关风控验证{"headersApplied": bool, "errorMessage"?}
interaction/browserListAI 要用浏览器{"browsers": [...]}（能力清单，只列已实现的命令）
interaction/browserExecute执行浏览器命令命令执行结果（约 40 个命令的 discriminatedUnion）
automation/create|update|delete|list|checkTaskBindingAI 调 Cron 系定时工具宿主调度器的执行结果

三、requestRuntimePreferences：最容易卡死新手的一帧

会话一创建，服务端马上发来这帧。三个布尔键缺任何一个，会话初始化都会一直等—— 表象是"会话建了但发消息没反应"。无脑全 false 也能跑：

// 收到 {"id":"server-1","method":"session/requestRuntimePreferences","params":{...}} 时：
{"id": "server-1", "result": {
    "nativeSearchEnhancementsEnabled": false,
    "memoryEnabled": true,
    "askUserQuestionAutoResolutionEnabled": false}}

memoryEnabled 等 开关要和插件设置页联动的话，就按设置回。这帧同时是官方客户端的一条隐藏链路—— 官方 GUI 能不注入凭证 env 裸跑靠的就是这类反向通道，纯 headless 宿主不具备，所以凭证 env 该注还是得注（第 1 课）。

四、requestPermission：strict schema，多字段必拒

// 服务端 params 携带工具名、输入、权限上下文；宿主弹审批面板，用户点允许后：
{"id": "server-2", "result": {"decision": "allow"}}

// 修改后放行：
{"id": "server-2", "result": {"decision": "modify",
                              "modifiedInput": {"path": "G:\\demo\\a.py", "content": "..."},
                              "reason": "调整了写入路径"}}

// 拒绝（意见式拒绝会作为反馈回流给 AI 继续跑；裸 deny 则终止该工具）：
{"id": "server-2", "result": {"decision": "deny", "reason": "这个文件不要动"}}
strict 应答 应答对象也是 strict 的：多了协议外的字段会被整体拒绝。decision 取值固定四个， 大小写敏感。审批面板要做"无超时等待"（超时自动拒绝会打断长任务），并处理同会话多个审批排队的情况。

五、requestUserInput：AskUserQuestion 的宿主侧

// params 里是问题结构（question/header/options 等，选项带 label/description/multiSelect）
// 用户选了"选项 B"：
{"id": "server-3", "result": {"action": "answer",
                              "content": {"answer": "B"}}}
// 用户关掉弹窗：
{"id": "server-3", "result": {"action": "decline"}}

宿主没有弹窗能力（如后台无人值守）时必须回 decline让 AI 走降级路径， 沉默会让回合无限挂起。完成态的问答对会作为工具回执落进转录（工具卡回看功能的数据源）。

六、browserExecute：把 AI 的浏览器工具接进自己的内核

这是插件最"宿主"的一帧：AI 发起 browser_navigate / browser_click / browser_snapshot 等命令， 宿主决定在哪执行——插件把它接进 IDE 内嵌 JCEF 浏览器：

// 服务端：
{"id": "server-4", "method": "interaction/browserExecute",
 "params": {"command": "navigate", "url": "https://example.com", ...}}
// 宿主驱动 JCEF 完成后：
{"id": "server-4", "result": {"ok": true, "snapshot": "..."}}

// browserList 先声明能力（只列真正实现的命令，AI 会按能力选择）：
{"id": "server-5", "result": {"browsers": [{"name": "jcef-embedded",
                                            "capabilities": ["navigate","click","snapshot","fill", ...]}]}}

生命周期类命令（closeSession 等）要做幂等空应答（重复 close 不报错）； 没有宿主能力时 browserList 回空数组，AI 会自动降级为"给你命令你自己跑"。

七、automation/*：定时任务的中继

AI 调 CronCreate / CronUpdate 这类工具时，服务端原样转成 automation 反向请求交给宿主—— 调度器在宿主手里（插件用 Java 定时器实现，webview 里只是镜像）。业务上拒绝（比如循环任务不支持）可以正常回执说明， handler 未注册则回 -32601。注意：CLI 的"闲时（off-peak）任务"定义存在官方 Electron 宿主的私有存储里，没有对应 RPC，第三方宿主拿不到也建不了。
