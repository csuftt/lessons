第 7 课：历史与高级操作

目标：掌握读历史、翻页、回合分叉、编辑历史消息、改标题、目标模式这些"进阶动作"。 核心新概念只有一个：乐观并发（CAS）——v4 写命令的通用套路。

一、读历史：两条通道

// legacy 转录（一次性全量，适合渲染完整历史）
{"id": 40, "method": "session/messages", "params": {"sessionId": "sess_abc"}}
// → messages[]，其中用户图片 part 是 {type:"file", url:"zcode-artifact://..."}，
//   宿主要自己把它映射成本地缓存 URL 才能显示

// v4 行模型翻页（适合虚拟滚动/按需加载，每页 ≤200）
{"id": 41, "method": "v4/conversation/rowsRange",
 "params": {"sessionId": "sess_abc", "topic": "conversation/sess_abc",
            "limit": 200, "beforeRowId": "row_0520"}}   // 不带 beforeRowId = 从最新往回
// → {"rows": [{rowId, turnId, kind, text, input, output, actions:{canFork, canEdit}}], "hasMore": true}

rowsRange 是 v4 写命令的定位器：fork / 编辑历史消息的 target（rowId + entityId）都从它的返回里拿， actions.canFork / canEdit 是服务端算好的可操作性标记，UI 直接用。

二、v4/command 的 CAS：乐观并发三步舞

所有"改历史"的写命令（fork / editUserQuery / deleteQueueItem）都带 baseRevision： 它必须等于服务端当前 revision，不等就回 stale。但服务端不会把 revision 免费给你——标准流程：

1. 首发带 baseRevision: 0
   → {"status": "stale", "revisionAtDecision": 57}    // 几乎必 stale，别慌，这是设计如此
2. 用 revisionAtDecision 作为 baseRevision 重发
   → {"status": "accepted"}                            // 一次重试即中
3. 若再 stale（期间又有并发写），重复第 2 步（插件设了最多 5 轮）
为什么这样设计 避免"读-算-写"竞态：服务端用 revision 做 CAS，保证两个客户端同时改历史不会互相覆盖。 revisionAtDecision 是"服务端拒绝那一刻的最新版本"，天然就是你的下一次筹码。

三、forkAssistant：从任意轮分叉新会话

{"id": 42, "method": "v4/command",
 "params": {"commandId": "cmd-u1", "clientId": "zcode-idea-plugin",
            "sessionId": "sess_abc", "type": "forkAssistant",
            "payload": {"target": {"rowId": "row_0518", "entityId": "ent_3"}},
            "baseRevision": 0, "baseLogEpoch": 3,       // CAS 双基准
            "issuedAt": 1758000000000}}
// stale → 用 revisionAtDecision 重试
// accepted → result.sessionId 即分叉出的新会话

要点：target 行须 actions.canFork（轮末的 assistantText 行）； 分叉会恢复工作区文件到那个时点——这是破坏性动作，且没有参数可跳过，UI 上要明示用户； 历史遗留的 legacy session/fork 通道已弃用（行为怪、同样会恢复文件），一律走 v4。

四、editUserQuery：编辑历史消息

{"id": 43, "method": "v4/command",
 "params": {..., "type": "editUserQuery",
            "payload": {"target": {"rowId": "row_0501", "entityId": "ent_1"},
                        "newText": "改成这样：只用标准库实现",
                        "attachments": [{"ref": "file:///tmp/x.png",   // ref 引用形态，非 base64
                                         "fileName": "x.png", "mime": "image/png",
                                         "bytes": 20480}]},
            "baseRevision": 0}}

三个实战要点：

  • 带图编辑必须显式传 attachments：不传数组，原图直接丢——服务端不会"保留原图"；
  • 回合中编辑要 stop-first 两段式：工具执行中提交会 accepted 却永不生效（重发被排队）。 正确姿势：先 stop 回合，等终态，再 edit，然后（可选）自动重发触发新回合；
  • 编辑后的行 id 行为：回合中=就地改写 id 复用；空闲=产生新 id。UI 不要缓存行 id 做长期主键。

五、renameSession 与 goal

// 改标题（payload 极简，无 CAS 要求）
{"id": 44, "method": "v4/command",
 "params": {..., "type": "renameSession", "payload": {"title": "重构协议客户端"}}}
// 注意：新会话要"发过一条消息激活 runtime"后改名才生效；自动标题只在第 0 回合正常结束后生成一次，
// 中断过的会话永远停在 first_input 来源。

// 目标模式：六动作引擎，执行在服务端
{"id": 45, "method": "session/goal",
 "params": {"sessionId": "sess_abc", "action": "set", "objective": "把测试全绿并保持不回退"}}
// action ∈ set / replace / pause / resume / clear / show
// → {response, snapshot:{...目标统计, tokenBudget, timeUsedSeconds}, startedTurn?}
// 续跑轮是"model-only 合成 user 消息"（转录里看到无正文的 user 帧不是 bug）；
// tokenBudget 没有设置入口，只能读。

六、杂项但常用

方法作用要点
