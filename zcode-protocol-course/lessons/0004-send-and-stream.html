第 4 课：发消息与流式交互

目标：掌握 session/send 与 v4/command sendText 双通道， 理解消息的三态路由（立即/排队/插队）、附件形态、以及"停止回合"为什么不能用 legacy stop。

一、session/send：主入口与它的参数陷阱

{"id": 20, "method": "session/send",
 "params": {"sessionId": "sess_abc",
            "content": "帮我看看这段代码",          // 注意：字段名是 content，不是 message！
            "modelSelection": {"providerId": "bigmodel-api",   // v2 代才传；v1 代用 runtimeModel
                               "modelId": "glm-4.7"},
            "attachments": [{"kind": "image", "filename": "err.png",
                             "mimeType": "image/png", "sizeBytes": 20480,
                             "dataBase64": "iVBORw0..."}]}}
// → {"id": 20, "result": {"accepted": true, "sessionId": "sess_abc", ...}}

要点：

  • 字段名是 content——写成 message 服务端不报错但也不干活，属"静默无效"类坑；
  • attachments 走 base64 内联（kind:"image"）；历史读回来时图片则变成 zcode-artifact:// 引用，两个世界别搞混；
  • -32031（restoreWarning）自救：send 被拒 = 会话没有可用的模型上下文。对策是把当前模型随 send 一起带上 （v1 带 runtimeModel / v2 带 modelSelection），原路重试即可，不需要先单独 setModel。

二、回合一分钟：send 之后事件怎么流

发送成功后，UI 完全由事件驱动（第 3 课的订阅此刻开始干活）：

#事件宿主动作
1turn.started插入回合容器，锁定输入态
2model.streaming(reasoning_delta…)思考区滚动
3model.streaming(text_delta…)正文打字机
4tool.updated(scheduled→started→progress→result)工具卡生命周期，按 toolCallId 关联
5turn.completed（usage 在 payload 里）收尾、显示耗时与 token
流式期间看门狗的豁免 宿主常有"N 秒无事件判卡死"的看门狗。但工具 progress 事件可能被 UI 拦截不落盘，造成"事件静默但回合活跃"的误报—— 看门狗的豁免判据要覆盖全部活跃信号（含 ended），别只看 streaming delta。

三、v4/command sendText：三态路由

回合进行中再发消息，走 v4/command 的 sendText，用 requestedDelivery 指定路由：

{"id": 21, "method": "v4/command",
 "params": {"commandId": "cmd-uuid-1",              // 客户端生成，排队伍 id 可由它派生
            "clientId": "zcode-idea-plugin",
            "sessionId": "sess_abc",
            "type": "sendText",
            "payload": {"text": "先改这个再继续",
                        "requestedDelivery": "guide"},   // startNow | queue | guide
            "issuedAt": 1758000000000,
            "connectionId": "b7e2...",
            "clientMode": "desktop-continuous"}}
startNow立即开启新回合
queue进队列，当前回合结束后自动发出
guide插队：注入当前回合，AI 即刻看到
三态由服务端裁决；回合空闲时 guide/startNow 等价于直接开跑

两个必须知道的坑：

  • ack 的 result.delivery 恒报 "queue"，不可信。真实路由看后续事件： turn.steerQueued（已受理插队，带 targetTurnId）/ turn.steerDrained（注入完成，injectedMessageIds 可定位落位）；
  • guide + 附件 = 服务端强制降级 queue（reasonCode 类 guide.attachmentsUnsupported）—— 插队通道不支持图片，UI 要提前拦截或提示。

队列管理配套两个命令：deleteQueueItem（撤回排队消息，队列 id = "queue_" + commandId，前端可预置）； 队列排空（当前回合结束把队首发出去）是客户端职责，服务端不会自动替你 flush。

四、停止回合：legacy stop 已死，v4 stop 当立

// 已实证失效：官方客户端从不调它，新版 CLI 上发了个寂寞
{"id": 22, "method": "session/stop", "params": {"sessionId": "sess_abc"}}

// 正确姿势（40ms 内真终止）：
{"id": 23, "method": "v4/command",
 "params": {"commandId": "cmd-uuid-2", "clientId": "zcode-idea-plugin",
            "sessionId": "sess_abc", "type": "stop",
            "payload": {}, "issuedAt": 1758000000000,
            "connectionId": "b7e2...", "clientMode": "desktop-continuous"}}

stop 的收尾有个隐蔽差异：流式期（模型吐字中）停下后，legacy 流不发终止帧； 工具执行期停则会发真实 turn.completed。所以宿主要按 turnId 守卫，自行合成收尾信号， 否则 UI 会一直转圈。另外 stop 只停前台回合，后台任务要用 session/cancelBackgroundTask（taskId 即子代理 agentId）单独停。
