第 3 课：订阅与事件流

目标：理解"请求拿一回执，订阅拿一辈子"的模型。学完你能画出一条消息从 send 到屏幕渲染的完整事件链，并知道为什么子代理会话要另走一条 v4 通道。

一、订阅模型总览

JSON-RPC 请求是"一问一答"，而 AI 回合是持续几分钟的流。事件的搬运靠订阅： 订阅一次，之后该会话的所有事件以通知帧持续推给宿主，直到进程结束（插件实践中从不退订，16 个运行时槽位跟着进程活死）。

session/subscribe主会话事件主通道（legacy 面）
v4/conversation/subscribe子会话 / v4 帧通道
↓↓ 通知帧持续下发（无 id）
session/event信封 {type, seq, sessionId, payload}
v4/conversation/frame行模型帧，客户端映射成 legacy 事件
↓↓ 按 sessionId 路由
宿主事件监听器归约进 UI 状态（16ms 节流批量刷新）

二、session/subscribe：主会话事件唯一来源

{"id": 10, "method": "session/subscribe",
 "params": {"sessionId": "sess_abc",
            "deliveryKind": "desktop-continuous",   // 必填
            "includeSnapshot": true,                // 带一次全量快照（历史回放）
            "afterSeq": 0}}                          // 断点续传：只推 seq 之后的事件
// → {"id": 10, "result": { ...快照对象... }}

三条纪律：

  • 先 subscribe 再 send：时序反了，回合事件在订阅生效前就发出去了，永远收不到；
  • deliveryKind 固定 desktop-continuous（continuous 才有流式增量路径）；
  • afterSeq + includeSnapshot 组合可实现断点续传：从上次收到的 seq 续着收，之前的从快照回放。
订阅白名单要先登记，再发请求 服务端在订阅 ack 回来之前就可能开始推首批帧。如果宿主"收到帧→查白名单→没登记→丢弃"， 首批快照+增量会静默丢失。正确顺序：先把会话记进本地白名单，再发 subscribe 请求；失败路径把登记回滚，否则重试也会错乱。

三、session/event：事件信封与全家福

legacy 通道上服务端→宿主的通知几乎只有 session/event 一个方法，一切业务事件都是它信封里的 type：

{"method": "session/event",
 "params": {"type": "model.streaming", "seq": 1042, "sessionId": "sess_abc",
            "turnId": "turn_1", "timestamp": 1758000000000,
            "payload": {"kind": "text_delta", "delta": "你好", "assistantMessageId": "msg_9"}}}
typepayload 要点UI 用途
turn.started{turnNumber, input, messageId}开新回合气泡
model.streamingkind = text_delta / reasoning_delta（另有 tool_input_start/delta 走 v4 映射），delta 增量文本打字机效果、思考区
tool.updatedkind = scheduled / started / progress / result / error / batch，按 toolCallId 关联工具卡全生命周期
session.updated{model, modelRef, iteration}；goal 推送也走它模型指示器、目标面板
turn.completed{response, usage:{inputTokens, outputTokens, totalTokens, cacheReadTokens…}}收尾 + 耗时统计
turn.failed{error:{type, code, message, stack}, turnPhase}——终止帧报错呈现
session.titleUpdated{title, source, previousTitle}标签页标题
turn.steerQueued / steerDrained{delivery:"guide", targetTurnId} / {injectedMessageIds}插队消息落位提示

另一个独立通知 state.updated（模式/思考级别/模型/权限的变更回执，patch 字段+revision）会被宿主转成 type="state.updated" 的事件进同一条流。此外新版 CLI 每几分钟会推 process/mcpResourceSamples 之类的 遥测通知，params 直接是数组——解析时必须安全转换，单帧失败不能炸掉读循环（第 1 课的教训）。

四、v4/conversation/subscribe：子会话的唯一实时通道

关键事实：对子代理会话调 legacy session/subscribe 会成功，但一条事件都不会推（恒 0 投递）。 子会话的实时流必须走 v4 通道：

{"id": 11, "method": "v4/conversation/subscribe",
 "params": {"topic": "conversation/sess_sub_1",   // topic = "conversation/" + sessionId
            "connectionId": "b7e2...",            // 连接级 UUID，整条连接复用一个
            "clientMode": "desktop-continuous"}}
// → {"id": 11, "result": {"ack": {"subscriptionId": "sub_9", "logEpoch": 3}}}

退订要带三件套：topic + connectionId + subscriptionId，缺一个就 -32603。 帧到达时是 v4/conversation/frame 方法，payload 是"行模型"：

op含义
row.appended / row.upserted追加/更新一行：{rowId, turnId, kind, text, output, status, actions:{canFork, canEdit}}；kind ∈ turnHeader / assistantText / reasoning / toolCall / userInput / timelineMarker
row.delta{rowId, path:"text", append}——流式增量往某行追加
state.updated / row.removed状态与删行（多数宿主可忽略）

宿主拿到帧后自己映射成 legacy 事件（turn.started / model.streaming / tool.updated…）， 这样上层 UI 只面对一种事件模型。要点：v4 订阅会话要先进本地白名单再发请求， 且临时订阅（比如只为取 logEpoch）不要进白名单，否则快照回放会误推给 UI。

五、v4/telemetry/event：v2 代的回合终态

v2 代 CLI 有个行为变化：模型校验后置——send 回执正常，但模型创建失败时 legacy 流上 没有 turn.failed，终态只走 v4/telemetry/event 通知（type=turn.terminal）：

{"method": "v4/telemetry/event",
 "params": {"kind": "turn.terminal", "status": "failed", "sessionId": "sess_abc",
            "turnId": "turn_1", "errorCode": "...", "errorMessage": "..."}}

宿主的映射纪律：failed → 合成 turn.failed；aborted / cancelled → 合成 turn.completed； success → 跳过（legacy 流已有真实完成帧，重复合成会出现两个结束气泡）。 终态来源必须收敛到单一出口。
