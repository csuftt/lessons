struct、方法与指针接收者:没有 class 的面向对象

目标:读懂并评审 Go 项目 · 实战 = tdengine-replicator

本课赢点:你不再把 Go 的 struct 当成「残废的 class」。你能说清「值接收者」和「指针接收者」的区别——这是 Go 评审里最容易藏 bug 的地方之一。

← 上一课:错误处理与 defer

1. struct = 只有数据的 class(方法在「外面」)

看 Config(config.go:9),你先感受 Go 的 struct:

type Config struct {
    LocalHost string
    LocalPort int
    PeerHost  string
    PeerPort  int
    User      string
    Password  string
    // ...更多字段
}
Go · struct只有字段,没有方法、没有构造器、没有继承。字段类型写在字段名后面(LocalHost string),无逗号。
Java · class字段+方法+构造器+继承都在一个 class 里。private String localHost;

关键差异:Java 的方法写在 class 大括号里;Go 的方法写在 struct 外面,靠「接收者(receiver)」声明归属。看 TopicSpec(config.go:62):

type TopicSpec struct {
    Topic    string
    DB       string
    Stable   string
    DataCols []string
    TagCols  []string
}

func (t TopicSpec) replIdx() int   { return len(t.DataCols) }          // ① 方法
func (t TopicSpec) tbnameIdx() int { return len(t.DataCols) + 1 }
func (t TopicSpec) totalCols() int { return len(t.DataCols) + 2 + len(t.TagCols) }

注意 func 和函数名之间多了 (t TopicSpec)——这就是接收者。它的意思等同于 Java 的 this:「这个方法属于 TopicSpec,t 就是接收者本身」。调用时:

spec := cfg.DataTopics[0]
i := spec.replIdx()   // 像 Java 的 spec.replIdx()
Go · 接收者func (t TopicSpec) replIdx() int
t 是接收者变量,TopicSpec 是类型。
Java · thispublic int replIdx() { ... }
this 隐含,不用写出来。

这里 (t TopicSpec) 里类型前没有 *——这是「值接收者」,下一节是重点。

2. 本课核心:值接收者 vs 指针接收者

对比同项目里两类方法,先看现象:

// config.go —— 值接收者(类型前无 *)
func (t TopicSpec) replIdx() int { return len(t.DataCols) }

// graceful_shutdown.go —— 指针接收者(类型前有 *)
func (sc *ShutdownCoordinator) Register() context.Context {
    sc.wg.Add(1)      // ← 在修改 sc 的字段
    return sc.ctx
}

* 在 Go 里是「指针」(类似 Java 的引用,但更显式)。这两种写法的区别是 Go 评审的重灾区:

Go · 值接收者 (t TopicSpec)t 是副本。方法里改 t 不影响原对象。适合只读/纯计算。replIdx 只读 DataCols,用值接收者合理。
Java 类比不存在「按副本传递」——Java 对象永远是引用。所以这点对 Java 人最反直觉。
Go · 指针接收者 (sc *ShutdownCoordinator)sc 是指向原对象的指针。方法里改 sc 的字段 = 改原对象。Register 调 sc.wg.Add(1) 改了 wg,必须用指针。
Java 类比≈ 普通实例方法操作 this。Java 习惯,Go 要你显式用 *。
⚠️ 评审高发 bug:该用指针却用了值接收者 如果你看到 func (sc ShutdownCoordinator) Register()(漏了 *),sc.wg.Add(1) 改的是副本的 wg,原对象的 wg 没变——关闭协调彻底失效,且不报错,极难查。评审规则:方法要修改对象状态 → 必须是指针接收者。本项目 ShutdownCoordinator、metrics、RecoveryCoordinator 全用指针接收者,因为它们都持状态——正确。

经验法则(够评审用)

  • 要改字段 / struct 很大 / 为了和同类型其他方法一致 → 用指针接收者 (s *T)。
  • 纯读、struct 很小(几个基本类型) → 可以用值接收者 (s T)。
  • 同一类型的方法,接收者类型要一致(别一半值一半指针)——这是 Go 惯用法,混用评审要打回。

3. 构造器:Go 用约定,不用关键字

Go 没有 new Config() 这种构造器语法。约定是写一个 NewXxx / newXxx 函数返回实例(通常返回指针):

// graceful_shutdown.go:20
func newShutdownCoordinator() *ShutdownCoordinator {     // 返回指针
    ctx, cancel := context.WithCancel(context.Background())
    return &ShutdownCoordinator{                         // & 取地址 → 得到指针
        ctx:    ctx,                                     // 字段:值 初始化(键值式)
        cancel: cancel,
    }
}
Go · 构造普通函数 + &T{...}。& 取地址。T{字段:值} 是字面量构造(类似 Java record 全参构造)。
Java · 构造new ShutdownCoordinator(ctx, cancel) + 构造器方法。

评审时找入口:main.go 里 sc := newShutdownCoordinator() / m := newMetrics(cfg) / recovery := newRecovery(...)——看到 newXxx() 就知道是「构造这个对象」。

4. 顺带:struct 里嵌入「类型」(不是继承)

Go 没有 extends。ShutdownCoordinator 里:

type ShutdownCoordinator struct {
    wg     sync.WaitGroup   // 命名字段:持有一个 WaitGroup
    ctx    context.Context  // 命名字段:持有接口
    cancel context.CancelFunc
}

这是组合(has-a),不是继承(is-a)。Go 的哲学是「组合优于继承」——和你 Spring 里习惯的类层次不同。后面讲 interface 时你会看到 Go 怎么用「隐式接口」替代继承的多态。

🔑 这对你 Spring 直觉的修正 别找「基类/抽象类/继承链」——Go 没有。找「struct + 方法 + interface」三件套:struct 装数据,方法挂外面,interface 定义能力。评审设计时,关心的是「接口是否小而专注」「组合是否合理」,而不是继承层次是否漂亮。

5. 自测

检索练习
func (t TopicSpec) replIdx() 和 func (sc *ShutdownCoordinator) Register(),哪个会在方法内的修改不反映到原对象?
点开看答案

前者(TopicSpec,值接收者)。它是副本,方法内的改动(如果有)只改副本。TopicSpec 方法都是只读计算,无副作用,所以用值接收者没问题。后者是指针接收者,改 sc 就是改原对象。

评审练习
某 PR 里写了 func (m metrics) incCount(),方法体是 m.count++。你的评审意见?
点开看答案

bug。值接收者,m.count++ 改的是副本,原 metrics.count 永远不增,且无编译错误。必须改成 func (m *metrics) incCount()。本项目 metrics 的方法正是指针接收者(func (m *metrics) pushLoop),对照即可。凡是方法里写 s.x = ... 或 s.x++,检查接收者是否带 *——这是 Go 评审肌肉记忆。

翻译练习
return &ShutdownCoordinator{ctx: ctx, cancel: cancel} 里的 &,对应 Java 什么概念?
点开看答案

& 取对象的地址,得到指针。Java 里你拿到的对象引用天然就是「指向堆对象的指针」,所以 Java 程序员从不写 &。Go 把「值」和「指向值的指针」显式区分:ShutdownCoordinator{...} 是值,&ShutdownCoordinator{...} 是指向它的指针。返回指针后,调用方修改的就是同一份对象。
