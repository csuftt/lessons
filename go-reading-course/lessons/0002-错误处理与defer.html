错误处理与 defer:Go 没有 try/catch

目标:读懂并评审 Go 项目 · 实战 = tdengine-replicator

本课赢点:你能看懂 tdengine.go 里所有err相关的写法,并作为评审者指出「哪个错误被吞了、哪个资源没用 defer 关」。这是 Go 代码评审的第二大重点。

← 上一课:从 main.go 入手

1. 核心转变:错误是「返回值」,不是「异常」

Java 里你抛 Exception,用 try/catch/finally。Go 没有异常。错误就是一个普通的返回值,类型是内置接口 error。函数把「结果」和「错误」一起返回,调用方必须显式检查。

看真实代码 openConn(tdengine.go:14):

func openConn(host string, port int, user, pass string) *af.Connector {
    c, err := af.Open(host, user, pass, "", port)  // ① 返回两个值:结果 + 错误
    if err != nil {                                 // ② Go 最高频惯用法
        log.Fatalf("[tdengine] open %s:%d failed: %v", host, port, err)
    }
    log.Printf("[tdengine] connected native %s:%d", host, port)
    return c
}
Go · 多返回值c, err := af.Open(...)
一次返回「连接 + 错误」。:= 同时声明两个变量。
Java · 异常Connector c = af.open(...);
失败时 af.open 抛异常,调用方 try/catch。
🔑 Go 评审的第一直觉:看到 , err 就问「err 被检查了吗?」 if err != nil 是 Go 里出现频率最高的模式,没有之一。评审时养成反射:凡是函数返回了 err,下面必须有对它的处理(返回、记日志、或显式忽略并注释原因)。返回了 err 却不检查 = 几乎一定是 bug。

这里的 %v 是什么?

log.Fatalf("...failed: %v", err) —— %v 是格式化占位符,表示「把 err 按默认形式打印」。类似 Java 的 String.format 或 SLF4J 的 {}。常见还有 %s(字符串)、%d(整数)。%v 最通用,打印 error 都用它。

⚠️ log.Fatalf = 直接结束进程 Fatalf 打完日志后调用 os.Exit(1)——整个进程立刻退出,defer 都不执行。它只该用在启动阶段不可恢复的错误(如连不上数据库、配置解析失败)。openConn 用在启动时,合理。但在请求处理/后台循环里用 Fatalf = 一个错误打死整个进程,评审要打回。

2. 多返回值的另一种用法:带「标志位」

不是所有多返回值都是「结果 + error」。看 queryChildTag(tdengine.go:52),它返回三个值:

func queryChildTag(c *af.Connector, db, childTable, tagCol string) (string, bool, error) {
    q := fmt.Sprintf("SELECT `%s` FROM `%s`.`%s`", tagCol, db, childTable)
    rows, err := c.Query(q)
    if err != nil {
        return "", false, err        // ① 出错:空值 + false + err
    }
    defer rows.Close()               // ② defer(下面讲)
    dest := make([]driver.Value, 1)
    if err := rows.Next(dest); err != nil {
        return "", false, nil        // ③ 无行:空值 + false + 无错(io.EOF)
    }
    v := dest[0]
    if v == nil {
        return "", true, nil         // ④ 有行但值 nil:空 + true + 无错
    }
    return fmt.Sprintf("%v", v), true, nil  // ⑤ 正常
}

Java 怎么写这个?你可能用 Optional<String> 或抛 NoSuchElementException。Go 的做法是把所有可能情况压进返回值:「真正的值 / 是否存在 / 是否出错」三个维度分开,调用方一眼能区分「没查到」和「查询失败」。这是 Go 处理「可能缺失」的标准姿势。

3. defer:Go 版的 finally

注意上面第 ② 行 defer rows.Close()。defer 的意思是:「这个函数返回时(无论正常返回还是出错返回),执行 rows.Close()」。

Go · defer写在「获取资源」的正下方,函数返回前自动执行。多个 defer 按后进先出栈序执行。
Java · try-finally / try-with-resources等价 finally 里 close()。Go 没有 ARM,但 defer 写在 open 旁边,可读性更好。

对比 Java 的写法,体会 defer 的简洁:

// Java
Rows rows = c.query(q);
try {
    ...
} finally {
    rows.close();   // 关闭逻辑在几十行之后,容易漏
}

// Go
rows, err := c.Query(q)
if err != nil { return ... }
defer rows.Close()  // ← 紧跟在 open 后面,获取即可见释放
...
// 函数任意 return,rows 自动 Close
🔑 评审心法:defer 要紧跟 open Go 评审资源泄漏的标准动作:看到 Open/Query/OpenFile/Dial,往下扫一眼有没有配对的 defer ...Close()。open 了却没 defer close = 资源泄漏隐患(尤其函数有多条 return 路径时)。queryChildTag 和 queryMaxTS 都正确地在 Query 之后立即 defer Close——这是好代码。

现在你能回答上一课留的问题了:「localInit.Close() 为什么不写成 defer?」——看 main.go 里那段:

localInit := openConn(...)
initSchema(localInit, cfg, initSQLText)
localInit.Close()   // 立即关闭,因为这个连接只在初始化时用一次

这里其实可以写成 defer localInit.Close(),但那样会拖到 main 返回(整个进程关闭时)才释放。作者选择立即 Close,是让连接的生命周期清晰可见。两种都对,但 defer 更防漏。

4. 评审进阶:错误是被「检查字符串」判断的——这是个坑

看 isIdempotentErr(tdengine.go:32):

func isIdempotentErr(err error) bool {
    if err == nil { return true }
    s := err.Error()
    return strings.Contains(s, "already exist") || strings.Contains(s, "Already exist") || isNotExistErr(err)
}

Go 的 error 默认只能拿到字符串(err.Error())。要判断「是什么错」,经常只能字符串包含匹配。这在 Java 看来很原始(Java 用 catch (SQLException e) + e.getErrorCode())。

⚠️ 评审时盯紧:字符串匹配错误 = 脆弱 TDengine 升级后如果错误文案从 "already exist" 变成 "Already exists",这段就静默失效,导致幂等判断错误 → 数据重复或丢失。这是 tdengine-replicator 评审时值得提的一个设计风险点:字符串大小写还特意写了两个变体,说明作者已被坑过。更好的做法是驱动层暴露结构化错误码(本项目用的是 native driver,暂时没有,属已知妥协)。

5. 自测

检索练习 · 判断
下面这段有什么问题?
rows, err := c.Query(q)
// 直接用 rows,没看 err
点开看答案

err 没被检查。若 Query 失败,rows 大概率是 nil,下面访问 rows.Next 会 panic(空指针)。Go 编译器不强制你检查 err(不同于 Java 的检查异常),所以这类遗漏只能靠评审和 linter(如 errcheck)抓。if err != nil { return err } 是必须的。

翻译练习 · defer
defer rows.Close() 放在 if err != nil { return ... } 之前还是之后?为什么?
点开看答案

之后。必须先确认 err == nil(即 Query 成功、rows 有效)再 defer Close。若放前面,Query 失败时 rows 是 nil,defer 一个 nil.Close() 会在返回时 panic。本项目 queryChildTag 正是「先判断 err,再 defer」——正确顺序。

评审练习
envIntOr(config.go:104)解析环境变量失败时直接返回默认值,不报错。作为评审者你怎么看?
点开看答案

这是静默吞错的典型。用户把 TD_LOCAL_PORT 写成 "abc",Atoi 失败,函数默默返回默认 6030,进程照常启动但连错端口,排查极痛。评审建议:启动期配置解析失败应 log.Fatalf 暴露问题(fail fast),而非静默回退。这是你可以给作者提的具体改进点。
