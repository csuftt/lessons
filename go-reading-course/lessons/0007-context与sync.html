context 与 sync:并发协调

目标:读懂并评审 Go 项目 · 实战 = tdengine-replicator

本课赢点:你理解为什么 Go 几乎每个函数第一个参数都是 ctx context.Context,并掌握 WaitGroup / Mutex / Once 三件套——把 goroutine 安全地组织起来。

1. context.Context:取消信号 + 超时 + 值,一统天下

Java 里你想让一个后台任务可取消,得自己造轮子(标志位、Interrupt、Future.cancel)。Go 用一个标准接口 context.Context 统一解决,贯穿所有代码。约定:长生命周期函数第一个参数就是 ctx。本项目 runDataConsumer(ctx, ...)、probeLoop(ctx)、runResync(ctx, ...) 全是。

ctx 能做三件事,本项目用到前两件:

  • 取消:调用 cancel() 后,所有持有该 ctx(或其子 ctx)的 goroutine 通过 <-ctx.Done() 解除阻塞、收到退出信号。
  • 超时:到点自动取消。
  • 携带值(request-scoped):本项目未用。

看两个创建 ctx 的真实场景:

// graceful_shutdown.go:21 —— 派生「可手动取消」的根 ctx
func newShutdownCoordinator() *ShutdownCoordinator {
    ctx, cancel := context.WithCancel(context.Background())  // context.Background() 是根
    return &ShutdownCoordinator{ctx: ctx, cancel: cancel}
}
// 收到 SIGTERM 时调 sc.cancel() → 所有用这个 ctx 的 goroutine 的 Done() 立刻就绪

// recovery.go:77 —— 派生「4 小时后自动取消」的子 ctx
ctx, cancel := context.WithTimeout(context.Background(), timeout)
defer cancel()        // ← 必配对:函数返回时释放 ctx 占的资源
... runResync(ctx ...) // 把 ctx 传下去,回补超时自动中止
⚠️ 评审铁律:凡 context.WithCancel/WithTimeout/WithDeadline 必须配 defer cancel() go vet 会检查这个。漏掉 cancel() 会泄漏 ctx 及其关联的 goroutine/定时器,直到父 ctx 取消。本项目 recovery.go:78 正确地 defer cancel()。评审时看到 WithTimeout 后没有 defer cancel = 一定打回。

ctx 如何向下传递:形成树

ctx 是树状的:context.Background() 是根,每次 WithCancel/WithTimeout 产生子 ctx。取消父 ctx → 所有子 ctx 自动取消。本项目:main 派生根 ctx → 传给每个 consumer/recovery loop → 它们内部再派生带超时的子 ctx(recovery)。取消根 ctx(关闭信号)→ 整棵树取消 → 所有 goroutine 退出。这就是「优雅关闭」能一秒停全部的原理。

读 ctx 状态的两个方法:<-ctx.Done()(阻塞,直到取消)和 ctx.Err()(返回 nil/Canceled/DeadlineExceeded)。本项目 recovery.go:97 用 if ctx.Err() != nil 在长循环里随时检查是否已超时。

2. sync.WaitGroup:等一群 goroutine 全部结束

Java 里你用 CountDownLatch 或 CompletableFuture.allOf。Go 用 sync.WaitGroup,三个动作:Add(计数+1)、Done(计数-1)、Wait(阻塞到计数归零)。

看本项目怎么用它跟踪所有 consumer:

// data_consumer.go:30 —— 每个 consumer goroutine 启动时注册,结束时通知
func runDataConsumer(ctx context ...) {
    sc.Register()        // 内部 sc.wg.Add(1)
    defer sc.Done()      // 内部 sc.wg.Done() —— 函数返回时 -1
    ...
}

// graceful_shutdown.go:29 —— Register/Done 的实现
func (sc *ShutdownCoordinator) Register() context.Context {
    sc.wg.Add(1)
    return sc.ctx
}
func (sc *ShutdownCoordinator) Done() { sc.wg.Done() }

// graceful_shutdown.go:49 —— 关闭时等全部
go func() {
    sc.wg.Wait()         // 阻塞,直到所有 consumer 都 Done()
    close(done)
}()
⚠️ 评审:WaitGroup 的 Add 和 Done 必须严格配对 每个 Add(1) 必须有且仅有一个 Done()。多一个 Done → panic(负计数);漏一个 → Wait 永远阻塞 → 优雅关闭卡死超时。defer sc.Done() 紧跟在 sc.Register() 后面是最安全的写法(本项目正是如此),保证所有 return 路径都执行 Done。评审规则:看到 Add,立刻找配对的 defer Done。
🔑 为什么 Register 返回 ctx sc.Register() 返回 sc.ctx——一行做两件事:把 goroutine 计入 WaitGroup,同时把取消信号 ctx 交给它。这样 consumer 既知道何时停(ctx.Done()),主人也知道何时等齐(wg.Wait())。优雅关闭的两条腿,一次注册完成。

3. sync.Mutex:保护共享状态

多个 goroutine 同时读写同一个变量会数据竞争(结果不可预测)。Go 不像 Java 有 synchronized 关键字,用 sync.Mutex 显式加锁。看 RecoveryCoordinator.Trigger(recovery.go:44):

type RecoveryCoordinator struct {
    ...
    mu       sync.Mutex    // 互斥锁
    lastRun  time.Time
    inflight bool          // 多个 goroutine 会同时访问 → 必须加锁
}

func (r *RecoveryCoordinator) Trigger(reason string, opts resyncOpts) {
    r.mu.Lock()                    // 进入临界区
    if r.inflight {                // 安全读 r.inflight
        r.mu.Unlock()              // ← 注意:提前 return 前手动解锁
        return
    }
    if time.Since(r.lastRun) < r.cool {
        r.mu.Unlock()
        return
    }
    r.lastRun = time.Now()         // 安全写
    r.inflight = true              // 安全写
    r.mu.Unlock()                  // 离开临界区

    go func() {
        defer func() {
            r.mu.Lock()
            r.inflight = false
            r.mu.Unlock()
        }()
        r.recover(opts)
    }()
}
Go · Mutexmu.Lock() / mu.Unlock(),成对手动调用。没有 synchronized 关键字。
Java · synchronized / ReentrantLockGo 更原始、更显式。
⚠️ 评审:锁的「提前 return」陷阱 Java 的 synchronized 自动释放锁;Go 的 Mutex 不会。每个 return 路径都必须先 Unlock,否则死锁。上面代码每个提前 return 都手动 Unlock 了,但很容易漏。更地道的写法用 defer: 
r.mu.Lock()
defer r.mu.Unlock()   // 函数任意 return 都解锁
...临界区逻辑...
但 defer 会在函数末尾才解锁——如果临界区很长、想尽早放锁(像上面 Trigger 想尽快启 goroutine),就得手动 Unlock。本项目选手动 Unlock 是为了缩短持锁时间(合理),但要逐条 return 检查。评审重点:Lock 之后到函数结束,每条路径是否都恰好 Unlock 一次。

4. sync.Once:只执行一次

看 data_consumer.go:17 / 135:

var schemaWarnOnce sync.Once   // 包级变量

schemaWarnOnce.Do(func() {       // 这段日志只会在整个进程第一次触发时打印一次
    log.Printf("⚠ 行列数与 topic 预期不符，疑似 schema 漂移(同类后续静默)")
})

Once.Do(f) 保证 f 在所有 goroutine 中只执行一次,且并发安全。Java 等价 double-checked locking 单例初始化,但 Go 用 Once 一行搞定。本项目用它做「高频路径告警去重」——schema 漂移每秒触发几百次,只告警首条避免刷屏。优雅。

5. 自测

检索练习
为什么约定「函数第一个参数是 ctx」?取消一个父 ctx 会发生什么?
点开看答案

ctx 是取消/超时的传播载体。第一个参数传 ctx,是为了让调用链任意一层都能感知「该停了」,且支持超时级联。取消父 ctx → 它的所有子 ctx(WithCancel/WithTimeout 派生的)自动取消 → 持有这些 ctx 的 goroutine 的 Done() 全部就绪,得以退出。这就是优雅关闭能一次停全部 goroutine 的原理。

评审练习
某代码:ctx, cancel := context.WithTimeout(...) 后忘了 defer cancel。后果?评审意见?
点开看答案

资源泄漏:ctx 内部关联的定时器/追踪数据直到父 ctx 取消才回收。若这个函数被高频调用(如每个请求派生 ctx),会持续泄漏。go vet 会报错。评审:补 defer cancel()。本项目 recovery.go:78 正确配对。这是 Go 评审的硬性规则,几乎无例外。

辨析题
下面哪个会数据竞争?为什么
// A: 多个 goroutine 各自用独立局部变量
// B: 多个 goroutine 读写同一个 RecoveryCoordinator.inflight,无锁
点开看答案

B。数据竞争 = 多个 goroutine 至少一个在写 同一变量且无同步。A 各自独立变量,无共享,安全。B 的 inflight 被多个 trigger 源(写协程 not exist、probeLoop、HTTP /recovery)并发读写,必须用 Mutex(本项目正是)。Go 数据竞争不报编译错,但结果不可预测;可用 go test -race 检测。
