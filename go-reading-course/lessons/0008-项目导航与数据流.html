1. 先读三样:go.mod → README → main.go

这是通用的「Go 项目侦察三件套」:

  1. go.mod——项目的「身份证」。
  2. README.md——作者自述的意图(比代码先读)。
  3. main.go——程序入口,执行顺序即阅读顺序。

go.mod 怎么读

module github.com/suiteng/tdengine-replicator   // ① 模块全路径(import 前缀)
go 1.21                                         // ② Go 版本

require (                                       // ③ 直接依赖
    github.com/prometheus/client_golang v1.19.0 //    指标暴露
    github.com/taosdata/driver-go/v3 v3.5.5     //    TDengine 官方驱动
)
require (                                       // ④ indirect:被依赖间接拉进来的
    github.com/google/uuid v1.3.0 // indirect
    ...
)
Go · go.modmodule 是全局唯一路径(类似 Maven groupId:artifactId)。require 是依赖,版本精确(非范围)。// indirect=间接依赖。
Java · pom.xml对应坐标+依赖。go.sum 类似 pom 的锁定版本(更严格)。

一眼能看出:这是「用 TDengine 驱动 + Prometheus 指标」的独立小程序,依赖极少(健康信号——Go 项目崇尚少依赖)。

2. 关键结构现象:14 个文件全是 package main

用一条命令看清布局:

$ grep -l "^package main" *.go | wc -l
14

本项目所有 .go 文件都在同一个 main 包。这意味着:

🔑 同包文件之间无需 import,符号直接共享 main.go 调用 loadConfig(),但 loadConfig 定义在 config.go——没有 import 语句。同 package 的所有标识符(函数、类型、变量)互相可见,就像 Java 同一个类里的方法。这是初学者最容易困惑的点:「这函数哪来的?怎么没 import?」——答案:它在同包的另一个文件里。

所以读本项目,把 14 个文件当成「一个巨型 class 的不同段落」即可。Java 架构师可以类比为:每个 .go 文件 = 一个方面的拆分(init 放 init.go、连接放 tdengine.go、消费者放 data_consumer.go…),但它们共享同一作用域。

文件分工速查表(读项目时的「目录」)

main.go
入口。启动顺序:配置→解析→协调器→指标→recovery→建表→起消费者→HTTP→等关闭
config.go
Config/TopicSpec 结构体 + loadConfig()(全环境变量)+ 列位置推导方法
init.go
initSchema():执行 init.sql + 补 repl 列 + 建 topic。含 //go:embed init.sql
parse.go
从 init.sql 解析出 DataTopics/MetaTopics(parseStables)
tdengine.go
连接/查询/拼 INSERT(openConn、queryMaxTS、buildInsert、formatValue)
data_consumer.go
数据面:poll 对端 TMQ → 攒批 → 写本机 → commit(at-least-once)
meta_consumer.go
META 面:消费 DDL/SET TAG,幂等应用,读后写防回声
recovery.go
RecoveryCoordinator:感知本地重建 → reinit + resync(Mutex/inflight/cooldown)
resync.go
回补引擎:FIRST(ts) diff、force-full、single-flight、worker 池
graceful_shutdown.go
ShutdownCoordinator:信号→cancel→WaitGroup 等齐(优雅关闭)
metrics.go
Prometheus 指标 + pushLoop 推 Pushgateway
consumer_cleanup.go
清理 lost 状态的消费者组(防重复实例堆积)
parse_test.go
parse.go 的单测(Go 测试 _test.go 后缀)

3. //go:embed:把文件编译进二进制

//go:embed init.sql     // 编译时把 init.sql 的内容嵌入二进制
var initSQL string       // 运行时 initSQL 就是文件内容,无需挂载文件

这是 Go 1.16+ 的特性。Java 没有直接对应(最接近的是把资源放 classpath 用 ClassLoader 读)。//go:embed 让 tdengine-replicator 单镜像运行时不依赖任何配置文件——init.sql 进了二进制,部署更干净。

4. 主数据流(把前 7 课串起来)

→ 数据流 goroutine 控制/恢复
对端 TDengine (peer) 本机 TDengine (local) ┌─────────────────┐ ┌─────────────────┐ │ 数据 TMQ topic │ │ │ │ META TMQ topic │ │ 写入目标 │ └────────┬────────┘ └────────▲────────┘ │ poll │ INSERT ▼ │ ┌────────────────────────────────────────┐ │ │ data_consumer.go (goroutine × topic×slot) │ │ │ for { select{ ctx.Done / ticker.C / │ │ │ default→Poll } } │ │ │ parseRow → 跳过 repl=true 回声 │ │ │ → 现查源端 tag → append 到 buf │ │ │ → len≥BatchSize 或 ticker → flush │──buildInsert──┘ │ → local.Exec → 成功才 consumer.Commit │ │ (at-least-once) │ └────────────────────┬───────────────────┘ │ 写失败 not exist ▼ ┌────────────────────────────────────────┐ │ recovery.go RecoveryCoordinator │ │ Trigger (Mutex 保护 inflight/cooldown) │ │ → recover goroutine: initSchema + │ │ runResync(FIRST(ts) diff / full) │──补数据──→ local │ + probeLoop (30s 探测 schema) 主动触发 │ └────────────────────────────────────────┘ 控制面:main → sc.cancel() (SIGTERM) ──所有 goroutine 的 ctx.Done() 就绪──→ 优雅退出

用 Java 架构师的话翻译:这是一套「消费-攒批-写入-提交」的管道,类似 Kafka 消费者 + 批量写库;ctx 是总线的取消信号;RecoveryCoordinator 是「自愈协调器」(检测到库被重建就重灌);优雅关闭靠 ctx 树状取消 + WaitGroup 等齐。你完全可以用 Spring 的心智模型理解,只是组件换成 Go 原语。

5. 通用「任意 Go 项目读法」清单

  1. cat go.mod —— 看模块名、Go 版本、关键依赖。
  2. ls *.go / 看目录结构 —— 单 package 还是多 package(多 package 时每个子目录是一个包)。
  3. 找 func main() —— 顺着调用链读,执行顺序即顺序。
  4. 遇到没 import 的函数/类型 —— grep -rn "func 名字" . 找定义(很可能在同包另一文件)。
  5. 看 type Xxx struct —— 摸清核心数据模型(本项目:Config / TopicSpec / pendingRow / 各 Coordinator)。
  6. 看 go func / select —— 摸清并发模型(几个后台任务、怎么停)。
  7. 看 _test.go —— 测试是理解意图的最佳文档。

6. 自测

检索练习
main.go 调 loadConfig() 却没 import config,这合法吗?为什么?
点开看答案

合法。因为 loadConfig 定义在 config.go,而 config.go 和 main.go 同属 package main。同 package 内的标识符无需 import、直接可见。这是 Go 初学者最大的困惑点。跨 package 才需要 import。

理解题
tdengine-replicator 数据面为什么是「at-least-once」?哪一行保证了这点?
点开看答案

因为 写成功后才提交 offset(data_consumer.go:104 consumer.Commit() 在 local.Exec 成功分支里)。写失败 → 不 commit → 下次 poll 重投该批 → 可能重复。所以是 at-least-once(至少一次,可能重复)而非 exactly-once。本项目靠 repl=true 回声标识 + upsert 去重来兜底重复——这是评审时要关注的「重复如何被吸收」机制。

导航题
你想知道 buildInsert 怎么实现的,但你不知道它在哪个文件。最快办法?
点开看答案

grep -rn "func buildInsert" .(或用 IDE 的 Go to Definition)。Go 函数定义都是 func 名字 开头,grep 这个模式秒定位。同包内符号靠 grep,跨包符号靠 import 路径 + 包名。这也是为什么 Go 命名习惯:导出符号(首字母大写)用完整英文、唯一性好,便于全局 grep。
