1. goroutine:轻量线程

第 1 课你见过 go m.pushLoop(ctx)。go 函数调用 = 在一个新 goroutine 里并发执行,当前代码不等待立刻继续。goroutine 是 Go 运行时调度的轻量线程(初始栈几 KB),一个进程跑几万个不夸张。

看 startDataConsumers(data_consumer.go:21)如何起一批 goroutine:

func startDataConsumers(ctx context.Context, cfg Config, ...) {
    for _, spec := range cfg.DataTopics {
        for slot := 0; slot < cfg.ConsumerSlots; slot++ {
            go runDataConsumer(ctx, cfg, spec, slot, m, rc, sc)   // 每个 topic×slot 起一个 goroutine
        }
    }
}
Go · goroutinego f(args)。无返回值(返回了也没人接)。M:N 调度,几 KB 栈。
Java · 虚拟线程Java 21 Thread.startVirtualThread(...)。理念接近 goroutine。
⚠️ goroutine 泄漏 = Go 头号评审点 go f() 起 goroutine 容易,让它退出难。如果一个 goroutine 永远阻塞(比如卡在 consumer.Poll() 或 <-ch),它会一直占着内存和连接——这叫 goroutine 泄漏。评审规则:每个 go f(ctx) 都要能通过 ctx 取消而退出。本项目每个 runDataConsumer 都接收 ctx,并在循环里检查 case <-ctx.Done(): return——正确。

2. channel:goroutine 间的管道

channel 是 Go 并发的「通信」原语。语法 chan T。两种操作:

ch := make(chan string)   // 创建一个传 string 的无缓冲 channel
ch <- "hello"             // 发送(把 "hello" 塞进 ch)
v := <-ch                 // 接收(从 ch 取一个出来,赋给 v)

关键性质:发送和接收都会阻塞,直到对端就绪。无缓冲 channel 像面对面交接:发送方必须等接收方在场,反之亦然。这天然构成同步点。

看 ShutdownCoordinator.Shutdown(graceful_shutdown.go:40)如何用 channel 等待「所有 goroutine 结束」:

func (sc *ShutdownCoordinator) Shutdown(timeout time.Duration) {
    sc.cancel()                          // 1. 发取消信号(通知所有 goroutine 该退出了)

    done := make(chan struct{})          // 2. 建一个传「无数据信号」的 channel(struct{} 不占空间
    go func() {                          //    这是惯用法:用 chan struct{} 当「事件信号」)
        sc.wg.Wait()                     // 3. 等所有 goroutine 调完 Done()(WaitGroup,下节讲)
        close(done)                      // 4. close(ch) 通知「完成了」
    }()

    select {                             // 5. 二选一(见下节)
    case <-done:                         //    所有 goroutine 正常退出
        log.Printf("所有goroutine已正常关闭")
    case <-time.After(timeout):          //    或者超时
        log.Printf("关闭超时，强制退出")
        os.Exit(1)
    }
}

这里 close(done) 是关键:close 一个 channel 后,对它的接收操作立刻不再阻塞、返回零值。所以 <-done 在 close 之前一直阻塞,close 之后立刻通过——这就是「事件通知」模式。

Go · channel语言级一等公民。阻塞式同步。close(ch) 广播「结束」。chan struct{} 当纯信号。
Java · BlockingQueue / CountDownLatchchannel 更万能:能当队列、当锁、当信号。

3. select:多路复用(channel 版 switch)

select 专门处理多个 channel 操作「谁先就绪」。它和普通 switch 完全不同——是给 channel 用的。语法:

select {
case v := <-ch1:        // 如果 ch1 能收到
    use(v)
case ch2 <- x:          // 如果 ch2 能发出
    // ...
default:                // 可选:都不行就立刻走这里(非阻塞)
    // ...
}

select 会随机挑一个就绪的 case 执行;有 default 时,没有 case 就绪就立刻走 default(非阻塞)。

实战 1:非阻塞轮询(data_consumer.go:109)

for {
    select {
    case <-ctx.Done():   // 收到取消 → 收尾退出
        flush()
        return
    case <-ticker.C:    // 定时器到 → 触发攒批刷新
        flush()
        continue
    default:             // 都没就绪 → 不阻塞,往下 Poll
    }
    ev := consumer.Poll(500)
    ...
}

这个循环是「消费-攒批」的核心。default 分支让它不会卡在 select 上——没信号时立刻去 Poll,保持高吞吐。同时 ctx.Done() 保证随时能优雅退出。这是非常地道的 Go 并发模式。

实战 2:取消信号监听

几乎每个后台循环都是这个骨架:

for {
    select {
    case <-ctx.Done():    // 主人喊停,立刻退
        return
    case <-tk.C:          // 定时干活
        doWork()
    }
}

看 probeLoop(recovery.go:120)、diffCheckLoop、recentDiffLoop——全是这个模式。评审 Go 后台任务的第一眼:有没有 case <-ctx.Done(): return。没有 = 泄漏隐患。

4. 评审清单:并发四大问

  1. 每个 goroutine 怎么退出? 找它的循环/阻塞点,确认有 ctx.Done() 或明确的结束条件。
  2. channel 谁负责 close? close 一个 channel 两次会 panic;往已 close 的 channel 发会 panic。评审确认 close 责任唯一(通常是唯一的发送方)。
  3. 有没有 default 误用? select 带 default 是非阻塞;如果你本意是「等待」却写了 default,会变成忙轮询烧 CPU。
  4. 共享变量有没有竞态? 多个 goroutine 读写同一变量必须有保护(下节讲 Mutex)。本项目 RecoveryCoordinator 的 inflight/lastRun 用 Mutex 保护——正确。

5. 自测

检索练习
close(done) 之后,执行 <-done 会发生什么?为什么要用 chan struct{}?
点开看答案

close 后 <-done 立刻返回(零值,struct{} 的零值无意义),不再阻塞。这正是「事件通知」:发送方 close,所有接收方同时解除阻塞。用 chan struct{} 因为它不携带任何数据(struct{} 占 0 字节),纯粹当信号用——这是 Go 惯用法。传数据才用 chan T。

评审练习
下面这段后台循环,评审意见?
go func() {
    for {
        doWork()
        time.Sleep(time.Second)
    }
}()
点开看答案

goroutine 泄漏。这个循环没有任何退出条件——进程不退它就永远跑,且无法被取消。应接收 ctx 并改为 select { case <-ctx.Done(): return; case <-time.After(time.Second): doWork() }。对比本项目 probeLoop 的正确骨架。这类「无 ctx 的 go + 死循环」是评审打回的典型。

辨析题
select 带 default 和不带 default,行为差异是?
点开看答案

不带 default:没有 case 就绪时,阻塞直到某个 case 就绪(适合「等待事件」)。带 default:没有 case 就绪时,立刻走 default 分支(适合「非阻塞尝试」)。本项目 data_consumer 的主循环带 default 是为了「没事干就去 Poll」保持吞吐;而 Shutdown 的 select 不带 default 是为了「死等 done 或超时」。
