OSS PROJECT INTRO · Pulsar 系列第 5 期：架构与源码导读

Pulsar 架构与源码导读：分片日志与分层存储的设计决策

前四期我们做到的是"会用"：认知、跑通、概念地图、接进 Spring Boot。这最后一棒进源码，讲两件更值钱的事——BookKeeper 分片日志凭什么这么设计，以及冷数据凭什么能搬到对象存储。三个设计决策、一条消息从入口到落盘的四站旅程、一张六步读码路线图，外加三段能搬回自己系统的架构师视角。所有代码逐行核对自 release tag v4.2.4（commit 534a635），关键类都给仓库内路径。

01上一期的 send()，埋着本期全部问题

第 4 期我们交付了一条端到端链路：Spring Boot 里 PulsarTemplate.send() 一行调用，订单事件落进 Topic，三份订阅各收各的，毒丸重投耗尽进死信。应用侧短得不能再短，但消息过了 6650 端口之后发生了什么，全是问号：broker 收下消息交给谁？ledger 凭什么敢叫"分片日志"？一卷写满了怎么办？冷数据搬到对象存储，消费者为什么毫无感知？这一期把这些问题全部问掉。

导读策略先立住：不从第一行顺着读，先抓设计决策，再顺着决策找类。类会随版本搬家，决策却相对稳定。Pulsar 最值得学的三个设计决策是：

  • 决策一 · 计算存储分层：broker 是无状态组件，消息与订阅进度全在存储层——官方架构页原话：BookKeeper 是一个分布式预写日志（WAL）系统；
  • 决策二 · 分片日志：一卷 ledger 写满就封卷，条带化摊在多台 bookie 上，故障时不修卷、换新卷；
  • 决策三 · 冷热分离：封卷即不可变，不可变才能整体搬去对象存储，读起来对消费者透明。

跨线提示存算分离与 Kafka 的整体对比、订阅模型与游标原理，daily 线已有专课（文末延伸阅读），本期不换皮重讲；本期讲的是项目本身的设计决策与源码落点。

02决策一：计算存储分层的源码兑现

"broker 无状态"不是口号，是三行事实：消息在 BookKeeper，进度（cursor）在 BookKeeper，broker 名下只剩归属元数据（记在元数据存储里，默认 ZooKeeper，可换 etcd / Oxia）。第 3 期讲过三层楼的分工，现在看它落在哪些类上。Broker 侧的入口是 BrokerService（pulsar-broker/src/main/java/org/apache/pulsar/broker/service/BrokerService.java），客户端要发消息，先由它把 topic 定位到本进程：

// pulsar-broker/src/main/java/org/apache/pulsar/broker/service/BrokerService.java · v4.2.4
public CompletableFuture<Optional<Topic>> getTopic(final TopicName topicName,
        boolean createIfMissing, @Nullable Map<String, String> properties) {
    CompletableFuture<Optional<Topic>> tp = topics.get(topicName.toString());
    if (tp != null) {
        return tp;                          // 命中缓存：归属已定，直接返回
    }
    final boolean isPersistentTopic =
            topicName.getDomain().equals(TopicDomain.persistent);
    // ...建超时 future、系统 topic 策略加载略
    final var cachedFuture = topics.computeIfAbsent(topicName.toString(), ___ -> {
        // 没缓存才真正加载/创建 topic，归属写入元数据存储
    });

每个 topic 同一时刻只归一个 broker 服务（官方架构页：each topic is handled by only one broker），归属就一条记录——"扩容"因此才是起进程这么轻的事。反过来想换种做法会怎样：把消息绑在 broker 本地盘（Kafka 的存算一体路线），扩缩容就得拷数据，故障转移变成数据搬运。两种定价各有所长，但"无状态 + 独立存储层"让你在扩容、故障、冷数据三件事上拿到同一张牌——分层。

读码坐标归属仲裁：BrokerService.getTopic（行 1194 起）；topic 门面：org.apache.pulsar.broker.service.persistent.PersistentTopic——名字里的 persistent 正对应 persistent:// 协议头。整体架构对比见 daily 线 《Pulsar 存算分离架构与 Kafka 对比》。

03一条消息的写入旅程：四站走完主干

第 4 期那条订单事件，进了 broker 之后走四站：入口定位 → 门面校验 → 托管账本 → 落盘 BookKeeper。前三站在计算层，第四站进存储层，调用链概述如下（只看主干）：

# 发布链：send() 的消息从入口到托管账本
Producer.publishMessage()                    // pulsar-broker/.../service/Producer.java
 └─ PersistentTopic.publishMessage()         // .../persistent/PersistentTopic.java
     ├─ 尺寸 / fenced / 最大延迟校验，消息去重检查
     └─ asyncAddEntry(headersAndPayload, ctx)     // 交给托管账本
         └─ ManagedLedgerImpl.asyncAddEntry()     // managed-ledger/.../impl/ManagedLedgerImpl.java
             ├─ executor.execute(...)             // 换到账本专属线程，规避多写者竞争
             └─ internalAsyncAddEntry(op)         // 选账本 + 判封卷
                 ├─ addOperation.setLedger(currentLedger)
                 ├─ currentLedgerIsFull() → setCloseWhenDone(true)  // 满了：这条写完就封卷
                 └─ addOperation.initiate()
                     └─ ledger.asyncAddEntry(...) // OpAddEntry：真正写给 BookKeeper

# 完成链：bookie 写成功之后发生什么（仍在 OpAddEntry.run()）
 ├─ ml.pendingAddEntries.poll()               // 从挂起队列摘下本次写
 ├─ ml.entryCache.insert(entry)               // 塞进缓存：消费者大概率直接从缓存拿走
 ├─ ml.lastConfirmedEntry = (ledgerId, entryId)   // 推进"最新位置"
 └─ closeWhenDone？
     ├─ true  → ledger.asyncClose()           // 封卷，随后 createComplete 开新卷
     └─ false → completeAdd() → cb.addComplete() + notifyCursors()  // 确认生产者、唤醒游标

两个值得停下来的细节：其一，asyncAddEntry 收到消息第一件事是 executor.execute(...)——把写操作切到 ledger 专属线程排队，生产者再多，同一账本上的写入也是串行的；其二，写成功后先插缓存再推进位置——官方说消息一般直接从缓存服务，命中不了才去摸 bookie，读多一跳的成本靠这层缓存买回来。

对应类速查入口 Producer.publishMessage（行 200）→ 门面 PersistentTopic.publishMessage（行 638）→ 托管账本 ManagedLedgerImpl.asyncAddEntry（行 835）→ 落盘 OpAddEntry.initiate / run（行 133 / 243）。行号按 tag v4.2.4 文件，读码时以类名定位为准。

04决策二：分片日志——封卷、条带、换卷

第 3 期讲过"账本按卷归档"，本期补上源码。一卷 ledger 不会一直写下去，currentLedgerIsFull()（ManagedLedgerImpl 行 4431）给封卷定了三个触发条件，任一满足即封：

// managed-ledger/src/main/java/org/apache/bookkeeper/mledger/impl/ManagedLedgerImpl.java · v4.2.4
private boolean currentLedgerIsFull() {
    boolean spaceQuotaReached =
            (currentLedgerEntries >= config.getMaxEntriesPerLedger()
             || currentLedgerSize >= (config.getMaxSizePerLedgerMb() * MegaByte));
    long timeSinceLedgerCreationMs = clock.millis() - lastLedgerCreatedTimestamp;
    boolean maxLedgerTimeReached =
            timeSinceLedgerCreationMs >= config.getMaximumRolloverTimeMs();
    if (spaceQuotaReached || maxLedgerTimeReached) {
        // ...还有最小封卷时间下限判断（minimumRolloverTimeMs），略
    }

这三个条件的默认值都在 conf/broker.conf 里，v4.2.4 的实际取值如下——注意"最小 10 分钟"这个反向条件：条数/尺寸就算到了，卷太新也不许立刻封，防止抖动场景疯狂换卷：

配置键（broker.conf）v4.2.4 默认值含义
managedLedgerMaxEntriesPerLedger50000一卷最多 5 万条，条数到即封卷
managedLedgerMaxSizePerLedgerMbytes2048一卷最多 2GB，尺寸到即封卷
managedLedgerMinLedgerRolloverTimeMinutes10卷龄不足 10 分钟不许封（防抖动）
managedLedgerMaxLedgerRolloverTimeMinutes240满 4 小时必封，时间到即封卷
managedLedgerDefaultEnsembleSize / WriteQuorum / AckQuorum2 / 2 / 2条带集合 E、写份数 W、确认份数 A（生产常调大三副本）

出处以上默认值逐条核对自 tag v4.2.4 的 conf/broker.conf（2026-09-19），standalone 模式另有更小的单机默认，别照抄。满足 A ≤ W ≤ E 的前提下，ledger 的条目被条带化摊到 E 台 bookie 组成的集合上——每条写 W 份、收到 A 份确认才算写成功。

封卷之后的故障故事，源码比文档更直白：bookie 坏了不修卷，createComplete（行 1734）里写下 log.info("[{}] Created new ledger {}", ...)，随即 createNewOpAddEntryForNewLedger()（行 1855）把挂起的写请求整体搬到新卷继续——旧账封存、新账另起，写入路径永不断流。这正是第 3 期"坏盘不修卷"的代码原貌：不可变分卷让副本之间没有"谁是对的"的长期分歧，恢复只需读够 A 份。

05决策三：冷热分离——不可变才有资格搬走

官方分层存储文档有一句值得划线的话：Pulsar 的分段式架构允许积压几乎无上限地增长——但代价会越来越贵，所以旧消息要从 BookKeeper 搬进更便宜的存储。搬走的资格从哪来？还是决策二的馈赠：封卷的 ledger 不可变（文档原话：closed ledger becomes immutable），不可变的东西才能整体复制、搬完即删，不怕中途变更。源码入口在 ManagedLedgerImpl.offloadLoop（行 3739）：

// managed-ledger/src/main/java/org/apache/bookkeeper/mledger/impl/ManagedLedgerImpl.java · offloadLoop · v4.2.4
LedgerInfo info = ledgersToOffload.poll();      // 取一卷待搬的封卷 ledger
long ledgerId = info.getLedgerId();
UUID uuid = UUID.randomUUID();
Map<String, String> extraMetadata = Map.of("ManagedLedgerName", name);
String driverName = config.getLedgerOffloader().getOffloadDriverName();
prepareLedgerInfoForOffloaded(ledgerId, uuid, driverName, driverMetadata)
    .thenCompose((ignore) -> getLedgerHandle(ledgerId))
    .thenCompose(readHandle -> config.getLedgerOffloader().offload(readHandle, uuid, extraMetadata))
    .thenCompose((ignore) -> Retries.run(..., () -> completeLedgerInfoForOffloaded(ledgerId, uuid), ...));

四步语义：登记 offload 中间态 → 拿到 ledger 的只读句柄 → 交给 offloader 上传 → 成功后回写元数据并清理本地副本。谁来实现"搬"这个动作？接口是 org.apache.bookkeeper.mledger.LedgerOffloader（managed-ledger 模块），仓库里 tiered-storage/ 目录下两个实现：jcloud（S3 / GCS / Azure 等对象存储，类 BlobStoreManagedLedgerOffloader）和 file-system（类 FileSystemManagedLedgerOffloader）。搬走之后读怎么办？offloader 同时提供只读句柄（如 BlobStoreBackedReadHandleImpl），游标读到被搬走的卷时按同一套接口透明回源——消费者"如同什么都没发生"（文档原话：Consumers can access offloaded data transparently）。

设计闭环三个决策其实是一条因果链：分层让 broker 无状态，分片日志让存储层只写不可变分卷，不可变又让冷数据有资格整体搬去对象存储——第三步不是独立发明，是前两步的免费赠品。

方法照旧：clone 后 checkout 到发布 tag（git checkout v4.2.4），带着第 2 期跑起来的 standalone 体感，沿调用链自顶向下，每步只回答一个问题：

07架构师视角：能搬回自己系统的三件事

把"状态"搬出计算层的定价账

计算存储分层不是免费午餐：多一层网络跳转、三种角色（broker / bookie / 元数据存储）各自要养，买回来的是扩缩容自由和故障转移的轻。选型用同一把尺：数据规模增长快、节点经常上下线的，分层划算；规模稳定、本地盘够快的，存算一体更省。先算账再分层，别把分层当信仰。

分片日志：一切"流水"类数据的通用骨架

Pulsar 把"只追加 + 按卷封存 + 满卷换卷 + 不可变"做成骨架，代价是读写路径多一层卷管理，换来顺序写吞吐、干净的删除、天然的冷热分离。操作日志、审计流水、事件溯源、行为埋点——凡是"只能追加、按时间冷化"的数据，都值得先想想能不能套这个骨架。卷的粒度就是故障恢复、删除和分层迁移的公共单位，选它比事后补省一个量级。

写路径纪律：单写者 + 专属线程串行

internalAsyncAddEntry 是 synchronized 单线程入口，写入又切到 ledger 专属执行线程——多生产者的并发写，在入口被收敛成账本上的串行追加，bookie 侧只见到顺序写。这和 Netty 的"channel 终身绑定一个线程"（上一系列）是同一个思想的两副面孔：把竞争消灭在入口，后面的每一段都因此不用加锁。写并发组件时，先问一句"我的 ledger 线程在哪"。

08随堂小测

每题点击选项立即反馈 · 共 4 题

1. broker 敢自称无状态，是因为哪两样最重的东西都不在它身上？

  • schema 在 ZooKeeper，客户端连接在 proxy
  • 消息在 BookKeeper，订阅进度（cursor）也在 BookKeeper
  • 消息在元数据存储，连接状态在 proxy

2. v4.2.4 默认配置下，封卷的三个触发条件是？

  • 5000 条 / 2MB / 满 24 小时
  • 满 10 分钟 / 满 2GB / 满 240 条
  • 50000 条 / 2048MB / 满 240 分钟（且受 10 分钟下限约束）

3. 某台 bookie 磁盘坏了，写入路径上的正确剧情是？

  • 封卷换新卷：新 ledger 开在健康 bookie 上，挂起写请求整体搬过去
  • 停写修复坏盘上的 ledger，修完继续写
  • 把该 topic 全量迁回客户端重放

4. offloadLoop 搬运一卷 ledger 的前提，和消费者读到它时的体验分别是？

  • 卷必须正在写入；消费者读到 offload 数据会明显变快
  • 卷已封卷不可变；消费者按同一套接口透明回源，如同什么都没发生
  • 卷已封卷不可变；但消费者必须先迁移订阅才能读到

09思考题（点击展开解析）

思考一：为什么把 ledger 设计成"写满就封卷"，而不是"一直追加一个大文件"？封卷粒度换来了什么、又付出了什么？展开解析 ▾

先看大文件方案的病：一个 topic 一个无限追加的文件，删除只能逐条标记、压缩在后台无止境地跑；单盘坏了整条流水不可用；想搬去别的存储，面对的是一个天天在变的活文件。封卷方案把这三件事一次性解决：卷是公共单位——所有订阅的游标越过整卷，直接删文件，不用逐条清理；卷条带化摊在多台 bookie 上，单盘故障只伤到部分卷；卷不可变，才能整体复制去对象存储。看 offloadLoop 的四步和 createComplete 的换卷，全都是在这个粒度上操作的。代价也要认：卷粒度让故障切换略粗（坏一台 bookie，未封的卷要作废重开，浪费一点写入）；读路径多了"这卷在哪本 bookie"的元数据查找；小 topic 也会周期性产生新卷，bookie 上的卷数随 topic 数水涨船高，所以才有 5 万条 / 2GB / 4 小时这组默认值去平衡。一句话：封卷粒度 = 故障恢复、删除、分层迁移三件事的最小公倍数，选对了粒度，后面全是顺手的副产品。

思考二：如果要把"计算存储分层"抄回自己公司的系统，哪三样东西必须先想清楚？展开解析 ▾

第一样，状态清单：把计算层手里所有状态列出来，逐个决定搬去哪。Pulsar 的清单很干净：消息给 BookKeeper，进度（cursor）也给 BookKeeper，归属关系这种轻元数据给元数据存储——正因为重的全搬走了，broker 才敢无状态。抄的时候最容易漏的是"隐性状态"：本地缓存、连接会话、未 flush 的批量缓冲，出故障时它们都会变成正确性问题。第二样，元数据一致性：分层之后"谁拥有什么"全靠元数据存储仲裁，owner 归属、卷清单、offload 中间态都要能扛住重启与并发（源码里 prepareLedgerInfoForOffloaded 先登记中间态、成功后才回写正式元数据，就是为了崩溃后可判定）。第三样，运维三种角色：broker、存储节点、元数据存储要分别部署、监控、升级，排障还要跨进程看调用链。建议的路径是先做"不可变分卷 + 按卷清理"（收益立现、架构不变），验证卷管理稳定后，再引入独立存储层与对象存储冷化——Pulsar 三层架构是结果，不是起点，别一上来就抄终态。
