01本期读法：从设计决策进源码

读源码最常见的死法是从第一个模块顺序读——那是写代码的顺序，不是读代码的顺序。本期反过来：先抓住三个设计决策，再顺着决策找类。类是易变的，决策是稳定的；理解了"为什么非这么设计不可"，具体代码只是决策的拼写。

三个决策对应三个"为什么"：一致性为什么按数据类型分流（第 02 节）、客户端为什么自己留一套容灾（第 03 节）、2.x 为什么把所有通信归到一条长连接（第 04 节）。随后第 05 节给入口表、第 06 节给三步路线图、第 07 节把源码跑起来、第 08 节把架构启发搬回自己的系统。

源码基准声明 本期以 2.3.x 为纲：一是公司生产的主力版本系，读它即读自己每天在跑的东西；二是 2.x 的社区分析资料最密集，卡住随手能查对照文章。3.x 差异只讲已核实的四处：console 独立部署（8080）、JDK 17 硬下限、persistence 拆分、鉴权默认开启——协议层重构细节不在本期能核实范围，读码时一律以对应 tag 为准。

02决策一：一致性按数据类型分流

第 3 期讲架构时留过一句"第 5 期讲源码时会看到它在代码里怎么落地"，现在兑现。先做一次反面推演：假如像 ZooKeeper 那样，用一套全 CP 协议做注册中心，会发生什么？每一次注册、心跳续约、订阅查询都要走多数派确认——集群 5 台挂 3 台，注册中心直接停摆：新服务注册不上、不健康实例摘不掉、新消费者发现不了。而注册中心是"基础设施的基础设施"，它停摆的每一秒都在向全公司业务链路广播抖动，短暂不可用被放大成全链路事故。ZK 没做错什么，只是它假设自己保管的是不可自愈的账本；拿账本的规矩管电话簿，可用性就被一致性绑架了。

Nacos 的回答是分家，而且分得比"选一边"细：

  • Distro 管"活着才算数"的数据（临时实例，AP）：任何节点都能接任何客户端的请求——客户端不用挑节点连；但集群内部按分片认权威：一个实例的数据只由它所连的节点说了算，写入先落本地、再异步批量同步给其他节点。分区时宁可短暂不一致，也把"能注册、能发现"保住——心跳一停坏记录自愈，第 1 期那句"电话簿丢一页会自己长回来"，代码里的保证就是这条。
  • Raft 管"写下去就必须都在"的数据（配置、持久实例，CP）：写入必须获多数节点确认才算成功，5 台挂 3 台宁拒不写。第 3 期思考题一推演过的"分区两边各记各账"式静默脑裂，在多数派面前从机制上就不会发生——账本宁可不记账，不能记错账。

源码落地总入口：DistroProtocol（naming 模块内，第 05 节入口表对号）；Raft 侧由 consistency 模块承接，读码优先级放后。

03决策二：客户端本地容灾三件套

第 3 期思考题二已把"读旧"的边界拆干净（旧开关风险、静默降级掩盖故障），不重复，只看机制。设计判断一句话：读旧胜过读不得——服务端挂掉的窗口里，消费端继续调存量、重启的应用以旧值起来。三件套各管一段：

  • 内存服务表：ServiceInfoHolder 维护的内存表，订阅的每个服务的实例清单都在这里。服务端推送到达时更新它，业务调用方读的也是它——服务发现的读路径根本不出 JVM，这是 Nacos 挂掉那几分钟里系统还能撑住的直接原因。
  • failover 文件：客户端会定时扫描磁盘上的 failover 开关文件；开关一打开，服务表的读取就切换到 failover 目录里的数据。这是给运维留的人工闸刀——服务端数据整体错乱时，宁可冻结一份已知正确的旧表继续服务。
  • 配置 snapshot 快照：ClientWorker 每拉到一条配置就在本地快照目录存一份。配置中心挂了若是"所有人都起不来"（第 3 期的原话），快照把这句话改写成"所有人以旧值起来"。

三件套有层次：内存表是常态（每次读都走），snapshot 是自动兜底（服务端读不到才走），failover 是人工闸刀（运维主动扳）——自动化与人的判断分开安排，这个分层本身就可借鉴。

04决策三：2.x 把一切归到一条 gRPC 长连接

第 1 期版本演进说 2.x 是"支撑超大规模的关键一跃"，现在把这笔账算清楚。1.x 的世界：HTTP 是无状态的，服务端"记住"一个客户端的办法只有让客户端反复来问。于是每个实例要为每个订阅的服务维持一条挂起的轮询连接、一个心跳定时任务、一个刷新任务——连接数和定时任务数都是 O(实例 × 任务)。100 个实例、每个订阅 20 个服务，服务端就挂着两千条连接、两千个定时器；规模再涨，FD、内存、GC 全线吃紧。

2.x 的解法：一条 gRPC 长连接（就是第 2 期端口账本里的 9848）把注册、心跳、订阅、推送全装进去——连接数降为 O(实例)，变更由服务端主动推、毫秒级触达。更深一层：长连接让服务端第一次有了"连接视图"，连接断开本身就是死亡信号——心跳从应用层的定时任务下沉到连接层的保活，省掉的是心跳任务，换来的是更快的实例死亡判定。配套的断线重连与请求重放（redo）设计：断连期间未送达的注册/订阅请求先记进队列，重连成功后自动重放补齐。

06读码路线图：三步走完主干

入口有了，顺序也有讲究——从最贴近使用者心智的一侧进，最后才碰服务端：

1
走通客户端 naming 链路：从 NamingService 的注册方法进 NacosNamingService，看请求怎么交到 NamingGrpcClientProxy、怎么变成 gRPC 调用、服务端怎么应答；再反方向跟一次订阅推送。预期看懂：一次注册在客户端侧的完整旅程，以及"订阅之后推送回来落在哪"。
2
读 ServiceInfoHolder 的本地表与 failover 判定：推送到达后谁更新内存表、缓存何时落盘、failover 开关文件怎么被定时扫描、开关打开后读取路径怎么切换。预期看懂：第 03 节那套"读旧降级"在代码里的每一行落点。
3
进服务端：长轮询 → Distro。先读 config 模块的 LongPollingService（挂起与 MD5 比对怎么实现），再进 naming 模块的 DistroProtocol 看分片同步。带着三个问题读：这条数据是哪类（临时还是持久）？一致性归属谁（Distro 还是 Raft）？节点挂掉谁兜底（客户端容灾还是集群同步）？预期看懂：一次注册怎么在集群里传播、一条配置变更多久推到客户端。

三个问题正是第 02、03 节两个设计决策的读码版——每碰到一个类问一遍，基本能直接推出这个类为什么存在。

07把源码跑起来：两条路

路线 A：发行包直接跑（最快）。GitHub Releases 下载 nacos-server 2.3.x 的 zip，解压进 bin 目录，一条命令起单机：

:: Windows
startup.cmd -m standalone
# Linux / macOS
sh startup.sh -m standalone

与第 2 期跑 3.x 的两点差异：2.x 的控制台挂在 8848/nacos 下（还没有独立 console）；鉴权默认关闭，首启不需要那套三件套。十分钟内能跑通，适合先建立运行直觉。

路线 B：IDEA 拉源码断点调试。clone alibaba/nacos 后切到 2.3.x tag。JDK 版本以仓库根目录的官方构建说明（BUILDING）为准——主线开发按 17+ 准没错，2.3.x 时代用 JDK 8/11 也能编译。启动跑源码自带的 server 主进程入口（2.x 在 console 模块，对照仓库说明确认），或用 distribution 模块打包后启动。断点下在 InstanceController 的注册方法和 ConfigController 的发布方法，然后用第 2 期那条注册 curl 打进去——注意把 API 前缀从 /nacos/v3 换成 2.x 的 /nacos/v1（v3 是 3.x 才有的路径），参数同名。请求一进断点，调用栈就是一张现成的链路图。

务实建议：先 A 后 B——跑通建立直觉，再下断点验证你从第 06 节路线图里形成的判断。

08可借鉴清单：搬回自己系统的四条

读开源项目源码的终点不是"我看过了"，是"我的系统能偷什么"。四条按可落地难度排序：

  • ① 按数据类型选一致性等级，而非全局一刀切。给自己的数据分型：能自愈的（有 TTL、有事实源可重新同步）配最终一致，不能自愈的（账本类）才上强一致——多数系统里真正需要强一致的数据比想象中少。
  • ② 客户端快照容灾（读旧降级）。凡是被强依赖的中间件，都值得在客户端做"内存态 + 磁盘快照 + 人工开关"，把"中间件挂了"从全面瘫痪降级成短时间读旧值，配上告警。成本是一个目录几个文件，收益是故障时刻的全链路存活。
  • ③ 长连接推送归一。多任务共用一条长连接、断线重连加请求重放（redo），连接数从 O(实例 × 任务) 降到 O(实例)，变更从轮询窗口变成主动推送。自研网关、配置下发、消息通知类组件都适用。
  • ④ 控制面数据面分离。3.x 把 console 拆成独立部署是明确的趋势信号：管理界面独立演进升级，核心进程保持纯粹。自己系统里 admin 后台与核心服务分离，省掉"改个管理页要重启核心"式的互相拖累。

09随堂小测

每题点击选项立即反馈 · 共 3 题

1. Nacos 里 Distro 和 Raft 的分工，哪个说法是对的？

  • Distro 管临时实例（AP，分片权威 + 异步同步），Raft 管配置等持久数据（多数派提交）
  • Distro 管配置数据，Raft 管服务实例
  • 两个协议管同样的数据，互为主备

2. Nacos 2.x 客户端与服务端之间那一条 gRPC 长连接，承载了什么？

  • 只有实例心跳保活
  • 注册和心跳仍走 HTTP，只有订阅推送走 gRPC
  • 注册、心跳、订阅、推送全在这一条连接上

3. LongPollingService（请求挂起 30 秒 + MD5 比对）是哪段历史？

  • 2.x naming 模块的实例心跳处理器
  • 1.x 时代 config 模块的配置变更监听经典实现，2.x 里作为兼容通道保留
  • 3.x 独立 console 的会话管理

10思考题（点击展开解析）

思考一：要给 Nacos 加"配置变更审计"能力（谁、何时、把哪条配置从什么改成什么），应该动哪里？

先看现成度：config 模块本身就有历史版本机制，每次发布都留痕、可回滚——审计要补的增量主要是操作者身份和统一的出口记录。候选扩展点有三层：(a) admin API 入口层——控制台和外部调用都从 admin API 发布配置，在入口统一记录（鉴权开启后操作者身份现成），覆盖面最广、侵入最浅，但拿不到模块内部细节；(b) 模块内变更事件——config 模块发布后有变更事件可订阅，能拿到 DataId 与前后内容，粒度最细，但挂载方式要贴着它的监听/事件体系做，别横插内部类；(c) 插件扩展点——Nacos 预留了 plugin 体系（数据源、trace、加密等 SPI），私有能力尽量以插件形态挂入，升级时零合并成本。为什么不建议直接改 config 模块源码？因为 fork 私有分支的那一刻起，你就背上了"每次社区升级都手动合并侵入改动"的长期债务——Nacos 迭代快、3.x 又是大重构，两三个版本后你的补丁会和主线越漂越远，最终被钉死在旧版本上，连安全补丁都吃不到。外围扩展换来的是"随社区升级的资格"，这个资格比任何单个功能都贵。

思考二：一个新节点加入 Distro 集群后，它负责分片的数据怎么恢复？推演全过程。

分三阶段。阶段一，启动加载：新节点起来后不立即对外宣称就绪，先从本地磁盘恢复自己上次的数据（若有），同时等集群成员关系收敛——其他节点通过成员发现机制看到它，开始向它同步。阶段二，全量校验：新节点向各分片的权威节点发起全量快照拉取（Distro 有 snapshot 全量传输机制），把自己负责分片的数据拉齐校验；期间到达的客户端请求不被拒绝——它先当学习者、不当裁判，这是 AP 系统的恢复姿态：先服务，再对齐。阶段三，加入正常同步：全量完成后标记就绪，进入常规节奏——变更触发的同步任务加周期性校验对账，正式接管自己分片的权威职责。为什么敢"先服务再对齐"？因为临时实例数据有心跳 TTL 兜底：就算恢复期间漏了一条过期记录，心跳一停它就会被摘掉，客户端重新注册会把正确数据顶上来——错误自愈。对照 Raft 新节点：日志回放必须严格对齐提交索引，一步不能少。你看，第 3 期思考题一的那个判断在恢复策略上再次生效：数据能否自愈，决定它配得上哪种一致性，也配得上哪种恢复节奏。

11本期要点与系列收尾

带走这四条：

  • 一致性按数据类型分流：Distro 管临时实例（AP，分片权威 + 异步同步），Raft 管配置等持久数据（CP，多数派提交）——比"全局选一边"精细得多；
  • 客户端容灾三件套：内存服务表（常态）、snapshot 快照（自动兜底）、failover 文件（人工闸刀），共同实现"读旧胜过读不得"；
  • 2.x 一条 gRPC 长连接承载注册/心跳/订阅/推送，连接数 O(实例)、推送毫秒化，连接断开即实例死亡信号；
  • 读码三步路线：客户端 naming 链路 → ServiceInfoHolder 本地表与 failover → 服务端长轮询与 Distro，全程带着"数据哪类 / 归谁管 / 挂了谁兜底"三问。

五期走完一条完整的入门弧线：认识它（电话簿与遥控器）→ 跑起来（curl 冒烟）→ 认概念（三层坐标与一致性分工）→ 接进真实应用（Spring Cloud Alibaba 实战）→ 打开源码（三个设计决策与读码地图）。Nacos 的入门就聊到这里，最新版本和完整文档认准官方文档 nacos.io。课程目录里还有其他开源项目的入门系列，感兴趣可以按需点开。
