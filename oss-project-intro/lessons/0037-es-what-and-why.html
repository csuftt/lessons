OSS PROJECT INTRO · ELASTICSEARCH 系列第 1 期：认识项目

Elasticsearch 是什么：分布式搜索与分析引擎

开源项目入门系列的每个新项目，都从三个问题开始：它解决什么痛点、凭什么活下来、什么场景该选它。上一个项目我们聊完了 Redis，今天开启新项目 Elasticsearch——你在各大网站的站内搜索框后面、公司的日志平台里、安全告警系统里见过它的名字。官方定义一句话：an open source, distributed search and analytics engine，一台开源的分布式搜索与分析引擎，JSON 文档进、相关性排序的结果出。本期不装任何软件，素材全部来自官方文档与官方仓库，每张图都标出处；你带走四样东西：模糊检索的三堵墙、倒排索引这条心智模型的根、一份四方选型对比，外加许可证风波十五年的来龙去脉。

01痛点："查文本"这件事，通用数据库先撑不住

先看三个每个业务系统都会撞上的查询。电商站要搜"无限适配器"，用户只记得商品名里的两三个词；运维要在昨晚至今的十亿条日志里找出所有带 timeout 的报错；运营要对全量订单按地区、品类、时间段自由组合出报表。这三件事的共同点：查询条件不是"某个字段等于某个值"，而是"文本里包含某个词"加"按匹配程度排序"。放进 MySQL 这类关系数据库，很快撞上三堵墙：

  • 模糊匹配只能全表扫描：WHERE name LIKE '%适配器%' 这种前缀带通配符的条件，用不上 B+ 树索引——MySQL 官方手册《Range Optimization》写明，LIKE 能走索引范围扫描的前提是匹配串不以通配符开头。前缀一通配，千万行表就一行一行翻；
  • 日志检索慢且贵：日志的查询形状就是"关键词 + 时间范围 + 任意维度过滤"，全靠索引扫描扛不住写入吞吐，也扛不住并发检索；
  • 聚合分析弱：按词分组计数、按时间分桶统计、多维下钻，关系库要写复杂 SQL 慢慢跑，日志场景还要求写入后秒级可查。

三堵墙的根源是同一句错配：B+ 树为"精确值查找"而生，文本搜索要的是"词级匹配 + 相关性排序"。解法是把文本拆成词、给每个词建一张"词到文档"的目录——这就是倒排索引。2010 年，Shay Banon 在 Lucene 之上包出一层分布式的 JSON 服务，取名 Elasticsearch，后来它成了这个位置的事实标准。

延伸一点：B+ 树为什么救不了 LIKE '%词%'，在每日微课程线的 MySQL 索引专题里有执行计划层面的展开，见文末延伸阅读。

02是什么：一台搜索与分析引擎，不只是搜索

官方产品页的定义值得逐词读（elastic.co/elasticsearch，2026-09 核对）："Elasticsearch is an open source, distributed search and analytics engine built for speed, scale, and AI applications."——开源的、分布式的搜索与分析引擎，为速度、规模和 AI 应用而生。拆成三段：搜索，全文检索带相关性打分；分析，对海量文档做秒级聚合；分布式，天然分片扩容，从笔记本单节点到上百节点的集群是同一套模型。用法上一切都是 JSON：文档以 JSON 进，查询以 JSON 写，结果以 JSON 出。

先看最基本的两步，写入与检索（命令与回显出自官方文档《Index and search basics》，2026-09 核对）：

PUT books
POST books/_doc
{ "name": "Snow Crash", "author": "Neal Stephenson",
  "release_date": "1992-06-01", "page_count": 470 }

GET books/_search
{ "query": { "match": { "name": "brave" } } }

注意 match 查询的形状：查的是 brave 这个词，命中的却是《Brave New World》整本书，还带回一个 _score 相关性分值，按匹配程度排序——LIKE 给不了"哪个结果更相关"这回事。这份能力全部长在倒排索引上，把流程画成一张图：

这张图解释了它为什么快：搜"brave"不再逐行翻表，而是查一次词典直接拿到文档列表；代价是写入时要额外分词、建索引，而且新文档默认要等约一秒才可被搜到（官方文档口径：index.refresh_interval 默认 1s，所以官方叫它"近实时"）。还有一个常见误会要澄清：Elasticsearch 不只是"站内搜索框"。官方产品页把它的角色列成检索平台、向量数据库、分析引擎、地理引擎，四大场景各有天地：

  • 应用搜索：电商商品、内容站、App 内搜索，全文检索加排序过滤的主场；
  • 日志与可观测：ELK/EFK 日志栈的核心就是它——Elasticsearch、Logstash、Kibana 三个字母里的 E 和 K；指标、链路、应用性能监控近年也全并进 Elastic 可观测方案；
  • 安全分析（SIEM）：安全事件与告警数据的检索与关联分析，Elastic 安全方案的地基；
  • AI 检索（RAG）：8.x 起内建向量检索与混合排序，给大模型当外挂知识库的候选之一。

04钩子一：许可证风波——搜索世界的"分家与复合"

Elasticsearch 的许可证故事比 Redis 更早演一遍，两边剧情还惊人地相似（口径核对自 Elastic 官方博客与 Wikipedia，2026-09-19）：

  • 2010—2021 · Apache 2.0 时代：项目以 Apache 2.0 开源十一年，与 Kibana、Logstash 组成 ELK 栈，长成搜索与日志两个市场的事实标准；
  • 2021-01-14 · 改双许可退出开源：Elastic 宣布自 7.11 起改用 SSPLv1 与 Elastic License 2.0（ELv2）双许可，两者都不是 OSI 认可的开源协议，矛头直指"拿 Elasticsearch 做托管服务转手卖钱"的大型云厂商——AWS 首当其冲；
  • 2021-01-21 · AWS 宣布分叉：AWS 用最后一个 Apache 2.0 版本（7.10.2）分叉，因商标问题同年 4 月更名 OpenSearch，Apache 2.0 路线续写；2024-09-16，OpenSearch 被捐给 Linux 基金会旗下的 OpenSearch 软件基金会，走向社区中立治理；
  • 2024-08-29 · AGPL 回归：Elastic 创始人发博《Elasticsearch is Open Source, Again》，宣布新增 AGPLv3 为第三许可选项，自 8.16.0 起生效——AGPLv3、ELv2、SSPLv1 三选一，官方重新自称开源。

对使用者的实际含义：自用、内部部署，三个许可都不限制；要改造后对外分发或做托管服务，AGPLv3 是不开商业授权的唯一选择（注意它的传染性：以它分发则你的衍生代码也须 AGPL 开源）；要彻底开源加社区中立治理，直接看 Apache 2.0 的 OpenSearch。而 2021 年那场分叉，也把"搜索选型"从一道题变成了两道——下一节正面对比。

06什么场景该选它（以及什么场景是错配）

✅ 适合：

  • 全文检索与相关性排序：商品搜索、内容检索、站内搜索框——词级匹配加打分，这是它吃饭的本事；
  • 日志与可观测检索：海量日志的关键词 + 时间范围 + 维度过滤查询，ELK 栈的核心位置；
  • 聚合分析：按词分组、按时间分桶、多维下钻的秒级统计，仪表盘与安全分析的地基。

❌ 错配：

  • 当主数据库：没有跨文档事务、没有 JOIN，账务订单这类"绝对不能错一行"的状态存储交给关系库，ES 只做它的从属索引；
  • 严格强一致的点查：写入默认约一秒后才可搜到（refresh 机制），强一致读不是它的合同；
  • 小数据量的单表查询：百万行以下的搜索框，MySQL 一个 FULLTEXT 索引或普通索引就够，为它养一套 JVM 集群是杀鸡用牛刀。

一条判断捷径：查询形状是"包含某词 + 按相关性排序 + 大规模聚合"的，ES 进候选；查询形状是"精确匹配 + 事务 + 关联"的，留在关系数据库。两个相关主题，每日微课程线已有专题，本系列不换皮重讲，选两篇最相关的作为延伸阅读：

08思考题（点击展开解析）

思考一：MySQL 明明自带 FULLTEXT 全文索引，为什么绝大多数公司要为搜索能力单独养一套 Elasticsearch 集群？是真的需要，还是架构师的洁癖？

这道题的答案不在"能不能"，而在"撑不撑得住、好不好用"。逐层拆。第一层，查询能力的天花板：MySQL FULLTEXT 提供关键词匹配，但相关性打分模型简单可调参数少，而 ES 的打分、词条加权、模糊容错、同义词、跨字段组合检索（bool 查询）是一套可编程的检索语言，业务搜索做到"用户输入两个错字也能找到商品"这一步，差距就拉开了。第二层，负载形状的冲突：搜索负载是"写入持续 + 查询突发 + 聚合重算"，和业务库的事务负载共用一个实例，慢查询互相拖累；ES 独立部署等于给检索负载做了资源隔离，扩容也独立。第三层，分词生态：中文分词在 ES 侧有成熟的 ik 等插件，MySQL 的 ngram 分词是"暴力二元切分"，索引膨胀且语义弱。第四层，数据规模与聚合：亿级文档的分组统计、时间分桶，ES 的聚合是倒排加列式优化的专用引擎，关系库跑同类 SQL 要扫大量行。第五层，数据同步的成本才是真正的门槛：单独养 ES 意味着要维护"业务库到 ES"的同步链路（binlog 订阅或双写），这是一笔实打实的运维账。所以结论是一个决策框架：数据量小、检索要求浅，FULLTEXT 就是正解，上 ES 是过度设计；检索是产品核心体验、或日志体量上来了，独立搜索集群不是洁癖，是分工。判断点不在"要不要搜索"，在"搜索在你的系统里是不是一等公民"。

思考二：Elasticsearch 官方自称"近实时"——新文档写入后默认约一秒才可被搜索到。这一秒从哪来？什么业务会被它坑到，又该怎么绕？

先把机制说清楚（细节第 3 期展开，这里建立直觉）。ES 写入流程是"先写内存缓冲与事务日志，攒一批生成一个不可变的索引段（segment），段打开后才能被检索"——把"可检索"这个动作批量化的就是 index.refresh_interval，默认 1s，官方文档原话是"新数据多久变为可搜索，默认 1s"。为什么要攒批？因为每来一条文档就重建一次可检索结构，成本会高到写入吞吐崩掉；这一秒本质是"搜索可见性"和"写入吞吐"之间的交易，ES 选择了吞吐。谁会被坑？三类：其一，写后立即读的场景——用户提交表单后立刻搜索自己的内容，搜不到就提 bug，这是 ES 新手最高频的"事故"；测试脚本插入数据马上断言查询结果，同样会闪失败。其二，"文档存在性"当锁用——有人拿"搜到就算存在"做幂等判断，一秒窗口内重复请求全部穿透，这类用法从根上就不该放在搜索侧，强一致判断属于数据库。其三，监控告警的时效期待——日志从写入到可查天然带着这一秒多的延迟，秒级 SLA 的告警要另想办法。怎么绕？官方给的旋钮是把 refresh_interval 调小甚至调用带 refresh=true 的接口强制刷新——但每一下刷新都有代价，高频刷新会显著拖慢写入，把默认值改回去的人很快会把改回来。正确姿势是接受这一定位：搜索与日志分析天然容忍秒级延迟；要"写完立刻准"的数据，根本不该只存在 ES 里。

09本期要点与下期预告

带走这五句话：

  • Elasticsearch = 开源的分布式搜索与分析引擎——JSON 文档进、相关性排序的结果出（官方口径）；
  • 它解决"查文本"的痛点：倒排索引让 LIKE '%词%' 式的全表扫描变成查词典，附带秒级聚合；
  • 不只是搜索：应用搜索、日志可观测（ELK 核心）、安全分析、AI 检索（RAG）四大场景；
  • 数据面：77.9k Stars、财富 100 强超 75% 使用、350+ 集成（2026-09-19 核对，官方口径）；许可证风波：2021 年 SSPL/ELv2 分家出 OpenSearch，2024 年 AGPL 回归三许可任选；
  • 版本基准 9.5.4（GitHub Latest，2026-09-15）；选型捷径：查文本 + 相关性 + 聚合找它，事务 + 强一致 + 关联查询留给关系库，别拿它当主库。
