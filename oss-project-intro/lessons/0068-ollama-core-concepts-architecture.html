一条命令的背后：Ollama 核心概念与整体架构

上一期我们五分钟把它跑了起来：装好软件，一条 pull 拉下模型，一条 run 开始对话。用是会用 了，但一条命令的背后究竟站着谁？本期把这条命令拆开：命令行与服务怎么分工、模型存放在哪、GGUF 量化档位怎么读、Modelfile 怎么写、本地接口和 OpenAI 兼容层什么关系、显存和上下文谁来管。本期结束，你能自己画出它的分层架构图，还能亲手做出一个带人设的自定义模型。版本口径：全部事实锚定 v0.34.2（GitHub Latest，2026-09-15 发布；2026-09-20 核对，更新的 v0.34.3 当时仍挂 pre-release）。

01回顾与转场：四条命令背后的三个问号

先接上期的进度：安装、ollama pull 拉模型、ollama run 开对话，再加 ls、ps、rm 做日常管理——四组命令，一个能跑大模型的本机环境就齐了。会用是会用了，但一条命令的背后究竟站着谁？上期结束时应该留下三个问号：模型拉下来放在哪、是什么格式？对话是谁在算，Ollama 自己吗？除了命令行，程序怎么调它？这三个问号，正好对应本期要拆的三层：模型管理层、推理引擎层、接口封装层。

02整体架构：三层分工，谁也不越界

Ollama 的架构可以画成三层。第一层是命令行入口：你敲的 run、pull、ls，由这一层接收并转达，对应仓库里的 cmd 目录。第二层是本机服务，整个项目的管家：默认监听端口 11434、只绑本机回环地址，负责模型下载登记、加载调度、对外接口——模型管理的一切杂活都在这层。第三层是推理引擎：真正逐字算出回答的部位。官方 README 的 Supported backends 一节写得明白，引擎是 Georgi Gerganov 创立的 llama.cpp 项目；Apple Silicon 平台上另有 MLX 引擎可选（官方开发文档口径，macOS arm64 默认启用）。

这个分层的妙处在于各层可独立进化：引擎升级你无感，换个模型只是换文件，命令和接口一条不变。Ollama 自己几乎不做矩阵运算，它做的是工程封装——把"跑大模型"里脏活累活全包了，这和 Docker 之于容器是同一种角色。加速硬件的感知也在服务层完成：启动时探测 CPU 与 GPU，调度器读驱动上报的显存来决定模型放卡上还是内存里；NVIDIA 走 CUDA（算力 5.0+、驱动 550+）、AMD 走 ROCm 7、Mac 走 Metal，另有 Vulkan 兜底，环境变量可指定用哪张卡。

把三层串成一次真实的旅程：敲下 ollama run mario，命令行把请求交给本机服务；服务先查登记册，模型不在显存里就调度引擎把它加载进来，参数与提示模板一并就位；随后引擎逐字生成，回答流式吐回终端；五分钟没人说话，服务再把它请出显存。整条链路里命令行是嘴，服务是脑，引擎是手——本期剩下的篇幅，就是把这三件事各自拆开看。

03模型放在哪：一个目录、两样东西

官方 FAQ 给了默认路径：macOS 为 ~/.ollama/models，Windows 为 C:\Users\%username%\.ollama\models，Linux 标准安装为 /usr/share/ollama/.ollama/models；想搬家，把环境变量 OLLAMA_MODELS 指到新目录即可（Linux 下注意给 ollama 用户读写权限）。目录内部是两样东西：manifests（清单）记录每个模型名字由哪些层组成，blobs 按内容摘要存实际数据——权重、模板、参数都各是一个分片。这与容器镜像 Registry 的分层思路同源：上期 pull 时第一行输出 pulling manifest，拉的就是这份清单；基座层已存在时直接复用，所以 create 自定义模型才可能秒级完成。

管家层的日常就围绕这些数据展开，可归纳为四本账：拉取与删除（pull/rm）、登记与查询（ls 列家底，show 看档案）、加载与调度（请求来了装进显存或内存）、卸载回收（默认驻留 5 分钟，ollama stop 立即请出）。

04GGUF 与量化：55 GB 怎么塞进 8 GB 显存

拉下来的模型为什么开箱即跑？因为它是 GGUF 格式——GGML 官方规范为推理设计的单文件格式：单文件分发、支持 mmap 内存映射加载、信息自包含，网络结构、分词器、权重全在一个文件里。但原始权重动辄几十 GB，消费级显卡装不下，接下来靠量化：把高精度权重压成低比特。档位信息就写在模型 tag 名里，形如 12b-it-q4_K_M——规格 12B、指令微调、Q4_K_M 量化，选型先读名字。

档位什么做法体积参照（gemma3 库页）取舍
q4_K_M4 比特为主混合量化12b 档 8.1 GB默认甜点档，平衡之选
q8_08 比特量化介于 q4 与 fp16 之间更贴原精度，显存富余再上
fp16 / bf16半精度不量化27b 档 55 GB上限档，消费级卡难装
qat量化感知训练1b 档 1.0 GB官方压好的 Q4，质量更稳

规律一句话：比特数越低体积越小、损耗越高。体积均取自 ollama.com/library/gemma3/tags 页各 tag 标注（2026-09-20 核对）。导入自家权重也走 GGUF：Modelfile 里 FROM /path/to/file.gguf（分片文件用通配符 model-*.gguf），官方提醒导入时不做量化，先用 llama.cpp 的 llama-quantize 压好。为什么坚持单文件？本地场景没有集群镜像分发的问题，痛点是"别再让我配环境、装依赖"——一个文件拷过去就能跑，对普通用户才是真友好；这也是它和 PyTorch 生态 safetensors（只有权重、配置另配）定位的分岔。

来源：github.com/ggml-org/ggml/blob/master/docs/gguf.md 截图（2026-09-20）——GGUF is a file format for storing models for inference with GGML；Specification 一节：Single-file deployment、mmap compatibility、Full information 等设计目标。

05Modelfile：五步做出一个"马里奥模型"

自定义模型不用训练。官方定义：Modelfile 是 "the blueprint to create and share customized models"，创建与分享自定义模型的蓝图。五条常用指令：FROM 指定基座（唯一必填，也支持 GGUF 与 Safetensors 目录）、PARAMETER 调运行参数、SYSTEM 一句话定人设、TEMPLATE 提示词模板（一般沿用基座）、MESSAGE 预置对话示范。下面五步全部对照官方文档与示例（2026-09-20 核对）。

第一步，写配方——内容逐字取自官方 Modelfile 文档示例：

# Modelfile
FROM llama3.2
PARAMETER temperature 1
PARAMETER num_ctx 4096
SYSTEM You are Mario from super mario bros, acting as an assistant.

第二步，create 建模——基座层已在本地直接复用，只写新清单，秒级完成：

$ ollama create mario -f ./Modelfile
gathering model components
using existing layer sha256:...
writing manifest
success

第三步，run 验证人设——权重还是那个基座，变的只是系统提示和两个参数：

$ ollama run mario
>>> 用一句话介绍你自己
It's-a me, Mario! ...（回答带标志性口吻，示意转写）

第四步，/api/chat 看协议——往本机 11434 端口发对话请求，答案在 message.content，done_reason、eval_count 等字段是结束原因与计时报表；stream 缺省为 true，逐块流式返回：

$ curl http://localhost:11434/api/chat -d '{
  "model": "mario",
  "messages": [{"role": "user", "content": "Hi"}],
  "stream": false}'

第五步，show 验收——量化 Q4_K_M 继承自基座，temperature 1 与 num_ctx 4096 来自配方，一次看全两层各自贡献了什么；ollama show --modelfile 还能导出任意模型的完整配方。

06API 双轨：原生全功能，兼容零改造

README 原话："Ollama has a REST API for running and managing models." 官方 Python、JavaScript 库一行安装直连同源接口。管理类操作（show、pull、ps、create）只在原生 /api/* 里有；同时服务还开着一个 OpenAI 兼容层，路径前缀 /v1，覆盖 chat completions、completions、embeddings、models、responses 等端点——官方明说这是 OpenAI API 的一个子集，个别字段（如 logprobs、tool_choice）不支持。

$ curl http://localhost:11434/v1/chat/completions \
  -H "Content-Type: application/json" \
  -d '{"model": "mario",
       "messages": [{"role": "user", "content": "Hi"}]}'

返回直接就是 OpenAI 格式，答案在 choices[0].message.content；本地调用无需密钥，官方文档原话是 API key "required but ignored"（必填但被忽略）。一个高频坑：OpenAI 协议没地方设上下文长度，官方给的解法正是上一节的 Modelfile——用 PARAMETER num_ctx 建一个新模型名再调它。Anthropic 协议的客户端同样有兼容入口；云端侧，ollama.com 提供同形接口（需 API key），本地与云端两条路官方都铺好了。

来源：github.com/ollama/ollama/blob/main/README.md 截图（2026-09-20）——REST API 一节含 /api/chat 的 curl 示例（model 为 gemma4）与 Python 库 pip install ollama 示例。

07运行参数：四个数字管住服务

  • 11434：本地服务默认端口，只绑本机回环地址，OLLAMA_HOST 可改；
  • 4096：默认上下文长度（tokens），三种改法——环境变量 OLLAMA_CONTEXT_LENGTH、会话里 /set parameter num_ctx、请求 options 传 num_ctx；并行请求会按倍数放大显存占用，官方 FAQ 有明说；
  • 5 分钟：模型默认驻留时长，请求参数 keep_alive 可调（支持时长字符串、秒数、负数常驻、0 立即卸载），服务端 OLLAMA_KEEP_ALIVE 统一设默认值；
  • 5.0+：NVIDIA 最低算力档（驱动 550+），AMD 需 ROCm 7 驱动，Apple 经 Metal 加速，Vulkan 默认兜底。

09思考题（点击展开解析）

思考一：模型库用"清单 + 内容寻址分片"的布局，而不是每个模型一个大文件，换来了什么？

至少三笔账。第一，去重。同一个基座被多个自定义模型引用时，权重分片只有一份，清单各自指向它——所以 ollama create 才敢号称秒级：不下载、只写清单。第二，增量与校验。每个分片按 SHA256 摘要命名寻址，下载中断可续、内容天然防篡改，pull 时的 verifying sha256 digest 就是在做这件事。第三，组合自由。权重、模板、参数、许可各是一层，改提示模板不必动几百 GB 的权重，新版本模型很多时候只是换清单指向新分片。这套思路与容器镜像、Git 对象库同源：内容寻址 + 分层清单，是"可复用分发"的通用解。理解了它，再看 Docker 镜像、OCI 制品乃至 Nix，都是同一个味道。

思考二：既然有 OpenAI 兼容层，什么时候还该用原生 /api？反过来呢？

两边的甜点位不同。选兼容层的场景：代码库已经压在 OpenAI SDK 上、要本地云端两套后端随时切换、或给第三方工具（多数只认 OpenAI 协议）接本地模型——零改造是它唯一的也是足够的理由。但记住官方口径它是子集：logprobs、tool_choice、部分响应语义不在覆盖内，重依赖这些的应用会踩空。选原生的场景：需要管理操作（pull、show、ps、create、delete 兼容层都没有）、要 keep_alive、num_ctx、think 这类 Ollama 特有参数的细粒度控制、或要结构化输出与工具调用的完整语义——官方 Python、JS 库走的就是这条路。一句话捷径：应用原型选兼容，深度集成选原生。顺带一提，Anthropic 客户端也有兼容入口，第 4 期实战会各接一遍。
