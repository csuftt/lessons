OSS PROJECT INTRO · ETCD 系列第 4 期：实战场景

etcd 实战场景：服务发现与配置管理怎么落地

上一期我们铺完了 etcd 的十块积木与三层楼：revision、watch、lease 你都叫得出名字了。这一期让它们上岗干活——亲手做出两个端到端最小系统：其一，服务注册与发现，实例启动申请租约、把地址写进前缀目录、心跳续约，进程被杀不清理、15 秒内自动摘除，消费方 watch 前缀实时感知上下线；其二，配置管理，改一条配置，订阅实例即时收到推送热更新，顺带看看它比轮询好在哪。客户端主用官方 Go clientv3（文档覆盖最全），Java 受众的 jetcd 坐标与对照一并给全。全文基于 etcd 3.7.x（v3.7.1，2026-07-23 发布）与 jetcd 0.8.7（2026-08-27 发布，2026-09-19 于 GitHub Releases 与 Maven Central 复核），命令与回显逐条对照官方 v3.7 文档。

🧩 分布式键值存储 · Go · Apache-2.0 📦 基于 etcd 3.7.x（3.7.1）· clientv3 / jetcd 0.8.7 📅 2026-09-19 · 第 4 期 ⏱ 预计阅读 15 分钟

01场景与蓝图：同一个 etcd，两种经典用法

微服务上线后马上会遇到两件事：服务实例上上下下，调用方怎么找得到活着的实例；一份配置改了，怎么让所有实例即时生效。这两件事恰好各占 etcd 的一块积木：前者靠 lease（实例的生死线）+ watch（上下线广播），后者靠 watch（配置推送）+ MVCC（改坏了可回溯）。第 3 期的两个钩子，在实战里都会给你答案。两条线的战场如下图：

全程四条目标，做完一条勾一条：

  • ① 注册：实例启动申请 15 秒租约，把地址写进 /services/order/ 前缀目录，keepalive 持续续约；
  • ② 发现：消费方启动拉一次前缀快照，然后 watch 前缀，实例上下线实时知道；
  • ③ 自愈：直接杀掉一个实例进程（不给优雅下线机会），15 秒内键自动消失、消费方收到 DELETE 事件；
  • ④ 热更新：改一条配置，订阅实例即时收到推送，对比轮询的延迟差距。

分工提醒本期只演示"用 etcd 怎么做"。租约续约语义在分布式锁场景的同源用法属于跨场景话题，延伸阅读见第 05 节与每日微课程线，原理不换皮重讲。

03场景一（上）：注册——lease 就是实例的生死线

注册的键有讲究：前缀当目录，末段当实例号——/services/order/inst-1，值就是实例地址。前缀目录等于服务的花名册，这为后面"按前缀订阅"铺了路。注册分三步，代码几乎是官方示例的原形：

cli, err := clientv3.New(clientv3.Config{
    Endpoints:   []string{"localhost:2379"},   // 第 2 期起的单成员集群
    DialTimeout: 5 * time.Second,
})
if err != nil {
    log.Fatal(err)
}
defer cli.Close()

// ① 申请 15 秒租约（官方 Grant leases 示例注释：# grant a lease with 60 second TTL）
resp, err := cli.Grant(context.TODO(), 15)
if err != nil {
    log.Fatal(err)
}

// ② 注册键挂上租约：租约在，键在
_, err = cli.Put(context.TODO(), "/services/order/inst-1",
    "10.0.4.11:8080", clientv3.WithLease(resp.ID))

第三步是心跳——KeepAlive 返回一个续约应答通道，官方示例同样写成"起循环读通道"：

// ③ keepalive 心跳续约：客户端活着，租约就一直被续
ch, kaerr := cli.KeepAlive(context.TODO(), resp.ID)
if kaerr != nil {
    log.Fatal(kaerr)
}
for ka := range ch {
    log.Println("租约已续，当前 TTL:", ka.TTL)
}

实例 inst-2 照抄一份（各申请各的租约）。跑起来后，用第 2 期学过的命令看花名册——正是官方文档 get --prefix 的回显格式：

$ etcdctl get --prefix /services/
/services/order/inst-1
10.0.4.11:8080
/services/order/inst-2
10.0.4.12:8080

为什么键必须挂租约？如果用普通 put 注册，进程崩溃后键会永远躺在那——花名册上全是"幽灵实例"，消费方调过去就是超时。挂上租约后，键的生命周期和进程的生命周期被 etcd 绑定：客户端持续续约则键在，客户端死了续约停止，TTL 一到服务端自动删键。

04场景一（中）：发现——get 是快照，watch 是直播

消费方要维护一份"活着的实例列表"，姿势是两段式：启动先 get 前缀拿全量快照，再 watch 前缀收增量。只 get 不 watch，列表会过期；只 watch 不 get，错过的上线补不回来。watch 的代码就是官方前缀订阅示例的原形：

// 快照：全量拉一次前缀（WithPrefix 等价于 etcdctl get --prefix）
getResp, err := cli.Get(context.TODO(),
    "/services/order/", clientv3.WithPrefix())

// 直播：订阅前缀，之后每次上下线都会从通道里冒出来
rch := cli.Watch(context.Background(),
    "/services/order/", clientv3.WithPrefix())
for wresp := range rch {
    for _, ev := range wresp.Events {
        log.Printf("%s %q : %q", ev.Type, ev.Kv.Key, ev.Kv.Value)
    }
}

这段代码里藏着第 3 期钩子二的答案：Watch 只用了 clientv3.WithPrefix() 一个选项，客户端什么都没做，事件却按全局 revision 的顺序送上门——服务端靠那把全局流水号给所有事件排队。watch 通道里的事件长这样（打印格式与官方示例一致）：

PUT "/services/order/inst-1" : "10.0.4.11:8080"
PUT "/services/order/inst-2" : "10.0.4.12:8080"

命令行等效验证（终端 A 挂起，终端 B 注册实例，A 瞬间打印——官方 watch 原样行为）：

$ etcdctl watch --prefix /services/
PUT
/services/order/inst-1
10.0.4.11:8080

口径备注事件类型枚举就是 PUT 与 DELETE 两种（官方 watch 示例的预期输出注释即此格式）；DELETE 事件的 Value 为空。至此目标①②达成。

05场景一（下）：进程被杀，15 秒内自动摘除

最考验注册中心的是不告而别：实例被 kill -9、机器断电——没有任何机会执行"注销代码"。租约的价值此刻全兑现：续约停止 → TTL 倒计时走完 → 服务端主动删键并派发 DELETE 事件。全程不需要任何一方写"清理逻辑"。时间线拉出来看：

$ kill -9 <inst-1 进程号>     # 模拟宕机：不给优雅下线的机会

# 消费方 watch 端（≤15 秒内）自动打印：
DELETE "/services/order/inst-1" : ""

# 再看花名册：inst-1 没了，inst-2 还在
$ etcdctl get --prefix /services/
/services/order/inst-2
10.0.4.12:8080

"服务端删键"的语义是官方明写的：lease revoke 原注"foo 已随租约撤销删除"，TTL 自然到期与主动撤销效果相同。比"自己写定时任务扫表清理"好在哪？这就是本期的第一个钩子：

反事实：心跳时间戳 + 定时任务清理

  • 实例定期上报心跳，注册中心另起扫描任务比对"最后心跳时间"，超时删记录；
  • 扫描任务是个新组件——它会挂、会延迟，阈值紧了误删活实例，松了死实例多活一阵；
  • "记录还在但心跳停了"的窗口里，消费方完全无感，调用直接打在死实例上。

etcd：lease 到期，原子完成三件事

  • 存活判定下沉到存储层：TTL 到期，服务端"删键"走第 3 期那条提案流水线，原子完成，没有"删一半"的状态；
  • 删除即事件：所有订阅该前缀的消费方同时收到 DELETE，花名册与真实存活没有窗口差；
  • 零额外组件：心跳由 keepalive 一条流承载，不需要任何人写清理代码。

TTL 不是越短越好：官方文档说明租约有最小 TTL、由应用在 grant 时指定，实际 TTL 不低于该最小值、由 etcd 集群选择，页面上并没有给出具体下限数值（Grant leases 示例注释原文：# grant a lease with 60 second TTL）。演示用 15 秒；生产按"心跳周期 × 容忍次数"定，一次网络抖动就误摘半活的实例。租约续约语义在分布式锁场景是同一套原理的延伸，对照阅读见 每日微课程线第 0009 期 · Redis 分布式锁。目标③达成。

06场景二：配置管理——推送热更新 vs 轮询

配置线更简单：配置是普通键，不挂租约——配置的生命周期跟进程无关，进程全死了配置也该在。变化全在客户端姿势：先 get 补齐当前配置，再从"当前 revision"起 watch，基线与增量无缝衔接：

// ① 先取当前配置：getResp.Header.Revision 是此刻的全局流水号
resp, err := cli.Get(context.TODO(), "/config/order-service")

// ② 从当前 revision 起订阅：中间的写入不会漏，之后的推送不重复
rch := cli.Watch(context.Background(), "/config/order-service",
    clientv3.WithRev(resp.Header.Revision))
for wresp := range rch {
    for _, ev := range wresp.Events {
        log.Printf("%s %q : %q", ev.Type, ev.Kv.Key, ev.Kv.Value)
        // 收到 PUT 即重新加载、应用到运行中的进程
    }
}

命令行验证（终端 A 挂起订阅，终端 B 改配置——A 瞬间收到推送，回显与官方 watch 样例一致）：

:: 终端 B：发布新配置（改线程池大小）
$ etcdctl put /config/order-service "pool.size=64"
OK
:: 终端 A：几乎同时自己打印出——
PUT
/config/order-service
pool.size=64

对比老朋友"定时轮询"，本期的第二个钩子就来了：

维度watch 推送轮询（如每 30 秒 get 一次）
感知延迟写入提交后服务端即刻推送平均半个周期（约 15 秒），最坏一个周期
无效开销无变更时零流量（连接挂着不发数据）绝大多数轮次是重复读
实现负担需处理断线重连与 revision 对齐（见下）看似简单，但"上次读到哪"要自己记账

生产三注意① 先 get 再 watch：重启时先有基线，watch 只管增量；② 断线重连不丢事件：官方文档明确可恢复错误自动重试直到重连，配合全局 revision 排序，补发不乱序；③ 用 WithRequireLeader 包上下文：防止卡在失去 leader 的成员上（官方原文建议）。配置改坏了不慌——第 3 期的 --rev 时间旅行在这里就是"查上一版配置"的凭据，前提是还没被 compaction 压缩。目标④达成。

07随堂小测

每题点击选项立即反馈 · 共 4 题

1. 实例被 kill -9 后，注册键最终由谁删除？

  • 注册中心侧另起的定时清理任务
  • lease 到期后 etcd 服务端删键并派发事件
  • 运维人工调用下线接口

2. 消费方想感知 /services/order/ 下所有实例的上下线，watch 的关键选项是？

  • clientv3.WithPrefix()
  • clientv3.WithRequireLeader()
  • clientv3.WithLease(resp.ID)

3. 官方 Grant leases 示例注释里，grant 的租约 TTL 是多少？

  • 5 秒
  • 60 秒
  • 15 秒

4. "先 get 再 watch"之间恰好有别的写入，会漏事件吗？

  • 会，只能重启后重新全量拉取
  • 不会：从 get 返回的 revision 起 watch，变更按号补发
  • 取决于轮询间隔设多长

08思考题（点击展开解析）

思考一：lease 心跳方案里，"存活判定"的责任在谁？如果改成"实例定期写心跳时间戳、注册中心定时扫描清理"，会出什么问题？

先钉住 etcd 方案的责任划分：存活判定整个下沉到了存储层。客户端只负责一件事——让 keepalive 流不断；TTL 到期后的"删键"由 etcd 服务端执行，而且这不是旁路脚本：它变成提案、多数派确认、revision 加一，应用后派发 DELETE 事件——删除本身是一笔被共识保护、被版本号记账、被 watch 广播的正规写入，这就是"原子完成、没有窗口差"的根源。

反事实方案的故障面有四层。第一层，判定者是新的单点：扫描任务挂了，死实例就永远躺在花名册里，还得给扫描任务再做存活检测，套娃开始。第二层，阈值两难：超时线设紧，一次 GC 停顿或网络抖动就误删活实例；设松，死实例多挂几十秒，请求持续打向死实例。第三层，时间戳依赖时钟：比较"最后心跳加阈值是否小于当前时间"，隐含假设各机时钟大致同步，漂移会直接扭曲判定。第四层最隐蔽：清理动作游离在一致性与广播体系之外——自研清理删掉记录，消费方要么另建通知机制才知道，要么下次读取才发现；而 lease 方案里"键的存在性"与"实例存活"是同一个事实，watch 订阅的就是它。最后说代价：keepalive 意味着常驻连接，TTL 要在"误摘风险"与"摘除速度"之间取舍——etcd 只是把这笔账从"每个应用自己算"收敛成"存储层统一算"。选型时值得记住：凡需要多方对同一事实达成一致，优先把这个事实放进共识存储，而不是在应用层各自模拟。

思考二：watch 断线重连期间发生的变更，凭什么能"补发不漏"？如果补发时历史已被 compaction 压缩，会发生什么？

答案还是第 3 期那把全局尺子。官方 watch 文档写明：请求的 revision 是 0 或未指定时，通道只送达"watch 请求到达之后"的事件；而配合 WithRev 指定起点，服务端会把从那个 revision 之后的所有变更按序补发。为什么可能？MVCC 把每个 revision 的变更都留了档——补发历史与推送新事件在服务端是同一条按号排序的通道，这是全局单调 revision 养活的第二条命（第一条是第 3 期的 watch 排队与时间旅行）。

边界官方也给了明：待补发的历史已被 compaction 压缩时，watch 会被服务端取消，客户端收到 ErrCompacted 错误后通道关闭——离线太久就得重新 get 全量快照、再从新 revision 起订，呼应第 3 期的压缩权衡：留档不免费，留多久是运维规划项。另一个细节是官方建议：watch 的上下文用 WithRequireLeader 包装——所连成员恰好无 leader（如网络分区）时，普通 watch 会静默等不到事件，带标记的 watch 会收到"no leader"错误并关闭通道，逼着重连到健康成员，避免抱着一条死流自以为"没有变更发生"。把三件事连起来——revision 对齐补发、ErrCompacted 触发全量重建、WithRequireLeader 防静默卡死——就是生产级 watch 客户端的最小正确姿势，也是第 5 期读 watch 源码时的三条主线。

09本期要点与下期预告

带走这几条：

  • 临时注册一句话：前缀目录 + lease 挂键 + keepalive 续约——进程在键在，进程亡键亡；
  • 发现 = 快照 + 直播：启动 get --prefix 拿全量，之后 watch --prefix 收增量，事件按全局 revision 排序；
  • 自动摘除不需要清理任务：TTL 到期由服务端原子删键并派发 DELETE，消费方与真实存活没有窗口差；TTL 参考官方示例注释取值（# grant a lease with 60 second TTL），按"心跳周期 × 容忍次数"定；
  • 配置热更新：先 get 补基线，再从当前 revision 起 watch；比轮询少了半个周期的平均延迟，配置历史还能 --rev 回溯；
  • 客户端两条线：Go clientv3 文档最全，以其为纲；Java 用 jetcd 0.8.7（io.etcd:jetcd-core），对照见第 02 节表格。
