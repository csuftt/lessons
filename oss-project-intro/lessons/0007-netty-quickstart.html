OSS PROJECT INTRO · Netty 系列第 2 期：5 分钟跑起来

5 分钟跑起来 Netty：你的第一个回声服务器

上一期我们认识了 Netty 的定位和主从 Reactor 心智模型，这一期把它请下神坛：加依赖、抄官方 Echo Server、启动、用 telnet 连上去发一条消息看它原样回来。全文基于 4.2.18.Final（2026-09-09 发布，官方当前推荐主线；4.1 系仍在长期维护，版本与 JDK 基线差异已分别标注，2026-09-18 于 netty.io 与 GitHub Releases 核对）。跑通判定标准和五个高频翻车点一并给全，跑不通先对照自查，再怀疑人生。

🧩 网络框架 · Java · Apache-2.0 📦 基于 4.2.18.Final（4.1.138.Final 同步维护） 📅 2026-09-18 · 第 2 期 ⏱ 预计阅读 15 分钟

01本期路线与跑通判定

四步路线：查 JDK → 加 Maven 依赖 → 建 EchoServer → telnet 验证。全部走完后你应该满足三条跑通判定，缺一条都算没通：

  • ① 进程不退：main 线程停在 closeFuture().sync() 上阻塞等待，是设计如此、不是卡死；
  • ② telnet 通：telnet 127.0.0.1 8009 能连上不报连接拒绝；
  • ③ 发啥回啥：键盘敲 hello netty，屏幕上看到服务器把这串字符原样送回来。

Echo（回声）服务器是官方入门示例的首选——收什么就回什么，零业务逻辑，恰好把"端口监听、连接接入、数据读写、业务处理"四个环节全部点亮。Discard 示例（收到即丢）更简单，但"看不到回显"对新手不友好，验证闭环还是 Echo 完整。

03Maven 依赖坐标：一把梭 or 分模块

入门阶段直接用聚合包 netty-all，一个坐标把 buffer、transport、codec、handler 全带上：

<dependency>
    <groupId>io.netty</groupId>
    <artifactId>netty-all</artifactId>
    <version>4.2.18.Final</version>
</dependency>

进阶写法是按模块拆开引，依赖树干净、体积可控：核心数据结构 netty-buffer（ByteBuf）、传输层 netty-transport（含 NIO）、编解码 netty-codec、以及聚合了常用功能的 netty-handler（SSL、日志、超时等）。本系列前几期一律 netty-all，讲架构拆模块时再换成清单式。

版本号尾巴别丢：Netty 4.x 的发布版本号一律带 .Final 后缀，写成 4.2.18 会直接 Maven 解析失败；5.0 预览版则是 5.0.0.Alpha5 这种格式。这是新手第二天坑（第一是端口占用）。

04官方 Echo Server 逐段讲：四步引导一台服务器

官方示例（netty.io user guide 与 GitHub example 模块的 io.netty.example.echo 包）主体就一个引导流程。先把全景图看一遍，再逐段抄代码——每一步对应第 1 期主从 Reactor 模型里的一个角色：

第一段：两个线程池，各就各位

EventLoopGroup bossGroup   = new NioEventLoopGroup(1);  // 只管接入，1 个线程足够
EventLoopGroup workerGroup = new NioEventLoopGroup();   // 管读写，默认 2×CPU 核数
try {
    ServerBootstrap b = new ServerBootstrap();          // 引导器：把零件组装成服务器

boss 和 worker 就是第 1 期"主从 Reactor"里的主和从：boss 只干一件事——accept 新连接，然后把连接转交 worker；worker 负责这条连接上之后所有的读写事件。两者交接是框架内部完成的，你的代码只需要声明这两个池子。

第二段：链式配置，一步一句

b.group(bossGroup, workerGroup)                        // 登记两个线程池
 .channel(NioServerSocketChannel.class)              // 用 NIO 的 ServerSocket 实现来监听
 .option(ChannelOption.SO_BACKLOG, 100)              // accept 积压队列上限（握手完成未被取走的连接最多 100 个）
 .handler(new LoggingHandler(LogLevel.INFO))         // boss 通道自己的 handler：打日志做观测
 .childHandler(new ChannelInitializer<SocketChannel>() {
     @Override
     public void initChannel(SocketChannel ch) {     // 每个新连接进来执行一次
         ch.pipeline().addLast(new EchoServerHandler());  // 把业务 handler 挂到该连接的流水线
     }
 });

注意 handler 与 childHandler 的分工：前者挂在监听通道上（通常只放日志），后者挂在每一条新连接上（业务逻辑放这）。写反了是新手第三大坑——业务代码不执行，日志里却一切正常。

第三段：绑定端口，挂住主线程

ChannelFuture f = b.bind(8009).sync();   // 绑定端口并等待完成；8009 是官方示例默认端口
f.channel().closeFuture().sync();       // 阻塞到服务器关闭——这就是"进程不退"的原因
} finally {
    bossGroup.shutdownGracefully();     // 优雅关闭：处理完存量事件再退
    workerGroup.shutdownGracefully();
}

第四段：业务逻辑，总共三件事

@Sharable                                        // 声明"我无状态，可以被多个连接共享"
public class EchoServerHandler extends ChannelInboundHandlerAdapter {
    @Override
    public void channelRead(ChannelHandlerContext ctx, Object msg) {
        ctx.write(msg);                          // 收到什么就写回什么（回声的全部秘密）
    }
    @Override
    public void channelReadComplete(ChannelHandlerContext ctx) {
        ctx.flush();                             // 读事件处理完，把积攒的写一次性冲出去
    }
    @Override
    public void exceptionCaught(ChannelHandlerContext ctx, Throwable cause) {
        cause.printStackTrace();                  // 出错别让异常把线程池打死
        ctx.close();                             // 关掉这条出问题的连接，服务器继续活着
    }
}

一个 TCP 包到达 → worker 线程触发 channelRead → write 把数据挂到出站队列 → channelReadComplete 里 flush 冲刷上线——回声逻辑就这三步。业务 handler 从 ChannelInboundHandlerAdapter 继承并只覆写关心的回调，这是 Netty 编程的基本姿势。

05客户端验证：telnet 连上去说句话

服务器跑起来后，不需要再写 Java 客户端，一个终端工具就够。Linux/macOS 自带 nc 与 telnet；Windows 的 telnet 客户端默认关闭，先花 30 秒打开：

:: Windows 开启 telnet（管理员 PowerShell，任选其一）
dism /online /Enable-Feature /FeatureName:TelnetClient
Add-WindowsCapability -Online -Name TelnetClient~~~~0.0.1.0
:: 图形界面路径：控制面板 → 程序 → 启用或关闭 Windows 功能 → 勾选 Telnet Client

# 验证（所有平台通用）
telnet 127.0.0.1 8009     # 注意：IP 和端口之间是空格，不是冒号
nc 127.0.0.1 8009         # 有 nc 的话更省心，输入即回显

连上后敲 hello netty，每敲一个字符屏幕上立刻回来一个——telnet 是逐字符发包的，所以回显也是一个字一个字地蹦，这是正常现象不是性能问题。

Windows telnet 最迷惑的坑：连上后打字"看不见"（自己敲的字符不显示），但服务器其实收到了也回了。原因是 Windows telnet 默认关闭本地回显。按 Ctrl+] 进入 telnet 命令模式，输入 set localecho 回车，回到会话就能看见自己打的字了。判断"到底通没通"，看的是有没有字符从服务器回来，而不是你能不能看见自己的输入。

06高频报错速查：现象 → 原因 → 解法

现象原因解法
BindException: Address already in use，启动即炸 8009 被占：上一个实例没退干净，或撞了本机其他程序 netstat -ano | findstr 8009 找 PID（Linux：lsof -i:8009），taskkill /PID xxx /F 后重启；或改绑别的端口
Maven 解析失败 / 运行时 NoClassDefFoundError 版本号少了 .Final 尾巴，写成了 4.2.18 补全为 4.2.18.Final；4.x 发布版本一律带 .Final，5.0 预览版是 5.0.0.Alpha5 格式
多个连接互相串数据 / 计数互相污染 带成员变量状态的 handler 被标了 @Sharable 并做成单例，所有连接共用同一份状态 @Sharable 只给真正无状态的 handler（如官方 EchoServerHandler）；有状态就在 initChannel 里每个连接 new 一份
日志出现 LEAK: ByteBuf.release() was not called before it's garbage-collected 入站 ByteBuf 是引用计数的：channelRead 里拿到后既没传递给下游、也没 release，GC 时泄漏探测器抓了现行 保持"引用计数守恒"：要么 ctx.write(msg)/fireChannelRead 把所有权传下去，要么 ReferenceCountUtil.release(msg)；排查加参数 -Dio.netty.leakDetection.level=paranoid
telnet 连上、服务端日志也打了，但屏幕没反应 Windows telnet 默认不开本地回显（见第 05 节） Ctrl+] → set localecho → 回车；或直接换 nc

其中 ByteBuf 泄漏值得多说一句：官方 Echo 示例里 ctx.write(msg) 会把 msg 的所有权转交给出站流水线、写完由框架释放，所以不漏；但你的代码一旦"读了不用又不管"，泄漏就发生了。第 4 期讲 ByteBuf 与内存池时会专门拆这套引用计数机制。

07随堂小测

每题点击选项立即反馈 · 共 4 题

1. ServerBootstrap 的四步引导中，真正让端口开始监听的是哪一步？

  • group(bossGroup, workerGroup)
  • channel(NioServerSocketChannel.class)
  • bind(8009)

2. 服务器启动后 main 线程停在 closeFuture().sync() 上不往下走，这是？

  • 设计如此：事件驱动服务要挂住主线程直到关闭，否则 finally 会把线程池关掉、服务秒退
  • 死锁了，需要重启
  • 端口没绑定成功的表现

3. 下面哪种 handler 可以安全地加 @Sharable 并在多个连接间共享单例？

  • 带一个 int 计数器成员变量、统计每连接消息数的 handler
  • 没有任何成员变量状态、只根据入参做转发的 handler
  • 所有继承自 ChannelInboundHandlerAdapter 的 handler

4. 日志报 LEAK: ByteBuf.release() was not called，最可能的原因是？

  • JDK 版本低于 Netty 基线
  • telnet 没开本地回显
  • channelRead 拿到的 ByteBuf 既没传递给下游、也没调用 release

08思考题（点击展开解析）

思考一：官方 EchoServerHandler 加了 @Sharable 做单例共享，为什么你随手加个计数器版本就出事？

@Sharable 的本质是一份契约声明："我承诺没有任何连接相关的状态，随便共享"。官方 EchoServerHandler 的 channelRead 只做 ctx.write(msg)——不存成员变量、不记上下文，输入输出都是参数和流水线，共享一万份和一份没有区别。而你加了 private int count 之后，这个成员变量就成了"单例的私有账本"：连接 A 的事件线程写一半、连接 B 的事件线程也来写（两个连接可能绑在不同的 worker 线程上），轻则计数互相污染，重则非原子操作下数据错乱。关键是 @Sharable 只是承诺，Netty 不会替你校验承诺的真伪——标了注解，框架就放行共享，出错时没有异常、只有诡异的数据。工程上更稳的默认姿势：入门阶段一律在 initChannel 里每连接 new 一个 handler 实例，创建开销可以忽略；等真正需要省对象、又确认无状态时，再上 @Sharable 单例。

思考二：bind 之后的代码"永远执行不到"，为什么这反而是 Netty 服务器的正确形态？

因为 Netty 服务是事件驱动的长活进程：main 线程的全部职责是"把零件组装起来、按下开关"，然后就该退到一边。真正干活的是 boss 和 worker 线程池里的事件循环——它们在各自的线程上转着，等连接来、等数据到，和 main 线程是平行的世界。closeFuture().sync() 的作用是把 main 挂住：如果去掉这行，main 跑完就进 finally，把两个线程池 shutdownGracefully 关掉，刚出生的服务器立刻死亡——这是"服务器闪退"最经典的原因。这和操作系统里守护进程要"前台挂住"是同一种模式：有生命周期的东西必须有个东西托着它。顺带一提，真正的事件处理永远不发生在 main 线程上——这也意味着 handler 里的代码默认跑在 worker 线程，耗时操作会直接堵住同一条 EventLoop 上的其他连接。这个问题怎么解，正是第 3 期讲 EventLoop 线程模型时要展开的主菜。
