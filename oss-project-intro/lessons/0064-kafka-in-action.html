OSS PROJECT INTRO · APACHE KAFKA 系列第 4 期：实战场景

把订单事件接进 Kafka：spring-kafka 从引入到死信队列

上一期我们铺完了 Kafka 的核心概念：主题、分区、消费者组、副本同步，还有它为什么快。这一期全部落进真实代码——你要亲手做出一个发订单事件的 Spring Boot 服务：一个依赖接入，KafkaTemplate 发 JSON 事件、@KafkaListener 收事件，失败自动换主题重试，耗尽转进死信队列。先说一个反直觉的事实：Pulsar 有官方 starter，Kafka 反而没有——官方姿势就是引入 org.springframework.kafka:spring-kafka 这一个依赖，自动装配全包。从依赖到死信验证，五步端到端。

01需求场景：一条订单事件，三个下游要吃

订单服务下单成功后发布一条订单事件，积分、风控、通知三个下游各自消费，互不拖累；风控处理失败时，消息要能自动重试，重试耗尽转进死信留人工通道。这个场景在 Pulsar 实战期做过同款，本期换成 Kafka 的实现——你会看到两边思路同形、写法各异。

  • 发布方：订单服务用 KafkaTemplate 一行发送，订单号当消息 key，同订单事件天然落进同一分区保住顺序；
  • 消费方：三个下游各起各的消费者组（points / risk / notice），同一份事件每组各得一份——消费者组的分工，正是上一期讲过的概念；
  • 兜底：失败消息换进独立重试主题按节奏排队，次数耗尽转进死信主题 order-events-dlt，主分区全程不被堵。

02步骤①：加依赖——Kafka 竟然没有官方 starter

接 Pulsar 有 spring-boot-starter-pulsar，接 Kafka 呢？没有同名 starter，这不是遗漏而是现状：Boot 官方文档原话是 "Apache Kafka is supported by providing auto-configuration of the spring-kafka project"——类路径上有 spring-kafka，自动装配就生效。坐标只有一个：

$ mvn dependency:tree | grep -E "kafka"
[INFO] +- org.springframework.kafka:spring-kafka:jar:3.3.16:compile
[INFO] |  \- org.apache.kafka:kafka-clients:jar:3.9.2:compile

两个版本都不用写死：Boot 3.5.16 的依赖管理（spring-boot-dependencies BOM）统一给 spring-kafka 3.3.16 和原生客户端 kafka-clients 3.9.2。服务端是第 2 期跑起来的 Kafka 4.3.1（KRaft 模式），客户端 3.9 连服务端 4.3 没有问题——Kafka 官方文档的兼容矩阵（Getting Started → Compatibility）写明：3.x Client 对 4.0+ Server 完全兼容。真想用新客户端，也不用改坐标：在自己工程里用 <kafka.version> 属性覆盖 BOM 值即可，spring-kafka 3.3.x 本身就构建在 kafka-clients 3.9 上。

来源实拍（2026-09）：start.spring.io 依赖面板勾选 Spring for Apache Kafka（MESSAGING 分组，描述原文 Publish, subscribe, store, and process streams of records）——生成的工程里就是上面这个 spring-kafka 坐标。

03步骤②：一份极薄的配置，其余交给自动装配

真正要写的新增配置只有 Kafka 这一节：服务地址指向第 2 期的 KRaft 服务（localhost:9092，本来也是默认值）；生产端把值序列化器换成 JSON；消费端定好组名，再告诉 JSON 反序列化器事件类型和信任的包：

spring:
  kafka:
    bootstrap-servers: localhost:9092
    producer:
      value-serializer: org.springframework.kafka.support.serializer.JsonSerializer
    consumer:
      group-id: points-group
      properties:
        "[spring.json.value.default.type]": com.example.order.OrderEvent
        "[spring.json.trusted.packages]": com.example.order

04步骤③④⑤：建主题、发事件、收事件

服务端建主题，命令和第 2 期跑官方 Quickstart 一模一样：

$ bin/kafka-topics.sh --create --topic order-events --bootstrap-server localhost:9092
$ bin/kafka-topics.sh --describe --topic order-events --bootstrap-server localhost:9092
Topic: order-events PartitionCount: 1 ReplicationFactor: 1 Configs:
Topic: order-events Partition: 0 Leader: 0 Replicas: 0 Isr: 0

演示一个分区一个副本够用；生产按吞吐规划分区与副本。订单事件带订单号当 key，同键进同分区，这条原则马上生效。发布侧，事件本体一个 record，注入 KafkaTemplate 一行发送：

public record OrderEvent(String orderId, String sku,
        double amount, Instant paidAt) {}

public void publish(OrderEvent event) {
    template.send("order-events", event.orderId(), event);  // key=订单号
    log.info("订单事件已投递: orderId={}", event.orderId());
}
// 订单事件已投递: orderId=SO-20260919-0001

注意 send 立刻返回一个 CompletableFuture<SendResult>，里面带分区和位移的回执；要确认就 .get() 阻塞等，官方建议带超时。订单这种不能丢的事件建议拿回执，日志埋点类直接异步。消费侧更短，任意 Bean 的方法标上注解：

@KafkaListener(topics = "order-events", groupId = "points-group")
public void onOrderEvent(OrderEvent event) {
    log.info("积分入账: orderId={}, amount={}", event.orderId(), event.amount());
}
// 积分入账: orderId=SO-20260919-0001, amount=399.0

监听容器自动建好，JSON 反序列化自动完成；方法正常返回即消费成功，容器自动提交位移，抛异常才算失败。失败怎么办——下一节专门引爆。补一句并发放大：spring.kafka.listener.concurrency=3 可以让一个监听开三个消费线程，但并行度上限是分区数——三个分区起步才吃得满三个线程，这正是上一期"分区决定并行度"的现场版。

05钩子：消费挂了，堵住分区等，还是换个主题等？

消费抛异常有两条路，官方文档各自成章。阻塞重试（DefaultErrorHandler）：在原分区原地重试，重试期间这条分区停摆，后面的事件全堵着，配 FixedBackOff 控节奏，耗尽可经 DeadLetterPublishingRecoverer 转存死信。非阻塞重试（@RetryableTopic）：失败的消息搬进独立的重试主题排队，主分区继续消费不堵车，退避节奏由重试主题的延迟天然实现。高并发订单场景，后者从容得多。

故意发一条毒丸——金额为负的订单事件，风控方法直接抛异常。给风控监听挂上注解：

@RetryableTopic(attempts = "4",
        backoff = @Backoff(delay = 1000, multiplier = 2.0))
@KafkaListener(topics = "order-events", groupId = "risk-group")
public void onOrderEvent(OrderEvent event) {
    if (event.amount() <= 0) throw new IllegalArgumentException("非法金额");
    log.info("风控放行: orderId={}", event.orderId());
}

@DltHandler
public void dlt(OrderEvent event) {
    log.info("进死信, 需人工介入: orderId={}", event.orderId());
}

节奏是这样走的：第一次失败，消息进 order-events-retry-0，一秒后再试；再失败进 retry-1，两秒；再失败进 retry-2，四秒；三次重试耗尽，转进 order-events-dlt，@DltHandler 当场喊话。几条硬规则全部出自官方参考手册（Non-Blocking Retries 一章，3.3.16 文档实拍核对）：

  • 默认值：3 次尝试、每次隔 1000 毫秒固定退避；重试主题数 = attempts 减一，默认单分区，由框架自动创建；
  • 命名：默认后缀 -retry-0/1/2… 和 -dlt，可用 retryTopicSuffix / dltTopicSuffix 自定义；
  • 开箱即用：Boot 下直接加 @RetryableTopic 即可，无需额外启用；@DltHandler 不写的话，框架默认只建一个仅打日志的死信消费者；
  • 红字提醒：批处理监听不支持；不能与容器事务混用。

最后验证死信：开第 2 期的控制台消费者从头读 order-events-dlt，毒丸原样躺在里面，字段数值一个没动——补偿、排查、人工修数随取。死信不是垃圾场，是人工通道。顺手用 kafka-topics.sh --list 看一眼服务端：主主题之外，order-events-retry-0/1/2 和 order-events-dlt 已经被框架自动铺好，每个重试主题就是一档延迟的"排队区"，监听它们的消费者组也由框架接管——业务代码里只有注解和两个方法，其余全是框架的事。

$ bin/kafka-console-consumer.sh --topic order-events-dlt --from-beginning --bootstrap-server localhost:9092
{"orderId":"SO-20260919-0002","sku":"TG-01","amount":-1.0,"paidAt":"2026-09-19T07:41:00Z"}

07三个高频坑，开工前过一遍

  • ✅ 消费端用 ErrorHandlingDeserializer 包住 JSON 反序列化：坏消息进来不会让同一条消息反复炸、分区原地打转——官方文档点名的姿势；
  • ❌ 批处理监听挂 @RetryableTopic：参考手册 IMPORTANT 红字写得很直白，非阻塞重试不支持批处理监听；
  • ❌ 指望生产环境自动建重试主题：自动建主题开关生产常被关闭，重试主题又随 attempts 成倍增加，用 NewTopic Bean 显式声明才稳。

三个数字顺手带走：1 个依赖从引入到死信全搞定；3 次默认重试尝试（每次隔 1 秒）；5 个主题是 attempts=4 时整条链的规模（主主题 1 + 重试 3 + 死信 1）。数字背后同一个思想：网络抖动、下游超时这类暂时性故障，重试就能自愈，交给重试主题按节奏慢慢来；金额非法、格式损坏这类永久性故障，试一万次也不会好，尽快请进死信转人工——重试管暂时性故障，死信管永久性故障，毒丸别留在主路上。

08随堂小测

1. Spring Boot 接入 Kafka 的官方姿势是？

  • 引入 spring-boot-starter-kafka
  • 手写 KafkaConsumer 建连
  • 引入 spring-kafka 单依赖，版本交给 Boot BOM 管

2. @RetryableTopic(attempts = "4") 会自动创建哪些主题？

  • 4 个重试主题 + 1 个死信主题
  • 3 个重试主题（retry-0/1/2）+ 1 个 -dlt 死信主题
  • 每个重试主题各配一个死信主题

3. 消费端 JSON 反序列化失败、同一条消息反复炸，该怎么接住？

  • 调大 attempts 多试几遍
  • 换一个 groupId 重新消费
  • 用 ErrorHandlingDeserializer 包住 JsonDeserializer

09思考题（点击展开解析）

思考一：非阻塞重试要为主题数量买单（attempts 减一个重试主题）。什么场景你反而会选阻塞重试？

两层判断。第一看故障概率。下游偶发超时、网络抖动这类瞬时故障一天没几次，阻塞重试原地等一下就过去了，为它养三个重试主题、三套消费者不划算；失败率高、恢复时间不可预期（对端降级、长抖动）的场景，非阻塞的"主路不堵"才开始值钱。第二看顺序敏感度。阻塞重试期间分区停摆是缺点，但反过来它绝不打乱分区内顺序；非阻塞重试把失败消息搬去别的主题，成功路径和重试路径的事件时间线从此分叉，强顺序业务要自己设计"重试完成后再处理后续"的机制。所以低频瞬时故障、分区强顺序的场景选阻塞；高并发、故障常见、顺序可按键局部解决的场景选非阻塞。两条路不互斥，官方文档也讲了组合姿势：外层阻塞兜底小抖动，内层非阻塞接大故障。

思考二：毒丸进了 order-events-dlt 之后呢？一套死信方案还差哪些部件才算闭环？

消息进死信只是"止损"，闭环还差四件事。第一，发现：DLT 没有消费者告警就等于垃圾场，监控要盯 DLT 的积压（lag），进一条就通知到人。第二，诊断：毒丸为什么炸，原始消息、异常栈、重试次数要能对上——非阻塞重试会带 Retry 头，死信排查时就是现场记录。第三，处置：人工修数后重新发布到主主题、走补偿接口、或确认废弃并留档，三种路径按业务定，工具上一个控制台生产者就够。第四，防复发：毒丸多半是上游 schema 变更或脏数据，回溯修复源头才是根治。对照 Pulsar 实战期的 DeadLetterPolicy：消息中间件只负责"把坏消息隔离到固定位置"，隔离之后的发现、诊断、处置、防复发，永远是自己系统的活——这也是"分层兜底"里最底下那层。

10本期要点与下期预告

带走这五句话：

  • 依赖一个就够：spring-kafka 版本交给 Boot 管（3.5.16 → 3.3.16 + kafka-clients 3.9.2），无 starter 是官方现状；
