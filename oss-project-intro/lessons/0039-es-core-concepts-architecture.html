OSS PROJECT INTRO · ELASTICSEARCH 系列第 3 期：核心概念与整体架构

看懂 Elasticsearch：概念地图与整体架构

上一期我们把 Elasticsearch 跑了起来，完成了第一次索引与搜索。但一条文档写进去之后经历了什么？一次搜索为什么能在亿级文档里毫秒返回？本期你带走一张概念地图：索引/文档/mapping 与倒排索引、segment 与 Lucene 的关系、主分片与副本、集群三种角色，再沿着写入路径把内存缓冲、translog、refresh、merge 一次讲透——搞明白为什么搜索叫"近实时"而不是"实时"。源码怎么读留给第 5 期，本期只建立"叫什么、管什么、为什么这么设计"。

01系列地图：概念承重墙期

老规矩先看地图。第 1 期立住了心智模型——分布式搜索与分析引擎；第 2 期把 ES 跑起来完成了第一次索引与搜索；本期是五期里的承重墙：术语体系与整体架构一次铺完。第 4 期实战里每个名词都会变成实打实的一步，第 5 期源码导读沿着本期画好的模块地图往下读。本期结束时你应该能回答两个问题：一条文档写入后经历了什么？一次搜索是怎么变快的？

02术语体系·数据面：索引、文档、字段与 mapping

ES 的术语先记三层递进的关系：索引（index）装文档（document），文档由字段（field）组成，mapping 决定字段怎么存。文档是你写入的一条 JSON 记录，类似数据库的一行；索引是同业务文档的集合，类似一张表。mapping 的官方定义只有一句："mapping 是定义文档及其包含的字段如何存储与索引的过程"——每个字段都有自己的数据类型（text、keyword、integer、date 等），不声明时 ES 会动态推断，生产环境建议显式声明。动手感受一下，两条请求建出本期要用的试验田：

PUT my-index-000001
{
  "settings": { "number_of_shards": 1 },
  "mappings": {
    "properties": {
      "age":   { "type": "integer" },
      "email": { "type": "keyword" },
      "name":  { "type": "text" }
    }
  }
}

请求体逐字取自官方《Explicit mapping》与《Create index》文档样例：mapping 定义 age（integer）、email（keyword）、name（text）三个字段。注意 text 与 keyword 的分工——text 会分词参与全文检索，keyword 整串精确匹配，这对组合是后面倒排索引的主角。number_of_shards 是主分片数，只能在建索引时设定，第 04 节讲为什么。

PUT my-index-000001/_create/1
{
  "@timestamp": "2099-11-15T13:12:00",
  "message": "GET /search HTTP/1.1 200 1070000",
  "user": { "id": "kimchy" }
}
{
  "_index": "my-index-000001",
  "_id": "1",
  "_version": 1,
  "result": "created",
  "_shards": { "total": 1, "successful": 1, "failed": 0 },
  "_seq_no": 0,
  "_primary_term": 1
}

请求与响应逐字取自官方 Index API 文档。回显里的 _shards.total=1 就是这份文档落进的主分片加副本总数（本例 1 主 0 副），文档还没讲到的分片概念已经在这里等你了。

03倒排索引：一本随时能反查的"书的术语表"

搜索引擎的核心数据结构是倒排索引（inverted index）。类比一本书：正排是"第几页写了什么"，你要找"架构"出现在哪，只能一页页翻；书的最后有张术语表——"架构……第 12、58、201 页"，直接翻到。倒排索引就是把这张术语表做进了引擎：文档写入时先分词（text 字段被拆成一个个词项），再登记每个词项（term）→ 包含它的文档列表（posting list）。查询时不再扫描文档，而是查词项、拿列表：

钩子一：为什么 ES 搜索快通用数据库（B+ 树 / LIKE 扫描）Elasticsearch（倒排 + segment + 缓存）
找"包含某词的文档"LIKE 全表扫描或前缀匹配，文档越多越慢词项字典定位词项，直接取文档列表，与数据总量近似无关
读时的并发读写共享可变结构，需要锁或 MVCCsegment 不可变，读完全无锁，随便并发
磁盘访问热数据外的访问落到磁盘小文件成批读，长期驻留文件系统缓存，多数查询是纯内存操作
存储体积通用行存为主不可变文件压缩率高，列存 doc values 让排序聚合也快

四行账合起来就是那句行业直觉：ES 的快是"用写入时的预处理，换查询时的直查"。B+ 树一侧的原理（什么时候走索引、什么时候失效）MySQL 官方文档有详细说明，延伸阅读见：官方文档 · MySQL 索引与 EXPLAIN。

04从索引到分片：index → shard → Lucene index → segment

倒排索引存在哪里？官方《Clusters, nodes, and shards》的口径一句话："每个索引是一个或多个物理分片（shard）的分组，每个分片是一个自包含的 Lucene 索引，装着该索引文档的一个子集"。所以层级是这样：你叫的"索引"是逻辑名，它的每个主分片（primary shard）是一个独立运转的 Lucene 实例，Lucene 索引内部由一段段segment组成——倒排索引就住在 segment 里：

官方还有两条硬规矩："索引里每个文档属于一个主分片"——文档落谁家由路由公式决定（默认对文档 ID 取哈希再对主分片数取模，所以主分片数改不了：一改，所有文档的归属全乱，等于整库搬家）；"副本数可以随时改"——副本只是拷贝，加副本只影响容灾能力与读吞吐，不动数据分布。分片副本在集群里由 ES 自动均衡分布，这就是"扩容加节点、数据自动摊开"的由来。

节点角色干什么一句话记忆
master 节点管集群状态：建删索引、决定分片放哪个节点、故障时重新分配分片集群的"管理员"，不扛数据流量
data 节点存分片、执行索引与搜索的数据操作（CPU/内存/磁盘大户）集群的"仓库名工人"
coordinating 协调节点接客户端请求：写入转发给主分片、搜索扇出到各分片再归并结果每个节点默认都是协调者，请求到谁谁协调

角色是"职责"不是"机器"：小集群一个节点身兼三职，生产集群才把 master 候选与 data 拆开部署。9.x 的完整角色表（ingest、ml、transform 等）见官方 Node roles 文档。

把上面的术语拼成一张架构图——这是本期的主图，第 4 期实战和第 5 期源码都会回到它：

06写入路径：为什么是"近实时"而不是"实时"

把第 02 节那条 _create 请求放大，一条文档在主分片内部走四步：① 进内存缓冲（indexing buffer），同时追加一条 translog 操作日志；② 缓冲攒够（默认每 1 秒）执行 refresh，生成一个新 segment——文档从此可被搜索；③ 主分片把操作并行转发给所有 in-sync 副本，全部确认后才向客户端回"created"；④ 后台周期 merge 把小 segment 合并成大段。官方 refresh 文档原话："refresh 操作让近期的改动对搜索可见"（makes recent changes to the index visible to search），默认间隔 refresh_interval=1s。可见性卡在 refresh 这一步，这就是官方叫它近实时（near real-time）的原因——文档写完到能搜到，通常隔一秒：

translog 兜的是什么底？refresh 只是把数据变成"可搜索"，还不是"可恢复"——Lucene 的提交（commit）很贵，不可能每条都做。于是每条操作"在返回确认之前"先追加进 translog，且默认 durability=request：落盘确认后才回客户端成功。断电重启时，"已确认但还没进 Lucene 提交点"的那一小段操作从 translog 重放补回。一句话分工：refresh 管"什么时候能搜到"，translog 管"确认过的绝不丢"——两个机制各管一头，合起来才是既快又可靠的写入。代价也有：默认每请求落盘一次，超高吞吐场景官方提供 async 模式（默认 5 秒刷一次），换成"崩溃时可能丢最后几秒"。想亲手触发可见性，一条命令：

# 官方 Refresh API 文档样例：不等 1 秒，立刻让缓冲里的文档可搜
POST my-index-000001/_refresh
{
  "_shards": {
    "total": 2,
    "successful": 2,
    "failed": 0
  }
}

命令取自官方文档样例；响应体是官方记载的 _shards 结构——total 是该索引的分片副本总数（本例 1 主 1 副）。批量导入的黄金组合是：refresh_interval=-1 暂时关刷新 + 导完手动 refresh，避免一路生成一堆马上就要被合并的中间 segment。

07segment 不可变设计：删除是标记，合并才清账

第二个钩子：segment 一旦生成就永不修改（官方 merge 文档原话："segment 是不可变的"——immutable）。不可变听起来笨，其实是第 03 节那些快的根源：读无锁（不会读到改了一半的文件，任何线程随便并发读）；缓存友好（文件永不变化，文件系统缓存可以长期驻留，热数据等同内存操作）；压缩率高（数据静态可大胆编码，省磁盘省内存）。那删除和更新怎么办？全靠"标记 + 新写"：删除只是在提交点记录"文档 N 已删"（.del 标记），文档数据原封不动躺在旧 segment 里，查询时被过滤掉——你删了它，它还占着空间；更新 = 对同一文档 ID 标记删除 + 在新 segment 写入新版本（所以更新一条文档的实际成本接近"删一次加写一次"）。真正物理回收空间的是第 06 节的 merge：官方原话——"较小的 segment 周期性合并成较大的 segment，以控制索引体积并清除删除（expunge deletes）"。

  • 查询为什么要打折：命中结果里凡带删除标记的要在返回前过滤掉，删除积压越多查询越亏——看得到"已删文档占比"这个指标（docs.deleted）就知道该不该治理；
  • merge 不是免费的：合并要重写数据、吃 IO 与 CPU，所以它是后台限速进行的——写入流量暴增时 segment 堆积、merge 追不上，观测的就是这个水位；
  • forcemerge 是把手术刀：批量导入结束后对只读索引强制合并成少数几个大段，一次性清掉全部删除标记，属于运维动作别在业务高峰做；
  • 事务不支持：没有回滚和部分更新——"改一行"的代价是重建整条文档，这决定了用 ES 的姿势：数据模型按查询优化，不按事务优化。

反直觉点收一下：删得快≠删得掉。靠删数据腾空间的同学要记住——删除标记只是让文档不可见，磁盘空间要等 merge 走完才归还；急用空间走 forcemerge 或直接删索引。

  • A. 搜不到，而且此时断电数据就丢了
  • B. 搜得到，因为 translog 已经落盘
  • C. 搜不到，但断电也不丢——translog 已留底
  • D. 搜得到，前提是它有副本分片

10思考题

思考一：为什么主分片数在建索引时定死、副本数却能随时改？这个限制对"一开始不知道数据量"的业务意味着什么？

先看机制：文档落在哪个主分片由路由公式决定——默认对文档 ID 取哈希、再对主分片数取模，官方原话是"每个文档属于一个主分片"。这个公式要求所有节点对"主分片数"达成一致答案，一旦改数字，每条文档算出的归属全变：已写进去的数据等于全部错位，所以 ES 干脆把主分片数锁在建索引那一刻（官方 Create index 文档明确 number_of_shards 只能建索引时设置）。副本则完全不同：它不是路由的目标，只是主分片的拷贝——增加副本只是多复制一份、分担读流量，减少副本只是少一份冗余，数据分布纹丝不动，官方原话"副本数可以随时改变而不中断操作"。对"不知道数据量"的业务，这个限制催生了几个工程姿势：宁可按"单分片 10~50 GB"的经验区间拆多一点的分片（分片数 = 预估总量 / 单片目标），因为分片只能多不能改；或者用数据流 + 按时间滚动的索引，让"分片数"变成按时间片可重估的参数；9.x 还提供了 shrink/split 等运维工具在事后搬正——但那是要重刷数据的重操作。本质上是用路由公式的简洁性（O(1) 定位）换掉了在线弹性，这是分布式系统里"算得快"和"搬得动"之间的经典取舍。

思考二：把 refresh_interval 设成 -1 之后，"近实时"还成立吗？写入的数据什么时候可搜、什么时候会丢？批量导入该怎么组合这几个开关？

先拆开两件容易被混为一谈的事：可见性归 refresh 管，可靠性归 translog 管，设 -1 只动了前者。关掉自动刷新后，文档写进去照样进内存缓冲、照样追加 translog（默认 durability=request 下逐请求落盘确认），所以"断电不丢"的性质一点没变；变的只是"什么时候生成新 segment"——不再每秒自动做，要等到你手动触发 POST 索引名/_refresh、或该分片触发 flush（Lucene 提交，官方文档：translog 最大不超过磁盘的 1%，到阈值会自动 flush）时才可见。也就是说"近实时"的"近"从 1 秒被拉长到"你愿意等多久"。批量导入的黄金组合因此是三件套：refresh_interval=-1 暂关刷新（避免生成一堆中间 segment 等着 merge，白费 IO）、副本数临时降为 0（少复制一倍数据）、导完恢复副本数并手动 refresh——官方 bulk 导入指引就是这个思路。反过来说，如果你的场景要求"写入后立刻可搜"（比如监控告警的秒级延迟），别把 refresh 调长，反过来按需把个别索引调小甚至写入后主动 refresh——它的粒度是索引级设置，完全可以按业务分而治之。这道题的通用结论：看到任何"近实时"，先问一句"可见性延迟和持久性保证分别是哪个机制给的"，两个变量分开调，才不会调出一个又慢又丢的配置。

11本期要点与下期预告

带走这五句话：

  • 术语三层：索引装文档、文档由字段组成、mapping 定义字段如何存储与索引（text 分词检索，keyword 精确匹配）；
  • 倒排索引是"书的术语表"：分词 → 词项字典 → 文档列表，查询直查不扫描，快在用写入时的预处理换查询时的直查；
  • 索引 = 主分片 + 副本的分组，每个分片是一个自包含的 Lucene 索引；主分片数建索引时定死，副本数随时可改；
  • 写入路径：内存缓冲 + translog 兜底 → refresh 生成新 segment 才可搜（近实时的由来，默认 1 秒）→ merge 合并清删除；
  • segment 不可变：读无锁、缓存友好、压缩率高；删除只是标记，merge 才真正回收空间。
