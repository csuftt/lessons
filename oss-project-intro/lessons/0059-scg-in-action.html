OSS PROJECT INTRO · SPRING CLOUD GATEWAY 系列第 4 期：实战场景

Spring Cloud Gateway 实战：给微服务装上统一入口

上一期我们拿到了 Route、Predicate、Filter 的概念地图。今天把地图用起来：把网关的三板斧串成一次真实接入——服务名路由自动生成、每秒限流真把请求拦成 429、十行以内的鉴权过滤器把缺 token 的请求挡成 401。两个极简下游服务、一个官方开关、一个路由过滤器、一个 Bean，端到端跑通"统一域名入口"；最后一张全景图把四道关卡对号入座，401 / 429 / 503 / 404 状态码即路标。全部口径当场对照官方文档（2026-09-20 核对），跟着敲就能通。

🧭 微服务网关 · Java · Apache-2.0（Spring 官方项目） 📦 基于 Spring Cloud Gateway 5.0.3（Spring Cloud 2025.1.3 · Boot 4.1.1 · JDK 17+，2026-09-20 核对） 📅 2026-09-20 · 第 4 期 ⏱ 预计阅读 15 分钟

01本期目标：三步搭出一个统一入口

需求先摆上桌，都是微服务接入期的真实诉求：统一域名入口——客户端只认网关，按路径找到对应服务；热点接口限流——突发流量把下游打挂之前，在入口先拦；无效请求进门就拦——缺 token 的请求不该到达下游。三步走，对应三样东西：

  • 服务名路由：开官方的 discovery locator 开关，按注册发现到的服务自动生成路由——路由 uri 用 lb://服务名，默认谓词 Path=/服务名/**，转发前自动剥掉服务名前缀；
  • 限流：给订单路由挂 RequestRateLimiter 过滤器，底层是 RedisRateLimiter（令牌桶，计数存 Redis，需本机起一个 Redis）；
  • 鉴权：自定义一个 GlobalFilter Bean，校验 X-Token 请求头，缺头回 401——官方开发者指南同款写法，十行以内。

版本前提沿用第 2 期口径：Spring Cloud 2025.1.3（Oakwood）+ Boot 4.1.1 + Gateway 5.0.3 + JDK 17+，网关工程仍是那个只带 spring-cloud-starter-gateway-server-webflux 起步器的应用。本期新增两样依赖：负载均衡起步器（服务名路由必需）与 reactive 版 data-redis 起步器（限流必需），下文逐一给官方出处。

02第一步：服务名路由——两个极简下游 + 一个官方开关

先备两个极简下游：用户服务起在 8081，订单服务起在 8082，各自只有一个接口、回一句 JSON（order-service 同款：@GetMapping("/order/list")，返回 items 数量）。它们就是两个普通 Web 应用，不知道网关的存在。

@SpringBootApplication
public class UserServiceApp {
    public static void main(String[] args) {
        SpringApplication.run(UserServiceApp.class, "--server.port=8081");
    }
}
@RestController
class MeController {
    @GetMapping("/me")
    Map<String, String> me() {
        return Map.of("service", "user-service", "ok", "true");
    }
}

让网关认识它们，官方有现成机制——DiscoveryClient 路由定位器，不是什么黑魔法。官方 5.0.3 文档原话：默认生成的路由用 lb://service-name 协议（负载均衡转发），默认谓词是 /serviceId/** 路径匹配，默认过滤器是一个 RewritePath——把服务名前缀剥掉再转发；因为要做负载均衡，classpath 上需要有 spring-cloud-starter-loadbalancer：

官方 5.0.3《The DiscoveryClient Route Definition Locator》：lb:// 默认协议、Path=/serviceId/** 默认谓词、剥前缀的默认过滤器，以及 IMPORTANT 警告——自定义 filters 会整组替换默认列表，RewritePath 必须保留（docs.spring.io，2026-09-20 截图）。

演示为了"零注册中心先跑起来"，用官方 Spring Cloud Commons 的 SimpleDiscoveryClient 静态实例清单——文档原话：classpath 上没有注册中心实现时，它自动兜底，实例信息按属性格式传入。开关用官方属性表（appendix）里的完整路径，注意 5.0 起挂在 server.webflux 之下——discovery 文档页示例里还是 4.x 风格的短根，以官方属性表为准（与第 2 期讲的属性根变更一脉相承）：

spring.cloud.discovery.client.simple.instances.user-service[0].uri=http://localhost:8081
spring.cloud.discovery.client.simple.instances.order-service[0].uri=http://localhost:8082
spring.cloud.gateway.server.webflux.discovery.locator.enabled=true
$ curl http://localhost:8080/user-service/me
{"service":"user-service","ok":"true"}

按服务名访问：网关自动生成的 /user-service/** 路由接住，剥掉前缀转发到 8081，客户端第一次只报服务名就拿到了响应。公司栈换成 Nacos 注册中心，走的也是同一个 DiscoveryClient 抽象——配置换成 Nacos 起步器即可，注册、配置与 Spring Cloud 集成的实战第 0004 期已经带大家跑过，这里不重讲。

03第二步：限流——RequestRateLimiter + RedisRateLimiter

官方前提先钉住：限流文档原话——Redis 实现"requires the use of the spring-boot-starter-data-redis-reactive Spring Boot starter"，算法是令牌桶（Token Bucket，源自 Stripe 的方案）。令牌桶的计数放在 Redis 里意味着这是全局限流：网关起多个实例，共享同一个桶。本机起一个 Redis、加这个 Boot 自家起步器（版本由依赖清单托管，不用手写）就位：

Maven Central 坐标页实拍：spring-boot-starter-data-redis-reactive，描述原文"Starter for using Redis key-value data store with Spring Data Redis reactive"。页面片段默认带出的 4.2.0-M1 是里程碑预发布——生产认准 GA 线，版本交给所用 Boot 的依赖清单托管（central.sonatype.com，2026-09-20 截图）。

给订单路由挂上 RequestRateLimiter。注意官方明示的坑：这个过滤器不支持 shortcut 一行式写法（原话：The RequestRateLimiter is not configurable with the 'shortcut' notation），必须展开成 name + args 的完整结构：

routes:
  - id: order_route
    uri: lb://order-service
    predicates:
      - Path=/order/**
    filters:
      - name: RequestRateLimiter
        args:
          redis-rate-limiter.replenishRate: 2    # 每秒注水 2 个令牌
          redis-rate-limiter.burstCapacity: 4    # 桶最多装 4 个
          redis-rate-limiter.requestedTokens: 1  # 每个请求花 1 个

限流数字里的令牌桶，两个参数定节奏：replenishRate 是注水速率——每秒往桶里放几个令牌，决定稳态下每秒放行几个（官方口径"without any dropped requests"的速率）；burstCapacity 是桶容量——允许的瞬时突发上限，官方明确设成零等于全拒。官方还给三档配方：要平稳，两值相等；要扛突发，桶容量调大；要低于每秒一次的限速，用 requestedTokens 凑——例如 1 / 60 / 60 折成每分钟一次。三段定义原文都在官方文档这一页：

官方 RequestRateLimiter 文档实拍：Redis 实现源自 Stripe、算法为 Token Bucket；replenishRate / burstCapacity / requestedTokens（默认 1）三段定义原文（docs.spring.io，2026-09-20 截图）。

还差一把钥匙：限流按谁算？官方的答案叫 KeyResolver，样例按 user 请求参数取值——同一个 user 打一百发，合用一个桶。这里藏着一个默认坑：默认实现是 PrincipalNameKeyResolver（从认证主体取名字），我们没接认证，官方口径是取不到 key 就默认拒绝（deny-empty-key 默认开启）——不配它，全站 429：

@Bean
KeyResolver userKeyResolver() {   // 官方文档样例
    return exchange -> Mono.just(
        exchange.getRequest().getQueryParams().getFirst("user"));
}

官方也注明了：样例按参数取 key，不适合直接上生产（真实场景按用户 ID、IP 等稳定维度）。现在见证时刻——对订单路由连打六发，间隔不到半秒：

$ for i in $(seq 1 6); do
    curl -s -o /dev/null -w "%{http_code}\n" \
      "http://localhost:8080/order/list?user=tom"
  done
200
200
200
200
429
429

前四发全绿——正好是桶容量 4 个令牌；第五发起 429，注水速率每秒 2 个跟不上（连打间隔小于 0.5 秒，回显为可复现演示输出）。429 响应还带官方默认的 X-RateLimit-Remaining 等额度头，看一眼就知道还能打几发。限流从配置到拦截，闭环。

04第三步：鉴权——十行以内的自定义 GlobalFilter

官方开发者指南《Writing Custom Global Filters》的写法：实现 GlobalFilter 接口注册成 Bean，原话"applies the filter to all requests"——对所有路由生效，这正是"进门先验票"该有的语义。逻辑读一遍：请求头里有 X-Token 就放行；没有，把响应状态码设成 401 直接打回：

@Bean
@Order(-1)  // 标准 Spring 排序：站到过滤器链最前面
GlobalFilter authGlobalFilter() {
    return (exchange, chain) -> {
        boolean ok = exchange.getRequest().getHeaders().containsKey("X-Token");
        if (!ok) exchange.getResponse().setStatusCode(HttpStatus.UNAUTHORIZED);
        return ok ? chain.filter(exchange) : exchange.getResponse().setComplete();
    };
}

@Order(-1) 借的是标准 Spring 排序约定：路由过滤器按官方实现取正序号（源码 RouteDefinitionRouteLocator 里按定义顺序取 1、2、3……），-1 让鉴权闸站到链条最前面——无效请求进门就挡，不浪费后面任何一段（思考一展开这个顺序的讲究）。验收：同一条路由、前后两发：

$ curl -s -o /dev/null -w "%{http_code}\n" http://localhost:8080/order/list
$ curl -s -H "X-Token: secret123" http://localhost:8080/order/list
401
{"service":"order-service","items":3}

缺头 401、带头放行（可复现演示回显）。三条需求全部兑现。

05全景解读：一条请求穿过的四道关卡

把整条链画出来（自绘，概念图）：① 是我们写的鉴权闸，② 是挂在路由上的限流闸，这两道决定请求死不死在门口；③ 负载均衡解析与 ④ Netty 转发，是框架自带的全局过滤器——官方文档《Global Filters》页原文：lb 协议由 ReactiveLoadBalancerClientFilter 把服务名换成真实地址，找不到实例默认回 503；Netty Routing Filter 用 Netty HttpClient 真正发往下游，回写响应。

本期三条 curl 对号入座：401 死在①，429 死在②，503 死在③。排障视角记住这条钩子——状态码即路标：401 鉴权闸拦的，查 token 头带没带、名字拼写对不对；429 限流闸拦的，看剩余额度头是不是归零；503 负载均衡没找到实例，先单独 curl 下游确认活着；404 根本没命中路由，查谓词和路径。四个信号四种病，先分诊再动手，别一上来就重启。

07思考题（点击展开解析）

思考一：鉴权闸放在限流闸前面，还是后面？两种顺序各付出什么代价？

先想清楚两道闸的成本模型。鉴权闸只查一个请求头，几乎零成本；限流闸要连一次 Redis、扣一个令牌。若把限流放在鉴权前面：缺 token 的垃圾请求也会消耗桶里的令牌——攻击者不用带合法凭证，就能把正常用户的配额打空，限流从"保护下游"变成可以被借刀的"间接 DoS"。所以本期用 @Order(-1) 让鉴权站最前：无效请求根本不占限流配额。反过来，"先鉴权"也有代价：鉴权逻辑如果将来升级成调远程认证服务，它自己就成了链条上第一个可能被拖垮的环节。排序不是技术对错，是成本与风险的位置经营：便宜且能挡掉大量后续工作的闸靠前，贵的闸靠后，还要警惕"便宜闸"变贵的那天。

思考二：本期用官方 SimpleDiscoveryClient 静态清单跑通了服务名路由，换成 Nacos 后，什么变了、什么没变？

没变的是网关这一侧的全部机制：discovery locator 照样按 DiscoveryClient::getServices 拿服务列表，照样生成 lb://服务名 的路由、照样剥前缀；ReactiveLoadBalancerClientFilter 照样解析地址。变的在清单的来源：静态清单要人肉维护，服务扩缩容、换端口都得改配置重启；Nacos 这样的注册中心让实例清单自动跟随心跳上下线，动态路由才名副其实——这正是"服务名路由是官方机制"的底气：机制不绑定任何一个注册中心实现。迁移成本小到只有依赖与实例来源两处（集成实战见第 0004 期）。这也回答了一个架构问题：为什么 Spring Cloud 坚持把"发现服务"抽象成 DiscoveryClient 接口——抽象稳定，实现可换，上层机制才能一次建成、处处复用。

08随堂小测

1. 网关加了 RequestRateLimiter 但没配 KeyResolver，会发生什么？

  • 限流自动按请求路径计数，正常工作
  • 全站请求被默认拒绝（429）
  • 限流静默失效，全部放行

2. RequestRateLimiter 过滤器在 yml 里的正确写法是？

  • - RequestRateLimiter=2, 4, #{@userKeyResolver}（一行式）
  • - name: RedisRateLimiter（直接写实现名）
  • - name: RequestRateLimiter + args: redis-rate-limiter.replenishRate 等

3. 客户端访问 /order/list 返回 503，最先该查什么？

  • 限流桶是不是空了
  • lb 找不到实例：下游活着吗、实例清单/负载均衡依赖对吗
  • 谓词是不是没命中路由

4. 开启 discovery locator 后，user-service 会被自动生成什么样的路由？

  • uri=lb://user-service，谓词 Path=/user-service/**，并剥前缀转发
  • uri=http://localhost:8081，谓词 Path=/**
  • uri=lb://user-service，谓词 Host=user-service

09本期小结

  • 三步搭出统一入口：服务名路由（开官方开关，静态清单先行）→ 限流（RequestRateLimiter + RedisRateLimiter）→ 鉴权（自定义 GlobalFilter Bean）；
  • 服务名路由是官方机制：默认生成 lb://服务名 路由、Path=/服务名/** 谓词、剥前缀转发；无注册中心时官方 SimpleDiscoveryClient 静态清单先行，Nacos 即插即换（集成实战见第 0004 期）；
  • 限流两参数一把钥匙：replenishRate 注水速率 + burstCapacity 桶容量（设零全拒；官方三档配方）；KeyResolver 必配——默认实现取不到 key 就默认拒绝；不支持 shortcut 一行式写法；
  • 状态码即路标：401 鉴权闸 / 429 限流闸 / 503 无实例 / 404 无路由——先分诊再动手；
  • 版本口径：Gateway 5.0.3 + Spring Cloud 2025.1.3 + Boot 4.1.1，限流需 spring-boot-starter-data-redis-reactive，服务名路由需 spring-cloud-starter-loadbalancer。
