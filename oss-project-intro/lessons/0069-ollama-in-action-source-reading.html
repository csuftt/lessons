演示环境沿用第 2 期口径：本机服务默认端口 11434，示例模型为官方 Quickstart 的 gemma4:e2b（下载约 7.2 GB，官方建议 8 GB 可用显存或 Mac 统一内存）。Python 侧标准库以外只需要 pip install requests 与 pip install openai。

02实战①②：十行写一个流式客户端，再接上记忆

官方接口文档对 /api/chat 的原话是："Generate the next message in a chat with a provided model"——默认流式返回，一行一个 JSON 对象，最后一个对象带统计信息。把它包成命令行工具，核心就是"边收边打印"：

# chat.py：把 /api/chat 流式接口包成命令行小工具
import json, requests

MODEL = "gemma4:e2b"
msgs = [{"role": "system", "content": "回答控制在两句话内"}]
r = requests.post("http://localhost:11434/api/chat",
    json={"model": MODEL, "messages": msgs}, stream=True)
for line in r.iter_lines():
    print(json.loads(line)["message"]["content"], end="", flush=True)
$ python chat.py
光在大气中被散射，短波长的蓝光散射最强，所以天空是蓝色的。（逐字蹦出，示意转写）

第二步接记忆。这个接口不存会话：服务端记不住你上一句说了什么，记忆全靠客户端把历史随请求带回。把流式收到的回答拼成 assistant 消息接回 messages，多轮对话就成了；role 一共四种——system、user、assistant、tool，最后那个给做工具调用留了口子：

# 把流式收到的回答拼起来，接回 messages，多轮记忆就成了
reply = ""
for line in r.iter_lines():
    chunk = json.loads(line)["message"]["content"]
    reply += chunk
    print(chunk, end="", flush=True)
msgs.append({"role": "assistant", "content": reply})

03实战③④：换模型改一行，换协议改个地址

换模型的真实成本：先把新模型拉到本地，再改一行字符串。模型名就是接口的一部分——这也是第 3 期讲过的"两段式命名"（家族 + 规格标签）在实战里的兑现：

ollama pull qwen3:4b
# MODEL = "gemma4:e2b"  →  MODEL = "qwen3:4b"
python chat.py
pulling manifest → verifying sha256 digest → success
你> 用一句话介绍自己
我是 Qwen……（首字偏慢：冷加载新模型；再问即秒回）

首字偏慢不是错觉：模型闲置五分钟后按默认策略卸载（保活参数 keep_alive 可调），冷加载要从磁盘重新读入显存。第二个"只改一处"是换协议：装上 OpenAI 官方客户端，把地址指向本机、路径加上 /v1，密钥随便填一个占位串——原来写死云端的代码就跑在了本地：

# 同一件事，OpenAI 兼容端点再来一遍
from openai import OpenAI

client = OpenAI(base_url="http://localhost:11434/v1", api_key="ollama")
r = client.chat.completions.create(model="gemma4:e2b",
    messages=[{"role": "user", "content": "一句话解释 GGUF"}])
print(r.choices[0].message.content)

读答案的方式换成 choices[0].message.content，其余照搬 OpenAI 写法。官方在文档里专门提醒：OpenAI 与 Anthropic 兼容各自只覆盖原接口的一个子集——换协议之前先对一眼能力表。顺手一提，同端口还有 /v1/messages（Anthropic 兼容）和 /v1/responses，三大生态的客户端都接得进来。

两个收尾小技巧。其一，想看现在谁占着显存，敲 ollama ps：在跑的模型、体积、装进显存的比例一目了然，冷加载还是热复用一眼可辨；其二，要模型"常驻不卸"或"用完即走"，不必改配置——请求里的 keep_alive 参数按次生效，填 -1 不卸载、填 0 立即卸载、填时长则到期再卸（官方 FAQ 口径）。另外，别把 /api/chat 和 /api/generate 混为一谈：前者按消息列表对话，后者按裸提示词补全，结构化输出、文本加工这类"不要角色扮演"的活更适合后者。

这四站各对应一个源码位置：server/routes.go 的路由表、server/sched.go 的调度器、llm 包的引擎子进程管理，以及流式写回。下一节按图索骥，三站读完。

05读码①：仓库顶层，一眼分清门面与引擎

源码导读为轻读码：抓结构不抠逐行，所有路径核对自 tag v0.34.2（2026-09-19）。先看仓库顶层目录分工——门面薄、引擎厚，是本地工具该有的身材：

  • cmd/ —— 命令行入口与交互界面（ollama run/pull/ls 的老家）；
  • server/ —— 服务本体：路由（routes.go）、模型调度（sched.go）、模型管理；
  • fs/ 与 manifest/ —— 模型文件解析（GGUF、safetensors）与清单管理；
  • llm/ —— 引擎子进程管理：找到引擎、拉起进程、转发请求；
  • llama/ 与 ml/ —— 推理引擎底层源码与张量库，仓库里的大头；
  • openai/ 与 anthropic/ —— 两家协议兼容层；discover/ 盘点显卡与内存；
  • 周边还有 api/（Go 客户端类型）、template/（聊天模板）、envconfig/（环境变量）——第 3 期讲过的概念都能在这三个目录里找到落点。

来源注记——github.com/ollama/ollama/tree/v0.34.2（2026-09-19 截图）：顶层约五十个目录与文件，上述八个目录构成从命令到推理的完整链路。

06读码②：模型存储——清单管名字，摘要管内容

全项目最值得抄的设计在模型存储。每个模型一份清单文件，记着名字对应哪几层；真正的权重与配置躺在内容仓库里，文件名就是文件内容的 sha256 摘要：

models/
├── manifests/registry.ollama.ai/library/gemma4/e2b
│       清单文件：名字到各层的账本（结构同容器镜像清单）
└── blobs/
        sha256-…：文件名即内容的 sha256 摘要（manifest/paths.go
        的 BlobsPath：冒号换连字符落盘，正则校验摘要格式）

这个设计买一送三：同一份权重只存一份，共享的层各模型直接引用；摘要即校验，下载中断的坏文件对不上摘要、进不了库；删除按引用计数，其他清单还在引用的层不能删——三件事没有一件需要额外机制，全是"文件名即内容"这一个决定的自然结果。与容器镜像同款的设计不是巧合：清单媒体类型用的正是 Docker manifest v2 的那套结构。再对照一下第 2 期的体验：敲 ollama ls 时看到的 ID 列，就是清单文件的摘要；ollama rm 删掉的是清单，内容仓库里没人引用的层随后由引用计数回收——两条命令背后是同一套存储模型。

来源注记——github.com/ollama/ollama/blob/v0.34.2/manifest/paths.go 第 52~72 行（2026-09-19 截图）：BlobsPath 函数以正则 ^sha256[:-][0-9a-fA-F]{64}$ 校验摘要，替换冒号为连字符后拼出 blobs 路径；manifest/manifest.go 中 Manifest 结构含 SchemaVersion 2、Config 与 Layers 字段，RemoveLayers 按其他清单的引用情况决定是否真删。

07读码③：接口与进程——一个核心，三种脸

第 3 期讲过"接口兼容层"，源码里它的实现比想象中轻。看 server/routes.go 的路由表（节选）：

/* server/routes.go @ v0.34.2，节选（gin 路由表） */
r.POST("/api/chat",  s.ChatHandler)          // 原生接口
r.POST("/v1/chat/completions", ..., s.ChatHandler)  // OpenAI 兼容
r.POST("/v1/messages", ..., s.ChatHandler)          // Anthropic 兼容

三种协议共用同一个处理函数：兼容端点靠中间件把外来格式翻译成内部结构，翻译完进门的就是同一个 ChatHandler。加一张协议脸，核心一行不改——这是"适配器"模式的教科书现场。进程模型上，llm/server.go 的官方注释把架构写成了白纸黑字：

/* llm/server.go @ v0.34.2，注释原文 */
// NewLlamaServer creates a new llama-server runner
// for the given model. All GGUF models are served
// via the upstream llama-server subprocess.

翻译过来：所有模型都由上游的 llama-server 子进程服务。配套的 llm/llama_server.go 负责在 lib/ollama 目录找到引擎可执行文件，用 exec.Command 拉起子进程，走本地端口通信；同文件的细节还有一处暖心的护栏——请求的上下文长度超过模型训练上限时，自动收敛到训练值再继续。

08钩子二：推理为什么单独住一个子进程？

看完实现，反问一句为什么。假如推理直接长在主进程里：引擎一崩，整个服务陪葬；换引擎要重新编译整个程序；显存是一笔糊涂账，调度无从谈起。拆到子进程后，四个问题同时消失：

  • 崩溃隔离：子进程退出，主服务能接住重建，正在排队的请求不至于全军覆没；
  • 独立升级：引擎升级只换 lib/ollama 目录下的文件，主程序原地不动；
  • 显存有账：调度器按进程盘点显存，多模型排队加载时算得清谁该让位；
  • 到期卸载：第 3 期讲过的"闲置五分钟自动卸载"，实现就在调度器的过期队列里。

把重活下沉到独立进程、门面保持清爽——这套思路不限于 Ollama：浏览器把页面渲染拆进程、数据库把后台清理拆线程，都是同一笔账。

09随堂小测

每题点击选项立即反馈 · 共 3 题

1. 服务端明明不存会话，多轮对话的"记忆"是从哪来的？

  • 模型自己在显存里记住了上下文
  • 客户端把历史 messages 随请求一起带回
  • 服务端的磁盘缓存自动拼接

2. 模型存储里"文件名即内容的 sha256 摘要"，不能带来的好处是？

  • 相同权重只存一份，天然去重
  • 下载中断的坏文件进不了库
  • 支持直接原地修改模型文件
  • 删除资源时可以按引用计数回收

3. OpenAI 兼容端点 /v1/chat/completions 收到请求后，实际由谁处理？

  • openai 目录里的一个专用推理服务
  • 中间件翻译成内部结构，进同一个 ChatHandler
  • llama-server 子进程直接接收 HTTP 请求

10思考题（点击展开解析）

思考一：把"文件名即内容摘要"用到你自己的系统里，能白拿哪些好处？要付什么代价？

好处至少三条。其一，天然去重：相同内容的文件在仓库里只有一份，多个模型共享同一份权重层，磁盘账直接省一笔；其二，天然校验：下载或拷贝后重算一遍摘要就能验真伪，坏文件连入库的资格都没有——Ollama 的做法更彻底，摘要格式不对连路径都拼不出来；其三，天然引用计数：删资源时搜一遍还有谁引用这个摘要，被引用就留着，误删从他名单上消失。代价也是三条：内容不可变，改一个字节就是新文件，需要"可变语义"时得在上面包一层（Ollama 的清单就扮演这个角色，名字到摘要的映射随时可换）；摘要要真算，写入时多一遍哈希，大文件有 CPU 成本；垃圾回收要有全局视角，得能枚举所有清单才能算清引用，Ollama 的 Manifests 函数干的就是这个活。一句话：内容寻址适合"写完不改、按名取用"的资产，不适合频繁更新的状态。

思考二：给现有系统加一套"OpenAI 兼容接口"，照 Ollama 的抄法，中间件里该做什么、不该做什么？

先想清楚 Ollama 的边界画在哪：兼容层是翻译，不是实现。中间件里该做的三件事——格式映射：外来字段名到内部结构的双向翻译（choices 数组进、message 流出），连同默认值兜底；协议差异吸收：流式分帧方式、结束标记、错误码的形状，按对方生态的约定来；能力边界声明：子集里没有的能力要明确拒绝并说明，而不是假装支持——官方文档那句"兼容各自只覆盖原接口的一个子集"就是这条的公开承诺。不该做的两件事——不要绕开核心另起炉灶：翻译完必须进同一个处理函数，否则修一个 bug 要修三处，兼容层很快变成第二个产品；不要把业务逻辑写进中间件：鉴权、计费、限流归各自的横切层，翻译层只做无状态的格式转换。验收标准一句话：删掉兼容层，核心照常工作；换掉核心，兼容层一行不改。

11本期要点与系列收官

带走这五句话：

  • 实战链四步：十行流式客户端 → 消息历史多轮记忆 → 换模型改一行 → OpenAI 兼容端点改个地址，全部对照官方文档可复现；
  • /api/chat 默认流式、服务端不存会话，记忆是客户端把历史带回去的；

  • 接口与进程：三种协议进同一个 ChatHandler；推理跑在上游 llama-server 子进程，换来崩溃隔离与独立升级；
  • 版本基准 v0.34.2（GitHub Latest，2026-09-15 发布，2026-09-19 核对）。
