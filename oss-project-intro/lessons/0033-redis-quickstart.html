OSS PROJECT INTRO · REDIS 系列第 2 期:5 分钟跑起来

5 分钟跑起来 Redis:从安装到第一次读写

上一期我们认识了 Redis——内存数据结构服务器,也讲了它的许可证风波。这一期把认识变成动手:亲手把 Redis 跑起来,完成第一次写入和读取,并说清"什么输出才算跑通"。全文基于 v8.10.2(2026-09-17 发布的 Latest 稳定版,含安全修复;官方更名后的正式名字叫 Redis Open Source,2026-09-19 复核),安装命令与 quickstart 逐字对照 redis.io 官方文档,Windows 路线、高频报错一并给全,卡住了先对号入座,再怀疑人生。

🧩 缓存与数据结构服务器 · C · 三许可(RSALv2/SSPLv1/AGPLv3) 📦 基于 v8.10.2(8.10 稳定线) 📅 2026-09-19 · 第 2 期 ⏱ 预计阅读 15 分钟

01本期路线与跑通判定

五步路线:钉版本 → 装起来 → 起服务 → 连得上 → 读写通。Redis 是出了名的"好装"——纯内存、无外部依赖,一条 Docker 命令就能起。但"装好"不等于"跑通",本期给你三条硬判定:

  • ① 服务就绪:启动日志出现 Ready to accept connections tcp,或 systemctl status redis-server 显示 active (running);
  • ② 连接就位:redis-cli 连上后提示符 127.0.0.1:6379> 出现,敲 PING 回 PONG——官方文档原样口径;
  • ③ 读写闭环:SET 返回 OK,GET 能查回刚写的值——数据进得去、出得来,才算真的通了。

三条全绿,Redis 就在你机器上跑起来了。整个过程五分钟以内,我们开始。

02动手前先钉版本:8.10.2,五条线同日补丁

先看一眼 GitHub 发布页(GitHub redis/redis Releases,2026-09-19 实拍),把版本钉死:

8.10.2 Latest 2026-09-17 发布 · 发布者 sundb · tag 8.10.2
Update urgency: SECURITY : There are security fixes in the release.
Security fixes:#15673 事务队列越权访问 / #15722 集群总线端口无认证可被加入 / TimeSeries 与 RedisSearch 崩溃修复 / Vector Sets 深嵌套 JSON 崩溃修复

读出两个信息:其一,当前最新稳定版是 8.10.2,2026-09-17 发布,官方标注"含安全修复";其二,发布页同一天还挂出了 8.8.3、8.6.7、8.4.7、8.2.10——官方同时维护五条稳定线,安全补丁五线同日齐发。追"最新版"之前先知道自己站在哪条线上,这是上生产前的好习惯。

名字口径:Redis 8.0(2025-05-02 GA)起,官方把"Redis Community Edition"正式更名为 Redis Open Source,许可证三选一——RSALv2、SSPLv1、以及新加回的 AGPLv3。上一期讲的许可证风波,在 8.0 落了地。本系列统一以 8.10 稳定线为基准。

03环境要求:轻到不像数据库,Windows 要绕行

官方 README 给的支持平台清单是:Linux、macOS(OSX)、OpenBSD、NetBSD、FreeBSD——注意,Windows 不在清单里,官方不提供原生 Windows 版本。这不是疏忽,Redis 从设计之初就是奔着 Unix 系去的。

  • Linux / macOS:按下面第 4 节直接装,一条命令的事;
  • Windows 两条官方路:官方 Windows 文档给的第一条是用 Docker 跑(Windows 上装 Docker Desktop,后面命令一模一样);第二条是 Memurai——官方合作伙伴提供的 Windows 兼容版本(目前以 8.2 RC1 预览形式提供原生 Windows 支持);此外还有个社区惯用变通:在 WSL2 里装个 Ubuntu,然后完全按 Linux 的 apt 路线走——对本教程来说它就是 Linux;
  • 内存:练习环境几百 MB 绰绰有余——纯内存数据库不等于"吃内存",空跑实例只占几 MB,放多少数据占多少内存。生产环境官方运维手册给两条硬建议:开启 swap,并显式设置 maxmemory 上限(留出开销余量,别顶到物理内存);
  • 两个内核提醒(生产):vm.overcommit_memory=1(否则后台保存可能 fork 失败)和关闭透明大页 THP——第 7 节报错清单里有原话。

04安装:三条路线,全按官方文档走

官方安装文档给的开箱路线:Docker、Linux 发行版包(APT/RPM/Snap)、macOS Homebrew、源码编译。练习推荐 Docker(干净、命令与文档逐字对照),长期挂着用推荐系统包管理(开机自启、systemd 托管)。

路线 A:Docker 一条命令起服务(全平台通用,Windows 就走这条)

docker run -d --name redis -p 6379:6379 redis:latest

# 官方镜像页 tag 序列:8.10.1 / 8.10 / 8 / latest(另有 -alpine 精简底座)
# 数据落盘(可选):docker run -v /local-data/:/data --name redis -p 6379:6379 redis:latest
# 看启动日志:
docker logs redis --tail 5

日志最后几行(真实回显,节选):

* Redis version=8.10.2, bits=64, commit=00000000, modified=0, pid=1, just started
* Ready to accept connections tcp

判定①达成:Ready to accept connections tcp——服务端就绪。Docker Hub 上这是 Docker Official Image,由 Redis 官方维护,下载量 10 亿+ 量级。

路线 B:Ubuntu / Debian 用官方 APT 源(生产 Linux 主线)

Ubuntu/Debian 自带源里的 Redis 版本偏旧,官方文档给的是添加 packages.redis.io 官方源再装,六条命令原文:

sudo apt-get install lsb-release curl gpg
curl -fsSL https://packages.redis.io/gpg | sudo gpg --dearmor -o /usr/share/keyrings/redis-archive-keyring.gpg
sudo chmod 644 /usr/share/keyrings/redis-archive-keyring.gpg
echo "deb [signed-by=/usr/share/keyrings/redis-archive-keyring.gpg] https://packages.redis.io/deb $(lsb_release -cs) main" | sudo tee /etc/apt/sources.list.d/redis.list
sudo apt-get update
sudo apt-get install redis

官方文档原话:装完"Redis should start automatically after the initial installation and also at boot time"——首次安装即自动启动、开机自启。若没起来:sudo systemctl enable redis-server && sudo systemctl start redis-server。确认版本:redis-server --version,源内为 8.10 线最新。上面六条命令与 redis.io「Install Redis Open Source on Ubuntu or Debian Linux using APT」一节逐字一致(2026-09-19 核对),装完想装指定旧版,文档还给了 apt policy redis 查可版本、按 6:8.x.x-1rl1~noble1 全名锁版本的路子。

路线 C:macOS 用 Homebrew

brew install redis

# 方式一:后台服务(开机自启)
brew services start redis
# 方式二:直接前台跑(练习推荐,日志看得见)
redis-server $(brew --prefix)/etc/redis.conf

# 官方提醒:8.10.1 起 formula 自带 Search/JSON/时序等模块

三种路线殊途同归:机器上多了一个监听 6379 端口的 redis-server 进程。接下来连它。

05官方 quickstart 逐段走:PING 到 SET,五分钟闭环

第一步:连上它,提示符出现

# 路线 A(Docker)从容器里进命令行:
docker exec -it redis redis-cli
# 路线 B / C 直接连本机:
redis-cli -h 127.0.0.1 -p 6379

看到提示符 127.0.0.1:6379>,你已经站在 Redis 门口。第一句先打个招呼:

127.0.0.1:6379> PING
PONG

PING 回 PONG——官方文档原样口径,判定②达成。这不是玩具命令:生产上判活探测、客户端健康检查,用的就是它,一来一回不携带任何数据结构开销。

第二步:第一次写入与读取,SET / GET

127.0.0.1:6379> SET bike:1 "Process 134"
OK
127.0.0.1:6379> GET bike:1
"Process 134"

redis.io 官方 quickstart「Redis as an in-memory data structure store」的 CLI 示例原文就是这两句(2026-09-19 核对):给自行车库存起名——键名 bike:1,值 "Process 134"。你屏幕上的回显应与文档一致。

拆一下这十秒钟发生了什么:SET 键 值 把字节序列存进内存,返回 OK;GET 键 原样取回,带引号表示字符串。键名里的冒号是社区惯例的命名空间分隔符(对象类型:编号),不是语法强制。判定③达成——数据进得去、出得来,Redis 跑通了。

第三步:顺手摸一下哈希与扫描(官方 quickstart 后半段)

127.0.0.1:6379> HSET bike:2 model Deimos brand Ergonom type 'Enduro bikes' price 4972
(integer) 4
127.0.0.1:6379> HGET bike:2 model
"Deimos"
127.0.0.1:6379> SCAN 0 MATCH "bike:*" COUNT 100

HSET 一次写四个字段,回显 (integer) 4 是"新增字段数";HGET 取单字段;SCAN 游标扫描键空间——官方文档用它替代有隐患的 KEYS 全量遍历。字符串之外,Redis 还有列表、集合、有序集合、流等原生结构,官方文档数据类型一章专讲(见文末延伸阅读)。

跑通判定,就这三条

  • ① 服务就绪:日志 Ready to accept connections tcp 或 active (running);
  • ② 连接就位:提示符出现,PING 回 PONG;
  • ③ 读写闭环:SET 回 OK,GET 回刚写的值。

想收工?Docker 一条 docker rm -f redis 连容器带数据清干净,重来零成本;apt/brew 装的用 sudo systemctl stop redis-server 或 redis-cli SHUTDOWN。

06高频翻车与解法(按官方口径)

① 端口被占:Address already in use。6379 上已经有别的进程(或上一次的 Redis 没退)。先查:lsof -i :6379(Linux/macOS)或 netstat -ano | findstr 6379(Windows),杀掉旧进程,或改配置文件里 port 6380,连接时 redis-cli -p 6380。

② 远程连不上:DENIED Redis is running in protected mode。这是保护模式在拦你——官方安全文档口径:自 3.2.0 起,以默认配置(绑定所有接口、无密码)运行时,Redis 只回环应答本机连接,远程连接会收到一段解释性报错。正确解法按顺序考虑:给实例设密码(requirepass,推荐再上 Redis 6 的 ACL 细粒度权限)→ 配置里 bind 到指定内网地址 → 都明确之后再考虑关 protected-mode。直接裸奔上公网是重大事故源,官方文档专门警告过。

③ 启动日志告警 overcommit。官方运维手册原话:把 vm.overcommit_memory 设为 1——写入 /etc/sysctl.conf 后重启,或直接 sysctl vm.overcommit_memory=1。不理它的话,后台保存(RDB)时 fork 可能失败。

④ 启动日志告警透明大页(THP)。官方口径:echo never > /sys/kernel/mm/transparent_hugepage/enabled 关掉它,避免内存占用与延迟抖动。

⑤ Windows 装不了原生服务端。官方平台清单本就没有 Windows——走 Docker(官方 Windows 文档路线),或 Memurai(官方合作伙伴),或 WSL2 里按 Linux 路线装。别去找来路不明的 exe。

⑥ 本机好好的,别的机器连不上。按顺序排查:配置里 bind 127.0.0.1 只绑了回环(官方文档示例默认写法,远程需求要改)→ 保护模式拦截(见②)→ 云主机安全组没放行 6379。三处都看过再怀疑网络。

07两个小彩蛋:五线同日,与 6379 的来历

彩蛋一:你以为的"最新版"其实是五条线。2026-09-17 一天之内,官方连发 8.10.2、8.8.3、8.6.7、8.4.7、8.2.10 五个版本,清一色 SECURITY 级别。开源项目的版本策略是"多线并行、旧线也喂补丁"——升级前先弄清自己跟的是哪条线,别无脑追号。

彩蛋二:6379 不是随手挑的号。在老式手机九宫格键盘上,6-3-7-9 三个键位能拼出 MERZ——一个和数据库毫无关系的意大利艺人名字缩写,作者 antirez 的程序员式恶趣味(这桩轶闻在《Redis in Action》与作者本人的解释中广为流传)。如今 6379 成了全球约定俗成的 Redis 端口,你在配置文件里随时能改,但没人真的改它。

09思考题(点击展开解析)

思考一:PING/PONG 看似玩具,为什么几乎所有 Redis 客户端库和生产探测都用它?一个命令要满足"健康检查"的哪些条件才算合格?

把"健康检查"拆成四个硬条件,就看懂 PING 的地位了。其一快:PING 在服务端走的是极短路径——不碰任何键空间、不分配数据结构、不做复杂解析,官方命令表里它属于最贵也只有常数开销的那一类,适合高频调用;其二轻:应答 PONG 只有固定几个字节,不占带宽,一秒打几百次也无感;其三真:它走的是完整链路——客户端序列化、网络传输、服务端事件循环处理、再原路返回,任何一环断了它就回不来,所以它能代表"整条通路活着",而不是"进程活着";其四定:协议层保留字,从 Redis 诞生到 8.10 语义未变,不会有版本兼容坑。对照着看,有些系统拿"查一个真实业务键"当健康检查,键一大就把探测做成了压测;有些拿"进程存在"当检查,TCP 队列堵死了也发现不了。PING 恰好都避开——用最小代价,验证最完整链路,这是所有健康检查设计的通用范式,学会它,你给自己服务的接口写探活时就有标准了。

思考二:本期你装的 Redis 没设密码、只监听本机,和生产环境的 Redis 中间差了哪几层?哪些今天练的东西到了生产依然成立?

分两侧看。生产必补的至少四层:其一,网络边界——生产 Redis 通常只允许应用服务器所在内网访问,公网彻底隔离(官方安全文档反复警告暴露公网的后果,历史上成规模的勒索事件都从裸奔 Redis 开始);其二,认证与授权——至少 requirepass,规范做法是 Redis 6 引入的 ACL,给不同服务发不同用户、只授所需命令;其三,持久化策略——默认 RDB 快照对缓存够用,要当数据库用就补 AOF,这直接决定重启后数据还剩多少;其四,资源上限——maxmemory 加淘汰策略,避免内存无限膨胀拖垮宿主机。今天练的东西,大部分到生产依然成立:PING 探活、SET/GET 语义、键名命名惯例、SCAN 替代 KEYS、overcommit 与 THP 两个内核参数——最后这两个恰恰是官方运维手册的生产建议,你今天提前见过了。正确的学习姿势:本机练语法,生产补边界——第 3 期讲核心概念与架构时,你会看到主从复制、哨兵与集群如何把今天这个单机实例铺成高可用系统。
