OSS PROJECT INTRO · ELASTICSEARCH 系列第 4 期：实战场景

Elasticsearch 实战：端到端做一个商品搜索

上一期拿到了 ES 的概念地图：倒排索引、mapping、segment、分片与写入路径。本期把地图用起来，端到端做一个真实小场景——商品搜索：输入关键词返回相关商品，命中的词高亮，侧栏给出品牌分布。从建索引、声明 mapping，到 bulk 批量上架，再到官方 Java 客户端一次请求拿齐"命中 + 高亮 + 聚合"，每一步都能对回官方文档、照着复现。深挖源码留给第 5 期，本期只做一件事：让它真实跑起来。

🔍 搜索引擎 · Java · 实战 📦 ES v9.5.4 + elasticsearch-java 9.5.4（Maven Central 核对） 📅 2026-09-19 · 第 4 期 ⏱ 预计阅读 15 分钟

01系列地图：实战把概念变成肌肉记忆

老规矩先看地图。第 1 期立住了心智模型，第 2 期把服务跑起来，第 3 期铺开了概念与架构。本期是第 4 期实战：上一期的每个名词——mapping、倒排索引、分片、聚合——都会变成实打实的一步命令或一段代码。第 5 期进源码。本期结束时你应该能独立搭出：一个能搜、能高亮、能按品牌聚合的商品搜索。

02需求拆解：一个商品搜索要的四样东西

场景很简单：电商站内搜。用户输入"wireless headphones"（无线耳机），系统返回相关商品列表，命中的词标红，侧栏还能按品牌筛。拆成能力清单，ES 三件套全部在场：

商品搜索需求ES 的能力背后靠什么
输关键词，搜出相关商品match 全文检索title 分词进倒排索引，查词项直接拿文档列表（第 3 期）
命中的词标红高亮highlight 高亮返回时按命中的词项加标记，不另建结构
侧栏显示品牌分布、点选筛选terms 聚合brand 是 keyword，按值分桶计数
按价格区间过滤range 过滤数值字段列存（doc values），范围判断很快

第 3 期的结论"类型声明了，检索行为就定了"在本期全程兑现：这条能力清单里，每个需求都能倒推回 mapping 里的一个字段类型选择。

03第一步：建索引，mapping 定生死

演示链第一站，把商品索引建出来。四个字段，每个都想清楚再声明：

PUT products
{
  "mappings": {
    "properties": {
      "title":       { "type": "text" },
      "description": { "type": "text" },
      "brand":       { "type": "keyword" },
      "price":       { "type": "double" }
    }
  }
}

标题和描述要参与全文检索，建成 text；品牌要精确过滤和聚合，建成 keyword；价格是数值。请求体结构对照官方《Explicit mapping》样例。为什么这个选择"定生死"？第 05 节踩一个坑你就信了。

04第二步：bulk 批量上架八件商品

POST products/_bulk
{ "index": { } }
{ "title": "Wireless Headphones WH-CH520", "description": "wireless bluetooth headphones, 35h battery", "brand": "Sony", "price": 399 }
{ "index": { } }
{ "title": "Wireless Mouse M185 Silent", "description": "silent wireless mouse with 2.4G dongle", "brand": "Logitech", "price": 199 }
:: ……同样格式再写 6 件：Sony×1 · Anker×3 · Xiaomi×1（共 8 件上架）
{ "errors": false, "took": 34, "items": [ …… 8 个结果逐一回执，全部 created …… ] }

格式一句话：一行元信息声明写到哪，紧跟一行文档，交替往下排（官方《Index and search basics》批量示例同款）。响应 errors:false 即全部成功。品牌账先记牢：索尼 2、罗技 2、安克 3、小米 1——等会儿聚合的桶要和它对账。

05钩子一：对 title 聚合，ES 当场翻脸

第三站故意踩坑。产品经理说"顺便给搜索词统计个热度"，那就顺手对 title 做个 terms 聚合试试：

GET products/_search
{
  "aggs": {
    "titles": { "terms": { "field": "title" } }
  }
}
{
  "status": 400,
  "error": { "type": "illegal_argument_exception",
    "reason": "Fielddata is disabled on text fields by default. …… Alternatively use a keyword field instead." }
}

服务端回 400，拒绝得干脆利落。错误消息最后一句就是药方：use a keyword field instead。这不是故障，是官方设计：

官方《Terms aggregation》文档 Note 原文：默认不能对 text 字段做 terms 聚合，用 keyword 字段代替；硬要开 fielddata 也能做，但官方明说会显著增加内存开销（来源：elastic.co/docs/reference/aggregations/search-aggregations-bucket-terms-aggregation，2026-09-19 截图）。brand 一开始就建成 keyword，此刻正好派上用场。

对比text：为"找"而建keyword：为"对"而建
写入时分词，拆成词项进倒排索引不分词，整串当一个值
主场match 全文检索 + 相关性得分精确过滤、排序、terms 聚合分桶
禁区整串聚合被官方拒绝（fielddata 默认禁用）全文检索轮不到它
两样都要text 字段挂一个 keyword 子字段（multi-fields），各干各的

一字之差，两个世界：text 管找，keyword 管对。mapping 是搜索引擎里的地基工程——建索引那一刻想清楚，后面每一步都是顺路；建错了，检索这一路处处别扭。

06接入 Java：官方客户端 9.5.4

命令行验证完，接进 Java。客户端用 Elastic 官方 elasticsearch-java（Java API Client），Maven Central 上当前版本 9.5.4，与服务端同步发版（2026-09-19 核对）；官方兼容口径：9.x 客户端配 9.x 服务端。

central.sonatype.com 实拍：版本选择器 9.5.4，依赖片段可直接抄（2026-09-19）。依赖只有一个：

<dependency>
  <groupId>co.elastic.clients</groupId>
  <artifactId>elasticsearch-java</artifactId>
  <version>9.5.4</version>
</dependency>

建连用 9.x 的新写法，一个 of 方法搞定——主机、账号、证书，全是第 2 期领的家当：

ElasticsearchClient es = ElasticsearchClient.of(b -> b
    .host("https://localhost:9200")
    .username("elastic").password(password)   // 也可 .apiKey(...)
    .sslContext(TransportUtils                // 第 2 期拷出的自签证书
        .sslContextFromHttpCaCrt(new File("http_ca.crt"))));

host / username / password / sslContext 均为官方 transport 配置项，TransportUtils.sslContextFromHttpCaCrt 是官方工具方法（核对于 elasticsearch-java 仓库 main 分支源码）。客户端官方建议建一次、全局复用。

07一次请求三件事：match + 高亮 + 聚合

主菜。一次搜索请求把三件事一起办了——搜、高亮、聚合：

SearchResponse<Product> resp = es.search(s -> s
    .index("products")
    .query(q -> q.match(m -> m
        .field("title").query("wireless headphones")))
    .highlight(h -> h.fields("title", f -> f))
    .aggregations("brands", a -> a.terms(t -> t.field("brand"))),
  Product.class);
:: 一次往返带回三样：hits 命中列表 · 每件的高亮片段 · brands 品牌桶
:: 聚合默认只统计"命中的文档"——侧栏品牌分布是这一轮搜索的分布

每一段写法都能对回官方文档。高亮在 REST 里就是请求体中一个 highlight 对象：

官方《Highlighting》：在请求体里加 highlight 对象、声明字段即可，响应里每个命中多一个 highlight 元素，装着加了 <em> 标记的片段（来源：elastic.co/docs/reference/elasticsearch/rest-apis/highlighting，2026-09-19 截图）。Java 那行 fields("title", …) 对应的就是这段 JSON。响应拆解：

System.out.println("共 " + resp.hits().total().value() + " 件");
for (Hit<Product> hit : resp.hits().hits()) {
    System.out.println(hit.score() + " "
        + hit.highlight().get("title").get(0));
}
for (StringTermsBucket b : resp.aggregations()
        .get("brands").sterms().buckets().array()) {
    System.out.println(b.key().stringValue() + " = " + b.docCount());
}
:: imports 略；Product 为 record：title / description / brand / price
:: sterms = 字符串分桶（brand 是 keyword）；桶 key 转字符串即品牌名

跑起来，一轮端到端的控制台回显：

$ mvn -q compile exec:java -Dexec.mainClass=ProductSearch

2.63  <em>Wireless</em> <em>Headphones</em> WH-CH520

:: 得分由 BM25 依词频与文档长度现算，数值随数据集而异

两个词全中的两副耳机排最前，只含 wireless 的商品跟在后面——这就是相关性排序；品牌分布加起来正好是命中的五件，印证了"聚合只数命中文档"。

08解读：得分是算出来的，桶是写入时备好的

回显里有两组数字值得多看一眼。相关性得分（_score）的三个直觉：

  • 得分是算出来的，不是存出来的：BM25 综合词频、文档长度、词的稀有度，在查询时实时计算——同一份文档，换个查询词，得分完全不同；
  • 两个词全中，贡献翻倍：wireless 与 headphones 都命中的商品拿到两份词的贡献，稳压只中一个词的——这就是"两个词全中的耳机排最前"的原因；
  • 高亮跟着得分走：highlight 拿命中的词项回原文定位加标记，查询时现加，换个词标记立刻跟着换。

聚合为什么快？这是本期第二个钩子。聚合不重读文档——它读的是写入时就备好的两样东西：

  • 列存的文档值（doc values）：第 3 期讲过，segment 不可变、列存让排序聚合同样受益；keyword 字段每个唯一值一行，聚合顺着列数下去就行；
  • 全局序数（global ordinals）：官方口径，terms 聚合不直接收集字符串，而是给每个唯一值发一个整数编号再计数，原话是"带来重要的性能提升"；segment 不可变，序数表建一次反复用。

还有两处"诚实的标注"：响应里 sum_other_doc_count 与 doc_count_error_upper_bound 说明 terms 聚合是近似计数——唯一值太多时默认只回前十个桶，size 调大要掂量内存，官方还给 search.max_buckets 设了天花板。用得好聚合，先尊重它的边界。

09收纪律：该做的与别做的

  • ✅ 生产环境显式写 mapping——动态推断方便试验，但 text/keyword 的选择决定检索行为，建索引前想清楚；
  • ✅ 聚合、过滤、排序字段用 keyword / 数值类型——官方口径，别跟类型对着干；
  • ✅ 批量灌数据走 bulk——一行元信息一行文档；配合第 3 期组合拳：导入前关刷新，导完手动刷；
  • ❌ 把高亮文本当业务数据——高亮片段带 <em> 标记，是给前端展示的；业务逻辑一律用 _source 原文；
  • ❌ 对 text 字段硬开 fielddata 凑合聚合——官方明说显著增加内存；正确姿势是 keyword 或 keyword 子字段。

搜索"wireless headphones"命中 5 件商品，请求里同时带了 brand 的 terms 聚合。聚合结果的品牌桶计数范围是？

  • A. products 索引里全部 8 件
  • B. 命中的 5 件
  • C. 只统计第一个分片上的命中文档
  • D. 只统计主分片上的文档，副本不参与

11思考题

思考一：brand 建成 keyword、title 建成 text——如果反过来会各发生什么？要是"既想对品牌做模糊搜索、又想按品牌聚合"呢？

反着建，两边同时塌。brand 若建成 text：精确过滤 term: "Sony" 会被分词坑掉——标准分词器把 Sony 原样保留是小幸运，换成多词品牌（如 "Logitech G"）拆成两个词项后，term 查询整串就再也匹配不上；聚合直接 400，就是第 05 节那幕。title 若建成 keyword：整串标题变成一个词项，用户搜 wireless 什么都搜不到——倒排索引里根本没有这个词，只有一串完整标题。工程上的正确姿势是 multi-fields（一子多母）：title 建成 text 并挂一个 keyword 子字段（官方动态映射默认就给 text 字段配了 title.keyword），写入时一份原文两条索引路径，全文检索走 text、排序聚合走 keyword 子字段；brand 反过来也一样——建成 keyword 满足聚合，模糊搜品牌用 match 查询照样可用（keyword 字段上的 match 会退化为整串匹配，想分词搜就显式加 text 子字段）。一句话：不是"选一个"，而是"各配各的检索路径"，mapping 写的就是这份路线图。

思考二：本期聚合只统计命中的文档。如果运营想要"全站品牌分布"和"搜索结果品牌分布"同时出现在一个页面，请求该怎么发？一次请求能都拿到吗？

能，而且正是一次请求两份答案的标准场景：ES 的聚合体系里有桶聚合的嵌套与 global 聚合。普通聚合挂在 query 作用域下——只统计命中文档，这就是本期侧栏的"搜索结果品牌分布"；而 global 聚合会脱离查询作用域，对整个索引分桶——把它套在外层、里面再嵌一个 terms 聚合，拿到的就是全站品牌分布。一个请求体里两者并存：query 管 hits，普通 aggs 管命中的分布，global + terms 管全站分布，响应里按名字各取各的。代价也要知道：global 聚合每次都扫全索引的列存，大索引上它不吃查询条件的便宜，频控和缓存策略要分开评估。这道题的通用结论：ES 的"聚合作用域"是跟着查询走的，query 是聚合的默认过滤器，global 是显式的逃生门——理解了作用域，facets 页面怎么拼请求就再也不是玄学。

12本期要点与下期预告

带走这五句话：

  • 端到端搭出一个商品搜索：mapping 定类型 → bulk 上架 → Java 官方客户端一次请求拿命中 + 高亮 + 品牌桶；
  • text 与 keyword 一字之差两个世界：text 分词管检索，keyword 整串管聚合过滤，两样都要用 multi-fields；
  • 对 text 做 terms 聚合被官方拒绝（fielddata 默认禁用）——报错消息的最后一句就是药方；
  • 客户端与服务端同步发版：elasticsearch-java 9.5.4 配 ES 9.5.4，of 方法三行建连；
  • 聚合快在写入时：列存 doc values + 全局序数，查询只数桶不重读文档，且默认只统计命中的文档。
