01主从 Reactor 的源码落地

第 1 期我们用"老板接客、伙计干活"比喻过主从 Reactor，现在把它落到类上。NioEventLoopGroup 本身不干活，它是线程组工厂：构造时创建 N 个 NioEventLoop，每个 NioEventLoop 是一个绑定了专属线程和专属 Selector 的单线程执行器（源码位置 io.netty.channel.nio.NioEventLoop，transport 模块）。它的 run() 方法是个死循环：select 等 IO 就绪 → processSelectedKeys() 处理就绪事件 → runAllTasks() 跑任务队列。"一个线程一个 Selector"就是 Netty 高并发的地基。

ServerBootstrap.bind(port) 之后到第一个连接进来之前，源码里发生了什么？两条调用链概述如下（只看主干）：

# bind 引导链：渠道创建 + 注册进 boss 组
ServerBootstrap.bind(port)
 └─ AbstractBootstrap.doBind()
     └─ initAndRegister()
         ├─ new NioServerSocketChannel()        // 建渠道 + 空 pipeline
         ├─ init(channel)                       // 往 boss pipeline 塞接纳器
         └─ config().group().register(channel)  // 交给 boss 组的某个 EventLoop
             └─ AbstractUnsafe.register0()
                 └─ doRegister()                // javaChannel().register(selector, 0)

# accept 交接链：boss 收下连接，转手给 worker
NioEventLoop.run() → processSelectedKeys()
 └─ NioServerSocketChannel 读到 OP_ACCEPT
     └─ AbstractNioMessageChannel.doReadMessages()
         ├─ new NioSocketChannel(...)           // 子渠道在此诞生
         └─ pipeline.fireChannelRead(child)     // 连接作为事件流过 boss pipeline
             └─ ServerBootstrapAcceptor.channelRead()
                 ├─ child.pipeline().addLast(...) // 用户 handler 装进子管道
                 └─ childGroup.register(child)    // 从 worker 组挑一个 EventLoop
                     └─ 子渠道注册 OP_READ，之后读写全在 worker 线程

第二段链里的 ServerBootstrapAcceptor 是答案所在：它是 ServerBootstrap.init() 时自动加到 boss pipeline 尾部的内部 handler。boss accept 出的每个 NioSocketChannel 以 channelRead 事件流到它手上，它把 childHandler() 里的 handler 装进子管道，再 childGroup.register(child) 挑一个 worker。这就是"你从没写过 accept 代码，连接却总能落到 worker 上"的机制。

读码坐标（均在 4.2 分支核实存在）io.netty.bootstrap.ServerBootstrap、io.netty.channel.nio.NioEventLoop / NioEventLoopGroup、io.netty.channel.socket.nio.NioServerSocketChannel / NioSocketChannel、io.netty.channel.AbstractChannelHandlerContext。4.1 与 4.2 在这些包路径上一致，差异在 EventLoopGroup 构造方式与默认分配器（见第 02、09 节）。

02ByteBuf 与内存池：arena、chunk 与引用计数

每秒几十万次 read，每次都向 JVM 要一块新内存再丢给 GC，分配和回收的成本都会被放大成性能墙。Netty 的解法是池化：PooledByteBufAllocator（io.netty.buffer，buffer 模块）的内存管理思想借鉴自 jemalloc，分三层看：

  • PoolArena——按线程分场。多个 arena 并存，分配时优先选当前线程绑定的那个，把锁竞争摊薄；
  • PoolChunk——按页切块。一个 chunk 默认 16MB，按 8KB 一页组织成完全二叉树做伙伴式分配；不足一页的小块用 subpage 位图切分，大小分级各走各的路径；
  • PoolThreadCache——线程本地回收站。release 归还的块先进线程本地缓存，下次同规格请求直接命中，连 arena 都不用碰。

池化内存不归 GC 管，生命周期就得自己记账，这就是引用计数：AbstractReferenceCountedByteBuf 给每个 ByteBuf 维护 refCnt，初始为 1；要在异步链路上多传一手就 retain() 加一，谁最后用完谁 release() 减一，减到零归还内存池。纪律是"谁传递谁 retain、谁消费谁 release"——忘了 release 是泄漏，多 release 是 double free。

泄漏了怎么抓？io.netty.util.ResourceLeakDetector（common 模块）在对象创建时采样挂一个弱引用哨兵，若 GC 回收时引用计数还没归零，就打出 LEAK: ByteBuf.release() was not called... 和访问轨迹。四个级别：DISABLED 关闭、SIMPLE 默认（约 1% 采样，只报不记轨迹）、ADVANCED（采样并记完整轨迹，排障首选）、PARANOID（100% 全采样，压测专项）。开法一行：-Dio.netty.leakDetection.level=ADVANCED。

版本注（4.2 的真变化）4.1 的默认分配器就是 PooledByteBufAllocator；4.2 起默认换成 AdaptiveByteBufAllocator——region 化、按负载自调优、不依赖 sun.misc.Unsafe、对虚拟线程友好的新实现。要回 arena 版池化，设 -Dio.netty.allocator.type=pooled。生产在 4.1、新项目在 4.2 的团队，看到的默认行为不一样；但读源码仍建议从 PooledByteBufAllocator 读起，arena/chunk 是理解一切池化的母题。

03Pipeline 双向传播：一条链，两个方向

每个 channel 一条 pipeline，链上是 head、若干 handler、tail。关键是事件分两个方向走：入站事件（channelRegistered / channelActive / channelRead……）由框架触发，从 head 向 tail 流，只经过 inbound handler；出站操作（write / flush / connect / bind……）由业务代码发起，从 tail 向 head 流，只经过 outbound handler。

这直接回答一个高频困惑：为什么 outbound handler 要放在发起写请求的 inbound handler 前面（更靠 head 侧）才生效？因为出站事件从 tail 向 head 传播，ctx.write() 只经过"当前节点到 head 之间"的出站处理器；编码器 addLast 在业务 handler 后面，根本不在路径上，等于白加。三个传播入口也就分清了：

  • ctx.fireChannelRead(msg)：向 tail 方向把接力棒交给下一个 inbound 节点——控制的是"下一个人是谁"，不传就短路整条入站链；
  • ctx.write(msg)：从当前节点出发向 head 做出站传播，只经过自己前面的出站 handler；
  • channel.writeAndFlush(msg)：从 tail 重新发起整条出站链，路上所有出站 handler 都会过一遍。

传播的发动机在 io.netty.channel.AbstractChannelHandlerContext：fireChannelRead 调 findContextInbound() 找下一个入站节点，write 调 findContextOutbound() 反向找——所谓"传播"，不过是沿双向链表找下一个匹配者、递归 invoke 而已。

04Netty 的"零拷贝"到底指哪几处

"零拷贝"是面试八股重灾区，因为它不是一次技术，而是四处（外加常被算上的第五处）各自独立的工程选择。逐处说清"省掉了哪一次拷贝"：

  • CompositeByteBuf 组合视图：把多个 ByteBuf 逻辑拼成一个整体（典型：协议头 + 包体），底层存储各归各，省掉了"把多段内容复制进一个大缓冲区"的那次拼接拷贝；
  • slice / duplicate 视图：与原 buf 共享底层存储，只各持一套读写指针，省掉了"截取子区就要复制一份"的拷贝（注意视图与本体共享 refCnt 语义上的内存，释放要小心 retain）；
  • FileRegion（sendfile）：静态文件下发走 transferTo，数据从内核页缓存直达网卡，省掉了"内核缓冲区 ↔ 用户态缓冲区"一进一出的两次 CPU 拷贝，文件传输全程不进用户态；
  • writev 聚集写：多个 ByteBuf 一次系统调用批量写出（scatter/gather），由网卡按段自取，省掉了"先在用户态攒成一个大缓冲区"的拷贝——writev 对应读方向的 readv 亦然。

常被算上的第五处堆外内存（DirectByteBuffer）：socket 写出时内核拿不到堆内地址，JVM 得先把堆内缓冲复制到堆外；Netty 默认分配堆外 ByteBuf，省掉了"堆内 → 堆外"那次拷贝。前两处是"用户态少拷贝"，后三处是"根本不过用户态"，混为一谈就答不真切。

05读码路线图：六步走完主干

两百万行仓库别硬啃。方法：clone 后 checkout 到发布 tag（本文按 netty-4.2.18.Final 核对），从 example 跑通一个 echo，沿调用链自顶向下，每步只回答一个问题：

1
example 模块进：example/src/main/java/io/netty/example/echo/EchoServer.java——回答"用户视角一次 echo 的生命周期是什么"（bind → accept → read → write → close）。
2
引导链：ServerBootstrap.bind() → AbstractBootstrap.initAndRegister() / doBind()——回答"channel 在哪创建、pipeline 在哪组装、注册到了哪个线程"。
3
事件循环：NioEventLoop.run()——回答"一个线程怎么同时伺候 IO 事件和任务队列"，顺带看它对 JDK select 空转 bug 的规避。
4
读路径分叉：AbstractNioMessageChannel（accept 分支）与 AbstractNioByteChannel（read 分支）里的 Unsafe.read()——回答"一次 read 分配多大的 ByteBuf、谁来释放"。
5
传播机制：DefaultChannelPipeline / AbstractChannelHandlerContext——回答"fire* 怎么找下一个入站节点、write 怎么反向找出站节点"。
6
内存收口：PooledByteBufAllocator → PoolArena / PoolChunk / PoolThreadCache 与 AbstractReferenceCountedByteBuf——回答"一块内存在池里怎么进出、refCnt 谁加谁减"。

三条纪律：从 example 进不从 util 进（工具类没有上下文）；带着问题读，每步只追一条链，见分叉先跳过；用调试器别用眼睛——EchoServer 里打断点单步走一遍 bind 和 read，比盯两小时源码有效。

06架构师视角：能搬回自己系统的三件事

串行无锁的线程模型

Netty 敢在 handler 里不写锁，靠的是"channel 终身绑定一个 EventLoop"：同一连接的所有事件都在同一线程按序执行，竞争根本不存在。这套思路在微服务里的对应物是一切"每 X 一个串行队列"的场景——长连接网关（推送、IM、IoT）、按订单 ID 哈希到固定线程的消费模型。另一面同样重要：EventLoop 被阻塞，这条线程上几百个 channel 全卡死，所以 Netty 提供 addLast(businessGroup, handler) 把慢业务挪到独立线程组——对比 Tomcat"一请求一线程"，这是两种定价，网关类组件该选前者。

责任链的工程化

我们都在 Spring 里写过 HandlerInterceptor 和 Filter，Netty 把责任链做出了三个可抄的细节：节点拿 ctx 而不是整条链（传播控制权在节点手上，可短路可跳段，测试时 mock 一个 ctx 即可）；双向传播让编解码天然对称（同一条链正着走读、反着走写）；运行时热插拔。网关插件化——鉴权、限流、审计、协议转换各占一节，按路由动态装卸——照这个骨架搭，比 if-else 堆砌体面得多。

池化与引用计数的成本观

池化不是免费午餐：省下的是 GC 和 malloc，付出的是引用计数纪律与排障复杂度。Netty 的配套值得整体搬走——采样式泄漏检测（默认 1% 采样 + GC 兜底报告，生产常开成本可控，压测切 PARANOID 全量）。评估自己系统要不要池化，看四件事：分配频率、对象大小分布、GC 表现、出事后能不能查。4.2 把默认分配器换成自适应版，正是官方在"性能上限"与"新 JVM 兼容、运维简单"之间重新定价——连 Netty 都不把池化当信仰，只当账。

07随堂小测

每题点击选项立即反馈 · 共 4 题

1. boss 线程 accept 到新连接后，是通过什么机制把连接交给 worker 组的？

  • 为新连接临时创建一个线程去处理
  • boss pipeline 尾部自动加入的 ServerBootstrapAcceptor 收到 channelRead(child) 后调用 childGroup.register(child)
  • worker 组定时轮询 boss 维护的待交接连接队列

2. 业务 handler（inbound）里发起的 ctx.write()，为什么要求编码器（outbound）加在它前面才生效？

  • 出站事件从 tail 向 head 传播，ctx.write 只经过当前节点到 head 之间的出站 handler，编码器放后面不在路径上
  • 因为入站事件从 head 向 tail 传播，编码器必须抢在解码器之前拿到数据
  • 因为编码器和解码器必须在 pipeline 里成对注册才能工作

3. ResourceLeakDetector 的默认级别和推荐的排障开法是？

  • 默认 SIMPLE（约 1% 采样）；排障时用 -Dio.netty.leakDetection.level=ADVANCED 调高并记录访问轨迹
  • 默认 DISABLED，需要手动打开才有泄漏检测
  • 默认 PARANOID，对每个 ByteBuf 全量检测

4. FileRegion 走 sendfile 下发文件，"零拷贝"省掉的到底是哪次拷贝？

  • 把多段 ByteBuf 拼成一个大缓冲区的用户态拷贝
  • 文件数据从内核页缓存拷到用户态缓冲区、再从用户态拷回内核 socket 缓冲区的两次 CPU 拷贝
  • socket 写出时从 JVM 堆内复制到堆外内存的那次拷贝

08思考题（点击展开解析）

思考一：如果让你给自己的 RPC 框架选线程模型，Netty 的方案里哪部分可以照抄，哪部分必须改？展开解析 ▾

可以照抄的是骨架：IO 线程与业务线程分离（对应 addLast(businessGroup, handler) 的 EventExecutorGroup 机制），以及连接绑定单一线程串行处理——同一连接的请求有序、handler 无锁，这两条放在任何 RPC 框架上都成立。必须改的是假设：Netty 的 handler 契约是"非阻塞、绝不卡 EventLoop"，而业务侧全是阻塞调用（JDBC、慢 RPC、文件），所以框架层要强制兜底——业务线程池 + 超时熔断 + 背压拒绝策略，不能指望使用者自觉。此外 Netty 不处理的领域正是你要补的：请求级超时传递、优雅停机（排空在途请求）、连接级限流与隔离。一句话：抄它的线程模型，补它的业务语义。

思考二：4.2 为什么敢把默认分配器从 PooledByteBufAllocator 换成 AdaptiveByteBufAllocator？这笔账对你评估自己系统"要不要池化"有什么启发？展开解析 ▾

Netty 换默认的动机有三：新 JVM 兼容（arena 版重度依赖 sun.misc.Unsafe，而 Unsafe 在新 JDK 上持续收紧）、虚拟线程时代（ThreadLocal 缓存绑定平台线程的假设被动摇）、运维成本（arena 版参数多难查，Adaptive 按观测负载自调优）。注意它没有删除池化，只是把"默认信仰"换成了"可选项"（io.netty.allocator.type=pooled 一键切回）。启发是：池化是道算术题不是信仰题——分配频率高、大小分布稳定、GC 压力可测、有泄漏检测手段时才值得上；条件缺两个，先用朴素实现，把采样式泄漏检测这类兜底设施先建好，比提前池化更划算。
