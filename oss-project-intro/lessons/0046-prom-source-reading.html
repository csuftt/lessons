00本期要点

  • Go 项目读法与 C/Java 不同：按"数据走哪条路、锁在哪、落盘在哪"三问读，顺着一条指标走，不从 main 顺读；

02Go 项目怎么读：带着三个问题进门

读 Go 项目和读 C/Java 项目手感不同：Go 社区习惯小接口、按包分职责，没有深到几十层的继承树，所以不建议从 main 第一行顺着读——会陷进装配代码里。更有效的姿势是带着三个问题，沿一条数据的路径走：

  • 数据走哪条路？——从被抓目标到查询结果，中间经过哪些包、哪些类型，路径上的每一站就是本期路线图；
  • 锁在哪？——Go 的并发无处不在，找到"谁持锁、锁什么"，就找到了这个系统的性能敏感区（Prometheus 的答案在 stripeSeries 的分片锁）；
  • 落盘在哪？——内存里的东西断电就没，找到顺序写的日志和封口的块，就找到了可靠性设计的全部底牌。

Prometheus 恰好是练习这套读法的绝佳样本：它的三个核心包——tsdb、scrape、promql——正好对应三问的落盘、路径与计算。下面逐站展开。

05决策一 · TSDB 两级存储：内存保写、磁盘保洁、WAL 保不丢

为什么这么设计？监控写入的特点是高频小样本：默认十五秒一个点，每秒可能有成千上万条序列各进一个点。磁盘最怕这种"为每个点付一次寻址"的写法；但数据又不能不放磁盘，否则存不下也查不快。Prometheus 的答案是把存储拆成两级：当前写入的head block 常驻内存，靠WAL 顺序日志兜底；每攒满两小时，封口成一个不可变的磁盘 block，后台再 compaction 合并成更长的块。写入路径的真实次序写在 tsdb/head_append.go 里：

head 里的序列长什么样？tsdb/head.go 的 memSeries 给出答案：每条序列一个结构，mmappedChunks 指着已落盘但还没进 block 的块，headChunks 是内存里正在写的最新块——注释里甚至自带一张 compaction 前后指针平移的示意图：before compaction 时 mmappedChunks=[p5,p6,p7,p8,p9]，前两个 chunk 存进 block 后指针平移成 [p7,p8,p9]、firstChunkID 从 5 变 7（memSeries 声明实拍见课程视频第 9 页；来源：github.com/prometheus/prometheus/blob/v3.14.0/tsdb/head.go，2026-09-20 实拍）。

官方文档对这套布局的口径更直接——"进行中的块保留在内存里，并未完整持久化"，由可回放的 WAL 保护；样本按两小时分组进块；WAL 以 128MB 段存放在 wal 目录，最少保留三个段以便覆盖至少两小时原始数据（官方《Storage》On-disk layout 节实拍见课程视频第 10 页；数据目录里每个 ULID 目录就是一个 block，内含 chunks、index、meta.json）。

换种做法会怎样？每条样本直接落盘：每次写入付一次寻址与 fsync，吞吐被磁盘吃掉，监控反而是最先拖垮业务机的那个；全部只留内存：断电全丢、存不下历史，查询也退化成全内存扫描。两级设计的账是——写吞吐归内存，读性能与压缩率归不可变块，崩溃安全归 WAL，三个承诺各找最便宜的机制兑现。

06钩子一 · 为什么 head 只留两小时

两小时这个数写在 tsdb/db.go：常量 DefaultBlockDuration = 2 * time.Hour，默认最小与最大块时长都是它。为什么不大一点、少压缩几次？因为 head 的内存账是"活跃序列数 × 每条序列的最近样本"：序列基数上万时，哪怕每条只留两小时，head 也要养着全部活跃序列的索引、标签与未封口的块——时间窗口每放大一倍，内存水位就抬高一截，而查询热点其实集中在最近的曲线。封口成 block 后数据变成只读列式压缩（官方口径平均每样本 1~2 字节），内存立刻卸下担子。顺带一提：默认数据保留期是十五天（RetentionDuration），更久的历史交给 remote storage 方案。两小时是官方在内存压力与压缩效率之间挑的平衡点，可调，但默认值别轻易动。

07决策二 · 抓取循环与服务发现：Pull 不是"定时轮询"四个字

很多人把 Pull 模型理解成"监控端定时轮询所有目标"。源码里的真相是两条异步流水线的配合：服务发现这边的 discovery.Manager 收到各机制（K8s、file_sd、consul……）的目标变更，聚合成"每个 job 的目标名单"，经 syncCh 通道推给抓取侧；抓取侧的 scrape.Manager 按名单维护每个 job 的 scrapePool——名单变了就 sync() 增删 scrapeLoop，每个循环按自己的 interval 抓取。两条线在 main 里接起来，就一行（main.go 第 1310~1321 行实拍见课程视频第 15 页）：

08决策三 · PromQL 引擎：分层查询，向量化按序列批量算

第 3 期讲过 PromQL 眼中只有即时向量与区间向量两种主力结果：即时查询回答"每条序列此刻的值"，区间查询按 step 逐步评估、一次算出整条曲线。向量化体现在按序列批量取数与计算：一次拉一条序列在窗口内的整段 chunk，算完再换下一条，摊平解释开销。

为什么 PromQL 敢做这么重的计算？三个前提都是架构送它的：数据本地——查询不跨网络RPC，磁盘就在本机；列式 chunk——同类数值紧挨着存放，解压一批算一批；block 不可变——历史块永不修改，倒排索引可以放心缓存，不用考虑失效。反过来说，如果把 Prometheus 的存储换成远程数据库、每次求值都走网络取数，这套当场算几百条序列的打法立刻就会被带宽和延迟拖死——PromQL 的激进，是两级存储喂出来的底气。

09三个能搬回自己项目的模式

  • 内存态 + 日志兜底——head 保写吞吐、WAL 保崩溃安全：凡"高频写、可重放"的数据，都可以用这套组合，不必每个写操作都做昂贵的一致性落盘；
  • 不可变数据块——两小时封口、永不修改：不可变换来免锁读、高压缩率与放心缓存，日志系统、时序库、消息存储都在用它；
  • 调度与执行分离——发现只出名单、抓取只管执行，配置热加载只改参数不换进程：把"谁该干活"和"怎么干活"拆成两层，系统才改得动。

11思考题

思考一：把 block 时长从两小时改成两天，系统各环节分别会发生什么？反过来改成两分钟呢？

改成两天：head 的内存水位先炸——活跃序列的最近样本、索引与未封口块在内存里多驻留二十四倍的时间，序列基数大的实例直接 OOM；同时每次封块的数据量变大，compaction 从"小步快跑"变成"大块慢炖"，单次压缩占用更长 I/O，失败重试的代价也更大；查询最新数据仍走 head，读热点不受影响。改成两分钟：内存压力骤降，但磁盘上出现海量小 block——每个 block 都要一份索引与 meta，打开一个查询要合并的块数暴涨，倒排缓存的命中率也随碎片化下降，compaction 反而要不停地把这些碎块再合并回去，写放大登场。两小时的本质是内存账与磁盘账的交点：head 承受"多久的写缓冲"成本最低、block 做到"多大"读放大与压缩率最划算。这类"分界参数"在自己的系统里同样存在——批处理攒多大、缓存留多久，答案都从两条成本曲线的交点来，而不是拍脑袋。

思考二：假设把 Prometheus 改成 Push 模型（目标主动推指标），服务发现与抓取循环这两条流水线要怎么改？会失去什么？

先看要改什么：scrapeLoop 的定时器循环可以删掉，换成接推送的接收端；但 scrapePool 的名单管理反而要留着——你得知道"哪些目标应该出现"，否则无法发现失联的目标。第一笔失去的账是up 信号的语义：Pull 模型里"抓取失败"是监控端亲历的事实，up 归零立刻可知；Push 模型里"没收到"有两种解释——目标挂了还是网络抖了？故障时的集体重试还可能反过来压垮监控端。第二笔是节奏控制权：interval 是监控端手里的旋钮，调密度、错峰、限流都不用惊动目标；Push 之后采样口径碎片化，rate 需要的固定窗口对齐也更难做。第三笔是配置热加载：现在改抓取间隔只需 ApplyConfig 加 reloader，Push 模型则要逐个目标通知变更，配置生效变成分布式协调问题。这套流水线的真正价值不是"谁请求谁"，而是监控端集中掌握名单、节奏与失败信号——这也是它敢用"笨办法"双实例做高可用的底气：每个实例独立全量抓取，挂一个另一个照常工作。
