OSS PROJECT INTRO · Pulsar 系列第 4 期：实战场景

把订单事件接进 Pulsar：从 starter 引入到死信队列的端到端实战

前三期你已经知道 Pulsar 为什么把计算和存储拆开、也亲手把服务端跑起来、拿到了 Topic 与订阅的概念地图——但都还没写过一行业务代码。这一期换真枪实弹：用 Spring Boot 3 官方的 spring-boot-starter-pulsar，把一个"下单成功后发订单事件"的最小系统端到端跑通——生产者发事件、消费者监听处理、失败重投、 poison 消息进死信队列，四件事一次做完。走完你会发现，前三期的每个概念（Topic、订阅、独占与共享、游标）都长在了某个注解或配置键上。

01场景设定：一条订单事件，多个下游要吃

场景刻意选小，但把消息队列最有价值的用法都装进去了：order-service 在下单成功后发布一条订单事件到 Topic order-events；积分、风控、通知三个下游各自用自己的订阅独立消费同一份事件——互不干扰、互不丢消息。这条链路如下图，一条事件被三份订阅各自取走，正是第 3 期讲的"发布-订阅与队列的统一体"在实战里的样子：

全程四条目标，做完一条勾一条：

  • ① 引入即用：只加一个 starter，不写一行手动建连代码，注入模板就能发消息；
  • ② 事件发布：下单成功后发出 JSON 格式的订单事件，拿到持久化确认；
  • ③ 监听消费：@PulsarListener 收到事件并处理，默认独占订阅自动提交确认；
  • ④ 失败兜底：构造一条"毒丸"事件，看它重投若干次后被转存进死信 Topic。

订阅模式（独占/灾备/共享/按键共享）与游标的原理，daily 线已有专课：《Pulsar 订阅模型深入：四种订阅、游标机制与 Key_Shared 保序》。本期只讲"在 Spring 里怎么用"，原理不换皮重讲；整体存算分离架构见 《Apache Pulsar 存算分离架构与 Kafka 对比》。

02依赖与版本：一个 starter，三份版本账本

Pulsar 接入 Spring Boot 的姿势在 Boot 3.2 之后简化到了一个依赖：Spring Boot 官方自带 spring-boot-starter-pulsar，自动配置由 Boot 直接提供（早先 Spring Pulsar 项目里那个 spring-pulsar-spring-boot-starter 只存在于 0.x 预览阶段，GA 后不再使用，老文章里的坐标别再抄）：

<dependency>
  <groupId>org.springframework.boot</groupId>
  <artifactId>spring-boot-starter-pulsar</artifactId>
</dependency>

版本号照例不写在依赖里，交给 Boot 的依赖管理统一管。本期按 Boot 3.5 线最新 3.5.16 锚定，它替你管好两层版本：Spring Pulsar 1.2.18（模板与监听注解的实现）+ Pulsar 客户端 4.0.11（底层网络与协议）。三个角色各管一摊：

组件版本由谁引入负责什么
Apache Pulsar（broker / standalone）4.2.4（当前 GA 稳定线）第 2 期安装的独立服务存消息、管订阅与游标
spring-pulsar1.2.18Boot 3.5.16 依赖管理PulsarTemplate、@PulsarListener 等编程模型
pulsar-client4.0.11同上（传递依赖）与 broker 之间的协议通信

版本线提醒：Spring Pulsar 已随 Spring Boot 4.0 进入 2.0.x 线（当前 GA 2.0.7），官方兼容矩阵的对应关系是——1.2.x 配 Boot 3.4/3.5，2.0.x 配 Boot 4.0。本系列钉在 Boot 3 线教学；升级 Boot 4 时 API 基本同形，但别把两条线的版本混搭。

其次是一份极薄的配置——src/main/resources/application.yaml：

spring:
  application:
    name: order-service
  pulsar:
    client:
      service-url: pulsar://localhost:6650   # 二进制协议端口，与第 2 期 standalone 一致
    admin:
      service-url: http://localhost:8080     # HTTP 管理端口；要自动建 Topic 才会用到

这两个默认值其实正好是 Pulsar 的默认端口——pulsar://localhost:6650 与 http://localhost:8080（出处：Spring Boot 参考手册 Apache Pulsar Support 一节），第 2 期跑的 standalone 没改端口的话，这两行都可以省。显式写出来的好处是：换环境时一眼就知道该改哪里。若想让应用启动时自动创建 Topic，加一个 PulsarTopic Bean 即可（走 admin 端口）；本期不依赖它。

03生产者：订单事件的定义与发布

先定义事件本体。一个 Java record 就够了，框架看到非原始类型，自动按 JSON schema 处理（这是 Spring Pulsar 的默认约定，不用注册 schema）：

public record OrderEvent(
        String orderId,      // 订单号：下游幂等的锚点
        String sku,
        int quantity,
        double amount,
        Instant paidAt) {}

然后是发布者。注入 PulsarTemplate<OrderEvent>，下单成功后一行发出去：

@Service
public class OrderEventPublisher {

    private static final Logger log = LoggerFactory.getLogger(OrderEventPublisher.class);
    private final PulsarTemplate<OrderEvent> pulsarTemplate;

    public OrderEventPublisher(PulsarTemplate<OrderEvent> pulsarTemplate) {
        this.pulsarTemplate = pulsarTemplate;
    }

    /** 下单成功后调用：发布订单事件（同步语义） */
    public void publish(OrderEvent event) {
        MessageId id = pulsarTemplate.send("order-events", event);
        log.info("订单事件已发布: orderId={}, messageId={}", event.orderId(), id);
    }
}

这段代码有三处值得停下来看：

  • Topic 名可以直接写短名：order-events 会被解析成 persistent://public/default/order-events（默认租户/命名空间）。想让"事件类型绑定固定 Topic"，也可以在 record 上标 @PulsarMessage(topic = "order-events")，之后连 Topic 参数都省了；
  • send() 是同步语义：阻塞到 broker 确认消息已持久化才返回 MessageId——订单这种不能丢的事件，用同步；吞吐优先的日志埋点类事件，换 sendAsync() 拿 CompletableFuture，这是官方文档明确给出的两条路；
  • 没写任何建连代码：PulsarClient、生产者工厂、模板全部由 Boot 自动配置好，生产者实例默认还会被缓存复用（spring.pulsar.producer.cache.* 可调）。

给事件带上业务键：需要按订单号保序或路由时，用流式 API 定制消息：pulsarTemplate.newMessage(event).withMessageCustomizer(mb -> mb.key(event.orderId())).send()——key 进了消息元数据，分区 Topic 下同 key 落同一分区，配合按键共享订阅就是"同一订单串行处理"的地基（保序原理见 daily 线订阅模型一课）。

04消费者：一个注解接住事件

消费侧更短。任何 Bean 的方法标上 @PulsarListener，监听容器就自动建好（方法参数类型决定反序列化目标，JSON 照旧自动推断）：

@Component
public class PointsListener {

    private static final Logger log = LoggerFactory.getLogger(PointsListener.class);

    @PulsarListener(subscriptionName = "points-sub", topics = "order-events")
    public void onOrderEvent(OrderEvent event) {
        log.info("积分服务已处理订单事件: orderId={}, amount={}", event.orderId(), event.amount());
        // 加积分……
    }
}

三个默认行为，对应第 3 期的概念清单：

  • 订阅类型默认独占（Exclusive）：一个订阅同时只有一个消费者在干活，同订阅内天然有序——没特殊理由就保持默认；
  • 处理成功自动确认（ack）：方法正常返回，游标推进；这正是"broker 替你记账"的部分；
  • 一个订阅对应一个业务：积分、风控各自起 subscriptionName，同一份事件每人拿到一份完整副本——加一个下游不用动上游代码，这就是发布-订阅的红利。

启动应用（mvn spring-boot:run），下单后看日志，两端各有一行：

订单事件已发布: orderId=SO-20260919-0001, messageId=12:5:-1:0
积分服务已处理订单事件: orderId=SO-20260919-0001, amount=399.0

messageId 是 ledger:entry:partition:batch 四段式——ledger 就是第 5 期要进 BookKeeper 源码时见到的账本。至此目标①②③达成：一个依赖、一个注解、一行发送，事件已经端到端流通。生产者/消费者更细的调优参数（批量、超时、接收队列）daily 线有专课：《Apache Pulsar 生产者/消费者调优》。

05失败怎么办：重投与死信队列

消费方法抛异常时，Spring 默认行为是否定确认（negative ack）：消息未确认，broker 会重新投递。重投节奏有官方默认值，也有两个可调的旋钮：

机制触发方式默认节奏调法
否定确认重投监听方法抛异常1 分钟后重投注解 properties：negativeAckRedeliveryDelay=10s
确认超时重投处理太慢、迟迟不 ack默认关闭（0）注解 properties：ackTimeoutMillis=5000
递增退避配合以上两者无注入 RedeliveryBackoff Bean（起始延迟/上限/倍率）
死信队列（DLQ）重投次数耗尽—DeadLetterPolicy Bean，仅共享订阅支持

一个反直觉的默认值值得划重点：异常抛出后消息默认等 1 分钟才重投。本地调试时不改这个参数，你会以为应用卡死了——其实消息在 broker 那边安静地排队等待重投。测试时把它调小（如 10s 或 1s），上线按业务容忍度定。

死信队列解决的是"重投多少次都没用"的消息——字段非法、上游数据坏掉的那类"毒丸"。它的用法官方文档给得很直白，照抄改两个值即可：

@Configuration
public class PulsarErrorHandlingConfig {

    /** 重投 3 次仍失败 → 转存进死信 Topic */
    @Bean
    DeadLetterPolicy orderDeadLetterPolicy() {
        return DeadLetterPolicy.builder()
                .maxRedeliverCount(3)
                .deadLetterTopic("order-events-dlq")   // 显式指定；不指定按 <topic>-<sub>-DLQ 默认命名
                .build();
    }
}

@Component
public class RiskControlListener {

    @PulsarListener(subscriptionName = "risk-sub", topics = "order-events",
            subscriptionType = SubscriptionType.Shared,   // DLQ 只支持共享订阅！
            deadLetterPolicy = "orderDeadLetterPolicy",
            properties = { "ackTimeoutMillis=5000" })
    public void onOrderEvent(OrderEvent event) {
        // 金额非法即视为毒丸：抛出异常触发重投
        if (event.amount() <= 0) {
            throw new IllegalArgumentException("非法金额: " + event.amount());
        }
        log.info("风控已放行订单: orderId={}", event.orderId());
    }
}

四个关键点，个个都是官方文档的原文口径：

  • 只有共享（Shared）订阅支持 DLQ，独占与灾备都不行——所以这里必须显式把订阅类型改成 Shared（四种订阅的语义差异见 daily 线订阅模型课）；
  • 死信 Topic 建议显式命名：不指定时默认名是 <topicname>-<subscriptionname>-DLQ；官方文档特别提醒，Topic 一旦分区，默认名里会混进 partition-<n>，干脆一开始就写死名字；
  • 重投来源二选一：要么异常否定确认，要么确认超时（上面的 ackTimeoutMillis），次数记满 maxRedeliverCount 后由消费者把消息转存进死信 Topic；
  • 死信也要有人接：再挂一个普通监听器盯着 order-events-dlq，告警、落库、人工排查都从这里走。
@PulsarListener(subscriptionName = "risk-dlq-sub", topics = "order-events-dlq")
public void onDeadLetter(OrderEvent event) {
    log.warn("进入死信, 需人工介入: orderId={}", event.orderId());
}

把毒丸事件（amount=-1）发出去，应用日志会依次打出三段：处理失败的异常栈 → 数次重投 → 最后死信监听器的告警行。目标④达成——消息一条没丢，只是从"正常通道"转进了"人工通道"，这正是死信队列的全部意义。可靠性全链路（ack、副本、持久化的整体视角）daily 线有更深的专课：《消息到底丢在哪：消息可靠性全链路》。

顺手要做的实验：把毒丸事件发一条，观察日志里的重投节奏；再把 maxRedeliverCount 改成 0 重发一条，看它"秒进"死信——两个数字一对比，重投与死信的接力关系就不用背了。

06随堂小测

每题点击选项立即反馈 · 共 3 题

1. Spring Boot 3 应用接 Pulsar，官方推荐的依赖是哪个？

  • org.springframework.pulsar:spring-pulsar-spring-boot-starter
  • org.springframework.boot:spring-boot-starter-pulsar
  • org.apache.pulsar:pulsar-client-all

2. 想给某个订阅配死信队列（DeadLetterPolicy），订阅类型必须是什么？

  • 独占 Exclusive——默认类型，越简单越能用
  • 灾备 Failover——主备切换专用
  • 共享 Shared——只有它支持死信队列

3. 监听方法抛出异常后，消息默认多久后被重新投递？

  • 1 分钟——negative ack 重投的官方默认值，调试时常被误认为卡死
  • 1 秒——框架会自动用最快的节奏重投
  • 永不——异常即丢弃，需要自己写补偿逻辑

07思考题（点击展开解析）

思考一：为什么死信队列只支持共享订阅，独占订阅就不行？这暴露了"失败责任在谁"的什么差异？

先把现象钉死：官方文档明确写着 DLQ 需要消费者使用共享订阅类型，独占与灾备不可用。原因要从游标的记账方式找：Pulsar 的重投与死信转存，依赖消费者对"单条消息"的精细反馈——哪条否定确认了、哪条确认超时了、这条已经重投几次了，都要按消息粒度记在订阅的游标账本上。共享订阅天然就是"逐条 ack/nack"的模型：多个消费者抢着消费，谁处理哪条各记各的账，单条失败不影响整批，重投计数自然挂在单条消息上。而独占订阅的优化取向是批量、顺序：一个消费者独占整个订阅，确认可以按累计进度推进（cumulative ack），重投的最小单位退化成"从某个位置起的一段"，没有清晰的"这一条失败了几次"账本，死信转存的判定依据就不存在了——不是框架偷懒，是模型对不上。引申到设计层面：独占订阅里消息失败的责任主体是整个消费者会话（挂了重启、从头或从最近确认点继续），共享订阅里责任主体是单条消息（逐条记账、逐条处置）。做消息系统选型时先问自己一句：我们的失败处理要精确到"这一条"，还是"这一段"？要精确到条，就接受共享订阅的代价（无顺序保证、每个消费者独立 ack）；要顺序，就别指望死信队列替你兜底，得在应用内自建重试表或补偿任务。两边都有代价，没有免费午餐。

思考二：send() 明明"阻塞到持久化才返回"，为什么下游还是可能收到重复事件？生产者侧和消费者侧各该做什么？

很多人把"同步 send"误解为"绝不重复"，其实持久化确认只解决了一半问题。拆开看时序：生产者发出消息 → broker 落盘 → 确认返回。若确认在网络上丢了或超时，生产者侧看不到成功，可能重发；broker 那边第一条其实已经落盘成功——于是同一事件出现两份。这正是消息系统默认承诺 at-least-once（至少一次）而不是"恰好一次"的原因：宁可重复，不可丢失，重复由业务侧消化。生产者侧能做的是收窄重复窗口：开启去重相关配置让 broker 按生产者序列号去重（producer name / sequence id 的幂等机制），或业务上给事件带全局唯一 ID 由 broker 的 deduplication 兜住；但这些都有适用边界，跨 Topic、跨重试路径的场景仍可能漏。所以消费者侧的幂等才是最后一道防线，也是本期代码里 orderId 真正的用途：加积分前先查"这笔订单的积分加过没有"——数据库唯一约束（orderId+业务动作做唯一键）、或状态机条件更新（只有"待加积分"能流转到"已加"）都是标准做法。一句口诀收束：投递语义交给消息系统兜底，业务正确性靠幂等设计兜底——把两件事混在一层，哪件都做不干净。
