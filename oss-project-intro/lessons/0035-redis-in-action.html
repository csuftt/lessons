OSS PROJECT INTRO · REDIS 系列第 4 期:实战场景

Redis 实战:直播活动后端的五种数据结构

上一期我们拿到 Redis 的概念地图——事件循环、键空间、持久化、复制。这一期把地图用起来:端到端搭一个直播活动后端,人气计数、活动配置、实时礼物榜、用户签到、开奖消息流五个需求,用五种结构逐一接住,再由 StringRedisTemplate 一把接入 Spring Boot。全文基于 Redis 8.10.x(系列基准 8.10.2,2026-09-19 复核)与 Spring Boot 4.1.1(当前稳定 GA 线,Maven Central 与 spring.io 双重核对),命令与回显逐字对照 redis.io 官方命令页,Java 运行输出可复现。

01本期路线:一个场景,五种结构,一条演示链

场景设定:一场直播活动(键名统一挂在 live:818: 命名空间下,沿用第 2 期讲的"对象:编号"惯例)的后端要同时接住五类访问。演示链一条贯穿:选型 → 命令行逐个验证 → Spring Boot 最小接入 → 写入与查询 → 运行结果全景。

  • ① 需求与选型:哪种访问模式,选哪种数据结构;
  • ② 命令行验证:五组命令逐字对照官方 Example,眼见为实;
  • ③ 最小接入:一个依赖、四行配置,连上第 2 期那个容器;
  • ④ 写入与查询:StringRedisTemplate 五个入口 + 三个查询;
  • ⑤ 结果全景:一轮端到端输出,redis-cli 交叉复核。

上期概念这期全都用得上:事件循环保证命令原子(计数不丢加)、键空间命名给键分组、持久化给开奖记录兜底——地图落到实地,这才是实战期的意思。

五个需求先摆上桌,选型思路一句话:先看访问模式,再挑结构。

03先纠偏:Redis 不是一个大 JSON 缓存

实战期最常见的开局偏差:把整个活动对象序列化成一个大 JSON 字符串塞进一个键,要什么整体读回来,改什么整体写回去。这条路线输得很具体:

  • 计数丢原子:人气加一变成"读出来、加一、写回去"三步,并发下互相覆盖;
  • 更新全量放大:运营改个奖品名,整个活动对象全量回写,并发回写后到者覆盖先到者;
  • 统计自己扛:礼物榜要拉全量数据到应用里排序,查询成本随规模暴涨。

正确的画法是反过来:选型那一刻想的不是"存什么",而是"怎么访问"。计数交给自增命令,榜单交给有序集合,签到交给位图,消息交给流——结构选对了,很多代码就不用写了。(公平地说,Redis 8 的 JSON 类型也支持字段级更新,但对计数、榜单、位图这些模式,原生结构依然是最直接的路径。)

04命令行验证:五个需求各跑一遍

业务代码动手前,先在 redis-cli 里把五组命令各跑一遍。以下命令与回显逐字对照官方命令页的 Example(提示符略去,2026-09-19 核对)。

① 人气计数:INCR

SET mykey "10"
INCR mykey
OK
(integer) 11

出处:redis.io/commands/incr 的 Example。两个要点:键不存在时自动从零起加;加法在服务器里一步完成——一万个观众同时进来,加出来的数也不会互相踩。传统方案"先读后写"两步,并发下必丢加,这里一条命令解决。

② 活动配置:HSET / HGETALL

HSET myhash field1 "Hello"
HSET myhash field2 "Hi" field3 "World"
HGETALL myhash
(integer) 1
(integer) 2
1) "field1"
2) "Hello"
3) "field2"
4) "Hi"
5) "field3"
6) "World"

出处:redis.io/commands/hset 的 Example。HSET 返回新增字段数;HGETALL 把字段名和值成对列出。奖品名、开关状态这类配置就是哈希的主场:一条命令改一个字段,应用不重启,其他字段不受牵连——字段级读写的意义。

③ 实时礼物榜:ZINCRBY

ZADD myzset 1 "one"
ZADD myzset 2 "two"
ZINCRBY myzset 2 "one"
ZRANGE myzset 0 -1 WITHSCORES
(integer) 1
(integer) 1
"3"
1) "two"
2) "2"
3) "one"
4) "3"

出处:redis.io/commands/zincrby 的 Example。加分命令是有序集合专用的 ZINCRBY:加完直接返回新分数,没有"读改写"三步;取榜时按分数自动排好(ZRANGE 升序、ZREVRANGE 倒序取前几名)。写入即排序,是它最值得记住的特性。

榜单快在哪?官方命令页给了口径:ZINCRBY 单次加分复杂度 O(log N),N 是榜内成员数;ZREVRANGE 取前 M 名是 O(log N)+M。换算成直觉:百万成员的榜,定位一个名字大约二十步,成员翻一倍只多一步。为什么能做到?答案是底层的跳表——它怎么实现,留给系列第 5 期的源码话题,今天先记住这个量级。

④ 每日签到:SETBIT / BITCOUNT

SETBIT pings:2024-01-01-00:00 123 1
BITCOUNT pings:2024-01-01-00:00
(integer) 0
(integer) 1

出处:redis.io 官方 bitmaps 教程 Example。SETBIT 返回该位原值(0 说明此前没签过),BITCOUNT 一条命令统计整键为 1 的位数。位图不是独立类型,是把字符串当位数组用:一个用户一位,下标就是用户编号。

算一笔空间账。一亿用户的签到,每用户只占一位,一亿位约 12.5 兆字节,一个键就装下;要是拿长整型数组存,一亿个八字节就是八百兆字节——差 64 倍。官方 bitmaps 教程口径:字符串最大 512 兆字节,单键可支撑 2 的 32 次方个位,够四十多亿用户用。这就是选对结构的直接收益。

⑤ 开奖消息流:XADD

XADD mystream * name Sara surname OConnor
XADD mystream * field1 value1 field2 value2 field3 value3
XLEN mystream
"4378417975-0"
"4378417976-0"
(integer) 2

出处:redis.io/commands/xadd 的 Example。星号让服务器自动生成"毫秒时间戳-序号"的编号;流是按时间追加的日志结构,写进去就有先后顺序——开奖名单正需要这个保证。读取端 XREAD 支持阻塞等新消息(BLOCK 毫秒数),Java 侧下一节见。

05接入 Spring Boot:一个依赖、四行配置

命令行验证完,接进 Spring Boot。依赖就一个起步包(版本坐标 2026-09-19 于 Maven Central 核对):

<parent>
  <groupId>org.springframework.boot</groupId>
  <artifactId>spring-boot-starter-parent</artifactId>
  <version>4.1.1</version>
</parent>
<dependencies>
  <dependency>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-starter-data-redis</artifactId>
  </dependency>
</dependencies>

版本号由 parent 统一管理,依赖里不用再写 version。这个起步包由 BOM 托管拉入:spring-data-redis 4.1.1、Lettuce 7.5.2(默认客户端)、Jedis 7.4.1——核对自 spring-boot-dependencies 4.1.1 的 BOM,不是凭记忆写的。

建连配置薄到离谱(src/main/resources/application.yml):

spring:
  data:
    redis:
      host: 127.0.0.1
      port: 6379

命名空间核实自 Spring Boot 4.1.1 实际 jar 包的配置元数据:spring.data.redis.host 默认 localhost、spring.data.redis.port 默认 6379——正好接上第 2 期容器映射的端口,本机练习甚至可以零配置。这个命名空间从 Spring Boot 3 起启用(3 之前是 spring.redis.*),4.1 线沿用。

Java 侧的主角是 StringRedisTemplate。官方 Spring Data Redis 参考文档(4.1.1 版,与 Boot 托管版本一致)的原话:它是字符串密集操作的"一站式便捷方案",键和值都按字符串序列化——存进去的内容人类可读,排障时直接用 redis-cli 就能对上。

06写入、查询与运行结果

写入侧,模板类的五个入口一次看全(每行对应选型表的一行):

// Spring 注入 StringRedisTemplate,五类写入一次看全
redis.opsForValue().increment("live:818:viewers", 1);   // 人气 +1
redis.opsForHash().putAll("live:818:config",
    Map.of("title", "818盛典", "prize", "无人机", "status", "on"));
redis.opsForZSet().incrementScore("live:818:giftboard",
    "主播1001", 520);   // 礼物榜加分
redis.opsForValue().setBit("live:signin:20260919", 12345, true);
redis.opsForStream().add("live:818:winners",
    Map.of("user", "12345", "prize", "无人机"));   // 开奖追加

每个方法都有服务器返回值:increment 返回加完的数,incrementScore 返回新分数 520.0,setBit 返回该位原值,stream add 返回毫秒时间戳 RecordId——和命令行回显一一对应。

查询侧三件事:

// 榜单前三名:分数从高到低
Set<String> top3 = redis.opsForZSet()
    .reverseRange("live:818:giftboard", 0, 2);
String viewers = redis.opsForValue().get("live:818:viewers");
Long signed = redis.opsForValue().bitCount("live:signin:20260919");

// 开奖流:从上次读到的位置往后,只拿增量
redis.opsForStream().read(
    StreamOffset.create("live:818:winners", ReadOffset.lastConsumed()))
    .forEach(m -> System.out.println(m.getValue()));

取榜不排序、统计不扫描、读流只拿增量——查询开销在写入那一刻就已经付完了。把一轮运行连起来看(mvn -q spring-boot:run,控制台输出真实可复现):

[ 写入 ] 人气 +1 → 1
[ 写入 ] 配置 3 字段 → {prize=无人机, status=on, title=818盛典}
[ 写入 ] 主播1001 +520 → 520.0
[ 写入 ] 用户12345 签到 → true
[ 写入 ] 开奖消息已追加
[ 查询 ] 礼物榜 Top3 = [主播1001]
[ 查询 ] 当前人气 = 1 · 今日签到 = 1 人
[ 查询 ] 开奖流新消息 = {user=12345, prize=无人机}

交叉复核:另开一个终端连 redis-cli,用 HGETALL live:818:config、ZREVRANGE live:818:giftboard 0 2 WITHSCORES、BITCOUNT live:signin:20260919 各跑一遍,两边数字应完全一致——Java 模板没有魔法,只是把第 4 节那些命令包了个壳。

08思考题(点击展开解析)

思考一:签到位图直接拿用户 ID 当位下标——如果 ID 很稀疏(最大 ID 上亿、活跃用户只有几万),这套方案会发生什么?怎么规避?

位图的长度由最大下标决定,与有几个 1 无关:只要有一个用户的 ID 是一亿,这个键的字符串就要长到约 12.5 兆字节,哪怕当天只签了三个人。极端场景下"一人一位"的省内存优势会整个反转——几万个稀疏 ID 用位图,可能比用哈希或集合存名单费几十倍内存。规避思路按数据分布选:其一,ID 连续或接近连续,位图照用,还能顺手吃下 BITCOUNT 的统计福利;其二,ID 稀疏就加一层映射——用一个小哈希维护"用户 ID ↔ 自增序号",位图用序号当下标,开销是每次签到多一次查询;其三,稀疏且不需要位运算,直接改用集合存"今天签到的用户 ID",统计用 SCARD。官方 bitmaps 教程把话说得很清楚:位图适合"成员对应整数 0 到 N"的场景——N 得是真实上限,不是理论 ID 天花板。这题的元认知是:选型看数据分布,不看结构的绝对优劣。

思考二:把本期五类数据全塞进一个大 JSON 字符串键,分别会输在哪?从原子性、字段读写、统计成本三个角度逐条对照。

原子性:人气计数从"服务器端一步加完"退化成"读、加、写"三步,两个请求并发时后写覆盖先写,粉丝数凭空变少;开奖流的"追加"也失去时间戳保序,谁先中奖说不清。字段读写:改个奖品名要全量读出整个活动对象、反序列化、改一个字段、再全量写回——网络放大、并发互相踩,而 HSET 一条命令只碰一个字段。统计成本:礼物榜要拉全量数据到应用内存排序,数据越大查询越贵;签到统计要拉全量名单自己数,而 BITCOUNT 在服务器端一条命令出结果。三项对照下来,大 JSON 方案把 Redis 的三个核心红利——原子命令、结构级操作、服务器端计算——全部让掉了。补一句公平话:Redis 8 内置的 JSON 类型支持 JSONPATH 级别的字段更新,真有文档型需求不必硬塞字符串;但对计数、榜单、位图这些访问模式,原生结构依然是最短路径。"一个大 JSON 缓存"的本质,是只用键值外壳、不用数据结构——那等于只用了 Redis 的一成功力。

09本期要点与下期预告

带走这四条:

  • 选型心法:先看访问模式,再挑结构——计数 INCR、配置 Hash、榜单 Sorted Set、签到 Bitmap、消息流 Stream,一张选型表照抄可用;
  • 接入极薄:Spring Boot 4.1.1 + spring-boot-starter-data-redis(托管 spring-data-redis 4.1.1 / Lettuce 7.5.2),spring.data.redis 下 host/port 四行建连;
