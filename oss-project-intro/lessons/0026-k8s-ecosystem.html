02CNCF 生态地图：以集群为圆心，按"离 API Server 的距离"分层

先认识圈子本身。CNCF（云原生计算基金会）2015 年随 Kubernetes 1.0 的发布一同成立，K8s 是它的种子项目——Google 把 1.0 捐给了这个新基金会（2015-07-21，Google Cloud 官方博客）。十年过去，CNCF 项目主页上列着 39 个毕业项目、38 个孵化项目（2026-09 在 cncf.io/projects 逐项清点）：Kubernetes、Prometheus、Envoy、etcd、Harbor、Argo、Helm、Flux 全在其中。别的生态是"围绕某项目的相关工具"，CNCF 是一整个以 K8s 为圆心的技术圈。

这张图记忆的重点不是六个名字，而是分层逻辑：离集群越近的越"基础设施"，离你越近的越"工作流"。Helm、Argo CD 离你最远——它们改变"你怎么提交期望"；Prometheus、Gateway API 贴着集群——它们扩展"集群怎么提供服务"；CRD/Operator 是插座，把任何新领域装成"一种资源"。最底下那行共同姿势是本期最重要的一句话，第 4 节展开。

03六类周边：是什么，什么时候需要它

地图有名字还不够，关键是"什么时候轮到它上场"。下表按引入频率从高到低排，每类给一句定位与引入信号，全部指向官方描述、不展开用法：

类别 · 代表项目是什么什么时候需要它
打包与发布 · HelmK8s 的包管理器（helm.sh 原话："The package manager for Kubernetes"；2026-09 查得最新版 4.3.0，CNCF 毕业项目）：一组 YAML 打成 Chart，参数化、版本化安装升级应用 YAML 超过两三个文件、想一键升级回滚时；装现成第三方应用几乎必经它
GitOps · Argo CD / FluxGit 里的声明就是期望状态，工具盯着仓库与集群的漂移自动对账（Argo CD 仓库自述 "Declarative Continuous Delivery for Kubernetes"，24.2k stars，2026-09 实测 GitHub）多环境频繁发布、发布要可审计、想让"回滚 = git revert"时
可观测性 · Prometheus + GrafanaPrometheus 拉取并存储指标、Grafana 出大盘，告警也在这层；CNCF 毕业项目生产集群第一天就需要。想深入再看 Prometheus 官方文档，这里只认门
镜像仓库 · Harbor自托管的企业级镜像仓库：存储、漏洞扫描、镜像签名、跨机房复制（CNCF 毕业项目）镜像不放公网、要审计谁推了什么镜像时；第 4 期清单里 image: 的来源就是它
网关与流量 · Gateway API / IstioGateway API 是 Ingress 的下一代官方 API（2023-10 发布 v1.0 GA）；Istio 做服务网格，把重试熔断灰度下沉到 SidecarIngress 注解力不从心、或要跨语言统一治理流量时
存储与安全 · CSI 驱动 / cert-manager 等CSI 标准接存储后端；cert-manager 自动签发续期 TLS 证书（官方自述："creates TLS certificates ... and renews the certificates before they expire"）挂持久卷要挑存储后端、证书申请人工跑到忘记续期时

两个衔接网关一层：Ingress 的运维视角与流量入口选型，见 官方文档 · Ingress；可观测一层：Prometheus 从 Pull 模型到 TSDB 的完整机制，见 Prometheus 官方文档。

04CRD 与 Operator：生态凭什么接上集群

上一节的工具从 Helm 到 cert-manager，来自不同公司、写着不同语言，凭什么都能"插"进 K8s？官方文档《Custom Resources》的定义是出发点："A custom resource is an extension of the Kubernetes API that is not necessarily available in a default Kubernetes installation."（自定义资源是对 K8s API 的扩展，默认安装里未必有。）而 CRD 就是声明这种资源的说明书——写一个 CRD 进集群，API Server 立刻为它开出一条新的 REST 路径：

# resourcedefinition.yaml 节选 · kubernetes.io《CustomResourceDefinitions》
apiVersion: apiextensions.k8s.io/v1
kind: CustomResourceDefinition
metadata:
  name: crontabs.stable.example.com   # 名字必须是 <plural>.<group>
spec:
  group: stable.example.com           # REST 路径：/apis/<group>/<version>
  scope: Namespaced
  names:
    plural: crontabs                  # kubectl get crontabs，短名 ct
    kind: CronTab                     # 你的清单里 kind 就写它
  versions:
  - name: v1
    storage: true                     # 存储版本只有一个
    schema:                           # openAPIV3Schema：字段校验
      openAPIV3Schema: { type: object, properties: { spec: { ... } } }

apply 之后，kubectl get crontabs、RBAC 授权、审计日志、kubectl get -o yaml 全套基础设施原样生效——第 5 期讲过的 client-go Informer/list-watch 对自定义资源同样适用：生态工具的开发者等于免费领了一套 K8s 的对账与存储机制。官方文档随后点题："The Operator pattern combines custom resources and custom controllers. You can use custom controllers to encode domain knowledge for specific applications into an extension of the Kubernetes API."（Operator 模式 = 自定义资源 + 自定义控制器，把某个应用的领域知识编码进 API 扩展。）第 5 期读过的 level-based 对账循环，就是 Operator 的全部内核。

举一个直观的例子。cert-manager 是一个 Operator，它把"证书签发"这个领域知识装成了两种资源：你声明一个 Certificate 对象（要什么域名、存进哪个 Secret），它的控制器就按期向 CA 申请、签发，并在证书快过期时自动续期——运维从"人肉跑 openssl、记续期日历"变成"声明期望、等对账"。和 ReplicaSet 对账 Pod 是同一个循环，只是领域知识换成了 PKI。

为什么说"万物皆资源"是 K8s 开放性的关键？反事实推一遍：如果扩展只能改源码、走插件二进制，每个生态项目都要自带鉴权、存储、CLI、高可用方案，K8s 的升级会扯上所有工具的重编译。CRD 把"加一种资源"变成"写一份 YAML"，把"写一个平台"变成"写一个控制器"——生态因此只需要对齐一个接口：API Server。这也回答了上一节那张图的"共同姿势"。

05十年演进：从 1.0 到 v1.37 的六个节点

版本节奏先立个坐标系：K8s 每年发三个小版本（1.37/1.36/1.35 三分支同时在维护，各约一年补丁支持，kubernetes.io/releases，2026-09-19 复核）。回头看六个改写了生态格局的节点：

1
2014-06 · 开源：Google 把内部 Borg 十余年集群经验开源成 Kubernetes（官方"10 Years of Kubernetes"回顾口径，2024-06）。
2
2015-07-21 · v1.0 与 CNCF 成立：1.0 在 OSCON 发布同日，Google 将它捐给新成立的 CNCF——API 承诺"v1 稳定兼容"是捐赠的前提。
3
2018-03-06 · 首个毕业项目：K8s 成为 CNCF 第一个毕业项目（cncf.io 公告）——生产采用、治理、社区健康度全过线。
4
2022-05 · v1.24 摘除 dockershim：内置 Docker 支持移除，运行时全面转向 CRI（containerd/CRI-O）——"K8s 不兼容 Docker"是当年最大的误读，实际只是不再内置那层垫片。
5
2023-10 · Gateway API v1.0 GA：Ingress 的继任者正式发布（2023-10-31，SIG-Network），流量入口有了角色分层的官方 API。
6
2026-08-26 · v1.37 "Garhwal"：67 项增强（16 项转正、23 项进 beta、27 项进 alpha，官方发布博客）；kubectl 支持更安全的 KYAML 输出格式；HPA 支持缩到零副本进入 beta。

读这份时间线有一个视角：K8s 的演进不是"加功能"，而是"把曾经的生态约定收编为官方 API"——Gateway API 收编了流量入口的碎片化，DRA 在收编 GPU 调度的碎片化。这也是判断"某个周边工具会不会被平台吃掉"的常用框架。

延伸一步HPA 的原理视角见 官方文档 · Horizontal Pod Autoscaler；v1.37 里 HPA 的 spec.minReplicas: 0 已进 beta，缩容不再受"至少一个副本"的旧约束。

06继续学习路线：官方文档地图 + 动手清单

kubernetes.io 的文档结构三棵树，查之前先分清去哪棵：

1
/docs/concepts —— 查"是什么"：概念字典，Pod、Service、调度架构都在这；想看底层为什么，回本系列第 3、5 期。
2
/docs/tasks —— 查"怎么做"：一段任务一篇：配探针、建 Secret、加 CRD，日常操作九成的疑问在这解决。
3
/docs/reference —— 查"字段与命令"：API 字段字典与 kubectl 命令参考，能配哪些字段、默认值是什么，以这棵树为准。
4
版本对齐的习惯：文档左下角切版本（当前默认 1.37），读文档先对版本，别拿最新文档对老集群。

动手建议一条：把第 2 期那个 minikube 集群重新拉起来，按第 4 期的清单纯手工交付一次，再用 Helm 4 装一个真实应用（官方 Quickstart 的 podinfo 就行，一条 helm install），最后用 kubectl get crd 看看 cert-manager 或 Helm 装完给你留下了哪些新资源类型——亲手摸过一次"生态工具往集群里注册了什么"，第 4 节的"万物皆资源"就从概念变成了体感。

08思考题（点击展开解析）

思考一：如果 K8s 不提供 CRD，扩展只能靠改源码或二进制插件，生态会变成什么样？CRD 到底"免费送"了生态工具哪些东西？展开解析 ▾

先数 CRD 送了什么。存储：CR 对象直接存进 etcd，一致性、备份、压缩全是集群现成的；鉴权与审计：RBAC、准入控制、审计日志对自定义资源原样生效；客户端全家桶：kubectl 原生可读写，client-go 的 Informer/list-watch 直接可用——第 5 期讲的"把集群读进内存"三大件零成本继承；对账框架：控制器模式、workqueue 限流重试、leader 选举，照抄内置控制器。

反事实世界则相反：每个生态项目自带数据库与鉴权体系，装一个监控要单独部署它的元数据存储；各工具 CLI 与配置格式互不相通；K8s 每次升级，所有工具跟着重编译适配。这正是很多"插件式架构"平台生态长不大的原因——扩展点定义了生态的形状：定义成"一种资源"，生态就长成声明式的样子；定义成"一个钩子"，生态就长成脚本的样子。K8s 把最重的公共部分（存储、一致性、鉴权、对账）做成底座，生态项目只需贡献自己那一点"领域知识"——cert-manager 只懂 PKI，Prometheus 只懂指标，Argo CD 只懂 Git 同步。分工程度之深，是 CRD 这份"说明书"换来的。

思考二：团队现在只有 kubectl 和手写清单，什么时候才真的需要 Helm、什么时候需要 GitOps？引入的判断标准是什么？展开解析 ▾

判断标准不是"工具火不火"，而是重复劳动和漂移风险何时超过工具本身的学习与运维成本。Helm 的引入信号：同一套 YAML 要在多环境以不同参数部署，你开始复制粘贴改端口改副本数——Chart 的 values 分层正是为这个；或者你要装第三方应用，对方只发 Chart。只有一个环境、几个应用时，手写清单加 kubectl apply 反而更直白。

GitOps 的引入信号比 Helm 更靠后：集群的实际状态开始偏离 Git 里的声明，而且没人知道是谁改的——凌晨的 kubectl edit、口头发布的配置、回滚全靠回忆。Argo CD/Flux 的价值是把"集群只认 Git"变成机器强制的对账，让每次变更有提交、可审计、回滚等于 revert；代价是多一套要维护的高可用组件，以及"改配置必须走 Git"的纪律。一个务实的顺序：手写清单 → 多环境了上 Helm → 多人协作与合规要求来了上 GitOps——每一步都由具体的痛触发，而不是由趋势触发，这也是第 2 期"先跑起来"在生态层的延续。

09本期要点与系列收尾

带走这几条：

  • K8s 是 CNCF 的种子项目，生态以它为圆心分层：打包（Helm 4.3.0）、GitOps（Argo CD/Flux）、观测（Prometheus+Grafana）、交付链（Harbor）、流量（Gateway API/Istio）、扩展插座（CRD/Operator）——先记分层逻辑，再记名字；
  • 共同姿势一句话：所有生态工具都是 API Server 的客户端，走同一套 API、认证与对账——学透第 3、5 期，等于拿了生态的万能钥匙；
  • CRD+Operator 是"万物皆资源"的落点：写一份 CRD 说明书，API Server 就为新领域开出 REST 路径，存储、RBAC、Informer 全套白送（官方 Custom Resources 页口径）；
  • 十年六个节点：2014 开源 → 2015 v1.0+CNCF 成立 → 2018 首个毕业 → 2022 摘 dockershim → 2023 Gateway API GA → 2026 v1.37（67 项增强）——演进主线是"把生态约定收编为官方 API"；
  • 学习路线：/concepts 查是什么、/tasks 查怎么做、/reference 查字段，读文档先对版本；动手从"重新拉起 minikube、Helm 装个 podinfo"开始。

系列收尾：Kubernetes 这个项目的入门就聊到这里——六期走完"认识、跑起来、概念与架构、实战交付、源码导读、生态地图"一条龙，从一句心智模型到 CNCF 版图，这个云原生地基你可以下手了。最新版本与完整文档认准官方文档 kubernetes.io。课程目录里还有其他开源项目的入门系列，感兴趣可以按需点开。
