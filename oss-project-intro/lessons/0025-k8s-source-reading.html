OSS PROJECT INTRO · KUBERNETES 系列第 5 期：架构与源码导读

Kubernetes 架构与源码导读：控制器模式、Informer 与两阶段调度

上一期我们把一个服务完整交付上了集群：一份清单、探针与资源底线、滚动更新与回滚。这一期进源码回答"凭什么"：对账循环凭什么敢只看当下不看过程（level-based 的底气）、控制器凭什么敢把集群读进内存（Informer 的 list-watch 与本地缓存）、调度器凭什么先过滤再打分（两阶段的取舍），再轻讲怎么从源码把控制面跑起来。一条"过滤到打分到绑定"的调度旅程串起调用链，收尾一张六步读码路线图。代码逐行核对自 tag v1.37.0 的 raw 文件。

02决策一：level-based 对账——为什么系统只看当下、不问过程

官方 API 约定（community 仓库 api-conventions.md）有个精彩的例子：spec 先从 2 改成 5、再改回 3，系统不要求"路过" 5，直接朝 3 收敛。原话是："the system's behavior is level-based rather than edge-based. This enables robust behavior in the presence of missed intermediate state changes."（系统行为按"水平触发"而非"边沿触发"，即使漏掉中间状态变化也能稳健收敛。）

为什么这么设计？中间事件一定会丢：watch 断线、控制器重启、发布窗口，任何一次抖动都会让"事件序列"出现缺口。如果系统靠"收到过什么指令"驱动（edge-triggered），丢一条指令就是永久性漂移，只能人工对账；改成 level-triggered，事件被降级成"该对账了"的提示——丢了无所谓，下一轮对账照着最新账本补齐。这就是第 3 期"组件挂了会自愈"的源码出处。落点在 replica_set.go：

// pkg/controller/replicaset/replica_set.go · syncReplicaSet（节选，v1.37.0）
rs, err := rsc.rsLister.ReplicaSets(namespace).Get(name)  // ① 从本地缓存读期望
allRSPods, err := controller.FilterPodsByOwner(rsc.podIndexer, ...)  // ② 缓存里认领实际
activePods := ...                                          // 统计存活的 Pod
if rsNeedsSync && rs.DeletionTimestamp == nil {
    manageReplicasErr = rsc.manageReplicas(ctx, activePods, rs)  // ③ 差额补齐
}
newStatus := calculateStatus(rs, activePods, ...)
// 源码原注释：Always updates status as pods come up or die.
updatedRS, err := updateReplicaSetStatus(logger, rsc.kubeClient.AppsV1()
    .ReplicaSets(rs.Namespace), rs, newStatus, ...)       // ④ status 写回

第 ③ 步是差额计算的全部：diff := len(activePods) - int(*(rs.Spec.Replicas))——少了补建（slowStartBatch 慢启动批量创建，1、2、4、8 翻倍，避免错误请求刷爆 API Server），多了并发删除。它从不问"刚才发生了什么"，只问"现在差多少"；处理失败 processNextWorkItem 把 key 限流重排（AddRateLimited），下一轮再来。换种做法会怎样？把控制器做成"命令处理器"，每次变更发指令——重启一次就丢账，靠人肉补偿的系统我们都维护过。

03决策二：Informer 的 list-watch——凭什么敢把集群读进内存

对账的前提是"随时知道实际状态"。如果每轮对账都去 API Server 全量 List，几千个控制器轮询起来，API Server 和它背后的 etcd（etcd 只管存，watch 链路由 API Server 对外转译）会被读请求打爆。K8s 的答案是 client-go 的 Informer：shared_informer.go 头注释写得像设计文档，三大件——

  • indexer 本地缓存：带索引的全量对象副本，控制器的读九成落在内存；
  • Reflector：ListAndWatch——原注释 "first lists all items and get the resource version at the moment of call, and then use the resource version to watch"，先 List 拿全量和版本号，再凭版本号 Watch 增量，断线从上次版本续传；
  • DeltaFIFO + sharedProcessor：变更先排队再分发，多控制器共享一份缓存与连接。

换种做法会怎样？纯轮询——延迟与压力双输；每个控制器各开一条 watch——连接数随控制器数爆炸，断线重连逻辑人人重写。SharedInformer 一份缓存多客户复用，把"读集群"变成"读内存"，这是整个控制器生态的公共底座。

04决策三：两阶段调度——先过滤保可行，再打分选最优

调度入口 schedule_one.go 的 schedulePod，一个函数讲完哲学：

// pkg/scheduler/schedule_one.go · schedulePod（节选，v1.37.0）
feasibleNodes, diagnosis, ... := sched.findNodesThatFitPod(ctx, fwk, state, podInfo)
if len(feasibleNodes) == 0 {              // ① 过滤后一个不剩：FitError，Pod 排队
    return result, &framework.FitError{Pod: pod, NumAllNodes: ..., Diagnosis: diagnosis}
}
if len(feasibleNodes) == 1 {              // 只剩一个：免打分直接用
    return ScheduleResult{SuggestedHost: feasibleNodes[0].Node().Name, ...}
}
priorityList, err := prioritizeNodes(ctx, sched.Extenders, fwk, state, pod, feasibleNodes)
node := framework.NewSortedScoredNodes(priorityList).Pop().Name  // ② 打分取最高 → ③ 绑定

过滤（Filtering）答"能不能放"，打分（Scoring）答"放哪最好"——官方 kube-scheduler 文档原话就是这两步。可行集为空不是错误而是排队：Pod 挂 Pending，事件里留下 0/42 nodes available: insufficient cpu 这样的原因（官方文档样例），绝不硬塞。过滤阶段还有个隐藏的量级控制：numFeasibleNodesToFind——大集群不扫全量节点，起始比例 50%、每 125 个节点再降 1 个百分点、下限 5%，凑够候选数就提前收工。绑定不是"调度器直接开容器"：结果经 RunBindPlugins 写回 API Server，kubelet watch 到 spec.nodeName 才认领执行——控制面各组件只跟账本对话。

换种做法会怎样？一阶段全量打分：每个插件对每个节点算分，万节点集群一轮调度就是几十万次评分，其中绝大多数节点连"可行"都算不上。两阶段把贵的计算只花在可行集上，还让"硬约束"（资源、污点、亲和）与"软偏好"（均衡、亲和权重）分属两组插件，扩展语义清爽。

05从源码把控制面跑起来（轻讲）

读码最好的伴侣是断点。仓库自带一条最小组件启动路径：hack/local-up-cluster.sh 把 apiserver、etcd、controller-manager、scheduler 在本机进程级拉起——加 -O 可复用预编译二进制免重复构建；日志末尾给一句 export KUBECONFIG=/var/run/kubernetes/admin.kubeconfig，照抄就能用 kubectl 连上这个"裸"集群。想单看某个组件，从 cmd/ 的 main 进：cmd/kube-scheduler/app/server.go 的 NewSchedulerCommand → scheduler.New，一条线读完启动流程。与第 2 期 minikube 的差别：minikube 起的是"生产形态"的沙盘，这条是"开发形态"——直接跑你工作区里的源码，改一行也能立刻验证。

延伸一步控制器模式不只内置：HPA 自动伸缩也是"改别人期望"的控制器——它调 Deployment 的 replicas，真正建 Pod 的还是 ReplicaSet 控制器。用法见 官方文档 · Horizontal Pod Autoscaler；服务交付后流量入口（Service/Ingress）的运维视角见 官方文档 · Ingress。

06一次调度决策的源码旅程 + 读码路线图

把决策三串成一条链——第 4 期交付清单里的每个 Pod，都走过这条路：

07架构师视角：能搬回自己系统的三件事

  • 用"期望 vs 实际的差额"建模，把事件当提醒而不是指令。自研平台里的定时对账、补偿任务常常写得心虚——"事件都到了才敢动"。level-based 给了相反的底气：处理逻辑幂等、只认最新状态，丢了就下一轮补；故障恢复从"回放历史"简化成"重读账本"；
  • 读多写少的系统：本地缓存 + 版本续传 + 周期对账三件套。Informer 的这套组合对配置中心、注册中心客户端是照抄级答案（watch 语义在客户端侧长成了这样）——先全量、后增量、断了从版本续、再定期全量兜底，四道防线各管一段；
  • 把贵的计算隔离在"可行集"内。先便宜的硬约束过滤、再昂贵的打分排序，过滤为空宁可排队也不硬塞——调度、推荐、风控引擎同样适用；顺带把"硬约束"与"软偏好"拆成两组扩展点，语义谁也不污染谁。

08随堂小测

每题点击选项立即反馈 · 共 4 题

1. spec 先从 2 改成 5 再改回 3，官方 API 约定说系统会怎么表现？

  • 必须先收敛到 5，再到 3
  • 5 被跳过，视为非法中间态回滚
  • 直接朝 3 收敛，不要求路过 5

2. Informer 的 Reflector 为什么要先 List 一次再 Watch？

  • 为了校验本地缓存的数据完整性
  • 拿全量数据与 resourceVersion 起点，之后凭版本号收增量
  • Watch 太贵，能用 List 就不用 Watch

3. 调度过滤后可行节点为 0，调度器会怎么做？

  • 挑一个得分最高的节点硬塞进去
  • 自动降低资源请求后重试
  • 返回 FitError，Pod 挂 Pending 排队等待

4. 调度器选出节点之后，容器是谁、在什么时候拉起的？

  • 调度器通过 Bind 插件直接在节点上启动容器
  • 绑定写回 API Server，kubelet watch 到后才调用运行时拉起
  • controller-manager 远程执行启动命令

09思考题（点击展开解析）

思考一：watch 断网十分钟、期间积压的所有事件全部丢失，控制器靠哪几层兜底把状态收敛回来？这暴露了 edge-triggered 方案的什么死穴？展开解析 ▾

逐层看。第一层：重连续传——Reflector 重连时带着断开前的 resourceVersion，API Server 从该版本回放此后所有变更，只要服务端历史窗口没滑走，一秒补齐。第二层：全量重新 List——版本号太旧已被压缩（对应 etcd 的 compacted 报错），Reflector 干脆重 List 一遍全量替换本地缓存，等价于" Forget everything, read the ledger again"。第三层：周期 Resync——就算什么都没断，MinResyncPeriod（默认 12 小时、乘随机因子错峰）也会把全部对象以 Sync 增量重放一遍，专治"事件到了但处理逻辑当时有 bug"这类静默漏账。第四层：workqueue 限流重试——对账本身失败也不丢：key 退避重排，下一轮再来。

反观 edge-triggered：它的正确性依赖"事件序列完整且按序处理"，丢一条就是永久漂移，而恢复手段只有一种——回放全部历史，代价与历史长度成正比。level-based 把恢复问题从"历史回放"降维成"重读当前账本"，成本与历史无关。这就是"不信任事件、只信任状态"的完整含义：不是不要事件，而是任何时候都可以不需要事件。

思考二：调度器为什么不把"过滤"与"打分"合并成一个插件、一次算完？拆成两阶段，牺牲了什么、换来了什么？展开解析 ▾

先看合并的隐含前提：每个节点都要算完整分数——包括那些最终会被硬约束一票否决的节点。资源不足、污点不匹配、亲和冲突的节点，它们的"得分"毫无意义却照常消耗插件计算；万节点集群一轮调度几十万次评分，热点插件还会互相拖慢。两阶段把 O(节点×插件) 的昂贵评分，压缩到只对可行集执行，再加 numFeasibleNodesToFind 的比例控制（50% 起步、下限 5%），可行集本身也有上限——性能是拆分换来的第一收益。

第二收益是语义：硬约束（Filter 插件）与软偏好（Score 插件）分属两组扩展点，"不允许"与"不 Prefer"不会被一个加权公式搅在一起，自定义插件注册时职责天然清晰。牺牲也明码标价：两阶段顺序执行，过滤结果的截断（候选上限）可能让真正最优的节点没进打分池——这是一种"足够好"对"全局最优"的让步；另外插件间想传递中间结果，要靠 CycleState 显式协作。与 etcd ReadIndex 的取舍同构：不追全局最优档，停在"默认档"，把最常见场景的性价比做到最高。

10本期要点与下期预告

带走这几条：

  • level-based 是 K8s 的一切：只认最新期望、不追中间事件（api-conventions 原话），manageReplicas 的 diff 就是全部逻辑（replica_set.go）；
  • Informer 三大件：indexer 本地缓存扛读、Reflector list-watch 凭 resourceVersion 续传、DeltaFIFO+sharedProcessor 分发——读集群变成读内存；
  • 两阶段调度：过滤答能不能、打分答放哪，可行集为空就排队（FitError/Pending），绑定只写回账本，起容器是 kubelet 的事（schedule_one.go）；
  • 从源码跑起来：hack/local-up-cluster.sh -O 拉起裸控制面，export KUBECONFIG 即可对接，cmd/ 下每个组件都有独立 main；
  • 读码路线：体感 → cache 包 → replica_set.go → schedule_one.go → 裸集群断点 → deployment_controller.go 横向拓展。
