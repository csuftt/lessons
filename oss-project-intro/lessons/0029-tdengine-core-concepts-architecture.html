OSS PROJECT INTRO · TDENGINE 系列第 3 期:核心概念与整体架构

TDengine 核心概念与整体架构:超级表、vnode 与数据分片

上一期我们把 TDengine 跑了起来:Docker 起容器、建出第一张超级表,taosBenchmark 一条命令灌进 1 亿条。但那 1 亿条存在哪、被谁管着、怎么在集群里摊开,命令行一个字没提。这一期把 TDengine 的"户口本"翻开:先认全两套术语——数据模型侧的超级表、子表、标签、时间戳主键,服务侧的 taosd、taosAdapter、dnode、mnode、vnode;再自绘一张整体架构图,跟着一条写入走完全程;最后打开源码仓库,把 source 目录下的模块一一对号入座。全文基于 v3.4.x(文档站 Latest v3.4.2,2026-09-19 复核;GitHub Releases Latest 为 ver-3.4.1.6,2026-04-30 发布),架构与概念表述逐条对照官方文档《技术内幕》各页。

01上一期的 1 亿条,此刻在哪里?

第 2 期收尾时,taosBenchmark 往 test 库写了 10,000 张子表、共 1 亿条数据,SELECT COUNT(*) 用 0.075 秒返回(官方文档样例)。现在问三个命令行没回答的问题:这 1 亿条存在哪?10,000 张子表由谁管?为什么 COUNT 全库能快成这样?答案藏在分片(sharding)与副本(replica)两个关键词里——官方《整体架构》开宗明义:TDengine 从第一天起就按分布式高可靠架构设计,通过节点虚拟化辅以负载均衡。

先把名片发齐。用户视角的 TDengine 词汇分两摞:数据模型侧五个——库、超级表、子表、标签、时间戳主键,第 2 期你全都敲过;服务侧六个——taosd、taosAdapter、taosc、dnode、mnode、vnode,藏在进程与集群里。前五个管"数据长什么样",后六个管"系统怎么跑"。先发名片,再上架构图对号入座。

02数据模型侧五件套:从架构视角重看第 2 期

第 2 期我们从"怎么用"的角度碰过它们,现在换架构视角,每个词补一句"它在系统里是什么":

① 库(Database)——分区的档案室

一句话定义:官方定义"库是 TDengine 中用于管理一组表的集合",一个实例可以有多个库,各库独立配置存储策略。

  • 库是 vnode 分配的单位:一个 vnode 只属于一个数据库,删除库时它的所有 vgroup 一并销毁;
  • 第 2 期敲的 KEEP、BUFFER、DURATION 全是库级参数,每个 vnode 各自执行。

② 超级表(STable)——虚位模板,不存一行

一句话定义:把同一类型的数据采集点聚成一张逻辑统一表的数据结构,自身不存储任何数据。

  • 第 2 期你只建了它没写入——不是漏了,是它本来就不存数据;
  • 架构视角:超级表的 schema 登记在元数据里,修改模板所有子表立即生效。

③ 子表——真正存数据的实体

一句话定义:隶属于某张超级表的具体表,一个数据采集点一张,按超级表模板创建。

  • 子表的数据按时间追加存在它所属的 vnode 上;一张表的数据不跨 vnode(第 05 节细说为什么);
  • 单 vnode 可管理的表上限官方口径为 100 万——第 1 期"表爆炸"的顾虑,架构层在这里兜底。

④ 标签 + ⑤ 时间戳主键——静态属性与唯一坐标

一句话定义:标签是采集点上"通常不随时间变化"的静态属性;时间戳是每张表的第一列、主键。

  • 标签值存在 vnode 的元数据里(官方《存储引擎》:子表标签信息与标签索引都在其中,用 B+ 树管理)——建表写死、不随每条数据重复存,这就是压缩率的来源之一;
  • 时间戳主键让"同设备数据按时间有序"变成物理事实,追加写与范围查都吃这红利。

边界说明怎么选标签、怎么设计列这类建模方法论,每日微课程线第 0015 期 · TDengine 超级表与子表数据建模已讲透,本系列不换皮重讲;本期只回答"它们在架构里是什么、存在哪"。

03服务侧六个名词:一家连锁物流分仓

服务侧词汇可以类比一家连锁物流分仓体系:仓库、库区、总台账房、前台收发室,各司其职。六个名词一句话:

名词类比一句话职责(官方口径)
taosd仓库本身"TDengine 数据库引擎的核心服务"——服务端主进程,默认监听 6030
dnode一座分仓"taosd 在物理节点上的一个运行实例"——集群的物理实体,至少要有一个
vnode仓内独立库区为数据分片、负载均衡而引入的虚拟节点,有独立的运行线程、内存空间和持久化存储路径;一个 vnode 只属于一个数据库
vgroup互为备份的库区组不同 dnode 上的 vnode 组成的逻辑单元,内部走 Raft;vnode 数量决定副本数(replica 默认 1)
mnode总台账房元数据(用户、数据库、超级表)的存储管理中心,又称 MetaNode;最多 3 个组成虚拟组,Raft 协议,更新必须在 leader 上执行
taosAdapter前台收发室"TDengine 集群和应用程序之间的桥梁和适配器"——RESTful/WebSocket 都走它(6041),各语言连接器经它通信

补两位"编外人员":taosc 是内嵌在各语言连接库里的应用驱动——缓存元数据、转发请求,还替服务端做"最后一级的聚合、排序、过滤";qnode 是专职查询计算的节点,不绑定数据库——官方说,引入它实现了存储和计算的分离。

04自绘整体架构:一条写入的完整旅程

把七个名词拼上数据流,就是 TDengine 的全景。读图三句话:taosAdapter 管接待,mnode 管查户口,vnode 管存数据。实线是写入路径,虚线是查询时的元数据与聚合协作。

顺着实线把第 2 期那条 INSERT INTO d1002 ... VALUES(NOW, 10.2, 219, 0.32) 走完:连接器把请求交给 taosAdapter(或原生连 6030)→ taosc 用缓存的元数据定位表,没缓存就先问 mnode"这张表在哪个 vnode" → 请求落到该 vnode:leader 验证后先写 WAL 保证持久性,再写内存跳表(多副本时同步转发 follower、超半数确认) → 内存池到阈值,后台刷成磁盘文件:元数据进 meta,时序数据按 LSM 进 tsdb,后台还会合并 stt 文件。走通这一条,第 2 期的三条跑通判定就都有了架构解释。

钩子一:为什么"一个采集点一张表"反而省存储?

直觉上"1 万台设备拆 1 万张表"很浪费,架构账正好相反。其一,标签只存一份——location、groupId 挂在 vnode 的元数据里(官方口径:标签信息与标签索引用 B+ 树管理),不随每条读数重复写;大宽表方案里,每行都得背一遍设备属性。其二,列存压缩吃得更饱——单设备电流电压缓变,块内相邻值高度相似,官方样例压缩率 23.98%(压到约 1/4,演示链②量过)。建模方法完整版见 daily 线 0015 期。

钩子二:vnode 怎么把写入并行度打开?

每个 vnode 有独立的运行线程、内存空间和持久化存储路径(官方原话),等于库内自带并行单元:10,000 张子表由一致性哈希摊到多个 vnode,各写各的 WAL、各刷各的盘——一张表的数据不跨 vnode,单表内天然无锁追加;跨表聚合时 mnode 给路由、各 vnode 并行扫描、taosc 做最后一级归并。这就是 COUNT(*) 0.075 秒和"1 亿条十几秒灌完"的架构底气。调优细节见 daily 线 0022 期。

05亲手验证:三条命令给架构做体检

架构不只画在纸上,回到第 2 期的容器里,几条命令就能摸到它。其一,清点物理节点——官方三节点 docker-compose 集群的 SHOW DNODES(官方运维文档样例回显):

taos> show dnodes;
id | endpoint  | vnodes | support_vnodes | status | create_time          | reboot_time           | note |
=================================================================================================
1  | td1:6030  |   0    |       85       | ready  | 2025-08-21 01:56:41.630 | 2025-08-21 01:56:41.462 | |
2  | td2:6030  |   1    |       85       | ready  | 2025-08-21 01:56:43.203 | 2025-08-21 01:56:43.453 | |
3  | td3:6030  |   0    |       85       | ready  | 2025-08-21 01:56:43.296 | 2025-08-21 01:56:43.491 | |
Query OK, 3 row(s) in set (0.006355s)

一列一个故事:endpoint 是"FQDN:6030"(一个 taosd 进程对应一个 dnode);vnodes 列说数据落在谁家——样例里全集群当时只有 1 个 vnode,分在了 td2 上;support_vnodes 是每个 dnode 承载 vnode 的上限(默认与 CPU 核数挂钩)。第 2 期单机容器里跑这条命令,看到的自然只有 id=1 一行。

其二,给存储做解剖——SHOW TABLE DISTRIBUTED 把一张子表在 vnode 里的物理形态摊开(官方文档样例回显):

taos> SHOW TABLE DISTRIBUTED d0\G;
Total_Blocks=[5] Total_Size=[93.65 KB] Average_size=[18.73 KB] Compression_Ratio=[23.98 %]
Total_Rows=[20000] Inmem_Rows=[0] MinRows=[3616] MaxRows=[4096] Average_Rows=[4000]
Total_Tables=[1] Total_Files=[2] Total_Vgroups=[1]

三行回显正好对应三个概念:数据切成 5 个块(默认块上限 maxRows=4096 行)、压缩率 23.98%(钩子一的实锤)、这些块属于 1 个 vgroup——vnode 才是数据文件的家。

其三,向元数据要答案——information_schema 里的表实为视图,只能查询、可用 SELECT 筛选排序(官方说明),给架构做体检最常用的四张:

视图关键列(官方定义)能回答什么
ins_databasesname · vgroups · replica · ntables一个库摊了几个 vgroup、几副本、多少张表
ins_dnodesid · endpoint · vnodes · support_vnodes · status每座"分仓"扛了几个 vnode、活没活
ins_vgroupsvgroup_id · tables · v1_dnode · is_ready分片实际分布:每个 vgroup 在哪个 dnode、管多少表
ins_tablestable_name · stable_name · vgroup_id · type任意子表的 vnode 归属与所属超级表

一条 SELECT table_name, vgroup_id FROM information_schema.ins_tables; 就能看到 10,000 张子表的 vnode 分配——分布一直都在,单机只是所有 vnode 住在同一座仓。

06打开仓库:source 目录模块地图

概念挂到代码上。以 GitHub 上 taosdata/TDengine 主分支为准(2026-09-19 核对;读码建议锁定 tag ver-3.4.1.6),C 项目重架构轻读码——每个目录一句话:

目录一句话职责
source/client/客户端驱动 taosc:连接管理、元数据缓存、最后一级聚合(各语言连接器的底座)
source/dnode/服务端节点主体:mnode(元数据)、vnode(时序数据)、qnode(查询)、snode(流计算)都在这
source/libs/内部公共库:parser(SQL 解析)、planner/executor(计划与执行)、scheduler(调度)、tdb(存储引擎)、wal(预写日志)等
source/common/前后端共享的结构与协议定义
source/os/ 与 source/util/跨平台系统调用封装与基础工具函数(C 项目的"地基件")
tools/辅助工具,含 shell/(taos 命令行真身)等
deps/ 与 include/第三方依赖与对外头文件接口
examples/ 与 tests/多语言示例与测试套件——读码时最好的"用法示例库"

读码提示优先级记三个:source/dnode/vnode(第 5 期"存算一体与缓存降采样"的主战场)、source/dnode/mnode(元数据与路由)、source/libs/tdb(存储引擎)。taos 命令行不在 source/ 里,在 tools/shell。

07随堂小测

每题点击选项立即反馈 · 共 4 题

1. 一个 vgroup 里的 vnode 数量,决定的是什么?

  • 集群里 dnode 的总数
  • 数据库能建多少张超级表
  • 这份数据的副本数

2. 子表 d1001 的数据,在 vnode 之间是怎么摆的?

  • 按时间范围切到多个 vnode,并行存
  • 整表落在一个 vnode 上,不跨 vnode
  • 随机分配到任意 vnode,每次写入可能换

3. 子表的标签值(如 location='北京')存在哪里?

  • 存在超级表里,所有子表共享一份
  • 随每条时序数据重复写入数据文件
  • 存在子表所属 vnode 的元数据里,建表时写死

4. 各语言连接器走 WebSocket 通信时,必须有哪个组件?

  • taosAdapter(监听 6041)
  • mnode(监听 6030)
  • taosc(客户端内嵌驱动)

08思考题(点击展开解析)

思考一:官方规定"一张表的数据不跨 vnode"。为什么不反过来——把一张大表切开摊到多个 vnode 上并行写,不是更快吗?

先看 TDengine 的世界里"一张表"是什么:一个采集点的全部读数,按时间严格递增追加。把它切开摊到多个 vnode,写入端确实多几条并行道,但代价立刻出现。其一,顺序性被打散——单设备数据天然按时间有序,集中在一个 vnode 上是纯追加写、块内连续存储,切开后读"这台设备最近一小时"要跨 vnode 归并排序;其二,并行度放错了地方——时序场景的写入压力来自"设备多"而非"单设备写不赢":电表一秒几条,真正的海量来自千万设备,而设备即子表,子表按一致性哈希摊到 vnode,并行度在"表→vnode"这一层已经打开了,犯不着单表内部再切;其三,一致性成本——vgroup 内本就有 Raft 复制,单表再跨 vnode 会让副本协议、WAL、事务边界全部复杂化。封死这条路,换来的是时序场景最值钱的三样:单表写路径极简、数据本地性极好、单 vnode 表上限 100 万足够用。再深一步:官方文档提到"按时间段划分数据文件实现分区"(duration 参数)——TDengine 的横向切分不在表内做,而在时间轴上做:同表数据按时间切成文件,超过 KEEP 期限整文件删除。表间切 vnode、表内切时间,两个维度各干各的,这是时序库分片设计的教科书答案。

思考二:第 2 期的单机容器里 replica=1,只有一座"分仓"。mnode 和 vgroup 的 Raft 那一套,在这个沙盘里还存在吗?

存在,一个不少——这正是 TDengine "单机即最小集群"设计的体现。mnode 侧:第一个 mnode 部署时自动创建,单机沙盘里它照样在岗,元数据(用户、库、超级表 schema)照样由它管理;"最多 3 个组成虚拟组"的上限用不上,它自己就是 leader,更新操作照样走"leader 执行"的规矩。vnode 侧:建库时 replica 默认 1,每个 vgroup 里只有一个 vnode——按官方定义"vgroup 由不同 dnode 上的 vnode 组成",此时"组"退化成单成员,但 Raft 的角色体系照演:它自己当选 leader,写入照样"验证 → 写 WAL → 写内存跳表",只是"超半数副本确认"的多数派是 1/1,确认退化成自己点头,复制开销为零。代价也要认清:第 2 期思考二说过,单机沙盘没有容错红利——容器一删数据就没了;生产上用 replica 2/3 把 vgroup 成员摊到不同 dnode,leader 挂了 follower 顶上,才是 Raft 副本组的完整形态。所以正确的理解是:沙盘是"副本数为 1 的最小集群",架构图里每个部件都在岗,只是多数派和备份的戏份被压缩了。这也是第 2 期学的所有 SQL 到集群里原样能跑的原因——从单机到集群,变的不是语法,是 vnode 们住进了几座仓库。

09本期要点与下期预告

带走这五条:

  • 两套术语:模型侧"库/超级表/子表/标签/时间戳主键"管数据长相;服务侧"taosd/dnode/vnode/vgroup/mnode/taosAdapter"管系统运行——超级表不存数据,标签躺在 vnode 元数据里;
  • 一条写入的旅程:taosAdapter 接待(6041)→ mnode 给路由 → leader vnode 写 WAL、写内存跳表 → 刷盘:meta 走 B+ 树,时序数据走 LSM;
  • 分片与副本:vnode 是分片单元(独立线程/内存/盘),一张表不跨 vnode;vgroup 是副本单元,vnode 数 = 副本数(replica 默认 1);
  • 命令行能摸到架构:SHOW DNODES 看"仓",SHOW TABLE DISTRIBUTED 看"块与压缩率"(官方样例 23.98%),information_schema 的 ins_tables/ins_vgroups 查 vnode 归属;
  • 仓库地图:source/client 是驱动,source/dnode 是服务端主体,source/libs 装 parser/tdb/wal,taos 命令行在 tools/shell。
