01需求：两句话翻译成一张作战地图

先把需求摆上桌，这是一家企业环境里最常见的两句话：其一，Docker Hub 上的官方基础镜像（ubuntu、redis 这类 library/ 官方镜像）要定时同步到私有 Harbor，让 CI 和集群走内网拉取——还记得第 1 期算过的账吗？匿名拉取每 IP 六小时限 100 次，中型团队一天的构建就能用光；其二，镜像里有已知漏洞没关系，但高危的必须挡在生产门外，不能等安全部门事后找上门。

翻译成 Harbor 的能力清单，正好是它的两块招牌：跨实例复制管同步，漏洞扫描 + 部署安全策略管拦截。一张作战地图如下：

需求用到的能力验收标准

本期的纪律照旧：不在本机部署 Harbor，所有界面操作按官方文档步骤转写，每张截图标出处；命令行验证用的是 Docker CLI 的标准行为。跟着走，配出来的东西在生产环境成立。

02演示①：一条复制规则，三个要素

先钩子后操作。钩子一：Harbor 的复制不是 cp 命令。它是一条声明式规则——你不搬镜像，你描述"什么镜像、到哪去、什么时候搬"，剩下的事仓库自己安排。对照官方文档《Creating a Replication Rule》（2.15，2026-09 核对），一条规则由三要素组成：源（Source resource filter：Name / Tag / Label / Resource 四类过滤器，支持 **、{a,b} 通配）、目标（目的仓库 + 目标命名空间，不填则沿用源命名空间）、触发器（Trigger Mode）。特别提醒：要同步 Docker Hub 官方镜像，名字过滤器必须带上 library 前缀，官方文档原话是 "You must add library if you want to replicate the official artifacts of Docker Hub"——这是新手第一个坑。

官方文档《Creating a Replication Rule》：Source resource filter 四类过滤器与通配模式表（library/* 只匹配一层，library/** 跨层匹配）（goharbor.io，2026-09-19 截图）。

本期的场景参数照抄即可：Pull-based 模式（Harbor 从上游拉）、源仓库选 Docker Hub 端点、Name 填 library/**、Resource 选 Images、目标命名空间填 base——以后 CI 一律从 harbor.example.com/base/ubuntu:24.04 取基础镜像。触发模式是三选一（官方口径）：Manual，需要时手动执行；Scheduled，按 cron 定时规则周期执行；Event Based，新制品推入或重新打标签时立即复制。三者的口径是删除操作默认不会被复制（Event Based 勾选 "Delete remote resources when locally deleted" 才会联动删除）。

官方文档同页 Trigger Mode 段：Manual 按需手动、Scheduled 按 cron 定时规则周期执行、Event Based 推入或重新打标签立即复制（goharbor.io，2026-09-19 截图）。

03演示②：执行一次复制，盯着任务列表看它跑完

规则保存后先别等定时，手动执行一遍验证链路。官方文档《Running Replication Manually》的步骤（2026-09 核对）：系统管理员登录 → 展开 Administration → Replications → 选中规则点 Replicate，规则命中的资源立即开始从源仓库向目标复制；点规则看执行状态，点执行的 ID 进入详情与任务列表。两个阅读任务列表的细节值得记住：汇总里的 IN PROGRESS 计数同时包含 Pending 与 In Progress 两种状态；某条任务失败不必慌，官方口径是失败任务几分钟后自动重新调度、重试若干次。每条任务旁边有日志图标，点开能看到这张镜像逐层的复制明细。

官方文档《Running Replication Manually》：Replicate 按钮触发 → 点规则看执行 → 点 ID 看任务列表 → 日志图标看单任务明细（goharbor.io，2026-09-19 截图）。

任务列表全部变成成功状态后，验收拉取。从新地址拉同一张镜像，Docker CLI 的动作和第 1 期完全一样——这正是协议兼容的福利：

docker pull harbor.example.com/base/ubuntu:24.04
24.04: Pulling from base/ubuntu
Digest: sha256:9c0b0a…  Status: Downloaded newer image

回显的 digest 与上游一致——复制是逐字节搬运，摘要值可验证。到这里，同步链路闭环：声明规则 → 触发执行 → 任务列表 → 内网拉取。注意整个过程 UI 只是"下指令看结果"，真正搬镜像的是后台的异步任务——这个伏笔在源码导读揭晓。

04演示③：把高危镜像挡在拉取门外

同步进来的基础镜像不等于安全，还差一道体检和一道门禁。两步都在项目的 Configuration 标签页里完成（需要项目管理员权限，官方文档《Project Configuration》，2026-09 核对）：第一步，勾选 Automatically scan images on push——官方原话，激活"新镜像推入项目即触发一次漏洞扫描"；第二步，勾选 Prevent vulnerable images from running 并在下拉里选严重级别。拦截的判定口径是这句："Images cannot be pulled if their level is equal to or higher than the selected level of severity"——等于或高于所选级别的镜像无法被拉取；同时文档明确：negligible 级别的漏洞不会被拦截，给运维留了余地。

官方文档《Project Configuration》：Configuration 标签页里 Prevent vulnerable images from running 勾选框、严重级别选择与 Automatically scan images on push（goharbor.io，2026-09-19 截图）。

扫描引擎是系列老朋友 Trivy（第 2 期安装时用 --with-trivy 带上的那个），对镜像做静态漏洞分析，报告按 Critical、High、Medium、Low、Negligible 分级列出 CVE 清单。策略生效后再 docker pull 一张命中级别的镜像，拉取请求会被 Harbor 直接拒绝——钩子二：扫描结果为什么能挡住 docker pull？因为这道策略钩在拉取链上而不是推送链上：Harbor 的仓库服务在响应拉取请求时先查该制品的扫描结论，命中策略就回绝。放在拉取侧有三个好处：推送不受影响，CI 产出照常入库；消费端把关，谁要上生产谁被拦；未扫描的镜像按保守原则同样不放行。真机上你会看到拉取报错被拒——这是策略命中的信号，而不是仓库故障。

三站读完，你对"一次定时复制在源码里的旅程"就有完整链路了：UI 调 REST 接口建规则 → 到点由周期调度投出任务 → runner 执行复制并把状态回写 → UI 任务列表里看到的 Success 就是这条链的终点。

06源码导读②：job 接口——"一切重活都是 job"

第一站看抽象。src/jobservice/job/interface.go 里定义了 job 的接口（节选，注释有删减）：

// src/jobservice/job/interface.go (tag v2.15.2)，节选
type Interface interface {
    MaxFails() uint                       // 允许的失败次数，0 取默认值 4
    MaxCurrency() uint                    // 同类任务的最大并发，0 为不限制
    ShouldRetry() bool                    // 失败后是否还重试
    Validate(params Parameters) error     // 入参合法性校验
    Run(ctx Context, params Parameters) error  // 业务逻辑本体
}

五个方法读出三层设计：可靠性写死在接口里（失败次数、重试意愿），新任务类型不用自己发明重试；并发是任务自己的属性（MaxCurrency），复制这种重活可以限速不让扫描饿死；参数是键值对（Parameters），接口只管约定形状，不关心业务语义。再看登记表 known_jobs.go，能一次认全 Harbor 的所有重活：REPLICATION（复制）、IMAGE_SCAN（扫描）、GARBAGE_COLLECTION（垃圾回收）、RETENTION（保留策略）、P2P_PREHEAT（分发预热）……全注册到同一个框架上跑。

GitHub goharbor/harbor @ v2.15.2：src/jobservice/job/interface.go 第 18~54 行实拍——Interface 五方法与官方注释（2026-09-19 截图）。

07源码导读③：周期任务执行器，与复制在哪里接线

第二站看"定时"怎么实现。jobservice 把任务分三种（src/jobservice/job/kinds.go）：Generic 跑一次、Scheduled 定时跑一次、Periodic 周期跑。src/jobservice/period/ 包是周期任务的执行器：policy_store.go 保存定时策略（cron 表达式存在任务元数据里），enqueuer.go 周期扫描这些策略，把到点的任务投进执行队列，再由 src/jobservice/runner/ 下的执行器领取运行、回写状态。第三站看复制的接线：src/controller/replication/policy.go 里，规则的 Scheduled 触发并不是自己起定时器，而是把一个名为 REPLICATION_CALLBACK 的回调注册到 src/pkg/scheduler——到点回调再投出复制执行。这印证了本期的核心观察：UI 只是写下一份策略声明，执行永远是 jobservice 里的异步任务；策略与执行分离，策略可以随时改，执行器按任务跑，两边互不拖累。

08可借鉴点：把这三手带回去

  • 异步任务框架的通用形态：登记（接口约定 + 任务注册表）→ 投递（队列 + 到点投递）→ 执行（runner 领取）→ 回写（状态 + 日志）→ 重试（失败次数与重试意愿进接口）→ 通知（状态钩子回调）。你自研系统里要做"后台重活"——对账、补偿、批量迁移——照这个骨架搭，能少踩一大片坑；
  • 策略与执行分离：复制规则、拦截策略都是"声明"（什么条件下做什么），真正干活的是统一的任务底座。改策略不动执行器，换执行器不碰策略；这条分离线也是 Harbor 能把扫描、复制、GC 长在同一座仓库上的原因；
  • 把安全卡点放在消费侧：高危镜像拦在"拉取"而不是"推送"，CI 节奏不被打断，风险在离生产最近的一步被拦下——同样的思路适用于制品晋级、配置下发这类"生产准入"场景。

09本期要点与系列收尾

带走这五句话：

  • 复制是声明式规则不是 cp 命令：源（四类过滤器）/ 目标（仓库 + 命名空间）/ 触发器（Manual、Scheduled、Event Based）三要素，Docker Hub 官方镜像记得带 library 前缀；
  • 复制链路验收：Administration → Replications → Replicate 执行，任务列表看明细，失败任务自动重试，digest 与上游一致即搬运无损；
  • 拦截策略两勾选：Automatically scan images on push 推入即扫，Prevent vulnerable images from running 按级别拦拉取——等于或高于所选级别即拒绝，negligible 不拦；
  • 源码三站（v2.15.2）：src/jobservice/job 定抽象，period + runner 管周期与执行，src/controller/replication 做策略接线——策略是声明，执行是任务；
  • 可借鉴：异步任务框架六件套（登记/投递/执行/回写/重试/通知），安全卡点放消费侧。

11思考题（点击展开解析）

思考一：Manual 与 Scheduled 触发的复制默认不复制删除操作，Event Based 要手动勾选才联动删除。为什么默认"只加不删"？这对你设计同步系统有什么启发？

先把事实钉牢：官方文档在 Manual 与 Scheduled 的说明里都写着 "Deletion operations are not replicated"，只有 Event Based 勾选 "Delete remote resources when locally deleted" 后，本地删除才会联动删掉目标端制品。为什么默认只加不删？第一层是安全语义：跨实例复制最常见的用途是灾备与分发，灾备库的底线是"源库出事我有货"——如果源库误删（脚本写错、项目清理、恶意操作）立即扩散到所有副本，灾备就变成了风险的放大器；只加不删让下游天然多一层保留窗口，事故恢复时还能从副本找回归档。第二层是语义差异：新增是幂等的（同一张镜像重复复制结果一致），删除却依赖严格的顺序与意图确认——批量规则命中范围变大时，一次误匹配的"删除联动"可能清空目标仓库，而复制任务的重试机制会把这种破坏性操作放大。所以 Harbor 把"要不要同步删除"做成显式勾选，把判断权交还给人。对你的启发：设计同步/备份系统时，把"写扩散"和"删扩散"当成两种风险等级处理——写扩散最多浪费空间，删扩散会毁数据；默认值应该保护数据，破坏性联动必须显式开启，并且最好配上保留窗口（Harbor 的对应物是保留策略与回收站）。一句话：同步系统的默认倾向，应该是"宁可多占空间，不让数据凭空消失"。

思考二：本期源码里，复制规则的定时触发不是自起定时器，而是注册回调给统一的调度器；扫描、GC、保留策略也都是注册到 jobservice 的 job。这种"底座统一 + 插件式接入"的结构，代价与收益各是什么？

收益先看。统一底座意味着横切能力只实现一次：失败重试（MaxFails/ShouldRetry 进接口）、并发上限（MaxCurrency）、状态查询与日志（任务列表能逐任务点开）、执行历史（审计）。每种新业务——复制、扫描、GC——只要实现五个方法加一个登记名，就"免费"获得全部这些；反过来，运维只需盯一个 jobservice 的监控面。插件式接入还带来可替换性：第 1 期提过扫描器从 Clair 换成 Trivy，业务侧没有伤筋动骨，因为扫描器也只是登记在底座上的一种 job 供给方。再看代价。抽象层不是免费的：所有任务都要适应"参数是键值对、上下文靠注入"的通用形状，业务个性化（比如复制要限速、要分块）只能靠往 Parameters 里塞约定字段，类型安全弱化；状态机统一后，个别业务的特殊语义（复制的 IN PROGRESS 兼含 Pending）会被"削足适履"；调试链路变长——UI 一次点击穿过 handler、controller、scheduler、jobservice 四层，排障要跨包追日志。判断标准：当你的系统里同类"后台重活"超过三种、且每种都要重试/限流/留痕时，统一底座的摊薄成本就开始划算；只有一两种重活时，直接写反而简单。这个阈值判断，比模式本身更值得带走。
