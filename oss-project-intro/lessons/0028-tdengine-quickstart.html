OSS PROJECT INTRO · TDENGINE 系列第 2 期:5 分钟跑起来

5 分钟跑起来 TDengine:Docker 起服务,亲手建出第一张超级表

上一期立住了心智模型:TDengine 是为时序数据而生的数据库,"一个数据采集点一张表"加超级表是它的招牌设计。这一期把这句话变成实物——Docker 一条命令起服务,进命令行建库、建超级表、建子表,用自动建表 INSERT 写入设备数据再查回来,最后用官方压测工具 taosBenchmark 一条命令灌进 1 亿条看看成色。全文基于 v3.4.x 稳定线(文档站 Latest v3.4.2;Docker Hub 社区镜像 tdengine/tsdb:latest 当前为 3.4.2.8,2026-08-31 更新;GitHub Releases Latest 为 ver-3.4.1.6,2026-04-30 发布——发布页更新滞后于镜像线,以官方文档与镜像为准,2026-09-19 复核),命令与预期输出逐字对照 docs.taosdata.com 官方文档,安装选型与高频报错一并给全,跑不通先对号入座再怀疑人生。

🧩 时序数据库 · C · AGPL-3.0 📦 基于 v3.4.x(镜像 3.4.2.8) 📅 2026-09-19 · 第 2 期 ⏱ 预计阅读 15 分钟

01本期路线与跑通判定

五步路线:起容器 → 判就绪 → 建库建超级表 → 写入 → 查询验证。全部走完,三条判定都满足才算跑通:

  • ① 容器健康:docker ps 的 STATUS 字段显示 Up ... (healthy)——这是官方文档给出的判定口径,不是"转起来了就行";
  • ② 命令行就位:taos 进入 shell 后提示符 taos> 出现,show databases; 能看到 information_schema 与 performance_schema 两个系统库(官方文档原样输出);
  • ③ 数据闭环:写进去的数据查得回来——自己建的子表能 SELECT 出刚写入的行,官方压测后 SELECT COUNT(*) 返回 100000000(官方文档原样输出)。

上一期我们认识了 TDengine:一颗专为时序数据设计的心脏,25,127 个 GitHub stars(2026-09-19 数据),物联网、IT 运维这些"设备疯狂吐数"的场景是它的主场。本期你会亲手用到它最招牌的三件套——超级表、子表、标签——看看它们在 SQL 里长什么样。

02安装方式选型:三条路,本期走 Docker

官方快速上手栏目给的三条路:Docker 快速体验、安装包快速体验、云服务快速体验。加上 Debian/Ubuntu 可用的官方 apt 仓库,常见四条路:

方式怎么装适合谁
Docker(本期主线)docker pull + docker run 两条命令,一条命令卸载:docker rm -f最快跑起来、环境干净不污染系统,官方快速上手首推
安装包(tar.gz)解压后 sudo ./install.sh,systemd 管理服务(systemctl status taosd)生产 Linux 服务器、无容器环境
apt 仓库(Debian/Ubuntu)官方源 repos.taosdata.com/tdengine-stable,sudo apt-get install tdengineDebian/Ubuntu 长期使用、方便升级
云服务免安装的托管版(TDengine Cloud)不想管运维、直接写应用

本期选 Docker,图的是命令能逐字对照官方文档、用完即删。动手前先认清镜像名——官方文档有一条例程必读的注记:自 3.3.7.0 版本起,社区版镜像由 tdengine/tdengine 改名为 tdengine/tsdb,企业版由 tdengine/tdengine-ee 改名为 tdengine/tsdb-ee。老教程里随处可见的 tdengine/tdengine 已停更(停留在 3.3.6.x),开源系列用社区版 tdengine/tsdb。

版本三渠道,别只盯一处:官方文档站 Latest 为 v3.4.2;Docker Hub 社区镜像 tdengine/tsdb:latest 当前为 3.4.2.8(2026-08-31 更新);而 GitHub Releases 页的 Latest 还停在 ver-3.4.1.6(2026-04-30 发布)——发布页的更新节奏滞后于镜像与文档线。安装类操作以官方文档和镜像仓库为准,这也是读开源项目版本的基本功:同一个项目,不同渠道的"最新"可能不同步。

顺带一条冷知识:想让 Windows 直接装服务端?社区版不支持——官方 README 原话,自 3.1.0.0 版本起 Windows 仅在 TSDB-Enterprise 版本中支持。Windows 用户的正解就是本期主角:Docker。

03第一步:拉镜像、起容器(两条命令的事)

docker pull tdengine/tsdb:latest

docker run -d --name tdengine \
  -p 6030:6030 -p 6041:6041 \
  tdengine/tsdb:latest

对照官方口径说三点。其一,镜像名:官方快速上手页用企业镜像 tdengine/tsdb-ee 演示完整功能,社区版把镜像名换成 tdengine/tsdb 即可,启动参数一致。其二,端口:官方完整示例映射了 6030、6041、6043、6060、6044-6049(TCP/UDP)、6050、6055 一大串;本期最小化只映射两个——6030 是服务端 taosd 的原生连接端口,6041 是 taosAdapter 组件提供的 HTTP 服务端口(RESTful 与 WebSocket 都走它)。官方运维文档甚至给过只映射 6041 的最小形态。其三,数据卷:认真使用建议按官方运维文档挂载数据与日志目录(-v ~/data/taos/dnode/data:/var/lib/taos、-v ~/data/taos/dnode/log:/var/log/taos),删容器不丢数据;纯练习可省略。

默认用户名 / 密码:root / taosdata——后面 REST 验证和登录都用它,先记下。

04第二步:判定就绪,进入 taos 命令行

容器起了不等于服务就绪,官方给的判定是看 STATUS 字段:

$ docker ps -f name=tdengine
CONTAINER ID   IMAGE                  STATUS         PORTS          NAMES
e6f1c2ab9087   tdengine/tsdb:latest   Up 30 seconds (healthy)   0.0.0.0:6030->6030/tcp, 0.0.0.0:6041->6041/tcp   tdengine

STATUS 显示 Up ... (healthy) 才算就绪(官方文档原话:"如果该状态的值为 Up ... (healthy), 说明容器已经启动并正常运行")。刚启动的几十秒内可能是 health: starting,等它翻绿再往下走;PORTS 列格式随 Docker 版本略有差异。

不进命令行也能先验证服务——taosAdapter 的 REST 接口(官方运维文档原样命令,注意默认密码):

curl -u root:taosdata -d "show databases" localhost:6041/rest/sql

返回一段 JSON 且 code 为 0,说明 6041 的 HTTP 服务通了。然后进容器、进命令行:

$ docker exec -it tdengine bash
[root@e6f1c2ab9087 /]# taos

taos> show databases;
              name              |
=================================
 information_schema             |
 performance_schema             |
Query OK, 2 rows in database (0.033802s)

看到 taos> 提示符和两个系统库,跑通判定第②条达成(输出为官方文档原样)。三件事记住:SQL 以分号结尾才会执行;系统库 information_schema / performance_schema 存元数据,别往里写;退出命令行输入 q 或 quit 或 exit(官方 CLI 文档口径)。

05第三步:建库、建超级表、建子表

主菜来了。先建一个库(官方数据建模文档示例,参数看注释):

CREATE DATABASE power PRECISION 'ms' KEEP 3650 DURATION 10 BUFFER 16;
USE power;
-- PRECISION 'ms':毫秒精度时间戳;KEEP 3650:数据留 3650 天
-- DURATION 10:每 10 天一个数据文件;BUFFER 16:16MB 写入内存池

然后是本期主角——超级表(官方建模文档示例,一块智能电表场景:电流、电压、相位三个采集量,位置、分组两个标签):

CREATE STABLE meters (
    ts timestamp,
    current float,
    voltage int,
    phase float
) TAGS (
    location varchar(64),
    group_id int
);

两个语法要点:第 1 列必须是时间戳(ts timestamp);TAGS 括号里定义的是标签——设备的静态属性。再建第一张子表(官方示例,USING 指定模板,TAGS 给这台设备的标签值):

CREATE TABLE d1001
USING meters (
    location,
    group_id
) TAGS (
    "California.SanFrancisco",
    2
);

把三个词一次说清(点到为止,原理留给下期):超级表是同类设备的模板,自己不存一行数据;子表才真正存数据,且"一个数据采集点一张表";标签是挂在子表上的静态属性,建表时给值,之后随时可改。对超级表查询时,TDengine 先按标签筛出子表、再聚合时序数据——这就是"千万设备轻松聚合"的入口。

06第四步:写入与查询——自动建表是灵魂

实战里最常用的写入姿势是自动建表(官方建模文档示例):设备 d1002 的表还不存在?一条 INSERT 先建表再写入:

INSERT INTO d1002
USING meters
TAGS (
    "California.SanFrancisco",
    2
) VALUES (
    NOW,
    10.2,
    219,
    0.32
);
-- NOW = 当前时间戳;子表已存在则直接写入,不存在先自动建表(官方文档口径)

它还支持一条语句写多张表——官方文档给的三表九条数据的例子,INSERT INTO d1001 USING meters TAGS (...) VALUES (...),(...),(...) d1002 USING meters TAGS (...) VALUES ... d1003 ...,官方说明:这条语句共写入 9 条数据。批量上报场景就是它。写入之后验证(查询列名与输出格式随数据而异,能查回刚写入的行即达成判定③):

taos> SELECT * FROM d1002;
taos> SELECT AVG(current), MAX(voltage), MIN(phase) FROM meters;
-- 查超级表 = 聚合全部子表;加 WHERE location = '...' 即按标签筛选

最后加个彩蛋,亲手感受一下它的写入成色。官方自带压测工具 taosBenchmark,一条命令:

taosBenchmark -y

它会自动在 test 库创建超级表 meters,10,000 张子表(表名 d0 到 d9999)、每张 10,000 条记录,总共写入 1 亿条——官方文档原话:即便在普通 PC 服务器上,这个过程通常也只需要十几秒。然后查总数(官方文档原样输出):

taos> SELECT COUNT(*) FROM test.meters;

         count(*)         |
==========================
              100000000 |
Query OK, 1 row(s) in set (0.075247s)

1 亿条,总数查询 0.075 秒返回(官方文档样例耗时);聚合查询 AVG / MAX / MIN 官方口径约 0.09 秒。上一期说的"为写入而生",到这里你亲手摸过了。想停?练习环境直接 docker rm -f tdengine 连容器带数据一起清掉,重来零成本。

07高频报错速查:现象 → 原因 → 解法

现象原因解法
docker pull 卡住、超时 访问 Docker Hub 网络不稳,第一高频翻车点 配置镜像加速器;或从官方产品下载中心的 Docker 镜像下载页取离线镜像,docker load 后按页面提示改名称与标签(官方口径)
容器 STATUS 一直 Restarting 或 unhealthy 宿主机端口被占用,或容器初始化失败 docker logs tdengine 看日志定位;确认宿主机 6030/6041 没被别的进程占用
启动报端口冲突 6041/6030 已被本机其他服务或旧容器占用 docker ps -a 清理旧容器,或改映射端口如 -p 6042:6041
taos 报连接失败、进不去 服务端未就绪(health: starting)或在容器外直连 等 STATUS 变 healthy;进容器执行 taos;官方提醒:从容器外用原生连接比较复杂,RESTful/WebSocket(6041)是最简单的方法
原生连接报客户端/服务端不兼容 客户端驱动 taosc 与服务端 taosd 版本不一致 官方文档原话:"为避免客户端驱动和服务端不兼容,请使用一致的版本";更推荐 WebSocket 连接——无需安装客户端驱动,走 6041
Windows 安装服务端失败 社区版不提供 Windows 服务端(3.1.0.0 起仅企业版支持) Windows 上用 Docker 跑社区版,或使用官方企业版安装包

08随堂小测

每题点击选项立即反馈 · 共 4 题

1. Docker 起的 TDengine 容器,官方文档判定"启动成功"的口径是什么?

  • 容器进程存在即为成功
  • STATUS 显示 Exited (0) 也算成功
  • STATUS 显示 Up ... (healthy)

2. 端口 6041 上跑的是什么服务?

  • taosd 的原生连接端口
  • taosAdapter 的 HTTP 服务(RESTful/WebSocket)
  • 容器 SSH 登录端口

3. 关于超级表与子表的关系,哪个说法是对的?

  • 超级表是模板不存数据,数据都在子表里
  • 数据存在超级表里,子表只是视图
  • 子表和超级表是两套独立的表

4. 执行 INSERT INTO d1002 USING meters TAGS (...) VALUES (...) 时子表 d1002 不存在,会发生什么?

  • 报错,必须先 CREATE TABLE 再写入
  • 只建空表,数据被丢弃
  • 先自动创建子表,再写入这条数据

09思考题(点击展开解析)

思考一:TDengine 坚持把"一台设备"拆成"一张子表",而不是像传统关系库那样把所有设备塞进一张大宽表——这个反直觉的设计,到底换来了什么?

官方数据建模文档把账算得很清楚,收益全在时序数据的特性上。其一写入无锁:一张子表只有一个写入者(这台设备自己),不同设备互不干扰,不需要锁保护——大宽表里成千上万个写入者挤一张表,网络时序一乱就得加锁排队;其二追加写:单设备数据按时间递增,写入就是顺序追加,这是磁盘最喜欢的访问模式;其三读得快:一台设备的数据连续成块存储,查它的时间段数据几乎不碰随机读;其四压缩率高:块内列式存储,电流电压这种缓变量相邻值高度相似,压缩算法吃得很饱。代价是什么?单表没法跨设备聚合——于是超级表来补:模板统一结构、标签负责筛选,聚合时先按标签选子表再合并。所以这套设计不是"为了拆而拆",而是把"写"和"跨设备查"拆到两种结构里,各自做到最优。你今天敲的 CREATE STABLE 加 TAGS,就是这套权衡的语法入口。

思考二:本期是"一个容器跑一切"的单机沙盘。它与生产环境的 TDengine 集群差在哪?今天学的哪些东西到了集群里依然成立?

分两层看。今天学到的东西大部分是集群通用的:SQL 语法面(建库建表、自动建表写入、超级表查询)、标签与子表的建模方式、taos 命令行与 REST 接口的用法——这些在单机和集群上完全一致,因为 TDengine 从设计之初就是分布式架构,单机只是"副本数为 1 的最小集群"。沙盘形态特有的至少三处:其一,没有多节点与数据分片——生产集群里数据按 vnode 分布在多个 dnode 上,官方运维文档的集群部署一节讲了 firstEp、TAOS_FQDN 这些今天没出现的配置,官方甚至给了三节点 docker-compose 示例;其二,没有副本与高可用——生产用 replica 参数多副本容错,单容器挂了数据就没了(这也是练习环境敢用 docker rm -f 的原因);其三,资源与容量——KEEP、BUFFER、DURATION 这些今天照抄的参数,生产上要按数据量与硬件重新算。正确的学习姿势:沙盘练语法,集群学分布——第 3 期讲 vnode 与数据分片时,你会看到今天这条单机路线如何横向铺开成一个集群。
