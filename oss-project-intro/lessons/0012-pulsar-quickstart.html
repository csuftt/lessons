OSS PROJECT INTRO · Pulsar 系列第 2 期：5 分钟跑起来

5 分钟跑起来 Pulsar：一条命令起集群，亲手发出第一条消息

上一期我们认识了 Pulsar 的计算存储分离：Broker 是不存货的分拣中心，BookKeeper 是仓库网络。这一期把比喻变成实物——下载官方二进制包，一条 bin/pulsar standalone 在本机起一个完整集群（三层架构全在一个进程里），再用 pulsar-client 发出第一条消息、亲眼看它带着 ----- got message ----- 回来。全文基于 4.2.x（稳定线 4.2.4，2026-08-03 发布，2026-09-19 于 GitHub Releases 与官方文档核对），命令与预期输出逐条对照官方 quickstart，Docker 方式与高频报错一并给全，跑不通先对号入座再怀疑人生。

🧩 消息平台 · Java · Apache-2.0 📦 基于 Pulsar 4.2.x（4.2.4） 📅 2026-09-19 · 第 2 期 ⏱ 预计阅读 15 分钟

01本期路线与跑通判定

四步路线：查 JDK → 下载解压 → 一条命令起服务 → 收发第一条消息。全部走完后，满足三条判定才算跑通：

  • ① 服务起来了：启动终端滚动出 messaging service is ready 的就绪日志，进程不退、光标停在日志末尾——是设计如此，不是卡死；
  • ② 发得出去：pulsar-client produce 执行完，CLI 打出成功提示（1 messages successfully produced）；
  • ③ 收得回来：pulsar-client consume 打出 ----- got message ----- 和 content:Hello Pulsar!——这行输出也原样写在官方文档里。

standalone 模式是官方为本地实验准备的"全家桶"：上一期讲的 Broker（计算）、BookKeeper（存储）、元数据存储三层，全部塞进一个 JVM 进程。学习阶段它让"起一个集群"退化成一条命令；代价是三层挤在一起没有故障隔离——所以官方文档明确它只用于开发，这个定位贯穿全文。

02环境要求：Java 21 是硬门槛

Pulsar 4.x 对 JDK 的要求是硬性的，官方 standalone 入门页原文："Java 21 is required for Pulsar 4.0+"。这是从 2.x 时代一路涨上来的：2.7 要 Java 8，2.11 要 Java 17，4.0 起要 Java 21。不少老机器上默认的 JDK 8 会直接启动失败，先查再说：

java -version

# 达标示例输出（21 及以上即可）
# openjdk version "21.0.8" 2025-07-15
# OpenJDK Runtime Environment Temurin-21.0.8+9 (build 21.0.8+9)

没装或版本不够，官方页给了两条路：SDKMAN 一条命令切换版本，或去 Adoptium 下载 Temurin OpenJDK 21。另一个容易忽略的前提：本机安装方式只支持 64 位 macOS 和 Linux——Windows 用户别硬来，直接跳到第 08 节走 Docker，这也是官方文档给 Windows 的唯一指引。

03第一步：下载解压，认识目录地图

官方 quickstart 用 curl 从 Apache 镜像分发页下载二进制包，解压、进目录、看一眼里面有什么：

curl -LO "https://www.apache.org/dyn/closer.lua/pulsar/pulsar-4.2.4/apache-pulsar-4.2.4-bin.tar.gz?action=download"
tar xvfz apache-pulsar-4.2.4-bin.tar.gz
cd apache-pulsar-4.2.4
ls -1F

ls -1F 会列出五个条目：bin/、conf/、lib/、examples/、instances/。官方文档给它们的一句话分工：bin 是入口脚本，conf 放配置（broker.conf 在这里），lib 是全部依赖 JAR。本期要打交道的命令都在 bin/ 里，四个脚本各管一摊：

命令职责本期用途
bin/pulsar起 Broker 服务本体standalone 启动集群
bin/pulsar-client命令行收发消息发出并收回第一条消息
bin/pulsar-admin管理面操作建租户、命名空间、Topic
bin/pulsar-daemon后台守护方式启停想让服务常驻时用

curl 参数里 ?action=download 别丢：Apache 的 closer.lua 分发页靠它才直接跳转镜像开始下载，漏掉会得到一个列镜像的 HTML 页面而不是 tar 包。

04第二步：一条命令起一个集群

bin/pulsar standalone

就这一条。终端开始滚动启动日志——这个进程要依次拉起 BookKeeper（bookie）、元数据服务和 Broker。等日志停止滚动、光标停在末尾，翻到附近找这行就绪标志（关键短语核对自 4.2 分支源码 PulsarService 的启动逻辑）：

# ... INFO  org.apache.pulsar.broker.PulsarService - messaging service is ready, ...
# 启动后工作目录下会多出 data/ 和 logs/ 两个目录（官方文档说明）
# 进程不退 = 服务活着；停止：回到这个终端按 Ctrl-C

三件事确认就绪：看到了 ready 日志、进程不退、目录里多了 data/（BookKeeper 与元数据的落盘位置）和 logs/。想让服务常驻后台，用 bin/pulsar-daemon start standalone；实验阶段更推荐前台跑——Ctrl-C 即停，日志直出终端，新手排障最直观。

启动时官方悄悄替你做了两件事：

  • 自动创建了 public/default 命名空间（官方原文："The public/default namespace is created when you start a Pulsar cluster"）——所以下一节不发一条 admin 命令也能直接收发；
  • 默认允许自动创建 Topic——produce 一个不存在的 Topic 名，它会先被创建再收消息。方便归方便，生产实践里官方仍建议显式建 Topic（第 11 节思考题会展开为什么）。

05第三步：发出去，收回来

三条命令完成闭环：建 Topic、发一条、收回来。命令与输出都出自官方 4.2.x standalone 文档，可逐字对照：

bin/pulsar-admin topics create persistent://public/default/my-topic
bin/pulsar-client produce my-topic --messages 'Hello Pulsar!'
bin/pulsar-client consume my-topic -s 'my-subscription' -p Earliest -n 0

produce 执行完，CLI 打出成功提示（消息文本核对自 4.2 分支源码 CmdProduce）：1 messages successfully produced。切到收消息的终端，重头戏来了——官方文档原样的回显：

----- got message -----
key:[null], properties:[], content:Hello Pulsar!

看到这两行，端到端就通了：消息经 Broker 写进 BookKeeper 落库，再被你的订阅取走。consume 的参数拆开看：-s 是订阅名（同一个名字记住上次读到的位置，就是上期说的"游标"）；-p Earliest 表示从该订阅最早的消息读起，避免"明明发了却收不到"；-n 0 表示不限条数、一直挂着等新消息。

顺手玩一把批量发送（官方示例，逗号分隔多条消息一次发出）：

bin/pulsar-client produce my-topic --messages "$(seq -s, -f 'Message NO.%g' 1 10)"

订阅名与游标背后的四种订阅模式、消息怎么确认不丢，是概念与原理深水区——延伸阅读：每日微课程线《Pulsar 订阅模型：四种订阅、游标与 Key_Shared 保序》、《Pulsar 消息可靠性全链路》。

06三板斧：自建租户、命名空间、Topic

刚才那条 Topic 地址不是随口写的，它是 Pulsar 的标准寻址格式：persistent://租户/命名空间/主题。public 是启动时自动创建的默认租户，default 是它下面的默认命名空间——多租户隔离是 Pulsar 的架构内建能力（上期讲过），这节亲手把它用起来：

按官方 admin API 文档的命令原文，建一个自己的租户和命名空间：

bin/pulsar-admin tenants create my-tenant -r role1 -c standalone
bin/pulsar-admin namespaces create my-tenant/my-ns
bin/pulsar-admin topics create persistent://my-tenant/my-ns/topic-1

-r（adminRoles）给这个租户指定管理员角色，-c（allowedClusters）圈定租户可用的集群——standalone 模式的集群名就叫 standalone。三类资源的 create/list 是对称的，做成速查表：

资源创建查看
租户tenants create my-tenanttenants list
命名空间namespaces create my-tenant/my-nsnamespaces list my-tenant
Topictopics create persistent://my-tenant/my-ns/topic-1topics list my-tenant/my-ns

建完自己的租户，把收发命令换上完整地址再跑一遍：bin/pulsar-client produce persistent://my-tenant/my-ns/topic-1 --messages 'Hello again!'——地址变了，玩法没变。

07Docker 方式：Windows 的唯一正道，Linux/macOS 的另一选项

官方《Run Pulsar In Docker》给的就是一条命令，镜像 tag 与本期版本一致（Windows 把行尾续行符 \ 换成 ^）：

docker run -it \
  -p 6650:6650 \
  -p 8080:8080 \
  --mount source=pulsardata,target=/pulsar/data \
  --mount source=pulsarconf,target=/pulsar/conf \
  apachepulsar/pulsar:4.2.4 \
  bin/pulsar standalone --advertised-address localhost

逐段拆：-p 6650:6650 映射二进制协议端口（pulsar-client 连的就是它），-p 8080:8080 映射 HTTP 端口（admin API 与监控）；两个 mount 把数据卷、配置卷挂出来，容器删了数据还在。末尾的 --advertised-address localhost 官方文档默认带着——容器里的服务要把自己" advertised（广播）"的地址写成宿主机可达的 localhost，否则宿主机客户端第一步寻址就碰壁。官方还提醒：容器默认以 UID 10000 运行，挂载卷要保证它可写。

起完之后验证与裸机完全同款：端口 6650 已映射到宿主机，宿主机上任何语言的客户端都能直连（官方 Docker 页用 Python 客户端 pulsar://localhost:6650 做演示）；也可以另开终端用 docker exec 进容器，容器里自带全套 bin/pulsar-client/pulsar-admin，收发输出与第 05 节一致。想看这颗 Topic 的运行统计，官方 Docker 页给了管理面查询：

curl http://localhost:8080/admin/v2/persistent/public/default/my-topic/stats | python -m json.tool

返回一屏 JSON 统计——生产速率、订阅情况都在里面，这是从"跑通了"走向"看得见"的第一步。

08高频报错速查：现象 → 原因 → 解法

现象原因解法
启动即抛 UnsupportedClassVersionError（提示 class file version 不匹配） JDK 低于 21。4.0+ 硬性要求 Java 21，老机器默认 JDK 8 最常见 升到 JDK 21+：SDKMAN 一条命令切换，或 Adoptium 下载 Temurin；再 java -version 确认
Windows 上 bin/pulsar 各种脚本报错 本机安装方式官方只支持 64 位 macOS / Linux 改走 Docker 方式（第 07 节命令），这是官方给 Windows 的唯一路径
pulsar-client 报连接被拒 / 连接超时 standalone 还没就绪就开始收发，或服务根本没起 回启动终端确认 messaging service is ready 日志与进程存活；端口 6650 是否被映射（Docker）
consume 挂着却一条消息都收不到 同名订阅之前消费过，游标已越过旧消息（订阅记住读到的位置） 加 -p Earliest 从最早读起，或换个全新订阅名（消息还没被确认删除时）
下载得到的是 HTML 页面，tar 解压报错 closer.lua 链接漏了 ?action=download 参数，拿到的是镜像列表页 用第 03 节的完整链接重新 curl；解压前 file apache-pulsar-4.2.4-bin.tar.gz 确认是 gzip 文件
Docker 卷挂载报权限错误 容器默认以 UID 10000 / GID 0 运行，挂载卷对它不可写 按官方文档提示：确保挂载卷对 UID 10000 或 GID 0 可写（Linux 上 chown 或放开组权限）

2. consume 命令里 -p Earliest 的作用是？

  • 自动创建一个名为 Earliest 的订阅
  • 从该订阅最早未确认的消息开始读

  • 租户 → 命名空间 → 主题
  • 命名空间 → 租户 → 主题
  • 集群 → 租户 → 主题

4. Windows 上想跑起 Pulsar，官方给的方式是？

  • 下载 macOS/Linux 安装包改个路径硬跑
  • 用官方 Docker 镜像方式运行
  • 从源码编译出 Windows 版本

10思考题（点击展开解析）

思考一：standalone 把三层塞进一个进程，它和生产集群的差异只是"少了几台机器"吗？

差异远不止规模，本质是三份"架构承诺"在 standalone 里被临时打折。第一，故障域合并：生产里 Broker、BookKeeper、元数据存储各自独立伸缩、独立容错——Broker 全挂了消息还在 bookie 里，元数据挂了 Broker 还能照常服务；standalone 三层同居一个 JVM，进程一死全没，"计算存储分离"的容错红利在本地模式下是看不出来的，它给你看的只是逻辑分层（配置与代码路径分离），不是物理分离。第二，定位是开发件：官方文档明确 standalone 用于开发实验，public/default 这种自带命名空间也是"图省事"的开发默认——生产集群的第一课恰恰是别用 public/default，而是按业务规划租户。第三，配置口径不同：standalone 为了本机流畅放开了不少默认值（自动建 Topic 等），生产的 broker.conf 则要逐项过。所以正确的用法是：用 standalone 建立肌肉记忆，把"哪些是架构承诺、哪些是开发默认"分清楚，上生产时逐条把默认值换掉——这也是第 3 期读架构、第 4 期接 Spring Boot 时反复回对照的一面镜子。

思考二：既然支持自动创建 Topic，为什么官方还建议显式建？

官方 standalone 文档的原文大意是：即使 Pulsar 支持自动创建，实践中也建议显式提前创建。原因拆三层。第一层是治理：自动创建意味着"谁先发出消息，谁就定义了 Topic 的属性"——生产者代码里手滑把 order-created 打成 order-cretaed，系统不会报错，而是安静地开一条新通道，消息从此分流，下游订阅旧名的那一半永远等不到货；显式创建 + 关闭自动创建，把这类拼写事故从"静默分流"变成"当场报错"。第二层是属性预置：自动创建的 Topic 用默认参数；而分区数、保留策略这些关键属性，显式建的时候才能一次性配对——事后改分区数是迁移级别的动作。第三层是权限与生命周期：企业里 Topic 的创建应该走审批面（admin API / 管理台），有主有据，而不是随第一个生产者"野生长出来"。一句话：自动创建是让第一次五分钟顺滑的开发善意，显式创建才是生产的纪律。官方文档同样提示，真实业务应使用 Producer/Consumer API 或 Pulsar IO，命令行工具只适合实验。

11本期要点与下期预告

带走这四条：

  • Java 21 硬门槛（4.0+），Windows 走 Docker，本机方式仅支持 64 位 macOS/Linux；
  • 四步路线：下载解压 → bin/pulsar standalone → 发 → 收，判定三条：ready 日志、produce 成功提示、----- got message -----；
  • Topic 地址 = persistent://租户/命名空间/主题，public/default 是启动自带的开发默认，admin 三板斧（tenants/namespaces/topics）建自己的；
  • consume 收不到先查订阅游标：-p Earliest 或换新订阅名；standalone 是开发件，生产另算。
