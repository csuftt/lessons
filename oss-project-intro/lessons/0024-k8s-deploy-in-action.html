OSS PROJECT INTRO · KUBERNETES 系列第 4 期：实战场景

把一个服务完整交付上 K8s：从镜像到可访问的端到端实战

前三期你认识了 K8s、用 minikube 把集群跑了起来、看懂了声明式 API 与控制平面——但那些还都是"半成品"：一条 create 命令起的裸 Pod，没有资源底线、没有健康检查、没有稳定入口。这一期做一次完整交付：一份 Deployment 清单（副本、资源请求与限制、就绪与存活探针）→ 一个 Service 暴露 → 发布新版本观察滚动更新 → 一键回滚。示例用 nginx HTTP 服务（换成你自己的 Spring Boot 镜像，清单一行不用改结构），每个字段、每条回显都能在官方文档找到原文出处。全文基于 v1.37.x（1.37.0，2026-08-26 发布，GitHub Latest，2026-09-19 复核）。

01场景设定：一次"完整交付"到底要补齐什么

第 2 期的 hello-node 是最小演示：单副本、裸命令、临时入口。真把一个服务交给 K8s，官方文档给出的标准姿势是写清单、apply、验证，其中至少要补齐四件事：副本与自愈（Pod 死了自动补）、资源底线（requests 与 limits，调度和限流的依据）、健康检查（就绪与存活探针，决定流量给不给、容器杀不杀）、稳定入口（Service，Pod 换了一茬照样找得到）。这份交付链就是本期的路线图：

全程四条目标，做完一条勾一条：

  • ① 清单即交付：一份 YAML 写全副本、资源、探针，apply 之后集群自己把三个 Pod 拉起来并全部就绪；
  • ② 稳定可访问：Service 用 NodePort 暴露，curl 打到 Welcome to nginx!；
  • ③ 滚动更新：改一行镜像，看新 ReplicaSet 渐进替换旧 Pod，全程服务不中断；
  • ④ 历史与回滚：发版记录自动留存，一条 undo 命令退回上一版。

为什么选 nginx本期讲的是交付流程与平台机制，示例选 nginx 是因为每个字段都能在官方文档找到原文，不掺任何臆测。换成你自己的 Spring Boot 镜像：改 image、探针路径换成真实健康端点、端口改成应用端口，清单一行结构都不用动。上期预告里提过的 ConfigMap（配置注入）走的是同一条 spec 声明思路，官方文档单独成页，本期不展开；各对象字段的详细用法与日常排障，官方文档有专页（Ingress 与流量入口），本期不重复展开。

02步骤① 一份 Deployment 清单：把期望状态写全

清单骨架照官方示例抄，只有五处要自己填——名字、副本数、选择器、镜像、端口：

apiVersion: apps/v1
kind: Deployment
metadata:
  name: nginx-deployment
spec:
  replicas: 3                    # 默认 1：不给就只起一个
  selector:
    matchLabels:
      app: nginx                 # 创建后不可变（apps/v1 起固定）
  template:                      # Pod 模板：改它才触发滚动更新
    metadata:
      labels:
        app: nginx               # 必须与 selector 匹配，否则拒绝
    spec:
      containers:
      - name: nginx
        image: nginx:1.14.2
        ports:
        - containerPort: 80

两处"隐形约束"值得停下来：.spec.template 与 .spec.selector 是 spec 里仅有的两个必填字段（官方原话），Pod 模板的 restartPolicy 只允许 Always（默认即 Always）。"改模板才触发更新、扩缩副本不触发"这条规则，第 04 节滚动更新全靠它。

骨架之上补生产底线——资源声明与探针，加在 container 段里：

        resources:
          requests:              # 调度器用它选节点（装得下才放）
            cpu: "250m"
            memory: "64Mi"
          limits:                # kubelet 强制执行的上限
            cpu: "500m"
            memory: "128Mi"
        readinessProbe:          # 失败 → 摘出 Service 端点，不重启
          httpGet: { path: /, port: 80 }
          initialDelaySeconds: 5
        livenessProbe:           # 失败 → 杀容器重启
          httpGet: { path: /, port: 80 }
          initialDelaySeconds: 10

官方文档对这两个词的定义一句话分开：request 是调度依据——调度器用它决定 Pod 放哪个节点；limit 是运行上限——kubelet 强制容器用不超这个数。超限后果分家：CPU 超限被内核节流（throttling），进程不死；内存超限被内核 OOM Kill（容器退出码 137）。只写 limit 不写 request？官方规则：request 自动复制 limit 值。探针字段的默认值一张表收好（出处：Pod API 参考与探针概念页）：

字段默认值含义与提醒
initialDelaySeconds0首次探测前等待；启动慢的应用别只靠它硬扛
periodSeconds10 秒探测周期，最小 1 秒
timeoutSeconds1 秒单次探测超时，慢端点要显式放大
successThreshold1连续成功几次算恢复；存活与启动探针必须为 1
failureThreshold3连续失败几次判死刑；配合周期决定"反应速度"

readiness 配错：活着，但没人理你

路径写错、端口写错，探测一直失败——容器不重启，但 EndpointSlice 控制器会把 Pod IP 从所有匹配 Service 的端点里摘掉。get pods 显示 0/1 NotReady，还算好排查；可怕的是探测路径恰好返回 200 却不验证真实依赖——Pod 就绪了，一打请求才 500。

liveness 配错：活着，但反复横死

失败即杀、即重启，配置激进时是连环反应：启动慢 → 首次探测就失败 → 杀掉重来 → 永远到不了就绪，重启计数一路上涨。它和 readiness 独立运行、互不依赖（官方原文），所以两者要按各自的职责分开配：就绪管流量、存活管死锁。

apply 之后验证，回显与官方文档逐字一致：

$ kubectl apply -f deployment.yaml
deployment.apps/nginx-deployment created
$ kubectl get deployments
NAME               READY   UP-TO-DATE   AVAILABLE   AGE
nginx-deployment   3/3     3            3           18s

读列READY 3/3 是"就绪/期望"——就绪这个词从此有了准确含义：探针说了算，容器在跑不算数。UP-TO-DATE 是已更新到最新模板的副本数，第 04 节滚动的就是它。

03步骤② Service：把会换 IP 的 Pod 包成稳定入口

Pod 会死会换、IP 随机分配（第 3 期的前台总机类比），直连 IP 的演示到交付这一步就该退役了。Service 用标签选择器圈住一组 Pod——控制器持续扫描匹配的 Pod，更新端点集（EndpointSlices）；流量只发给就绪端点，第 02 节的 readiness 探针在这里被"消费"：

apiVersion: v1
kind: Service
metadata:
  name: nginx-deployment
spec:
  type: NodePort                 # 默认 ClusterIP：仅集群内可达
  selector:
    app: nginx                   # 圈住 Deployment 打的标签
  ports:
  - port: 80                     # Service 自己监听的端口
    targetPort: 80               # 转发到 Pod 容器的端口

类型按暴露面选：ClusterIP 只在集群内，NodePort 在每个节点上开一个静态端口（控制平面从 30000-32767 默认范围分配），LoadBalancer 挂云厂商的外部负载均衡器。本地 minikube 用 NodePort 最直接：

$ kubectl apply -f service.yaml
service/nginx-deployment created
$ kubectl get svc nginx-deployment
NAME               TYPE       CLUSTER-IP    EXTERNAL-IP   PORT(S)        AGE
nginx-deployment   NodePort   10.96.34.117  <none>        80:31432/TCP   12s
$ curl -s http://$(minikube ip):31432 | grep title
<title>Welcome to nginx!</title>

Welcome to nginx! 出现，四条目标完成两条。CLUSTER-IP 与分配到的端口每台机器不同（端口落在 30000-32767 内），minikube service nginx-deployment 一条命令直接在浏览器打开。生产级流量入口（Ingress、Gateway API）见官方文档专页，从 Service 往上走的路那里都有。

04步骤③ 滚动更新：发布新版本，服务不中断

发新版 = 改 Pod 模板里的镜像。命令行一条直达（kubectl set image），改完立刻盯进度：

$ kubectl set image deployment/nginx-deployment nginx=nginx:1.16.1
deployment.apps/nginx-deployment image updated
$ kubectl rollout status deployment/nginx-deployment
Waiting for rollout to finish: 2 out of 3 new replicas have been updated...
deployment "nginx-deployment" successfully rolled out

中间那行"等新副本"的等待，就是滚动更新的本体：Deployment 创建新的 ReplicaSet，渐进地扩它、同时缩旧的（官方原话），替换节奏由更新策略控制。默认策略 RollingUpdate 的两个参数默认值都是 25%：maxSurge 允许多起几个（向上取整），maxUnavailable 允许几个不可用（向下取整）。3 副本代入：surge = 1、unavailable = 0——滚动全程最多 4 个 Pod，可用数始终不少于 3。一条 get rs 看到两代同堂：

$ kubectl get rs
NAME                          DESIRED   CURRENT   READY   AGE
nginx-deployment-1564180365   3         3         3       6s
nginx-deployment-2035384211   0         0         0       36s

新 RS（新哈希）三个全部就绪，旧 RS 归零但记录还在——这不是废数据，是第 05 节的后悔药。顺手一提：此时扩副本到 10 个，多出来的副本会按比例同时分给新旧两代 RS（官方"比例伸缩"规则，份额向副本多的 RS 倾斜）——扩缩不触发滚动，但滚动的中间态扩缩，两代都会长。

05步骤④ 历史与回滚：发版记录就是后悔药

每次模板变更自动记一代版本，历史与回滚两条命令：

$ kubectl rollout history deployment/nginx-deployment
deployments "nginx-deployment"
REVISION  CHANGE-CAUSE
1         <none>
2         <none>
$ kubectl rollout undo deployment/nginx-deployment
deployment.apps/nginx-deployment rolled back

不带参数的 undo 退回上一版（2 → 退回 1），--to-revision=2 可以跳回指定代。回滚同样走滚动替换，事件里能看到 DeploymentRollback 记录。CHANGE-CAUSE 列默认 <none>，想留发版说明，在清单上配 kubernetes.io/change-cause 注解。历史默认保留 10 代（revisionHistoryLimit）；官方特别提醒：显式设为 0 会清空全部历史，Deployment 从此无法回滚——省这点存储不划算。

顺手要做的实验：滚动进行中另开终端敲 kubectl get pods -w，你会亲眼看到带新哈希的 Pod 逐个出现、就绪、旧 Pod 逐个终止——第 3 期"一次部署的旅程"的完整回放，这次是你自己触发的。

06随堂小测

每题点击选项立即反馈 · 共 4 题

1. readiness 探针持续失败，Pod 会发生什么？

  • 容器被杀掉并重启，RESTARTS 加一
  • 被摘出 Service 端点收不到流量，容器照跑
  • Pod 对象被删除，由 Deployment 重建

2. 滚动更新默认策略下，maxSurge 与 maxUnavailable 的默认值与取整方向是？

  • 都是 25%，都向上取整
  • surge 25% 向上取整，unavailable 25% 向上取整
  • surge 25% 向上取整，unavailable 25% 向下取整

3. 修改 Deployment 的哪个字段会触发滚动更新？

  • .spec.template（Pod 模板）
  • .spec.replicas（副本数）
  • .spec.selector（标签选择器）

4. 容器只写 limits 不写 requests，官方规则怎么处理？

  • 创建被拒绝，两者必须都写
  • request 自动复制 limit 的值
  • request 按 0 处理，可调度到任意节点

07思考题（点击展开解析）

思考一：liveness 探针的 initialDelaySeconds 配得比应用启动时间还短，会发生什么连环反应？官方为什么还要引入 startupProbe？

逐环推演。应用启动要 30 秒，探针 3 秒就开始查：第一环探测失败——应用没起来，任何路径都不通；第二环达到 failureThreshold——默认连续失败 3 次（约 3×周期+初始延迟，半分钟内），kubelet 判定失败、杀容器重启；第三环重启回到原点——新容器还是需要 30 秒才能服务，但探针计时重新开始，同样的剧本再演一遍。结果是无限重启循环：RESTARTS 一路上涨、容器永远到不了就绪、readiness 也永远不通过、Service 端点始终为空、上游调用方看到的是"服务存在但全部超时"。更阴险的是，每次重启都把启动进度清零，应用越重，越不可能靠自身熬过窗口。有人把 initialDelaySeconds 调到 60 秒硬扛——启动 90 秒就又崩了，而且健康的应用重启后也要白等 60 秒。官方给的正解是 startupProbe：它成功之前，liveness 与 readiness 根本不执行，允许应用安心完成初始化；按官方建议给它 failureThreshold × periodSeconds 覆盖最坏启动时间（示例 30×10s = 5 分钟），成功之后无缝切换到正常的存活检查——liveness 保持默认的灵敏参数不用放宽，慢启动与快死锁两件事就解耦了。设计层面的启示：存活检查的职责是抓"运行中的死锁"，不是"还没启动完"，用一个探针去管两件事，两头都会误伤。

思考二：双 25% 的默认节奏是怎么同时照顾"可用性"与"资源"的？把 maxUnavailable 设为 0、maxSurge 放大，收益与代价各是什么？

先看默认值各自的算法：maxUnavailable 向下取整——宁可少算不可多算，3 副本 × 25% = 0.75 取 0，保证"最少可用数"不吃亏；maxSurge 向上取整——宁可多备不可少备，0.75 进到 1，保证替换通道始终有人顶上。合起来就是默认节奏的精髓：可用数全程不掉线，代价是多占一个 Pod 的资源位。把 unavailable 设为 0、surge 放大（比如 100%），走的是"先起够新的、再停旧的"路线：收益是容量零缩水、滚动更快（新旧可以并行多组）、回滚窗口更从容；代价也明确——瞬时 Pod 数翻倍，每个 surge 出来的 Pod 都带着自己的 requests 去要资源，节点的容量规划必须按峰值预留，公有云上就是真金白银。反过来 surge=0、unavailable=25% 不占额外资源，但可用数先掉再补，高峰期滚动就是主动制造容量缺口。所以发布节奏本质是一道资源预算与可用性预算的交换题，没有两全默认——而它成立的前提，恰恰是第 02 节那份 requests 声明：没有 request，调度器不知道 surge 出来的 Pod 该放哪、放不放得下，节奏参数调得再精细也是空中楼阁。这也解释了为什么"资源声明"要进本期清单的第一课，而不是可选项。

08本期要点与下期预告

带走这几条：

  • 清单五要素：name、replicas（默认 1）、selector（创建后不可变）、template（改它才滚动）、image；必填只有 template 与 selector 两项；
  • 资源两分法：requests 给调度器（选节点），limits 由 kubelet 强制（CPU 节流、内存 OOM Kill 137）；只写 limits 则 requests 自动复制；
  • 探针两分法：readiness 失败摘流量不重启，liveness 失败杀容器重启；默认周期 10 秒、超时 1 秒、连续失败 3 次判死；慢启动交给 startupProbe；
  • 滚动默认节奏：双 25%——surge 向上取整、unavailable 向下取整，3 副本即"最多 4 个、可用始终 3"；改模板才滚动，扩缩不触发；
  • 回滚底气：历史默认留 10 代（revisionHistoryLimit），undo 无参退上一版、--to-revision 跳任意代，设 0 则无法回滚。
