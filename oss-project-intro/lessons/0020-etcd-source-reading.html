02决策一：Raft 库——算法的最小化，使用的最大化

先回答"凭什么成工业标准"。README 的自我介绍两句句句是设计宣言：一是只实现 Raft 算法本身，网络与磁盘都留给使用方（原文：both network and disk IO are left to the user）；二是自称 2016 年起生产环境使用最广的 Raft 库，用户列表里躺着 etcd、Kubernetes、Docker Swarm、CockroachDB、TiDB。共识算法是共用的难题，网络与磁盘却是各家各异的现实——把难题做成纯状态机，任何系统都能带着自己的 IO 来用。

etcd 自己是第一个使用方，接入点在 server/etcdserver/raft.go：一个循环把算法库的产出逐批落地——

// server/etcdserver/raft.go · raftNode.start 主循环（节选，v3.7.1）
for {
    select {
    case <-r.ticker.C:
        r.tick()                       // 时钟推进：选举超时、心跳，全靠它喂
    case rd := <-r.Ready():            // 算法库交出一批"待办"
        if len(rd.ReadStates) != 0 {   // ① 读请求的回执（决策二的入口）
            select { case r.readStateC <- rd.ReadStates[...]: ... }
        }
        // ② leader 先把消息发出去，再慢慢落盘（Raft 论文 10.2.1）
        if islead { r.transport.Send(r.processMessages(rd.Messages)) }
        if err := r.storage.Save(rd.HardState, rd.Entries); ...  // ③ WAL 落盘
        select { case r.applyc <- ap: ... }                      // ④ 已提交条目交给应用层
        r.Advance()
    }
}

这个循环就是"解耦"的全部秘密：算法库不知道 WAL 与网络的存在，使用方不需要懂选举与复制的内部状态机，两边只用 tick/Ready/Advance 三个握手交接。换种做法会怎样？把网络与存储焊死进算法库，每个想用 Raft 的系统都得改造它的 IO 假设——README 里那串用户列表就不会存在。

读码坐标算法本体 raft 仓库 raft.go 的 Step()；使用侧 server/etcdserver/raft.go。两边都是一屏能翻完的量级——理解共识不用啃整个 etcd，这是"最小化"的收益。

03决策二：读请求的协商——为什么不写日志也能线性一致

官方 API guarantees 措辞很强硬：linearized requests must go through the Raft consensus process。但"走共识流程"不等于"写一条日志"。每次读都当提案走完整复制——正确，但读多的系统日志会被读请求灌满。etcd 的选择是 ReadIndex 协商：向多数派确认"当前提交下标"，然后读本机状态机——零日志条目，结果仍线性一致。

入口在 v3_server.go 的 Range：非 Serializable 的读先挂起等待；协商本体在 server/etcdserver/read/read.go：

// server/etcdserver/read/read.go · v3.7.1（节选）
func (r *Read) LinearizableReadLoop() {
    for {
        // ... 攒一批读请求后：
        confirmedIndex, err := r.requestCurrentIndex(leaderChangedNotifier)
        // requestCurrentIndex → sendReadIndex → r.raft.ReadIndex(...)：向算法库要下标
        if err != nil { nr.notify(err); continue }
        appliedIndex := r.server.AppliedIndex()
        if appliedIndex < confirmedIndex {
            // 本机应用位点还没追上多数派确认的下标：等到追上为止
            select {
            case <-r.server.ApplyWait(confirmedIndex):
            case <-r.server.Stopping(): return
            }
        }
        nr.notify(nil)   // 放行这一批读：现在读本机状态机，结果必不落后于 confirmedIndex
    }
}

两个细节都写在源码里：其一，leader 上任后还没提交过当前任期的日志时，ReadIndex 请求先搁置（raft.go 的 !r.committedEntryInCurrentTerm() 分支，read.go 重试日志原话 "first commit in current term"）；其二，confirmedIndex 是"已提交"下标不是"已应用"下标，拿到后还要 ApplyWait 等状态机追平——提交与应用是两本账，差一步线性一致就破产。算法库侧只三行：leader 随心跳向多数派确认下标（quorum），follower 转发给 leader，单成员集群（第 2 期那个）走 IsSingleton 分支直接以 committed 应答。

读模式代价适用
linearizable（ReadIndex）一次多数派心跳往返 + 等应用位点，零日志默认模式，"差一个版本就出错"的读
serializable本机直接应答，可能读到旧值监控大盘、巡检类"读个大概"
lease read（raft 库可选）靠时钟租约免心跳确认（README：relies on the clock）时钟有保障才敢用，etcd 主线未采用

04决策三：MVCC 双层记账——读历史为什么比读当下还顺

第 3 期说过 revision 是全库一把的流水号，本期看它怎么落账。写入落点在 kvstore_txn.go 的 put：第一笔变更领 beginRev+1 作 main，事务内第几笔当 sub；值本体按 revision 字节序写进 bbolt，同时内存树索引登记新版本。

// server/storage/mvcc/kvstore_txn.go · put（节选，v3.7.1）
rev := tw.beginRev + 1                       // 本事务的全局 revision
_, created, ver, err := tw.s.kvindex.Get(key, rev)  // 查旧代：拿 created/version
idxRev := Revision{Main: rev, Sub: int64(len(tw.changes))}
ibytes = RevToBytes(idxRev, ibytes)          // 键 = revision 的字节序编码
kv := &mvccpb.KeyValue{ Key: key, Value: value,
    CreateRevision: c, ModRevision: rev, Version: ver + 1, ... }
tw.tx.UnsafeSeqPut(schema.Key, ibytes, d)    // ① 值本体 → bbolt（backend）
tw.s.kvindex.Put(key, idxRev)                // ② 版本登记 → 内存树索引

// revision.go 的字节格式原注释：前 8 字节 main 大端 + '_' + 后 8 字节 sub
// 墓碑（删除）在尾部再追加 1 字节标记 't'

双层记账的分工：内存 treeIndex（B 树按 key 组织，keyIndex 记录各代 revision 区间）答"这个键在那个时刻的版本号"；数据本体按 revision 字节序躺在 bbolt 里，答"那个版本的值是什么"。字节格式是点睛之笔：main 大端序，按字节比较就是按时间线比较——顺序扫描等于沿时间线回放，--rev 历史读、watch 断线补发吃的就是这个红利。

换种做法会怎样？历史值和最新值混在一张按 key 排序的表里，读历史要扫全量记录再过滤，越老越慢；双层记账把两个问题拆开、各用最合适的数据结构。代价明码标价：旧版本只增不减，compaction 负责断舍离（第 3 期那个 required revision has been compacted 报错的出处）——留多久是运维规划项。

05两条配套链路：watch 推送与 lease 心跳

watch：三本账管推送

写入应用完成后，事件从哪来？watchable_store_txn.go 的 End() 把变更打包成事件，调 s.notify(rev, evs)——快路径：已同步的 watcher 直达通道。watchable_store.go 里 watcher 分三本账：synced（已跟上进度）、unsynced（断线重连追历史的）、victims（通道满了暂存的）。对账由 syncWatchersLoop 驱动，每 100ms 一轮：挑出组内最小起点 minRev，rangeEvents 从 bbolt 捞 [minRev, curRev+1) 的事件逐个补发——第 4 期断线补发的服务端实现。快慢两条路共用第 4 节的 revision 存档，没有第二份事件存储。

lease：心跳不进共识，checkpoint 兜底

第 4 期的 keepalive 心跳，服务端不走 Raft——v3_server.go 原注释："renewals don't go through raft; forward to leader manually"。续约只是 leader 在内存过期堆里刷新一下时间，每次心跳都写日志的话，租约一多共识日志会被心跳淹没。但纯内存记账有破绽：leader 切换后新主内存是空的，所有租约"满血复活"。checkpoint 补上这个洞：lessor.go 默认每 5 分钟把存活租约的剩余 TTL 批量写进共识日志（单批上限 1000 条、限速每秒 1000 条），v3.6 起持久化默认开启；新 leader Promote 时按剩余时间恢复——租约不"换个主子就重置倒计时"。到期撤销走 LeaseRevoke 提案删键（Revoke 里先排序再删，注释写明"否则各成员 backend 哈希会不一致"），键删除与租约删除同事务——第 4 期"到期删键即广播"的源码落点。

07架构师视角：能搬回自己系统的三件事

  • 把"共用的难题"做成纯状态机，把"各异的现实"留给使用方。做可复用组件时常把"我假设你怎么存、怎么传"焊死进去，复用价值当场归零；分层线画在"算法稳定、环境多变"的边界上，是这套库最值得抄的一刀；
  • 强一致不一定要付"每次都写日志"的全价。确认下标、等本机追平、读本机状态——把一次全量复制换成一次心跳确认，配置中心、元数据服务可以直接借这笔账；
  • 双层记账 + 全局单调序列。内存索引管"哪个版本"、追加友好的存储管"内容"，一把全局流水号养活排序、补发、回溯三件套——做事件溯源、变更推送时，比"每处各记各的时间戳"便宜得多。

08随堂小测

每题点击选项立即反馈 · 共 4 题

1. Raft 库（github.com/etcd-io/raft）刻意不包含哪部分？

  • 选举与日志复制的算法本体
  • 网络传输与磁盘持久化
  • 成员变更与日志压缩

2. ReadIndex 线性一致读，拿到 confirmedIndex 之后为什么还要 ApplyWait？

  • 还要再等一次多数派确认
  • 为了等 WAL 落盘完成
  • confirmedIndex 是已提交下标，要等本机状态机应用到该下标才能读

3. MVCC 双层记账里，内存 treeIndex 和 bbolt 各管什么？

  • treeIndex 管键到 revision 的索引，bbolt 管各版本的值本体
  • treeIndex 存最新值，bbolt 只存历史值
  • treeIndex 负责事务过滤，bbolt 负责排序

4. lease 的 keepalive 心跳为什么不直接写进 Raft 日志？

  • 心跳对延迟要求低，共识流程跟不上
  • 逐次心跳写日志会淹没共识日志，改由 checkpoint 定期落剩余 TTL
  • 租约状态不要求一致性，纯内存就够

09思考题（点击展开解析）

思考一：每次读都走一遍完整日志复制，与 ReadIndex 正确性等价吗？成本差在哪？lease read 省掉心跳确认，赌的是什么？展开解析 ▾

正确性等价——读作为提案走日志，应用后应答，读到的状态同样不落后于任何先前完成的写，Raft 论文也把"用日志实现线性一致读"列为可行做法。差距全在成本：走日志的读要付一条日志的复制+落盘+应用全价，还挤占写请求的日志空间，读多的系统写吞吐直接受损。ReadIndex 把它降级成"心跳里捎带一次下标确认"：一个 RTT 换来"我确实是 leader、下标已过半数"的凭证，然后读本机状态机——日志零污染。

lease read 更激进：leader 靠"时钟租约"自我声明，连心跳确认都省，代价是把正确性押在全组时钟漂移有界上——旧 leader 的租约在别人眼里过期而它自己不知道，就可能出现两个"合法读出口"。README 对它的注释直白写了 "relies on the clock"。三种读是同一道题的三档定价：日志复制（最贵最稳）→ ReadIndex（一个 RTT，零日志）→ 时钟租约（零协商，赌时钟）。etcd 停在中间档：不赌时钟，也不为读付日志全价——"默认档"的选择最见设计者的权衡。

思考二：watch 断线补发为什么敢直接从 bbolt 捞历史，不在内存另留一份？把 100ms 对账改成每次写入实时遍历，又会怎样？展开解析 ▾

敢直接捞，是因为第 4 节的双层记账让"捞历史"近乎免费：事件就是 revision 字节序下的变更记录，rangeEvents 一次顺序扫描 [minRev, curRev+1) 就拿到，不需要任何"事件表"冗余。反事实——内存里为 watch 单独留全量历史——等于把 MVCC 记过的账再记一遍：内存无界增长，compaction 清掉的历史还得单独清理，两本账迟早对不上。单一事实源 + 按需捞取才是底气；代价只是补发有 100ms 量级的对账周期，完全可以接受。

再看对账节奏。每 100ms 批量对账一轮：先挑全组最小 revision，一次扫描喂饱整组 watcher——摊销扫描成本。改成每次写入实时遍历，延迟虽好，但写入放大随订阅数上涨；何况补发请求大多成片出现（重启、重连、新建订阅），批处理天然贴合这个负载。第三本账兜底：通道满的进 victims 独立重试，不阻塞写入主流程。三本账合起来是教科书式的背压分级：顺的走快路，慢的排队，堵的缓冲。

10本期要点与系列收尾

带走这几条：

  • Raft 库只做算法状态机（tick/Ready/Advance 握手），网络与磁盘归使用方——etcd、Kubernetes、CockroachDB 共用一份实现（raft v3.7.0）；
  • 线性一致读不写日志：ReadIndex 确认提交下标 + ApplyWait 等应用位点追平，一个心跳往返换零日志污染（read.go）；
  • MVCC 双层记账：内存 treeIndex 答"哪个版本"，bbolt 按 revision 字节序存"内容是什么"——历史读等于顺序扫描，compaction 是留档的账单；
  • watch 三本账：synced 直达、unsynced 每 100ms 对账补发、victims 兜底——补发直接吃 revision 存档；
  • lease 心跳不进共识（leader 内存记账），checkpoint 默认每 5 分钟把剩余 TTL 写进日志（v3.6 起默认持久化），切换不再"满血复活"。
