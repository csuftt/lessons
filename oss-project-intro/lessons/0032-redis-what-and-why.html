OSS PROJECT INTRO · REDIS 系列第 1 期：认识项目

Redis 是什么：内存数据结构服务器

开源项目入门系列的每个新项目，都从三个问题开始：它解决什么痛点、凭什么活下来、什么场景该选它。上一个项目我们聊完了 TDengine，今天开启新项目 Redis——大多数人对它的第一印象是"缓存"，但官方文档开篇第一句是 "Redis is a data structure server"：它是一台内存数据结构服务器，字符串、哈希、有序集合、流，每类结构自带一套原子操作，缓存只是其中一个组合用法。本期不装任何软件，素材全部来自官方文档与官方仓库，每张图都标出处；你带走四样东西：热数据的痛点、这张心智模型、一份五方选型对比，外加 Redis 许可证风波四年的来龙去脉。

01痛点：热数据在磁盘数据库里排队

先看一类每个系统都会遇到的压力。一个电商大促页，商品详情、库存余量、秒杀计数器，一秒钟被读写几十万次；一条热搜话题，排行榜名次每秒钟重算上百回。这类被反复摸的热数据，放进 MySQL 这类磁盘数据库，很快撞上三堵墙：

  • 读写延迟上不去：磁盘库的 B+ 树页不可能全常驻内存，一旦命中磁盘，单次访问从内存的纳秒级跳到磁盘的毫秒级，差着五六个数量级；
  • 高并发读扛不住：磁盘库的连接数与查询吞吐有天花板，大促流量先压垮数据库，连带拖死整条业务链路；
  • 简单操作太重：计数、去重、排行榜、限流这类操作，本质是"对一个结构做一次原子运算"，走 SQL 解析、事务、索引维护的全链路，纯属杀鸡用牛刀。

三堵墙的根源是同一句错配：磁盘数据库为"数据量大、持久第一"设计，热数据场景要的是"数据量小、延迟第一"。解法顺理成章——把热数据整个放进内存，把操作降到数据结构级。2009 年，Salvatore Sanfilippo（网名 antirez）为此写出了 Redis，后来它成了这个位置的事实标准。

02是什么：内存数据结构服务器，数据结构是主角

官方文档的开篇值得逐词读（redis.io《Redis data types》，2026-09 核对）："Redis is a data structure server."——Redis 是一台数据结构服务器。不是"缓存工具"，不是"键值存储"这么简单：键值只是寻址外壳，真正的主角是它内存里内置的十几类数据结构，每类都配了一组原子命令。Redis Open Source 当前实现的类型包括：Strings（含 Bitmaps、Bitfields）、Lists、Hashes、Sets、Sorted sets、Streams、Geospatial indexes、JSON、Time series、Vector sets，外加 Bloom filter、Cuckoo filter、HyperLogLog、t-digest、Top-K 等概率类型——其中 JSON、时间序列、向量集合与五种概率结构，是 2025 年 5 月 Redis 8 把原 Stack 模块收编进内核后的新成员。

> SET bike:1 Deimos
OK
> GET bike:1
"Deimos"
> ZADD racer_scores 10 "Norem"   # 有序集合：成员挂分数，写入即排序
(integer) 1

记住这张图，Redis 的一半设计就懂了：快，是因为数据全在内存、操作是结构级的原生运算；简，是因为命令执行在单线程事件循环里逐条跑，没有锁、没有并发冲突——官方 benchmark 文档原话："Redis is, mostly, a single-threaded server from the POV of commands execution"（从命令执行的视角看，Redis 大多是单线程的）。要用满多核，标准做法是一台机器起多个实例。至于"单线程为什么还能扛住十万级每秒"，第 04 节用官方数字拆。

04钩子一：许可证风波——退出开源又回归的四年

Redis 这四年把"开源商业化"的矛盾演了一遍，时间线值得每个用开源的人记一遍（口径核对自 Redis 官方博客与 Wikipedia，2026-09-19）：

  • 2009—2024 · BSD 时代：核心一直以 BSD-3 条款开源，15 年长成缓存组件的事实标准；
  • 2024-03-20 · 退出 OSI 开源：官方宣布自 7.4 起改用 RSALv2 与 SSPLv1 双许可——两者都不是 OSI 认可的开源协议，RSALv2 禁止把软件商业化或作为托管服务提供给他人，矛头直指"免费托管 Redis 转手卖钱"的大型云厂商；
  • 2024-03 · 社区分叉 Valkey：Linux 基金会牵头，用最后一个 BSD 版本分叉出 Valkey，Google、AWS、Oracle 等云厂商跟进支持，BSD-3 路线得以延续；
  • 2025-05-01 · AGPL 回归：Redis 8 GA，把 AGPLv3 加回第三选项，形成 RSALv2 / SSPLv1 / AGPLv3 三许可任选；同时 Redis Stack 并入核心、免费产品更名 Redis Open Source，官方称分叉已达到"拉平竞争环境"的目的。

对使用者的实际含义：自用、内部托管，三个许可都不限制；要改造后对外分发或做托管服务，AGPLv3 是唯一不开商业授权的选择（注意它的传染性），或者直接选 BSD-3 的 Valkey。这也是"选型对比"绕不开的一节——下一节正面对比。

06什么场景该选它（以及什么场景是错配）

✅ 适合：

  • 热点数据缓存：给磁盘数据库挡读写并发，毫秒级变微秒级——最经典也最大宗的用法；
  • 计数器 / 排行榜 / 去重 / 限流：INCR、ZADD、Set、滑动窗口，一个结构一条命令，天然原子；
  • 会话、购物车这类带过期的热状态：TTL 到期自动清理，配合持久化可当轻量主存储；
  • 队列与事件流：List 阻塞读、Stream 消费组，轻量消息场景不必先上重型队列。

❌ 错配：

  • 大数据量的冷数据主存储：数据集装不进内存，成本随数据量线性走，持久化终究是补充而非替代；
  • 强事务与复杂关联查询：没有跨表 JOIN 与多行事务语义，账务订单交给关系数据库；
  • 当主存储却没配持久化与容灾：内存库怕断电，持久化、复制与哨兵是"当存储用"的前置条件。

一条判断捷径：数据是"热的、结构简单的、要求延迟低的"，Redis 进候选；数据是"冷的、关系复杂的、要求绝对不丢的"，留在磁盘数据库。数据结构用法、缓存三大问题、分布式锁与性能调优这些"怎么用好"的主题，每日微课程线已有七期专题，本系列不换皮重讲，选三篇最相关的作为延伸阅读：

  • Redis 至今仍在使用 RSALv2/SSPLv1 双许可，没有开源选项
  • 2025 年 5 月起 Redis 8 提供 RSALv2/SSPLv1/AGPLv3 三许可任选

3. 按本期的判断捷径，哪个场景最不该选 Redis？

  • 几 TB 历史订单的归档主存储
  • 秒杀活动的实时计数与排行榜
  • 登录会话与购物车，带过期时间

4. "单线程"这个说法，对 Redis 而言准确的理解是？

  • 整个 Redis 进程只有一个线程，任何工作都不并行
  • 命令执行大多在单线程里逐条跑，网络 IO 等可以是多线程
  • 单线程是历史包袱，多实例部署是被废弃的旧方案

08思考题（点击展开解析）

思考一：把缓存从"进程内 HashMap"换成"独立 Redis 服务"，多了一次网络往返，为什么大家反而觉得更快了？这笔账应该怎么算？

直觉的账只算了一头：本机 HashMap 访问是百纳秒级，走一次网络到 Redis 要零点几毫秒，看起来慢了几千倍。但真实系统里，瓶颈很少在"单次访问"，而在"数据库被击穿之后的连锁反应"。算总账要看四笔：其一，兜底对象的速度——缓存未命中时回源的是磁盘数据库，单次几毫秒到几十毫秒，Redis 的零点几毫秒是"快两个数量级之上的缓冲层"，进程内 HashMap 挡不住这一层，因为它是每个实例各存一份，命中率低还互相不一致；其二，一致性成本——多实例部署时进程内缓存要自己解决实例间失效同步，Redis 把状态集中到一处，失效逻辑天然单一；其三，数据结构红利——排行榜、去重、限流这些操作在 HashMap 里要自己写线程安全代码，Redis 一条 ZADD/INCR 就带原子语义；其四，故障与容量边界——Redis 独立部署可以单独扩容、单独重启、配淘汰策略，进程内缓存与业务进程同生共死。所以结论不是"网络往返不贵"，而是"用一次可预算的网络往返，换掉磁盘数据库被击穿时不可预算的雪崩"。什么时候进程内缓存反而对？单实例部署、数据只读且极小、对延迟敏感到微秒级——这时别引入网络，本地缓存加主动刷新更合理。

思考二：2024 年 Redis 改许可证后云厂商集体转向 Valkey，2025 年 Redis 又把 AGPL 加了回来。这场博弈里，谁赢了？如果你在选型，这个历史会如何影响你在 Redis 与 Valkey 之间的取舍？

先别急着站队，把三方的得失摆开。Redis 公司：短期看是让步——AGPL 回归等于承认"用许可证挡云厂商"没挡住；但它换来了生态回流的可能性，并且把 Stack 模块全部并进免费核心，产品反而更完整。云厂商：拿到了彻底开源（BSD-3）、社区中立的 Valkey，托管服务不再受制于人，这是它们最初的目标。社区与普通使用者：表面上多了一个可选项，实际上要面对一个新问题——两个兼容项目从此分头演进，新特性、性能修复、安全补丁的节奏开始分叉。给使用者的选型框架，我建议按四步走：一看许可证约束——自用与内部托管两家都行；要把改造版对外分发，Valkey 的 BSD-3 最干净，Redis 需走 AGPL 或商业授权；二看功能需求——要用 JSON、向量检索、时间序列、概率结构，Redis 8 已内建，Valkey 的对应扩展在跟进中，选型时逐项核对当下版本；三看运维生态——托管服务、云产品、监控工具、客户端兼容矩阵，Redis 仍是最厚的；四看演进风险——兼容双雄并存意味着"Redis 协议"已是公共财产，锁定风险两侧都可控。我的倾向：新项目默认 Redis 官方开源版，许可证有硬约束或明确要社区中立治理时选 Valkey——把决策依据写在架构文档里，比选哪一个本身更重要。
