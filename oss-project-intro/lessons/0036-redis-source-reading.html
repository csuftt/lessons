04决策一 · SDS：拒绝 C 字符串的理由

为什么这么设计？C 字符串有三堵墙。取长度要从头数到尾——C 字符串没有长度字段，strlen 逐字节扫描，开销与内容等长，对每秒上万次操作的内存库不可接受；二进制不安全——以空字符当结尾，内容里出现空字节就被截断，图片与序列化对象存不了；拼接不查边界——溢出是 C 程序的经典事故。Redis 的答案是自造 SDS（简单动态字符串）：一段连续内存，头紧贴数据，指针直接指向数据区。

解决什么问题？除了长度，还有分配次数。sds.c 的 sdsMakeRoomFor 定下预分配规矩：增长后不足 1 MB 就翻倍拿，超过 1 MB 就每次多拿 1 MB——连续追加不必一次次向系统要内存；缩短字符串时只改 len 不还内存（惰性释放），真要归还另有 sdsRemoveFreeSpace。配一个真实细节：sdshdr 的 flags 字段一物两用，低三位存类型，在 sdshdr5 里剩下五位还能存长度——源码注释原文 3 lsb of type, and 5 msb of string length。

换种做法会怎样？硬用 C 字符串：长度现数、二进制截断、溢出自担、扩容抖动，四样全占。换 C++ 字符串或别的语言？Redis 选 C 是为了零依赖、每个字节可控，然后用内存布局技巧把 C 的短板一块块补上——这是它给所有 C 程序员的示范：你的项目未必用 C，但"头贴着数据、按需选头、取消对齐"这套账，换种语言照样算得通。

05决策二 · zset 的双结构：左右互搏

为什么这么设计？排行榜这个负载有两类问题：给一个成员问它的分数（点查），和按分数段取一批成员（范围查询）。一个结构很难两头都做到最优，Redis 干脆养两个——官方文档的实现注记原话：有序集合由一个 dual-ported（双端口）结构实现，同时包含跳表和哈希表：

解决什么问题？看源码里的咬合点（src/t_zset.c，tag 8.10.2）：新增成员先 zslInsert 进跳表，再 dictSetKeyAtLink 把节点指针登记进哈希表；注意哈希表的值存的是节点指针而非分数，于是判重与取分数走哈希表（常数时间），分数变化只动跳表、节点指针不变，哈希表无须重排。判重由调用方 zsetAdd 用 dictFindLink 在哈希表完成；zslInsert 的注释只约定"元素已存在由调用方保证"。小编码的转换由 zsetConvertToListpackIfNeeded 把关，阈值就是配置项 zset-max-listpack-entries（默认 128）与 zset-max-listpack-value（默认 64 字节）。

换种做法会怎样？只留跳表：点查退化成对数级遍历，判重也要付一次对数代价；只留哈希表：范围查询与排序直接消失。写入时多付一次登记，换读取时两条路径各自最优——排行榜读取远多于写入，这笔交易稳赚。这正是"读写比例决定结构数量"的活教材。

06钩子一 · 为什么不用平衡树，更不用 B+ 树

跳表不是唯一能做有序范围查询的结构。红黑树取一段范围要中序遍历，插入删除要旋转保平衡，实现繁琐；B+ 树更不对路——它是为磁盘设计的：节点按页（通常 16 KB）组织，赌的是"磁盘读一块顺手多拿一块"，还要浪费页内空间换矮树减少寻道。而 Redis 全程在内存里，随机访问免费，页式预设全部落空。跳表用多层链表换来同样的对数级范围查询，核心一两百行，还天生带有序遍历，插入按随机层数挂链、没有旋转。内存里选结构，磁盘的规矩不作数——这句话反过来说也一样：做磁盘存储时，别把内存结构的习惯带下去。顺带一提，第 3 期讲过的近似 LRU 不维护全局链表，与本期的取舍是同一门哲学：用可接受的近似，换掉不可接受的成本。

演进故事（钩子二）：小集合的紧凑编码也换过代。最早的 ziplist 让每个元素记着前一项的长度（为了从后往前走），代价是前一项变长、后面全跟着改，极端时一条写入放大成连锁反应，即级联更新。Redis 5.0（2018）引入的 listpack 去掉这个字段，每个元素只记自己，隐患从根上拔掉；7.0（2022）起 hash/zset 等小集合编码默认换新；到 8.10.2，配置项里 zset-max-ziplist-entries 这个老名字还在，只是被官方映射成 listpack 新名的别名。好结构也迭代，别把历史名字当永恒真理。

07决策三 · 单线程的分界线画在哪

为什么这么设计？"Redis 是单线程的"这句话省略了主语，第 3 期给过官方口径：从命令执行视角看，大多是单线程。分界线画在这——网络读写与协议解析可以多线程，命令执行永远串行。敢串行的底气：操作全在内存，微秒级完成，串行成本可忽略；换来的是无锁、无线程切换、每条命令天然原子。

解决什么问题？执行链的源码坐标（tag 8.10.2）：server.c 的 main 启动一切，末尾 aeMain(server.el) 把控制权交给事件循环（ae.c），大循环反复处理事件；命令到达后由 networking.c 的 readQueryFromClient 收下解析，进 server.c 的 processCommand 查命令表、过校验，再由 call 经函数指针 c->cmd->proc(c) 调到具体命令实现——整条链上没有一把锁。IO 线程组在 8.0 起独立为 iothread.c：客户端按分配进某个线程完成读写解析，命令仍交回主线程。配置口径：io-threads 默认 1（注释原文 Single threaded by default），且在 8.10.2 中为启动级配置，改线程数需重启。

换种做法会怎样？命令也多线程化：锁竞争与线程切换立刻盖过微秒级的计算本身，INCR 这类命令还得靠脚本或锁补原子性，复杂度上去了，收益却仍看网络脸色。Redis 把最贵的并发问题整个收走，把真正的瓶颈交给线程组——官方基准每秒十八万次写入就是这么来的。设计不是堆并发，是把钱花在瓶颈上。也记住代价：正因串行，一条慢命令会堵住后面所有人（延伸阅读见 daily 线《性能调优》）。

08这些设计，能搬回你自己的系统

  • 内存布局技巧：头贴着数据、按长度分档选头、packed 取消对齐——序列化协议、网络包解析、自定义存储格式都用得上"按字节抠"的账本；
  • 双结构配合：点查与范围查询两类负载并存时，别硬让一个结构两头兼顾——用同一个对象指针把两个结构咬合起来，写入多付一次，读取各自最优；
  • 把并发收进单线程的勇气：先算清操作的真实成本（内存微秒级 vs 切换与锁），若串行成本可忽略，原子性白送、延迟可预期；真瓶颈在 IO，就把多线程给 IO；
  • 能不分配就不分配：预分配、惰性释放、小编码过渡——分配是昂贵操作，写路径的平稳比单次极限速度更重要。

09随堂小测

1. SDS 取长度是常数时间，靠的是什么？

  • 结尾空字符帮忙计数
  • 头结构里带着 len 字段
  • 单独缓存了长度副本

2. tag 8.10.2 里，zset 的 dict 哈希表中"值"存的是什么？

  • 分数（double 值）
  • 成员字符串的副本
  • 跳表节点的指针

3. 关于 8.10.2 的 io-threads 配置，哪个说法对？

  • 默认 4，运行时可随时改
  • 默认 1，启动级配置需重启生效
  • 默认 8，只影响写回包

4. 小 zset 默认住 listpack、超阈值才转跳表，默认阈值是？

  • 成员数不超 128 且单个成员不超 64 字节
  • 成员数不超 512
  • 总大小不超 1024 字节

10思考题（点击展开解析）

思考一：把 SDS 改成"头和数据分开两次分配"的经典 C 结构体做法，会失去什么？为什么 Redis 宁可用 s[-1] 这种取巧写法？

先列分开分配的账：一次 SDS 创建变成两次 malloc，释放也要两次；对象多一个指针字段；头和数据在堆上可能相距很远，缓存局部性变差——对每秒上百万次操作、以内存访问为主体的引擎，这些都是真金白银的开销。再看紧贴布局换来的三样东西：一次分配一次释放，创建销毁路径最短；头和数据几乎必然落在同一缓存行附近，sdslen 读头、业务读数据都便宜；s[-1] 一个字节就能拿到类型，分支选头的成本降到最低。sdshdr5 更是极端：头只有 1 字节，类型和长度共用一个字节——分开分配根本做不到这个密度。代价也要认：紧贴布局意味着增长时头和数据要一起 realloc，SDS 用预分配（不足 1 MB 翻倍）摊薄这个成本；同时 sds 指针不是对象首地址，不能 free(s) 了事，必须走 sdsfree——这是一切取巧的代价，源码里用"永远返回指向 buf 的指针 + 统一走 sds 系函数"的纪律来管住。可借鉴的判断点：当你有一种小对象要海量创建时，把元数据和数据放进同一次分配，通常是赢的；前提是像 Redis 一样，把"指针不是首地址"的纪律封装在访问函数里，而不是散落在业务代码中。

思考二：假如让 zset 只留跳表、砍掉哈希表，功能上还完整吗？反过来只留哈希表呢？由此说说"结构数量该由什么决定"？

只留跳表：功能几乎完整——判重可以在插入时顺带查到（zslInsert 前先按分数区间定位），取分数 O(1)（节点自带），排名与范围照常。但两件事变贵：一是点查判重从哈希的常数时间变成对数级，二是像 ZSCORE 这种高频点查命令每次都要先走一遍跳表定位——排行榜刷分场景里，这正是最热的路径。只留哈希表：更糟，范围查询与排序能力整体消失，ZRANGE/ZRANGEBYSCORE/排行榜全没了，等于砍掉这个类型存在的理由。所以答案分两层：第一层是负载决定结构——读路径有几种，就值得养几个结构，点查养哈希、范围养跳表；第二层是一致性成本决定咬合方式——两个结构必须指向同一批节点（dict 存节点指针而非分数副本），才能把"一次写入两处登记"的成本压到最低，改分数时只动跳表一边。推而广之：数据库的二级索引、搜索引擎的正排加倒排，都是同一个模式。当你发现一个结构为了两类查询互相妥协时，别急着优化它——先算算，多养一个结构是不是更便宜。

11本期要点与下期预告

带走这五句话：

  • SDS 是一段连续内存：len 头常数时间取长度、二进制安全、预分配加惰性释放——C 项目内存布局的教科书；
  • zset 双结构：哈希管点查、跳表管范围，一个节点指针咬合；小集合先住 listpack，超 128 成员才升级；
  • 单线程分界线：网络读写可多线程（iothread.c），命令执行永远串行——无锁、无切换、原子性白送；
  • 能不分配就不分配：按长选头、packed 省对齐、预分配、listpack——内存哲学贯穿全库；
  • 读码路线：main → aeMain → readQueryFromClient → processCommand → 命令实现 → 写传播，基准 tag 8.10.2。
