OSS PROJECT INTRO · TDENGINE 系列第 4 期:实战场景

把设备数据接进 TDengine:从 JDBC 连接到窗口聚合的端到端实战

前三期你认识了 TDengine、把它跑了起来、画出了架构地图——但业务代码还一行没写。这一期把"写入旅程"接上真实应用:用官方 Java 连接器 taos-jdbcdriver,走 WebSocket 连上第 2 期跑起来的容器,把设备心跳数据端到端写进去——自动建表写入让设备上线零 DDL,一条 INSERT 批量写一批心跳,LAST_ROW 随手查设备最新状态,INTERVAL 窗口聚合出每分钟平均电流;最后用 schemaless 行协议做对照,连超级表都自动建。全文基于 v3.4.x + taos-jdbcdriver 3.9.2(Maven Central 2026-09-19 核对),连接方式、依赖坐标、代码与回显逐条对照官方文档。

01场景设定:一千台设备的"心跳",怎么接进来?

场景刻意选小,但把时序数据接入最有代表性的动作都装进去了:1000 台智能电表,每台每 10 秒上报一条心跳——采集时间、电流、电压、功率相位;设备上线前无法逐台写 DDL,数据要随时能查"这台设备现在什么样",还要能出"每分钟平均电流"这样的趋势线。数据流如下图:

全程四条目标,做完一条勾一条:

  • ① 连接器接入:官方 taos-jdbcdriver,走 WebSocket 连上第 2 期的容器,不装任何客户端驱动;
  • ② 自动建表写入:设备心跳一条 INSERT 进库,子表不存在自动建——设备上线零 DDL;
  • ③ 最近值查询:一条 SQL 查回每台设备最新一条心跳,大屏轮询就用它;
  • ④ 窗口聚合:INTERVAL 按分钟聚合平均电流,趋势线数据一句话出来;最后用 schemaless 做一次"协议直连"对照。

怎么设计标签、怎么划分超级表这类建模方法论,官方文档 · TDengine 数据建模已讲透;写入与查询的性能调优见 官方文档 · TDengine 写读性能实践。本期只讲"用 Java 把链路跑通",不换皮重讲。

02依赖与版本:一个连接器,先选对连接方式

Java 侧只需要一个依赖:官方连接器 taos-jdbcdriver。版本动笔前在 Maven Central 核对过,最新 release 是 3.9.2(2026-09-16 发布):

<dependency>
  <groupId>com.taosdata.jdbc</groupId>
  <artifactId>taos-jdbcdriver</artifactId>
  <version>3.9.2</version>
</dependency>

三份版本账本一起对齐:

组件版本出处负责什么
TDengine 服务端3.4.x(文档站 v3.4.2)第 2 期 Docker 容器存数据、跑 SQL
taos-jdbcdriver3.9.2Maven Central(2026-09-19 核对)JDBC 驱动:建连、执行 SQL、写入
JRE / JDBC 标准JRE 8+ / JDBC 4.2+官方连接器文档"兼容性"一节驱动运行环境

连接方式三选一,先选对再写码:官方文档明确"推荐使用 WebSocket 连接"——通过 taosAdapter(6041 端口)通信,不依赖客户端驱动,还带兼容性保证(服务端 v3.3.6.0 及以上,连接器 3.6.0+)。而原生连接(jdbc:TAOS://,走 6030,要装 taosc 客户端驱动)和 REST 连接(jdbc:TAOS-RS://)都将于 2027-01-01 下线,官方已发出废弃通知。老文章里那两类 URL,现在别再抄进新项目。

一句话记住选型逻辑:WebSocket 连接的地址走 6041,请求先到 taosAdapter——正是第 3 期说的"前台收发室";原生连接虽然少一跳,但要给每台部署机器装平台相关的驱动库,分发成本高,官方已经宣判。本期全程 WebSocket。

03第一步:一条 URL 建连,两张 SQL 建模

WebSocket 连接的 URL 规范是 jdbc:TAOS-WS://host:6041/db?user=…&password=…,驱动类为 com.taosdata.jdbc.ws.WebSocketDriver——taos-jdbcdriver 3.x 遵循 JDBC 4.0 的 SPI 自动发现,不需要写 Class.forName。URL 里直接带上库名 power(第 2 期建的),连接即默认库:

String url = "jdbc:TAOS-WS://localhost:6041/power?user=root&password=taosdata";
try (Connection conn = DriverManager.getConnection(url)) {
    System.out.println("[ OK ] Connection established.");   // 官方示例同款回显
}

连接拿到了,建数据模型。两条 SQL 与第 2 期命令行里敲的完全一致——SQL 不变,只是换了执行入口:以前在 taos 命令行敲,现在从 Java 发过去:

try (Statement stmt = conn.createStatement()) {
    stmt.executeUpdate("CREATE DATABASE IF NOT EXISTS power "
        + "PRECISION 'ms' KEEP 3650 DURATION 10 BUFFER 16");
    stmt.executeUpdate("USE power");
    stmt.executeUpdate("CREATE STABLE IF NOT EXISTS meters ("
        + "ts TIMESTAMP, current FLOAT, voltage INT, phase FLOAT) "
        + "TAGS (location VARCHAR(64), group_id INT)");
}

超级表是"模板":四列采集量 + 两个标签。IF NOT EXISTS 让这段代码天然幂等——应用重启多少次,模型只有一份。到这一步,目标①达成:一个依赖、一条 URL、零本地驱动安装。

04第二步:自动建表写入,设备上线零 DDL

写入的核心是自动建表语法(第 2 期埋的伏笔):INSERT INTO 子表 USING 超级表 TAGS(标签值) VALUES(…)——子表不存在就先按模板建一张再写,存在就直接写。设备上线瞬间,子表自动出现,应用侧没有任何建表代码:

// 单台设备上报一条心跳(设备号、标签值由上报数据携带)
String sql = "INSERT INTO d1001 USING meters TAGS('California.SanFrancisco', 2) "
           + "VALUES (NOW, 10.3, 219, 0.31)";
stmt.executeUpdate(sql);

实战里设备是攒一批再发的(每 10 秒一条,一次同步 10 分钟的数据)。一条 INSERT 写多行、甚至多张子表,这是官方示例的标准写法——一条语句同时写 d1001、d1002 两张表:

String sql = "INSERT INTO "
    + "d1001 USING meters TAGS(2, 'California.SanFrancisco') VALUES "
    + "(NOW + 1a, 10.3, 219, 0.31) (NOW + 2a, 12.6, 218, 0.33) (NOW + 3a, 12.3, 221, 0.31) "
    + "d1002 USING meters TAGS(3, 'California.SanFrancisco') VALUES "
    + "(NOW + 1a, 10.3, 218, 0.25)";
int rows = stmt.executeUpdate(sql);
System.out.println("insert " + rows + " rows.");   // 官方 JDBCDemo 同款回显

这里藏着本期最重要的一个性能反直觉,官方文档常见问题一节写得很直白:用 JDBC 标准的 addBatch() / executeBatch() 做"批量写入",不会带来性能提升——因为驱动只是把 SQL 按顺序逐条执行,和服务端的交互次数一点没少。官方给出的三条正路:

写入方式怎么用适合场景
一条 INSERT 拼多个 values上面的写法,一次网络往返写一批中小批量、代码最简单
参数绑定(PreparedStatement)tbname 与标签、列都作为绑定列,预编译后循环绑定大批量高频写入,免 SQL 拼接注入风险
多线程并发插入按设备或分片拆到多个线程配合前两者继续压吞吐

为什么"多 values 拼接"赢在交互次数:对 TDengine 这种写入极快的服务端,Java 端一次 executeUpdate 的耗时大头在网络往返和语句解析上。100 条心跳逐条发 = 100 次往返;拼成一条 = 1 次。参数绑定的 addBatch 在 taos-jdbcdriver 3.x 的 WebSocket 连接下则走预编译语句复用(3.9.1 起还支持 stmtCacheSize 缓存),同样是"少交互"思路——两条路殊途同归,想深挖见官方文档性能一章。

05第三步:查最近值与窗口聚合,大屏两个接口就齐了

先查"设备现在什么样"。TDengine 专门为"最新一条"准备了 LAST_ROW:取最后一行的值,不忽略空值——和取"最后非空值"的 LAST 有细微差别。查单台设备直接指定子表;查全部设备就在超级表上 PARTITION BY tbname,每台设备各取各的最新行:

SELECT LAST_ROW(ts), LAST_ROW(current), LAST_ROW(voltage)
FROM meters PARTITION BY tbname;

再出"每分钟平均电流"趋势线。INTERVAL(1m) 把数据按一分钟切窗,_wstart 是每个窗口的起始时间;SELECT 列表里只有聚合函数时,每个窗口输出一行聚合结果。把窗口聚合配上标签过滤,就能只看某一组设备:

SELECT _wstart, AVG(current) FROM d1001
WHERE ts >= NOW - 1h INTERVAL(1m);

两段查询跑起来,回显长这样(数值取自官方示例写入的那批心跳:10.3、12.6、12.3 三条在 10:29 窗口,13.4 一条在 10:30 窗口;回显格式对照官方文档):

taos> SELECT LAST_ROW(ts), LAST_ROW(current) FROM d1001;
         last_row(ts)         |    last_row(current) |
=====================================================
 2026-09-19 10:30:01.000     |             13.40000 |
Query OK, 1 row(s) in set (0.004514s)

taos> SELECT _wstart, AVG(current) FROM d1001 INTERVAL(1m);
         _wstart              |        avg(current) |
==============================================
 2026-09-19 10:29:00.000     |             11.73333 |
 2026-09-19 10:30:00.000     |             13.40000 |
Query OK, 2 row(s) in set (0.008816s)

目标③④达成。注意这两条查询的执行形态正好是第 3 期架构图的"查询回路":mnode 给路由,各 vnode 并行扫,taosc 做最后一级聚合——设备越多,这条回路摊得越开,大屏轮询越敢写。最近值查询还有一类进阶用法(结合缓存 last_row 与流计算持续输出),属于性能与建模话题,官方文档性能一章已覆盖。

06对照实验:schemaless 行协议,连超级表都不用建

前面四步都假设"超级表是我建的"。但如果设备上报的字段今天三个明天五个,schema 由数据源说了算,就该请出 TDengine 的无模式写入(schemaless):直接写 InfluxDB 行协议,一行字符串一个数据点,格式 measurement,tag_set field_set timestamp。连接对象上就能调用(官方 API:Connection.write):

String[] lines = {
    "meters,location=California.LosAngeles,groupid=2 "
        + "current=11.8,voltage=221,phase=0.28 1648432611249000",
    "meters,location=California.LosAngeles,groupid=3 "
        + "current=10.8,voltage=223,phase=0.29 1648432611249300"
};
conn.write(lines, SchemalessProtocolType.LINE,
           SchemalessTimestampType.MICRO_SECONDS);   // 官方 LineProtocolExample 同款

跑完去库里看,TDengine 替你做了三件事,全部零 DDL:

  • ① 超级表自动建:行协议里的 measurement(device_metrics)不存在就自动建为超级表;
  • ② 列自动增:下一批数据多了个 humidity 字段?超级表自动加上这一列(只增不减);
  • ③ 子表自动建:子表名由 measurement + 标签做 MD5 映射自动生成(固定 t_ 前缀),标签值统一按 NCHAR 处理。

两种写入怎么选?给你一张对照表:

INSERT INTO … USING(本期主线)schemaless 行协议(本节对照)
schema 控制权应用侧显式建模,类型精确数据侧说了算,自动建表加列
子表名自己起(d1001,语义清晰)自动生成 t_ + MD5,可配置改
适合场景业务建模稳定,要按标签聚合多协议接入源、字段多变的边缘侧

一个工程提醒:schemaless 的标签值统一转 NCHAR,如果后面又要用 SQL 按标签做数值比较,自动转型的类型可能不如显式建模清爽——能显式建模就显式建模,schemaless 留给"schema 不可控"的场景。这正是"写入方式是分层工具箱"的含义。

07随堂小测

每题点击选项立即反馈 · 共 3 题

1. 新写的 Java 应用接 TDengine 3.4,官方推荐的连接方式是?

  • 原生连接 jdbc:TAOS://,走 6030 端口
  • REST 连接 jdbc:TAOS-RS://,HTTP 通用
  • WebSocket 连接 jdbc:TAOS-WS://,走 6041

2. 用 addBatch()/executeBatch() 批量写入,为什么官方说没有性能提升?

  • 网络带宽被 JSON 序列化占满了
  • SQL 仍逐条执行,服务端交互次数没减少
  • 自动建表在批量里被反复触发

3. LAST_ROW 和 LAST 的差别是什么?

  • LAST_ROW 取最后一行不忽略空值,LAST 取最后非空值
  • LAST 只能查子表,LAST_ROW 只能查超级表
  • LAST_ROW 是 LAST 的别名,完全等价

08思考题(点击展开解析)

思考一:官方为什么要给原生连接和 REST 连接定死"2027-01-01 下线"?从驱动分发、通信形态、功能演进三个角度,分别推一遍 WebSocket 的胜因。

先看驱动分发:原生连接要求每个部署了 Java 应用的机器都装上平台相关的客户端驱动(Linux 是 libtaos.so,Windows 是 taos.dll),版本还得和服务端对齐——JVM 应用引一个 jar 就能跑的惯例被打破了,连接器每次升级都拖着一串驱动包变更。WebSocket 连接只需要一个 taos-jdbcdriver,不依赖任何本地库,这是"官方文档特别强调不需要依赖客户端驱动"的原因,也是 Java 生态最看重的一点。再看通信形态:REST 是一问一答的短连接 HTTP,每次请求都要重建会话语义,延迟和并发能力都吃亏,后来者 WebSocket 天生就是长连接,还支持多端点负载均衡与自动重连(3.7.5 起)。最后看功能演进:近两年连接器的新能力几乎全落在 WebSocket 通道上——高效写入(asyncWrite=stmt)、Decimal/BLOB 类型、参数绑定缓存、传输压缩、连接器高可用端点发现,而原生通道基本只剩维护。综合起来,这是一次教科书式的"收拢通道"决策:维护三条通道的成本,远高于把全部新特性押在一条上的收益。给我们的借鉴是:自家系统里同一种能力若有多个接入协议并存,尽早定主推通道并给出迁移期限,拖着不决只会让三边都做不深。

思考二:自动建表写入是"子表不存在就建",那 1000 台设备同时上线会怎样?设备离线半年后重新上线,标签改了、又多了个新字段,INSERT USING 会发生什么?

分三段推。并发上线:INSERT USING 的自动建表是幂等的——表不存在就建、存在就直接写,1000 台设备同时上报不会互相覆盖;按第 3 期的架构,这 1000 张子表会被一致性哈希摊到多个 vnode 上,建表请求各自落在自己 vnode 的元数据里,并发建表互不阻塞,这正是"单 vnode 表上限 100 万"敢开这么大的原因之一。标签变更:子表已存在时,TAGS 子句里的标签值不会改写历史标签——想改设备属性要走 ALTER TABLE … SET TAG(标签躺在 vnode 元数据里,改的是元数据,不重写数据)。所以"设备换了安装位置"这类事件,要作为一条显式的变更操作,而不是指望下一条 INSERT 顺手改掉。新增字段:如果设备固件升级后多报了一个字段,显式建模的路径是 ALTER STABLE meters ADD COLUMN——模板一改,所有子表立即生效(第 3 期讲过超级表 schema 存元数据);而如果走的是 schemaless,新字段会自动加列(只增不减)。两相对照就更清楚"两条写入路线"的分工:INSERT USING 给"schema 在我手里"的业务,加列是显式决策;schemaless 给"schema 跟着设备走"的边缘场景,加列是自动行为。理解了这些边界,自动建表就不是一个"省事的语法糖",而是一套带规则的变更协议。

09本期要点与下期预告

带走这五条:

  • 连接方式先选对:WebSocket(jdbc:TAOS-WS://,6041)是官方推荐,免装客户端驱动;原生与 REST 连接 2027-01-01 下线,老 URL 别再抄;
