OSS PROJECT INTRO · Nacos 系列第 3 期：核心概念与整体架构

Nacos 的概念地图：三层寻址、两类实例、一套分层架构

前两期你已经能让 Nacos 跑起来、能用 curl 塞数据进去，但控制台里那些 Namespace、Group、DataId、临时实例，大概率还是一团模糊。这一期把这团雾拆干净：先建立"三层寻址"的空间感（数据放在哪），再分清"临时与持久"两类实例的本质差别（数据以什么方式活着），最后自上而下走一遍服务端分层架构，并把源码仓库的每个模块对号入座——你第 2 期敲的每条 curl，这一期都能看到它落在了哪个模块。

四层各自只关心一件事：接入层管"怎么说得上话"，核心域管"业务规则"，协议层管"集群内数据怎么达成一致"，持久层管"重启后还在不在"。后面所有小节都是这张图的局部放大。

02数据放在哪：Namespace → Group → Service/DataId

Nacos 里所有数据——不管是服务还是配置——都用同一个三层坐标定位，用"省 → 区 → 门牌"来记：

  • Namespace（命名空间）：最外层的硬隔离单位。最典型用法是按环境切：dev、test、pre、prod 各一个 namespace，互相完全不可见——dev 环境注册的服务绝不可能被 prod 的消费者拉到，因为它们连"看见"都看不见。也用于多租户隔离。
  • Group（分组）：namespace 内的软分组，默认 DEFAULT_GROUP。常见用法是按业务域或项目划（如 TRADE_GROUP），解决"不同业务给服务/配置起了同名"的冲突。
  • Service（服务）/ DataId（配置条目）：具体的叶子。服务侧是服务名（如 stock-service）；配置侧是 DataId——通常就是"应用名+环境+格式"的文件名（如 stock-service-dev.yaml），每条配置还有独立的 MD5 内容指纹用于变更比对。

一条命令复习三层坐标：第 2 期那条注册 curl 里的 serviceName=quickstart.test.service 是叶子；没写 namespace/group 时都落在 public 命名空间的 DEFAULT_GROUP——控制台顶部的命名空间下拉一切，三个世界就分开了。

03实例的两种活法：临时 vs 持久

服务模型是三级树：Service（服务）→ Cluster（逻辑集群，常按机房/可用区划分）→ Instance（实例）。每个实例带着 IP、端口、权重（weight，负载均衡用）、元数据（metadata）和一个决定命运的布尔值：ephemeral——是否临时实例。这个布尔值同时改变三件事：

维度临时实例（ephemeral=true，默认）持久实例（ephemeral=false）
怎么保持在线客户端主动发心跳续约，停跳即"失联"服务端主动探测（TCP/HTTP 探活）
下线方式心跳超时自动摘除，记录消失进程没了记录仍在，标记不健康
一致性归属Distro 协议（AP，最终一致）Raft 协议（CP，多数派提交）
典型是谁微服务实例（伸缩无常，死了就该消失）DB、Redis 这类"地址基本不变"的基础设施

为什么默认是临时？因为微服务实例天然"无常"——K8s 滚动更新一晚实例换一轮，电话簿跟得上变化的唯一办法就是"活着才算数"。持久实例是给那些"人走了门牌还在"的老基础设施准备的：DB 实例探不通了你要的是告警（记录还在、标红），而不是记录消失。

04配置的生命线：推送与本地快照

配置侧的三个概念补完：每条配置由 DataId + Group + Namespace 定位；每次发布产生一个历史版本（可回滚），支持 Beta 灰度（先推给指定 IP 验证再全量）。但配置真正的设计精华在客户端：

  • 监听机制：SDK 对每条用到的配置注册监听器；1.x 时代靠长轮询（客户端发起 30 秒挂起的请求，服务端有变更立刻返回，没有就超时返回再发下一轮），2.x 起统一走 gRPC 长连接的服务端推送——对使用者无感，只是延迟从"最多一个轮询周期"变成毫秒级。
  • 本地快照（snapshot）：SDK 会把拉到的配置在本地磁盘存一份快照。Nacos 服务端整个宕机、重启的几分钟里，应用启动仍能从快照读到上次的配置以旧值启动——注册中心挂了是"找不到新朋友"，配置中心挂了若没有快照就是"所有人都起不来"，后者是致命的。快照让配置中心具备"读旧"的降级能力。

05一致性层：Distro 与 Raft 怎么分工

第 1 期留的思考题在这里正式展开。Nacos 集群里流动的数据分两类，一致性层给了两套协议——这是 Nacos 架构上最有辨识度的决策：

  • Distro（AP，最终一致）：服务临时实例数据。集群每个节点都能接收任何客户端的注册/订阅（这点很重要：客户端不用管连的是哪个节点），节点对自己"负责"的那部分数据做分片权威——写请求路由到负责节点，再异步同步给其他节点。网络分区时各节点宁可短暂数据不一致，也保证"能注册、能发现"持续可用；反正心跳停了坏记录会自愈。
  • Raft（CP，多数派提交）：配置数据与持久实例。写入必须获得集群多数节点确认才算成功——集群 5 台挂 2 台照常写，挂 3 台（不过半）则拒绝写入保一致。配置是账本，宁可不写也不能两边各记各的。

对照第 1 期的"电话簿 vs 账本"：电话簿丢一页会自愈（实例重新注册就回来了），账本丢一行永远不会自己长回来——所以前者换可用性，后者换一致性。这个"按数据类型拆协议"的思路，比"整个系统选一边"精细得多，第 5 期讲源码时会看到它在代码里怎么落地。

06源码仓库模块地图：对号入座

把上面的分层对到源码目录（develop 分支，2026-09 核对），每个模块一句话：

模块对应分层一句话职责
api客户端契约NamingService / ConfigService 等对外接口与数据模型定义
client客户端 SDK接口实现：注册代理、本地缓存、快照、gRPC 通道（你 pom 里引的就是它）
namingL2a 核心域服务发现全部业务逻辑，Distro 协议实现也在这条线
configL2b 核心域配置管理、灰度、历史版本、变更推送（1.x 长轮询的经典实现在此）
consistencyL3 协议层一致性抽象与 Raft 接入（持久数据多数派复制）
persistenceL4 持久层（3.x）存储抽象，内嵌库与外置 MySQL 数据源在插件机制下切换
console + console-uiL1 接入层控制台后端与前端（3.x 拆为独立部署的 console）
core / auth / plugin旁挂能力成员管理、鉴权体系、扩展点（数据源/trace/加密插件）
distribution—打包发行：第 2 期下载的 zip 就是它产出的
ai / ai-registry-adaptor / k8s-sync / istio生态对接3.x 面向 AI 服务注册与云原生生态的新阵地（呼应第 1 期的版本演进）

2.x 的目录更精简（无 persistence/console 拆分等），主干模块名一致；第 5 期读码以 2.3.x 为纲，届时对差异单独标注。

07随堂小测

每题点击选项立即反馈 · 共 3 题

1. dev 环境的服务想彻底不被 prod 看到，应该用哪层坐标隔离？

  • 给服务名加前缀 dev-
  • 用不同的 Group
  • 用不同的 Namespace

2. MySQL 地址想注册进 Nacos 被服务发现，实例应该建成哪种？

  • 持久实例——探不通要的是标记不健康和告警，不是记录消失
  • 临时实例——跟微服务一样心跳保活
  • 随便，两者没有行为差别

3. Nacos 集群 5 节点挂掉 3 个（不过半），临时实例的注册与发现还能用吗？

  • 完全停摆，必须恢复到多数节点
  • 仍可用——Distro 走 AP，牺牲短暂一致性保注册发现持续服务
  • 能读不能写

08思考题（点击展开解析）

思考一：为什么配置数据宁可"挂掉时拒绝写入"，也不能像临时实例那样各节点先各自记着？

推演一下"分区时两边各记各的账"会发生什么：网络分区把 5 节点切成 2+3，若配置写入不要求多数派，两个分区都能接受发布——同一 DataId 在分区 A 是 v2（改了超时为 5s）、分区 B 是 v3（回滚成 10s）。分区恢复后无论以哪边为准，另一边已经生效过的配置都会被静默覆盖：依赖 5s 的服务可能突然回到 10s，依赖 10s 的可能突然变 5s——而没有人发布过任何东西。配置的威力在于"一条变更瞬间影响所有实例"，所以它的错误也会被同样放大。拒绝写入的代价（分区期间发不了配置）是显性的、可预期的运维事件；静默脑裂的代价是隐性的、事后无法追溯的生产事故。临时实例不怕这个：实例数据的事实源在客户端（心跳），分区两边记录不一致，等心跳一停/一续，错误记录自愈——数据能否自愈，决定了它配得上哪种一致性。

思考二：客户端本地快照（snapshot）让应用在 Nacos 全挂时"以旧值启动"，这个降级有没有代价和边界？

有，而且值得想清楚再用。代价一：读到的是过去——快照可能是上次正常拉取的旧版本，如果这条配置恰恰是"昨晚紧急把支付通道切到备用"的开关，旧值启动等于把故障期间的错误决策又执行了一遍；代价二：静默降级掩盖故障——应用全都"正常"起来了，没有人第一时间知道 Nacos 挂了，等真正的新配置发不下去时才发现，故障窗口被拉长。边界判断因此很清晰：快照兜底适合启动期读不到服务端的可用性兜底（起不来比读旧更糟），而不适合运行期长期脱轨运行——所以成熟用法会配套两件事：快照命中的路径打告警日志（甚至接入监控），以及把"必须新值才安全"的关键配置（如安全开关）在应用侧做版本校验。架构里的每个降级开关都一样：它交换的是可用性与正确性，你必须知道自己在交易什么。

09本期要点与下期预告

带走这四句：

  • 三层坐标 Namespace（硬隔离）→ Group（软分组）→ Service/DataId（叶子），注册与配置共用；
  • 实例分临时/持久，一个布尔值改变"心跳还是探测、消失还是标红、Distro 还是 Raft"；
  • 服务端四层：接入（8848/9848/8080）→ naming/config 核心域 → Distro/Raft 协议层 → Derby/MySQL 持久层；
  • 客户端有自己的容灾三件套：内存服务表、failover 文件、配置快照——Nacos 挂掉的那一刻，它们决定你的系统是"降级活着"还是"全链路瘫痪"。
