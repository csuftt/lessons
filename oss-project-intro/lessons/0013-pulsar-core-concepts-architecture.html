OSS PROJECT INTRO · Pulsar 系列第 3 期：核心概念与整体架构

Pulsar 核心概念与整体架构：一套术语、三层架构与一张模块地图

上一期我们用 standalone 模式跑起了集群，发出并消费了第一条消息。但回头看，那条命令里其实全是问号：persistent://public/default/my-topic 里的 public 和 default 是什么？消息发出去到底存到了哪？为什么官方架构图里 Broker 敢自称"无状态"？这一期把 Pulsar 的户口本翻开：六个核心名词配类比和一句话定义——租户、命名空间、主题、订阅、游标、账本；四大订阅模式从使用视角扫一遍（原理深入有专线课程，文末延伸阅读）；一张自绘三层架构图看懂计算与存储怎么分工，顺带回答两个值得琢磨的问题——Broker 凭什么可以无状态横向扩、Ledger 分卷写入凭什么扛得住单块磁盘故障。最后打开源码仓库，把顶层模块一一对号入座。读完这一期，第 4 期把它接进 Spring Boot 时，每个配置项你都知道自己在配什么。

01上一期的第一条消息，埋着今天的全部问题

第 2 期我们跑通了两条命令：服务端 bin/pulsar standalone 起一个单机集群，客户端发出并收回了第一条消息。命令里那个 my-topic 前面没写任何前缀，消息照样落地——但如果把完整名字写全，它是这样的：

persistent://public/default/my-topic
└─────┬────┘ └──┬──┘ └───┬──┘ └──┬──┘
    持久化类型   租户    命名空间   主题
（省略时默认 persistent） public  default  你起的名字

三个新名词当场出现：租户、命名空间、主题。而消息收走之后，它去哪了？官方架构图把系统画成三层，最上面那层 Broker 明晃晃写着 stateless（无状态）——消息队列的节点居然不存消息？这一期的任务就是把这些问题全部问掉。用户视角的 Pulsar 核心，说穿了就是六个名词：Tenant、Namespace、Topic、Subscription、Cursor、Ledger。后面不管你接 Spring Boot 还是做数据管道，本质都是在用这六块积木。

02六块积木：类比 + 一句话定义 + 关键点

① Tenant 租户——入驻的公司

一句话定义：多租户的最外层隔离单位，官方把 tenant 称为多租户能力的基石。

  • 类比同一座写字楼里的入驻公司：房租（配额）、门禁（权限）按公司算；
  • 建租户要指定管理员角色（--admin-roles）和允许部署的集群（--allowed-clusters），隔离从出生就定死。

② Namespace 命名空间——部门的行政章

一句话定义：租户内的管理单元，一批相关 topic 归它管，官方称之为 administrative grouping unit。

  • 类比公司里的部门：考勤、报销制度是部门级的——保留策略（retention）、TTL、配额都配在 namespace 上，名下 topic 全体生效；
  • 写法就是一条路径：tenant/namespace，如 public/default。

③ Topic 主题——贴了门牌的公告栏

一句话定义：一条从生产者向消费者传消息的命名通道（官方：a named channel for transmitting messages）。

  • URL 式全名：{persistent|non-persistent}://tenant/namespace/topic——persistent 落盘可恢复，non-persistent 只在内存里飞，broker 挂了在途消息就丢，换来的延迟更低；
  • topic 不预创建也能用（自动落进默认租户/命名空间），但生产建议显式建；
  • 还有分区 topic：一个逻辑名背后拆成 N 个内部 topic 分给多个 broker，为的是吞吐。

④ Subscription 订阅——自己的报刊户头

一句话定义：消费者在 topic 上立的"户头"，一条命名规则，决定消息怎么送到消费者手上。

  • 类比订报：同一份报纸（topic），各订各的户头，各收各的全套——三个订阅互不干扰，每个都能把全量消息走一遍；
  • 消费者断线重连，报订阅名字就行，户头还在，消息照补；
  • 四大模式（Exclusive / Failover / Shared / Key_Shared）下一节展开。

⑤ Cursor 游标——户头里的书签

一句话定义：每个订阅一个，记录"这个订阅读到哪条了"的进度标记。

  • 默认是持久游标（durable），书签本体存在 BookKeeper 里——broker 重启、消费者掉线，进度都不丢；
  • 消费者确认（ack）一条消息，本质就是挪动书签；
  • 一条消息要等所有订阅都挪过书签，才真正具备删除资格。

⑥ Ledger 账本——只进不改的分卷

一句话定义：BookKeeper 里的只追加（append-only）数据结构，同一时刻只有一个写入者，封卷后只读。

  • 类比一套按卷归档的账本：一卷写满（或到了时间）就封卷、换新卷继续写——这个动作叫 rollover；
  • 一个 topic 的存储在 Pulsar 里叫 managed ledger：一个写入者往后追加，多个 cursor（订阅）各读各的进度；
  • 封掉的卷还是分层存储的主角：不动就能搬去对象存储省钱——第 5 期细讲。

版本备注以上术语与官方表述已对照 Pulsar 4.2.x 文档 Messaging / Architecture 概念页核对（2026-09-19）。版本基线：当前 GA 稳定线 4.2.4（2026-08-03 发布），4.0 LTS 线并行维护（4.0.13，安全支持到 2027-10）；5.0 尚处里程碑（5.0.0-M2，官方明确不用于生产）。

03四大订阅模式：建消费者时选的那一个参数

对使用者来说，订阅模式就是建消费者时指定的 subscriptionType——一个参数决定"消息怎么分给手里的几个消费者"。从使用视角一句话扫过：

模式使用体感典型场景
Exclusive（默认）一个订阅只许挂一个消费者，第二个直接报错严格单实例消费，如某些配置同步任务
Failover可挂多个，同一时刻只有主消费者收消息，主断了备顶上主备容灾，要保序又要高可用
Shared消息轮流发给各消费者，吞吐好扩，但不保证顺序、不支持累计确认无序批量处理，堆实例提吞吐
Key_Shared也是多消费者，但相同 key 的消息只发给同一个消费者——分 key 保序按业务键（如订单号）保序又要并行

跨线提示四种模式内部的分发算法、游标与 Key_Shared 的哈希保序原理，属于"原理视角"，本系列不换皮重讲——想抠原理直接读 官方文档 · 《Apache Pulsar 订阅模型：四种订阅、游标与 Key_Shared 保序》。本期你只需记住使用层的选型口诀：默认独占要排他，主备 Failover，堆吞吐 Shared，按 key 保序 Key_Shared。

04整体架构：计算与存储分家的三层楼

六块积木拼上三层楼，就是 Pulsar 的全景。读图三句话：Broker 只管计算不存数据，BookKeeper 只管存储不算业务，中间的元数据存储记账。实线是消息流，虚线是元数据流。

三层楼各司其职：Broker 层是无状态计算层——每个 broker 跑一个 REST 管理服务和一个自定义二进制协议的异步 TCP 服务，消息进来先走托管账本缓存（managed ledger cache），攒够条件就写进 BookKeeper；BookKeeper 层是存储层——官方给它一个定位：分布式预写日志（WAL）系统，ledger 是其中只追加的基本单元；元数据存储是总账房——topic 归谁管、schema、集群配置、ledger 元数据都在它那里，Pulsar 4.2 里默认 ZooKeeper，也可换 etcd、RocksDB（standalone 用）或 Oxia。

钩子一：Broker 凭什么敢无状态？

因为两样最重的东西都不在它身上：消息在 BookKeeper，进度（cursor）也在 BookKeeper，broker 名下只剩"归属关系"这种轻量元数据，记在元数据存储里。于是扩容变得极其简单——新加一台 broker 就是多起一个进程，元数据存储里一登记，topic 的 owner 分配就自然摊到新机器上；某台 broker 宕机，它名下 topic 的归属被转移到活着的 broker，新 owner 从 BookKeeper 把 ledger 和 cursor 接过来接着服务。计算层的"状态"被整层搬去了存储层，这就是"无状态"的底气。

钩子二：Ledger 分卷写入怎么抗单盘故障？

一个 ledger 不是写死在一块盘上，而是摊在多台 bookie 组成的集合（ensemble）上：每条消息写 W 份（write quorum），收到 A 份成功确认才算写成功（ack quorum），满足 A ≤ W ≤ 集合大小 E——官方文档默认数据存 3 份。更妙的是故障处理方式：某台 bookie 坏了，不修复坏卷，直接封卷换新卷——新消息滚动（rollover）到健康 bookie 上开的新 ledger，坏卷里已写的部分只要凑得够读就行。旧账不翻新账接着记，写入路径永远不打断。

分层存储一笔带过封卷后的 ledger 不可变，所以还能整体搬到对象存储（S3 等）给热数据腾地方，读的时候对消费者透明——这套"冷热分离"的设计决策是第 5 期源码导读的主角之一。与 Kafka 存算一体的架构对比，同样属于原理视角，可见 官方文档 · 《Pulsar 存算分离架构与 Kafka 对比》。

05打开仓库：顶层模块地图

概念清楚了，再看源码仓库就不慌。以 GitHub 上 apache/pulsar 主分支（对应 4.2 线开发中，2026-09-19 核对）的实际目录为准，常用模块一句话：

顶层模块一句话职责
pulsar-broker/Broker 主体：topic 加载、消息分发、订阅管理——计算层的核心入口
managed-ledger/存储抽象层：把 BookKeeper 的 ledger 包成"一写多读带游标"的托管账本，cursor 实现也在这
pulsar-metadata/元数据抽象层：一套接口屏蔽 ZooKeeper / etcd / RocksDB / Oxia 差异
pulsar-common/客户端与 broker 共用：二进制协议定义、公共数据结构与工具
pulsar-client-api/ + pulsar-client/Java 客户端的接口定义与实现（Producer / Consumer / Reader）
pulsar-client-admin/ + pulsar-client-tools/管理 REST 客户端与命令行工具——pulsar-admin 命令的真身
pulsar-proxy/可选网关：客户端统一入口，转发给背后的 broker
pulsar-functions/ + pulsar-io/轻量计算框架（Functions）与外部系统连接器（IO Connectors）
pulsar-transaction/事务支持：跨 topic / 消费确认的原子性
tiered-storage/分层存储 offloader 实现：S3、GCS、文件系统等冷存后端
bin/ + conf/启动脚本与配置文件——第 2 期敲的命令都从这来
tests/集成测试套件，读码时是最好的"用法示例库"

读码提示三个模块记优先级：pulsar-broker 是计算层入口，managed-ledger 是 Broker 与 BookKeeper 之间的"翻译官"，pulsar-metadata 是屏蔽各家元数据存储的适配层——第 5 期读源码就从这三个进门。

06随堂小测

每题点击选项立即反馈 · 共 4 题

1. persistent://public/default/my-topic 中，public 和 default 分别是？

  • 命名空间在前，租户在后
  • 租户 public，其下命名空间 default
  • public 是集群名，default 是分区数

2. 消息什么时候才真正具备被删除的资格？

  • 任意一个订阅确认后即删除
  • 生产者发完即删除
  • 所有订阅都确认之后

3. Broker 被称为无状态，是因为哪两样最重的东西都不在它身上？

  • 消息在 BookKeeper，进度（cursor）也在 BookKeeper
  • 消息在内存缓存，配置在本地文件
  • 数据在元数据存储，连接在代理层

4. 某台 bookie 的磁盘坏了，Pulsar 的处理方式是？

  • 停写并修复坏盘上的 ledger
  • 封卷换新卷，新消息写入健康 bookie
  • 该 topic 数据全部迁到客户端重放

07思考题（点击展开解析）

思考一：既然消息和 cursor 都在 BookKeeper，那 Broker 到底"计算"了什么？它是不是可有可无？

反过来看就明白了：BookKeeper 只是个"老实记账"的分布式日志系统，它不懂业务——不知道什么是 topic、subscription、优先级、重试策略。这些"懂业务"的活全在 Broker：服务发现与归属仲裁（客户端连上来，先查元数据存储把 topic 定位到 owner broker，同一条消息不会有两个 broker 同时服务）；分发调度（四种订阅模式的分发逻辑、消息优先级、背压与流控都在 broker 的 dispatcher 里）；缓存加速（刚写入的消息先待在 managed ledger cache 里，消费者多半能直接从缓存拿走，命中不了才去摸 bookie——官方文档原话：消息一般从缓存服务，除非积压超过缓存）；生命周期管理（什么时候开新卷、封旧卷、把冷卷卸载到对象存储，决策都由 broker 做出）。所以 Broker 不是可有可无，而是把"智能"与"存储"解耦了：BookKeeper 提供的是不带业务语义的可靠追加日志，Broker 在上面长出整套消息语义。这套分工的代价是多一层网络跳转与组件复杂度（运维要同时养 broker、bookie、元数据存储三种角色），收益是两侧各自独立扩缩——理解了这层取舍，"无状态"三个字才算真懂。

思考二：Ledger"封卷换新"而不是"原地修复"，到底换来了什么？换种做法会怎样？

先看"原地修复"这个反事实方案：ledger 要支持就地改写，存储就得处理"半新半旧"的页、修复期间的并发读写锁、以及"修到一半又坏"的递归难题——整个写入路径从纯顺序追加退化为随机读写，日志型存储最值钱的顺序写优势就没了。再看"封卷换新"这套不可变（immutable）设计的收益清单：写入永远顺序追加（journal 和 entry log 都是顺序写盘，这是吞吐的根基）；封卷即定稿，副本之间不存在"谁是对的"的长期分歧，故障恢复只需读够法定数量（ack quorum）的副本即可定案；删除变得干净——所有订阅的 cursor 越过整卷后，直接删文件即可，不用逐条清理；分层存储成了顺手的副产品——正因为卷不可变，才能整体搬去对象存储而不怕中途变更。代价也得认：卷的粒度在"故障切换"时略粗（坏一台 bookie，其上未封的卷要作废滚动，浪费一点写入），以及读路径多了一层"这卷在哪本 bookie"的元数据查找。Pulsar 把 ledger 做成不可变分卷，本质和 Netty 里 ByteBuf 不可变切片、Kafka 里 segment 不可变是同一家思想：用"不许改"换"简单与快"，把变更转化为追加新数据。在你自己的系统里，凡是"日志、流水、事件"类数据，都值得先想想能不能套这个模式。

08本期要点与下期预告

带走这几句：

  • 路径即身份：persistent://tenant/namespace/topic——租户是公司，命名空间是部门，topic 是贴了门牌的公告栏；
  • 订阅是户头，游标是书签：一份消息各订阅各收全套，一条消息等所有订阅都确认才有删除资格；
  • 三层分工：Broker 管计算（归属、分发、缓存），BookKeeper 管存储（ledger 只追加、默认 3 副本），元数据存储记总账；
  • 无状态的底气：最重的消息与 cursor 都在存储层，broker 只剩归属元数据——扩容即起进程，故障即转移；
  • 抗故障靠换卷：ledger 摊在 bookie 集合上（A ≤ W ≤ E），坏盘不修卷、封卷开新卷。
