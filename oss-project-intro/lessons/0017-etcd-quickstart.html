OSS PROJECT INTRO · ETCD 系列第 2 期：5 分钟跑起来

5 分钟跑起来 etcd：两个二进制、五条命令，亲手完成第一次读写

上一期我们认识了 etcd 的定位：API Server 是门面，etcd 是心脏——K8s 全部集群数据的后备存储。这一期把心脏请到自己机器上，官方快速上手页的第一句话就是承诺："Get etcd up and running in less than 5 minutes!"。下载官方二进制，一条命令起一个单成员集群，亲手写入第一个键、读回它、订阅一次变更推送，最后用官方口径判定跑通。全文基于 3.7.x（v3.7.1，2026-07-23 发布，2026-09-19 于 GitHub Releases 与官方文档复核），命令与预期输出逐字对照官方文档，Docker 方式与高频报错一并给全，跑不通先对号入座再怀疑人生。

🧩 分布式键值存储 · Go · Apache-2.0 📦 基于 etcd 3.7.x（3.7.1） 📅 2026-09-19 · 第 2 期 ⏱ 预计阅读 15 分钟

01本期路线与跑通判定

四步路线：装好 → 起服务 → 第一次读写 → 订阅与判定。全部走完，满足三条判定才算跑通：

  • ① 服务起来了：启动终端持续滚动日志（官方 Note：info 级日志可直接忽略），进程不退、光标停在日志末尾——是长活服务的正常形态，不是卡死；
  • ② 写得进、读得出：put 回显 OK，get 固定两行——键名一行、值一行，与官方 quickstart 印的一字不差；
  • ③ 健康检查通过：etcdctl endpoint health 回显 is healthy: successfully committed proposal——健康＝能提交提案，不是端口应答（官方 etcdctl 文档口径）。

这条路线起的是官方 quickstart 原话里的 single-member cluster（单成员集群）。上一期讲的"多数派写入"，在单机版里由它自己给自己点头——学习够用，生产的差别在思考题一里展开。

02环境要求：平台分三层，磁盘比 CPU 金贵

etcd 的"支持平台"不是一句"跨平台"就完事，官方 v3.7 支持平台页把平台分成三档，档位决定你能理直气壮到什么程度：

架构操作系统支持层官方口径
AMD64 / ARM64LinuxTier 1全部测试通过，维护者完全支持
AMD64 / ARM64Darwin（macOS）Tier 3只保证能编译，测试很少甚至没有，"should be considered unstable"（官方原话）
AMD64WindowsTier 3

翻译一下：Linux 是主场；macOS 能跑但别较真；Windows 只在第三层——官方没有给"Windows 走 Docker"的明文指引，稳妥做法就是第 09 节的容器方式，容器里跑的是 Tier 1 的 Linux 镜像。

硬件方面，单机学习毫无门槛（官方硬件建议页口径）：典型集群只要 2-4 核、8GB 内存；真正金贵的是磁盘——共识协议要求每个请求持久化落盘，官方给的下限是 50 顺序 IOPS、推荐 SSD。本机起一个单成员集群，任何近十年的电脑都行。

03第一步：安装——官方下载脚本，三个可执行文件

官方安装页的主线方式是预构建二进制（pre-built binaries），要求"choosing release v3.7.0 or later"。官方发布页针对每个版本给了现成下载脚本，v3.7.1 的 Linux 段节选如下（原文见 GitHub Releases v3.7.1 说明）：

ETCD_VER=v3.7.1

# choose either URL（两条下载线二选一：谷歌云存储 / GitHub Releases）
GOOGLE_URL=https://storage.googleapis.com/etcd
GITHUB_URL=https://github.com/etcd-io/etcd/releases/download
DOWNLOAD_URL=${GOOGLE_URL}

rm -f /tmp/etcd-${ETCD_VER}-linux-amd64.tar.gz
rm -rf /tmp/etcd-download-test && mkdir -p /tmp/etcd-download-test
curl -L ${DOWNLOAD_URL}/${ETCD_VER}/etcd-${ETCD_VER}-linux-amd64.tar.gz -o /tmp/etcd-${ETCD_VER}-linux-amd64.tar.gz
tar xzvf /tmp/etcd-${ETCD_VER}-linux-amd64.tar.gz -C /tmp/etcd-download-test --strip-components=1 --no-same-owner
rm -f /tmp/etcd-${ETCD_VER}-linux-amd64.tar.gz

解压出来三个可执行文件：etcd（服务端）、etcdctl（命令行客户端）、etcdutl（运维工具）——本期主角是前两个。按官方安装页，把可执行文件加入 PATH（移到 /usr/local/bin，或把解压目录加进 PATH），然后验证——官方在 quickstart 页用 Important 标出这句话："Ensure that you perform the last step of the installation instructions to verify that etcd is in your path." 最后一步验证别省，PATH 没配好，下一步直接 command not found：

$ etcd --version
etcd Version: 3.7.0
...

输出样例取自官方安装页（样例基于 v3.7.0，装 3.7.1 时首行相应变化，格式一致）。对照方式两条：macOS/Linux 可 brew install etcd——官方明确警告系统包里的版本可能明显过旧，Linux 发行版仓库"强烈不建议"；源码构建要 Go 1.21+ 加 ./scripts/build.sh，门槛最高，入门不必。

04第二步：一条命令，起一个单成员集群

$ etcd

就这一条。终端开始滚动一屏屏 JSON 日志——新手最容易在这里慌，官方 Note 原话："The output produced by etcd are logs — info-level logs can be ignored." 这些输出就是日志，info 级直接忽略，不必逐行研究。服务起来后长这样：

两个端口各管一头：2379 给客户端进出（etcdctl 和各语言客户端连的就是它），2380 给集群成员之间说话——单机版暂时用不上，多节点时它就是 Raft 同步的通道。服务形态：前台进程、不退出、光标停在日志末尾。想让它在后台待着不是本期话题，实验阶段前台跑最直观。

05第三步：第一次读写（官方 quickstart 原文）

再开一个新终端——让起服务的那个继续滚日志。官方 quickstart 第三、四步原文，可逐字对照：

$ etcdctl put greeting "Hello, etcd"
OK

$ etcdctl get greeting
greeting
Hello, etcd

两个细节值得嚼。其一，写入即存在：put 成功就回一个词 OK，不需要提前"建键"——对比上一门消息队列课还得先建 Topic，键值模型把仪式感全省了。其二，回显固定两行：get 的输出第一行键名、第二行值，后面所有读命令都保持这个两行式。几个顺手的小开关（出自官方交互文档）：--print-value-only 只取值；--prefix 按前缀批量读；--hex 十六进制展示。

06第四步：watch，亲眼看一次变更推送

两个终端配合：终端 A 先订阅，终端 B 再写入。命令与回显出自官方交互文档：

# 终端 A：订阅后挂起等待
$ etcdctl watch foo

# 终端 B：写入触发变更
$ etcdctl put foo bar

# 终端 A 在写入的瞬间自己打印：
PUT
foo
bar

没有谁去轮询，变更主动送上门——上一期说的"变更即事件"，配置下发从"推文件再重启"变成"订阅即生效"，就是这一幕的实物。watch 还支持前缀订阅：etcdctl watch --prefix foo，一条订阅盯住一组键，这是配置目录同步的用法雏形。

07顺手一把：lease，会自灭的临时键

官方交互文档的 lease 样例走一遍（编号每次随机，你敲出来会是另一串数字，别慌）：

# 申请一个 60 秒的租约
$ etcdctl lease grant 60
lease 32695410dcc0ca06 granted with TTL(60s)

# 把键挂到租约上
$ etcdctl put --lease=32695410dcc0ca06 foo bar
OK

# 主动撤销租约
$ etcdctl lease revoke 32695410dcc0ca06
lease 32695410dcc0ca06 revoked

$ etcdctl get foo
# empty response since foo is deleted due to lease revocation（官方原注）

租约就是给一批键装的 TTL 倒计时：到期或主动撤销，挂在上面的键全部自动清掉，再读就是空。节点存活检测、临时注册，都长在这套机制上——上一期说"存活检测是内建的"，这就是实物。除了 revoke，还有 lease keep-alive 持续续期：客户端活着就续，掉线了租约到期、键自动消失。

08跑通判定：endpoint health

$ etcdctl endpoint health
127.0.0.1:2379 is healthy: successfully committed proposal: took = 2.095242ms

回显逐段读：健康、成功提交了一条提案、耗时两毫秒上下（输出取自官方 etcdctl 文档）。官方对"不健康"的定义是"cannot participate in consensus with the rest of the cluster"——无法参与共识。所以这条命令的实质是往集群里提交一条探测提案、走完整个共识与落盘流程，比"端口能连上"严格得多：端口在、共识瘫痪的实例照样存在，但提案过不去。三条判定到这里全部验收，五分钟目标达成。

09Docker 方式对照：Windows 用户的稳妥路径

官方安装页给了完整的容器命令（主仓库 gcr.io，样例 tag 为 v3.7.0，想用 3.7.1 换标签即可；Windows 下把行尾 \ 换成 ^）：

ETCD_VER=v3.7.0

rm -rf /tmp/etcd-data.tmp && mkdir -p /tmp/etcd-data.tmp && \
docker run \
  -p 2379:2379 \
  -p 2380:2380 \
  --mount type=bind,source=/tmp/etcd-data.tmp,destination=/etcd-data \
  --name etcd-gcr-${ETCD_VER} \
  gcr.io/etcd-development/etcd:${ETCD_VER} \
  /usr/local/bin/etcd \
  --name s1 \
  --data-dir /etcd-data \
  --listen-client-urls http://0.0.0.0:2379 \
  --advertise-client-urls http://0.0.0.0:2379 \
  --listen-peer-urls http://0.0.0.0:2380 \
  --initial-advertise-peer-urls http://0.0.0.0:2380 \
  --initial-cluster s1=http://0.0.0.0:2380 \
  --initial-cluster-token tkn \
  --initial-cluster-state new \
  --log-level info \
  --logger zap \
  --log-outputs stderr

逐段拆：两个 -p 把客户端口与成员口映射到宿主机；--mount 把数据目录挂出容器，删容器不丢数据；后面一串参数把单成员集群的监听地址、广播地址、初始集群写死——容器里不写广播地址，宿主机客户端第一步寻址就碰壁，这和 Pulsar 的 --advertised-address 是同一个道理。验证用官方安装页原样的清单（容器内外同一套 CLI，回显与第 05-08 节一致）：

docker exec etcd-gcr-${ETCD_VER} /usr/local/bin/etcd --version
docker exec etcd-gcr-${ETCD_VER} /usr/local/bin/etcdctl version
docker exec etcd-gcr-${ETCD_VER} /usr/local/bin/etcdctl endpoint health
docker exec etcd-gcr-${ETCD_VER} /usr/local/bin/etcdctl put foo bar
docker exec etcd-gcr-${ETCD_VER} /usr/local/bin/etcdctl get foo

10高频报错速查：现象 → 原因 → 解法

现象原因解法
command not found PATH 没配好——正是官方 quickstart 用 Important 强调的"最后一步验证别省" 回官方安装页第 3 步：把 etcd / etcdctl 所在目录加入 PATH，再跑 etcd --version 验证
etcdctl 报连接被拒（connection refused） 服务端没起，或还没就绪就开始敲客户端命令 回启动终端确认 etcd 进程还在滚日志；确认 2379 已监听后再开客户端终端
API 版本对不上 / 老脚本行为怪异 ETCDCTL_API 版本坑：v3.4 起默认 v3 接口，更老的客户端要 export ETCDCTL_API=3；且 v2 接口建的键 v3 接口查不到（官方交互文档原注） 统一走 v3：显式设 ETCDCTL_API=3，别混用两代接口的键
brew install etcd 装出来的版本很旧 系统包里的版本可能明显过旧（官方安装页警告），Linux 发行版仓库"强烈不建议" 改用第 03 节官方二进制；装完 etcd --version 核对版本号
服务端启动失败、日志报端口相关错误 2379 或 2380 被其他进程占用 看启动日志定位端口，停掉占用进程或改监听端口（客户端命令需同步 --endpoints）
本机跑得好好的，换台机器远程连不上 跨机访问牵扯防火墙与广播地址，不只端口问题 先确认防火墙放行 2379；远程部署还涉及 advertise 地址配置，属多节点部署话题，第 3 期后再回头看

11随堂小测

每题点击选项立即反馈 · 共 4 题

1. 启动 etcd 后终端滚个不停的日志，官方建议怎么对待？

  • 逐行读懂才算启动成功
  • 必须重定向到文件，否则会丢
  • 它们就是日志，info 级可直接忽略

2. etcdctl get greeting 的回显是？

  • 一行：Hello, etcd
  • 两行：键名 greeting，值 Hello, etcd
  • 一个词：OK

3. endpoint health 回显"successfully committed proposal"，这个判定为什么比"端口能连上"严格？

  • 它真实提交了一条提案，走完共识与落盘流程
  • 它额外校验了 TLS 证书链
  • 它只是 ICMP 探测的另一种写法，实质一样

4. 关于 ETCDCTL_API 版本坑，哪个说法符合官方文档？

  • 任何版本都必须显式 export ETCDCTL_API=3
  • v2 与 v3 接口的键互相可见
  • v3.4 起默认 v3；v2 建的键 v3 查不到

12思考题（点击展开解析）

思考一：单成员集群里"多数派"怎么成立？它和生产三节点集群的差距，只是少了两台机器吗？

多数派的定义是"超过半数确认"，单成员集群的半数就是它自己——1/1 也是多数派，所以上一期讲的共识流程并没有缺席，只是投票人只剩一个：写入确认从"等过半节点点头"退化成"自己点头"，延迟自然小，但这恰恰意味着共识协议的容错红利在这个形态里是零。生产三节点集群容忍 1 台故障（2/3 仍构成多数派）、五节点容忍 2 台；单成员任何故障都直接不可用，只剩磁盘上那份数据可救。第二个差距在见证者：多数派的价值是"任何决定至少过半的人知道"，单机版没有第二个见证者，磁盘一坏，"当时到底写没写"就死无对证——这也是官方文档反复强调备份的原因。所以正确的理解是：单成员集群是共识机制的"教学沙盘"，协议还在、容错不在；第 3 期讲 Raft 与一条写请求的旅程时，会看到同一个协议在多节点上怎样靠心跳、选举与日志复制活起来。

思考二：为什么官方把"能提交提案"当健康标准，而不是"端口能连上"？顺着这个口径，生产上该盯哪些信号？

先看两种判定的差别。端口探测只证明进程活着、网络可达；而 etcd 的价值承诺是"每次写入过多数派、任何读取拿到最新值"，这份承诺的兑现路径是提案 → 共识确认 → 落盘 → 状态机生效，任何一环卡住，端口照样亮着，但集群已经不健康——磁盘写延迟飙升让心跳超时、网络分区让成员掉出多数派、文件句柄耗尽让写入失败，都是"端口在、共识瘫"的典型形态。官方 etcdctl 文档对不健康的定义正是"cannot participate in consensus"（无法参与共识），endpoint health 用一条真实探测提案把这整条路径走一遍，能走通才算数。顺着这个口径，生产监控该盯的就不是"进程在不在"：写延迟分位数（落盘耗时）、提议提交速率、选举次数、成员是否掉出多数派——这几个信号共同回答一个问题：这个心脏还在不在正常泵血。这也是为什么第 02 节说磁盘是 etcd 最金贵的硬件：共识协议对写延迟极其敏感，磁盘一慢，最先死的就是提案这条路。

13本期要点与下期预告

带走这四条：

  • 平台分三层：Linux 是 Tier 1 主场，macOS/Windows 是 Tier 3——Windows 稳妥走 Docker 方式跑 Tier 1 镜像；硬件下限极低，磁盘（50 顺序 IOPS 起、推荐 SSD）比 CPU 金贵；
  • 安装三选一：官方二进制为主线（v3.7.0+，两个主角 etcd / etcdctl），Docker 对照给全，系统包防旧；PATH 验证这步官方用 Important 标出，别省；
  • 五条命令第一天地板：put 回 OK（写入即存在）、get 两行回显（键名+值）、watch 瞬间推送、lease 让键自灭、endpoint health 判定跑通——全部出自官方文档原样；
  • 跑通判定＝健康检查通过：健康＝能提交提案、参与共识，不是端口应答；ETCDCTL_API 版本坑与连接被拒先查速查表。
