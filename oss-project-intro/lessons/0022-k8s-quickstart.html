OSS PROJECT INTRO · KUBERNETES 系列第 2 期：5 分钟跑起来

5 分钟跑起来 Kubernetes：minikube 起本地集群，亲手部署第一个工作负载

上一期立住了心智模型：你只声明期望状态，一群控制器负责把现实拉到那里。这一期把这句话变成实物——官方 hello-minikube 教程全程走一遍：minikube 一条命令起一个本地单节点集群，kubectl 部署第一个 Deployment、暴露成 Service、在浏览器里亲眼看到应用响应。全文基于 v1.37.x（1.37.0，2026-08-26 发布，GitHub Latest；minikube 官方命令参考中 --kubernetes-version 的 stable 口径同为 v1.37.0，2026-09-19 复核），命令与预期输出逐字对照 kubernetes.io 官方教程与 minikube 官方文档，本地方案选型与高频报错一并给全，跑不通先对号入座再怀疑人生。

🧩 容器编排平台 · Go · Apache-2.0 📦 基于 v1.37.x（1.37.0） 📅 2026-09-19 · 第 2 期 ⏱ 预计阅读 15 分钟

01本期路线与跑通判定

五步路线：装工具 → 起集群 → 判就绪 → 部署 → 暴露访问。全部走完，三条判定都满足才算跑通：

  • ① 集群起来了：minikube status 回显 host / kubelet / apiserver 三行 Running、kubeconfig Configured（官方教程原样输出）；
  • ② 工作负载真跑起来了：kubectl get pods 看到 hello-node 的 Pod 状态 1/1 Running；
  • ③ 浏览器访问成功：minikube service hello-node 自动开浏览器并显示应用响应（官方教程原话："opens up a browser window that serves your app"）。

这条路线用的 minikube 是官方"学习环境"主推工具——kubernetes.io 的入门教程 hello-minikube 就是围着它写的。上一期说"声明式 API + 控制器模式"，本期你会亲眼看到一次：提交一个 Deployment 声明，Pod 自己出现。

02本地集群方案选型：三条路，本期跟官方教程走 minikube

官方 Install Tools 页把"本机跑 K8s"指向两个工具：kind（"requires that you have either Docker or Podman installed"）和 minikube（"runs an all-in-one or a multi-node local Kubernetes cluster on your personal computer…so that you can try out Kubernetes, or for daily development work"）。加上 Docker Desktop 内置的 K8s 开关，常见三条路：

方案定位依赖适合谁
minikube官方学习环境主推；官方教程的配套工具；addon 生态（dashboard、metrics-server 一键开）容器或虚拟机管理器（Docker / Hyper-V / KVM 等）跟官方教程入门、本地开发，本期主线
kind"Kubernetes in Docker"，官方同页推荐，起停快Docker 或 PodmanCI 流水线、自动化测试
Docker Desktop桌面端内置 K8s 开关（设置里一键启用，非官方文档学习环境推荐项）Docker Desktop 本体已装 Docker Desktop、只想"顺手能用"

本期选 minikube，理由很朴素：要跟的官方教程就是 minikube 教程，命令能逐字对照。前置要求出自 minikube 官方 start 文档：2 核以上 CPU、2GB 空闲内存、20GB 磁盘、网络连接、一个容器或虚拟机管理器——近五年的电脑基本都达标。驱动方面官方 drivers 页按平台标了 preferred：Windows 是 Hyper-V 与 Docker，macOS 是 Docker 与 VFkit，Linux 是 Docker 与 KVM2；启动时用 --driver 可以显式指定。

03第一步：装 minikube 与 kubectl（两条命令的事）

安装命令出自 minikube 官方 start 文档，按平台三选一：

# Windows（官方文档另有 choco install minikube 等价方式）
winget install Kubernetes.minikube

# macOS
brew install minikube

# Linux（官方文档原文命令）
curl -LO https://github.com/kubernetes/minikube/releases/latest/download/minikube-linux-amd64
sudo install minikube-linux-amd64 /usr/local/bin/minikube && rm minikube-linux-amd64

kubectl 有两种姿势。其一独立安装（官方 Install Tools 页按操作系统给安装器）；其二先不装——minikube 官方 start 文档给了免装用法 minikube kubectl -- get po -A，并建议设别名 alias kubectl="minikube kubectl --"。学习期推荐后者，少装一样东西。装完验证：

$ minikube version
minikube version: v1.39.0
commit: ...

版本号随安装时点变化：2026-09-19 官方 Latest 为 v1.39.0（2026-09-02 发布）。首行格式如上，commit 哈希随版本而异。kubectl 验证用 kubectl version --client。

04第二步：一条命令，起一个单节点集群

$ minikube start

官方要求在具备管理员权限（但非 root）的终端里运行。接下来一两分钟，终端会滚动一段进度输出，关键几行（节选；文本随驱动与系统而异）：

* Automatically selected the docker driver
* Creating docker container (CPUs=2, Memory=4000MB) ...
* Preparing Kubernetes v1.37.0 on Docker ...
* Verifying Kubernetes components...
* Enabled addons: default-storageclass, storage-provisioner
* Done! kubectl is now configured to use "minikube" cluster and "default" namespace by default

逐行读：先选驱动（官方 start 页：可用驱动取决于操作系统，--driver 可显式指定）；再建容器/虚拟机、准备 Kubernetes——注意 "Preparing Kubernetes v1.37.0" 这行：minikube 官方命令参考里 --kubernetes-version 的说明原文是 "'stable' for v1.37.0"，也就是默认 stable 正是本系列基准版本，不需要额外指定；最后 Done! 那一行是本步的完成标志——kubectl 已自动配置好，能直接对集群说话。

官方教程对这份集群的定义只有一句："The command minikube start creates a single-Node cluster. That Node acts as both the control plane and a worker Node."——单节点，既是控制平面又是工作节点。上一期画的"控制平面 + 工作节点"分工，在这里浓缩进一台机器：教学沙盘，不是生产形态，这个差距值得在思考题里想想。两个常用可选项一并记住：多实例用 -p 起 profile（官方描述"allow having multiple instances of minikube independently"）；国内网络环境拉镜像慢，官方命令参考给了 --image-mirror-country=cn。

05第三步：就绪判定——status、get nodes、cluster-info

官方 hello-minikube 教程的判定命令是 minikube status，预期输出原样：

$ minikube status
minikube
type: Control Plane
host: Running
kubelet: Running
apiserver: Running
kubeconfig: Configured

五行读三层：机器层 host 在跑，节点层 kubelet 在跑，控制面层 apiserver 在跑，最后 kubeconfig 已配置——kubectl 与集群的"通信录"就位。再看一眼节点清单：

$ kubectl get nodes
NAME       STATUS   ROLES           AGE   VERSION
minikube   Ready    control-plane   45s   v1.37.0

五列表格：名字叫 minikube、状态 Ready、角色 control-plane；AGE 与 VERSION 随环境而变（STATUS 为 Ready 即就绪判定通过）。官方 kubectl 安装文档还给了第三个口径：kubectl cluster-info——"If you see a URL response, kubectl is correctly configured to access your cluster"，看到 URL 就说明 kubectl 配置正确。顺带认识 kubeconfig：官方文档原话，minikube 集群部署成功时会自动生成 kubeconfig 文件，默认在 ~/.kube/config——kubectl 就是靠它找到集群的，这也是第 07 节"上下文切换"报错的根源。

06第四步：第一个工作负载——部署、暴露、访问

主菜来了。官方教程的部署命令逐字照录（一个带 Web 服务器的测试镜像，容器内监听 8080）：

# Run a test container image that includes a webserver
$ kubectl create deployment hello-node --image=registry.k8s.io/e2e-test-images/agnhost:2.53 -- /agnhost netexec --http-port=8080

$ kubectl get deployments
NAME         READY   UP-TO-DATE   AVAILABLE   AGE
hello-node   1/1     1            1           1m

$ kubectl get pods
NAME                          READY   STATUS    RESTARTS   AGE
hello-node-5f76cf6ccf-br9b5   1/1     Running   0          1m

注意，我们没写一行 YAML——kubectl create deployment 帮你生成了一份"要 1 个副本"的声明提交上去，谁来执行？正是上一期的控制器模式：

集群里发生了什么：Deployment 控制器发现"声明要 1 个副本、现实 0 个"，于是创建 ReplicaSet，ReplicaSet 拉起 Pod——get pods 里那个 hello-node-5f76cf6ccf-br9b5 就是产物（后缀哈希每次不同）。看看它自己的日志，官方教程原样输出：

$ kubectl logs hello-node-5f76cf6ccf-br9b5
I0911 09:19:26.677397       1 log.go:195] Started HTTP server on port 8080
I0911 09:19:26.677586       1 log.go:195] Started UDP server on port 8081

服务在容器里跑着，但官方教程说得很清楚：默认 Pod 只能被集群内部网络访问，要从外面访问，得把它暴露成 Service：

$ kubectl expose deployment hello-node --type=LoadBalancer --port=8080

$ kubectl get services
NAME         TYPE           CLUSTER-IP      EXTERNAL-IP   PORT(S)          AGE
hello-node   LoadBalancer   10.108.144.78   <pending>     8080:30369/TCP   21s
kubernetes   ClusterIP      10.96.0.1       <none>        443/TCP          23m

反直觉的一幕：EXTERNAL-IP 是 <pending>——不是坏了。官方原话：在支持负载均衡器的云厂商上，这里会被分配一个外部 IP；在 minikube 上，LoadBalancer 类型通过 minikube service 命令访问。本地没有云厂商的负载均衡器，这个 IP 永远 pending，minikube 用自己的方式把端口 30369 接到你的浏览器：

$ minikube service hello-node

浏览器自动打开、页面显示应用的响应——三条跑通判定全部达成。这里插一句官方警告（原话）："The agnhost container has a /shell endpoint, which is useful for debugging, but dangerous to expose to the public internet. Do not run this on an internet-facing cluster, or a production cluster."——这个测试镜像带调试后门，只在本地玩，别暴露到公网。另外官方教程开头还有一个加分项：minikube dashboard 一条命令打开官方 Web 界面，能在页面上创建 Deployment 和 Service——底层就是 minikube 的 addon 机制，起一个临时代理把默认只在内网可达的 dashboard 映射出来。收尾清理也是两条：kubectl delete service hello-node、kubectl delete deployment hello-node，集群本身 minikube stop 即可——官方提醒：还想继续学就不用 delete。

07高频报错速查：现象 → 原因 → 解法

现象原因解法
minikube start 启动即失败，报驱动相关错误 容器/虚拟机管理器没装或没启动——前置要求里那项"容器或虚拟机管理器"缺了 按官方 drivers 页对号安装（Windows 优先 Hyper-V 或 Docker），或 --driver 换一个已有的
start 卡在下载镜像、超时重试 首次启动要下载容器镜像与二进制，网络慢是第一高频翻车 先重试；国内网络环境按官方命令参考加 --image-mirror-country=cn；反复失败 minikube delete 后重来
kubectl 连不上或操作了别的集群 本机有多套 kubeconfig 上下文，当前 context 不是 minikube kubectl config get-contexts 查看，kubectl config use-context minikube 切换，kubectl cluster-info 验证
Pod 一直起不来，状态 ImagePullBackOff 应用镜像拉取失败——镜像名拼错或网络不通（镜像在 registry.k8s.io） kubectl describe pod 看 Events 定位；网络问题多为等待重试后自愈
start 中途失败，提示内存/磁盘不足 前置要求未满足：2GB 空闲内存、20GB 磁盘、2 核 CPU 关掉吃内存的应用再试，或 --memory 显式分配（官方格式 <number>[<unit>]，单位 b/k/m/g）
想彻底重来 实验环境堆了一堆试验品 minikube delete 连集群一起删，minikube start 全新开始——本地沙盘，重来零成本

08随堂小测

每题点击选项立即反馈 · 共 4 题

1. minikube start 起的集群，官方教程怎么描述它的形态？

  • 一个多节点高可用集群
  • 单节点集群，该节点既是控制平面又是工作节点
  • 只有控制平面、没有工作节点

2. kubectl get services 里 hello-node 的 EXTERNAL-IP 显示 <pending>，官方的解释是？

  • Service 创建失败，需要删了重建
  • 再等几分钟就会自动分配
  • 云上会分配外部 IP；minikube 上改用 minikube service 命令访问

3. 为什么 kubectl 不装独立客户端也能用？

  • minikube 自带 kubectl，可用 minikube kubectl -- 调用
  • kubectl 只是文档里的示例命令，实际不存在
  • kubectl 会自动安装进容器里运行

4. 部署后 kubectl get pods 看到 ImagePullBackOff，第一步该干什么？

  • 立刻 minikube delete 重来
  • kubectl describe pod 看 Events 定位拉取失败原因
  • 删掉 Pod 让它自动重建

09思考题（点击展开解析）

思考一：minikube 单节点"既是控制平面又是工作节点"，与生产集群的控制面/工作面分离相比，你今天学到的哪些东西是通用的，哪些只是本地沙盘的形态？

分两层看。通用的是 API 与对象模型：kubectl 的命令面、Deployment/Service/Pod 的声明方式、控制器对账的行为、kubeconfig 与上下文机制——今天在单节点沙盘上的每一次操作，语法与语义都和生产集群一致，官方文档也不用区分场景，这正是"可移植"承诺的一部分。本地形态特有的至少三处：其一，控制面与负载挤在同一台机器，etcd、apiserver 与业务容器抢 CPU 内存，生产上控制面独立部署、甚至买云厂商托管（你只管工作节点）；其二，LoadBalancer 的 <pending> 是本地没有云负载均衡器的产物，生产云上它会变成真实 IP，流量入口的玩法（Ingress、Gateway API）也更丰富；其三，单节点没有"调度"可言——Pod 永远落在唯一节点上，调度器的两阶段过滤打分（第 5 期展开）在这里是空转。所以正确的学习姿势：把沙盘当语法练习场，别把沙盘当生产缩影——形态差异清单留着，上生产时逐条对账。

思考二：本期只用一条 kubectl create deployment 命令、没写 YAML，K8s 就把 Pod 拉起来了。那"写 YAML 文件再 kubectl apply"多出来的那一步，到底多在哪里？

两种方式提交的东西是同类的——都是一份期望状态。差别在声明存在于哪里：create 命令把声明"说"给集群听，说过就散了，除了你的命令历史，集群外没有任何记录；apply 把声明固化成文件，文件进版本库、过评审、可回滚、可复制到另一个集群——上一期说的"状态是数据，不是记忆"，在生产语境下就是"状态是文件，进 Git"。四个具体差距：其一可重现——新同事拿着同一份 YAML 在任何集群 apply 出同一个结果，create 的历史做不到；其二可演进——改文件重新 apply，K8s 算出差异只改动必要部分，而 create 是无差别的"再说一遍"；其三可组合——Service、ConfigMap、多个 Deployment 的关系在文件目录里一目了然；其四可审计——谁在什么时候改了什么，Git 记得。所以官方教程用 create 帮你迈第一步（少学一层文件格式），而第 4 期实战会切到 YAML + apply 的生产姿势——那时你会感谢今天的沙盘已经把对象模型练熟了。
