02设计决策一:标签与数据分家,各自住进最合适的房子

第 2 期建子表时你敲过 CREATE TABLE d1001 USING meters TAGS ('北京.厂区A', 2)——标签只在建表那一刻出现,之后一万次写入都不用再管它。这不是语法糖,是存储层的分家:标签进了 vnode 的元数据,由 meta 模块管理;时序数据进了 tsdb,按列存文件落盘。第 3 期从文档角度说过"标签信息与标签索引都在 vnode 元数据里,用 B+ 树管理",现在补上源码坐标:元数据实现在 source/dnode/vnode/src/meta/(metaTable.c 管表的登记与查询),底下垫的是 source/libs/tdb/——TDengine 自研的 B+ 树存储引擎,事务接口在 tdb.h。

分家的红利第 3 期量过一个:官方样例压缩率 23.98%——数据文件每行只有时间戳和采集列,设备属性一个字节不占,单设备读数缓变,列存压缩吃得更饱。另一个常被忽略:改模板立即生效。超级表加一列,元数据里改一份 schema,一万张子表同时"长出"新列,数据文件一行不用动——schema 与数据解耦,是模板化建模的存储底气。

源码里还有个值得驻足的细节:每条写入落到 vnode 时,vnodeHandleDataWrite(vnodeSvr.c:2432)先用 metaGetInfo 查子表登记信息,核对所属超级表和 schema 版本,对不上直接拒写。标签分家没让写入变松,反而多了一道免费的合法性闸门。建模方法论(标签怎么选、宽表怎么拆)第 3 期已链到每日课程线 0015 期,不换皮重讲。

03设计决策二:vnode 存算一体,一条写入的完整旅程

"存算一体"这词容易被讲玄。对 TDengine 的 vnode 来说它很具体:一个 vnode 独占自己的线程、内存和磁盘路径,这条数据的写入、事务、查询、合并全在同一分片内完成——不把数据搬到别的节点去算。看一条写入的完整旅程,每一步都给函数坐标:

# 一条 INSERT 的 vnode 内旅程(tag ver-3.4.1.6,行号已核对)
taosAdapter/连接器收到写入
 └─ 请求路由到该子表所在的 vnode(第 3 期:mnode 给路由)
     └─ vnodeSvr.c: vnodeProcessWriteMsg(799)        # 写消息入口
         └─ case TDMT_VND_SUBMIT(917)
             └─ vnodeProcessSubmitReq(3207)           # 解码、自动建表
                 └─ vnodeHandleDataWrite(2432)
                     ├─ metaGetInfo(2452)             # 查元数据:表存在?schema 对?
                     └─ tsdbInsertTableData           # tsdbMemTable.c:119
                         └─ 写进内存表(MemTable)     # 此刻数据可查

# 在这之前:预写日志已经落了
syncRaftLog.c: walAppendLog(266)                       # Raft 层先记日志再应用

# 内存攒够后异步提交落盘
vnodeCommit.c: vnodeCommit(322)
 ├─ walPersist(408)                                    # 预写日志落盘持久化
 ├─ tsdbCommitBegin(418) / tsdbCacheCommit(423)
 └─ tsdbCommitCommit(434)                              # 内存表刷成数据文件

两个最值得咀嚼的选择。其一,先日志后应用:写入先进 Raft 层记预写日志,多数派确认后才应用到内存表。顺序换过来行不行?不行——崩溃恢复时,日志是"这条数据到底收没收"的唯一凭证;先应用后记日志,宕机瞬间会出现"用户收到成功、数据却消失"的窗口。其二,内存表是查询路径的一部分:数据进内存表那一刻就可查,持久化异步进行——写入延迟和查询新鲜度不必互相等待,这是时序库高吞吐的关键权衡。

换种做法会怎样拆成"存储节点 + 计算节点"的存算分离,弹性扩缩容和资源隔离更灵活,但每条写入多一跳网络、每笔事务的提交协议跨节点,时序场景"写入永远大于天"的诉求第一个不答应。TDengine 的取舍:查询侧用 qnode 做存算分离(第 3 期提过),写入侧坚守存算一体——两头的便宜各拿一头。

04设计决策三:缓存与降采样,让"读最新"和"读趋势"都不扫盘

时序查询有两副面孔:监控大屏每秒问"电流现在多少"(最新值),报表问"过去 24 小时每 10 分钟均值多少"(降采样)。两副面孔的读压力,TDengine 用两套机制分别卸掉。

第一套:最新值缓存。建库参数 CACHEMODEL(官方取值 none/last_row/last_value/both):last_row 缓存每张子表最近一行,last_value 缓存每列最近的非 NULL 值——正好对上 LAST_ROW 与 LAST 两个函数。实现在 source/dnode/vnode/src/tsdb/tsdbCache.c(四千余行):内存里是 LRU 缓存,底下垫一层持久化键值引擎(RocksDB)——tsdbCachePutToLRU(1410)管内存命中,tsdbCachePutToRocksdb(1388)管持久化,重启后不必重建;tsdbCacheCommit(775)在提交时把脏项刷下去。查询侧入口在 tsdbCacheRead.c:tsdbCacherowsReaderOpen(280)打开缓存读游标,tsdbRetrieveCacheRows(441)按表批量取回最新值,内部调 tsdbCacheGetBatch(tsdbCache.c:2686)。

精髓在更新时机:缓存更新挂在写入路径上(写入流程顺带调 tsdbCacheRowFormatUpdate,tsdbCache.c:1620),不是查询未命中才回填。于是"读最新值"永远不打扰数据文件——写入时多付一次内存写,换来监控大屏类查询的常数时间应答。官方文档也诚实提醒:频繁切换 CACHEMODEL 可能导致 LAST/LAST_ROW 结果短期不准——缓存与数据是最终一致,这是这套设计的代价。

第二套:降采样交给流计算与预聚合。"每 10 分钟一个均值"这类连续聚合,答案是写入时就算好:流计算由 snode 承载(source/dnode/snode/src/snode.c 是入口,3.4 把流处理主体重构成 source/libs/new-stream/),vnode 侧的触发装配在 vnd/vnodeStream.c;另一路是超级表上的 rollup 预聚合(source/dnode/vnode/src/sma/,tsdb 文件族里能看到 tsdbFSet2.c 的 rollup sma 提交记录)。聚合结果随数据一起落地,查询读的是算好的结果,不是现场扫原始数据。两条机制合起来,才是第 1 期"内建缓存、流式计算"的完整含义。

核对说明CACHEMODEL/CACHESIZE 的取值与语义对照官方文档《数据库管理》页(3.4 文档站,2026-09-19 截图留档于本期素材);写入性能调优见每日课程线 0022 期。

06架构师视角:三件能搬回自己系统的事

主数据与事实数据分家存

标签与数据分离,本质是"变化慢的属性"与"疯涨的事实"分开治理。对应到业务系统:订单的收货地址快照跟着订单走(事实),商品的类目树单独一张维表(属性);设备档案与设备读数分表。判断标准一句话:这份数据是"每行都要带"还是"登记一次就够"?登记一次的进主数据,每行都带的进事实表——别让事实表背着主数据的行囊跑长跑,那是存储与压缩率的双输。

写入的"先记账、后干活、攒批落盘"

这条写入链是通用模式:先顺序追加日志(Raft/WAL)拿到持久性与顺序,再应用到内存结构即时可见,攒够批量再整理成有序文件,后台合并压放大。你会在消息队列、LSM 族存储、甚至支付系统的流水表设计里反复见到它。值得抄的还有"应用即生效"的读新鲜度权衡:别等落盘才可查——代价是要把崩溃恢复的凭证做扎实,日志就是那本死账。

读压力要"预付",不要"现结"

最新值缓存与流计算降采样是同一个思想的两面:把读时的计算挪到写时一次性付出。大屏接口、首页聚合、报表看板,凡是"问题反复问、答案变化慢"的读,都值得问一句:能不能在写入路径顺带维护答案?缓存的一致性账也要学 TDengine 的诚实——文档明说切换缓存模式后结果短期可能不准,把语义讲清楚,比装作强一致更让使用者安心。

07随堂小测

每题点击选项立即反馈 · 共 4 题

1. 一条 INSERT 在 vnode 内生效的过程中,预写日志(walAppendLog)是在哪一步落的?

  • 应用进内存表之后、异步提交之前补记
  • Raft 层先记日志,多数派确认后才应用到内存表
  • 内存表提交落盘时才写日志

2. 数据进入内存表(MemTable)后、异步提交完成前,这条数据能被查询到吗?

  • 能,内存表本身就是查询路径的一部分
  • 不能,必须等提交落盘后才可见
  • 不能,要等后台合并完成后才可见

3. last/last_row 缓存(LRU + 持久化键值引擎)的更新时机是?

  • 查询未命中时回填,类似旁路缓存
  • 后台定时任务周期性刷新
  • 挂在写入路径上,写入顺带更新

4. "vnode 存算一体"里"一体"指的是?

  • 内存表和数据文件存在同一个目录里
  • 写入、事务、查询、合并在同一分片内闭环完成
  • 数据落盘前先做一层加密存储

08思考题(点击展开解析)

思考一:如果把写入顺序反过来——先应用到内存表、再异步补记预写日志,省一次同步等待,会出什么问题?展开解析 ▾

表面看省了一次磁盘等待,实际把三样东西全赔进去。其一,持久性失去凭证:内存表是易失的,日志是"这条写入到底发生过没有"的唯一凭证;先应用后记日志,进程在两步之间宕机,用户已收到"写入成功",恢复后数据却凭空消失——对时序库这是不可接受的静默丢数。其二,复制顺序失去依据:vgroup 里多副本靠 Raft 日志的 index 定先后,日志后补意味着各副本可能按不同顺序应用同一批写入,leader 切换后数据分叉,对账成本远高于省下的那几毫秒。其三,提交语义失去锚点:第 3 期讲的"内存攒够后提交"依赖"已应用的写入必然已在日志里"这条不变量,vnodeCommit(322) 才能放心按版本推进;反过来写,提交流程要额外处理"日志缺口",复杂度指数上升。正确的问题不是"能不能省这次等待",而是"这次等待能不能更便宜"——TDengine 的答案是把日志做成顺序追加写(顺序盘是最快的盘),wal_fsync_period 等参数把"等多久"交给使用者定价。顺序换不得,成本可以调。

思考二:你的系统要做一个"每台设备当前状态"的接口,一万台设备、每秒几千条更新,读多写少。照搬 TDengine 的缓存设计,关键要抄哪三点?展开解析 ▾

第一,抄"挂在写入路径上":状态接口读的是"每台设备最新一条",若每次读都去原始表里捞 MAX(ts),等于用全表聚合回答一个常数问题。TDengine 在写入流程里顺带更新缓存(tsdbCacheRowFormatUpdate),读路径永远不回源——你的系统也该在写入口多付一次内存写(按设备 ID 哈希一份当前值),让读变成一次哈希查找。第二,抄两级结构:纯内存缓存重启即空,冷启动全量回源可能打垮库;TDengine 的 LRU 底下垫一层持久化键值引擎(tsdbCachePutToRocksdb),重启后大部分命中来自持久层,不用重建。对应到你:本地缓存 + 一个可持久化的 KV(公司主栈里 Redis 正合适)分层兜底。第三,抄"诚实的一致性语义":TDengine 文档明说切换 CACHEMODEL 后 LAST/LAST_ROW 结果短期可能不准——缓存方案的边界要写进接口文档:你的"当前状态"允许几秒滞后?切换缓存时怎么过渡?把语义钉死,比事后解释"为什么偶尔不一致"体面得多。至于降采样那一半(历史趋势类查询),思路同源:预聚合、定时物化,别让报表去扫流水。
