OSS PROJECT INTRO · TDENGINE 系列第 1 期：认识项目

TDengine 是什么：为时序数据而生的数据库

开源项目入门系列的每个新项目，都从三个问题开始：它解决什么痛点、凭什么活下来、什么场景该选它。今天开启新项目 TDengine——官方自我定义是"高性能、集群开源、云原生的时序数据库"，最特别的地方不在"又一个数据库"，而在数据模型：一个数据采集点一张表，超级表管一类设备。这条建模思路贯穿全系列，也是它敢把缓存、流式计算、数据订阅内建进内核的底气。公司主栈也在用它，本期带你把它认清楚。

🧩 时序数据库 · C · AGPL-3.0 📦 基于 3.4.1.6（GitHub Latest） 📅 2026-09-19 · 第 1 期 ⏱ 预计阅读 15 分钟

01痛点：设备一多，通用数据库先撑不住

先算一笔账。十万块智能电表，每块每秒上报 1 条读数，一天就是 86.4 亿行——这还只是一个数据源、一种指标。这类数据叫时序数据：按时间追加、只写不改，查询关心的是"最近一小时均值多少""昨晚哪台越限了"这类聚合。塞进 MySQL 这类通用关系库，很快撞上三堵墙：

  • 写入吞吐撑不住：每秒几十上百万条追加写入，走索引加事务的开销路径，磁盘开销花在"维护有序结构"而不是"存数据"，峰值前就先排队；
  • 存储成本扛不住：传感器读数模式高度重复（电压永远在 220 上下抖），通用行存压缩率很低，磁盘增长曲线几个月就打穿预算；
  • 降采样查询等不起：监控最常用的"每 10 秒聚合一次"这类窗口查询，在亿级行里逐行扫描，等查出来告警窗口早过了。

三堵墙的根源是同一句话：通用数据库为"行的事务"设计，时序场景要的是"列的聚合"，硬捏在一起等于用记账本去接消防水管。于是时序数据库（TSDB）品类出现，TDengine 是其中一员——它的差异化打法，下一节讲。

02是什么：一个数据采集点一张表，超级表管一类设备

官方文档的定义值得逐词读："TDengine TSDB 是一款高性能、集群开源、云原生的时序数据库，专为物联网平台、工业互联网、电力、IT 运维等场景设计并优化"，并且"内建缓存、流式计算、数据订阅"等组件（docs.taosdata.com《产品简介》，2026-09 核对）。高性能、云原生各家都在说，真正独特的是数据建模这一层——"一个数据采集点一张表"：

  • 一个数据采集点一张表：每台设备（一块电表、一个传感器）单独建一张子表，结构完全相同，数据按设备分表有序追加——写入变成最朴素的追加写，压缩与查询都顺了；
  • 超级表管一类设备：同类型设备的"模板"叫超级表（STABLE），采集列（电压、电流、相位）写在模板里，设备间差异（厂区、型号、分组）作为静态标签挂在子表上——建子表时引用超级表，标签写死，不随每条数据重复存储；
  • 查询时超级表当一张表用：查询自动下发到所有子表再聚合，还能按标签分组——"各厂区的平均电流"一条 SQL 出结果。这一步同时缓解了时序场景最头疼的高基数（high cardinality）问题。
CREATE STABLE meters (ts TIMESTAMP, current FLOAT, voltage INT, phase FLOAT)
  TAGS (location BINARY(64), groupId INT);
-- 一张子表 = 一个采集点，标签在建表时写死（语法对照官方文档）
CREATE TABLE d1001 USING meters TAGS ('北京.厂区A', 2);

把这张图记住，TDengine 的一半设计就懂了：写路径天然按设备分表追加，读路径始终从超级表出发聚合。官方把它包装成"全栈时序数据处理平台"：缓存、流式计算、数据订阅长在内核里，原本要四件套搭的管道一个项目顶上，这是"极简"卖点的由来。内核用 C 写成、无第三方依赖，第 3 期再拆 vnode 架构。

TDengine 赢在哪？不是"每个指标都最强"——TimescaleDB 的 SQL 兼容更好，InfluxDB 的生态牌子更老。它赢在数据模型与产品形态的匹配度：设备多、类型规整的物联网场景里，"一个数据采集点一张表 + 超级表"把建模、压缩、聚合查询一起解决；缓存、流式计算、数据订阅内建，部署面少一串组件，运维成本是真金白银的差价。代价也要看清：AGPL-3.0 对"改造后对外分发 SaaS"的公司不友好，自用无碍；自研内核意味着 SQL 方言与工具链要跟着它走，通用性不如 PG 系。没有全能冠军，只有场景匹配。

05什么场景该选它（以及什么场景是杀鸡用牛刀）

✅ 适合：

  • 物联网 / 工业数据采集：设备多、上报频繁、指标规整——电表、水气表、网关、车联网，超级表模型正对口；
  • IT 运维监控指标：服务器、中间件的指标采集与告警聚合，写入与降采样都是强项；
  • 想收敛部署面：缓存、流式计算、数据订阅内建，替代"消息队列 + 缓存 + 时序库 + 流计算"一长串管道（公司主栈正看中这层）；
  • 数据只进不改、以时间为轴：追加写 + 聚合读的模式越纯粹，它跑得越快。

❌ 不必：

  • 强事务业务库：订单、账务这类要跨表事务、复杂关联更新的场景，交给 MySQL/PostgreSQL，别硬塞时序库；
  • 单机小量数据：一天几千行的设备日志，SQLite 就够，引入分布式时序库是杀鸡用牛刀；
  • 深度依赖 PG 生态：已有大量 PostgreSQL 工具链与 DBA 积累的团队，TimescaleDB 的迁移成本低得多。

一条判断捷径：先看数据形状——本质是"设备按时间追加、读时按窗口聚合"的量测值，TDengine 进候选；"既要写又要改还要连表事务"，留在通用数据库。建模方法的细节与写读性能调优，官方文档有对应专题，本系列不重复展开：

06随堂小测

每题点击选项立即反馈 · 共 4 题

1. "一个数据采集点一张表"是什么意思？

  • 每个采集指标单独建一张表
  • 每台设备一张子表，同类设备共用超级表模板
  • 所有设备的数据合并进一张大宽表

2. 超级表的"标签列"存的是什么？

  • 随时间变化的量测值，每条数据都带
  • 每条上报数据的附加字段，逐条写入
  • 设备的静态属性，建子表时写死在子表上

3. 关于 TDengine 的许可证与版本，下列说法正确的是？

  • 社区版采用 AGPL-3.0，自用无碍、对外分发需谨慎
  • 采用 Apache-2.0，可以随意闭源商用
  • 集群功能只在企业版提供，社区版没有

4. 按本期的判断捷径，哪个场景最不该选 TDengine？

  • 十万块电表，每秒上报读数，按厂区聚合分析
  • 服务器监控指标采集，每 10 秒出聚合告警
  • 订单系统要跨表事务与复杂关联更新

07思考题（点击展开解析）

思考一：设备几十上百万台，"一个数据采集点一张表"不会把表数量爆炸成灾难吗？MySQL 分表为什么撑不住，TDengine 却撑得住？

直觉的顾虑来自 MySQL 时代的教育：表多了元数据膨胀、文件句柄暴涨、跨表查询要人肉 UNION。但这些痛点的根子不在"表多"本身，而在通用数据库为"少量大表"设计——每张表都是一等公民，元数据全局共享、索引逐表维护。TDengine 敢这么做，靠三件事：其一，子表不是一等公民——它只是超级表模板的实例化，元数据为时序场景专门设计，单节点可管理十万到百万级子表；其二，分而治之是设计目标——子表按设备分布到 vnode，"表多"摊薄成"每节点适度多"，写入并行度随设备数提升；其三，查询从超级表进——聚合下发由内核完成，跨表成本被引擎内部化。反观 MySQL 手工分表：分表键之外的第二维查询全靠人排，结构变更要逐表执行——TDengine 用模板把"结构"收敛成一份、把"数据"摊开成千万份，正好吃定时序场景"结构同构、数据异构"的特点。一句话：表爆炸是不是灾难，取决于引擎为哪种数据形状设计——TDengine 为时序设计，表多反而是主场。

思考二：公司已经用 MySQL 按月分表存了几年的设备数据，现在评估迁到 TDengine，收益与成本各该怎么算？给出你的评估框架。

这种迁移的陷阱是只算"性能收益"，按四步框架过一遍。一算查询匹配度：把现有慢查询清单列出来——大都是"按设备 + 时间窗口聚合"，超级表 + 降采样就是降维打击；若大量是跨维度复杂关联，收益打折，那部分数据本就不该进时序库。二算存储账：对比现网 MySQL 磁盘占用与压缩后体积（官方口径 1/10，实测为准），乘以年增长量与单价，这是最硬的钱；三算迁移与双写成本：历史数据导入、新数据双写验证、SQL 方言改写，逐项估人天——历史数据可只迁聚合结果或冷归档，不必全量搬家；四算运维与合规：团队养不养得起新内核的运维技能，AGPL-3.0 对使用形态（自用/对外分发）有无影响。我的倾向：先拿最痛的一条查询链路做影子验证——双写两周，对比查询耗时与磁盘曲线，用数据说服团队。公司主栈已在用它的场景，迁移还多一层"运维技能现成"的加成，评估时别漏计。

08本期要点与下期预告

带走这五句话：

  • 时序数据的三堵墙：写入吞吐、存储成本、降采样查询——通用数据库为"行的事务"设计，时序场景要"列的聚合"；
  • TDengine = 高性能、集群开源、云原生时序库 + 内建缓存/流式计算/数据订阅，主打"极简时序数据平台"；
  • 心智模型：一个数据采集点一张子表，超级表管一类设备——采集列随数据走，标签写死在子表，查询从超级表进；
  • 数据面：25.1k Stars（2026-09-19）；73 万+ 运行实例（README 口径）；AGPL-3.0；基准版本 3.4.1.6（GitHub Latest，2026-04-30）；
  • 选型捷径：数据是"设备按时间追加、按窗口聚合"就进候选；强事务、深度依赖 PG 生态就绕道。
