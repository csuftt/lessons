读进 Elasticsearch 源码：一条写请求的旅程

上一期我们端到端做了一个商品搜索。本期是系列收官，也是本线的灵魂期：先把一个常见误读拆掉——倒排索引和 segment 的底层实现不在 ES 仓库里，而在独立的 Lucene 项目中，ES 仓库读的是"怎么把检索库包装成分布式系统"；然后讲透两个设计决策——Engine 写入闭环与 translog 恢复、内置协调 Coordinator（为什么不把选主外包给 ZooKeeper/etcd）；再看 refresh 与 merge 的调度面，最后合成一张读码路线图。本期引用的每个类与文件路径，均逐条核对自源码 tag v9.5.4。

00本期要点

  • 分层先分仓库：倒排索引与 segment 的实现在 Lucene（独立 Apache 项目，以库嵌入 ES）；ES 仓库读的是分布式那一半；
  • 写入闭环：源码里是"先写内存 Lucene、再追加 translog、后推进检查点"三步；重启恢复 = 从检查点+1 回放日志，先提交后裁日志；
  • 选主内置：预投票、任期、发布在 Coordinator 一个类里闭环——零外部依赖是部署哲学，不是偷懒；
  • 调度面各管一段：refresh 定时任务挂在 IndexService（默认 1 秒、空闲跳过），merge 执行归 Lucene、调度归 ES 节点线程池；
  • 一条写请求的读码路线图：REST 层 → Transport 层 → 路由定位 → IndexShard/Engine → 副本广播与定时刷新。

02动笔前先分清：哪部分代码不在 ES 仓库里

网上流行一种说法："读 ES 源码就是读倒排索引的实现。"这话说错了一半。倒排索引、segment 的写入与合并执行、分词与打分，这些核心能力住在 Lucene 里——一个独立的 Apache 项目，ES 以库的方式嵌入它。ES 仓库真正沉淀的是分布式那一半：分片包装、写引擎、事务日志、集群协调。这不是短板，而是分层设计的活教材：

所以本期的读法只有一条主线：读 ES 怎么"用"Lucene，不读 Lucene 怎么"做"检索。遇到 segment、merge、打分的边界，切去 Lucene 仓库对应类，两个仓库分开钉 tag。

05决策一 · Engine 写入闭环与 translog 恢复

为什么这么设计？Lucene 的提交（把内存改动固化成完整可恢复状态）很贵，不能每条写入都做一次；但"客户端已确认"的写入又绝不能丢。ES 的解法是给每个分片配一个写引擎（Engine）：写操作先落内存 Lucene，再追加一份顺序写的日志 translog；昂贵的 Lucene 提交低频做。次序就写在这一段真实源码里：

/* 摘自 server/src/main/java/org/elasticsearch/index/engine/
   InternalEngine.java 的 index()（tag v9.5.4），节选 */
indexResult = indexIntoLucene(index, plan);          // ① 先写内存 Lucene
...
if (index.origin().isFromTranslog() == false) {      // 回放来的不再记，防循环
    location = translog.add(new Translog.Index(index, indexResult));  // ② 追加 translog
}
...
localCheckpointTracker.markSeqNoAsProcessed(indexResult.getSeqNo());  // ③ 推进检查点

三步的次序是关键：内存负责快，日志负责不丢，检查点负责记账。"确认前不丢"由 translog 的落盘策略兜住——默认 durability=request，每个请求同步一次磁盘后才回执。

重启恢复怎么走？引擎从"本地检查点 + 1"取日志快照，逐条回放到目标序号；回放完先做一次 Lucene 提交，再裁掉不再被引用的旧日志——次序不能反：

/* 摘自 server/src/main/java/org/elasticsearch/index/engine/
   InternalEngine.java 的 recoverFromTranslogInternal()（tag v9.5.4），节选 */
try (Translog.Snapshot snapshot = newTranslogSnapshot(localCheckpoint + 1, recoverUpToSeqNo)) {
    opsRecovered = translogRecoveryRunner.run(this, snapshot);   // 从检查点+1 逐条回放
}
...
flush(false, true, flushListener);          // 回放完先做 Lucene 提交
translog.trimUnreferencedReaders();         // 再裁掉不再被引用的旧日志

translog 自己的契约，类注释写得最直白（截图核对于 tag v9.5.4）：每个分片一个实例、持久记录所有未提交操作；检查点文件 translog.ckp 刻意做成单磁盘块大小，写入原子；每个 Lucene 提交点绑定日志 UUID，防止拿错日志恢复到别的分片。

Translog.java @ tag v9.5.4 类注释：A Translog is a per index shard component that records all non-committed index operations in a durable manner（来源：github.com/elastic/elasticsearch，2026-09-19 实拍）

换种做法会怎样？每条写入都做 Lucene 提交：segment 一条一个，延迟被磁盘开销吃掉，近实时无从谈起；只写内存不记日志：断电全丢，承诺兑不了。ES 的账是"内存 + 顺序日志 + 低频提交"——重启只回放增量，代价可控。这套"以日志兜底内存状态"的模式，与 MySQL 的 redo log、Redis 的 AOF 同族，是可以直接搬走的。

06决策二 · 自研选主：为什么不外包给 ZooKeeper/etcd

很多分布式系统把选主外包给 ZooKeeper 或 etcd，ES 的选择是把协调内置：server 模块的 cluster/coordination 包（7.0 起的 Zen2），选举、健康检查、发布全部在一个仓库闭环。Coordinator 这个类约两千三百行，预投票（PreVote）、任期（term）、发布（publish）一应俱全——读到"赢得选举要过几道关"，就看 startElectionScheduler()：

/* 摘自 server/src/main/java/org/elasticsearch/cluster/coordination/
   Coordinator.java 的 startElectionScheduler()（tag v9.5.4），节选 */
if (mode == Mode.CANDIDATE) {
    final var nodeEligibility = localNodeMayWinElection(lastAcceptedState, electionStrategy);
    if (nodeEligibility.mayWin() == false) { return; }   // 赢不了就不参选
    if (statusInfo.getStatus() == UNHEALTHY) { return; } // 本节点不健康不参选
    prevotingRound = preVoteCollector.start(lastAcceptedState, getDiscoveredNodes()); // 预投票

预投票是"先问大家愿不愿意投我，再正式拉票"——避免无人可赢时反复冲击选举。发布入口 publish() 则先校验：节点仍是 LEADER 且任期一致才发布，否则抛 NotMasterException。周边类各管一段：LeaderChecker 盯现任主、FollowersChecker 盯从节点、PublicationTransportHandler 管集群状态广播。

Coordinator.java @ tag v9.5.4 字段区实拍：preVoteCollector、electionSchedulerFactory、publicationHandler、leaderChecker、followersChecker——一张依赖清单就是一张职责分工表（来源：github.com/elastic/elasticsearch，2026-09-19 实拍）

这个决策的取舍在哪？外包的代价是部署面翻倍：多一套要部署、升级、监控的组件，故障排查跨系统，小集群起步门槛抬高。内置的代价是协调代码长在自己家，写对它责任自负——7.0 之前老一代选主的脑裂教训就是学费，Zen2 用预投票和投票配置把它修成了同类里的上乘之作。与 etcd 系列（第 20 期）呼应一句：同样是多数派加任期加日志复制的思路，区别只在 etcd 把 Raft 做成产品，ES 把它做成地基。

07决策三 · refresh 与 merge 的调度面

第三期讲过的"写入后默认 1 秒可搜"，落到代码上是两处开关。refresh 的节奏在 ES 手里：IndexService 按索引的 refresh_interval 起定时任务，调到分片的 scheduledRefresh()——最近没人搜的分片直接跳过（search-idle 优化），真正要刷才进引擎把缓冲写成新 segment。merge 的执行在 Lucene 手里，调度权又在 ES 手里：

/* 摘自 server/src/main/java/org/elasticsearch/index/engine/
   InternalEngine.java 的 getIndexWriterConfig()（tag v9.5.4），节选 */
final IndexWriterConfig iwc = new IndexWriterConfig(engineConfig.getAnalyzer());
iwc.setMergeScheduler(mergeScheduler.getMergeScheduler());  /* 合并调度器交给 ES 自己的实现 */

Lucene 的 IndexWriter 只判断"哪些 segment 该合并"，在哪个线程池跑由 ES 决定：v9.5.4 默认 ThreadPoolMergeScheduler，把合并交给节点级共享线程池 ThreadPoolMergeExecutorService，合并不再挤占索引与检索线程（源码注释原话：switched ON by default）。谁该干活和谁有资源干活，是两个问题——调度权与执行权分离的教科书示范。批量导入时把 refresh_interval 设成 -1 全关、导完手动刷，官方批量导入指引正是这么用的。

官方《Near real-time search》开篇实拍：文档写入后即被索引、near real-time——within 1 second 内可搜；Lucene 的 per-segment search，segment 即"段集合加提交点"，新文档从内存缓冲写成新段、先落文件系统缓存（refresh 的定义与默认 1s 在同页下文；来源：elastic.co 官方文档，2026-09-19 截图）

08读错仓库，是读大项目最常见的迷路

把两个钩子合到一起说：想在 ES 仓库里找倒排索引和打分的实现，方向先错——它们在 Lucene；想找一个"最核心的类"逐行读完，主线先错——ES 的价值在分布式那一半。正确的姿势是先分仓库，再读主线：认下 Engine、Translog、IndexShard 这条写入链，遇到 segment 与打分的边界就切去 Lucene 对应类，两个仓库分开钉 tag。第 04 节那张路线图，就是你的主线地图。

四个能搬回自己项目的模式：

  • 把复杂第三方包成有限接口——Engine 抽象把整个 Lucene 包在后面，NoOpEngine、ReadOnlyEngine 共用同一接口，换实现不动上层；
  • 以日志兜底内存状态——translog 就是 WAL 通用模式，MySQL redo、Redis AOF 同族：内存负责快，日志负责不丢；
  • 调度权与执行权分离——merge 由 Lucene 执行、节奏归节点线程池：谁该干活和谁有资源干活是两个问题；
  • 零外部依赖的自洽——协调内置换来"部署面等于集群面"，能内置的依赖就内置，装得越少越稳。

  • A. 丢了——它还没进 Lucene 提交点
  • B. 不丢——重启后从 translog 回放补回
  • C. 不丢——它必然已随上一次 flush 落盘
  • D. 看副本——副本同步了就没事，没同步就丢

10思考题

思考一：把 translog 从 ES 里拿掉，靠"每条写入都做一次 Lucene 提交"来保证不丢，会发生什么？反过来，只留内存不记日志呢？

先看 Lucene 提交的成本构成：一次提交要把内存里的改动固化成完整、自恢复的段结构，生成提交点、fsync 多个文件——它是为"批量、低频"设计的。逐条提交意味着每个 segment 只装一条文档，segment 数量爆炸后 merge 追着写跑，磁盘 IO 被提交放大，"近实时"退化成"远实时"，这就是为什么 ES 用 translog 把"不丢"和"提交"解耦：确认只需顺序追加日志（durability=request 下一次 fsync），昂贵提交攒到 flush 再做。反过来只留内存，则每次断电都丢掉"已确认"的写入——对客户端来说这是最恶劣的违约：返回了 created 却查无此文档。两个反事实合起来正是本期的核心结论：内存负责快，日志负责不丢，提交负责清账，三者各司其职。检查自己系统的时候可以套同一个问题：你承诺过的数据，崩溃后靠什么回来？答案若不是"一份顺序日志"，就要小心了。

思考二：假如 ES 当年真的把选主外包给 ZooKeeper/etcd，架构上会多出什么麻烦？反过来，内置协调的代价又由谁承担？

外包的第一笔账是部署面：用户装 ES 变成装两套系统，容量规划、升级窗口、监控告警、安全加固全部乘以二；对"一个容器起一个集群"的轻量心智模型是致命伤——ES 的主流用户是数据工程师而不是分布式系统专家。第二笔账是故障域：集群状态要经过外部系统的数据模型翻译一遍，"ES 看到的主"与"协调组件看到的主"可能不一致，排障时两个系统互相甩锅；心跳与会话还额外吃一跳网络。第三笔账是语义贴合度：ES 要的不只是"选出主"，还有分片分配、投票配置、节点失联判定这一整套与集群状态联动的逻辑，放外部系统里每一条都要跨系统协商。内置的代价则是复杂度留在自己家：协调代码与业务同仓演进，错了没有外部社区背书——7.0 之前老一代选主在脑裂场景下的教训就是这笔代价的真实账单，Zen2 用预投票（先探意愿再拉票）和投票配置把修复做进了架构。通用的启发：依赖外包省的是开发成本，付的是运维成本与故障复杂度；核心协调逻辑这类"错一次就丢整个系统"的部件，值得自己养。
