OSS PROJECT INTRO · PROMETHEUS 系列第 2 期:5 分钟跑起来

5 分钟跑起来 Prometheus:解压即用起服务,亲手查出第一条曲线

上一期我们认识了 Prometheus——Pull 模型的指标监控一体机,公司监控大屏和 K8s 告警链路背后的那双眼睛。这一期把认识变成动手:把它在你机器上跑起来,让第一个抓取目标变成绿色,亲手用 PromQL 查出第一条曲线,并说清楚什么状态才算真的跑通。全文基于 v3.14.0(2026-08-17 发布,GitHub Releases Latest 标记,官方下载页口径,2026-09-19 复核;官方同时维护 3.13 LTS 线,最新补丁 3.13.3),下载解压、最小配置、启动验证与示例表达式逐字对照 prometheus.io 官方 First steps 与 Installation 文档,高频报错一并给全——Prometheus 是单二进制、零外部依赖,这可能是全系列最轻松的一期上手。

📈 监控与告警 · Go · Apache-2.0(CNCF 毕业项目) 📦 基于 v3.14.0(2026-08-17) 📅 2026-09-19 · 第 2 期 ⏱ 预计阅读 15 分钟

01本期路线与跑通判定

四步路线:解压 → 配置 → 启动 → 查询。全程一条演示链走到底,三条判定全绿才算跑通:

  • ① Target Up:打开 9090 端口的 Web 界面,Status → Targets 页里第一个抓取目标 Prometheus 自己,State 是绿色的 Up;
  • ② 指标查得出:表达式浏览器的 Table 页,输入官方示例表达式,能返回一批带标签的时间序列和最新值;
  • ③ 曲线画得出:Graph 页用 rate(...) 查出一条随时间变化的曲线——数据进得来、查得出、画得动,才是"跑起来"。

先给一个心理预期:上期说过 Prometheus 是 Pull 模型——它主动去拉每个目标的指标。本期第一个被拉的目标,就是 Prometheus 自己:它启动后会抓取自己的 /metrics 端点,所以你不用再部署任何业务应用,就能完整体验"抓取、存储、查询"整条链路。这也是官方 First steps 的教学习惯:先用自己当靶子,把流程跑通。

02动手前:钉版本、选路线、看环境

先钉版本。GitHub 发布页上,v3.14.0 挂着 Latest 标记(2026-08-17,官方下载页口径);官方同时在维护 3.13 LTS 长期支持线,最新补丁 3.13.3(2026-09-07);而 3.15 还停在 rc 预发布(3.15.0-rc.0,2026-09-09)——尝鲜可以,生产别追 rc。本系列统一以 3.14 线为基准,所有命令当日逐字对照过官方文档。

安装路线怎么装适合谁
解压单二进制(本期主线)官方下载页拿压缩包,tar 解压即用,解压出来就是可执行文件最快跑通、最贴官方 First steps 口径
Docker 官方镜像docker run -p 9090:9090 prom/prometheus 一条命令机器上已有 Docker、想环境隔离
配置管理包 / 源码编译Debian/Ubuntu、RHEL 系仓库包,或自行编译长期挂在服务器、有配置管理习惯

本期主线选 解压单二进制:它是官方 First steps 的原生口径,每一步都能逐字对照文档,而且最能体现这个项目的性格——单二进制、零外部依赖(官方原话 no external dependencies)。对比一下:上一期 Elasticsearch 起一个容器要配密码、拷证书、留 4GB 内存;Prometheus 解压完就能跑,上手成本低一个量级。

环境要求一句话:一台普通机器就行。官方文档没有给"最低内存"这种硬指标,给的口径是:平均每个样本只占 1 到 2 字节磁盘,容量公式 needed_disk_space = retention_time_seconds × ingested_samples_per_second × bytes_per_sample;官方 FAQ 说单实例可靠承载千万级活跃序列。像本期这样只抓自己一个 job 的实例,几百 MB 内存绰绰有余(实践口径)。Windows 用户也有对应的 prometheus.exe,不装 Linux 一样跟完本期。

03第一步:下载解压,拿到两个可执行文件

去官方下载页 prometheus.io/download 找到 3.14.0 对应平台的压缩包(Linux amd64 的包名形如 prometheus-3.14.0.linux-amd64.tar.gz,约 102 MiB,页面附 SHA256 校验值),然后按官方 First steps 原样两条命令:

tar xvfz prometheus-*.tar.gz
cd prometheus-*

解压出来的目录里有两个可执行文件:prometheus 本体,和 promtool——官方配套的检查工具,校验配置、校验规则文件都用它,高频报错一节会请它出场。Windows 用户下载 zip 包解压,对应的是 prometheus.exe。可以先跑 ./prometheus --help 看一眼帮助,官方 First steps 也是这么建议的——确认二进制能执行,再往下走。

顺带说 Docker 路线:官方 Installation 页原话是 docker run -p 9090:9090 prom/prometheus,"用一份样例配置启动 Prometheus 并暴露 9090 端口";想挂自己的配置文件,加 -v /path/to/prometheus.yml:/etc/prometheus/prometheus.yml。注意官方提醒:容器里数据写在 /prometheus 目录,容器一删数据就没了,要留数据就挂一个 volume。两条路线殊途同归,后面的界面操作完全一致。

04第二步:最小配置,让它先抓自己

Prometheus 的所有配置都在一个 YAML 文件里,默认就叫 prometheus.yml(压缩包里带一份带完整注释的样例)。官方 First steps 给的精简版长这样:

global:
  scrape_interval:     15s
  evaluation_interval: 15s

rule_files:
  # - "first.rules"
  # - "second.rules"

scrape_configs:
  - job_name: prometheus
    static_configs:
      - targets: ['localhost:9090']

三块结构逐个说。global:全局默认——抓取间隔 15 秒、规则评估间隔 15 秒(不写的话官方默认都是 1 分钟,样例显式改小,是为了界面上的数据变化肉眼可见)。rule_files:告警与记录规则文件列表,本期先注释着,告警规则是后面期数的剧情。scrape_configs:抓取目标清单——这里定义了一个叫 prometheus 的 job,目标是 localhost:9090。还记得上期说的 Pull 模型吗?这十几行就是那个"拉"字的落地:Prometheus 会每 15 秒请求一次 http://localhost:9090/metrics,把返回的指标文本存进自带的时序数据库。

缩进就是语法:YAML 靠两个空格的层级表达从属关系,Tab 和空格混用会直接报错——这是新手第一大坑,报错清单里给解法。

05第三步:启动,打开 9090 状态页

官方 First steps 原样命令,在解压目录里执行:

./prometheus --config.file=prometheus.yml

终端会滚动打印启动日志:加载配置、启动 TSDB、监听 9090 端口。看到不再刷屏,就可以按官方文档说的做——打开 http://localhost:9090,这是 Prometheus 自带的 Web 界面;官方提醒给它大约 30 秒去采集自身数据。想验证指标端点,直接浏览器或 curl 访问 http://localhost:9090/metrics:能刷出一大屏文本,每行一条"指标名{标签} 值",这就是 Pull 模型拉回来的原料,也是第 3 期要拆的数据模型的样子。

此刻它已经在存数据了:抓回来的每个样本都写进本地 TSDB(时序数据库),不需要装 MySQL 也不需要装 Redis——零外部依赖不是口号,是启动那一刻就成立的事实。

06第四步:Status → Targets,看第一个目标变绿

Web 界面菜单里点 Status → Targets:这个页面列出所有抓取目标的健康状态。你应该看到 prometheus 这个 job 下有一个 http://localhost:9090/metrics 端点,State 一栏是绿色的 Up,旁边还有 Last scrape(上次抓取时刻)和抓取耗时。跑通判定第一条达成。

页面上的 Up/Down 不是摆设,它对应一条官方合成的指标 up:官方 Concepts 文档口径——每次抓取成功,up 记 1;抓取失败,记 0。所以"目标活着"本身就是一条可以查询的时序,后面排查"为什么没数据"时,第一个要查的就是它。

顺便把同一菜单里的 Status → Runtime & Build Information 留个印象:版本号、启动时长、存储统计都在那里——以后怀疑"跑的是哪个版本"时,来这里对答案。

07第五步:查第一条指标,画第一条曲线

点菜单 Query 进表达式浏览器(或直接访问 http://localhost:9090/query)。官方 First steps 给的第一条表达式,是 Prometheus 暴露的自身请求计数:

promhttp_metric_handler_requests_total

Table 页回车,官方文档描述的结果是:返回若干条时间序列,指标名相同、标签不同,每条带一个最新值——标签里的 code 区分了 HTTP 状态码。想只看成功的 200,加标签过滤 {code="200"};想知道一共几条,套一层 count(...)。这就是 PromQL 的味道:指标名加花括号标签做筛选,函数做聚合,一行顶别家一段配置。

然后切到 Graph 页,画本期第一条曲线。官方给的示例表达式:

rate(promhttp_metric_handler_requests_total{code="200"}[1m])

rate(...[1m]) 是"最近 1 分钟的每秒增长速率"——计数器只会涨,直接看数值意义不大,增长率才有剧情。曲线虽然此刻还比较平(毕竟只有你自己访问),但数据从抓取、存储到查询、画图的整条链路,你已经亲手走通了。跑通判定第二、三条达成。

08高频翻车与解法(对号入座)

症状原因与官方口径解法
启动即退,日志报 Error loading config ... parsing YAML file ... line N配置文件语法错误,日志会给出行号,去第 N 行找缩进问题(Tab 混入、冒号后缺空格是常客)。更稳的做法:用官方配套工具 ./promtool check config prometheus.yml 先校验再启动
9090 端口被占,启动报监听失败或页面打开是别的服务查占用(lsof -i :9090 或 netstat -ano);或者换端口启动:./prometheus --config.file=prometheus.yml --web.listen-address=:9091,之后访问 9091
Targets 页目标 Down,Error 里写 connection refusedPull 模型下,"抓不到"本身就是信号:目标进程没起、端口没听、地址写错或防火墙拦截。上期说过监控靠拉——现在你亲身体会到拉失败的报错长什么样了,先确认目标活着,再看地址对不对
Docker 路线:容器重启后数据没了官方 Installation 页提醒:数据写在容器内 /prometheus 目录,容器删除即清空;要持久化就 docker volume create prometheus-data 并以 -v prometheus-data:/prometheus 挂载
改了配置不生效配置在启动时加载。向进程发 kill -s SIGHUP 可触发热加载(官方 Getting started 口径),或者干脆 Ctrl-C 重启——上手期重启最快
Graph 页查不到曲线 / 数据点很稀先看 Targets 是不是 Up(判定第一条);确认全局 scrape_interval——官方默认 1 分钟,样例里的 15 秒是显式配置;rate 的窗口至少要覆盖两个样本点,窗口太小会算不出

09随堂小测

1. 官方最小配置里,job_name 为 prometheus 的抓取目标是谁?

  • 本机的 Node Exporter
  • Grafana 的数据源端点
  • 它自己的 localhost:9090

2. Status → Targets 页里 State=Up 对应哪条官方合成指标?

  • scrape_duration_seconds
  • up(成功为 1,失败为 0)
  • prometheus_build_info

3. 启动报 parsing YAML file line N,最快的官方校验方式是?

  • ./promtool check config prometheus.yml
  • 多重启几次就好了
  • 加 --web.listen-address 换端口

10思考题(点击展开解析)

思考一:官方反复强调"单二进制、零外部依赖"。对比上一期 Elasticsearch 的安装体验,这个设计到底换来了什么、又付出了什么?

先看换来了什么。监控基础设施有个特殊要求:哪里都能落,而且落地越快越好——你要监控的机器越"边缘",环境越不可控,越装不动一堆依赖。Prometheus 把存储(TSDB)、抓取、查询、规则评估全部塞进一个 Go 编译的可执行文件,解压即用,启动只吃一个配置文件;对比上期 ES:JVM 之上,首次启动生成密码证书、还要留意内核参数,上手成本高一个量级。零外部依赖还有一层含义:数据存本地,不依赖 MySQL、不依赖分布式存储(官方特性清单原话 single server nodes are autonomous),坏一家不影响另一家,排障时也只有一个进程要看。代价同样明确:单机自治意味着它天生不横向扩展,容量顶到头只能加机器分片或者换长期存储;本地存储不复制,机器一坏数据全没。所以生产上 Prometheus 的高可用方案,官方建议很"笨":跑两个一模一样的实例各抓各的——为什么这个笨办法反而被认为是对的,第 3 期架构篇展开。

思考二:配置里 scrape_interval 写 15 秒,官方默认却是 1 分钟。抓取间隔的取舍,到底在权衡什么?

抓取间隔决定数据的时间分辨率:15 秒一个点,异常从发生到被看见平均慢不到 8 秒;1 分钟一个点,同样的故障可能要等半分钟才进库。监控的本质是"用今天的钱买明天的知情权",间隔越密,看见得越快——但成本有三笔:第一,存储,虽然官方口径平均每样本只有 1 到 2 字节,序列数一多,样本量是"序列数 × 每分钟点数"的乘法,密一倍、磁盘和内存翻一倍;第二,被监控端的压力,每次抓取都要序列化全部指标,几万个目标把间隔调到 5 秒,抓取本身就成了压垮目标的最后一根稻草;第三,查询时的计算量,点密一倍,区间函数要多算一倍样本。官方默认 1 分钟,是给"大多数指标大多数时候"的稳健值;样例改成 15 秒,是教学场景让界面数据动起来。实际落地的心法:不是所有指标都值得密抓——全局默认放宽,关键 job 单独调密,再配合 rate 这类区间函数的窗口要至少覆盖两个样本点的约束去选窗口。抓取间隔的选择没有标准答案,只有"告警时效、成本、目标承受力"的三方谈判,这份权衡感从第一天就该建立。
