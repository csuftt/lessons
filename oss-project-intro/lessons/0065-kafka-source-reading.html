03钩子一：一条 produce 请求，到底经过哪几站？

一条消息从客户端出发到落盘确认，服务端一共五站：网络层收字节 → 分发层认协议 → 副本管理器写主副本 → 日志门面分配偏移量 → 段与文件落盘。acks 等于负一时还要在延迟队列里等副本追上。接下来五站一页一步，行号全部锚定 tag 4.3.1。

04第 1 站 · 分发：ApiKeys 与 KafkaApis

网络层把请求放进队列，请求处理线程取出后交给 KafkaApis.handle——全部请求的唯一总入口，按协议枚举分发，produce 是第一号协议：

    case ApiKeys.FETCH   => handleFetchRequest(request)                   // L171

def handleProduceRequest(request: RequestChannel.Request, requestLocal: RequestLocal): Unit = {  // L396
  // ...鉴权与记录校验略：未授权 / 未知主题 / 非法记录各自记入响应

05第 2 站 · 副本追加：acks 在这里被解释

// core/src/main/scala/kafka/server/ReplicaManager.scala · 摘自 tag 4.3.1
def appendRecords(timeout: Long, requiredAcks: Short, ...): Unit = {   // L637
  if (!isValidRequiredAcks(requiredAcks)) {        // L647 合法值只有 0 / 1 / -1
    sendInvalidRequiredAcksResponse(...); return
  }
  val localProduceResults = appendRecordsToLeader(...)  // L652 逐分区写主副本日志
  ...
  maybeAddDelayedProduce(requiredAcks, timeout, ...)    // L669 acks=-1：挂入延迟操作
}
// appendToLocalLog 内 · L1413-1414
val partition = getPartitionOrException(topicIdPartition)
val info = partition.appendRecordsToLeader(records, origin, requiredAcks, ...)

确认语义就是这几行分支：acks 等于零，不等任何确认，丢了也不重发；等于一，主副本写完就算成功；等于负一且至少一个分区追加成功，请求挂进延迟队列，等副本追上再回调。逐分区追加时任何一个分区失败，都单独记进响应，不牵连其他分区。

来源：kafka.apache.org/43/configuration/producer-configs/ 官方 acks 条目（2026-09-20 实拍）：acks=0 不等服务器任何确认；acks=1 主副本写入即成功；acks=all 全部同步副本到位。

06第 3 站 · 日志门面：UnifiedLog 分配偏移量

进 storage 模块。UnifiedLog 是分区日志的门面（4.3.1 共 2787 行），appendAsLeader 只做转接，真身在私有 append 里：

// storage/src/main/java/org/apache/kafka/storage/internals/log/UnifiedLog.java · 摘自 tag 4.3.1
public LogAppendInfo appendAsLeader(MemoryRecords records, int leaderEpoch, ...) {  // L1049
  boolean validateAndAssignOffsets = origin != AppendOrigin.RAFT_LEADER;  // L1055
  return append(records, origin, validateAndAssignOffsets, leaderEpoch, ...);
}
private LogAppendInfo append(...) {
  synchronized (lock) {                                      // L1137 分区级串行
    LogSegment segment = maybeRoll(validRecords.sizeInBytes(), appendInfo);  // L1234 段满滚动
    localLog.append(appendInfo.lastOffset(), validRecords);  // L1262 追加进活动段：顺序写
    updateHighWatermarkWithLogEndOffset();                   // L1263 高水位推进到日志末端

三件事值得划线：分区锁收敛在分区这一层，同一分区串行、不同分区互不阻塞；偏移量由主副本在此分配，这就是"日志末端前移"的动作本体；段写满就地滚动新段，老段从此只读。

07第 4 站 · 落盘一击：顺序写在这里发生

本地日志 LocalLog 只写活动段，段内追加是最后三步：

  segments.activeSegment().append(lastOffset, records);   // L527 只写活动段
  updateLogEndOffset(lastOffset + 1);                     // L528 日志末端前移
}
// LogSegment.append：段内三件事

long appendedBytes = log.append(records);             // L260 字节直写文件通道
if (bytesSinceLastIndexEntry > indexIntervalBytes) {  // L270 稀疏索引：攒够间隔才记
  offsetIndex().append(batchLastOffset, physicalPosition);   // L271 偏移索引
  timeIndex().maybeAppend(maxTimestampSoFar(), ...);          // L272 时间索引

log.append(records) 的 log 就是 FileRecords，内部一行 records.writeFullyTo(channel)（L198）——字节直写文件通道，追加位置永远是段尾。顺序写本体 + 稀疏索引：磁盘友好和按偏移量查找，两头都占了。这就是第 1 期"用最笨的写法换数量级差距"的代码落点。

08钩子三：为什么读数据的进程一个字节都不碰？

消费侧读日志时，数据不去进程里绕路。写出方法把活交给传输层，零拷贝的终点就一行：

// clients/.../internal/FileRecords.java L290 与 PlaintextTransportLayer.java L213 · tag 4.3.1
public int writeTo(TransferableChannel destChannel, int offset, int length) throws IOException {
  long position = start + offset;                     // L299 从段的物理位置起
  int count = Math.min(length, oldSize - offset);     // L300
  return (int) destChannel.transferFrom(channel, position, count);  // L302 交给传输层
}
// PlaintextTransportLayer：零拷贝的终点
public long transferFrom(FileChannel fileChannel, long position, long count) throws IOException {
  return fileChannel.transferTo(position, count, socketChannel);  // L214 sendfile：页缓存直达网卡
}

transferTo 就是操作系统的 sendfile：数据从页缓存直接进网卡，Kafka 进程全程不碰字节。为什么敢这么干？因为日志只需要"原样转发"，不需要在应用层加工——这是第 1 期零拷贝直觉的代码终点。代价也要知道：TLS 加密场景用不上，SslTransportLayer 退回用户态拷贝，零拷贝失效。顺手看清页缓存的位置：Kafka 进程内不缓存消息数据，读写都压在操作系统页缓存上，进程内存只放索引与元数据——JVM 大堆垃圾回收远离数据路径，这是第三个设计决策。

来源：github.com/apache/kafka/blob/4.3.1 · FileRecords.java #L290-L303（writeTo 高亮，2026-09-20 实拍）。

09钩子二：acks 等于负一时，broker 在等谁？

等 ISR 里的每一个副本追上高水位。主副本落盘只是第一步：追随者各自来 fetch，日志末端推进；当所有同步副本都越过旧高水位，高水位才能前移，挂起的 produce 请求才被完成。所谓"等全部确认"，等的不是人工审批，是副本们的一场追赶赛。

这场赛有进出规则，代码在 core/src/main/scala/kafka/cluster/Partition.scala：

// Partition.scala · 摘自 tag 4.3.1
def maybeShrinkIsr(): Unit = {                               // L1089
  val outOfSyncReplicaIds = getOutOfSyncReplicas(replicaLagTimeMaxMs)  // L1099 谁掉队：看最后追平时间
  ...
  alterIsrUpdateOpt.foreach(submitAlterPartition)            // L1125 KRaft：交控制器仲裁
}
// 扩张在 L876 maybeExpandIsr：副本 LEO 追上高水位、且越过当前纪元起点才回队（L907-912）

两个细节。掉队判定不看心跳看进度：副本的"最后追平时间"落后超过 replicaLagTimeMaxMs 才进掉队名单。KRaft 之后 ISR 变更要提交控制器仲裁（AlterPartition），不再是 leader 单方面改——元数据的权威收回到了控制器一侧，这是与旧版最大的行为差异。

来源：github.com/apache/kafka/blob/4.3.1 · Partition.scala #L1089-L1125（maybeShrinkIsr 全段高亮，2026-09-20 实拍）。

10对照 Pulsar：两种存储定价，没有对错

Pulsar 系列第 0015 期源码导读我们看过存算分离：broker 无状态，消息与进度全在 BookKeeper，扩容即起进程，封卷的账本还能整体搬去对象存储。Kafka 反着来，存算一体：日志段文件就放在 broker 本地盘，读写压在页缓存上，路径最短、组件最少——一个进程同时是计算与存储。代价也清楚：扩缩容与再均衡要搬分区，Topic 数量大了 broker 自己扛。

一个用路径换弹性，一个用弹性换路径，这是两种定价，不是两个对错。读两边源码的体验也对仗：Pulsar 的写入链要跨 broker 与 bookie 两层进程，Kafka 的写入链在一个进程里从套接字一路走到文件通道。

11回收第 3 期伏笔：Topic 多了为什么抖？

现在能从源码结构回答这个反直觉现象，证据有三，全部有行号：

  • 证据一 · 每分区常驻对象群：每个分区一个 Partition 对象、一个 UnifiedLog、一把分区读写锁，纯元数据也吃堆内存（Partition.scala L163 起）；
  • 证据二 · 每段三件套：每个日志段一个文件句柄加偏移索引、时间索引两份稀疏索引（LogSegment L270-272），句柄与索引随分区数线性涨；
  • 证据三 · 线程是固定配额：请求处理线程数固定——num.io.threads 默认 8（server-common 的 ServerConfigs L51），而挂起的延迟操作、每分区的副本拉取流都随分区数涨。

快的设计和抖的隐患是同一套机制的两面：把状态压到进程与本地盘换来了路径短，也就接住了分区数的乘数。规划 Topic 分区数时按吞吐算，不为"以后可能用"预铺。

13可借鉴清单：搬回自己的系统

  • ✅ 只追加的不可变结构：顺序写加整段回收——操作日志、审计流水、事件溯源都能抄这个骨架；
  • ✅ 进程内不缓存数据：读写压在操作系统页缓存，数据路径远离垃圾回收大堆；
  • ✅ 延迟完成而非轮询等待：acks=-1 挂进 purgatory，副本追上即回调，不空转；
  • ❌ 一把大锁管所有分区：Kafka 每分区一把锁、入口收敛串行——全局锁是多分区吞吐杀手。

15思考题（点击展开解析）

思考一：Kafka 敢把"进程内不缓存数据"当设计底线。如果把页缓存换成进程内缓存，会失去什么、得到什么？

得到的是理论上的读延迟下限——进程内存总比页缓存快一跳；失去的有三样，且都比这一跳值钱。第一，丢掉 sendfile。零拷贝的前提是数据留在页缓存、由内核直送网卡；数据一旦进 JVM 堆，写出就得先拷回内核，快的那一跳立刻赔回去。第二，丢掉"免刷盘语义"。页缓存由操作系统统一管理，落盘时机、写合并、断电后的恢复都交给内核；进程内缓存得自己回答"这条到底落没落盘"。第三，丢掉容量弹性。页缓存随空闲内存自动伸缩，进程内缓存要预先圈堆，大堆直接恶化垃圾回收——数据路径和 GC 互相拖累。回过头看，"进程不碰数据"不是省事，是顺序写、零拷贝、页缓存三件套能同时成立的前提条件。

思考二：Kafka 的 ISR 用"追赶赛"定义同步，Raft 用"多数派"定义提交。两种思路各自的代价是什么？

ISR 的代价在可用性侧：它要求配置的全部同步副本追上才确认（acks=-1），一个 follower 掉队就卡写入，于是才有收缩机制把掉队者踢出去换可用性；而收缩本身又是元数据变更，KRaft 下要走控制器仲裁，窗口期内高水位纹丝不动——代价被转移成了元数据协议的复杂度。多数派的代价在成本侧：只要过半节点确认就提交，写入更不容易被单个慢节点卡住，但每个分区至少要三个副本才有意义，存储成本乘三起步。Kafka 用 ISR 把"确认人数"变成可配置项，等于把这笔账交给用户算：acks=1 快但弱，acks=-1 稳但要养够副本。两套思路没有对错，选型时真正该问的是：你的业务能容忍多大的确认窗口，又愿意为它付几份存储。
