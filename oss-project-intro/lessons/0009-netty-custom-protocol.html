OSS PROJECT INTRO · Netty 系列第 4 期：实战场景

自定义协议的 TCP 服务器：拆包、编解码、心跳一次打通

看过五大核心概念，这一期把它们全部拧在一台真实机器上：从零定义一个"设备上报 / 消息推送"风格的自定义 TCP 协议，用 LengthFieldBasedFrameDecoder 解决粘包半包（五个参数逐个算给你看），写一对出站入站编解码器，加上 IdleStateHandler 心跳踢线，把阻塞任务隔离到业务线程池，再给两种与 Spring Boot 共存的形态，最后用模拟客户端把报文打进服务器、收回 ACK。跑通这一条链，第 3 期的概念就全落了地。

01需求与报文：为什么 TCP 必须自己框边界

目标场景很典型：海量设备长连接接入——设备连上服务器后定时上报数据（温度、坐标、状态），服务器偶尔反向推送指令。HTTP 头太重、连接太短；WebSocket 语义又不完全合身。很多团队的选择是在裸 TCP 上定义一个自己的报文格式，本期就用这个简单够用的五字段协议：

  • 魔数（2B）：0xCAFE，第一眼识别"是不是自家协议"，防误连；
  • 版本（1B）：0x01，给未来的协议升级留逃生门；
  • 类型（1B）：0x01 上报 / 0x02 ACK 应答 / 0x10 心跳；
  • 长度（4B）：大端整数 N，只统计"体"的字节数；
  • 体（NB）：JSON 或二进制载荷。

有了格式，还要回答那个绕不开的问题：为什么必须由长度字段来框边界？因为 TCP 是字节流，它只承诺字节顺序不变，不承诺"你发几次我就收几次"。两种日常事故：粘包——客户端连发两条 40B 报文，服务端一次 channelRead 可能收到 80B；半包——一条 40B 报文先到 13B、再到 27B，长度字段自己都被截成了两半。这不是 bug，是 TCP 的本性（Nagle 合包、MSS 分段、接收缓冲区读取粒度都会促成）。所以应用层必须自带边界信息——长度字段就是干这个的：先凑够 8B 头，读出 N，再等齐 8+N 字节，切出完整一帧。

02拆包：LengthFieldBasedFrameDecoder 五个参数逐个算

框边界的活儿 Netty 早就做成了现成零件：LengthFieldBasedFrameDecoder（继承自 ByteToMessageDecoder），按长度字段把字节流切成一帧一帧。它的官方 javadoc 里有一句必须记住的默认假设：长度字段的值，表示它后面还跟着多少字节。我们的协议"长度只算体"正好踩在这个假设上。构造器五个参数，对着上面的报文图逐个算：

参数本协议取值怎么算出来的
maxFrameLength1024 * 1024防御上限：帧长超过它就抛 TooLongFrameException，防恶意长度值打爆内存
lengthFieldOffset4长度字段前面有几个字节：魔数 2 + 版本 1 + 类型 1 = 4
lengthFieldLength4协议规定长度字段本身占 4 字节（1/2/3/4/8 都支持）
lengthAdjustment0javadoc 原文：补偿值（加到长度字段的值上）。本协议长度只算"体"，而 offset + 字段宽 = 4 + 4 = 8 已覆盖整个头，无需补偿
initialBytesToStrip0切完帧从头丢掉几个字节。后续业务解码器还要读魔数/版本/类型，一个都不能丢

参数对不对，一条式子就能验证（也是 Netty 源码里帧长的计算逻辑）：

frame-length.txt
帧长度 = lengthFieldOffset + lengthFieldLength + lengthAdjustment + 长度字段的值
      =      4        +        4         +       0         +     N
      = 8 + N   ✓ 正好 = 头 8 字节 + 体 N 字节

反例：若长度字段定义成"整包长度（含头）"，值为 8+N：
      =      4        +        4         +     (-8)         +    (8+N)
      = 8 + N   ✓ 多算进去的 8 字节头，用 -8 补偿回来

所以 lengthAdjustment 不是玄学：长度字段"少算"了头，就补正数；"多算"了头，就补负数。改协议先写这条式子，参数自然落地。另外还有 failFast 变体构造器（超长帧是"发现即抛"还是"读完整帧再抛"），以及指定 ByteOrder 的七参版本，4.1 与 4.2 的签名完全一致。

03编解码器：出站编码 + 入站解码，成对出现

拆包器只负责"切出完整一帧"，帧里读字段、对象变字节，还要自己写两个小类。先看消息对象和出站编码器（MessageToByteEncoder）：泛型声明消息类型，Netty 在出站方向碰到这种消息就回调 encode，第三个参数 out 就是最终要写向网络的字节：

ProtocolEncoder.java
public class ProtocolEncoder extends MessageToByteEncoder<ProtocolMessage> {
    @Override protected void encode(ChannelHandlerContext ctx,
                          ProtocolMessage msg, ByteBuf out) {
        out.writeShort(ProtocolMessage.MAGIC);   // 魔数 2B
        out.writeByte(ProtocolMessage.VERSION);  // 版本 1B
        out.writeByte(msg.getType());            // 类型 1B
        byte[] body = msg.getBody() == null ? new byte[0] : msg.getBody();
        out.writeInt(body.length);               // 长度 4B：只算体
        out.writeBytes(body);                    // 体 NB
    }
}

再看入站解码器：直接继承 LengthFieldBasedFrameDecoder，把五参数封进构造器，然后在 decode 里先调 super.decode 拿到完整一帧，再顺着偏移读字段——拆包和解字段一个类搞定：

ProtocolDecoder.java
public class ProtocolDecoder extends LengthFieldBasedFrameDecoder {
    public ProtocolDecoder() {
        super(1024 * 1024, 4, 4, 0, 0);  // 第 02 节算出的五参数
    }

    @Override protected Object decode(ChannelHandlerContext ctx, ByteBuf in) throws Exception {
        ByteBuf frame = (ByteBuf) super.decode(ctx, in);
        if (frame == null) return null;         // 半包：字节不够，安静等下一批
        try {
            short magic = frame.readShort();
            if (magic != ProtocolMessage.MAGIC)
                throw new DecoderException("bad magic"); // 不是自家协议
            frame.readByte();                     // 版本：暂存兼容字段
            ProtocolMessage msg = new ProtocolMessage();
            msg.setType(frame.readByte());
            int len = frame.readInt();            // 体长度（拆包器已保证够读）
            byte[] body = new byte[len];
            frame.readBytes(body);
            msg.setBody(body);
            return msg;                        // 传给下一个入站 handler
        } finally {
            frame.release();                       // 池化内存必须还，否则泄漏
        }
    }
}

两段代码是镜像关系：编码时怎么写的，解码时就怎么读，共用同一张报文定义。装配时解码器放 pipeline 最前（否则后面的处理器拿到的是一锅字节粥），编码器放它后面：

ProtocolServer.java（装配核心）
b.group(boss, worker)
 .channel(NioServerSocketChannel.class)
 .childHandler(new ChannelInitializer<SocketChannel>() {
     @Override protected void initChannel(SocketChannel ch) {
         ch.pipeline().addLast(
             new ProtocolDecoder(),          // 入站：拆包 + 解字段
             new ProtocolEncoder(),          // 出站：对象编回字节
             new IdleStateHandler(15, 0, 0), // 15s 读空闲
             new ServerHandler());           // 业务
     }
 });
b.bind(9000).sync();

04心跳与空闲踢线：IdleStateHandler + userEventTriggered

长连接有个现实问题：设备断电、拔网线、进电梯，服务端未必收到任何断开通知，连接就变成挂在内存里的幽灵。Netty 的答案是空闲检测：IdleStateHandler 三个参数——readerIdleTime / writerIdleTime / allIdleTime（读空闲 / 写空闲 / 全空闲，单位秒，传 0 关闭对应检测）。到点没动静，它触发一个 IdleStateEvent，注意这条事件不走 channelRead，走 userEventTriggered，一条专门的旁路通道：

ServerHandler.java（空闲踢线）
@Override
public void userEventTriggered(ChannelHandlerContext ctx, Object evt) throws Exception {
    if (evt instanceof IdleStateEvent e && e.state() == IdleState.READER_IDLE) {
        ctx.writeAndFlush(ProtocolMessage.heartbeat())  // 最后探测一次
           .addListener(f -> ctx.close());               // 15s 没收到任何字节：踢线
    } else {
        ctx.fireUserEventTriggered(evt);                 // 别的事件继续往后传
    }
}

策略可以更温柔：记录连续读空闲次数，探测两三次都无响应再 ctx.close()，容忍瞬时抖动。设备端则应起定时器，安静超过半分钟就发一条心跳报文（类型 0x10，体为空），把服务端的读空闲计时器喂饱。心跳不只是保活，它同时也是 NAT 映射的续租手段。

05线程模型：业务 handler 里别阻塞 EventLoop

第 3 期讲过：一个 Channel 终身绑定一个 EventLoop 线程，而 worker 线程组默认只有 CPU 核数个线程，每个线程身上挂着一大把连接。在 channelRead 里查库、调第三方接口，卡 100ms，同一线程上几百条连接全部陪等——这是 Netty 服务端最常见的性能事故。正确姿势是把阻塞任务隔离到业务线程池，Netty 给的口子只要一个参数：

business-group.java
// 业务线程池：落库、调接口等阻塞活在这里消化
EventLoopGroup businessGroup = new DefaultEventLoopGroup(8);

ch.pipeline().addLast(
    new ProtocolDecoder(),
    new ProtocolEncoder(),
    new IdleStateHandler(15, 0, 0));

// 关键一行：指定执行线程组，之后的回调都在 businessGroup 里跑
ch.pipeline().addLast(businessGroup, new ServerHandler());

addLast(EventLoopGroup, handler) 的含义是：pipeline 从这个节点开始，该 handler 的事件回调都被派到指定线程组执行。于是 channelRead0 里可以放心写慢代码，EventLoop 只负责网络读写和纯内存计算，互不拖累。另一条路是在 handler 里自己 submit 任务到线程池，效果类似，但管道级切换让业务代码完全不用感知线程问题。

06与 Spring Boot 共存：两种形态

  • 形态一：Netty 独立进程。单独打包部署、端口独立，与 Web 应用彻底解耦，重启互不影响，还能单独扩容。设备接入网关、长连接推送层这类独立组件常这么干。
  • 形态二：嵌入 Spring 容器。Netty 跟业务应用同进程，handler 是 Spring 托管的 Bean，直接注入 service、事务和数据源；用 SmartLifecycle 把启停挂进容器生命周期。设备量不大的业务系统选它最省运维。
NettyServer.java（嵌入形态最小骨架）
@Component
public class NettyServer implements SmartLifecycle {
    private EventLoopGroup boss, worker;
    private Channel serverChannel;
    @Resource private ServerHandler serverHandler;  // Spring 托管的业务 handler

    @Override public void start() {          // 容器 refresh 完成后自动回调
        boss = new NioEventLoopGroup(1);
        worker = new NioEventLoopGroup();
        // ServerBootstrap 装配同第 03 节，仅业务 handler 换成注入的单例
        serverChannel = bootstrap(serverHandler).bind(9000).channel();
    }
    @Override public void stop() {           // 容器关闭：优雅停机，不丢存量连接
        serverChannel.close();
        boss.shutdownGracefully();
        worker.shutdownGracefully();
    }
    @Override public boolean isRunning() { return serverChannel.isActive(); }
}

单例注入的代价：同一个 handler 实例会被加进所有连接的 pipeline，必须给类标上 @ChannelHandler.Sharable，并保证它无连接级的可变成员变量（连接状态放进 AttributeKey）——否则第二个连接建立马抛异常，这是嵌入形态的头号翻车点。

07端到端验证：发一条报文，收一个 ACK

二进制协议用 telnet 手敲太痛苦，十几行客户端代码最踏实（装配同服务端，只是去掉业务逻辑）：

ClientMain.java
Channel ch = new Bootstrap()
    .group(new NioEventLoopGroup(1))
    .channel(NioSocketChannel.class)
    .handler(new ChannelInitializer<SocketChannel>() {
        @Override protected void initChannel(SocketChannel c) {
            c.pipeline().addLast(new ProtocolDecoder(),
                                 new ProtocolEncoder());
        }})
    .connect("127.0.0.1", 9000).sync().channel();

ProtocolMessage msg = new ProtocolMessage();
msg.setType(ProtocolMessage.TYPE_REPORT);
msg.setBody("{\"deviceId\":\"A-001\",\"temp\":26.5}".getBytes(StandardCharsets.UTF_8));
ch.writeAndFlush(msg);   // 编码器自动转成协议字节流

跑起来后，在服务端把收发的字节打成十六进制，整条链路肉眼可见：

运行结果
客户端发出 40 字节（头 8B + 体 32B）：
  CA FE 01 01 00 00 00 20
  7B 22 64 65 76 69 63 65 49 64 22 3A 22 41 2D 30 30 31 22 2C 22 74 65 6D 70 22 3A 32 36 2E 35 7D
  // 即 {"deviceId":"A-001","temp":26.5}，N=0x20=32

服务端日志：
  收到完整一包 40B：magic=CAFE version=01 type=REPORT len=32
  业务线程入库完成，回 ACK 16 字节：
  CA FE 01 02 00 00 00 08 4F 4B 3A 41 2D 30 30 31
  // 头 8B（type=0x02 应答，len=8）+ 体 "OK:A-001"

想复现粘包很简单：循环连发两条再 flush，服务端照样一条条解析——拆包器在前面框好了边界；再故意把 lengthAdjustment 改错，立刻解码错乱或抛 TooLongFrameException，反向验证第 02 节的公式。

08随堂小测

每题点击选项立即反馈 · 共 4 题

1.（计算题）协议其他字段不变，但把长度字段的定义从"体的长度"改成"整包长度（含 8 字节头）"，此时 lengthAdjustment 应该填多少？

  • 8
  • 0
  • -8

2. 本协议中 lengthFieldOffset = 4 是怎么算出来的？

  • 从报文第 0 字节开始数，所以是 0
  • 魔数 2B + 版本 1B + 类型 1B = 4 字节，跳过它们才到长度字段
  • 头部固定 8 字节，所以是 8

3. IdleStateHandler 触发的 READER_IDLE 事件，应该在哪个回调里接收处理？

  • channelRead
  • exceptionCaught
  • userEventTriggered

4. 为什么本协议把 initialBytesToStrip 设为 0？

  • Netty 不允许传 0 以外的其他值给自定义协议
  • 后续业务解码器还要读魔数、版本、类型这些头部字段，一个字节都不能丢
  • 传 0 比传 8 解码速度快一倍

09思考题（点击展开解析）

思考一：为什么"一次 channelRead 收到的 ByteBuf"几乎永远不等于"一条报文"？从 TCP 的交付机制说起。展开解析 ▸

因为 TCP 对上层的交付单位是字节流片段，不是消息。发送端每次 write 只是把字节灌进发送缓冲区，内核按 MSS（最大分段大小）切成报文段发出，还可能被 Nagle 算法攒一攒再发；接收端内核把数据放进接收缓冲区，Netty 的 EventLoop 醒来时"手里有多少读多少"。于是：两次 write 的字节可能挤在同一次读里（粘包），一次 write 的大块字节可能分散在几次读里（半包），读到的边界跟发送边界之间没有任何对应关系——唯一保证的是字节顺序。这也解释了为什么"长度字段 + 等齐再切"是通用解：它把消息边界从内核的交付行为里拿回来，交还给应用层的协议自己定义。UDP 没这个问题（数据报天然有边界），但 UDP 不保证顺序、不保证到达、有报文大小上限，所以可靠有序的设备通道依然首选 TCP 加自定义拆包。

思考二：既然怕阻塞，为什么不干脆把 worker 线程组调大到几百个线程，而要另建业务线程池？展开解析 ▸

三个账。①绑定关系不变：NioEventLoopGroup 调大只是多了线程，但每个 Channel 仍绑定其中一个 EventLoop，你在 handler 里阻塞，卡住的还是这根线程以及挂在它身上的所有连接——调大线程数只是让"陪葬的连接"换了个分布，单连接的尾延迟一点没改善。②成本账：EventLoop 是注册在 Selector 上的 IO 线程，数量远超核数只会带来上下文切换和内存开销，浪费在"等数据库"上的线程纯粹是死重。③职责分离：IO 线程的理想的活是"读写 + 纯内存计算"，阻塞操作天然属于另一类资源池——连接池、异步客户端、业务线程组。Netty 的 addLast(businessGroup, handler) 让这个切换零成本落进 pipeline 结构里，慢活被隔离后，几百个连接共享十几个 IO 线程依然丝滑。一句话：线程多少不是关键，别让等外部资源的线程和跑网络 IO 的线程是同一批才是关键。

10本期要点与下期预告

带走这三句话：

  • TCP 是字节流不是报文流，边界必须自己框：五参数对着报文格式逐个算，一条帧长公式保平安；
  • 编解码成对出现（MessageToByteEncoder 出站 / 拆包器加字段读取站），心跳用 IdleStateHandler + userEventTriggered 踢线；
  • 重活别在 EventLoop 里干：addLast(businessGroup, handler) 隔离到业务线程池，Spring 共存按规模选独立进程或嵌入容器。
