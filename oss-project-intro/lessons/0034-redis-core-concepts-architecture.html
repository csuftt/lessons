03概念地图·数据面：命令面与实现面两层术语

Redis 的术语要分两层记。命令面是你敲命令时面对的类型——第 1 期说过，官方开篇第一句是 "Redis is a data structure server"，六个核心类型各配一族原子命令：

命令面类型代表命令一句话定位
StringSET · GET · INCR字节序列：缓存、计数器、分布式锁的基础
ListLPUSH · LRANGE按插入顺序的双端队列：时间线、简单队列
HashHSET · HGET字段-值映射：对象存档，改一个字段不用全量读写
SetSADD · SINTER无序去重集合：标签、共同关注、抽奖
Sorted setZADD · ZRANGE成员挂分数自动排序：排行榜、延迟队列
StreamXADD · XREAD只追加日志：事件流，消费组读位点

实现面是每种类型背后真正的内存结构。用 OBJECT ENCODING 能当场看穿：同一个命令面类型，小对象用紧凑编码，长大后自动换成通用编码——官方文档原话：一旦操作让空间编码无法维持，就自动转成通用编码。本期只点名叫什么、不展开怎么实现：

命令面类型底层编码（按官方 OBJECT ENCODING 文档）
Stringint（整数值）· embstr（短字符串）· raw（长字符串）
Listlistpack（小）· quicklist（quicklist 挂 listpack 节点）
Hashlistpack（小）· hashtable（字典）
Setintset（纯整数小集合）· listpack（小）· hashtable
Sorted setlistpack（小）· skiplist（跳表）
Streamstream：基数树（rax）组织的一串 listpack

这批名字就是第 5 期源码导读的主演名单：SDS（简单动态字符串，embstr/raw 的底层）、listpack、quicklist、intset、skiplist 都在 src/ 下有同名文件。数据结构怎么选型、编码何时切换的原理深入见：官方文档 · 《Redis 数据结构与选型》，本线不换皮重讲。

04概念地图·生命周期：过期删除与内存淘汰

键空间里每个键有两条"死法"，机制完全不同，先分清楚：过期删除管"带了 TTL 的键到点该消失"，内存淘汰管"内存满了该牺牲谁"。TTL 到点了键还查得到？正常，因为过期删除分两个时机：

  • 惰性删除（被动）：访问键时才发现已过期，当场删除并当作不存在——省 CPU，但没人再访问的键会滞留；
  • 主动删除（定期抽查）：Redis 周期性随机抽查一批带过期时间的键，过期的直接删，过期键占比高就继续抽查——兜住"永远不再被访问"的过期键。

实现上，过期时间存在另一张 expires 字典里（绝对 Unix 毫秒时间戳，所以服务器时钟不对会"提前过期"），与键空间主字典分开管。内存淘汰则是另一套：maxmemory 划定内存上限，触顶后按 maxmemory-policy 驱逐。按 2026-09 官方文档，策略族已有十种——两大维度的组合：

作用范围 →
淘汰依据 ↓		全部键 allkeys-*仅带 TTL 的键 volatile-*
最近未使用（近似 LRU）allkeys-lruvolatile-lru
最近未修改（LRM，8.6 新增）allkeys-lrmvolatile-lrm
访问频率（近似 LFU，4.0 起）allkeys-lfuvolatile-lfu
随机allkeys-randomvolatile-random
剩余存活时间最短—volatile-ttl

两句话记要点：LRU/LFU 都是近似算法——不维护全局链表，驱逐时随机抽 maxmemory-samples（默认 5）个候选，省内存省到极致；volatile 族在没有任何键带 TTL 时退化为 noeviction（触顶直接报错，宁可拒绝写入也不丢数据）。策略怎么选、缓存命中率怎么算：原理见官方文档内存管理一章。

05概念地图·持久面：RDB 快照与 AOF 日志

内存数据库怕断电，持久化就是"把内存状态落到磁盘"的两条路线，官方文档称它们为可组合的选项：RDB 是时间点快照，AOF 是写命令日志——一个是"结果存档"，一个是"过程回放"：

  • RDB（Redis Database）：按 save 点（如"60 秒内至少 1000 次修改"）生成某一刻的二进制全量快照，存为单个紧凑的 dump.rdb。生成时主进程 fork 出子进程，靠写时复制不动主进程内存——性能影响小、恢复快，代价是两次快照之间的数据在宕机时丢掉；
  • AOF（Append Only File）：每条写命令执行后追加进日志，重启时回放重建数据。落盘节奏由 appendfsync 决定：always（每条）、everysec（每秒，默认，最多丢一秒）、no（交给操作系统）。日志越写越大，Redis 会在后台自动重写——用重建当前数据集所需的最小命令集生成新日志。7.0 起采用多文件形态：base 文件（重写产物）+ incr 增量文件 + manifest 清单；
  • 两者同开是官方推荐姿态：AOF 保证数据更完整（重启时优先用它重建），RDB 兜底做备份与快速恢复。8.10 又给了新工具：BACKUP 命令族，不停写产出可直接恢复的备份。

概念先到"两制式 + 取舍"为止：RDB 换性能与紧凑、AOF 换数据安全窗口。参数细节、故障排障与容量规划见：官方文档 · 《Redis 持久化机制：RDB vs AOF 的架构权衡》。

06概念地图·分布面：主从、哨兵、集群分片

单机撑不住可用性与数据量时，Redis 给了三层递进的方案，官方统称里它们是叠加关系而非三选一：

  • 主从复制（replication）：副本（replica）用一行 replicaof 主节点 端口 挂到主节点下，持续接收主节点的写命令流，默认异步复制——主节点不等副本确认就回客户端，低延迟但故障切换时可能丢最后一点写入。断线重连先尝试部分重同步（只补断连期间缺的命令流），补不上才全量同步（主节点生成 RDB 发过去再续命令流）；
  • 哨兵（Sentinel）：一组独立进程（至少三个，互为多数派）盯着主从，官方列的四件事：监控主从健康、通知运维或程序、主挂了挑一个副本自动故障转移升主、充当客户端的配置提供者（问它"当前主节点是谁"）。多个哨兵对故障达成一致才行动，避免单点误判；
  • 集群（Cluster）：数据量大到一台装不下时用。数据按哈希槽分片：每个键属于 16384 个槽之一（CRC16 对键取模），槽分给多个主节点，每个主节点再挂副本。客户端访问错节点会被重定向到对的节点。

三者选型与脑裂、数据丢失窗口的分析见：官方文档 · 《Redis 集群方案：哨兵 vs Cluster》；本期只立住"主从管复制、哨兵管高可用、集群管分片"这根总纲。

07钩子一："单线程"的准确口径

每秒处理上百万次操作的引擎竟是"单线程"——这句流传最广的话，官方文档给过精确表述（《Redis benchmark》原文）："Redis is, mostly, a single-threaded server from the POV of commands execution"——从命令执行的视角看，Redis 大多是单线程的。整条命令链里只有"执行"这一环是串行的：

  • 执行串行的收益：所有命令逐条跑，没有锁、没有竞态，INCR 天然原子——快的前提是操作全在内存（微秒级），串行成本可以忽略；
  • 6.0 起 IO 可多线程：网络读写与协议解析从主线程拆了出去。官方 redis.conf 注释原话：开启 IO 线程后"不仅写回用线程，读取与协议解析也用线程"。8.0 把 IO 线程重新实现，吞吐进一步提升；
  • 要多核怎么办：官方口径是一台机器起多个实例横向扩展，而不是指望单实例吃满多核；
  • 代价：一条慢命令（如超大集合的全量遍历）会阻塞后面所有命令——延迟排查先查慢查询，见 官方文档 · 《Redis 性能调优》。

所以准确说法是：命令执行单线程，IO 读写与解析可多线程，后台任务（持久化、过期抽查、AOF 落盘）各有线程或子进程。"Redis 是单线程的"这句话省略的主语，正是理解它并发模型的关键。

10随堂小测

1. "Redis 是单线程的"——按官方口径，缺的主语是什么？

  • 整个 redis-server 进程只有一个线程
  • 命令执行在单线程里串行
  • Redis 无法利用任何多核 CPU

2. 一个带 TTL 的键过期后仍能被 GET 到，最可能的原因是？

  • 它是从副本上读到的，副本永不删键
  • 内存淘汰策略把它保护了起来
  • 惰性删除要等访问，主动抽查还没扫到它

3. 关于 RDB 与 AOF 的取舍，哪个说法符合官方文档？

  • 两者可以同开，重启重建数据时 AOF 优先
  • AOF 开了 everysec 就一条都不会丢
  • AOF 靠 fork 子进程加写时复制落盘

4. 主从、哨兵、集群三层各自管的活，哪个对应关系是对的？

  • 主从管分片，哨兵管分片调度，集群管监控
  • 主从自带自动故障转移，不需要哨兵
  • 主从管复制，哨兵管高可用，集群管分片

11思考题（点击展开解析）

思考一：把过期删除设计成"定时器精确到点删除"不行吗？为什么 Redis 宁可选"惰性 + 随机抽查"这种看起来不精确的组合？

先算定时器方案的账。若每个带 TTL 的键挂一个精确定时器，百万级带过期键的实例就要维护百万个定时事件：事件表本身吃内存，事件循环每次要处理大量到点回调，CPU 在键稀疏过期时大量空转、在键密集过期时集中抖动——而绝大多数业务根本不需要毫秒级精确的过期，会话晚删几秒没有业务后果。再看 Redis 的组合怎么覆盖两类极端：惰性删除保证"只要有人访问，过期键立刻不可见"，把删除成本摊到访问路径上；主动抽查用固定频率的少量随机采样兜住"再也没人访问"的键，让过期键总量收敛——官方文档的描述是周期性地在带过期键中随机测试一批、删掉其中已过期的。两头都有残余误差：惰性路径下没人访问的键会短暂滞留（但主动抽查在收敛），抽查路径下单次扫描不完（但下个周期继续）。这是典型的"用可接受的近似，换掉不可接受的成本"——与近似 LRU 不维护全局链表是同一个设计哲学，第 5 期读 expire.c 源码时你会看到这套抽查的具体实现。反例也要会认：秒级精确过期的场景（如限流窗口）不该依赖"到点即删"，该按"逻辑过期 + 业务判断"或用有序集合按时间戳扫描来设计。

思考二：主从复制是异步的，哨兵故障切换时"最后一条写命令"可能还没到副本就被提升为新主。单靠 Redis 自身能把这个丢失窗口收窄到什么程度？

先承认上限：官方文档明确说异步复制下无法保证已确认写入在故障切换后一定存活，WAIT 命令也只是降低概率而非提供强一致。但 Redis 给了三道收窄窗口的闸门，思路都是"把不可控的丢数窗口变成有界的"。第一道，min-replicas-to-write + min-replicas-max-lag：主节点发现可用副本数不足、或副本确认滞后超过阈值就拒绝写入——宁可短暂不可写，也不给"孤立主"继续收写的窗口，哨兵文档的网络分区案例用的正是它。第二道，哨兵选副本升主时按"优先级 → 复制偏移量"排序，偏移量大者胜——优先挑数据最全的副本，天然减少被丢弃的命令量。第三道，部分重同步（PSYNC）让切换后旧主降级重连时只补差异，缩短数据再收敛的时间。三道闸门叠完，窗口从"无限"变成"最多若干秒的确认滞后"，代价是可用性轻微下降——这正是哨兵文档说的 trade off。想彻底消除窗口只有两条路：同步复制（性能代价，Redis 不做）或外部共识层（代价更高）。架构师的判断点不是"能不能丢"，而是这个业务的写入能接受几秒的有界丢失，再决定闸门开多大。

12本期要点与下期预告

带走这五句话：

  • 术语分两层：命令面六大类型各带一族原子命令；实现面编码（SDS/listpack/intset/skiplist 等）只点名，第 5 期展开；
  • 键的生命周期：过期删除是惰性 + 主动抽查，淘汰是 maxmemory 触顶后按十种策略驱逐（8.6 起新增 LRM 族），LRU/LFU 都是近似算法；
  • 持久化两制式：RDB 是 fork 子进程做的时间点快照，AOF 是可回放的写命令日志（默认每秒 fsync、自动重写），官方建议两者同开；
  • 复制三件套：主从管异步复制与命令流，哨兵管监控/通知/故障转移/配置提供者，集群按 16384 个哈希槽分片；
  • 单线程的准确口径：命令执行单线程串行，IO 读写与协议解析 6.0 起可多线程，8.0 重写加强，多核靠多实例。
