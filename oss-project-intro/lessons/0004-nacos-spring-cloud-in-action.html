OSS PROJECT INTRO · Nacos 系列第 4 期：实战场景

把 stock-service 接进 Nacos：注册、按名调用、热更新、优雅下线

前三期你已经知道 Nacos 是什么、能把它跑起来、也拿到了它的概念地图——但都是隔着 curl 看的。这一期换真枪实弹：用 Spring Cloud Alibaba 把一个真实的 Spring Boot 服务接进来。主角是"下单扣库存"的最小系统：库存服务 stock-service 部署两个实例，同时吃 Nacos 的注册与配置两碗饭；订单服务 order-service 只凭服务名调用它。注册可见、按名调用、配置热更新、权重摘流量，四件事端到端走完——走完你会发现自己前几期学的每个概念都长在了配置文件的某一行上。

🧩 注册/配置中心 · Java · Apache-2.0 📦 基于 Nacos v3.x + Spring Boot 3.x / SCA 2023.x 📅 2026-09-18 · 第 4 期 ⏱ 预计阅读 18 分钟

01场景设定：一个最小的"下单扣库存"

场景刻意选小，但五脏俱全：stock-service（库存服务）部署两个实例（8081、8082），启动后注册进 Nacos，业务参数从 Nacos 的配置中心读；order-service（订单服务）自己不碰库存数据，只通过服务名调 stock-service。整条链路如下图，右上的控制台是你全程的"驾驶舱"（8080，别忘了第 2 期它已经搬家）：

全程四条目标，做完一条勾一条，缺一条都算没接通：

  • ① 注册可见：两个实例出现在控制台服务列表，健康、权重、元数据对得上；
  • ② 按名调用：order-service 连续下单，流量轮询落到 8081/8082 两个实例；
  • ③ 配置热更新：控制台改一个参数并发布，两个实例不重启读到新值；
  • ④ 权重摘流量：把 8081 权重调成 0，新流量全部导向 8082。

02依赖与配置：两个 starter + 一份 yaml

Spring Cloud Alibaba（SCA）把 Nacos 能力封成了两个 starter，注册发现与配置各管一个，stock-service 两个都要：

<!-- 服务注册与发现 -->
<dependency>
  <groupId>com.alibaba.cloud</groupId>
  <artifactId>spring-cloud-starter-alibaba-nacos-discovery</artifactId>
</dependency>
<!-- 配置中心 -->
<dependency>
  <groupId>com.alibaba.cloud</groupId>
  <artifactId>spring-cloud-starter-alibaba-nacos-config</artifactId>
</dependency>

版本号不在依赖里写死，交给 dependencyManagement 中的 SCA BOM 统一管（本系列按 SCA 2023.x，对应 Spring Boot 3.x / Spring Cloud 2023.x）。SCA 各版本与 Spring Boot/Cloud 的对应关系每版都会调整，以你所用 SCA 版本的官方版本文档为准，不要抄旧教程里的组合。

接下来是本期最重要的一个文件——src/main/resources/application.yaml，完整可抄：

spring:
  application:
    name: stock-service            # 服务名：注册进电话簿的“名字”，也是 DataId 的前缀
  config:
    import:
      - optional:nacos:stock-service.yaml   # Boot 3.x 接 Nacos 配置的正统写法，DataId 直接写明
  cloud:
    nacos:
      server-addr: 127.0.0.1:8848  # 主端口；SDK 的数据通道实际走 9848 gRPC（第 2 期端口账本）
      username: nacos
      password: 你的控制台密码      # 3.x 默认开鉴权，客户端不带凭证会被拒（见第 2 期）
      discovery:
        namespace: 6d3f1a2e-xxxx   # 命名空间 ID（不是名字！）；不配则落 public
        group: TRADE_GROUP         # 服务分组：库存类服务都归这组，默认 DEFAULT_GROUP
      config:
        namespace: 6d3f1a2e-xxxx   # 注意：与 discovery 分开配置，只配一处是经典串坑
        file-extension: yaml       # DataId 约定：服务名.扩展名 → stock-service.yaml
server:
  port: 8081

五个关键点，每个都对应前几期的一个概念：

  • 服务名是一切的锚点：注册进电话簿的条目、配置 DataId 的前缀、Feign 调用写的名字，三处共用 spring.application.name——起名要像变量名一样认真。
  • spring.config.import 是 Boot 3.x 的正统：Boot 3 默认不再加载老教程里的 bootstrap.yaml（想沿用得额外引 spring-cloud-starter-bootstrap，以版本文档为准）；optional: 前缀表示 Nacos 拉不到时用本地默认值继续启动，别让配置中心一抖全公司起不来。
  • DataId 约定：不显式写 DataId 时，按 服务名.扩展名 推导——file-extension 默认是 properties，配成 yaml 才有上面的 stock-service.yaml。import 里写明 DataId 的，以写明的为准。
  • namespace 填 ID 不填名字：控制台建命名空间生成的是一串 ID（第 3 期讲过的硬隔离层），yaml 里填名字不生效，是新手高频翻车点。
  • discovery 与 config 的 namespace/group 各配各的：本文刻意让服务注册进 TRADE_GROUP、配置落默认 DEFAULT_GROUP——两套坐标互不相干，漏配哪处哪处就悄悄掉回 public/DEFAULT_GROUP。

03注册与核对：启动即注册，控制台对账

近年版本的 SCA 里，引入 discovery starter 后注册是自动行为——不用在启动类上标任何注解，应用起来就会把自己挂上电话簿。两个实例同 jar 起两份，只差端口：

# 实例一：按 application.yaml 默认启动（8081）
java -jar stock-service.jar

# 实例二：命令行只覆盖端口，其余配置完全相同（8082）
java -jar stock-service.jar --server.port=8082

启动日志里搜 register finished 字样（不同版本措辞略有差异），看到服务名带上自己的 IP:端口即注册成功。然后开控制台对账（http://127.0.0.1:8080，服务管理 → 服务列表）：切到 dev 命名空间，出现 stock-service，组 TRADE_GROUP，实例数 2。点进详情逐项核对——这正是第 3 期概念的实物对照：

  • 健康状态：两个实例都是健康（临时实例靠心跳续约，停跳才掉线）；
  • 权重：都是默认 1.0，第 06 节要在它身上做文章；
  • 元数据：能查到实例自报的版本、机房类标签（metadata），订阅方按需读取。

顺手做一个行为差异实验，体会临时实例的"活法"：直接 kill -9 掉 8082 的进程（模拟宕机，不给任何善后机会），控制台十几秒内把它标为不健康、随后摘除——心跳默认 5 秒一发，失联后先标记再剔除，这正是第 3 期"电话簿自愈"的现场版。重新拉起进程，实例又自己回来了：注册这事的正确心智是报户口，不是办户口——实例自己上门，服务端只管记账。

04配置接入与热更新：改值、发布、不重启

第 02 节的 import 已经把 stock-service.yaml（DEFAULT_GROUP）接了进来，现在去控制台把这条配置真的建出来：配置管理 → 配置列表 → 创建，DataId 填 stock-service.yaml，Group 用默认 DEFAULT_GROUP，格式 YAML，内容先放两个业务参数：

stock:
  deduct:
    mode: batch          # 扣减模式：single 逐件 / batch 批量
    lock-seconds: 30     # 库存锁定秒数

发布后重启两个实例（此刻还没有热更新需求，正常启动加载即可），代码里这样消费：

@RestController
@RefreshScope                            // 关键注解：没有它，@Value 只在启动时读一次
public class StockConfigController {

    @Value("${stock.deduct.lock-seconds:30}")   // 冒号后是本地兜底默认值
    private int lockSeconds;

    @GetMapping("/stock/config")
    public Map<String, Object> current() {
        return Map.of("lockSeconds", lockSeconds);
    }
}

验证热更新三步走：先 curl http://127.0.0.1:8081/stock/config 得到 30；控制台把 lock-seconds 改成 60 点发布；再 curl 一次（以及 8082 那份）——不重启，读到 60。改动到达是推送而非轮询：gRPC 长连接毫秒级送达（第 3 期讲过的通道升级），应用日志里能看到配置变更记录。窗口里的另两个实用件：每次发布自动留历史版本可一键回滚；发布前可选 Beta 灰度（先推给指定 IP 验证再全量），上一期概念篇都点过名，这里不展开。

本节唯一的坑：只写 @Value 忘了 @RefreshScope，热更新静默失效——值永远停在启动时读的那份，接口表现"改了没反应"。判断方法就一步：curl 拿到的还是旧值时，先查这个注解，再查是不是改错了 DataId/Group。

05按服务名调用：OpenFeign + LoadBalancer

轮到 order-service。它引同样的 nacos-discovery starter（配置只把 spring.application.name 换成 order-service，namespace/group 保持与 stock 一致，否则互相看不见），再加 OpenFeign 的 starter（spring-cloud-starter-openfeign），启动类标 @EnableFeignClients。调用代码总共一个接口：

@FeignClient(name = "stock-service")     // 只写服务名，没有 IP、没有端口
public interface StockClient {
    @GetMapping("/stock/deduct")
    String deduct(@RequestParam("sku") String sku);
}

@RestController
public class OrderController {
    private final StockClient stockClient;
    public OrderController(StockClient stockClient) { this.stockClient = stockClient; }

    @PostMapping("/order")
    public String create(@RequestParam("sku") String sku) {
        return "下单成功，库存侧返回：" + stockClient.deduct(sku);
    }
}

stock 侧让接口返回自己的端口，方便肉眼核对流量去向：

@GetMapping("/stock/deduct")
public String deduct(@RequestParam String sku) {
    log.info("扣减 {}，本实例端口 {}", sku, port);   // port 由 @Value("${server.port}") 注入
    return "ok-" + port;
}

order-service 自身端口按 8090 起（server.port: 8090），然后连续 curl -X POST "http://127.0.0.1:8090/order?sku=A001" 若干次，返回在 ok-8081 与 ok-8082 之间交替，两边的 stock 日志也各有一半扣减记录——目标②达成。幕后分工：Feign 只负责"把方法调用变成 HTTP 请求"，请求发给谁由负载均衡器从服务表里挑，SCA 2023.x 默认用 spring-cloud-loadbalancer（轮询策略）——Ribbon 是 Spring Cloud 2020 之前的旧话，老教程里"default ribbon"的说法直接跳过，别再往 pom 里塞它。另注意：order 侧拿到的实例列表同样来自订阅推送，本地有缓存兜底（第 3 期容灾三件套），所以 Nacos 短暂抖动不至于打断存量调用。

06优雅下线与权重：把 8081 摘出流量

最后一个动作，也是这套路子在生产里最日常的用法。控制台 → stock-service 详情 → 编辑 8081 实例，把权重从 1.0 改成 0，保存。保持下单流量不停，观察返回值：几秒内全部变成 ok-8082——权重 0 表示"不再分新流量"，但实例还健康地活在列表里，随时可以恢复。这个秒级的生效速度靠的是订阅推送，不是轮询。

这个开关的两类现实用法：

  • 滚动发布：发布 stock-service 新版本时，先把实例一的权重调 0 → 确认流量干净地全在实例二 → 停实例一、换包、启动 → 权重调回 → 对实例二如法炮制。全程在途请求不被切断，"先摘流量再动进程"就是"优雅"二字的全部含义；
  • 紧急摘流量：某实例行为异常（内存泄漏、响应变慢）时，先权重调 0 把它隔离出现场再慢慢排查——比直接 kill 温柔得多，kill 掉临时实例虽会自动摘除，但那有十几秒的心跳超时窗口，窗口内的新请求仍可能砸向尸体。

收尾别忘：权重 0 只是"暂停营业"不是"注销"，实验做完记得把 8081 调回 1.0，否则下次压测你会困惑为什么一台机器闲着。四条目标此刻应该全部打勾——这四步合起来，就是绝大多数团队用 Nacos 的日常全景。

07随堂小测

每题点击选项立即反馈 · 共 3 题

1. 把 stock-service 注册进 Nacos，下面哪一步是【不需要】的？

  • 在控制台服务列表里手动"添加实例"、填 IP 和端口
  • pom 引入 spring-cloud-starter-alibaba-nacos-discovery
  • 配置 spring.cloud.nacos.server-addr 指向服务端

2. 控制台改了 lock-seconds 并发布，想让 @Value 注入的值不重启就生效，必须配合什么？

  • 给持有该 @Value 的 Bean 加 @RefreshScope
  • 给配置字段加 volatile 关键字
  • 没有办法，@Value 的值只能重启刷新

3. dev 与 prod 的服务要彻底互不可见，用第 3 期三层坐标的哪一层隔离？

  • Group——把环境写进分组名
  • Namespace——硬隔离层，配错的那个环境连"看见"都看不见
  • 给服务名加 dev- / prod- 前缀

08思考题（点击展开解析）

思考一：@RefreshScope 的热更新有边界——为什么数据库连接池、线程池这类资源改了配置不会自动跟着变？怎么处理？

原理先说透：@RefreshScope 的实现是代理刷新。容器给带该注解的 bean 生成一个代理，配置变更事件到达时并不"原地改字段"，而是把代理背后的目标实例作废，下次请求再访问代理时重新创建一个 bean、用新值完成注入——所以它刷得动的是"每次被调用时才取值"的东西，比如我们那个每次请求都读 lockSeconds 的 Controller。而连接池、线程池是启动期一次性装配的资源：池子在某个 bean 的构造/初始化阶段就按当时的配置把连接、线程建好了，之后字段哪怕被新值覆盖，已建好的池子也不会自己伸缩——好比把菜单上的价格改了，厨房里按旧菜单备好的菜不会消失。处理方式按需求选三档：一，把可热更项收敛为"用值时才生效"的参数（每次请求重读，@Value 或 @ConfigurationProperties 都行），池类参数不进热更清单；二，确实要跟随变更的资源，监听刷新事件（如 EnvironmentChangeEvent）自行销毁重建池——要自己处理并发使用中的旧池优雅排空，成本不低；三，最朴素的工程答案：池类配置改动就走第 06 节的权重摘流量 + 滚动重启，用发布流程换确定性。另附一个易踩的边角：RefreshScope 刷新瞬间旧 bean 被作废重建，有状态的 bean（持有用户会话、缓存）别放进 RefreshScope，刷新即失忆。

思考二：多环境隔离，Namespace 与 Group 各该承担什么？混用会踩什么坑？

第 3 期给过定性：namespace 硬隔离、group 软分组。落到实战，分工应该是一句话：环境用 namespace，业务域用 group。namespace 强在"隔离是结构性的"：dev 与 prod 各自独立 ID，互相连列举都做不到；3.x 的权限体系还能把账号的可见/可操作范围绑到 namespace 上——开发账号碰不到 prod 的服务与配置，误操作的能量从根上被限住。group 弱在"只是名字里多了一段前缀"：同 namespace 内按组寻址、避免不同业务同名服务打架，够用，但没有权限语义，隔而不离。混用的大坑是拿 group 冒充环境隔离：图省事全公司共用 public namespace，用 TRADE_GROUP_PROD、TRADE_GROUP_DEV 分环境——某台开发机上的配置漏写 group（默认落 DEFAULT_GROUP）或写错组，它的服务就可能注册进"生产组"；prod 的消费者按服务名订阅时把这台开发机一并拉进服务表，流量就真的打到开发者的笔记本上了——同名服务跨环境串流量，这是有真实事故样本的经典模式，而且静默：没有任何报错，只是"生产偶发诡异"。辅助坑同样值得记：discovery 与 config 的 namespace 是分开配置的，只改了一处另一处还留在旧环境，服务注册进了 dev、配置却读着 prod，行为立刻精神分裂。所以团队规约应该写死：环境切换只允许出现在 namespace 一处，group 只表达业务语义——一个维度只干一件事，出问题时排查路径才是唯一的。

09本期要点与下期预告

带走这四句：

  • 注册是 starter 的自动行为：依赖 + server-addr（3.x 记得带鉴权凭证）即报上户口，控制台手动加实例是给无 SDK 场景留的后门；
  • Boot 3.x 用 spring.config.import 接配置，DataId 约定"服务名.扩展名"；热更新 = @RefreshScope + gRPC 推送，缺注解则静默失效；
  • 按名调用：@FeignClient 写服务名，挑实例交给 Spring Cloud LoadBalancer——Ribbon 是历史，老教程的说法别再抄；
  • 权重调 0 = 摘流量不动进程：滚动发布与紧急止损的标准动作，秒级生效，做完记得改回。
