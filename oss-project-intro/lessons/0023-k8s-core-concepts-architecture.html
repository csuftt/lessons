OSS PROJECT INTRO · KUBERNETES 系列第 3 期：核心概念与整体架构

Kubernetes 核心概念与整体架构：声明式 API、控制平面与一次部署的旅程

上一期我们用 minikube 起了本地集群，部署了第一个工作负载：一条 create 命令，Pod 自己出现了。但"自己出现"这件事，命令行一个字都没解释——谁看到了你的声明、谁决定 Pod 落在哪、账记在哪。这一期把 K8s 的户口本翻开：术语体系按抽象层级串成一条线（Pod、ReplicaSet、Deployment、Service，用进程、线程池、发版、总机来类比）；期望状态 vs 实际状态与声明式 API 的真正含义；控制平面五个组件与节点侧三个组件各自干什么；一张自绘架构图看懂一次部署从 kubectl apply 到容器运行的全部走向，再打开源码仓库把顶层模块一一对号入座。全文基于 v1.37.x（1.37.0，2026-08-26 发布，GitHub Latest，2026-09-19 复核），概念表述逐条对照 kubernetes.io 官方文档。

01上一期那条命令，背后站着一整个控制平面

第 2 期我们跑通三条判定：minikube status 三行 Running、kubectl get pods 看到 1/1 Running、浏览器里看到应用响应。回头看那条部署命令：kubectl create deployment hello-node——只说了一句"要一个叫 hello-node 的 Deployment"，没人登录任何机器手动起容器，Pod 就自己出现了。谁读到了这句话？谁把它记下来？谁照着它干活？

答案是：这不是命令，是一份期望状态的声明，集群里站着一整个控制平面在消费它。读懂它只要两组词汇：一组描述"你声明什么"——对象体系与声明式 API；一组描述"谁来干活"——控制平面与节点组件。先发名片架，再上架构图对号入座。

02术语体系：按抽象层级串起来，不背名词

K8s 的对象名词少说几十个，但入门只需要抓一条主线：Deployment 管 ReplicaSet，ReplicaSet 管 Pod，Service 把一组 Pod 包装成稳定入口——一层套一层，每层只干一件事。四个核心对象配类比：

① Pod——最小调度单元，像"进程组"

一句话定义：一个或多个容器的组合，共享网络与存储，同生共死，是集群调度的最小单位。

  • 类比操作系统：容器是线程，Pod 是进程组——主容器加边车容器共用一个网络命名空间；
  • Pod 是"牲口不是宠物"：被删了不复活，由上一层对象重新生一个新的；第 2 期看到的 hello-node-5f76cf6ccf-br9b5 就是一个 Pod 的全名。

② ReplicaSet——副本保活员，像"线程池"

一句话定义：维持指定数量的 Pod 副本时刻在线：少了补、多了删。

  • 类比线程池保活：核心线程数设为 3，挂一个补一个——只认"数量"，不关心版本怎么换；
  • 靠标签选择器认领 Pod，靠属主引用（ownerReferences）挂在 Deployment 名下——第 05 节演示链亲眼看这条链；日常几乎不直接操作它。

③ Deployment——发版管理员，管版本与滚动

一句话定义：声明 Pod 模板与副本数的期望状态，负责滚动更新、回滚与扩缩。

  • 类比发版系统：你只提交新版本声明，它控制新旧 ReplicaSet 此消彼长，滚动着换流量；
  • 改镜像不是改 Pod，而是生成新的 ReplicaSet——get rs 里每代哈希就是一次发版存档；
  • 副本数随负载自动伸缩是另一套机制，用法见 官方文档 · Horizontal Pod Autoscaler。

④ Service——稳定前台总机，像"域名 + 负载均衡"

一句话定义：给一组 Pod 提供固定访问入口（虚拟 IP 与 DNS 名），Pod 换了一茬照样找得到。

  • Pod 会死会换、IP 随机分配——Service 用标签选择器圈住一组 Pod，入口地址却不变，类比公司前台总机：员工工位天天换，总机号码不变；
  • 第 2 期那个 EXTERNAL-IP <pending> 只是入口体系的最小演示，生产级流量入口（Ingress、Gateway API）见 官方文档 · Ingress。

边界说明各对象的 YAML 用法与日常排障不在本期展开，需要时看上面两处延伸阅读；本期只回答"这些对象是什么、谁在背后驱动它们"。

03期望状态 vs 实际状态：声明式 API 的真正含义

上一期的心智模型是"你声明期望状态，控制器把现实拉过去"。落到对象上，就是每个 K8s 对象几乎都有的两个嵌套字段。官方 working-with-objects 文档原话：spec 由你提供，是"期望状态的描述"；status 由系统及其组件提供并更新，描述"对象的当前状态"，而控制平面"持续且主动地管理每个对象的实际状态，使其匹配你提供的期望状态"。

字段谁写装什么一句话理解
spec用户（你）要几个副本、用什么镜像、暴露哪个端口期望状态——你说了算的唯一一份
status系统（控制器）现在几个就绪、更新到第几代实际状态——只能读，别手改

官方给 K8s 对象的定义是 "record of intent"（意图记录）——对象一旦创建，系统会持续工作确保它存在。声明式的完整含义在 kubectl apply 里：官方 object-management 文档把对象管理分成三种——命令式命令（直接操作活动对象，适合入门）、命令式对象配置（kubectl create -f 单文件全量定义）、声明式对象配置（kubectl apply -f 目录，增删改由 kubectl 逐对象自动判定，还能保留其他人的直接改动）。生产推荐第三种，官方同时警告：同一对象只用一种方式管理，混用会导致未定义行为。API 侧，对象按 API 组与版本暴露在 /api/v1、/apis/apps/v1 这样的路径上，apiVersion 与 kind 正是 YAML 头两行的来历；序列化的对象状态写入 etcd 持久化——etcd 就是这本总账，是集群唯一可信的状态存储。

04控制平面与节点组件：一张架构图看懂一次部署

概念有了承重墙，现在看房子。官方 components 文档把组件分两拨：控制平面组件管理集群的整体状态，节点组件运行在每个节点上、维持运行中的 Pod 并提供运行时环境。每个组件一句话：

组件位置一句话职责（对照官方文档）
kube-apiserver控制平面暴露 Kubernetes HTTP API 的核心组件服务器——所有读写的唯一入口
etcd控制平面为所有 API 服务器数据提供一致且高可用的键值存储——集群总账本
kube-scheduler控制平面寻找尚未绑定节点的 Pod，为每个 Pod 分配合适的节点（过滤 + 打分，第 5 期展开）
kube-controller-manager控制平面运行控制器以实现 Kubernetes API 行为——Deployment、ReplicaSet 等对账循环的合集
cloud-controller-manager（可选）控制平面与底层云提供商集成：负载均衡器、挂载盘、节点地址这些"云上的事"
kubelet每个节点确保 Pod 及其容器处于运行状态——节点上照看容器的人
kube-proxy（可选）每个节点在节点上维护网络规则以实现 Service——流量怎么转发的执行者
容器运行时每个节点负责运行容器的软件（containerd 等，官方标注为第三方项目）

一次部署的完整旅程，顺着实线走：① kubectl apply 把声明交给 apiserver → 认证、鉴权、准入后写进 etcd 落账 → ② Deployment 控制器 watch 到新对象创建 ReplicaSet，ReplicaSet 控制器创建 Pod（此刻还没节点，处于 Pending）→ ③ kube-scheduler 为每个 Pod 过滤打分、绑定结果写回 apiserver → kubelet watch 到"本节点有新 Pod"，④ 调用容器运行时拉镜像、起容器 → ⑤ kubelet 持续回报状态，status 更新为 Running。第 2 期那个"自己出现"的 Pod，就是这条流水线的终点。

钩子一：为什么一切读写都要过 apiserver 这道门？

反着想：如果控制器与客户端都直连 etcd 会怎样？认证、鉴权、准入三道安检没了集中执行的地方；并发写入没有乐观并发控制（resourceVersion 比对）兜底，互相覆盖；watch 广播要每个客户端自己造轮子；存储演进也没了转换层。把门收拢到一处，换来：策略一处生效、冲突一处裁决、事件一处广播、审计一处留痕。apiserver 无状态、可水平扩，真正的状态瓶颈在 etcd——这道"门"不是设计失误，而是把复杂性换成可控性的关键取舍。

钩子二：组件挂了会发生什么？

看三个典型故障：kube-scheduler 挂——新 Pod 没人分派节点、卡 Pending，已在跑的容器照常服务；某个 kubelet 挂——该节点 Pod 失去照看、状态不再回报，控制面把节点标 NotReady 并驱逐重建其上 Pod；apiserver 挂——大门关闭，kubectl 全部失联，但节点上的 kubelet 与运行时还在照看既有容器，业务照跑。这正是声明式架构的底气：数据面与控制面分离，控制面短暂失能不打断业务，恢复后一切向期望状态对齐。

05打开仓库：顶层模块地图

Kubernetes 是单体大仓库（k8s.io/kubernetes，GitHub 上 128k stars）。以主分支为据（2026-09-19 核对；阅读源码建议锁定 tag v1.37.0），顶层目录一句话：

顶层目录一句话职责
cmd/每个二进制的 main 入口：kube-apiserver、kubelet、kube-proxy 等都从这编译出来
pkg/主体实现：控制平面与节点的核心逻辑（调度器、控制器、kubelet 等）都在这
staging/待拆分出去的子仓库：client-go、k8s.io/api 等从这里发布给外部使用
api/API 对象的 Go 类型与序列化定义，与 staging 中的对外仓库同步
test/e2e 与集成测试套件——读码时最好的"用法示例库"
hack/构建、代码生成与校验的开发脚本（改代码前先看这里怎么跑）
third_party/、vendor/外部依赖的 fork 与 vendored 副本
cluster/、build/集群部署脚本与构建发布流水线
plugin/、docs/、logo/插件（鉴权等）、仓库内文档与品牌资源

读码提示两个目录记优先级：cmd/ 是"哪里进"（每个组件的 main 函数），pkg/ 是"里面是什么"（控制器模式、调度器都在这）——第 5 期源码导读从这两处进门；想在 K8s API 上做开发，看 staging/ 里的 client-go。

06随堂小测

每题点击选项立即反馈 · 共 4 题

1. 对象的 spec 与 status，分别由谁写？

  • spec 系统写，status 用户写
  • 两个都是用户写，字段不同
  • spec 用户写期望，status 系统写实际

2. 一切读写都要过 kube-apiserver，最主要的原因是什么？

  • 因为 etcd 性能太弱，需要代理缓存
  • 安检与一致性策略集中一处：认证、鉴权、准入、并发控制、审计、watch 都在门口
  • 因为它是集群里唯一的负载均衡器

3. kubectl apply -f configs/ 属于官方定义的哪种管理方式？

  • 声明式对象配置
  • 命令式命令
  • 三者混用，视心情而定

4. kube-scheduler 挂掉之后，已经在运行的 Pod 会怎样？

  • 立刻全部被杀掉并重新调度
  • 照常运行；新 Pod 没人分派节点，卡在 Pending
  • 所在节点立刻被清空，Pod 全部驱逐

07思考题（点击展开解析）

思考一：如果允许控制器与客户端绕过 apiserver 直连 etcd 读写，集群会在哪些具体地方坏掉？这反过来解释了 apiserver 的哪些设计？

逐层推演。第一层安全崩塌：认证、鉴权、准入目前在 apiserver 一处集中执行，直连 etcd 意味着每个客户端都自带"内部人员"权限——RBAC 名存实亡，准入校验要么没人做、要么几十个客户端各做一遍。第二层并发崩塌：多个控制器同时改一个对象，靠的是 apiserver 的乐观并发控制——请求带着 resourceVersion，版本不对就拒绝重试；直连后这层裁决消失，丢更新、互相覆盖变成日常。第三层事件崩塌：控制器的"观察"能力来自 apiserver 的 watch 广播（带资源版本排序、断线连续传），直连则每个客户端都要自己处理 etcd 的 watch 语义与历史窗口。第四层演进崩塌：API 版本转换发生在 apiserver，存储格式想换也不惊动客户端——直连则存储 schema 被锁死。这些"坏掉的地方"逐条对应 apiserver 的设计职责：它是集群唯一的写入裁决者与事件广播者。第 5 期读控制器源码会反复看到同一个模式：控制器从不"直接改变现实"，只通过 apiserver 提交期望——那里才有并发安全。

思考二：第 2 期的 minikube 单节点"既是控制平面又是工作节点"，本期的"组件挂了会发生什么"分析还成立吗？哪些结论在沙盘里要打折扣？

逐条对账。成立的结论：组件分工与对账机制完全一致——沙盘里的 apiserver、scheduler、controller-manager、kubelet 与生产是同一批程序，演示链敲的每条命令语义不变。要打折扣的结论：其一，"apiserver 挂了数据面照跑"在沙盘里只对一半——minikube 把控制面组件跑在节点上的静态 Pod 里，apiserver 进程挂掉，kubelet 与运行时确实还在、既有容器照跑，kubectl 也确实失联；但控制面与数据面挤在同一台机器，整机故障时两者一起完蛋，而生产集群控制面独立部署（云上常为托管形态），worker 故障只影响该节点。其二，沙盘没有"调度"可言：唯一节点上 scheduler 的过滤打分基本空转。其三，容错为零：单 etcd、单 apiserver，任何控制面进程崩溃都意味着对应能力完全不可用——生产用多副本加 quorum 换容错。所以正确的读法是：沙盘练语法，故障语义按"多节点 + 控制面独立"的生产形态想象——这也是第 4 期实战交付前要建立的默认画像。

08本期要点与下期预告

带走这几条：

  • 术语一条线：Pod 是最小调度单元（进程组），ReplicaSet 保副本数（线程池），Deployment 管版本与滚动（发版管理员），Service 给稳定入口（前台总机）；
  • 声明式的含义：spec 你写期望、status 系统写实际，对象是"意图记录"，控制平面持续对账；apply 是生产姿势，同一对象别混用管理方式；
  • 控制平面五件套：apiserver 守门、etcd 落账、scheduler 派位、controller-manager 对账、cloud-controller-manager 对接云；节点侧三件套：kubelet 照看、运行时拉起、kube-proxy 通流量；
  • 一次部署的旅程：apply → 落账 etcd → 控制器接力（Deployment→ReplicaSet→Pod）→ 调度绑定 → kubelet 起容器 → 状态回报，全程没有一步靠人；
  • 仓库地图：cmd/ 是入口，pkg/ 是主体，staging/ 里是 client-go 等对外仓库，读码先锁 v1.37.0 tag。
