OSS PROJECT INTRO · ETCD 系列第 3 期：核心概念与整体架构

etcd 核心概念与整体架构：一把全局版本号、一套 Raft 术语与一条写请求的旅程

上一期我们跑通了 etcd 的第一公里：一条命令起单成员集群，put 回 OK、get 两行回显、watch 瞬间推送、lease 让键自灭，健康检查判定跑通。但回头看，那个 OK 来得并不简单——写入先在哪记账、谁点头、最后落到哪，命令行一个字都没说。这一期把 etcd 的户口本翻开：键值模型的六个核心名词配类比和一句话定义——revision、version、MVCC、watch、lease、compaction；Raft 侧的四个角色——leader、follower、learner、log；一张自绘三层架构图看懂 API 层、共识层与存储层怎么分工，顺带回答两个值得琢磨的问题——读请求凭什么可以不走共识、revision 为什么是全局单调而不是每个键各自计数。最后打开源码仓库，把顶层模块一一对号入座。全文基于 3.7.x（v3.7.1，2026-07-23 发布，2026-09-19 于 GitHub Releases 与官方文档复核），概念表述逐条对照官方 v3.7 文档。

01上一期的 OK，背后其实有一条流水线

第 2 期我们验证过三条判定：put 回 OK、get 固定两行、健康检查回显"successfully committed proposal"。其中健康检查那条已经漏了底：一次写入的真实身份是一条"提案"，要走完共识确认才算数。也就是说，那个轻描淡写的 OK 背后，etcd 内部跑完了一整条流水线：请求先变成提案、提案先记进预写日志（WAL）、多数派点头后应用到多版本存储、再顺手把变更事件推给所有订阅者。这条流水线上的每个岗位，都有一个正式名词。

用户视角的 etcd 核心词汇，说穿了就是十个小名词：键值模型侧六个——revision、version、MVCC、watch、lease、compaction；共识侧四个——leader、follower、learner、log。后面不管你用 etcd 做服务发现还是配置中心，本质都是在跟这十块积木打交道。先发名片架，再上架构图对号入座。

02键值模型六件套：类比 + 一句话定义 + 关键点

① Revision 全局版本号——整栋楼的快递流水号

一句话定义：整个键空间共用一个单调递增的计数器，官方 data model 文档原话：每次原子修改都会在键空间上"创建一个新 revision"。

  • 类比小区快递柜：出库流水号是全网一个计数器，不是每个柜格各数各的——放一件包裹，全楼的流水号一起涨；
  • 官方口径：Revisions are monotonically increasing over the lifetime of a cluster（集群存活期内单调递增）；store 从 revision 1 起步；
  • 它就是 etcd 的"全局逻辑时钟"——watch 靠它排队，历史读靠它定位，钩子二细讲。

② Version 键内版本——每个柜格自己的计数

一句话定义：单个 key 自己的修改次数，从创建那一刻起算。

  • key 的一生是一"代"（generation）：创建时 version=1，每次修改加一；
  • 删除时写一块墓碑（tombstone），当前一代终结、version 归零——下次重建又从 1 开始；
  • 注意分清：revision 回答"全库第几笔写"，version 回答"这个键第几笔写"。

③ MVCC 多版本——旧值都在，可以时间旅行

一句话定义：多版本并发控制——新值写入不覆盖旧值，旧版本保留到压缩为止，官方管查历史叫"time travel queries"。

  • 物理形态是一棵持久 B+ 树，键是 (major, sub, type) 三元组——major 就是 revision；旁边还有一颗内存 btree 索引加速按键查询；
  • 第 2 期那句"写入即存在"现在有了下半句：写入即留痕——每个历史 revision 都能原样读回；
  • 快照便宜、watch 历史事件，都吃的是"旧版本还在"这个红利。

④ Watch 订阅——按流水号排序的变更广播

一句话定义：订阅某个键或前缀，变更事件按 revision 顺序推送上门——第 2 期亲眼看过的那一幕。

  • 官方 data model 的原话是"ranging over revisions with watchers is efficient"——watch 直接复用全局 revision 这把尺子；
  • 事件里带着事件发生的 revision，消费端能对齐顺序、不重不漏；
  • 配置下发、服务目录同步，底层都是这一条订阅通道。

⑤ Lease 租约——一组键共享的 TTL 倒计时

一句话定义：先申请一个带 TTL 的租约，把一批键挂上去；到期或主动撤销，整组键一起自动删除。

  • 客户端用 lease keep-alive 持续续期——人还在，租约就在；掉线了，键跟着租约一起消失；
  • 节点存活检测、临时注册（第 4 期服务发现的底座）都长在这套机制上；
  • 拿它做分布式锁的原理对照，见官方文档 · Redis 分布式锁。

⑥ Compaction 压缩与 Snapshot 快照——房间的断舍离

一句话定义：compaction 把指定 revision 之前的旧版本清掉；snapshot 是定期的全量快照文件。

  • 多版本不是免费午餐：etcdctl compact 5 之后，读 revision 4 及更早的请求直接报错（第 05 节演示）；
  • 官方存储文件文档：快照大约每 --snapshot-count 次（默认 100'000）已应用提案落一份；
  • 不压缩，数据只增不减——生产上这是一个需要规划的例行运维项。

版本备注以上术语与官方表述已对照 etcd v3.7 文档 Data model / API guarantees / Persistent storage files / etcd API 各页核对（2026-09-19）。版本基线：当前 GA 稳定线 v3.7.1（2026-07-23 发布，GitHub Releases 标 Latest），3.6 与 3.5 线并行维护。

03Raft 侧四个角色：一场永不散会的班委会

共识层的词汇可以类比一场班委会：leader 是主持例会的班长，follower 是参与表决的班委，learner 是只听不投的旁听生，log 是一本会期连着会期的会议纪要。四个角色各一句话：

角色类比一句话职责
Leader 领导者班长任期（term）内主持一切写入：把请求变成提案，安排日志复制
Follower 跟随者班委接收 leader 复制来的日志，参与投票表决；leader 掉线时参与竞选
Learner 学习者旁听生官方 learner 设计文档：以非投票成员身份入群，先追平 leader 日志，再由 member promote 转正——新成员不再拖累法定人数
Log 日志会议纪要每条写请求先成为一条日志；复制到多数派才算提交，然后应用到状态机

读码提示Raft 的工程实现已拆成独立仓库 etcd-io/raft（module 路径 go.etcd.io/raft/v3），etcd 主仓库按模块引用。官方 README 里列着同一批使用方：etcd、Kubernetes、Docker Swarm、CockroachDB、TiDB——一份班委手册，好几家学校在用。它只管算法本身，网络收发和落盘由使用方自己接。

04整体架构：三层楼，一条写请求的旅程

十块积木拼上三层楼，就是 etcd 的全景。读图三句话：API 层只管接待，共识层管点头，存储层管记账与落库。实线是写请求的路径，虚线是变更事件的回推。

顺着实线把一条写请求走完：客户端 put 打到 2379 的 gRPC KV 服务 → leader 把请求包成一条 Raft 提案、追加进 WAL → 复制给 follower，凑够多数派确认 → 已提交的日志应用到状态机：全局 revision 加一、改动写进 MVCC B+ 树 → 回给客户端那个 OK → watch 订阅者按 revision 顺序收到变更事件。崩溃恢复也在这张图里：状态机靠重放 WAL 补账，快照把重放的起点往前挪——这就是"先记账再落库"的完整含义。

钩子一：读请求为什么可以不走共识？

官方 API guarantees 文档给了两条路：线性一致读（默认）必须经过 Raft 共识流程，读之前先确认自己还握着最新状态，代价是多一轮协商；serializable 读则由成员本地直接应答，不需要跟其他节点达成共识——可能读到相对过时的数据，换来的是更低延迟与更高吞吐（官方 API 参考对 Range 的描述：linearizable by default，higher latency and lower throughput）。命令行上就是 etcdctl get 键 --consistency=s。监控巡检、大盘展示这类"读个大概"的场景可以走右边省成本；配置读取这种"差一个版本就出错"的场景，别省。

钩子二：revision 为什么是全局单调，而不是每个键各计各的？

反着想：如果版本号 per-key，watch 就没有一条统一的时间线给所有事件排队——你订阅一组前缀，事件之间比不出先后；事务（txn）也无法原子地领到"这一笔写"的全局序号。官方 data model 的设计是：每次原子修改创建一个新 revision，全库共用——watch 复用这把尺子（ranging over revisions with watchers is efficient），历史读用 --rev 直达任意时刻，压缩（compact）也才有单一的"清到第几号"的口径。一把全局刻度尺，换来的是全系统对"先后"的零争议——第 05 节的演示链会让你亲眼看到：改另一个键，你的 revision 也会涨。

05打开仓库：顶层模块地图

概念清楚了，再看源码仓库就不慌。以 GitHub 上 etcd-io/etcd 主分支（go.work 所列模块，2026-09-19 核对；阅读源码建议锁定 tag v3.7.1）为准，常用模块一句话：

顶层模块一句话职责
api/gRPC API 与 protobuf 定义：KV/Watch/Lease/Auth/Cluster/Maintenance 六个服务的接口契约
server/服务端主体：etcdserver（Raft 集成、请求处理）与 storage/（WAL、MVCC 后端）都在这
client/客户端库：clientv3（v3 gRPC 客户端）与共享的 transport 等基础包
etcdctl/命令行客户端——第 2 期敲的 put/get/watch/lease 命令的真身
etcdutl/运维工具：快照恢复、备份、碎片整理（3.5 起从 etcdctl 拆出）
pkg/各模块共用的基础工具包（transport、wait、schedule 等）
cache/实验性的客户端缓存库：本地缓存 + watch 保持一致（v3.7 时代的新成员）
tests/集成与 e2e 测试套件——读码时最好的"用法示例库"
tools/benchmark 压测等辅助工具
raft/（独立仓库）Raft 算法本体在 etcd-io/raft（go.etcd.io/raft/v3），主仓库按模块引用——见第 03 节

读码提示三个模块记优先级：server/etcdserver 是请求进共识层的入口，server/storage 是 MVCC 与 WAL 的家，api/ 是所有接口的契约——第 5 期源码导读（MVCC、watch 与 lease 的设计决策）就从这三个进门。

06随堂小测

每题点击选项立即反馈 · 共 4 题

1. etcd 的 revision 是什么口径的计数器？

  • 每个键各自维护一份
  • 全库共用一个，单调递增
  • 每个租约单独维护一份

2. 默认的线性一致读，代价是什么？

  • 可能读到相对过时的数据
  • 每次读都会多落一次盘
  • 读之前要走一遍 Raft 共识流程

3. etcdctl compact 5 之后，etcdctl get --rev=4 键 会发生什么？

  • 返回 revision 4 当时的旧值
  • 报错：required revision has been compacted
  • 自动回落到返回最新值

4. learner（学习者）在集群里是什么角色？

  • 非投票成员，追平日志后转正
  • 永久只读副本，不能转正
  • 专门负责备份的节点

07思考题（点击展开解析）

思考一：写请求为什么必须"先记账（WAL）再落库"，顺序反过来会怎样？快照和 WAL 又是怎么配合的？

先看承诺：etcd 对 KV 接口的第一个保证是持久性（durability）——写入一旦向你确认，断电重启后必须还在。WAL（预写日志）就是这份承诺的兑现凭证：提案在应用到状态机之前先追加落盘，而且官方存储文件文档明确它是追加写——条目"不在原位覆盖，后写的同位条目取代前者"。反过来看"先改状态机再记账"的反事实方案：状态机改完、WAL 还没落盘的瞬间宕机，这条已经向客户端回过 OK 的写入就蒸发了——确认过的事没了下文，持久性承诺破产；而"先记账再落库"最坏情况只是"记了账还没应用"，重启后重放 WAL 补齐状态机，一切对得上。快照的角色是给重放一个起点：官方口径约每 10 万次已应用提案（--snapshot-count，默认 100'000）落一份快照文件，恢复时先加载快照、再重放其后的 WAL——没有快照，就要从开天辟地重放全部日志；没有 WAL，快照之后的新写入无从补齐。一个管"起点"，一个管"增量"，合起来才是完整的崩溃恢复。这套"预写日志 + 周期快照"的组合拳不是 etcd 独有，数据库、消息队列、共识系统里随处可见——理解一次，处处受益。

思考二：第 2 期那个单成员集群里，Raft 的四个角色都还在吗？谁来当 leader、多数派怎么算？

都在，一个不少。单成员集群也要走完整的协议流程：启动照样有选举，它自己当选 leader；写入照样生成提案、照样落 WAL、照样"复制到多数派"——只是多数派的定义是超过半数，1/1 也是多数派，所以确认退化成"自己点头"，延迟很小，但第 2 期思考一说过：共识协议的容错红利在这个形态里是零。follower 的戏份由谁接？没有别人，leader 身兼两角；learner 则完全没戏份——集群里只有它一个成员，谈不上"新成员追日志"。反过来做实验也行：单机上用 member add 加成员时，官方会提示用 --learner 让新成员先做旁听生——这正是 learner 机制存在的意义：扩容先追平再投票，别让一张新面孔拖垮表决。所以正确的理解是：单成员集群是共识机制的"教学沙盘"，四个角色、一条流水线全都在演，只是台下没有观众。

08本期要点与下期预告

带走这几条：

  • 十块积木：键值侧 revision / version / MVCC / watch / lease / compaction，共识侧 leader / follower / learner / log——revision 是全库一把的流水号，version 是每个键自己的计数；
  • 三层分工：API 层（gRPC 六服务）只管接待，Raft 共识层管点头（复制到多数派才算提交），存储层先记账（WAL 追加写）再落库（MVCC B+ 树）；
  • 一条写请求的旅程：put → 提案进 WAL → 多数派确认 → revision 加一写进 B+ 树 → 回 OK → watch 按 revision 派发事件；
  • 两个反直觉：读可以不走共识（serializable 换性能，可能读旧）；revision 全局单调，才养得起 watch 排队与 --rev 时间旅行；
  • 仓库地图：api/ 是契约，server/ 是主体，etcdctl/etcdutl 是命令行双工具，Raft 本体在独立仓库 etcd-io/raft。
