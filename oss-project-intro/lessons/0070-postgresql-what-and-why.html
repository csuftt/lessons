OSS PROJECT INTRO · POSTGRESQL 系列第 1 期：认识项目

PostgreSQL 是什么：35 年老将，凭什么号称最先进的关系数据库

今天开启新项目 PostgreSQL——官网自述 The World's Most Advanced Open Source Relational Database，世界上最先进的开源关系数据库。MySQL 之外，它是关系库世界的另一极：35 年持续演进、每年一个主版本的社区纪律，以及一套"内核管标准、扩展管特长"的开放架构——装上 pgvector 它就是向量库，装上 PostGIS 它就是地理库，装上 TimescaleDB 它就是时序库。一句话心智模型：PostgreSQL 是一台"标准 SQL 完全体"打底、什么特长都能外挂的数据库底座。本期结束，你能答上四个问题：它是什么、凭什么说"最先进"、与 MySQL 的生态位怎么分、什么信号出现时该把它请进你的架构。

01痛点：MySQL 之外，那些"外挂拼图"的时刻

大多数后端工程师的关系数据库第一课是 MySQL，这没有问题——直到某天需求开始"越界"：业务要存灵活多变的 JSON 文档、要做全文检索、要按经纬度算附近五公里、AI 应用要把向量存进库里做相似度检索。每一项在 MySQL 生态里的答案都是"再挂一个专用组件"：文档转 Es、全文检索上 Es、地理能力靠应用层算、向量检索再引一个专门的向量库。组件越挂越多，数据同步链越来越长，一致性、运维面、故障定位都在为"拼图式架构"付利息。

还有一条更行业级的信号：数据库国产化与去 Oracle 运动里，大量国产数据库选择以 PostgreSQL 为底座二次开发——读得懂 PG 的源码与术语，你就拿到了理解这一整层国产数据库生态的钥匙。于是"要不要认真看看 PG"不再是兴趣问题，而是架构师知识结构的补全问题。

02是什么：官方定位与一句话心智模型

PostgreSQL 是一个开源的对象-关系型数据库管理系统：C 语言编写，PostgreSQL License（BSD 系宽松许可，商用无负担），1986 年从 Berkeley 的 POSTGRES 项目起步，官方口径"超过 35 年的持续活跃开发"。它由 PostgreSQL Global Development Group——一个由多家公司和个人贡献者组成的社区——开发维护，不隶属于任何单一商业公司，这在全球主流数据库里相当罕见：Oracle 是 Oracle 的，SQL Server 是微软的，而 PostgreSQL 是社区的吗哪。

一句话心智模型：标准 SQL 的完全体，加上一套开放到"能自己造数据类型"的扩展系统。前者指它对 SQL 标准的实现深度常年领先——窗口函数、CTE、事务内 DDL（建表改表可回滚）、丰富的隔离级别；后者指它的扩展机制（CREATE EXTENSION）允许第三方把新类型、新函数、新索引方法挂进内核，内核不必为每个热点需求改代码。官方那句"最先进"，底气就来自这两件事的乘积。

来源注记——postgresql.org 首页（2026-09-30 核对）：slogan "The World's Most Advanced Open Source Relational Database" · "over 35 years of active development" · 当前稳定版 18.6；GitHub postgres/postgres 仓库（2026-09-30 核对）：Star 约 22.2k · Fork 约 5.9k · 主语言 C——主仓库星数不高是常态，用户流量在官网与各发行版渠道。

03心智模型：内核管标准，扩展管特长

这张图是理解 PG 生态的钥匙：内核层守着 SQL 标准与事务、存储这些地基，演进克制而稳定；扩展层是自由的——pgvector 让它长出向量检索，PostGIS 让它长出地理能力，TimescaleDB 让它长出时序分片，装上什么它就是什么；衍生层则直接复用源码，分析型 MPP 数据库与大量国产数据库都在这层。你在第 01 节感到的"拼图之痛"，在这里的答案就是：数据不动，能力挂载。

04用起来的样子：三步尝鲜链

先看清形状，第 2 期再亲手跑。下面三步对照官网 Download 页与官方文档口径（postgresql.org，2026-09-30 核对）。

第一步，安装——三大平台各有官方推荐：macOS 用 Homebrew 或 Postgres.app，Windows 用 EDB 安装器，Linux 配 PGDG 官方软件仓库后一条包管理命令装最新版：

# macOS（Homebrew）
brew install postgresql@18
# Debian/Ubuntu（先配 PGDG 仓库，详见第 2 期）
sudo apt install postgresql-18

第二步，连上它——psql 是官方命令行客户端，装完服务即自动初始化一个本地实例，进交互终端一条命令：

psql -U postgres
# 提示符变成 postgres=#，\l 列数据库、\dt 列表、\q 退出

第三步，跑一句 SQL——建表、插入、查询，顺手体验一个 MySQL 没有的细节：DDL 也在事务里，可以回滚：

CREATE TABLE hello (id serial, name text);
BEGIN;
ALTER TABLE hello ADD COLUMN memo text;  -- 改表
ROLLBACK;                                 -- 改表也回去了
\d hello                                  -- 表结构里没有 memo

来源注记——postgresql.org/download（2026-09-30 核对）：macOS 推荐 Homebrew 与 Postgres.app，Windows 推荐 EDB 安装器，Linux 走各发行版 PGDG 仓库；psql 元命令 \l \dt \d \q 见官方文档 Reference → psql 一章。

05版本口径：一年一版，五年维护线

PG 的版本纪律在开源数据库里堪称楷模：每年 9 月发一个主版本，每个主版本维护约 5 年。以 2026-09-30 官网口径为准，当前同时维护五条线：

版本线当前小版定位
PostgreSQL 1818.6（2026-08-13）最新稳定线，新项目首选
PostgreSQL 17 / 16 / 1517.11 / 16.15 / 15.19存量主力，持续收安全补丁
PostgreSQL 1414.242026-11-12 停止维护，存量需规划升级
PostgreSQL 19Beta 4（2026-09-24）测试中，勿上生产

PG 18 这条线有几个值得架构师记住的看点：异步 I/O（AIO）——读操作可以并行发出而不必排队，I/O 密集负载（大扫描）吞吐提升明显；UUIDv7——时间有序 UUID，索引页分裂与 WAL 写入更少，高写入场景友好；虚拟生成列——读取时才计算、不占存储；Skip Scan——多列索引前导列不在条件里也能用索引；pg_upgrade --swap——大版本升级的停机窗口大幅缩短。一句话：性能、索引、升级三条线都有硬货。

来源注记——postgresql.org 首页版本公告区与 About → Feature Matrix（2026-09-30 核对）：18.6/17.11/16.15/15.19/14.24 同日更新（2026-08-13）；PG 19 Beta 4 发布于 2026-09-24；PG 14 EOL 日期 2026-11-12；AIO/UUIDv7/虚拟生成列/Skip Scan/pg_upgrade --swap 均见官方 Feature Matrix 18 筛选结果。

06扩展生态：一个内核，长出一片数据库

PG 最与众不同的资产是扩展生态。机制上，CREATE EXTENSION 一条命令把第三方包的能力挂进当前库——新数据类型、新函数、新索引方法、新语言过程调用都可以。几个改变数据库形态的代表：

  • pgvector：向量类型与相似度检索，AI 应用的向量存储直接长在主库里，不必另起一套向量数据库——这是这两年 PG 热度回升的最大引擎之一；
  • PostGIS：空间数据类型与空间索引，地理围栏、附近检索的行业标准方案；
  • TimescaleDB：时序数据自动分片与压缩，物联网与监控场景不用专门引时序库；
  • pg_trgm / pg_stat_statements：模糊检索与 SQL 性能统计，一个管搜索一个管调优，都是日常刚需。

再往外一层是源码级衍生：分析型 MPP 数据库用 PG 做 SQL 前端与执行层（如 Greenplum），国产数据库大量以 PG 为底座起步。这就是第 03 节那张图的外圈——读懂 PG，等于半只脚迈进这一整层生态的门。

来源注记——扩展清单与文档入口见 postgresql.org/docs 当前版 Extensions 章节；pgvector/PostGIS/TimescaleDB 各自官方文档（2026-09-30 可访问）。

07与 MySQL 怎么选：生态位对比，不吹不黑

架构师最关心的问题。两门数据库都是久经考验的生产级选择，生态位差异远大于"谁更强"：

维度PostgreSQLMySQL
SQL 标准与功能纵深实现更深：事务内 DDL、窗口函数与 CDD 丰富、自定义类型常用够用，深度功能历史包袱多
JSON 文档jsonb 二进制存储 + GIN 索引，文档查询是一等公民JSON 函数可用，索引与优化深度弱一档
扩展生态向量/地理/时序一库全挂，数据不出库生态倾向"专用组件拼图"
复制与高可用流复制 + 逻辑复制，生态方案多主从复制成熟，运维心智模型普及度更高
国内人才与存量增长快，DBA 储备相对少存量巨大，招聘与运维经验最普及

选型口径一句话：常规业务表 + 团队 MySQL 经验深，MySQL 依然是稳的；一旦数据形态多元（文档 + 向量 + 地理 + 时序交叠）、或要在库内做复杂分析型查询，PG 的"一库多能"开始兑现复利。另一个务实视角：新项目用 PG 的试错成本很低（云厂商全部标配托管版），而它省下的是第 01 节那些拼图组件的运维面。

08架构师视角：PG 化趋势与"要不要动"的决策框架

把镜头拉远：全球云厂商全部提供 PG 托管产品，国产数据库以 PG 为底座者众多，AI 时代 pgvector 把"向量存主库"变成默认选项——PG 化是趋势，但趋势不等于你该连夜迁移。给一个三问决策框架：

  • 数据形态问：新业务的数据是不是"表 + JSON + 向量"混合？是 → PG 的收益从第一天就开始计；纯关系 CRUD → 两者差异小，团队熟悉度优先；
  • 拼图利息问：现有架构里为搜索/向量/地理挂了几个专用组件？同步链路和一致性成本是否已经在痛？痛 → 把这些能力收回主库是减法；
  • 团队能力问：有没有人愿意吃透 PG 的运维差异（连接模型、vacuum、复制拓扑）？没有 → 从托管版 + 非核心业务试点，别裸奔上生产。

09随堂小测

每题点击选项立即反馈 · 共 3 题

1. PostgreSQL 的开发维护模式是？

  • 由 Oracle 公司主导开发
  • 由社区 PostgreSQL Global Development Group 开发，不隶属单一公司
  • 已停止维护，只剩商业发行版在更新

2. PostgreSQL 18 的异步 I/O（AIO）主要解决什么问题？

  • I/O 密集型负载里多个 I/O 请求并行发出，不再逐个排队等待
  • 让数据库写入不需要权限校验，加速写路径
  • 让大版本升级不用停机

3. 团队要在库里做 AI 应用的向量相似度检索，PG 生态的做法是？

  • 把 PG 改造成文档数据库再存向量
  • fork 源码自己加向量功能
  • CREATE EXTENSION 挂载 pgvector，主库直接长出向量检索能力

10思考题（点击展开解析）

思考一：PG 把"标准 SQL 做深"留给内核、把"特长能力"开放给扩展，这种分层演进的好处和代价各是什么？

好处有三。第一，内核稳。热点需求（向量、地理、时序）不必都挤进内核主线，内核保持克制演进，35 年每年一版的纪律才守得住；对用户来说升级内核不会因为某个"特长功能"被连带重构。第二，生态快。扩展各自按自己的节奏发版，pgvector 赶上 AI 浪潮的速度远快于任何数据库内核吸纳一个新特性的速度——市场验证过的能力留下来了，没人用的自然淘汰，这是一场分布式的试错。第三，用户省。能力挂载不动数据、不加同步链路，"拼图利息"从根上省掉。代价也真实存在：扩展质量参差，索引、并发、崩溃恢复这些深水行为由扩展作者各自负责，选扩展要看社区活跃度与生产案例；版本耦合，主版本升级时扩展兼容性是额外检查项；能力组合的边界模糊，多个扩展叠用的性能行为需要自己压测。分层不是免费的，它是把"集成风险"从内核团队转移到了选型架构师手上——这也是为什么扩展生态的选型本身就是架构工作。

思考二：存量业务全在 MySQL 上，新起一个"商品中心"服务（表 + 商品详情 JSON + 向量化商品描述检索），数据库怎么选？给出决策链。

按"数据形态 → 团队能力 → 运维成本 → 回退路径"四步走。第一步，数据形态定候选。这个服务的三份数据里有两份是 PG 的甜点：JSON 详情走 jsonb + GIN 索引是成熟打法，向量检索挂 pgvector 即可；MySQL 路线则要主库 + 搜索引擎 + 向量库三件套拼图，同步链路和一致性都是长期利息。候选倾向 PG。第二步，能力盘点。团队有没有人懂 PG 的连接模型（进程型、连接池几乎必配 pgbouncer）、vacuum 机制、基础调优？有 → 放心选；没有 → 选托管版（云厂商标配）把运维差异兜住，同时指定一人吃透。第三步，成本对账。PG 单库方案的省项：少两个组件的部署监控、少两条同步链路、少一类一致性故障；付项：团队学习成本、与存量 MySQL 运维体系并行的一套心智。第四步，回退路径。商品中心这类新服务天然独立，选错了代价是"一个服务换库"而不是"全公司换库"——正因为回退成本可控，新服务正是试 PG 的正确切口。结论通常是：数据形态收益明确 + 托管版兜住运维 + 服务边界可控，PG 值得上；反过来若团队极度缺人、需求又急着上，MySQL + 成熟拼图也不是耻辱选项——架构决策比的是总成本，不是技术先进性。

11本期要点与下期预告

带走这五句话：

  • PostgreSQL = 35 年社区维护的开源关系库（基准 v18.6，2026-08-13），官网自述"世界上最先进的开源关系数据库"；
  • 心智模型：标准 SQL 完全体打底 + 开放扩展系统外挂特长——pgvector 是向量库、PostGIS 是地理库、TimescaleDB 是时序库，数据不出库；
  • 版本纪律：每年 9 月一个主版本、每版维护约 5 年；PG 18 看点：异步 I/O、UUIDv7、虚拟生成列、Skip Scan、pg_upgrade --swap；
  • 选型边界：纯关系常规业务 MySQL 稳、数据形态多元时 PG 复利兑现，新服务是试 PG 的最佳切口；
  • PG 化是趋势但不等于连夜迁移：数据形态、拼图利息、团队能力三问之后再动。
