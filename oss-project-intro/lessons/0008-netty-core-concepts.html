OSS PROJECT INTRO · Netty 系列第 3 期：核心概念与整体架构

Netty 核心概念与整体架构：五块积木与一次数据的旅程

上一期我们用二十来行代码跑通了 Echo Server，但那二十行里其实埋着 Netty 的全部主角：两个 EventLoopGroup、一条 ChannelPipeline、一串 ChannelHandler、还有 channelRead 里接住的 ByteBuf。这一期把它们一个个请出来：Channel 是连接、EventLoop 是工人、Pipeline 是流水线、Handler 是工序、ByteBuf 是集装箱——五大概念配类比和一句话定义，一张自绘整体架构图看懂 boss 与 worker 的交接，再跟着一条数据从网卡走到业务再写回网卡。最后附上源码仓库的顶层模块地图。读完这一期，Netty 对你就不再是一堆模糊的类名。

01上一期的 Echo 代码，其实已经用全了五个概念

回看第 2 期那段 Echo Server，它就是今天整期内容的预告片：

  • 两个 EventLoopGroup：boss 负责接连接，worker 负责处理连接上的读写——工人团队的分工；
  • 传给 childHandler 的 ChannelInitializer：往这条连接的 ChannelPipeline 里铺工序；
  • channelRead 里接住的 msg：一个 ByteBuf，装着刚从网卡读进来的字节。

上一期的目标是"跑起来"，这一期的目标是"看明白"。用户视角的 Netty 核心，说穿了就是五个名词：Channel、EventLoop（与 EventLoopGroup）、ChannelHandler、ChannelPipeline、ByteBuf。后面不管你写 HTTP 服务器还是自定义协议服务器，本质都是在组合这五块积木。

02五块积木：类比 + 一句话定义 + 关键点

① Channel——一条拨通的电话线

一句话定义：网络连接的抽象，读、写、连接、绑定等 I/O 操作的"总枢纽"（官方 javadoc：a nexus to a network socket）。

  • 比 JDK Socket 多了状态（open / active / closed）与统一的异步操作：所有操作立刻返回 ChannelFuture，完成时回调；
  • 一条连接对应一个 Channel，它自带一条 Pipeline，并终身注册在一个 EventLoop 上。

② EventLoop / EventLoopGroup——一工人一线程一 Selector

一句话定义：事件循环——一个 EventLoop 就是一个线程加一个事件分发器，不停轮询"我名下的连接谁来事件了"；Group 是这支队伍。

  • 官方 javadoc 的说法：EventLoop "will handle all the I/O operations for a Channel once registered"——注册之后，这个连接的所有 I/O 都归它；
  • 连接终身绑定一个 worker：同一个连接的事件永远由同一线程串行处理，因此 handler 里不需要加锁——串行无锁的关键；
  • boss 只管 accept 新连接，注册完就撒手，读写全是 worker 的事。

③ ChannelHandler——一道工序

一句话定义：处理或拦截 I/O 事件的处理单元，业务逻辑就写在这里。

  • 分入站（ChannelInboundHandler：收到数据、连接激活）、出站（ChannelOutboundHandler：写出、绑定）和双工三类；
  • 常见角色：解码器、编码器、业务处理器，以及官方内置的空闲检测、日志等；
  • 约定俗成的责任：消费掉的消息要释放引用、要转发就显式调 ctx.fireChannelRead()。

④ ChannelPipeline——双向流水线

一句话定义：每个 Channel 自带一条 handler 链，入站事件与出站操作在链上沿相反方向传播。

  • 入站（读到的数据）：从靠近socket的 head 出发，按添加顺序一站站传向 tail；
  • 出站（写操作）：从 tail 一侧出发，按相反顺序流回 head，由 head 真正落到网络；
  • 运行期可动态增删 handler——发敏感数据前插一个 SSL handler，发完再摘掉。

⑤ ByteBuf——集装箱（读写双指针）

一句话定义：字节容器，用独立的读、写两个指针管理数据，替代 java.nio.ByteBuffer。

  • JDK ByteBuffer 只有一个 position，读写切换必须手工 flip()，忘一次就翻车；ByteBuf 读写指针各管各的，永远不需要 flip；
  • 池化：默认从池化分配器取缓冲区（PooledByteBufAllocator），配引用计数（refCnt）显式回收；
  • 支持堆内/堆外、按需扩容，以及 slice / composite 视图组合——零拷贝的基础。

版本备注以上概念与官方表述已对照 Netty 4.2 用户指南与 javadoc 核对（2026-09-18）。4.1 与 4.2 两条稳定线在这些用户级概念上基本一致，4.x 老资料仍然适用。

03整体架构：一次连接的交接仪式

五块积木拼起来的全景如下。读图三句话：boss 接连接、worker 管连接、pipeline 承载连接上的一切事件。虚线是"注册/绑定"关系，实线是数据流向。

交接仪式分两步：第一步，客户端发起 TCP 连接，boss 的事件循环发现 accept 就绪，创建对应的 Channel，并把它注册到 worker 组里的某个 EventLoop 上——从这一刻起，这条连接终身归这个工人管，boss 不再过问；第二步，这条连接后续所有的读写事件，都由绑定的 worker 从事件循环中拿出来，沿着它的 Pipeline 传播处理。图里 EventLoop 名下的 Channel 小方块就是"终身绑定"的样子：每个工人名下挂一批连接，互不越界。

04叙事主线：一条数据的旅程

概念讲完了，现在用一条数据把它们串起来。假设客户端发来一句 "hello"，Echo Server 要把它原样送回去：

  1. 字节到达。网卡收到数据，内核把它放进这条 TCP 连接的接收缓冲区——注意，TCP 给你的是一串没有边界感的字节流，"一条消息"的边界要由你自己定义；
  2. EventLoop 醒来。这条连接绑定的 worker EventLoop 正在轮询自己名下的事件，发现"这条 Channel 可读了"，就把字节读进一个池化的 ByteBuf（集装箱在这一步装货）；
  3. 入站传播。EventLoop 从 Pipeline 的 head 触发 channelRead，事件像零件上流水线一样按添加顺序过站：解码器先把字节流切出完整的帧（这就是上一期说的"拆包粘包"要处理的事），再交到下一站；
  4. 业务 handler。拿到解码后的完整消息，执行你的业务逻辑。Echo 的逻辑就一句：ctx.writeAndFlush(msg)——把货发回去；
  5. 出站回程。这次写从 tail 一侧反向出发：编码器把消息转回字节，装进 ByteBuf，流到 head 由它真正写到网络；
  6. 异步收尾。writeAndFlush 立刻返回一个 ChannelFuture，写完成的回调在 listener 里触发——想"发完再关连接"，逻辑就写在那里。

走完这一圈你会发现：一条数据的旅程，恰好把五大概念各用了一次——Channel 提供连接与操作、EventLoop 驱动整个旅程、Pipeline 规定路线、Handler 是沿途站点、ByteBuf 是全程的载具。以后看任何 Netty 代码，先在心里把这条路线画出来，类名就都有位置了。

07思考题（点击展开解析）

思考一：为什么连接"绑死"一个 EventLoop 反而更快？多线程不是万能答案吗？

直觉上，谁空闲谁处理似乎更"充分利用"线程，但那套方案（类似传统线程池 per-request 模型）有三笔隐性开销：锁竞争（同一条连接的缓冲区、handler 状态被多线程碰，处处加锁）、上下文切换（任务在线程间倒手，缓存与栈帧反复重建）、顺序难题（两条消息可能被并发处理，想保序就得引入队列与同步）。而"终身绑定一个工人"一次性解决了三件事：单线程串行执行，所有共享状态天然无锁；事件的处理顺序等于到达顺序，免费获得；同一个工人反复摸同一条连接的缓冲区，CPU 缓存局部性更好。线程模型从"多条线程抢一份状态"变成"一条线程独占一批连接"，吞吐反而上去——这正是 Netty 高性能的第一块基石。当然它有代价：一个 EventLoop 名下的所有连接共享这条线程，任何阻塞调用（JDBC、sleep、重计算）都会拖死一整批连接，所以铁律是"EventLoop 上不阻塞"，重逻辑丢给业务线程池，算完再调 write 写回——那一步是线程安全的，因为写操作会被提交回这条连接绑定的 EventLoop 执行。

思考二：为什么 ByteBuf 必须手动 release，而不能像普通 Java 对象一样交给 GC？

因为池化 + 堆外这两件事都超出了 GC 的管辖范围。堆外内存 GC 看不见，不回收；而池化的意义在于"用完还回池子"，可 GC 根本不知道"什么时候算用完"。所以 Netty 用引用计数（refCnt）手工管理生命周期：谁最后用完，谁负责 release，归零时堆外内存被释放、缓冲区被还回池子。配套的是几条约定：写出到网络的消息，Netty 在写完时替你 release；你自己消费（比如解码后丢弃）或传递的消息，需要你自己释放；忘了释放的入站消息漂到 tail 时会被记日志，ResourceLeakDetector 还会采样报告泄漏——这也是初学者最常撞的坑（典型症状：日志里出现 LEAK 警告）。反观 JDK ByteBuffer：默认堆内、不池化，可以偷懒全交给 GC，代价是高并发下频繁分配带来的 GC 压力。本质上，Netty 是用"手工生命周期"换"性能"，再把这份手工成本尽量放在框架能代劳的边界上——理解了这层取舍，引用计数就不再是玄学。

08本期要点与下期预告

带走这三句话：

  • 五块积木：Channel 是连接、EventLoop 是工人、Pipeline 是流水线、Handler 是工序、ByteBuf 是集装箱；
  • 一条铁律：连接终身绑定一个 EventLoop，单线程串行、无锁——代价是 EventLoop 上不能阻塞；
  • 两个方向：入站 head → tail 按添加顺序，出站 tail → head 反向回流；ByteBuf 读写双指针、池化加引用计数。
